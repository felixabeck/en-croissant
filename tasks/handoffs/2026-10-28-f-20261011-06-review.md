## Decided autonomously (record through `findings.py record-decision` on adoption, not in this PLAN-ONLY run)

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `publications` counts threads inside `open`/`write`/`fchmod`/`close`. `forks` counts prepare handlers that have not finished the matching parent handler. The publisher allocates before the section and does not fork or allocate inside it. Every in-process write of an inode this process later execs uses that section.

Rejected: temp-name plus rename (ETXTBSY remains while the write fd is open); one shared immutable runner plus a per-test body file (Linux execs `/proc/self/fd/N`); retry, sleep, or a process-wide `Command` lock (d-20261014-18, and the lock would miss `native_lock_is_held`); production argument plumbing; reopening the `/bin/cat` fixtures (d-20261014-18 supersedes d-20261014-17).

Reversal: replace this barrier only with a measured mechanism that closes the parent-held write fd and the `libc::fork` inheritance window for every exec'd fixture inode, keeps the cat fixtures and the held-writer witness, and does not change production spawn.

Question: does `d-20261028-05`'s macOS private `/bin/cat` copy stay outside the publication barrier?

Chosen: no. Read `/bin/cat` before the section and publish those bytes with `publish_test_executable` at mode `0o755`. Keep a distinct `stdin-waiting-cat` per fixture directory. Linux observer tests stay on canonical `/bin/cat`.

Rejected: leaving `std::fs::copy` because a shebang audit cannot see it; reverting the two tests to one shared `/bin/cat` open; a script written in the test and then executed.

Reason: `std::fs::copy` holds a destination write fd until it returns. The drift added this producer after the shebang audit was closed. `d-20261028-05` keeps the private command target and does not close f-20261011-06.

Question: which Cargo target runs the Phase 1 proof?

Chosen: `cargo test --manifest-path src-tauri/Cargo.toml --bin chessfable`. One filter substring per invocation.

Rejected: `--lib`. This package has no library target, so those commands fail before any test runs.

Reason: `cargo metadata --no-deps` lists only the `chessfable` binary (`src/main.rs`) and the build script. The renamed-database handoff in the drift records the same fact.

## Threat model and non-goals

Adversary and environment, frozen for round 1: one `cargo test` process, tests running in parallel on several threads (stated in `src-tauri/src/infra/test_hooks.rs`). A thread writes a file this process will later `execve`. Before that write descriptor is closed, another thread in the same process calls `libc::fork`. The child inherits the write descriptor. `execve` of that inode then returns ETXTBSY until every writer, including the child, has closed it. The observed failure is Linux CI. This is not a remote attacker and not a cross-process attacker.

## Approach

### Publication barrier

Add `src-tauri/src/infra/test_executable.rs`, declared `#[cfg(test)] pub(crate) mod test_executable;` from `src-tauri/src/infra/mod.rs`. Do not put it in `test_hooks.rs`. That module is the keyed one-shot hook table.

The public function is `publish_test_executable(path, bytes, mode) -> io::Result<()>`. It is `cfg(test)` and compiled for Unix only. Windows call sites stay on their current writes. There is no public closure that runs caller code while the barrier is held.

One process-wide counter (`AtomicUsize`) counts in-flight publications. The first call installs a `pthread_atfork` prepare handler exactly once. The handler loads the counter and, while it is non-zero, calls `sched_yield`. It allocates nothing and takes no lock. If `pthread_atfork` fails, publication returns that error and does not write. There is no unguarded fallback.

The caller-facing function allocates the path `CString` and copies `bytes` before it increments the counter. Inside the section the only operations are `open` (`O_CREAT | O_WRONLY | O_TRUNC | O_CLOEXEC`), `write` of the prepared bytes, `fchmod` to `mode as libc::c_uint`, and `close`. A short write or any syscall error closes the fd, drops the guard, and returns the error. The guard decrements on drop, including panic. The final path is written in place. A rename does not clear ETXTBSY while a write fd is open, so the helper does not rename.

The publisher does not call `libc::fork` and does not call `malloc` while the counter is held. A same-thread `libc::fork` during the section would deadlock, because the prepare handler waits for a counter that thread owns. Nested publication is allowed: the counter is a count, not a flag. Callers use the function and do not hold the section themselves.

Registering the handler on first publication, after process start, is what POSIX describes as running before earlier handlers. This plan does not treat that order as something the local machine proved. The no-allocation rule is what keeps a forker that spins in the prepare handler from deadlocking against this publisher.

### Which writers go through it

Every Unix test path that this process writes and then `execve`s goes through `publish_test_executable` before any later `chmod` or spawn. "Execs" means the written inode is the `execve` target: `Command::new` of that path, `EngineExecutable::test_fixture` followed by spawn, or an equivalent spawn. The mode argument is the mode the test needs at the end of publication, including `0o700` and the macOS materialized-mode case that uses a different mode. Call sites drop the separate `set_permissions` on that executable so the mode change is not repeated outside the barrier.

Direct `std::fs::write` of those scripts is replaced by the helper. Non-exec bytes in the same test (resource files, logs, the `exit 22` replacements) stay ordinary writes.

For `extract_zip` / gzip-tar extraction, the test cannot replace the writer without missing the window: the write fd exists inside the extractor. The Unix `cfg(test)` write of a regular payload file that a test in this change execs must perform its `open`/`write`/`fchmod`/`close` inside the same section, after the bytes are already buffered and after directory creation has finished. The counter is not held across zip parsing, directory walks, or any other allocating work. Non-test extraction, the `0o600` extraction mode, and the later registration that adds the execute bit stay as they are. `installed_engine_archive_registration_makes_payload_executable` still observes `0o600` before registration and a successful exec after it. If a payload write cannot be separated from allocation that way, the executor stops and reports. It does not wrap `extract_zip` in the counter.

The executor applies this rule to every shebang site in the traced inventory, including sites this plan did not open line by line. A site that execs the written inode and is left on `std::fs::write` is a missed fix. A site in the traced out-of-class list that is migrated is a behavior change this plan does not allow.

### What stays

`stdin_waiting_executable` and its callers stay on `/bin/cat`. The held-writer witness stays a raw write that is left open, and it must still fail with ETXTBSY while that fd is open. `spawn_owned`, `pin_engine_launch`, and `native_lock_is_held` are not edited. No production argv, no spawn retry, no sleep, no process-wide `Command` lock.

### Deterministic proof

The proof is in `test_executable`, not a flaky full-suite rerun.

- A parent holds a script open for write. A raw `fork` child sleeps about 300 ms and `_exit`s. The parent closes its fd. `Command::new(script)` returns `ExecutableFileBusy` while that child is alive, and succeeds after the child has exited. This shows the kernel failure the barrier exists to close, without the publisher.
- A second thread blocks in the prepare handler while `publish_test_executable` is inside the syscall section. A counter the handler increments shows the forker entered before the section finished, and the child is created only after the section finishes. Exec of the published script then succeeds.
- When `pthread_atfork` cannot be installed, publication returns the error and leaves the path unwritten.
- The cat fixtures and the held-writer witness still pass, and the witness still sees ETXTBSY on the held script.

## Decisions and trade-offs

### Decided autonomously

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `pthread_atfork` prepare handler spins while a count of in-flight publications is non-zero. The publication itself is `open`/`write`/`fchmod`/`close` with no allocation and no fork. Every in-process write of an inode this process later execs uses that helper.

Rejected:

- Write to a temp name, close, and rename into place. Measured: ETXTBSY remains while the write fd is open. Rename does not drop that fd.
- One shared immutable runner plus a per-test body file. Linux execs `/proc/self/fd/N`, so `$0` is not the script name, and two engines share a working directory. A chmod of a hardlink would also change the shared inode.

## Approach

### Publication barrier

Add `src-tauri/src/infra/test_executable.rs`, declared `#[cfg(test)] pub(crate) mod test_executable;` from `src-tauri/src/infra/mod.rs`. Do not put it in `test_hooks.rs`. That module is the keyed one-shot hook table.

The public function is `publish_test_executable(path, bytes, mode) -> io::Result<()>`. It is `cfg(test)` and compiled for Unix only. Windows call sites stay on their current writes. There is no public closure that runs caller code while the barrier is held.

Two process-wide atomics coordinate publication with `libc::fork`. `publications` counts threads inside the syscall section. `fork_active` is set by the prepare handler and cleared by the parent handler and the child handler. Every load, store, and `fetch_add` on these two atomics uses `Ordering::SeqCst`. A weaker ordering does not implement the exclusion: a relaxed increment can stay invisible to the prepare spin while a relaxed `fork_active` store stays invisible to the publisher's second check. The first publication installs all three `pthread_atfork` handlers exactly once. If installation fails, publication returns that error and does not write. There is no unguarded fallback. The handlers allocate nothing and take no lock.

A publisher allocates the path `CString` and copies `bytes` before it enters the section. It then waits while `fork_active` is set. It increments `publications`, checks `fork_active` again, and if a fork became active it decrements and retries. Only after that second check does it run `open` (`O_CREAT | O_WRONLY | O_TRUNC | O_CLOEXEC`), `write` of the prepared bytes, `fchmod(fd, mode as libc::mode_t)`, and `close`. A short write or any syscall error closes the fd, drops the section count, and returns the error. The count drops on panic too. The final path is written in place. A rename does not clear ETXTBSY while a write fd is open, so the helper does not rename.

`fchmod` takes `libc::mode_t`. On macOS that type is `u16` (docs.rs `libc` 0.2.177, `aarch64-apple-darwin`: `pub type mode_t = u16`, and `fchmod` takes `mode_t`). Casting the mode to `libc::c_uint` (`u32`) does not compile there. The variadic `open` mode argument, where this crate already passes one, stays `as libc::c_uint` (`src-tauri/src/db/bound_sqlite.rs:1307`).

The prepare handler stores `fork_active`, then waits until `publications` is zero, then returns. A publisher that passed the first check and then sees `fork_active` leaves the section before `open`. A publisher that has not entered waits. The fork therefore cannot inherit a publication write fd. The parent handler clears `fork_active` only after `fork` has returned, so publication may open the file only once the child's descriptor table is already fixed. The child handler clears the child's copy so the child is not stuck excluded.

The publisher does not call `libc::fork` and does not call `malloc` while `publications` is non-zero for that thread. A same-thread `libc::fork` during the section deadlocks, because prepare waits for a count that thread holds. Nested publication is allowed. Callers use the function and do not hold the section themselves. `Command::spawn` with `pre_exec` takes this fork path, so the same handlers cover production engine spawn and `native_lock_is_held`.

### Which writers go through it

Every Unix test path that this process writes and then `execve`s goes through `publish_test_executable` before any later `chmod` or spawn. "Execs" means the written inode is the `execve` target: `Command::new` of that path, `EngineExecutable::test_fixture` followed by spawn, or an equivalent spawn. The mode argument is the mode the test needs at the end of publication, including `0o700` and the macOS materialized-mode case that uses a different mode. Call sites drop the separate `set_permissions` on that executable so the mode change is not repeated outside the barrier.

Direct `std::fs::write` of those scripts is replaced by the helper. Non-exec bytes in the same test (resource files, logs, the `exit 22` replacements) stay ordinary writes.

For `extract_zip` / gzip-tar extraction, the test cannot replace the writer without missing the window: the write fd exists inside the extractor. The Unix `cfg(test)` write of a regular payload file that a test in this change execs must perform its `open`/`write`/`fchmod`/`close` inside the same section, after the bytes are already buffered and after directory creation has finished. The counter is not held across zip parsing, directory walks, or any other allocating work. Non-test extraction, the `0o600` extraction mode, and the later registration that adds the execute bit stay as they are. `installed_engine_archive_registration_makes_payload_executable` still observes `0o600` before registration and a successful exec after it. If a payload write cannot be separated from allocation that way, the executor stops and reports. It does not wrap `extract_zip` in the counter.

The executor applies this rule to every shebang site in the traced inventory, including sites this plan did not open line by line. A site that execs the written inode and is left on `std::fs::write` is a missed fix. A site in the traced out-of-class list that is migrated is a behavior change this plan does not allow.

### What stays

`stdin_waiting_executable` and its callers stay on `/bin/cat`. The held-writer witness stays a raw write that is left open, and it must still fail with ETXTBSY while that fd is open. `spawn_owned`, `pin_engine_launch`, and `native_lock_is_held` are not edited. No production argv, no spawn retry, no sleep, no process-wide `Command` lock.

### Deterministic proof

The proof is in `test_executable`, not a flaky full-suite rerun.

- A parent holds a script open for write, outside the publisher. A raw `fork` child sleeps about 300 ms and `_exit`s. The parent closes its fd. `Command::new(script)` returns `ExecutableFileBusy` while that child is alive, and succeeds after the child has exited. This shows the kernel failure without the publisher.
- Publication-first: a forker blocks in the prepare handler while `publish_test_executable` is inside the syscall section. The forker has entered before the section finishes, and the child is created only after the section finishes. Exec of the published script then succeeds.
- Fork-first: the prepare handler has stored `fork_active`, observed `publications == 0`, and is held before it returns. A concurrent `publish_test_executable` must not create or open the target while that hold lasts. After the hold is released, `fork` completes, the child stays alive, publication finishes, and exec of the published script succeeds while that child is alive. A barrier that only waits for the counter and then returns fails this test, because publication can open the write fd before `fork` and the child inherits it.
- The same fork-first hold drives the `cfg(test)` extraction payload writer, not only `publish_test_executable`. Removing the publication section from either producer fails that producer's assertion.
- A test in `test_executable` fails if an in-class file still passes a `#!/bin/sh` literal to `std::fs::write`, `fs::write`, or an equivalent direct write of the exec inode, except the traced exclusions: the held-writer witness, the non-exec `exit 22` replacements, `terminal_snapshot_production_child_broken_pipe_keeps_unread_reason`, archive payload constructors that do not exec, and `inherited_descriptors_cover_every_resource_lease_and_the_engine_image`. Reverting a migrated fixture writer to `std::fs::write` fails this test.
- When `pthread_atfork` cannot be installed, publication returns the error and leaves the path unwritten.
- The cat fixtures and the held-writer witness still pass, and the witness still sees ETXTBSY on the held script.

## Decisions and trade-offs

### Decided autonomously

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `publications` counts threads inside `open`/`write`/`fchmod`/`close`. `fork_active` excludes new publication from prepare until the parent handler runs after `fork` returns. The publisher allocates before the section and does not fork or allocate inside it. Every in-process write of an inode this process later execs uses that section.

Rejected:

- Write to a temp name, close, and rename into place. Measured: ETXTBSY remains while the write fd is open. Rename does not drop that fd.
- One shared immutable runner plus a per-test body file. Linux execs `/proc/self/fd/N`, so `$0` is not the script name, and two engines share a working directory. A chmod of a hardlink would also change the shared inode.
- Retry spawn on ETXTBSY, sleeps, or a process-wide lock around `Command::spawn`. `d-20261014-18` rejected startup retries, sleeps, and global spawn synchronization for the retention fixtures. On Rust 1.98, `Command` with `pre_exec` inherits the write fd during `pre_exec` (measured by `etxtbsy-during`). A lock around `Command::spawn` would still miss `native_lock_is_held`'s `libc::fork` and would serialize concurrency tests. The atfork barrier covers both fork sites.
- Production argument plumbing or a change to `spawn_owned`. `test_fixture`'s third argument is resource leases. `d-20261014-18` rejected that plumbing.
- Reopening the `/bin/cat` retention fixtures. `d-20261014-18` is in force. `d-20261014-17` is superseded by it.

Reversal: replace this barrier only with a measured mechanism that closes the parent-held write fd and the `libc::fork` inheritance window for every exec'd fixture inode, keeps the cat fixtures and the held-writer witness, and does not change production spawn. Record that as a new decision at adoption. This plan does not call `record-decision`.

## Approach

### Publication barrier

Add `src-tauri/src/infra/test_executable.rs`, declared `#[cfg(test)] pub(crate) mod test_executable;` from `src-tauri/src/infra/mod.rs`. Do not put it in `test_hooks.rs`. That module is the keyed one-shot hook table.

The public function is `publish_test_executable(path, bytes, mode) -> io::Result<()>`. It is `cfg(test)` and compiled for Unix only. Windows call sites stay on their current writes. There is no public closure that runs caller code while the barrier is held.

Two process-wide atomics coordinate publication with `libc::fork`. `publications` counts threads inside the syscall section. `forks` counts threads that have entered a prepare handler and have not yet finished the matching parent handler. Every load, store, `fetch_add`, and `fetch_sub` on these two atomics uses `Ordering::SeqCst`. A weaker ordering does not implement the exclusion. A boolean cleared by one parent handler does not either: two prepares can both observe zero publications, then one parent handler can clear the flag while the other thread has not yet entered `fork`. The first publication installs all three `pthread_atfork` handlers exactly once. If installation fails, publication returns that error and does not write. There is no unguarded fallback. The handlers allocate nothing and take no lock.

A publisher allocates the path `CString` and copies `bytes` before it enters the section. It then waits while `forks` is non-zero. It increments `publications`, checks `forks` again, and if a fork is in flight it decrements and retries. Only after that second check does it run `open` (`O_CREAT | O_WRONLY | O_TRUNC | O_CLOEXEC`), `write` of the prepared bytes, `fchmod(fd, mode as libc::mode_t)`, and `close`. A short write or any syscall error closes the fd, drops the section count, and returns the error. The count drops on panic too. The final path is written in place. A rename does not clear ETXTBSY while a write fd is open, so the helper does not rename.

`fchmod` takes `libc::mode_t`. On macOS that type is `u16` (docs.rs `libc` 0.2.177, `aarch64-apple-darwin`: `pub type mode_t = u16`, and `fchmod` takes `mode_t`). Casting the mode to `libc::c_uint` (`u32`) does not compile there. The variadic `open` mode argument, where this crate already passes one, stays `as libc::c_uint` (`src-tauri/src/db/bound_sqlite.rs:1307`).

The prepare handler increments `forks`, then waits until `publications` is zero, then returns. A publisher that passed the first check and then sees `forks` non-zero leaves the section before `open`. A publisher that has not entered waits. The parent handler decrements `forks` only after `fork` has returned. Publication stays excluded until every in-flight fork has decremented, so one completed fork cannot open the window for a fork that is still between prepare and `fork`. The child is the forking thread only. Its handler stores zero to both `forks` and `publications`, because counts copied from other parent threads would otherwise stick with no thread left to drop them. The child is not stuck excluded, and a later fork in that child does not spin on a stale publication count.

The publisher does not call `libc::fork` and does not call `malloc` while `publications` is non-zero for that thread. A same-thread `libc::fork` during the section deadlocks, because prepare waits for a count that thread holds. Nested publication is allowed. Callers use the function and do not hold the section themselves. `Command::spawn` with `pre_exec` takes this fork path, so the same handlers cover production engine spawn and `native_lock_is_held`.

### Which writers go through it

Every Unix test path that this process writes and then `execve`s goes through `publish_test_executable` before any later `chmod` or spawn. "Execs" means the written inode is the `execve` target: `Command::new` of that path, `EngineExecutable::test_fixture` followed by spawn, or an equivalent spawn. The mode argument is the mode the test needs at the end of publication, including `0o700` and the macOS materialized-mode case that uses a different mode. Call sites drop the separate `set_permissions` on that executable so the mode change is not repeated outside the barrier.

Direct `std::fs::write` of those scripts is replaced by the helper. Non-exec bytes in the same test (resource files, logs, the `exit 22` replacements) stay ordinary writes.

For `extract_zip` / gzip-tar extraction, the destination inode is opened in `prepare_zip_cancellable` and `prepare_tar_cancellable` (`src-tauri/src/fs.rs`) before `bounded_copy` streams the entry. `create_relative_regular` (`src-tauri/src/infra/fs.rs`) only creates that inode and returns the open file. It never sees the payload bytes, so it cannot buffer first. The Unix `cfg(test)` arm of those two prepare functions buffers one entry with the existing limit and cancellation checks, outside the section, into storage that is not the destination inode. After that entry is complete and its parent directories exist, the arm publishes those bytes through the same `open`/`write`/`fchmod`/`close` section at mode `0o600` and closes the fd before return. The section is not held across archive parsing, decompression, or `bounded_copy`. The non-test arm stays `create_relative_regular` plus `bounded_copy`. Non-test extraction and the later registration that adds the execute bit stay as they are. `installed_engine_archive_registration_makes_payload_executable` still observes `0o600` before registration and a successful exec after it. If a cancellation test requires a partial destination inode from a mid-entry failure, the executor stops and reports. It does not wrap `extract_zip` in the counter.

The executor applies this rule to every shebang site in the traced inventory, including sites this plan did not open line by line. A site that execs the written inode and is left on `std::fs::write` is a missed fix. A site in the traced out-of-class list that is migrated is a behavior change this plan does not allow.

### What stays

`stdin_waiting_executable` and its callers stay on `/bin/cat`. The held-writer witness stays a raw write that is left open, and it must still fail with ETXTBSY while that fd is open. `spawn_owned`, `pin_engine_launch`, and `native_lock_is_held` are not edited. No production argv, no spawn retry, no sleep, no process-wide `Command` lock.

### Deterministic proof

The proof is in `test_executable`, not a flaky full-suite rerun.

- A parent holds a script open for write, outside the publisher. A raw `fork` child sleeps about 300 ms and `_exit`s. The parent closes its fd. `Command::new(script)` returns `ExecutableFileBusy` while that child is alive, and succeeds after the child has exited. This shows the kernel failure without the publisher.
- Publication-first: a forker blocks in the prepare handler while `publish_test_executable` is inside the syscall section. The forker has entered before the section finishes, and the child is created only after the section finishes. Exec of the published script then succeeds.
- Fork-first: one prepare handler has incremented `forks`, observed `publications == 0`, and is held before it returns. A concurrent `publish_test_executable` must not create or open the target while that hold lasts. After the hold is released, `fork` completes, the child stays alive, publication finishes, and exec of the published script succeeds while that child is alive. A barrier that only waits for the publication counter and then returns fails this test.
- Two-fork: current glibc holds its atfork lock from the prepare handlers until the parent handler returns, including when `fork` fails (`sysdeps/nptl/fork.c`: the `pid != 0` branch runs the parent handlers). Two `libc::fork` calls therefore do not overlap on this Linux, and a test that waits for that overlap hangs. The proof calls the handlers itself. Prepare A increments `forks`, prepare B increments it, parent A decrements it, and publication must not open the target until parent B. A boolean cleared by parent A fails this sequence. The same sequence drives the `cfg(test)` extraction payload writer, not only `publish_test_executable`. Removing the publication section from either producer fails that producer's assertion. The count stays even though this glibc serializes `libc::fork`. macOS was not checked, and a libc that overlaps `fork` is the case the count covers.
- A test in `test_executable` fails if an in-class file still passes a `#!/bin/sh` literal to `std::fs::write`, `fs::write`, or an equivalent direct write of the exec inode, except the traced exclusions: the held-writer witness, the non-exec `exit 22` replacements, `terminal_snapshot_production_child_broken_pipe_keeps_unread_reason`, archive payload constructors that do not exec, and `inherited_descriptors_cover_every_resource_lease_and_the_engine_image`. Reverting a migrated fixture writer to `std::fs::write` fails this test.
- When `pthread_atfork` cannot be installed, publication returns the error and leaves the path unwritten.
- The cat fixtures and the held-writer witness still pass, and the witness still sees ETXTBSY on the held script.

## Decisions and trade-offs

### Decided autonomously

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `publications` counts threads inside `open`/`write`/`fchmod`/`close`. `forks` counts prepare handlers that have not finished the matching parent handler, so one completed fork does not admit publication while another fork is still pending. The publisher allocates before the section and does not fork or allocate inside it. Every in-process write of an inode this process later execs uses that section.

Rejected:

- Write to a temp name, close, and rename into place. Measured: ETXTBSY remains while the write fd is open. Rename does not drop that fd.
- One shared immutable runner plus a per-test body file. Linux execs `/proc/self/fd/N`, so `$0` is not the script name, and two engines share a working directory. A chmod of a hardlink would also change the shared inode.
- Retry spawn on ETXTBSY, sleeps, or a process-wide lock around `Command::spawn`. `d-20261014-18` rejected startup retries, sleeps, and global spawn synchronization for the retention fixtures. On Rust 1.98, `Command` with `pre_exec` inherits the write fd during `pre_exec` (measured by `etxtbsy-during`). A lock around `Command::spawn` would still miss `native_lock_is_held`'s `libc::fork` and would serialize concurrency tests. The atfork barrier covers both fork sites.
- Production argument plumbing or a change to `spawn_owned`. `test_fixture`'s third argument is resource leases. `d-20261014-18` rejected that plumbing.
- Reopening the `/bin/cat` retention fixtures. `d-20261014-18` is in force. `d-20261014-17` is superseded by it.

Reversal: replace this barrier only with a measured mechanism that closes the parent-held write fd and the `libc::fork` inheritance window for every exec'd fixture inode, keeps the cat fixtures and the held-writer witness, and does not change production spawn. Record that as a new decision at adoption. This plan does not call `record-decision`.

- The prepare-handler registration order was not read from a local man page. The no-allocation rule is the deadlock control. A later change that allocates while the counter is held reintroduces the deadlock the rule exists to avoid.

## Approach

### Publication barrier

Add `src-tauri/src/infra/test_executable.rs`, declared `#[cfg(test)] pub(crate) mod test_executable;` from `src-tauri/src/infra/mod.rs`. Do not put it in `test_hooks.rs`. That module is the keyed one-shot hook table.

The public function is `publish_test_executable(path, bytes, mode) -> io::Result<()>`. It is `cfg(test)` and compiled for Unix only. Windows call sites stay on their current writes. There is no public closure that runs caller code while the barrier is held.

Two process-wide atomics coordinate publication with `libc::fork`. `publications` counts threads inside the syscall section. `forks` counts threads that have entered a prepare handler and have not yet finished the matching parent handler. Every load, store, `fetch_add`, and `fetch_sub` on these two atomics uses `Ordering::SeqCst`. A weaker ordering does not implement the exclusion. A boolean cleared by one parent handler does not either: two prepares can both observe zero publications, then one parent handler can clear the flag while the other thread has not yet entered `fork`. The first publication installs all three `pthread_atfork` handlers exactly once. If installation fails, publication returns that error and does not write. There is no unguarded fallback. The handlers allocate nothing and take no lock.

A publisher allocates the path `CString` and copies `bytes` before it enters the section. It then waits while `forks` is non-zero. It increments `publications`, checks `forks` again, and if a fork is in flight it decrements and retries. Only after that second check does it run `open` (`O_CREAT | O_WRONLY | O_TRUNC | O_CLOEXEC`), `write` of the prepared bytes, `fchmod(fd, mode as libc::mode_t)`, and `close`. A short write or any syscall error closes the fd, drops the section count, and returns the error. The count drops on panic too. The final path is written in place. A rename does not clear ETXTBSY while a write fd is open, so the helper does not rename.

`fchmod` takes `libc::mode_t`. On macOS that type is `u16` (docs.rs `libc` 0.2.177, `aarch64-apple-darwin`: `pub type mode_t = u16`, and `fchmod` takes `mode_t`). Casting the mode to `libc::c_uint` (`u32`) does not compile there. The variadic `open` mode argument, where this crate already passes one, stays `as libc::c_uint` (`src-tauri/src/db/bound_sqlite.rs:1307`).

The prepare handler increments `forks`, then waits until `publications` is zero, then returns. A publisher that passed the first check and then sees `forks` non-zero leaves the section before `open`. A publisher that has not entered waits. The parent handler decrements `forks` only after `fork` has returned. Publication stays excluded until every in-flight fork has decremented, so one completed fork cannot open the window for a fork that is still between prepare and `fork`. The child is the forking thread only. Its handler stores zero to both `forks` and `publications`, because counts copied from other parent threads would otherwise stick with no thread left to drop them. The child is not stuck excluded, and a later fork in that child does not spin on a stale publication count.

The publisher does not call `libc::fork` and does not call `malloc` while `publications` is non-zero for that thread. A same-thread `libc::fork` during the section deadlocks, because prepare waits for a count that thread holds. Nested publication is allowed. Callers use the function and do not hold the section themselves. `Command::spawn` with `pre_exec` takes this fork path, so the same handlers cover production engine spawn and `native_lock_is_held`.

### Which writers go through it

Every Unix test path that this process writes and then `execve`s goes through `publish_test_executable` before any later `chmod` or spawn. "Execs" means the written inode is the `execve` target: `Command::new` of that path, `EngineExecutable::test_fixture` followed by spawn, or an equivalent spawn. The mode argument is the mode the test needs at the end of publication, including `0o700` and the macOS materialized-mode case that uses a different mode. Call sites drop the separate `set_permissions` on that executable so the mode change is not repeated outside the barrier.

Direct `std::fs::write` of those scripts is replaced by the helper. Non-exec bytes in the same test (resource files, logs, the `exit 22` replacements) stay ordinary writes.

### Deterministic proof

The proof is in `test_executable`, not a flaky full-suite rerun.

- A parent holds a script open for write, outside the publisher. A raw `fork` child sleeps about 300 ms and `_exit`s. The parent closes its fd. `Command::new(script)` returns `ExecutableFileBusy` while that child is alive, and succeeds after the child has exited. This shows the kernel failure without the publisher.
- Publication-first: a forker blocks in the prepare handler while `publish_test_executable` is inside the syscall section. The forker has entered before the section finishes, and the child is created only after the section finishes. Exec of the published script then succeeds.
- Fork-first: one prepare handler has incremented `forks`, observed `publications == 0`, and is held before it returns. A concurrent `publish_test_executable` must not create or open the target while that hold lasts. After the hold is released, `fork` completes, the child stays alive, publication finishes, and exec of the published script succeeds while that child is alive. A barrier that only waits for the publication counter and then returns fails this test.
- Two-fork: glibc 2.39 `posix/register-atfork.c` unlocks `atfork_lock` around each prepare handler and around each parent handler, so two `libc::fork` calls can overlap. The earlier claim that an overlap test hangs is withdrawn. The required proof calls the handlers itself so it does not depend on that schedule. Prepare A increments `forks`, prepare B increments it, parent A decrements it, and publication must not open the target until parent B. A boolean cleared by parent A fails this sequence. The same sequence drives the `cfg(test)` extraction arm, not only `publish_test_executable`. Removing the publication section from either producer fails that producer's assertion.
- A test in `test_executable` fails if an in-class file still passes a `#!/bin/sh` literal to `std::fs::write`, `fs::write`, or an equivalent direct write of the exec inode, except the traced exclusions: the held-writer witness, the non-exec `exit 22` replacements, `terminal_snapshot_production_child_broken_pipe_keeps_unread_reason`, archive payload constructors that do not exec, and `inherited_descriptors_cover_every_resource_lease_and_the_engine_image`. Reverting a migrated fixture writer to `std::fs::write` fails this test.
- An archive with two regular members of the same name fails on the second member through the `cfg(test)` arm, and the first member's bytes are unchanged. Replacing `O_EXCL` with `O_TRUNC` fails this test. A rename of the staging root does not redirect the write.
- When `pthread_atfork` cannot be installed, publication returns the error and leaves the path unwritten.
- The cat fixtures and the held-writer witness still pass, and the witness still sees ETXTBSY on the held script.

## Decisions and trade-offs

### Decided autonomously

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `publications` counts threads inside `open`/`write`/`fchmod`/`close`. `forks` counts prepare handlers that have not finished the matching parent handler, so one completed fork does not admit publication while another fork is still pending. The publisher allocates before the section and does not fork or allocate inside it. Every in-process write of an inode this process later execs uses that section.

Rejected:

- Write to a temp name, close, and rename into place. Measured: ETXTBSY remains while the write fd is open. Rename does not drop that fd.
- One shared immutable runner plus a per-test body file. Linux execs `/proc/self/fd/N`, so `$0` is not the script name, and two engines share a working directory. A chmod of a hardlink would also change the shared inode.
- Retry spawn on ETXTBSY, sleeps, or a process-wide lock around `Command::spawn`. `d-20261014-18` rejected startup retries, sleeps, and global spawn synchronization for the retention fixtures. On Rust 1.98, `Command` with `pre_exec` inherits the write fd during `pre_exec` (measured by `etxtbsy-during`). A lock around `Command::spawn` would still miss `native_lock_is_held`'s `libc::fork` and would serialize concurrency tests. The atfork barrier covers both fork sites.
- Production argument plumbing or a change to `spawn_owned`. `test_fixture`'s third argument is resource leases. `d-20261014-18` rejected that plumbing.
- Reopening the `/bin/cat` retention fixtures. `d-20261014-18` is in force. `d-20261014-17` is superseded by it.

Reversal: replace this barrier only with a measured mechanism that closes the parent-held write fd and the `libc::fork` inheritance window for every exec'd fixture inode, keeps the cat fixtures and the held-writer witness, and does not change production spawn. Record that as a new decision at adoption. This plan does not call `record-decision`.

## Approach

### Publication barrier

Add `src-tauri/src/infra/test_executable.rs`, declared `#[cfg(test)] pub(crate) mod test_executable;` from `src-tauri/src/infra/mod.rs`. Do not put it in `test_hooks.rs`. That module is the keyed one-shot hook table.

The public function is `publish_test_executable(path, bytes, mode) -> io::Result<()>`. It is `cfg(test)` and compiled for Unix only. Windows call sites stay on their current writes. There is no public closure that runs caller code while the barrier is held.

Two process-wide atomics coordinate publication with `libc::fork`. `publications` counts threads inside the syscall section. `forks` counts threads that have entered a prepare handler and have not yet finished the matching parent handler. Every load, store, `fetch_add`, and `fetch_sub` on these two atomics uses `Ordering::SeqCst`. A weaker ordering does not implement the exclusion. A boolean cleared by one parent handler does not either: two prepares can both observe zero publications, then one parent handler can clear the flag while the other thread has not yet entered `fork`. The first publication installs all three `pthread_atfork` handlers exactly once. If installation fails, publication returns that error and does not write. There is no unguarded fallback. The handlers allocate nothing and take no lock.

A publisher allocates the path `CString` and copies `bytes` before it enters the section. It then waits while `forks` is non-zero. It increments `publications`, checks `forks` again, and if a fork is in flight it decrements and retries. Only after that second check does it run `open` (`O_CREAT | O_WRONLY | O_TRUNC | O_CLOEXEC`), `write` of the prepared bytes, `fchmod(fd, mode as libc::mode_t)`, and `close`. A short write or any syscall error closes the fd, drops the section count, and returns the error. The count drops on panic too. The final path is written in place. A rename does not clear ETXTBSY while a write fd is open, so the helper does not rename.

`fchmod` takes `libc::mode_t`. On macOS that type is `u16` (docs.rs `libc` 0.2.177, `aarch64-apple-darwin`: `pub type mode_t = u16`, and `fchmod` takes `mode_t`). Casting the mode to `libc::c_uint` (`u32`) does not compile there. The variadic `open` mode argument, where this crate already passes one, stays `as libc::c_uint` (`src-tauri/src/db/bound_sqlite.rs:1307`).

The prepare handler increments `forks`, then waits until `publications` is zero, then returns. A publisher that passed the first check and then sees `forks` non-zero leaves the section before `open`. A publisher that has not entered waits. The parent handler decrements `forks` only after `fork` has returned. Publication stays excluded until every in-flight fork has decremented, so one completed fork cannot open the window for a fork that is still between prepare and `fork`. The child is the forking thread only. Its handler stores zero to both `forks` and `publications`, because counts copied from other parent threads would otherwise stick with no thread left to drop them. The child is not stuck excluded, and a later fork in that child does not spin on a stale publication count.

The publisher does not call `libc::fork` and does not call `malloc` while `publications` is non-zero for that thread. A same-thread `libc::fork` during the section deadlocks, because prepare waits for a count that thread holds. Nested publication is allowed. Callers use the function and do not hold the section themselves. `Command::spawn` with `pre_exec` takes this fork path, so the same handlers cover production engine spawn and `native_lock_is_held`.

### Which writers go through it

Every Unix test path that this process writes and then `execve`s goes through `publish_test_executable` before any later `chmod` or spawn. "Execs" means the written inode is the `execve` target: `Command::new` of that path, `EngineExecutable::test_fixture` followed by spawn, or an equivalent spawn. The mode argument is the mode the test needs at the end of publication, including `0o700` and the macOS materialized-mode case that uses a different mode. Call sites drop the separate `set_permissions` on that executable so the mode change is not repeated outside the barrier.

Direct `std::fs::write` of those scripts is replaced by the helper. Non-exec bytes in the same test (resource files, logs, the `exit 22` replacements) stay ordinary writes.

For `extract_zip` / gzip-tar extraction, the destination inode is opened in `prepare_zip_cancellable` and `prepare_tar_cancellable` (`src-tauri/src/fs.rs`) before `bounded_copy` streams the entry. `create_relative_regular` (`src-tauri/src/infra/fs.rs`) only creates that inode and returns the open file. It never sees the payload bytes, so it cannot buffer first. The Unix `cfg(test)` arm of those two prepare functions buffers one entry with the existing limit and cancellation checks, outside the section, into storage that is not the destination inode. After that entry is complete and its parent directories exist, the arm publishes through the held staging directory descriptor, not through the pathname helper. Inside the section it `openat`s that directory with `O_CREAT | O_EXCL | O_WRONLY | O_NOFOLLOW | O_CLOEXEC`, the same writable access `create_regular_at` passes (`infra/fs.rs:5977`), writes the buffered bytes, `fchmod`s `0o600`, and closes. Flags without `O_WRONLY` or `O_RDWR` open a read-only descriptor, and the payload write then fails with `EBADF`. A second member of the same name gets the same `AlreadyExists` failure production gets from `create_at` (`O_EXCL` at `inode_ownership.rs:943`) and does not truncate the first member. `OwnedStagingDir` has no pathname (`infra/fs.rs:6598`), so a renamed staging root must not redirect this write. The section is not held across archive parsing, decompression, or `bounded_copy`. The non-test arm stays `create_relative_regular` plus `bounded_copy`. Non-test extraction and the later registration that adds the execute bit stay as they are. `installed_engine_archive_registration_makes_payload_executable` still observes `0o600` before registration and a successful exec after it. If a cancellation test requires a partial destination inode from a mid-entry failure, the executor stops and reports. It does not wrap `extract_zip` in the counter.

The executor applies this rule to every shebang site in the traced inventory, including sites this plan did not open line by line. A site that execs the written inode and is left on `std::fs::write` is a missed fix. A site in the traced out-of-class list that is migrated is a behavior change this plan does not allow.

The held-writer witness stays a raw write that is left open, and it must still fail with ETXTBSY while that fd is open. `spawn_owned`, `pin_engine_launch`, and `native_lock_is_held` are not edited. ### Deterministic proof

The proof is in `test_executable`, not a flaky full-suite rerun.

- A parent holds a script open for write, outside the publisher. A raw `fork` child sleeps about 300 ms and `_exit`s. The parent closes its fd. `Command::new(script)` returns `ExecutableFileBusy` while that child is alive, and succeeds after the child has exited. This shows the kernel failure without the publisher.
- Publication-first: a forker blocks in the prepare handler while `publish_test_executable` is inside the syscall section. The forker has entered before the section finishes, and the child is created only after the section finishes. Exec of the published script then succeeds.
- Fork-first: one prepare handler has incremented `forks`, observed `publications == 0`, and is held before it returns. A concurrent `publish_test_executable` must not create or open the target while that hold lasts. After the hold is released, `fork` completes, the child stays alive, publication finishes, and exec of the published script succeeds while that child is alive. A barrier that only waits for the publication counter and then returns fails this test.
- Two-fork: glibc 2.39 `posix/register-atfork.c` unlocks `atfork_lock` around each prepare handler and around each parent handler, so two `libc::fork` calls can overlap. The earlier claim that an overlap test hangs is withdrawn. The required proof calls the handlers itself so it does not depend on that schedule. Prepare A increments `forks`, prepare B increments it, parent A decrements it, and publication must not open the target until parent B. A boolean cleared by parent A fails this sequence. The same sequence drives the `cfg(test)` extraction arm, not only `publish_test_executable`. Removing the publication section from either producer fails that producer's assertion.
- A test in `test_executable` fails if an in-class file still passes a `#!/bin/sh` literal to `std::fs::write`, `fs::write`, or an equivalent direct write of the exec inode, except the traced exclusions: the held-writer witness, the non-exec `exit 22` replacements, `terminal_snapshot_production_child_broken_pipe_keeps_unread_reason`, archive payload constructors that do not exec, and `inherited_descriptors_cover_every_resource_lease_and_the_engine_image`. Reverting a migrated fixture writer to `std::fs::write` fails this test.
- An archive with two regular members of the same name fails on the second member through the `cfg(test)` arm, and the first member's bytes are unchanged. Replacing `O_EXCL` with `O_TRUNC` fails this test. A rename of the staging root does not redirect the write.
- When `pthread_atfork` cannot be installed, publication returns the error and leaves the path unwritten.
- The cat fixtures and the held-writer witness still pass, and the witness still sees ETXTBSY on the held script.

## Decisions and trade-offs

### Decided autonomously

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `publications` counts threads inside `open`/`write`/`fchmod`/`close`. `forks` counts prepare handlers that have not finished the matching parent handler, so one completed fork does not admit publication while another fork is still pending. The publisher allocates before the section and does not fork or allocate inside it. Every in-process write of an inode this process later execs uses that section.

Rejected:

- Write to a temp name, close, and rename into place. Measured: ETXTBSY remains while the write fd is open. Rename does not drop that fd.
- One shared immutable runner plus a per-test body file. Linux execs `/proc/self/fd/N`, so `$0` is not the script name, and two engines share a working directory. A chmod of a hardlink would also change the shared inode.
- Retry spawn on ETXTBSY, sleeps, or a process-wide lock around `Command::spawn`. `d-20261014-18` rejected startup retries, sleeps, and global spawn synchronization for the retention fixtures. On Rust 1.98, `Command` with `pre_exec` inherits the write fd during `pre_exec` (measured by `etxtbsy-during`). A lock around `Command::spawn` would still miss `native_lock_is_held`'s `libc::fork` and would serialize concurrency tests. The atfork barrier covers both fork sites.
- Production argument plumbing or a change to `spawn_owned`. `test_fixture`'s third argument is resource leases. `d-20261014-18` rejected that plumbing.
- Reopening the `/bin/cat` retention fixtures. `d-20261014-18` is in force. `d-20261014-17` is superseded by it.

Reversal: replace this barrier only with a measured mechanism that closes the parent-held write fd and the `libc::fork` inheritance window for every exec'd fixture inode, keeps the cat fixtures and the held-writer witness, and does not change production spawn. Record that as a new decision at adoption. This plan does not call `record-decision`.

## Risks / open questions

- The prepare-handler registration order was not read from a local man page. The no-allocation rule is the deadlock control. A later change that allocates while the counter is held reintroduces the deadlock the rule exists to avoid.
- A `clone` that does not run `pthread_atfork` handlers would skip the barrier. None was found in this crate. That remains a known residual, not a second mechanism to build.
- macOS `pin_engine_launch` still copies an image and execs the copy. That production write-then-exec is out of scope. The macOS test that drives it publishes only the test's own script write.
- glibc 2.39 `posix_spawn` copies the fd table and does not run atfork handlers. `CLONE_VFORK` suspends only the spawning thread. Until that child execs or `_exit`s, its copied writer keeps the inode busy for every other thread, including an engine `execve` at `process.rs:3990` after the publisher has already closed. Closing the fd after `posix_spawn` returns does not describe this interval. The interval is a known residual. This change does not add a second barrier for it. Production engine spawn itself uses `pre_exec` and is on the `libc::fork` path the barrier covers. `process.rs:6392` is one such different-image spawn (`/bin/sh`).

## Approach

### Publication barrier

Add `src-tauri/src/infra/test_executable.rs`, declared `#[cfg(test)] pub(crate) mod test_executable;` from `src-tauri/src/infra/mod.rs`. Do not put it in `test_hooks.rs`. That module is the keyed one-shot hook table.

The public function is `publish_test_executable(path, bytes, mode) -> io::Result<()>`. It is `cfg(test)` and compiled for Unix only. Windows call sites stay on their current writes. There is no public closure that runs caller code while the barrier is held.

Two process-wide atomics coordinate publication with `libc::fork`. `publications` counts threads inside the syscall section. `forks` counts threads that have entered a prepare handler and have not yet finished the matching parent handler. Every load, store, `fetch_add`, and `fetch_sub` on these two atomics uses `Ordering::SeqCst`. A weaker ordering does not implement the exclusion. A boolean cleared by one parent handler does not either: two prepares can both observe zero publications, then one parent handler can clear the flag while the other thread has not yet entered `fork`. The first publication installs all three `pthread_atfork` handlers exactly once. If installation fails, publication returns that error and does not write. There is no unguarded fallback. The handlers allocate nothing and take no lock.

A publisher allocates the path `CString` and copies `bytes` before it enters the section. It then waits while `forks` is non-zero. It increments `publications`, checks `forks` again, and if a fork is in flight it decrements and retries. Only after that second check does it run `open` (`O_CREAT | O_WRONLY | O_TRUNC | O_CLOEXEC`), `write` of the prepared bytes, `fchmod(fd, mode as libc::mode_t)`, and `close`. A short write or any syscall error closes the fd, drops the section count, and returns the error. The count drops on panic too. The final path is written in place. A rename does not clear ETXTBSY while a write fd is open, so the helper does not rename.

`fchmod` takes `libc::mode_t`. On macOS that type is `u16` (docs.rs `libc` 0.2.177, `aarch64-apple-darwin`: `pub type mode_t = u16`, and `fchmod` takes `mode_t`). Casting the mode to `libc::c_uint` (`u32`) does not compile there. The variadic `open` mode argument, where this crate already passes one, stays `as libc::c_uint` (`src-tauri/src/db/bound_sqlite.rs:1307`).

The prepare handler increments `forks`, then waits until `publications` is zero, then returns. A publisher that passed the first check and then sees `forks` non-zero leaves the section before `open`. A publisher that has not entered waits. The parent handler decrements `forks` only after `fork` has returned. Publication stays excluded until every in-flight fork has decremented, so one completed fork cannot open the window for a fork that is still between prepare and `fork`. The child is the forking thread only. Its handler stores zero to both `forks` and `publications`, because counts copied from other parent threads would otherwise stick with no thread left to drop them. The child is not stuck excluded, and a later fork in that child does not spin on a stale publication count.

The publisher does not call `libc::fork` and does not call `malloc` while `publications` is non-zero for that thread. A same-thread `libc::fork` during the section deadlocks, because prepare waits for a count that thread holds. Nested publication is allowed. Callers use the function and do not hold the section themselves. `Command::spawn` with `pre_exec` takes this fork path, so the same handlers cover production engine spawn and `native_lock_is_held`.

### Which writers go through it

Every Unix test path that this process writes and then `execve`s goes through `publish_test_executable` before any later `chmod` or spawn. "Execs" means the written inode is the `execve` target: `Command::new` of that path, `EngineExecutable::test_fixture` followed by spawn, or an equivalent spawn. The mode argument is the mode the test needs at the end of publication, including `0o700` and the macOS materialized-mode case that uses a different mode. Call sites drop the separate `set_permissions` on that executable so the mode change is not repeated outside the barrier.

Direct `std::fs::write` of those scripts is replaced by the helper. Non-exec bytes in the same test (resource files, logs, the `exit 22` replacements) stay ordinary writes.

For `extract_zip` / gzip-tar extraction, the destination inode is opened in `prepare_zip_cancellable` and `prepare_tar_cancellable` (`src-tauri/src/fs.rs`) before `bounded_copy` streams the entry. `create_relative_regular` (`src-tauri/src/infra/fs.rs`) only creates that inode and returns the open file. It never sees the payload bytes, so it cannot buffer first. The Unix `cfg(test)` arm of those two prepare functions buffers one entry with the existing limit and cancellation checks, outside the section, into storage that is not the destination inode. After that entry is complete and its parent directories exist, the arm publishes through the held staging directory descriptor, not through the pathname helper. Inside the section it `openat`s that directory with `O_CREAT | O_EXCL | O_WRONLY | O_NOFOLLOW | O_CLOEXEC`, the same writable access `create_regular_at` passes (`infra/fs.rs:5977`), writes the buffered bytes, `fchmod`s `0o600`, and closes. Flags without `O_WRONLY` or `O_RDWR` open a read-only descriptor, and the payload write then fails with `EBADF`. A second member of the same name gets the same `AlreadyExists` failure production gets from `create_at` (`O_EXCL` at `inode_ownership.rs:943`) and does not truncate the first member. `OwnedStagingDir` has no pathname (`infra/fs.rs:6598`), so a renamed staging root must not redirect this write. The section is not held across archive parsing, decompression, or `bounded_copy`. The non-test arm stays `create_relative_regular` plus `bounded_copy`. Non-test extraction and the later registration that adds the execute bit stay as they are. `installed_engine_archive_registration_makes_payload_executable` still observes `0o600` before registration and a successful exec after it. If a cancellation test requires a partial destination inode from a mid-entry failure, the executor stops and reports. It does not wrap `extract_zip` in the counter.

The executor applies this rule to every shebang site in the traced inventory, including sites this plan did not open line by line. A site that execs the written inode and is left on `std::fs::write` is a missed fix. A site in the traced out-of-class list that is migrated is a behavior change this plan does not allow.

### What stays

`stdin_waiting_executable` and its callers stay on `/bin/cat`. The held-writer witness stays a raw write that is left open, and it must still fail with ETXTBSY while that fd is open. `spawn_owned`, `pin_engine_launch`, and `native_lock_is_held` are not edited. No production argv, no spawn retry, no sleep, no process-wide `Command` lock.

### Deterministic proof

The proof is in `test_executable`, not a flaky full-suite rerun.

- A parent holds a script open for write, outside the publisher. A raw `fork` child sleeps about 300 ms and `_exit`s. The parent closes its fd. `Command::new(script)` returns `ExecutableFileBusy` while that child is alive, and succeeds after the child has exited. This shows the kernel failure without the publisher.
- Publication-first: a forker blocks in the prepare handler while `publish_test_executable` is inside the syscall section. The forker has entered before the section finishes, and the child is created only after the section finishes. Exec of the published script then succeeds.
- Fork-first: one prepare handler has incremented `forks`, observed `publications == 0`, and is held before it returns. A concurrent `publish_test_executable` must not create or open the target while that hold lasts. After the hold is released, `fork` completes, the child stays alive, publication finishes, and exec of the published script succeeds while that child is alive. A barrier that only waits for the publication counter and then returns fails this test.
- Two-fork: glibc 2.39 `posix/register-atfork.c` unlocks `atfork_lock` around each prepare handler and around each parent handler, so two `libc::fork` calls can overlap. The earlier claim that an overlap test hangs is withdrawn. The required proof calls the handlers itself so it does not depend on that schedule. Prepare A increments `forks`, prepare B increments it, parent A decrements it, and publication must not open the target until parent B. A boolean cleared by parent A fails this sequence. The same sequence drives the `cfg(test)` extraction arm, not only `publish_test_executable`. Removing the publication section from either producer fails that producer's assertion.
- A test in `test_executable` fails if an in-class file still passes a `#!/bin/sh` literal to `std::fs::write`, `fs::write`, or an equivalent direct write of the exec inode, except the traced exclusions: the held-writer witness, the non-exec `exit 22` replacements, `terminal_snapshot_production_child_broken_pipe_keeps_unread_reason`, archive payload constructors that do not exec, and `inherited_descriptors_cover_every_resource_lease_and_the_engine_image`. Reverting a migrated fixture writer to `std::fs::write` fails this test.
- An archive with two regular members of the same name fails on the second member through the `cfg(test)` arm, and the first member's bytes are unchanged. Replacing `O_EXCL` with `O_TRUNC` fails this test. A rename of the staging root does not redirect the write.
- When `pthread_atfork` cannot be installed, publication returns the error and leaves the path unwritten.
- The cat fixtures and the held-writer witness still pass, and the witness still sees ETXTBSY on the held script.

## Decisions and trade-offs

### Decided autonomously

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `publications` counts threads inside `open`/`write`/`fchmod`/`close`. `forks` counts prepare handlers that have not finished the matching parent handler, so one completed fork does not admit publication while another fork is still pending. The publisher allocates before the section and does not fork or allocate inside it. Every in-process write of an inode this process later execs uses that section.

Rejected:

- Write to a temp name, close, and rename into place. Measured: ETXTBSY remains while the write fd is open. Rename does not drop that fd.
- One shared immutable runner plus a per-test body file. Linux execs `/proc/self/fd/N`, so `$0` is not the script name, and two engines share a working directory. A chmod of a hardlink would also change the shared inode.
- Retry spawn on ETXTBSY, sleeps, or a process-wide lock around `Command::spawn`. `d-20261014-18` rejected startup retries, sleeps, and global spawn synchronization for the retention fixtures. On Rust 1.98, `Command` with `pre_exec` inherits the write fd during `pre_exec` (measured by `etxtbsy-during`). A lock around `Command::spawn` would still miss `native_lock_is_held`'s `libc::fork` and would serialize concurrency tests. The atfork barrier covers both fork sites.
- Production argument plumbing or a change to `spawn_owned`. `test_fixture`'s third argument is resource leases. `d-20261014-18` rejected that plumbing.
- Reopening the `/bin/cat` retention fixtures. `d-20261014-18` is in force. `d-20261014-17` is superseded by it.

Reversal: replace this barrier only with a measured mechanism that closes the parent-held write fd and the `libc::fork` inheritance window for every exec'd fixture inode, keeps the cat fixtures and the held-writer witness, and does not change production spawn. Record that as a new decision at adoption. This plan does not call `record-decision`.

## Risks / open questions

- The prepare-handler registration order was not read from a local man page. The no-allocation rule is the deadlock control. A later change that allocates while the counter is held reintroduces the deadlock the rule exists to avoid.
- A `clone` that does not run `pthread_atfork` handlers would skip the barrier. None was found in this crate. That remains a known residual, not a second mechanism to build.
- macOS `pin_engine_launch` still copies an image and execs the copy. That production write-then-exec is out of scope. The macOS test that drives it publishes only the test's own script write.
- glibc 2.39 `posix_spawn` copies the fd table and does not run atfork handlers. `CLONE_VFORK` suspends only the spawning thread. Until that child execs or `_exit`s, its copied writer keeps the inode busy for every other thread, including an engine `execve` at `process.rs:3990` after the publisher has already closed. Closing the fd after `posix_spawn` returns does not describe this interval. The interval is a known residual. This change does not add a second barrier for it. Production engine spawn itself uses `pre_exec` and is on the `libc::fork` path the barrier covers. `process.rs:6392` is one such different-image spawn (`/bin/sh`).

## Threat model and non-goals

Adversary and environment, frozen for round 1: one `cargo test` process, tests running in parallel on several threads (stated in `src-tauri/src/infra/test_hooks.rs`). A thread writes a file this process will later `execve`. Before that write descriptor is closed, another thread in the same process calls `libc::fork`. The child inherits the write descriptor. `execve` of that inode then returns ETXTBSY until every writer, including the child, has closed it. The observed failure is Linux CI. This is not a remote attacker and not a cross-process attacker.

Non-goals: production engine launch, a change to how engines are spawned or killed, Windows, and making a deliberately held write descriptor executable.

## Approach

### Publication barrier

Add `src-tauri/src/infra/test_executable.rs`, declared `#[cfg(test)] pub(crate) mod test_executable;` from `src-tauri/src/infra/mod.rs`. Do not put it in `test_hooks.rs`. That module is the keyed one-shot hook table.

The public function is `publish_test_executable(path, bytes, mode) -> io::Result<()>`. It is `cfg(test)` and compiled for Unix only. Windows call sites stay on their current writes. There is no public closure that runs caller code while the barrier is held.

Two process-wide atomics coordinate publication with `libc::fork`. `publications` counts threads inside the syscall section. `forks` counts threads that have entered a prepare handler and have not yet finished the matching parent handler. Every load, store, `fetch_add`, and `fetch_sub` on these two atomics uses `Ordering::SeqCst`. A weaker ordering does not implement the exclusion. A boolean cleared by one parent handler does not either: two prepares can both observe zero publications, then one parent handler can clear the flag while the other thread has not yet entered `fork`. The first publication installs all three `pthread_atfork` handlers exactly once. If installation fails, publication returns that error and does not write. There is no unguarded fallback. The handlers allocate nothing and take no lock.

A publisher allocates the path `CString` and copies `bytes` before it enters the section. It then waits while `forks` is non-zero. It increments `publications`, checks `forks` again, and if a fork is in flight it decrements and retries. Only after that second check does it run `open` (`O_CREAT | O_WRONLY | O_TRUNC | O_CLOEXEC`), `write` of the prepared bytes, `fchmod(fd, mode as libc::mode_t)`, and `close`. A short write or any syscall error closes the fd, drops the section count, and returns the error. The count drops on panic too. The final path is written in place. A rename does not clear ETXTBSY while a write fd is open, so the helper does not rename.

`fchmod` takes `libc::mode_t`. On macOS that type is `u16` (docs.rs `libc` 0.2.177, `aarch64-apple-darwin`: `pub type mode_t = u16`, and `fchmod` takes `mode_t`). Casting the mode to `libc::c_uint` (`u32`) does not compile there. The variadic `open` mode argument, where this crate already passes one, stays `as libc::c_uint` (`src-tauri/src/db/bound_sqlite.rs:1307`).

The prepare handler increments `forks`, then waits until `publications` is zero, then returns. A publisher that passed the first check and then sees `forks` non-zero leaves the section before `open`. A publisher that has not entered waits. The parent handler decrements `forks` only after `fork` has returned. Publication stays excluded until every in-flight fork has decremented, so one completed fork cannot open the window for a fork that is still between prepare and `fork`. The child is the forking thread only. Its handler stores zero to both `forks` and `publications`, because counts copied from other parent threads would otherwise stick with no thread left to drop them. The child is not stuck excluded, and a later fork in that child does not spin on a stale publication count.

The publisher does not call `libc::fork` and does not call `malloc` while `publications` is non-zero for that thread. A same-thread `libc::fork` during the section deadlocks, because prepare waits for a count that thread holds. Nested publication is allowed. Callers use the function and do not hold the section themselves. `Command::spawn` with `pre_exec` takes this fork path, so the same handlers cover production engine spawn and `native_lock_is_held`.

### Which writers go through it

Every Unix test path that this process writes and then `execve`s goes through `publish_test_executable` before any later `chmod` or spawn. "Execs" means the written inode is the `execve` target: `Command::new` of that path, `EngineExecutable::test_fixture` followed by spawn, or an equivalent spawn. The mode argument is the mode the test needs at the end of publication, including `0o700` and the macOS materialized-mode case that uses a different mode. Call sites drop the separate `set_permissions` on that executable so the mode change is not repeated outside the barrier.

Direct `std::fs::write` of those scripts is replaced by the helper. Non-exec bytes in the same test (resource files, logs, the `exit 22` replacements) stay ordinary writes.

For `extract_zip` / gzip-tar extraction, the destination inode is opened in `prepare_zip_cancellable` and `prepare_tar_cancellable` (`src-tauri/src/fs.rs`) before `bounded_copy` streams the entry. `create_relative_regular` (`src-tauri/src/infra/fs.rs`) only creates that inode and returns the open file. It never sees the payload bytes, so it cannot buffer first. The Unix `cfg(test)` arm of those two prepare functions buffers one entry with the existing limit and cancellation checks, outside the section, into storage that is not the destination inode. After that entry is complete and its parent directories exist, the arm publishes through the held staging directory descriptor, not through the pathname helper. Inside the section it `openat`s that directory with `O_CREAT | O_EXCL | O_WRONLY | O_NOFOLLOW | O_CLOEXEC`, the same writable access `create_regular_at` passes (`infra/fs.rs:5977`), writes the buffered bytes, `fchmod`s `0o600`, and closes. Flags without `O_WRONLY` or `O_RDWR` open a read-only descriptor, and the payload write then fails with `EBADF`. A second member of the same name gets the same `AlreadyExists` failure production gets from `create_at` (`O_EXCL` at `inode_ownership.rs:943`) and does not truncate the first member. `OwnedStagingDir` has no pathname (`infra/fs.rs:6598`), so a renamed staging root must not redirect this write. The section is not held across archive parsing, decompression, or `bounded_copy`. The non-test arm stays `create_relative_regular` plus `bounded_copy`. Non-test extraction and the later registration that adds the execute bit stay as they are. `installed_engine_archive_registration_makes_payload_executable` still observes `0o600` before registration and a successful exec after it. If a cancellation test requires a partial destination inode from a mid-entry failure, the executor stops and reports. It does not wrap `extract_zip` in the counter.

The executor applies this rule to every shebang site in the traced inventory, including sites this plan did not open line by line, and to `copy_closed_cat_fixture` even though its bytes are not a shebang. A site that execs the written inode and is left on `std::fs::write` or `std::fs::copy` is a missed fix. A site in the traced out-of-class list that is migrated is a behavior change this plan does not allow.

### What stays

`stdin_waiting_executable` stays a no-argument open of canonical `/bin/cat`. Linux callers, the three retention fixtures, and `real_child_ignoring_quit_is_force_killed_within_reap_budget` stay on it. Do not revert the macOS private command target that `d-20261028-05` requires for the two observer tests. `copy_closed_cat_fixture` does not stay on `std::fs::copy`: read `/bin/cat` before the section, then `publish_test_executable` writes `stdin-waiting-cat` in that fixture directory at mode `0o755` and closes the writer inside the section. The two directories still get two distinct files, neither of which is `/bin/cat`. The held-writer witness stays a raw write that is left open, and it must still fail with ETXTBSY while that fd is open. `spawn_owned`, `pin_engine_launch`, and `native_lock_is_held` are not edited. No production argv, no spawn retry, no sleep, no process-wide `Command` lock. Publishing this copy does not by itself close f-20261011-06.

### Deterministic proof

The proof is in `test_executable`, not a flaky full-suite rerun.

- A parent holds a script open for write, outside the publisher. A raw `fork` child sleeps about 300 ms and `_exit`s. The parent closes its fd. `Command::new(script)` returns `ExecutableFileBusy` while that child is alive, and succeeds after the child has exited. This shows the kernel failure without the publisher.
- Publication-first: a forker blocks in the prepare handler while `publish_test_executable` is inside the syscall section. The forker has entered before the section finishes, and the child is created only after the section finishes. Exec of the published script then succeeds.
- Fork-first: one prepare handler has incremented `forks`, observed `publications == 0`, and is held before it returns. A concurrent `publish_test_executable` must not create or open the target while that hold lasts. After the hold is released, `fork` completes, the child stays alive, publication finishes, and exec of the published script succeeds while that child is alive. A barrier that only waits for the publication counter and then returns fails this test.
- Two-fork: glibc 2.39 `posix/register-atfork.c` unlocks `atfork_lock` around each prepare handler and around each parent handler, so two `libc::fork` calls can overlap. The earlier claim that an overlap test hangs is withdrawn. The required proof calls the handlers itself so it does not depend on that schedule. Prepare A increments `forks`, prepare B increments it, parent A decrements it, and publication must not open the target until parent B. A boolean cleared by parent A fails this sequence. The same sequence drives the `cfg(test)` extraction arm, not only `publish_test_executable`. Removing the publication section from either producer fails that producer's assertion.
- A test in `test_executable` fails if an in-class file still passes a `#!/bin/sh` literal to `std::fs::write`, `fs::write`, or an equivalent direct write of the exec inode, except the traced exclusions: the held-writer witness, the non-exec `exit 22` replacements, `terminal_snapshot_production_child_broken_pipe_keeps_unread_reason`, archive payload constructors that do not exec, and `inherited_descriptors_cover_every_resource_lease_and_the_engine_image`. Reverting a migrated fixture writer to `std::fs::write` fails this test. The same test fails if `copy_closed_cat_fixture` still calls `std::fs::copy` or `set_permissions` on `stdin-waiting-cat`. The shebang literal check alone does not cover that producer.
- An archive with two regular members of the same name fails on the second member through the `cfg(test)` arm, and the first member's bytes are unchanged. Replacing `O_EXCL` with `O_TRUNC` fails this test. A rename of the staging root does not redirect the write.
- When `pthread_atfork` cannot be installed, publication returns the error and leaves the path unwritten.
- The cat fixtures and the held-writer witness still pass, and the witness still sees ETXTBSY on the held script.

## Decisions and trade-offs

### Decided autonomously

Question: which fix removes the Linux write-then-exec ETXTBSY race for every fixture script, not one test?

Chosen: a `cfg(test)` publication barrier. `publications` counts threads inside `open`/`write`/`fchmod`/`close`. `forks` counts prepare handlers that have not finished the matching parent handler, so one completed fork does not admit publication while another fork is still pending. The publisher allocates before the section and does not fork or allocate inside it. Every in-process write of an inode this process later execs uses that section.

Rejected:

- Write to a temp name, close, and rename into place. Measured: ETXTBSY remains while the write fd is open. Rename does not drop that fd.
- One shared immutable runner plus a per-test body file. Linux execs `/proc/self/fd/N`, so `$0` is not the script name, and two engines share a working directory. A chmod of a hardlink would also change the shared inode.
- Retry spawn on ETXTBSY, sleeps, or a process-wide lock around `Command::spawn`. `d-20261014-18` rejected startup retries, sleeps, and global spawn synchronization for the retention fixtures. On Rust 1.98, `Command` with `pre_exec` inherits the write fd during `pre_exec` (measured by `etxtbsy-during`). A lock around `Command::spawn` would still miss `native_lock_is_held`'s `libc::fork` and would serialize concurrency tests. The atfork barrier covers both fork sites.
- Production argument plumbing or a change to `spawn_owned`. `test_fixture`'s third argument is resource leases. `d-20261014-18` rejected that plumbing.
- Reopening the `/bin/cat` retention fixtures. `d-20261014-18` is in force. `d-20261014-17` is superseded by it.

Question: does `d-20261028-05`'s macOS private `/bin/cat` copy stay outside the publication barrier?

Chosen: no. `copy_closed_cat_fixture` writes an inode the two macOS observer tests exec. Read `/bin/cat` before the section and publish those bytes with `publish_test_executable` at mode `0o755`. Keep a distinct `stdin-waiting-cat` per fixture directory. Linux observer tests stay on canonical `/bin/cat`.

Rejected: leaving `std::fs::copy` because a shebang audit cannot see it; reverting the two tests to one shared `/bin/cat` open; a script written in the test and then executed.

Reason: `std::fs::copy` holds a destination write fd until it returns, so a concurrent `libc::fork` inherits that writer. The drift added this producer after the shebang audit was closed. `d-20261028-05` keeps the private command target and does not close f-20261011-06.

Question: which Cargo target runs the Phase 1 proof?

Chosen: `cargo test --manifest-path src-tauri/Cargo.toml --bin chessfable`. One filter substring per invocation.

Rejected: `--lib`. This package has no library target, so those commands fail before any test runs.

Reason: `cargo metadata --no-deps` lists only the `chessfable` binary (`src/main.rs`) and the build script. The renamed-database handoff in the drift records the same fact.

Reversal: replace this barrier only with a measured mechanism that closes the parent-held write fd and the `libc::fork` inheritance window for every exec'd fixture inode, keeps the cat fixtures and the held-writer witness, and does not change production spawn. Record that as a new decision at adoption. This plan does not call `record-decision`.

## Risks / open questions

- The prepare-handler registration order was not read from a local man page. The no-allocation rule is the deadlock control. A later change that allocates while the counter is held reintroduces the deadlock the rule exists to avoid.
- A `clone` that does not run `pthread_atfork` handlers would skip the barrier. None was found in this crate. That remains a known residual, not a second mechanism to build.
- macOS `pin_engine_launch` still copies an image and execs the copy. That production write-then-exec is out of scope. The macOS test that drives it publishes only the test's own script write.
- glibc 2.39 `posix_spawn` copies the fd table and does not run atfork handlers. `CLONE_VFORK` suspends only the spawning thread. Until that child execs or `_exit`s, its copied writer keeps the inode busy for every other thread, including an engine `execve` at `process.rs:3990` after the publisher has already closed. Closing the fd after `posix_spawn` returns does not describe this interval. The interval is a known residual. This change does not add a second barrier for it. Production engine spawn itself uses `pre_exec` and is on the `libc::fork` path the barrier covers. `process.rs:6392` is one such different-image spawn (`/bin/sh`).
