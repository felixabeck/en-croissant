### R1-01 — ambiguous provider response cannot confirm invalidity

Claim: DELETE's exact 401 No such token response also covers signature rejection of an existing token. The r1 plan would therefore clear pending and report allRevoked despite a potentially usable bearer surviving failed storage erasure. MANDATE obligation: distinguish already-invalid from unconfirmed provider rejection without exposing secrets. Dependencies: O1 classification determines O2 pending and O3 startup summary, O4 must test the correct discriminator.

Raw findings, preserved verbatim as individual finding lines rather than whole reports:

* correctness r1 index 1: [blocker] /tmp/drain-plan-drain-90a2aa88-slot0/build/plan-r1.md:54 — `401 {"error":"No such token"}` does not prove permanent token invalidity. The frozen `provider-OAuthServer.scala:68–76` returns `None` when an existing token fails `signedClients.allow`, and lines 35–36 convert that result into `NoSuchToken`. `provider-LilaController.scala:263–269` then emits the same 401 discriminator. A valid token rejected because its required signature is absent therefore becomes `already_invalid`, although no revocation occurred and it can remain usable with an accepted signature. O2 consequently clears `revocation_pending`, and O3 can report `allRevoked=true` while a working token remains stored. Correct the provider premise and establish a discriminator that excludes signature rejection, or retain this response as unconfirmed. (confidence: 97)
* error-handling r1 index 1: [blocker] /tmp/drain-plan-drain-90a2aa88-slot0/build/plan-r1.md:54 — O1 treats `401 {"error":"No such token"}` as confirmed invalidity, but the frozen `provider-OAuthServer.scala:68-76` also returns `None` when signature policy rejects an existing token. * plan r1 index 1: [blocker] /tmp/drain-plan-drain-90a2aa88-slot0/build/plan-r1.md:54 — O1’s `401 / "No such token"` discriminator does not establish permanent invalidity. * tauri-security r1 index 1: [blocker] /tmp/drain-plan-drain-90a2aa88-slot0/build/plan-r1.md:54 — `401 {"error":"No such token"}` does not prove invalidity. ## MANDATE

Verbatim finding selected by `next --pin f-20261004-04`:

### Lichess token revocation collapses an unreachable provider and a rejected token into one generic failure

* **ID:** f-20261004-04 · **Status:** open · **Area:** oauth-credentials · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** 4d37a1f3-c56b-44b0-82ce-6bbb4ede1a0a (plan-only run for `f-20260914-16`)
* **Where:** `src-tauri/src/oauth.rs:367-379` (`ProdOAuthServices::revoke_token` maps a transport failure and every non-2xx status to `Error::OAuthFailure(OAUTH_FAILURE)`); consumer `src-tauri/src/oauth.rs:557-561` (account removal reports `revocation_pending` as `revoke_token(...).is_err()`).
* **Defect:** neither the user nor the diagnostic can tell a timeout or offline provider (the token may still work; retry is right) from a credential Lichess already rejects (for example 401: the token no longer works, so "revocation pending" is false) or from rate limiting. Account removal therefore reports `revocation_pending` for a token that is already dead, and any later consumer of `revoke_token` (the `f-20260914-16` plan adds one for legacy tokens that could not be erased) inherits the same blind boolean.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` — typed errors from commands, mapped at the facade; an error path that loses its context cannot drive the right terminal state.
* **Open question:** which outcomes does `revoke_token` distinguish (revoked / already invalid / unreachable / rejected for another reason), how does a sanitised kind reach account removal's `revocation_pending` and the renderer without exposing the token, and does an already-invalid token count as revoked?
* **Found by:** `review-error-handling` plan lens (Codex), 2026-10-04, confidence 96, during the `f-20260914-16` plan review round 2. Confirmed by reading the cited lines; not reproduced. Pre-existing for account removal and not required by that run's MANDATE, whose summary treats any unconfirmed revocation as "not revoked" (the safe direction) and retries it.

Ordinary account unlink and legacy-storage sanitization under real provider success, expired/revoked credentials, connectivity failure, rate limiting, provider rejection and malformed/truncated responses. Provider payloads and transport errors may contain secrets and remain untrusted. No real credentials or live revocations are used for proof. Existing native HTTPS origin, DNS, redirect refusal and request deadlines remain authoritative. No new retry service, persistent token queue, storage format, credential journal redesign, settings or endpoint is introduced. No hostile renderer or deliberately evasive input model is added.

## Approach

### O1 — classify provider outcomes once

`OAuthServices::revoke_token` produces one typed, token-free outcome shared by production and tests: revoked, already_invalid, unreachable, rate_limited or rejected. A successful DELETE means revoked. After DELETE returns 401, make exactly one native POST to the fixed `https://lichess.org/api/token/test` endpoint with the exact single token as text/plain body. Only a successful HTTP 200 JSON response explicitly mapping that exact token to null means already_invalid. An existing-token object, omitted key, wrong type, malformed response or any other response remains unconfirmed. Do not infer invalidity from the DELETE body, including `No such token`, and do not run token testing after other DELETE outcomes.

Transport failure during sending or reading means unreachable and HTTP 429 means rate_limited at either request. All remaining unconfirmed HTTP or parse outcomes mean rejected, which says confirmation failed without claiming a credential is invalid. Both requests and response reading share one absolute operation deadline of 30 seconds, matching the current JSON request budget rather than doubling it. Deadline expiration means unreachable. Token-test response parsing is bounded to 64 KiB while streaming, including absent or false Content-Length. Exceeding the cap remains rejected. Both endpoints retain the existing HTTPS/DNS/no-redirect policy. Test-only endpoint injection remains private.

The token-test endpoint echoes the token as a JSON key. Its response exists only in native ephemeral memory, is never serialized into an outcome, and is discarded after classification. No provider body, error text, request, header, URL or token is formatted into any returned value, Debug representation or log. Native diagnostics record only the closed outcome kind and optionally HTTP status, never raw errors. No retry loop is added.

### O2 — keep local removal and provider confirmation independent

Local removal remains committed before the provider attempt and stays a successful removed result for every provider outcome. Preserve not_found, no-token and durability_uncertain behavior. Keep the existing revocation_pending boolean for compatibility with d-20260831-20, derive it centrally from the outcome, and add the sanitized revocation outcome as an optional field, absent/null only when no local token needed a provider attempt. Pending is false for revoked, already_invalid or no token, and true for every unconfirmed outcome. No-token does not claim a provider request succeeded.

The handle-free legacy command returns the same typed outcome as successful command data for provider outcomes. Successful IPC delivery is not itself proof of revocation. Unexpected command/IPC failure remains an unconfirmed fallback, without copying the exception. Both commands remain in the existing Specta registry and facade. Regenerate bindings rather than editing them.
