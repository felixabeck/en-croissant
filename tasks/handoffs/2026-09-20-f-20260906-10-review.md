# Plan: f-20260906-10 — report the sound-server port failure once and stop re-asking

## Goal

`src/utils/sound.ts` swallows the only failure path it has. `playSound` is fire-and-forget and
its single `.catch(() => {})` (`src/utils/sound.ts:59-61`) discards the rejection of
`tauri.getSoundServerPort()`, so a backend that cannot answer leaves the user with silence and
no log line. Because `soundServerPort` is only assigned on success (`:19`), a rejection also
leaves the module-level cache `null`, and every subsequent move re-issues the IPC.

MANDATE (fixed for every review round): a rejected sound-server port lookup must be reported,
exactly once per process, and must not be retried on every move; `playSound` must remain
fire-and-forget, must not throw, and must not leave an unhandled promise rejection.

## Approach

### A. Stop asking after a failure, and report it once

Two mechanisms, because they bound two different things. Neither touches the success path.

**A1 — no lookup after a failure: a module-level latch.** Today `soundServerPort` is assigned
only after `await` succeeds (`src/utils/sound.ts:19`), so a rejection leaves it `null` and every
later move re-asks. Add one latch, set in the rejection handler and tested at the top of
`playSound`, before the 75 ms throttle:

```ts
let soundServerPortFailed = false;

export function playSound(capture: boolean, check: boolean) {
    if (soundServerPortFailed) {
        return;
    }
    // ... unchanged from here
```

Once set, a move does no work at all: no IPC, no throttle bookkeeping, no atom reads, no
microtask, no audio.

**Bound, stated explicitly:** the latch stops every lookup that *begins* after the first
rejection is observed. Lookups already in flight when it rejects still complete, because a
failure cannot be latched before it is known. The 75 ms throttle admits at most one such call
per 75 ms of one IPC round trip. Those are not retries in the finding's sense — the finding's
defect is "retries the IPC on every move", and after the latch there are no further moves that
reach the IPC at all.

**A2 — one report, ever: the same latch, set synchronously.** The handler tests and sets the
latch with no `await` between the test and the set, so of several concurrent rejections exactly
one can see it unset:

```ts
.catch((error) => {
    if (soundServerPortFailed) return;
    soundServerPortFailed = true;
    void warn(`Sound server port request failed: ${String(error)}`).catch((logError) =>
        console.warn("Sound server port request failed, and the log facade did too:", error, logError),
    );
});
```

The `console.warn` fallback is not decoration. Round-3 `review-error-handling` reported
(blocker, 94) that `.catch(() => undefined)` — the `src/hooks/downloadJobs.ts:47` form — would
leave the sound failure with **no** record whenever the log IPC itself rejects, which is
precisely the situation the report exists for: no Tauri backend. MANDATE requires the failure to
be reported, so a silent fallback fails it. `console.warn` is chosen over `console.error`
because the facade call is `warn` and a fallback must not upgrade severity; `console` cannot
itself reject, so the chain terminates. This is a deliberate, documented deviation from the
`downloadJobs.ts` precedent, written here so the next reader does not "restore" it.

**Settled invariant — how tightly the failing lookup is bounded.** Three rounds of review
argued this (B2/B3 in round 2, E2 in round 3, and a rule 12a focused architecture judgment in
round 4). Three options were on the table; **the plan's first two revisions chose (i) and were
wrong**, and both lenses converged independently on (iii) in round 4.

* **(i) Memoize the promise** (`portRequest ??= tauri.getSoundServerPort()`). One IPC ever,
  including the in-flight window. **Rejected:** it also deduplicates concurrent *successful*
  lookups, which today's value cache does not, and MANDATE asks nothing about the success path.
  The earlier revisions defended it first as "inseparable" (refuted in round 3 — it is
  separable) and then as "unobservable" (true, but an unobservable change is still an
  unmandated one, and it is not the arbiter's to grant).
* **(ii) An attempt latch set before the IPC.** One IPC ever, no success dedupe. **Ruled out by
  measurement:** a `playSound` arriving while the first lookup is pending becomes a no-op, so a
  move played inside the first round trip is **silent**. That trades an invisible cost for a
  user-visible one. Round-4 `review-error-handling` agreed: "option (ii) would indeed silence
  an overlapping move".
* **(iii) Failure latch only — chosen.** Exactly what MANDATE asks, and nothing else: the
  success path is byte-for-byte unchanged, and the only cost is that the bound is stated with
  the in-flight qualifier above rather than as a flat "one". Round-4 `review-plan`: option
  (iii) "satisfies the mandate by latching after rejection without changing concurrent
  successful lookups".

Reversal path: if the in-flight window ever needs closing too, (i) is the mechanism, and it
needs a MANDATE that asks for it.

### B. Report through the platform facade, with the promise handled

`warn` from `@/platform/native` is the project's log door and is already used from
`src/utils/signedCatalog.ts:25`, `src/state/utils.ts:50`, `src/state/store/tabStorage.ts:280`
and `src/hooks/downloadJobs.ts:47`.

The call must be `void warn(...).catch(<console fallback>)` — never a bare `warn(...)` as in
`state/utils.ts:50`, and never the `.catch(() => undefined)` of `downloadJobs.ts:47`, which
discards the log failure (section A2). Two measurements, one of them a correction to an earlier
draft of this plan:

  (`node_modules/@tauri-apps/plugin-log/dist-js/index.js:135`), which awaits `log` (`:89`),
  which awaits `invoke('plugin:log|log', …)`. `invoke` is
  `return window.__TAURI_INTERNALS__.invoke(...)` inside an `async function`
  (`node_modules/@tauri-apps/api/core.js:201-203`), so any failure of the log plugin surfaces
  as a rejected promise, not a throw. An unhandled rejection here is a real failure mode, not a
  test artefact, and `async-resource-invariants.md` requires the error path.
* **Two existing suites run `playSound` for real with no `@/platform/native` mock.** Both were
  traced end to end by the arbiter in round 3; neither is modified by this plan.
  * `src/utils/tests/store.test.ts` contains **no `vi.mock` line at all** and calls
    `store.getState().makeMove(...)` (`:205`, `:251`, `:470-488`). The store action

    (`:677-706`), whose `sound` parameter defaults to `true` (`:684`), so `:706` calls
    `playSound`.
  * `src/components/puzzles/Puzzles.test.tsx` mocks `@/platform/tauri` but **not**
    `@/platform/native`, and reaches the same path *without* going through the mocked

    directly (`:251-254`, bound at `:80`). Its
    `getSoundServerPort.mockRejectedValue(new Error("sound disabled in test"))` at `:175` is
    therefore live, not decorative.

  `vite.config.ts:54-76` registers no `setupFiles`, so there is no global Tauri stub: in both
  suites `tauri.getSoundServerPort()` really rejects today and is really swallowed. After this
  change they reach the new `warn` call, and a bare `warn(...)` would turn them into unhandled
  rejections.
* **Two retractions, both recorded because they were load-bearing.**
  * Round 1: both lenses reported that `Puzzles.test.tsx` cannot reach `playSound` because
    `./PuzzleBoard` is mocked (`:54-73`), and the arbiter adopted that. It is **false** — the

  * Round 2: this plan claimed `src/components/common/TreeStateContext.test.tsx` as a second

    no `playSound`; it only mounts and hydrates. `review-error-handling` and `review-plan` both

The message carries the cause (`String(error)`), matching the surrounding precedents. The
message text is not translated: it is a log line, not UI, and no other `warn` call site in the

### C. Leave the `port === 0` path alone

`port === 0` is the backend saying it has no sound server. It resolves successfully, so it is

carries the comment at `:45-47` explaining why it is silent, and it issues no

### D. Proof

`src/utils/sound.test.ts` already runs under fake timers (`:46-47`), which is what makes the
75 ms throttle controllable. Add five cases. Each one is written so that exactly one mechanism
reverts it — round-3 and round-4 `review-plan` both caught earlier drafts claiming a
discrimination the case did not have, so the reverting change is named per case and must be
checked, not assumed.

1. **Stops asking after a failure.** `getSoundServerPort` rejects; call `playSound`, settle,
   advance the clock past 75 ms, call `playSound` again, settle. Assert
   `mocks.getSoundServerPort` was called **once**, the mocked `warn` **once**, its argument
   contains the cause, and no audio element played.
   *Reverts on:* deleting the top-of-function latch → the second call reaches the lookup and the
   IPC count is 2. With option (iii) there is no promise memo to mask that, which is exactly why
   this case discriminates now and did not in r3/r4.
2. **Reports once with two lookups in flight.** Back `getSoundServerPort` with a **deferred**
   promise the test controls. Call `playSound`, advance past 75 ms, call `playSound` again —
   both past the throttle, both before any rejection — then reject the deferred and settle.
   Assert the mocked `warn` was called **once**, and assert `mocks.getSoundServerPort` was
   called **twice**, which pins the in-flight allowance as deliberate rather than accidental.
   *Reverts on:* deleting the report latch, or making it asynchronous → `warn` twice.
3. **Two overlapping successful lookups both play.** Same deferred setup, resolved with a real
   port instead of rejected. Assert **two** audio elements were played.
   *Reverts on:* adopting option (ii)'s attempt latch, which turns the second call into a no-op.
   This is a regression guard for the behaviour option (iii) was chosen to preserve, not an
   acceptance criterion; it asserts nothing about the IPC count.
4. **The report's own failure is not silent and does not escape.** Mock `warn` to **reject** and
   spy on `console.warn`; call `playSound` with a rejecting lookup and settle. Assert
   `console.warn` called once with both errors. The second assertion is the run itself: Vitest
   fails a test on an unhandled rejection.
   *Reverts on:* dropping the `.catch` → unhandled rejection; `.catch(() => undefined)` →
   `console.warn` never called.
5. **`playSound` stays fire-and-forget.** Assert `playSound(false, false)` returns `undefined`,
   on the success path and after the lookup has failed.
   *Reverts on:* returning the internal chain.

All five require `vi.mock("@/platform/native", ...)` in `sound.test.ts`, which the suite does
not have today.

The two unmodified witnesses that exercise the real path are `src/utils/tests/store.test.ts`
and `src/components/puzzles/Puzzles.test.tsx` — section B has the traced call chain for both.
Neither is edited by this plan; both go red on an unhandled rejection if the `.catch` is
dropped. `src/components/common/TreeStateContext.test.tsx` is **not** a witness and is not
cited as one.

## Decisions and trade-offs

* **D1 — one module-level latch, not a keyed structure.** Chosen because the module has one
  lookup and one cache slot after `8738ccf5`. Rejected: a `Set`/`Map` keyed by
  `collection/kind` (the shape the capability-surface lenses argued over) — it would be an
  unbounded-by-construction container reintroduced to index a single key, and
  `async-resource-invariants.md` asks for a stated bound. Reversal path: if a future change
  reintroduces per-collection lookups, the latch becomes a bounded map over the eight
  collections × three kinds.
* **D1b — the IPC is bounded by the failure latch alone, not by memoizing the promise.**
  Adopted in round 4 after both lenses converged on it; revisions r2 and r3 of this plan chose
  the promise memo and were wrong. The memo bounds the in-flight window too, but it also
  deduplicates concurrent successful lookups, which MANDATE does not ask for. Rejected with it:
  an attempt latch set before the IPC, measured to silence a move played inside the first round
  trip. Full argument and both lens quotations: section A1's settled-invariant block.
* **D2 — `void warn(...)` with a `console.warn` fallback, not a bare `warn(...)` and not
  `.catch(() => undefined)`.** The bare form is forced out by the production rejection path and
  the two unmocked suites named in section B; the empty catch is forced out because it erases
  the only report in exactly the case the report exists for. Measured, not preferred.
* **D3 — latch checked at the top of `playSound`, before the throttle.** Rejected: checking
  inside `getSoundServerPort` and throwing/resolving a sentinel — that puts the decision behind
  the promise boundary and keeps a needless microtask per move. Rejected: leaving the throttle
  first — harmless, but then `lastTime` is advanced by calls that do nothing, which is a
  behavioural difference with no purpose.
* **D4 — no recovery, ever, within a process.** A rejected `get_sound_server_port` is not a
  transient condition: `src-tauri/src/sound.rs:251-253` returns `Ok(state.0)` unconditionally,
  so the command cannot fail in the app; a rejection means the IPC transport is absent (tests,
  a browser). Retrying it per move is the defect, not a feature. Rejected: a bounded retry with
  backoff — nothing would ever succeed on the second attempt.

## Acceptance criteria

1. Once a `tauri.getSoundServerPort` lookup has **failed**, no `playSound` call that begins
   afterwards issues a lookup, for the lifetime of the module. Lookups already in flight when
   the rejection arrives are permitted and are asserted to be permitted (proof case 2), because
   a failure cannot be latched before it is observed; nothing else is. The success path is
   unchanged and is out of scope.
2. Exactly one `warn` reaches `@/platform/native` per process for that failure, and it names the
   cause.
3. No unhandled promise rejection is produced by the report, in a suite that mocks
   `@/platform/native` and in one that does not; and when the facade log itself fails, the
   sound failure still leaves exactly one record, on `console`.
4. `playSound` returns `undefined` and never throws, on the success path and after the lookup
   has failed.
5. Each of the five new tests goes red when the single mechanism it pins is reverted, as named
   per case in section D: top-of-function latch, report latch, absence of an attempt latch,
   the `console.warn` fallback, and the return contract.

Not acceptance, recorded as a regression note only: the `port === 0` path keeps its present
behaviour — it plays nothing, warns nothing and sets no latch. It is outside MANDATE
(section C) and nothing in this plan touches it. The existing test at
`src/utils/sound.test.ts:79-88` pins the silence and the single-call count for **one**
`playSound` call; it makes no second call, so it does not pin caching or the absence of a
repeated IPC, and this plan does not claim it does (round-2 `review-error-handling` nit).
