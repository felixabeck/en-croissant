## Approach

### O1 — Own the created file through handoff

Arm compensation immediately after a successful exclusive create and keep the exact created descriptor until all required validation and ownership admission succeed. No post-create error may escape before compensation has run or returned an explicit cleanup failure. Disarm only on successful handoff of the admitted owner and its already-verified identity. Use that captured identity rather than adding a redundant fallible metadata query after cleanup ownership has been transferred.

Apply the contract at the actual Unix exclusive adapter shared by capability, sidecar and atomic-temp creation. Route missing-leaf open-or-create through proven exclusive creation on both Linux and non-Linux Unix. If another writer wins creation, follow the existing-file admission path without treating that file as owned by this create. Preserve flags, caller mode, owner class, close ordering and registry arbitration without nested acquisition. Do not apply deletion rollback to a non-exclusive open of an existing file. On Windows, keep cleanup armed across disk/type checks, identity and `OwnedFile` admission, including the private atomic temporary's equivalent handoff. Reuse one created-file ownership mechanism where the same concept occurs twice. Keep the single NT create primitive and d-20261004-36's created-outcome reparse rule unchanged.

### O2 — Compensate only the created object

On Unix, use the retained parent and no-follow leaf identity check before unlink. If initial fstat failed, make one bounded independent descriptor identity observation for cleanup. A successful observation supplies the identity required by the existing regular-leaf removal primitive. If identity still cannot be established, refuse deletion and return that uncertainty as cleanup failure. A missing original name is cleanup-complete, while a replacement, changed kind or failed observation is preserved and reported. Never derive the expected identity solely from the current pathname. Preserve the recorded final identity-check-to-unlink race without claiming to solve it.

Keep admission arbitration, quarantine bounds and close ordering intact on failure. Cleanup must not recursively acquire the registry or close a possibly SQLite-owned descriptor outside its existing quarantine rules. Successful cleanup does not by itself authorize an unsafe descriptor close. Admission failure after identity is known uses the same compensation contract.

On Windows, request DELETE on the exclusive created regular handle only, alongside its existing read/write/attribute/synchronization rights. Delete through that same held handle using the existing classic disposition operation and release the owned handle before returning failure. Generalize its native-handle input only as needed for raw and admitted owners, routing private-temp cleanup through it too. Preserve ordinary opens and share policies. Do not introduce a second NtCreateFile call, pathname reopening, or make compensation depend on the separately troubled POSIX Ex disposition. Concurrent external handles may defer classic deletion until their release, so do not promise immediate disappearance in that case.

### O3 — Preserve truthful error classification

Use d-20261007-22's classification for create rollback and existing PGN rollback through one shared implementation. Removed, already missing and unlink-completed-but-parent-sync-uncertain retain the primary error. Durability uncertainty retains an operation-specific native warning. Failed or unprovable removal, including replacement refusal, returns `Error::with_cleanup(primary, Err(cleanup))`. Preserve both diagnostics and the existing renderer-safe serialized category and message. Never return compensation failure as success, classify an already-unlinked leaf as an orphan, or persist a later deletion intent for a user-selected name.

At the SQLite sidecar C ABI, preserve its failure return and existing errno mapping. A combined create-and-cleanup failure must emit both causes once into the existing native log sink before conversion, using the registration identity for context. Do not transmit native diagnostics through SQLite messages or IPC and do not create a new persistent error channel. Ordinary I/O and conflict mappings retain their existing behavior. This native observation belongs at the lossy ABI boundary, not in the shared PGN cleanup classifier that d-20261007-22 requires to remain free of helper error logging.

### Decided autonomously

1. **Question:** Where does rollback ownership begin and end after the Unix adapter moved? **Chosen:** exclusive creation through completed checked `OwnedFile` handoff, with captured verified identity returned without a new fallible query. **Rejected:** caller-only rollback or fixing only the old fs wrapper. **Reason:** callers cannot compensate an adapter error and the source now has failures below that wrapper. **Reversal path:** replace the internal handoff while preserving O1–O4 and every native regression.
2. **Question:** What happens if Unix cannot recover the created descriptor identity? **Chosen:** one bounded observation, then preserve the unknown name and combine the primary and cleanup failure. **Rejected:** blind unlink or treating a pathname observation as provenance. **Reason:** no evidence authorizes deleting a replacement. **Reversal path:** a measured equivalent descriptor-bound deletion primitive can replace the guarded name removal, preserving the d-20260906-01 limit until then.
3. **Question:** Which Windows deletion contract covers failed created-file admission? **Chosen:** same-handle classic disposition with DELETE granted only to exclusive creation and shared with the existing private-temp operation. **Rejected:** reopening by pathname, blanket broader access on ordinary opens or relying on Ex-only removal. **Reason:** the retained handle supplies exact object authority before identity admission. **Reversal path:** replace only this primitive after native platform proof while retaining ownership and failure semantics.
4. **Question:** How does the SQLite sidecar ABI retain a combined cleanup error? **Chosen:** retain its existing errno failure behavior and emit both causes once through the existing native log sink at that boundary. **Rejected:** silently discarding the combined error, changing the C ABI or adding a persistent diagnostic registry. **Reason:** the shared exclusive adapter reaches this consumer and errno cannot carry both causes. **Reversal path:** replace the native observation with an existing equivalent diagnostic carrier only when a regression proves both causes survive the real boundary without leaking into user-facing messages.
5. **Question:** How does Windows open-or-create distinguish creation ownership? **Chosen:** open an existing file normally, and route confirmed absence through the shared exclusive creator, handling creation collisions through existing-file admission with bounded competing-change behavior. **Rejected:** keeping FILE_OPEN_IF while discarding its outcome, adding deletion access to all opens or broadening the low-level NT result contract for every traversal caller. **Reason:** only exclusive success proves ownership and the existing shared creator already carries compensation through admission. **Reversal path:** an outcome-carrying native adapter may replace this dispatch after equivalent cleanup, existing-byte preservation and bounded-race proof, with no loss of authority checks.
