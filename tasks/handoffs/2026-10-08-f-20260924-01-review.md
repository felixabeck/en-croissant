## Goal

Stale renderer ids — ids whose native registry record is already gone — can no longer make
`reconcile_startup_owners` refuse the whole startup reconciliation. Native discards unknown ids
before applying its retained-id bound, and a separate hard cap on the raw request size still bounds
the work an absurd request can cause.

## Approach

### O1 — Unknown ids never count against the retained-id bound

MANDATE: "the count check precedes the `persistent.contains_key` filter", "Native rejects the whole
request with `ResourceLimit` when that raw count exceeds max(registry size, 4096), before it discards
unknown ids".

* **Required behavior.** `reconcile_startup_owners` decides admissibility from the request's ids
  *after* discarding ids absent from `persistent` (duplicates collapse too). The retained set it then
  uses is exactly today's filtered set (P3); nothing about sweep, protection, family trust,
  durability or `startup_retained_ids` changes.
* **Consequence.** The known ids are a subset of the registry, so they can never exceed
  `authority_id_input_limit()`; a request is no longer refused for carrying stale ids up to the O2
  cap. Because that bound holds by construction, no separate post-filter count check is added —
  the only count check left is O2's. The MANDATE example (≈4,100 stale ids against a small registry, plus live ids) succeeds and
  sweeps unowned entries of trusted families.
* **Failure semantics.** Unchanged for every other path: the trusted-family cap (32) still refuses
  with `ResourceLimit` before any work; durability outcomes unchanged.
* **Ownership / integration boundary.** Native only. The IPC type `StartupPathOwners`, its Specta
  binding and the renderer collector are unchanged, so `src/bindings/generated.ts` does not change.

### O2 — A separate hard cap on raw request size

MANDATE: "with a separate hard cap on raw input size" (the finding's open question, option one).

* **Required behavior.** Before filtering, the raw `retained_ids` vector length is checked against
  `authority_id_input_limit() + MAX_STARTUP_OWNER_UNKNOWN_IDS`, a new named constant equal to
  `65_536` (16 × `MAX_AUTHORITY_IDS`), documented as headroom for ids native does not know. Over the
  cap → `Error::ResourceLimit("startup path owner input exceeds its limit")` exactly as today, before
  any allocation proportional to the input and without touching memory or disk state.
* **Why additive.** The cap is the registry-dependent limit plus a fixed allowance, so a request is
  refused only when it carries more than 65,536 ids beyond everything the registry could know —
  independent of registry size, including grandfathered registries above 4,096 (P2, f-20260830-35).
  The renderer's realistic union is a few thousand at most (P4).
* **Scope of the constant.** Only `reconcile_startup_owners` uses it. `MAX_AUTHORITY_REQUEST_IDS`
  and `reconcile_engine_attachments` keep their current limit (non-goal above).

### O3 — Verification

* **Regression (fails on base).** A registry with a few live entries across at least two trusted
  families, one unowned entry of a trusted family, and a request carrying the live ids plus
  ≥ 4,097 unknown ids spread across families: the call succeeds; the unowned entry is swept and
  persisted (reopen the authority and observe it gone); live ids stay resolvable; no unknown id
  enters `startup_retained_ids`. On base the same request returns `ResourceLimit`.
* **Cap boundary.** Exactly `authority_id_input_limit() + MAX_STARTUP_OWNER_UNKNOWN_IDS` raw ids is
  accepted; one more is refused with `ResourceLimit` and leaves memory and the on-disk registry
  unchanged (same assertion style as `attachment_action_validation_matrix_preserves_memory_and_disk`,
  `mod.rs:23002`).
* **Existing tests.** `oversized_startup_input_and_unknown_ids_do_not_mutate_or_accumulate` is
  re-pointed at the new cap (its "unknown ids never accumulate" half unchanged);
  `legacy_startup_owner_union_can_shrink_from_four_thousand_ninety_eight_ids` stays green unchanged.
* **Level.** Rust unit tests in `path_authority`'s unix test module; no renderer, binding or e2e
  change is needed because the IPC contract is unchanged. `pnpm checks:pre-review` and the Rust
  final gates prove the backend coverage ratchet.

## Decisions and trade-offs

* **Native filter-first, not renderer truncation.** The renderer cannot tell stale from live ids
  without a native round-trip (P4: shape-only validation), so any per-family truncation either drops
  live ids — and an omitted live id in a trusted family is swept, losing a capability — or must also
  untrust the truncated family, which disables cleanup for every purpose that family covers (P3:
  e.g. one overflowing PGN family keeps all `PgnWorkspace`/`PgnFile`/`PgnReadOnlyFile` entries).
  Native already knows the registry and already discards unknown ids; moving the check after that
  discard is the smallest change that removes the mechanism.
* **Additive headroom, not `max(…)`.** `max(65_536, registry)` would re-create the defect for a
  grandfathered registry larger than the constant plus any stale ids; addition cannot.
* **Keep a raw cap at all.** P5: the payload is already deserialized, so the cap bounds only the
  dedupe/filter work; it is kept as the defense-in-depth shape the finding's option names and
  `d-20260906-09` established, with a value chosen so no realistic renderer reaches it.
* **Decisions cited, not reopened.** `d-20260906-09` (bound registry ids at 4,096, owner-collector
  reclamation, untrusted families conservative) is preserved: registry bounds are untouched; only
  the request admission check moves. `d-20260924-07` / `d-20260925-01` / `d-20260925-02` (expanded
  directories ≤ 1,000, workspace-scoped) are unaffected.

## Decided autonomously

* **Question:** Where does the startup path-owner request bound apply, given that the renderer's
  union of owner families can carry ids native no longer knows?
  **Governs:** f-20260924-01.
  **Chosen:** Native discards ids absent from the registry before applying the retained-id bound;
  a separate raw-input hard cap of `authority_id_input_limit() + 65_536` (`MAX_STARTUP_OWNER_UNKNOWN_IDS`)
  refuses only absurd requests, before any proportional work. Renderer collection and the IPC type
  are unchanged.
  **Rejected:** Renderer-side per-family prioritisation and truncation (cannot distinguish stale
  from live ids; truncation sweeps live capabilities or, with untrusting, disables cleanup for whole
  purposes); `max(constant, registry)` as the raw cap (re-creates the refusal for large grandfathered
  registries); removing the raw cap (drops the existing defense-in-depth shape for no gain).
  **Reason:** Unknown ids are discarded by native anyway and cannot be retained, so counting them is
  the defect's mechanism; the known subset is bounded by the registry by construction.
  **Reversal path:** measured startup cost or memory evidence may change the 65,536 allowance; a
  renderer-side bound would need a native membership query first.

## Risks / open questions

* **Large raw requests near the cap.** ~70k short strings deduplicated in a `BTreeSet` is
  milliseconds; the test at the cap boundary measures it implicitly. No open product question.
* **Renderer still warns only.** A refusal above the cap still only `warn`s (P6); with the cap three
  orders of magnitude above realistic input this is a named known limit, unchanged from today.

## Not part of this task

* Engine attachment stale-id handling (filed; see Threat model).
* IPC byte-size or per-id length bounds (P5).
* Renderer-side pruning of stale ids from persisted owner records.
* Surfacing the reconciliation refusal to the user beyond today's `warn`.

## Approach

### O1 — Unknown ids never count against the retained-id bound

MANDATE: "the count check precedes the `persistent.contains_key` filter", "Native rejects the whole
request with `ResourceLimit` when that raw count exceeds max(registry size, 4096), before it discards
unknown ids".

* **Required behavior.** `reconcile_startup_owners` decides admissibility from the request's ids
  *after* discarding ids absent from `persistent` (duplicates collapse too). The retained set it then
  uses is exactly today's filtered set (P3); nothing about sweep, protection, family trust,
  durability or `startup_retained_ids` changes.
* **Consequence.** The known ids are a subset of the registry, so they can never exceed
  `authority_id_input_limit()`; a request is no longer refused for carrying stale ids up to the O2
  cap. Because that bound holds by construction, no separate post-filter count check is added —
  the only count check left is O2's. The MANDATE example (≈4,100 stale ids against a small registry, plus live ids) succeeds and
  sweeps unowned entries of trusted families.
* **Failure semantics.** Unchanged for every other path: the trusted-family cap (32) still refuses
  with `ResourceLimit` before any work; durability outcomes unchanged.
* **Ownership / integration boundary.** Native only. The IPC type `StartupPathOwners`, its Specta
  binding and the renderer collector are unchanged, so `src/bindings/generated.ts` does not change.

### O2 — A separate hard cap on raw request size

MANDATE: "with a separate hard cap on raw input size" (the finding's open question, option one).

* **Required behavior.** Before filtering, the raw `retained_ids` vector length is checked against
  `authority_id_input_limit() + MAX_STARTUP_OWNER_UNKNOWN_IDS`, a new named constant equal to
  `65_536` (16 × `MAX_AUTHORITY_IDS`), documented as headroom for ids native does not know. Over the
  cap → `Error::ResourceLimit("startup path owner input exceeds its limit")` exactly as today, before
  any allocation proportional to the input and without touching memory or disk state.
* **Why additive.** The cap is the registry-dependent limit plus a fixed allowance, so a request is
  refused only when it carries more than 65,536 ids beyond everything the registry could know —
  independent of registry size, including grandfathered registries above 4,096 (P2, f-20260830-35).
  The renderer's union is not bounded by construction (P4: engines, practiceDeck, recentFiles on
  read and the collector's tab arrays are unbounded); in ordinary use it is the sum of the bounded
  writers (well under 2,000 ids) plus engines and practice decks, far below the 65,536 allowance.
  The allowance is a sizing judgment, not a proven ceiling — an input above it keeps today's
  refusal (named known limit under Risks).
* **Scope of the constant.** Only `reconcile_startup_owners` uses it. `MAX_AUTHORITY_REQUEST_IDS`
  and `reconcile_engine_attachments` keep their current limit (non-goal above).

* **Cap boundary.** Exactly `authority_id_input_limit() + MAX_STARTUP_OWNER_UNKNOWN_IDS` raw ids is
  accepted; one more is refused with `ResourceLimit` and leaves memory and the on-disk registry
  unchanged (same assertion style as `attachment_action_validation_matrix_preserves_memory_and_disk`,

* **Existing tests.** `oversized_startup_input_and_unknown_ids_do_not_mutate_or_accumulate` is

## Decisions and trade-offs

* **Native filter-first, not renderer truncation.** The renderer cannot tell stale from live ids
  without a native round-trip (P4: shape-only validation), so any per-family truncation either drops
  live ids — and an omitted live id in a trusted family is swept, losing a capability — or must also
  untrust the truncated family, which disables cleanup for every purpose that family covers (P3:
  e.g. one overflowing PGN family keeps all `PgnWorkspace`/`PgnFile`/`PgnReadOnlyFile` entries).
  Native already knows the registry and already discards unknown ids; moving the check after that
  discard is the smallest change that removes the mechanism.
* **Additive headroom, not `max(…)`.** `max(65_536, registry)` would re-create the defect for a
  grandfathered registry larger than the constant plus any stale ids; addition cannot.
* **Keep a raw cap at all.** P5: the payload is already deserialized, so the cap bounds only the
  dedupe/filter work; it is kept as the defense-in-depth shape the finding's option names and
  `d-20260906-09` established, with a value chosen so no realistic renderer reaches it.
* **Decisions cited, not reopened.** `d-20260906-09` (bound registry ids at 4,096, owner-collector
  reclamation, untrusted families conservative) is preserved: registry bounds are untouched; only
  the request admission check moves. `d-20260924-07` / `d-20260925-01` / `d-20260925-02` (expanded
  directories ≤ 1,000, workspace-scoped) are unaffected.

## Decided autonomously

* **Question:** Where does the startup path-owner request bound apply, given that the renderer's
  union of owner families can carry ids native no longer knows?
  **Governs:** f-20260924-01.
  **Chosen:** Native discards ids absent from the registry before applying the retained-id bound;
  a separate raw-input hard cap of `authority_id_input_limit() + 65_536` (`MAX_STARTUP_OWNER_UNKNOWN_IDS`)
  refuses only absurd requests, before any proportional work. Renderer collection and the IPC type
  are unchanged.
  **Rejected:** Renderer-side per-family prioritisation and truncation (cannot distinguish stale
  from live ids; truncation sweeps live capabilities or, with untrusting, disables cleanup for whole
  purposes); `max(constant, registry)` as the raw cap (re-creates the refusal for large grandfathered
  registries); removing the raw cap (drops the existing defense-in-depth shape for no gain).
  **Reason:** Unknown ids are discarded by native anyway and cannot be retained, so counting them is
  the defect's mechanism; the known subset is bounded by the registry by construction.
  **Reversal path:** measured startup cost or memory evidence may change the 65,536 allowance; a
  renderer-side bound would need a native membership query first.

## Risks / open questions

* **Input above the allowance.** The renderer union has no proven ceiling (P4); a request with more
  than 65,536 unknown ids beyond the registry limit is still refused as today. Named known limit; not
  reachable in ordinary use.
* **Large raw requests near the cap.** ~70k short strings deduplicated in a `BTreeSet` is
  milliseconds; the test at the cap boundary measures it implicitly. No open product question.
* **Renderer still warns only.** A refusal above the cap still only `warn`s (P6); with the allowance
  well above ordinary input this is a named known limit, unchanged from today.

* **Failure semantics.** Unchanged for every other path: the trusted-family cap (32) still refuses

* **Ownership / integration boundary.** Native only. The IPC type `StartupPathOwners`, its Specta

### O2 — A separate hard cap on raw request size

MANDATE: "with a separate hard cap on raw input size" (the finding's open question, option one).

* **Required behavior.** Before filtering, the raw `retained_ids` vector length is checked against
  `authority_id_input_limit() + MAX_STARTUP_OWNER_UNKNOWN_IDS`, a new named constant equal to
  `65_536` (16 × `MAX_AUTHORITY_IDS`), documented as headroom for ids native does not know. Over the
  cap → `Error::ResourceLimit("startup path owner input exceeds its limit")` exactly as today, before
  any allocation proportional to the input and without touching memory or disk state.
* **Why additive.** The cap is the registry-dependent limit plus a fixed allowance, so a request is
  refused only when it carries more than 65,536 ids beyond everything the registry could know —
  independent of registry size, including grandfathered registries above 4,096 (P2, f-20260830-35).
  The renderer's union is not bounded by construction (P4: engines, practiceDeck, recentFiles on
  read and the collector's tab arrays are unbounded); in ordinary use it is the sum of the bounded
  writers (well under 2,000 ids) plus engines and practice decks, far below the 65,536 allowance.
  The allowance is a sizing judgment, not a proven ceiling — an input above it keeps today's
  refusal (named known limit under Risks).
* **Scope of the constant.** Only `reconcile_startup_owners` uses it. `MAX_AUTHORITY_REQUEST_IDS`
  and `reconcile_engine_attachments` keep their current limit (non-goal above).

### O3 — Verification

* **Regression (fails on base).** A registry with a few live entries across at least two trusted
  families, one unowned entry of a trusted family, and a request carrying the live ids plus
  ≥ 4,097 unknown ids spread across families: the call succeeds; the unowned entry is swept and
  persisted (reopen the authority and observe it gone); live ids stay resolvable; no unknown id
  enters `startup_retained_ids`. On base the same request returns `ResourceLimit`.
* **Cap boundary.** Exactly `authority_id_input_limit() + MAX_STARTUP_OWNER_UNKNOWN_IDS` raw ids is
  accepted; one more is refused with `ResourceLimit` and leaves memory and the on-disk registry
  unchanged (same assertion style as `attachment_action_validation_matrix_preserves_memory_and_disk`,
  `mod.rs:23002`).
* **Existing tests.** `oversized_startup_input_and_unknown_ids_do_not_mutate_or_accumulate` is
  re-pointed at the new cap (its "unknown ids never accumulate" half unchanged);
  `legacy_startup_owner_union_can_shrink_from_four_thousand_ninety_eight_ids` stays green unchanged.
* **Level.** Rust unit tests placed in the target-independent `portable_tests` module

## Decisions and trade-offs

* **Native filter-first, not renderer truncation.** The renderer cannot tell stale from live ids
  without a native round-trip (P4: shape-only validation), so any per-family truncation either drops
  live ids — and an omitted live id in a trusted family is swept, losing a capability — or must also
  untrust the truncated family, which disables cleanup for every purpose that family covers (P3:
  e.g. one overflowing PGN family keeps all `PgnWorkspace`/`PgnFile`/`PgnReadOnlyFile` entries).
  Native already knows the registry and already discards unknown ids; moving the check after that
  discard is the smallest change that removes the mechanism.
* **Additive headroom, not `max(…)`.** `max(65_536, registry)` would re-create the defect for a
  grandfathered registry larger than the constant plus any stale ids; addition cannot.
* **Keep a raw cap at all.** P5: the payload is already deserialized, so the cap bounds only the
  dedupe/filter work; it is kept as the defense-in-depth shape the finding's option names and
  `d-20260906-09` established, with a value chosen so no realistic renderer reaches it.
* **Decisions cited, not reopened.** `d-20260906-09` (bound registry ids at 4,096, owner-collector
  reclamation, untrusted families conservative) is preserved: registry bounds are untouched; only
  the request admission check moves. `d-20260924-07` / `d-20260925-01` / `d-20260925-02` (expanded
  directories ≤ 1,000, workspace-scoped) are unaffected.

## Decided autonomously

* **Question:** Where does the startup path-owner request bound apply, given that the renderer's
  union of owner families can carry ids native no longer knows?
  **Governs:** f-20260924-01.
  **Chosen:** Native discards ids absent from the registry before applying the retained-id bound;
  a separate raw-input hard cap of `authority_id_input_limit() + 65_536` (`MAX_STARTUP_OWNER_UNKNOWN_IDS`)
  refuses only absurd requests, before any proportional work. Renderer collection and the IPC type
  are unchanged.
  **Rejected:** Renderer-side per-family prioritisation and truncation (cannot distinguish stale
  from live ids; truncation sweeps live capabilities or, with untrusting, disables cleanup for whole
  purposes); `max(constant, registry)` as the raw cap (re-creates the refusal for large grandfathered
  registries); removing the raw cap (drops the existing defense-in-depth shape for no gain).
  **Reason:** Unknown ids are discarded by native anyway and cannot be retained, so counting them is
  the defect's mechanism; the known subset is bounded by the registry by construction.
  **Reversal path:** measured startup cost or memory evidence may change the 65,536 allowance; a
  renderer-side bound would need a native membership query first.

## Risks / open questions

* **Input above the allowance.** The renderer union has no proven ceiling (P4); a request with more
  than 65,536 unknown ids beyond the registry limit is still refused as today. Named known limit; not
  reachable in ordinary use.
* **Large raw requests near the cap.** ~70k short strings deduplicated in a `BTreeSet` is
  milliseconds; the test at the cap boundary measures it implicitly. No open product question.
* **Renderer still warns only.** A refusal above the cap still only `warn`s (P6); with the allowance
  well above ordinary input this is a named known limit, unchanged from today.
