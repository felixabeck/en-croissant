## Approach

### O1 — Answer the open question: per-runner accounting, not scheduler allocation

The traced arithmetic shows every OOM run sized runners from the correct cap and ran mutation
alone, so the scheduler allocation behaved as designed and the per-runner charge is what is
wrong for the current workload. The fix changes the measured per-runner (and, if measured
higher, per-parent) constant only. Scheduler shares, `ONE_WAVE_BYTES`, slot selection logic, the
`agent-gate` cap and the reserve are unchanged.

### O2 — One-off measurement of the current per-runner footprint

Before choosing the value, measure the current workload once inside a real `agent-gate` scope
on this host, at the known-clean `GATE_MEMORY_BYTES=6442450944` sizing (one slot, four
runners), all four packages, full suite (`pnpm mutation:frontend`). A disposable sampler kept
under `$RUN_TMP` (never committed, deleted with the run) records, per Stryker test-runner process
and per Stryker parent process, the maximum `VmHWM` seen, plus the scope's `memory.peak`,
`memory.swap.peak` and `memory.events` captured inside the scope before it exits. Four runners
live longest and therefore grow most, so their high-water mark is an upper bound for the same
package at higher concurrency.

Sampler contract (measurement validity, all fail closed):

* Roles come from `/proc/<pid>/cmdline` under the scope's `cgroup.procs`: **runner** (a Stryker
  test-runner child process), **parent** (the `stryker.js run` process) and **helper** (any other
  Node child of the parent that is not a runner). The parent figure O3 consumes is, per package,
  the maximum of parent `VmHWM` + the sum of concurrently live helper `VmHWM`s.
* A pid that vanishes between `cgroup.procs` and its `/proc` read is skipped (normal race). Any
  other read or parse error, a sampler exit other than 0, a package for which fewer than four
  distinct runner pids were seen, or a package for which no parent pid was identified makes the
  measurement **red**. Unclassified Node pids are recorded by cmdline in `summary.json` so a
  misclassified parent or helper is visible.
* The sampler resolves its cgroup directory from the `0::` line of `/proc/self/cgroup` and refuses
  (red) unless that directory is an `agent-gate-*.scope`; it never falls back to the root cgroup.
* The measurement is also **red** if the scope's `memory.events` shows `oom` or `oom_kill` above 0,
  `memory.swap.peak` is above 0, or any package's `stryker.log` reports an unexpected worker exit.
  An OOM-truncated runner undercounts its footprint (`d-20260930-03`), so such a run never feeds O3.
* A red measurement is not retried with altered sizing; it stops the run and is reported with its
  raw evidence. This is a measurement input for the constant, required by
gate-performance rule (b) ("each project records its measured per-worker memory"); it is not a
validation criterion and not persistent machinery, which keeps `d-20261002-03`'s rejection of a
reinstated RSS sampler intact. The raw sample file and per-package maxima are retained in the
handoff.

### O3 — Set the constants from the measurement

`STRYKER_PARENT_BYTES` = max(640 MiB, largest per-package parent figure from O2 × 1.25), the
product rounded up to a whole 64 MiB. `STRYKER_RUNNER_BYTES` = the largest of three values, the
first two rounded up to a whole 64 MiB before comparison:

1. **Measured:** largest runner `VmHWM` across the four packages × 1.25. The 25% headroom matches
   the adjacent Rust constant's convention (`:44-50`, about 28%).
2. **Observed-failure bound:** the smallest whole-64-MiB value at which, with the new

## Approach

### O1 — Answer the open question: per-runner accounting, not scheduler allocation

The traced arithmetic shows every OOM run sized runners from the correct cap and ran mutation
alone, so the scheduler allocation behaved as designed and the per-runner charge is what is
wrong for the current workload. The fix changes the measured per-runner (and, if measured
higher, per-parent) constant only. Scheduler shares, `ONE_WAVE_BYTES`, slot selection logic, the
`agent-gate` cap and the reserve are unchanged.

### O2 — One-off measurement of the current per-runner footprint

Before choosing the value, measure the current workload once inside a real `agent-gate` scope
on this host, at the known-clean `GATE_MEMORY_BYTES=6442450944` sizing (one slot, four
runners), all four packages, full suite (`pnpm mutation:frontend`). A disposable sampler kept
under `$RUN_TMP` (never committed, deleted with the run) records, per Stryker test-runner process
and per Stryker parent process, the maximum `VmHWM` seen, plus the scope's `memory.peak`,
`memory.swap.peak` and `memory.events` captured inside the scope before it exits. Four runners
live longest and therefore grow most, so their high-water mark is an upper bound for the same
package at higher concurrency.

Sampler contract (measurement validity, all fail closed):

* Roles come from `/proc/<pid>/cmdline` under the scope's `cgroup.procs`: **runner** (a Stryker
  test-runner child process), **parent** (the `stryker.js run` process) and **helper** (any other
  Node child of the parent that is not a runner). The parent figure O3 consumes is, per package,
  the maximum of parent `VmHWM` + the sum of concurrently live helper `VmHWM`s.
* A pid that vanishes between `cgroup.procs` and its `/proc` read is skipped (normal race). Any
  other read or parse error, a sampler exit other than 0, a package for which fewer than four
  distinct runner pids were seen, or a package for which no parent pid was identified makes the
  measurement **red**. Unclassified Node pids are recorded by cmdline in `summary.json` so a
  misclassified parent or helper is visible.
* The sampler resolves its cgroup directory from the `0::` line of `/proc/self/cgroup` and refuses
  (red) unless that directory is an `agent-gate-*.scope`; it never falls back to the root cgroup.
* The measurement is also **red** if the scope's `memory.events` shows `oom` or `oom_kill` above 0,
  `memory.swap.peak` is above 0, or any package's `stryker.log` reports an unexpected worker exit.
  An OOM-truncated runner undercounts its footprint (`d-20260930-03`), so such a run never feeds O3.
* A red measurement is not retried with altered sizing; it stops the run and is reported with its
  raw evidence. This is a measurement input for the constant, required by
gate-performance rule (b) ("each project records its measured per-worker memory"); it is not a
validation criterion and not persistent machinery, which keeps `d-20261002-03`'s rejection of a
reinstated RSS sampler intact. The raw sample file and per-package maxima are retained in the
handoff.

### O3 — Set the constants from the measurement

`STRYKER_PARENT_BYTES` = max(640 MiB, largest per-package parent figure from O2 × 1.25), the
product rounded up to a whole 64 MiB. `STRYKER_RUNNER_BYTES` = the largest of three values, the
first two rounded up to a whole 64 MiB before comparison:

1. **Measured:** largest runner `VmHWM` across the four packages × 1.25. The 25% headroom matches
   the adjacent Rust constant's convention (`:44-50`, about 28%).
2. **Observed-failure bound:** the smallest whole-64-MiB value at which, with the new
   `STRYKER_PARENT_BYTES` and the unchanged 1 GiB reserve, one package slot holding the whole
   budget (`strykerSlots` with `packageCount` 1, the shape of every observed failure) admits at
   most 6 runners at `memory.max` 11596410880 and at most 12 at 19327352832. Seven and thirteen
   runners in one slot were the counts the kernel OOM-killed under those exact caps. The bound
   says nothing about multi-slot shapes: each extra slot charges another `STRYKER_PARENT_BYTES`,
   so a four-package split (for example 3 × 2 at 1344 MiB on 11596410880) can commit more of the
   budget than the one-slot shape. O5 run B is the empirical check for that shape.
3. **Floor:** the current `Math.round(1.2 * 1024 ** 3)`.

The constant must also keep the 7 GiB fallback valid: `STRYKER_PARENT_BYTES + STRYKER_RUNNER_BYTES`
≤ `CONSERVATIVE_CGROUP_LIMIT_BYTES − UNSIZED_PROCESS_RESERVE_BYTES`, so `workerCount` at the
fallback still admits at least one runner. If it would not, the run stops and returns to plan
review instead of changing the fallback. The comment above each
constant names the date, commit, host scope cap, concurrency, per-package maxima and the reason
the previous figure failed (f-20261022-05). `CONSERVATIVE_STRYKER_RUNNERS` is recomputed from the
new constants at the 7 GiB fallback budget (it is a derived figure the tests assert), and its
comment is updated. One constant for all packages: per-package constants are rejected unless the
measurement shows the largest package exceeding the smallest by more than 2×, in which case the
plan returns to review rather than adding per-package machinery silently. Bounding growth with
`maxTestRunnerReuse` stays rejected (`d-20260930-03`: 40 still reached 6.53 GiB at eight runners).

## Decisions and trade-offs

Decided autonomously (full auto; technical, no product impact):

* **Question:** Does f-20261022-05 need different per-runner accounting or a different scheduler
