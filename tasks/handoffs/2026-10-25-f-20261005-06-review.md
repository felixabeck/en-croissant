## Threat model and non-goals

The adversary is a download that continues on the native side after the renderer document that started it is gone. ## Approach

### Safe cause on the existing progress item

Add an optional `failure` field to `ProgressItem` and `ProgressEvent`: `Option<ErrorPayload>`, `#[serde(default, skip_serializing_if = "Option::is_none")]`, specta-optional. Running, succeeded, cancelled, and cleared events stay wire-compatible, including listeners that deserialize `ProgressEvent` today. Do not add a progress event. Do not add a payload argument to `update_progress_with_state` or `set_progress_state`.

Add an optional `progress_generation` to `ErrorPayload`, serde-default and specta-optional. It stays absent on the payload stored in the progress item. It is set only on the file-download, Lichess, and Chess.com command error returned after `begin_progress` has run, and it is that lease's generation. A command error returned before `begin_progress` leaves it absent. Engine command errors leave it absent. `renderer_payload()` itself does not set it. Do not put native diagnostics in the field.

Add `Deserialize` and `PartialEq` on `ErrorPayload`. Add `Deserialize` on `ErrorCategory`, `ErrorPayloadTag`, `RemoteHttpRejection`, `RootFailure`, `EngineFailureKind`, `EngineExitStatus`, `EngineTerminalEntry`, and `EngineTerminalSnapshot`. Do not add `Deserialize` to `Error`. Do not change `EngineKey`.

Add one native publish function that transitions the lease to `Failed` at `0.0` and stores the payload on that same transition. The high-water rule stays. A generation that is already terminal is left unchanged, including its payload. A stale lease fails before the write. The clear event is still the synthetic cancelled item and its `failure` is absent.

Build the payload from the error by reference. For `Error::Io`, apply the same source replacement `sanitize_download_error` uses, then `renderer_payload()`. For every other non-cancellation error, call `renderer_payload()` on the borrowed error. Never call `diagnostic()`. Cancellation publishes no payload.

`download_to_destination_inner` publishes that payload on every non-cancellation `report_download_error`. `download_engine_archive_core` and `run_engine_install_completion` report the failed state without a payload. Chess.com `report_terminal_progress` publishes the payload only for a non-cancellation failure, computed before `complete_preserving_result` moves the result. Player-statistics `JobProgress::complete` stays unchanged.

This heading does not register a command. Phase 1 does not edit `src-tauri/src/main.rs`.

### One announcement for a document that does not own the download

Register the read-only command `failed_progress_snapshot` beside `get_progress` in the same phase as its consumer. It returns the stored items whose `failure` is present. It does not clear them and it does not accept a payload. Add it to `collect_commands!`. The only production consumer is a platform-facade method beside `getProgress`. The observer calls that facade. Do not widen any other capability. Regenerate bindings with `pnpm bindings:generate`. Do not hand-edit `src/bindings/generated.ts`.

The document does not own progress ids. It owns generations. `runDownloadJob` attempts the card id. `downloadLichess` and `downloadChessCom` attempt the ticket, because that ticket is the progress id. `withDownloadTicket` does not record an attempt: `download_file`'s ticket is not the progress id. Do not edit `AccountCard.tsx`. Account, database, and puzzle attempts use this same generation rule.

An attempt has two stages. It is preparing from the moment it is recorded until the native download command is invoked. It is invoked from that call until the job map entry is deleted, including the unsuccessful clear. `runDownloadJob` invokes only inside `run`, after the ticket is set. `downloadLichess` and `downloadChessCom` invoke at `downloadLichessGames` and `downloadChessComGames`, not when the ticket is minted. Cancellation while the ticket is still unset never invokes native work.

A generation G of id I becomes a candidate only when this document observes an event for I that is `running`, progress `0`, not `cleared`, generation G, while that attempt is invoked. An event during preparation is not a candidate. The observer handles each event. It does not treat a later snapshot as a substitute for the start event.

During preparation the observer does not buffer and does not take candidates. An unowned `failed` payload is announced immediately, because this attempt has not started native work. While the attempt is invoked, it does not announce a `failed` payload for I yet. It buffers that event by generation. A `failed` payload for any other id is never buffered by this attempt.

When the attempt ends without invocation, or settles with the duplicate-admission conflict, renderer message exactly `Conflict: download progress is already active`, discard every candidate and arm nothing. Announce each buffered `failed` payload for I once. Those generations stay unowned. A refused or never-invoked attempt does not call `begin_progress` for a new generation. The conflict, when that was the settlement, is the only toast from the attempt itself. The announced payload is the survivor's failure, not a second toast for the conflict.

When an invoked attempt settles any other way, commit every candidate observed while it was invoked. Also commit generation H when the command error carries `progress_generation` H. Suppress a buffered `failed` payload only when its generation was committed. Announce every other buffered `failed` payload now, including when no candidate was observed and the command error carries no generation. Do not hold a buffered failure for a later start event. Do not arm a binding on the next `running` event. A native error before `begin_progress`, such as creating the staging file, carries no generation: the survivor payload is announced when the attempt settles. A later `running` event for the survivor does not become ownership, and the survivor's later `failed` payload is announced. A command error that carries H keeps H silent, including when `running` at progress `0` and `failed` for H arrive after the command result. A different generation is not owned. ## Approach

### Safe cause on the existing progress item

Add an optional `failure` field to `ProgressItem` and `ProgressEvent`: `Option<ErrorPayload>`, `#[serde(default, skip_serializing_if = "Option::is_none")]`, specta-optional. Running, succeeded, cancelled, and cleared events stay wire-compatible, including listeners that deserialize `ProgressEvent` today. Do not add a progress event. Do not add a payload argument to `update_progress_with_state`. Do not reintroduce `set_progress_state` or `start_progress`.

Add an optional `progress_generation` to `ErrorPayload`, serde-default and specta-optional. It stays absent on the payload stored in the progress item. It is set only on the `download_file` command error returned after `begin_progress` has run, and it is that lease's generation. A command error returned before `begin_progress` leaves it absent. Lichess, Chess.com, account-import, and engine command errors leave it absent. `renderer_payload()` itself does not set it. Do not put native diagnostics in the field.

Add `Deserialize` and `PartialEq` on `ErrorPayload`. Add `Deserialize` on `ErrorCategory`, `ErrorPayloadTag`, `RemoteHttpRejection`, `RootFailure`, `EngineFailureKind`, `EngineExitStatus`, `EngineTerminalEntry`, and `EngineTerminalSnapshot`. Those nested types already derive `PartialEq`; do not add a second derive. Do not add `Deserialize` to `Error`. Do not change `EngineKey`.

Add one native publish function that transitions the lease to `Failed` at `0.0` and stores the payload on that same transition. The high-water rule stays. A generation that is already terminal is left unchanged, including its payload. A stale lease fails before the write. The clear event is still the synthetic cancelled item and its `failure` is absent.

Build the payload from the error by reference. For `Error::Io`, apply the same source replacement `sanitize_download_error` uses, then `renderer_payload()`. For every other non-cancellation error, call `renderer_payload()` on the borrowed error. Never call `diagnostic()`. Cancellation publishes no payload.

Publish that payload only for a non-cancellation failure of the `download_file` command. `download_lichess_games_runtime` uses the same `download_to_destination` and must still report the failed state with no payload. `download_engine_archive_core` and `run_engine_install_completion` report the failed state without a payload. Chess.com `report_terminal_progress` stays without a payload. Account conversion's failed progress update stays without a payload. Player-statistics `JobProgress::complete` stays unchanged. Do not edit `src-tauri/src/infra/operations/accounts.rs`.

This heading does not register a command. Phase 1 does not edit `src-tauri/src/main.rs`.

### One announcement for a document that does not own the download

Register the read-only command `failed_progress_snapshot` beside `get_progress` in the same phase as its consumer. It returns the stored items whose `failure` is present. It does not clear them and it does not accept a payload. Add it to `collect_commands!`. The only production consumer is a platform-facade method beside `getProgress`. The observer calls that facade. Do not widen any other capability. Regenerate bindings with `pnpm bindings:generate`. Do not hand-edit `src/bindings/generated.ts`.

The document does not own progress ids. It owns generations. `runDownloadJob` attempts the card id. That card id is the progress id for Add Database and Add Puzzle. `withDownloadTicket` does not record an attempt: `download_file`'s ticket is not the progress id. Do not edit `AccountCard.tsx`, `src/utils/lichess/api.tsx`, or `src/utils/chess.com/api.tsx`. Account import is not an attempt in this observer. Database and puzzle attempts use this same generation rule.

An attempt has two stages. It is preparing from the moment it is recorded until the native download command is invoked. It is invoked from that call until the job map entry is deleted, including the unsuccessful clear. `runDownloadJob` invokes only inside `run`, after the ticket is set. Cancellation while the ticket is still unset never invokes native work.

A `running` event does not create ownership. The only ownership evidence is `progress_generation` on the command error after it has passed through `normalizeError`. The observer handles each event. It does not treat a later snapshot as a substitute for that field.

During preparation the observer does not buffer. An unowned `failed` payload is announced immediately, because this attempt has not started native work. While the attempt is invoked, including the unsuccessful clear before the job entry is deleted, it does not announce a `failed` payload for I yet. It buffers that event by generation. A `failed` payload for any other id is never buffered by this attempt.

When the attempt ends without invocation, or settles with the duplicate-admission conflict, renderer message exactly `Conflict: download progress is already active`, announce each buffered `failed` payload for I once and own nothing. A refused or never-invoked attempt does not call `begin_progress`. The conflict, when that was the settlement, is the only toast from the attempt itself. The announced payload is the survivor's failure, not a second toast for the conflict.

When an invoked attempt settles any other way, read the generation only from the normalized command error. Commit H when that error carries `progress_generation` H. Suppress a buffered `failed` payload only for H, and announce every other buffered generation. When the error carries no generation, commit nothing and announce every buffered failure. A `running` event observed during invocation or during the clear does not commit a generation, including when it arrives before a pre-begin error settles. Do not arm a binding on the next `running` event. A native error before `begin_progress`, such as creating the staging file, carries no generation. The survivor's `failed` payload is announced whether it was buffered during the clear or arrives afterwards. A command error that carries H keeps H silent, including when `running` at progress `0` and `failed` for H arrive after the command result. A different generation is not owned. A committed generation stays owned after the job map entry is deleted. Do not use the `WeakSet` in `errors.ts`.

`normalizeError` in `src/platform/errors.ts` drops fields it does not copy, and `TauriCommandError` stores that result. Copy `progress_generation` onto the normalized error when it is the same wire type as `ProgressEvent.generation`. Leave it absent otherwise. The observer reads it from the error `unwrapCommand` throws, not from a raw payload that production discards.

The starter subscribes to the existing progress event first, then reads `failed_progress_snapshot`. For a `failed` item that carries `failure`, is not `cleared`, and whose `(id, generation)` is not owned and not buffered for an attempt still in preparation or invoked, it calls `notifyUnlessCancelled` with `Common.Error` and the payload, and no domain, once per `(id, generation)`. It then best-effort `clearProgress` only because that item is already `failed`. It does not clear a live `running` bar. A snapshot failure is logged and does not block startup or the listener. Committed generations are ignored, so the live `runUnlessCancelled` remains the only toast for a generation this document started, including when the `failed` event is delivered before the command settles and again after the job entry is gone. An account completion failure is not that toast.

Call the starter from `src/index.tsx` on the success path, before `await initializeEngineCompletions()`, in its own failure isolation. An observer failure must not skip engine recovery, and engine recovery failure must not skip the observer. Extend the existing `src/index.test.tsx` mock so the new import does not call a partial `tauri` mock, and assert the starter runs before render.

Do not notify from `useProgress` or from `ProgressButton`.
