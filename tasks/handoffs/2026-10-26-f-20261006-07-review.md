# Plan: Files durability notice

## Goal

When a Files create, create-folder, rename, metadata edit, or move lands and the native command reports durability uncertainty, the page relists and closes the dialog as it does today, and it also shows one non-blocking notice that the change was saved and must not be retried. Trash, restore, and permanent delete keep their confirm dialog open and show that same sentence when the rejection is a durability error. A partial removal keeps the sentence it already shows.

## MANDATE

Files page mutation dialogs close silently when the change landed but its durability is uncertain.

* **ID:** f-20261006-07 · **Status:** open · **Area:** frontend-ui · **Root:** - · **Entry:** build · **Blocked:** none
* **Defect:** when a workspace mutation returns `CommittedDurabilityUncertain` (renderer category `applied-despite-error`), `runAppliedMutationWithRefresh` relists and resolves to `undefined`, and the dialog closes exactly as on a durable success. The user is never told that the change landed but may not survive a crash or power loss, although `d-20260906-03` rejected "treating uncertainty as success anywhere a user is promised a saved file" for the backend half of the same contract. The trash path is the only Files mutation that keeps a separate applied-despite-error warning.
* **Open question:** should the Files create, rename, move and metadata dialogs show a non-blocking "saved, but the disk did not confirm it" notice after the relist (one shared message for the `durability` category, `d-20260901-34`), and does that notice belong in `runAppliedMutationWithRefresh` itself, so every caller gets it, or in each dialog? Coordinate with `f-20261005-04` (category-specific copy for the same dialogs) and `f-20261003-09` (operation-and-cleanup relist).

Pickup at `d59ec916e6a9e58507f2b7f7812d9b7360a1fb74`: the silent close still holds. `f-20261005-04` and `f-20261003-09` are handled and are not members of this slice. No co-located joiner is planned. Tier stays `build`: the notice text, which outcomes receive it, and which owner shows it are one design across the Files dialogs and the shared confirm message. `d-20260906-03` already forbids treating uncertainty as success; it does not choose the renderer owner.

## Threat model and non-goals

The input is a workspace mutation the native command has already committed, whose result is `ErrorCategory::Durability` because a later sync or registry step could not be confirmed. The person at the keyboard may submit again. A second create can add another file; a second rename or move can target the already-moved entry. The notice exists so that retry is not offered as the next step.

Out of the threat model: a renderer that forges an error payload, a crash before the command returns, and any outcome that is not `backendCategory === "durability"` after `normalizeError`. Partial removal and operation-and-cleanup stay on their existing sentences. No native command, IPC category, or binding changes.

The key is a literal at both call sites only if they both go through that function; they do not each inline a second copy of the sentence.

### Which outcome gets it

The sentence is selected only when `normalizeError(cause).backendCategory === "durability"`. Category `applied-despite-error` without that backend category keeps `Common.ConfirmationError.applied-despite-error`. Operation-and-cleanup, name taken, conflict, not-found, permission, validation, cancellation, and ordinary failures are unchanged.

A durability result is not `Files.OperationFailed` and is not an invitation to submit again. The notice does not interpolate `error.message`.

### Who shows it

`runAppliedMutationWithRefresh` and `runDestructiveWithRefresh` stay control-flow helpers. They do not import notifications and do not gain a user-facing sentence. `runAppliedMutationWithRefresh` still returns the command value on durable success, still returns `undefined` after a swallowed applied error whose refresh succeeded, and still rethrows that error when the refresh throws.

`runFilesMutationWithRefresh` tells its caller which of these happened:

- durable commit, carrying the command value
- durability uncertainty whose refresh succeeded

A durability uncertainty whose refresh throws still rejects with the original cause. Any other rejection, including operation-and-cleanup and a swallowed applied error that is not durability, stays as it is today. A swallowed non-durability applied error still looks like a commit to the Files caller. None of the five form commands return `PartialRemoval`; that limit stays named rather than gaining a second sentence.

`runMutation` is the only Files owner of the five form commands, including dialog move and drag move:

- On a durable commit, if this presentation still owns the page, run the existing success close. Show no durability notice.
- On durability uncertainty after a successful refresh, if this presentation still owns the page, run that same close, then show the notice.
- On a rejected durability uncertainty, if this presentation still owns the page, run that same close and show the notice. Do not set the action error.
- If this presentation no longer owns the page, do not close whatever is open now. Still show the notice, because the native change already landed.
- Show the notice at most once per outcome.

The notice is `notifications.show` with `color: "orange"` and `message` set to the shared sentence, and with no title. That matches the account durability notice, not the red collection-selection failure.

`confirmationErrorMessage` returns the shared sentence when the normalized backend category is `durability`. `ConfirmModal` otherwise stays as it is: a resolved confirm closes, a rejection stays open with the alert. Trash, restore, and permanent delete therefore keep the dialog open, show the durability sentence for a durability rejection, and show no toast. A partial-removal rejection still shows `Common.ConfirmationError.applied-despite-error`.

Database delete is the other production confirm that lets `runDestructiveWithRefresh` reject into `ConfirmModal`. A durability rejection there shows this same sentence and stays open. Puzzle delete and engine removal catch their own errors and do not change. No database, puzzle, or engine component is edited.

## Decisions and trade-offs

Decided autonomously for the adopter to record. Reversal of each is a new decision naming the evidence below.

1. Show the notice, do not leave the silent close.
   - Chosen: the sentence in "One durability sentence", orange, non-blocking, after the relist, including when the relist itself fails.
   - Rejected: keeping the silent close. `d-20260906-03` already rejected treating uncertainty as success where a saved file is promised, and the account surfaces already say "Do not retry."
   - Rejected: a red error that says the operation failed or asks the user to try again. That is the current `Files.OperationFailed` fallback, and a retry can create a second file.

2. The platform helpers do not own the sentence.
   - Chosen: `runFilesMutationWithRefresh` reports durability to `runMutation`, and `confirmationErrorMessage` selects the sentence for confirms.
   - Rejected: putting the toast inside `runAppliedMutationWithRefresh`. Its only production caller is Files, and a UI import in the platform helper would also fire for a swallowed partial removal. `d-20261025-16` keeps `runDestructiveWithRefresh` free of a new notice.
   - Rejected: a new IPC variant or a new renderer category. `d-20261025-16` and `d-20260904-06` already give the renderer `backendCategory: "durability"`.

3. Trash, restore, and permanent delete stay on the confirm dialog.
   - Chosen: they still reject, the dialog stays open, and only the durability sentence changes.
   - Rejected: routing them through `runAppliedMutationWithRefresh`. `d-20261025-16` rejected that because it treats applied-despite-error as success and closes the warning.

4. Database delete inherits the confirm sentence and nothing else.
   - Chosen: no edit under `src/components/databases/`. The shared confirm function is the one place a rejecting confirm reads the sentence.
   - Rejected: a Files-only prop on `ConfirmModal`. It would fork the durability sentence the mandate asks to share, and database delete would keep the partial-removal sentence for a committed-but-unconfirmed delete.

# Plan: Files durability notice

## Goal

When a Files create, create-folder, rename, metadata edit, or move lands and the native command reports durability uncertainty, the page relists and closes the dialog as it does today, and it also shows one non-blocking notice that the change was saved and must not be retried. Trash, restore, and permanent delete keep their confirm dialog open and show that same sentence when the rejection is a durability error. A partial removal keeps the sentence it already shows.

## MANDATE

Files page mutation dialogs close silently when the change landed but its durability is uncertain.

* **ID:** f-20261006-07 · **Status:** open · **Area:** frontend-ui · **Root:** - · **Entry:** build · **Blocked:** none
* **Defect:** when a workspace mutation returns `CommittedDurabilityUncertain` (renderer category `applied-despite-error`), `runAppliedMutationWithRefresh` relists and resolves to `undefined`, and the dialog closes exactly as on a durable success. The user is never told that the change landed but may not survive a crash or power loss, although `d-20260906-03` rejected "treating uncertainty as success anywhere a user is promised a saved file" for the backend half of the same contract. The trash path is the only Files mutation that keeps a separate applied-despite-error warning.
* **Open question:** should the Files create, rename, move and metadata dialogs show a non-blocking "saved, but the disk did not confirm it" notice after the relist (one shared message for the `durability` category, `d-20260901-34`), and does that notice belong in `runAppliedMutationWithRefresh` itself, so every caller gets it, or in each dialog? Pickup at `d59ec916e6a9e58507f2b7f7812d9b7360a1fb74`: the silent close still holds. `f-20261005-04` and `f-20261003-09` are handled and are not members of this slice. No co-located joiner is planned. The input is a workspace mutation the native command has already committed, whose result is `ErrorCategory::Durability` because a later sync or registry step could not be confirmed. Partial removal and operation-and-cleanup stay on their existing sentences. No native command, IPC category, or binding changes.

The key is a literal at both call sites only if they both go through that function; they do not each inline a second copy of the sentence.

### Which outcome gets it

The sentence is selected only when `normalizeError(cause).backendCategory === "durability"`. Category `applied-despite-error` without that backend category keeps `Common.ConfirmationError.applied-despite-error`. Operation-and-cleanup, name taken, conflict, not-found, permission, validation, cancellation, and ordinary failures are unchanged.

A durability result is not `Files.OperationFailed` and is not an invitation to submit again. The notice does not interpolate `error.message`.

### Who shows it

`runAppliedMutationWithRefresh` and `runDestructiveWithRefresh` stay control-flow helpers. They do not import notifications and do not gain a user-facing sentence. `runAppliedMutationWithRefresh` still returns the command value on durable success, still returns `undefined` after a swallowed applied error whose refresh succeeded, and still rethrows that error when the refresh throws.

`runFilesMutationWithRefresh` tells its caller which of these happened:

- durable commit, carrying the command value
- durability uncertainty whose refresh succeeded

A durability uncertainty whose refresh throws still rejects with the original cause. Any other rejection, including operation-and-cleanup and a swallowed applied error that is not durability, stays as it is today. A swallowed non-durability applied error still looks like a commit to the Files caller. None of the five form commands return `PartialRemoval`; that limit stays named rather than gaining a second sentence.

`runMutation` is the only Files owner of the five form commands, including dialog move and drag move:

- On a durable commit, if this presentation still owns the page, run the existing success close. Show no durability notice.
- On durability uncertainty after a successful refresh, if this presentation still owns the page, run that same close, then show the notice.
- On a rejected durability uncertainty, if this presentation still owns the page, run that same close and show the notice. Do not set the action error.
- If this presentation no longer owns the page, do not close whatever is open now. Still show the notice, because the native change already landed.
- Show the notice at most once per outcome.

The notice is `notifications.show` with `color: "orange"` and `message` set to the shared sentence, and with no title. That matches the account durability notice, not the red collection-selection failure.

`confirmationErrorMessage` returns the shared sentence when the normalized backend category is `durability`. `ConfirmModal` otherwise stays as it is: a resolved confirm closes, a rejection stays open with the alert. Trash, restore, and permanent delete show the durability sentence for a durability rejection, and show no toast. A partial-removal rejection still shows `Common.ConfirmationError.applied-despite-error`.

### Confirm stays mounted

The three Files confirms stay mounted until `ConfirmModal` closes them. A refresh that runs while the command is still rejecting must not clear `deleteTarget`, `restoreTarget`, or `purgeTarget`.

Trash's refresh currently clears `deleteTarget` before it relists. `runDestructiveWithRefresh` runs that refresh on a durability rejection and only then rethrows, so the dialog unmounts and the alert never appears. That clear belongs only to the resolved path. `ConfirmModal` already calls `onClose` after `onConfirm` resolves, and that close removes the trash dialog after a durable success. The durability refresh still records the trashed entry, clears the selection, and relists. Restore and permanent delete already relist through `clearTrashAndRelist`, which does not clear their targets, and they keep that split. Operation-and-cleanup still relists through the cleanup callback and still leaves the dialog open.

Database delete is the other production confirm that lets `runDestructiveWithRefresh` reject into `ConfirmModal`. Its refresh does not clear `deleteModal`. A durability rejection there shows this same sentence and stays open. Puzzle delete and engine removal catch their own errors and do not change. No database, puzzle, or engine component is edited.

## Decisions and trade-offs

Decided autonomously for the adopter to record. Reversal of each is a new decision naming the evidence below.

1. Show the notice, do not leave the silent close.
   - Chosen: the sentence in "One durability sentence", orange, non-blocking, after the relist, including when the relist itself fails.
   - Rejected: keeping the silent close. `d-20260906-03` already rejected treating uncertainty as success where a saved file is promised, and the account surfaces already say "Do not retry."
   - Rejected: a red error that says the operation failed or asks the user to try again. That is the current `Files.OperationFailed` fallback, and a retry can create a second file.

2. The platform helpers do not own the sentence.
   - Chosen: `runFilesMutationWithRefresh` reports durability to `runMutation`, and `confirmationErrorMessage` selects the sentence for confirms.
   - Rejected: putting the toast inside `runAppliedMutationWithRefresh`. Its only production caller is Files, and a UI import in the platform helper would also fire for a swallowed partial removal. `d-20261025-16` keeps `runDestructiveWithRefresh` free of a new notice.
   - Rejected: a new IPC variant or a new renderer category. `d-20261025-16` and `d-20260904-06` already give the renderer `backendCategory: "durability"`.

3. Trash, restore, and permanent delete stay on the confirm dialog.
   - Chosen: they still reject, the dialog stays open, and only the durability sentence changes. The refresh that runs before that rejection does not clear the confirmation target. Trash stops clearing `deleteTarget` inside that refresh. A durable success still closes through `ConfirmModal`'s `onClose`.
   - Rejected: routing them through `runAppliedMutationWithRefresh`. `d-20261025-16` rejected that because it treats applied-despite-error as success and closes the warning.
   - Rejected: changing only the sentence and leaving trash's refresh as it is. That refresh unmounts the dialog before the alert can render.

4. Database delete inherits the confirm sentence and nothing else.
   - Chosen: no edit under `src/components/databases/`. The shared confirm function is the one place a rejecting confirm reads the sentence.
   - Rejected: a Files-only prop on `ConfirmModal`. It would fork the durability sentence the mandate asks to share, and database delete would keep the partial-removal sentence for a committed-but-unconfirmed delete.

None that park. A substring-only `Error` whose message contains "committed but durability uncertain:" normalizes to `applied-despite-error` with no `backendCategory`. ## Approach

### One durability sentence

One literal key, `Common.DurabilityUncertain`, is the only new user-facing sentence. English (`en-US` and `en-GB`):

`fr-FR` and `it-IT` use the same U+2019 apostrophe the neighbouring account strings already use. No catalogue stores the native diagnostic or the English sentence except `en-US` and `en-GB`.

A single exported function returns `t("Common.DurabilityUncertain")` with that English `defaultValue`. `confirmationErrorMessage` and the Files notice both call it. The key is a literal at both call sites only if they both go through that function; they do not each inline a second copy of the sentence.

### Which outcome gets it

The sentence is selected only when `normalizeError(cause).backendCategory === "durability"`. Category `applied-despite-error` without that backend category keeps `Common.ConfirmationError.applied-despite-error`. Operation-and-cleanup, name taken, conflict, not-found, permission, validation, cancellation, and ordinary failures are unchanged.

A durability result is not `Files.OperationFailed` and is not an invitation to submit again. The notice does not interpolate `error.message`.

### Who shows it

`runAppliedMutationWithRefresh` and `runDestructiveWithRefresh` stay control-flow helpers. They do not import notifications and do not gain a user-facing sentence. `runAppliedMutationWithRefresh` still returns the command value on durable success, still returns `undefined` after a swallowed applied error whose refresh succeeded, and still rethrows that error when the refresh throws.

`runFilesMutationWithRefresh` tells its caller which of these happened:

- durable commit, carrying the command value
- durability uncertainty whose refresh succeeded

A durability uncertainty whose refresh throws still rejects with the original cause. Any other rejection, including operation-and-cleanup and a swallowed applied error that is not durability, stays as it is today. A swallowed non-durability applied error still looks like a commit to the Files caller. None of the five form commands return `PartialRemoval`; that limit stays named rather than gaining a second sentence.

`runMutation` is the only Files owner of the five form commands, including dialog move and drag move:

- On a durable commit, if this presentation still owns the page, run the existing success close. Show no durability notice.
- On durability uncertainty after a successful refresh, if this presentation still owns the page, run that same close, then show the notice.
- On a rejected durability uncertainty, if this presentation still owns the page, run that same close and show the notice. Do not set the action error.
- If this presentation no longer owns the page, do not close whatever is open now. Still show the notice, because the native change already landed.
- Show the notice at most once per outcome.

The notice is `notifications.show` with `color: "orange"` and `message` set to the shared sentence, and with no title. That matches the account durability notice, not the red collection-selection failure.

`confirmationErrorMessage` returns the shared sentence when the normalized backend category is `durability`. `ConfirmModal` otherwise stays as it is: a resolved confirm closes, a rejection stays open with the alert. Trash, restore, and permanent delete show the durability sentence for a durability rejection, and show no toast. A partial-removal rejection still shows `Common.ConfirmationError.applied-despite-error`.

### Confirm stays mounted

The three Files confirms stay mounted until `ConfirmModal` closes them. A refresh that runs while the command is still rejecting must not clear `deleteTarget`, `restoreTarget`, or `purgeTarget`.

Trash's refresh currently clears `deleteTarget` before it relists. `runDestructiveWithRefresh` runs that refresh on a durability rejection and only then rethrows, so the dialog unmounts and the alert never appears. That clear belongs only to the resolved path. `ConfirmModal` already calls `onClose` after `onConfirm` resolves, and that close removes the trash dialog after a durable success. The durability refresh still records the trashed entry, clears the selection, and relists. Restore and permanent delete already relist through `clearTrashAndRelist`, which does not clear their targets, and they keep that split. Operation-and-cleanup still relists through the cleanup callback and still leaves the dialog open.

A durable success whose relist fails still closes, and it does not show `Common.ConfirmationError.unexpected`. Trash's success refresh swallows the listing failure the same way `clearTrashAndRelist` does, so `onConfirm` resolves and `ConfirmModal` calls `onClose`. `runDestructiveWithRefresh` stays unchanged: on the success path it propagates a refresh rejection, which is why the swallow lives in the trash refresh and not in the helper. A durability rejection still shows the durability sentence when that relist fails. `runDestructiveWithRefresh` already discards a refresh rejection on `applied-despite-error` and rethrows the original cause.

Database delete is the other production confirm that lets `runDestructiveWithRefresh` reject into `ConfirmModal`. Its refresh does not clear `deleteModal`. A durability rejection there shows this same sentence and stays open. Puzzle delete and engine removal catch their own errors and do not change. No database, puzzle, or engine component is edited.

## Decisions and trade-offs

Decided autonomously for the adopter to record. Reversal of each is a new decision naming the evidence below.

1. Show the notice, do not leave the silent close.
   - Chosen: the sentence in "One durability sentence", orange, non-blocking, after the relist, including when the relist itself fails.
   - Rejected: keeping the silent close. `d-20260906-03` already rejected treating uncertainty as success where a saved file is promised, and the account surfaces already say "Do not retry."
   - Rejected: a red error that says the operation failed or asks the user to try again. That is the current `Files.OperationFailed` fallback, and a retry can create a second file.

2. The platform helpers do not own the sentence.
   - Chosen: `runFilesMutationWithRefresh` reports durability to `runMutation`, and `confirmationErrorMessage` selects the sentence for confirms.
   - Rejected: putting the toast inside `runAppliedMutationWithRefresh`. Its only production caller is Files, and a UI import in the platform helper would also fire for a swallowed partial removal. `d-20261025-16` keeps `runDestructiveWithRefresh` free of a new notice.
   - Rejected: a new IPC variant or a new renderer category. `d-20261025-16` and `d-20260904-06` already give the renderer `backendCategory: "durability"`.

3. Trash, restore, and permanent delete stay on the confirm dialog.
   - Chosen: they still reject, the dialog stays open, and only the durability sentence changes. The refresh that runs before that rejection does not clear the confirmation target. Trash stops clearing `deleteTarget` inside that refresh. A durable success still closes through `ConfirmModal`'s `onClose`. A listing failure after that durable success is swallowed in the trash refresh, as `clearTrashAndRelist` already does, so the closed dialog does not ask the user to retry a trash that landed.
   - Rejected: routing them through `runAppliedMutationWithRefresh`. `d-20261025-16` rejected that because it treats applied-despite-error as success and closes the warning.
   - Rejected: changing only the sentence and leaving trash's refresh as it is. That refresh unmounts the dialog before the alert can render.

4. Database delete inherits the confirm sentence and nothing else.
   - Chosen: no edit under `src/components/databases/`. The shared confirm function is the one place a rejecting confirm reads the sentence.
   - Rejected: a Files-only prop on `ConfirmModal`. It would fork the durability sentence the mandate asks to share, and database delete would keep the partial-removal sentence for a committed-but-unconfirmed delete.

# Plan: Files durability notice

## Goal

When a Files create, create-folder, rename, metadata edit, or move lands and the native command reports durability uncertainty, the page relists and closes the dialog as it does today, and it also shows one non-blocking notice that the change was saved and must not be retried. Trash, restore, and permanent delete keep their confirm dialog open and show that same sentence when the rejection is a durability error. A partial removal keeps the sentence it already shows.

Files page mutation dialogs close silently when the change landed but its durability is uncertain.

* **ID:** f-20261006-07 · **Status:** open · **Area:** frontend-ui · **Root:** - · **Entry:** build · **Blocked:** none

## Threat model and non-goals

The input is a workspace mutation the native command has already committed, whose result is `ErrorCategory::Durability` because a later sync or registry step could not be confirmed. The person at the keyboard may submit again. A second create can add another file; a second rename or move can target the already-moved entry. ## Decisions and trade-offs

Decided autonomously for the adopter to record. Reversal of each is a new decision naming the evidence below.

1. Show the notice, do not leave the silent close.
   - Chosen: the sentence in "One durability sentence", orange, non-blocking, after the relist, including when the relist itself fails.
   - Rejected: keeping the silent close. `d-20260906-03` already rejected treating uncertainty as success where a saved file is promised, and the account surfaces already say "Do not retry."
   - Rejected: a red error that says the operation failed or asks the user to try again. That is the current `Files.OperationFailed` fallback, and a retry can create a second file.

2. The platform helpers do not own the sentence.
   - Chosen: `runFilesMutationWithRefresh` reports durability to `runMutation`, and `confirmationErrorMessage` selects the sentence for confirms.
   - Rejected: putting the toast inside `runAppliedMutationWithRefresh`. Its only production caller is Files, and a UI import in the platform helper would also fire for a swallowed partial removal. `d-20261025-16` keeps `runDestructiveWithRefresh` free of a new notice.
   - Rejected: a new IPC variant or a new renderer category. `d-20261025-16` and `d-20260904-06` already give the renderer `backendCategory: "durability"`.

3. Trash, restore, and permanent delete stay on the confirm dialog.
   - Chosen: they still reject, the dialog stays open, and only the durability sentence changes. The refresh that runs before that rejection does not clear the confirmation target. Trash stops clearing `deleteTarget` inside that refresh. A durable success still closes through `ConfirmModal`'s `onClose`. A listing failure after that durable success is swallowed in the trash refresh, as `clearTrashAndRelist` already does, so the closed dialog does not ask the user to retry a trash that landed.
   - Rejected: routing them through `runAppliedMutationWithRefresh`. `d-20261025-16` rejected that because it treats applied-despite-error as success and closes the warning.
   - Rejected: changing only the sentence and leaving trash's refresh as it is. That refresh unmounts the dialog before the alert can render.

4. Database delete inherits the confirm sentence and nothing else.
   - Chosen: no edit under `src/components/databases/`. The shared confirm function is the one place a rejecting confirm reads the sentence.
   - Rejected: a Files-only prop on `ConfirmModal`. It would fork the durability sentence the mandate asks to share, and database delete would keep the partial-removal sentence for a committed-but-unconfirmed delete.
