## Approach

### O1 — synchronous workspace initialization with one initial snapshot

Authority: MANDATE's "move the load/repair out of module evaluation" and "keeping hydration semantics identical".

Replace the eager workspace value with a synchronous initializer owned by the atom module. It establishes one shared initial workspace snapshot per module instance only after `loadWorkspace` returns. Production calls it explicitly in `src/index.tsx` before bootstrap starts asynchronous native/session work or renders anything. Every direct workspace atom read or write also reaches that same initializer when needed, so test and non-React callers require no async readiness protocol and always observe a complete workspace in the same call.

Subsequent atom reads, repeated initialization and React remounts do not re-run hydration, allocate new initial IDs or repeat migration/deletion. New Jotai stores start from that same original snapshot, as they do today, while acknowledged edits remain local to the store that made them. A stored empty workspace remains distinct from an uninitialized workspace. Failed initialization does not publish or cache a successful default. Existing exceptions propagate and existing refusal/repair reporting remains intact. Capture `originalPathOwnersSnapshot` before this initializer can repair storage, including a direct atom access outside `index.tsx`.

The tab-admission boundary in `src/utils/tabs.ts` must establish that same initial snapshot before it allocates an ID or stages any tree. This applies even when `commitNewTab` is the first workspace operation and its setter is supplied directly by a caller. Hydration must never run its orphan sweep between tree staging and metadata admission. Initialization failure precedes staging and cannot leave a new tree or admitted metadata. The shared staging boundary covers `createTab`, `commitNewTab` and replacement, without duplicating initialization logic or weakening orphan cleanup.

## Decided autonomously

* **Question:** Where does workspace hydration execute? **Chosen:** one synchronous atom-owned initializer, explicitly invoked by renderer startup and lazily reached by direct atom callers. **Rejected:** async effect hydration, which exposes incomplete state, and bootstrap-only initialization, which requires every direct/test caller to wire readiness. **Reason:** the existing synchronous public atom API must continue working in the same call. **Reversal path:** atom initialization and the index bootstrap call, with importer tests and mutation evidence.
* **Question:** What lifetime should validation schemas have? **Chosen:** operation-local construction with shared recursive graphs inside each operation. **Rejected:** import-time schema construction, which retains the static mutants, and one module-level lazy cache, whose construction can be attributed only to the first covering test. **Reason:** schema construction must be observable under each validation test's active mutant without adding reset plumbing. **Reversal path:** schema construction boundaries after matched runtime and mutation measurements establish a better lifetime with equivalent coverage.
* **Question:** Who verifies startup behavior? **Chosen:** the adopting agent through unit/importer tests, container e2e and the existing real-app driver. **Rejected:** asking Felix to perform a manual startup check. **Reason:** this changes lifecycle timing rather than taste or native GTK chrome. **Reversal path:** the existing verify-ui contract if a limitation in the driver is actually found.
