# Plan: Database-list writes supersede before they publish

## Goal

A database-list write must not let a listing that started before the write become the list the user sees afterwards. Every such write retires in-flight `"databases"` generations, waits until those retirements have been delivered, then publishes one owned post-write read and lets SWR revalidate. Remount and StrictMode rejoin of a live listing that no write has retired stays as it is.

## MANDATE

Cluster: `finding:f-20261004-09`. Ids: `f-20261004-09`.

### `useNativeRequestOwner.run` rejoins an in-flight listing that started before a newer mutation, so a later revalidation can publish stale data

* **ID:** f-20261004-09 · **Status:** open · **Area:** frontend-ui · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** 0fa004d0-93e4-4004-86d2-6652e891bd6e
* **Where:** `src/hooks/useNativeRequestOwner.ts:111-120` (`run`: `if (current) return current.promise` for any live, non-abandoned generation); consumers of the shared SWR "databases" key: `src/components/home/Accounts.tsx:31`, `src/components/databases/DatabasesPage.tsx:90-95` (and its `mutate()` after "Add games", `:540`), `src/components/databases/DatabaseView.tsx:26-29`, `src/components/panels/info/InfoPanel.tsx:101-102`, `src/components/panels/database/DatabasePanel.tsx:146-147`; producer `src/components/home/AccountCard.tsx` (`mutate("databases", getDatabases(), { revalidate: false })` after an account import's cleanup).

## Approach

### O1. Retire before publish

Every `"databases"` write awaits retirement of the current generations before it publishes or revalidates. Retirement is `owner.supersede()`: the generation set is cleared synchronously, both abort signals fire, and the await resolves only after those generation promises have settled. The publish or revalidation starts after that await. A revalidation that starts after this retirement cannot rejoin a generation the write retired, because `run` only rejoins a live non-abandoned generation still in the set.

### O2. One write-refresh helper

`refreshDatabaseList(owner, mutate)` lives next to `fetchDatabaseList`. `owner` is a `NativeRequestOwner`. `mutate` is SWR's global `ScopedMutator` from `useSWRConfig`, so AccountCard and the library call one function. The helper awaits `owner.supersede()`, then returns `mutate(DATABASE_LIST_KEY, fetchDatabaseList(owner))` with no options object. Default `revalidate` stays true. It must not pass `revalidate: false`.

Callers that already have a bound `KeyedMutator` do not pass that bound function. They pass the global mutator. AccountCard already has it. The library already has `mutateCache`.

Edit, delete, index, and duplicate removal today revalidate with a bare `mutate()` after the native write. Routing them through the helper adds one owned list read plus SWR's revalidation read. That extra read is the same shape AccountCard already uses. One write-refresh shape is the point of the helper. `chooseWorkspace` is not routed through it.

### O3. Route the writers

* AccountCard `refreshDatabases` becomes the helper. The surrounding `try`/`catch`, including the import-failed log path, stays. Behavior matches the two lines it replaces.
* The library's add-games refresh callback and its import-refresh-failed retry await the helper instead of `mutate(await getDatabases())`.
* Delete keeps a floating call: `void refreshDatabaseList(...)`. Do not add a catch. Today's `void mutate()` is also unhandled.
* GeneralSettings receives a function whose returned promise is the helper. `.then(() => mutate())` stays, so the existing `.catch` still receives a rejected refresh. Widen the prop type so that promise is part of the type.
* IndexInput's `reload` is the helper. `.then(() => reload())` stays, so its `.catch` still receives a rejected refresh.

# Plan: Database-list writes supersede before they publish

## Goal

A database-list write must not let a listing that started before the write become the list the user sees afterwards. Every such write retires in-flight `"databases"` generations and waits until those retirements have been delivered. A caller that already awaits an owned read then publishes that read. ## Approach

### O1. Retire before publish

Every `"databases"` write awaits retirement of the current generations before it publishes or revalidates. Retirement is `owner.supersede()`: the generation set is cleared synchronously, both abort signals fire, and the await resolves only after those generation promises have settled. The publish or revalidation starts after that await. A revalidation that starts after this retirement cannot rejoin a generation the write retired, because `run` only rejoins a live non-abandoned generation still in the set.

### O2. Two write-refresh helpers

Both helpers live next to `fetchDatabaseList`. `owner` is a `NativeRequestOwner`. `mutate` is SWR's global `ScopedMutator` from `useSWRConfig`, so AccountCard and the library call the same functions. Callers that already have a bound `KeyedMutator` pass this global mutator. AccountCard already has it. The library already has `mutateCache`. Owner instances differ; the cache key is the same, so `supersede` on either owner clears the shared generation set. The owner is non-null for the string `DATABASE_LIST_KEY`.

`refreshDatabaseList(owner, mutate)` awaits `owner.supersede()`, then returns `mutate(DATABASE_LIST_KEY, fetchDatabaseList(owner))` with no options object. Default `revalidate` stays true. It must not pass `revalidate: false`. The supplied read is data-bearing, so a rejected owned read rejects the returned promise. Use it only where the caller already awaits an owned read and already surfaces that rejection.

`revalidateDatabaseList(owner, mutate)` awaits `owner.supersede()`, then returns `mutate(DATABASE_LIST_KEY)` with no data and no options. That is a bare revalidation after retirement. A fetcher failure is stored as `cache.error` and the returned promise fulfills. Use it where today's refresh is a bare `mutate()` and the failure surface is `cache.error`, not a toast and not the native command's outcome.

`chooseWorkspace` is not routed through either helper.

### O5. Regression that fails by assertion

Add real-SWR coverage in `useDatabaseList.test.tsx`. `dedupingInterval: 0`, `shouldRetryOnError: false`. The mounted fetcher and `fetchDatabaseList` both call `owner.run`. For `refreshDatabaseList`, the post-retirement read is `fetchDatabaseList(owner)`, passed as the data argument. Record the cache error at that `owner.run` entry. Do not record it inside the request body `run` schedules on a later microtask: that body runs after the retirement catch even when `supersede` was not awaited, so it cannot tell the two controls apart. A new owned read means that entry scheduled a new request body. A rejoin returns the pending generation and does not. Do not use a wall-clock timeout. Do not await the helper before the assertions in steps 3 and 4. Awaiting it first deadlocks when `supersede` is absent, because the data-bearing mutate then waits on the still-pending first generation.

Sequence for `refreshDatabaseList`:

1. Mount the list. The first fetcher call returns deferred L and leaves it pending.
2. Invoke `refreshDatabaseList` and do not await it yet. Flush only microtasks.
3. A new owned read has started. This fails immediately when `supersede` is not called: `run` rejoins L, and no new request body is scheduled.
4. That new read already observed the retired generation's terminal cache state when it entered `owner.run`: `cache.get(DATABASE_LIST_KEY).error` is the cancellation. The flag is false when `supersede()` is called and not awaited, because `owner.run` then runs in the same turn as the abort, before the catch microtask. # Plan: Database-list writes supersede before they publish

## Goal

A database-list write must not let a listing that started before the write become the list the user sees afterwards. Every such write retires in-flight `"databases"` generations and waits until those retirements have been delivered. A caller that already awaits an owned read then publishes that read. ## Approach

### O1. Retire before publish

Every `"databases"` write awaits retirement of the current generations before it publishes or revalidates. Retirement is `owner.supersede()`: the generation set is cleared synchronously, both abort signals fire, and the await resolves only after those generation promises have settled. The publish or revalidation starts after that await. A revalidation that starts after this retirement cannot rejoin a generation the write retired, because `run` only rejoins a live non-abandoned generation still in the set.

### O2. Two write-refresh helpers

Both helpers live next to `fetchDatabaseList`. `owner` is a `NativeRequestOwner`. `mutate` is SWR's global `ScopedMutator` from `useSWRConfig`, so AccountCard and the library call the same functions. Callers that already have a bound `KeyedMutator` pass this global mutator. AccountCard already has it. The library already has `mutateCache`. Owner instances differ; the cache key is the same, so `supersede` on either owner clears the shared generation set. The owner is non-null for the string `DATABASE_LIST_KEY`.

`refreshDatabaseList(owner, mutate)` awaits `owner.supersede()`, then returns `mutate(DATABASE_LIST_KEY, fetchDatabaseList(owner))` with no options object. Default `revalidate` stays true. It must not pass `revalidate: false`. The supplied read is data-bearing, so a rejected owned read rejects the returned promise. Use it only where the caller already awaits an owned read and already surfaces that rejection.

`revalidateDatabaseList(owner, mutate)` awaits `owner.supersede()`, then returns `mutate(DATABASE_LIST_KEY)` with no data and no options. That is a bare revalidation after retirement. A fetcher failure is stored as `cache.error` and the returned promise fulfills. Use it where today's refresh is a bare `mutate()` and the failure surface is `cache.error`, not a toast and not the native command's outcome.

`chooseWorkspace` is not routed through either helper.

### O3. Route the writers

* AccountCard `refreshDatabases` becomes `refreshDatabaseList`. The surrounding `try`/`catch`, including the import-failed log path, stays. Behavior matches the two lines it replaces.
* The library's add-games refresh callback and its import-refresh-failed retry await `refreshDatabaseList` instead of `mutate(await getDatabases())`.
* AddDatabase stops taking `setDatabases: KeyedMutator<DatabaseList>`. It takes `reloadDatabases: () => Promise<unknown>`, implemented as `() => refreshDatabaseList(owner, mutateCache)`. Local convert and the reference download await `reloadDatabases()` and do not call `getDatabases`. `refreshAfterDatabaseConversion` is not edited. A rejected reload is still the refresh failure that helper already logs and, on the success path, notifies. The download path stays inside `runUnlessCancelled`, so a rejected reload still fails that attempt.

* GeneralSettings' `.then(() => mutate())` and `.catch` stay. The function passed as `mutate` is `revalidateDatabaseList`. A list-read failure must not reject, so the existing catch still receives only `editDbInfo`'s rejection and does not notify for a list refresh. The prop may stay `() => void`.

### O5. Regression that fails by assertion

Add real-SWR coverage in `useDatabaseList.test.tsx`. `dedupingInterval: 0`, `shouldRetryOnError: false`. The mounted fetcher and `fetchDatabaseList` both call `owner.run`. For `refreshDatabaseList`, the post-retirement read is `fetchDatabaseList(owner)`, passed as the data argument. Record the cache error at that `owner.run` entry. ### plan-r4.md

# Plan: Database-list writes supersede before they publish

## Goal

A database-list write must not let a listing that started before the write become the list the user sees afterwards. Every such write retires in-flight `"databases"` generations and waits until those retirements have been delivered. A caller that already awaits an owned read then publishes that read. A caller whose refresh is a bare revalidation then revalidates with no data argument. Remount and StrictMode rejoin of a live listing that no write has retired stays as it is.

## Approach

### O1. Retire before publish

Every `"databases"` write awaits retirement of the current generations before it publishes or revalidates. Retirement is `owner.supersede()`: the generation set is cleared synchronously, both abort signals fire, and the await resolves only after those generation promises have settled. The publish or revalidation starts after that await. A revalidation that starts after this retirement cannot rejoin a generation the write retired, because `run` only rejoins a live non-abandoned generation still in the set.

### O2. Two write-refresh helpers

Both helpers live next to `fetchDatabaseList`. `owner` is a `NativeRequestOwner`. `mutate` is SWR's global `ScopedMutator` from `useSWRConfig`, so AccountCard and the library call the same functions. Callers that already have a bound `KeyedMutator` pass this global mutator. AccountCard already has it. The library already has `mutateCache`. Owner instances differ; the cache key is the same, so `supersede` on either owner clears the shared generation set. The owner is non-null for the string `DATABASE_LIST_KEY`.

`refreshDatabaseList(owner, mutate)` awaits `owner.supersede()`, then returns `mutate(DATABASE_LIST_KEY, fetchDatabaseList(owner))` with no options object. Default `revalidate` stays true. It must not pass `revalidate: false`. The supplied read is data-bearing, so a rejected owned read rejects the returned promise. Use it only where the caller already awaits an owned read and already surfaces that rejection.

`revalidateDatabaseList(owner, mutate)` awaits `owner.supersede()`, then returns `mutate(DATABASE_LIST_KEY)` with no data and no options. That is a bare revalidation after retirement. A fetcher failure is stored as `cache.error` and the returned promise fulfills. Use it where today's refresh is a bare `mutate()` and the failure surface is `cache.error`, not a toast and not the native command's outcome.

`chooseWorkspace` is not routed through either helper.

### O3. Route the writers

* AccountCard `refreshDatabases` becomes `refreshDatabaseList`. The surrounding `try`/`catch`, including the import-failed log path, stays. Behavior matches the two lines it replaces.
* The library's add-games refresh callback and its import-refresh-failed retry await `refreshDatabaseList` instead of `mutate(await getDatabases())`.
* AddDatabase stops taking `setDatabases: KeyedMutator<DatabaseList>`. It takes `reloadDatabases: () => Promise<unknown>`, implemented as `() => refreshDatabaseList(owner, mutateCache)`. Local convert and the reference download await `reloadDatabases()` and do not call `getDatabases`. `refreshAfterDatabaseConversion` is not edited. A rejected reload is still the refresh failure that helper already logs and, on the success path, notifies. The download path stays inside `runUnlessCancelled`, so a rejected reload still fails that attempt.
* Delete calls `void revalidateDatabaseList(...)` at the end of `invalidateDeletedDatabaseState`. Do not return that promise from the invalidate callback. `runDestructiveWithRefresh` would otherwise await it, and a rejection would replace the committed native delete. Do not add a catch and do not add a notification. The list-read failure stays `cache.error`.
* GeneralSettings' `.then(() => mutate())` and `.catch` stay. The function passed as `mutate` is `revalidateDatabaseList`. A list-read failure must not reject, so the existing catch still receives only `editDbInfo`'s rejection and does not notify for a list refresh. The prop may stay `() => void`.
* IndexInput's `reload` is `revalidateDatabaseList`. `.then(() => reload())` stays. A list-read failure must not reject, so its `.catch` still receives only the index command's rejection.
* DuplicateRemover's `reload` is `revalidateDatabaseList`. `runCleanup` still calls `reload()` without returning or awaiting it, on success and on failure. The returned promise must not reject on a list-read failure, so there is no unhandled rejection and no new notification. The native cleanup failure still notifies as today.

The library Load Retry button and `DatabaseView`'s retry stay `void mutate()`. `chooseWorkspace` stays `await databaseOwner.supersede(); await mutate();`. Do not supersede on retry.

### O4. Leave the owner primitive alone

`useNativeRequestOwner.ts` is not edited. No per-key epoch. No supersede inside `run`. No read of SWR's `MUTATION` map. Remount rejoin, "one subscriber leaving preserves the request", and explicit revalidation that retires abandoned work stay covered by the existing owner tests. `reconcileWorkspaceListing`, `refreshDatabaseGameQueries`, `useDatabaseContentValidation`, and `PlayerMerger` are not edited.

### O5. Regression that fails by assertion

Add real-SWR coverage in `useDatabaseList.test.tsx`. `dedupingInterval: 0`, `shouldRetryOnError: false`. The mounted fetcher and `fetchDatabaseList` both call `owner.run`. For `refreshDatabaseList`, the post-retirement read is `fetchDatabaseList(owner)`, passed as the data argument. Record the cache error at that `owner.run` entry. Do not record it inside the request body `run` schedules on a later microtask: that body runs after the retirement catch even when `supersede` was not awaited, so it cannot tell the two controls apart. A new owned read means that entry scheduled a new request body. A rejoin returns the pending generation and does not. Do not use a wall-clock timeout. Do not await the helper before the assertions in steps 3 and 4. Awaiting it first deadlocks when `supersede` is absent, because the data-bearing mutate then waits on the still-pending first generation.

Sequence for `refreshDatabaseList`:

1. Mount the list. The first fetcher call returns deferred L and leaves it pending.
2. Invoke `refreshDatabaseList` and do not await it yet. Flush only microtasks.
3. A new owned read has started. This fails immediately when `supersede` is not called: `run` rejoins L, and no new request body is scheduled.
4. That new read already observed the retired generation's terminal cache state when it entered `owner.run`: `cache.get(DATABASE_LIST_KEY).error` is the cancellation. The flag is false when `supersede()` is called and not awaited, because `owner.run` then runs in the same turn as the abort, before the catch microtask. After the microtask flush, the flag is true only when the helper awaited `supersede`.
5. Resolve the owned read and the post-mutation revalidation (`startRevalidate`, default `revalidate` true) with the fresh list, not with L. The third fetcher call is that revalidation and is also fresh. Then await the helper.
6. Resolve L with the stale list. Flush microtasks.
7. Cache data is the fresh list. Cache error is not the cancellation error.

The green path is retirement delivered before the owned read. Do not reject the old generation from inside `run` after the fresh fetch has started.

Same file: `revalidateDatabaseList`'s returned promise fulfills when its fetcher rejects, and `cache.error` is that failure. That case is not the rejoin proof. The rejoin proof is the same pending L, through `revalidateDatabaseList` itself:

1. Mount the list. The first fetcher call returns deferred L and leaves it pending.
2. Invoke `revalidateDatabaseList` and do not await it yet. Flush only microtasks. Awaiting it first deadlocks when `supersede` is absent, because the bare revalidation waits on L.
3. The mounted fetcher has entered `owner.run` again and scheduled a new request body. This fails immediately when `supersede` is not called: bare `mutate` rejoins L. For this helper the mounted fetcher is the post-retirement read. Record the cache error at that `owner.run` entry, not inside the later request body.
4. That entry already observed the cancellation. The flag is false when `supersede()` is called and not awaited. After the microtask flush it is true only when the helper awaited `supersede`.
5. Resolve the new read with the fresh list, not with L. Then await the helper. The returned promise fulfills.
6. Resolve L with the stale list. Flush microtasks.
7. Cache data is the fresh list. Cache error is not the cancellation error.

A failure-surface test on an already settled list does not replace this sequence. Removing `supersede` from `revalidateDatabaseList` still passes a settled-list failure test, and it restores the rejoin for delete, edit, index, and duplicate removal.

### Decided autonomously

The adopter records this with `record-decision`. This planner does not.

* **Question:** How does a revalidation requested after a `"databases"` write refuse to rejoin a generation started before that write, without losing StrictMode and remount rejoin?
* **Chosen:** The missing call is `supersede` on the write, not a new discriminator inside `run`. Two helpers. `refreshDatabaseList` awaits `owner.supersede()` and then `mutate(DATABASE_LIST_KEY, fetchDatabaseList(owner))` with default revalidate. It is for callers that already await an owned read and already surface that rejection: AccountCard, add games, the import-refresh retry, and AddDatabase. `revalidateDatabaseList` awaits `owner.supersede()` and then `mutate(DATABASE_LIST_KEY)` with no data. It is for delete, edit, index, and duplicate removal, whose refresh today is a bare `mutate()` and whose failure surface is `cache.error`. `chooseWorkspace` stays on `d-20261003-24`. Retry buttons stay bare `mutate()`.
* **Rejected:** A per-key epoch bumped inside `supersede` and compared by `run`. The set clear already drops the joinable generation before the await, so the epoch bit is never observed. A forgotten bump fails the same way as a forgotten `supersede`. Superseding on every revalidation, including focus, peer mount, and retry. That aborts shared reads no write invalidated and breaks remount rejoin. Reading SWR's `MUTATION` map from `run`. Bare `mutate()` never sets it (`args.length < 3`), and it couples the owner to SWR internals. Routing `chooseWorkspace` through either helper. The data-bearing helper would add a read the settled root-switch sequence does not have. One data-bearing helper for every writer. Data-bearing `mutate` rejects when the supplied read rejects (`throwOnError` defaults true). Delete and duplicate removal float the refresh promise, so that rejection is unhandled, and a later successful revalidation would drop the `cache.error` the bare path records. Edit and index would newly toast a list-refresh failure that today is only `cache.error`.
* **Reason:** The open question's three mechanisms are not required once the writers that skip `supersede` are enumerated. `await supersede()` is already the discriminator `d-20261003-24` measured against SWR 2.4: the old promise rejects and is delivered before the next fetch, so the unchecked catch cannot land after the fresh publish. Remount rejoin only needs a live non-abandoned generation, which a write that has not happened must not destroy. Bare `mutate` after an awaited `supersede` cannot rejoin the retired pre-write generation, so those four callers do not need a second owned read.
* **Reversal:** A per-root SWR key, or a request API that refuses rejoin of a pre-write generation without an extra list read, proven against the same real-SWR regression. A second reversal of this choice parks under the ledger contract.
* **Authority:** `revalidateDatabaseList` was not in round 1. The MANDATE's open question asks how a revalidation requested after a write refuses to rejoin a generation started before it, without losing StrictMode and remount rejoin. The frozen threat model is that revalidation receiving the earlier read. Awaited `supersede` followed by a bare `mutate(DATABASE_LIST_KEY)` is that refusal. The data-bearing helper stays for callers that already publish an owned read. The Reviews row for round 2 records the same authority.
