# Plan: An oversized PGN game stays one list row

## Goal

A game list that reaches a PGN game larger than 10 MiB still shows the readable games in that load, and shows the oversized game as one stable row that is not opened, parsed, or deleted.

## MANDATE

f-20261004-06, entry=build, area frontend-ui. Pickup re-check at 4655c1126f02517f9321b19bfb38878e724aba45: the defect still holds. `read_games_core` still selects an oversized first game and `read_range_bytes` still returns `ResourceLimit`. `GameSelector.loadPage` still discards every row of a load whose later page throws. Entry stays `build`: the open question is how that game is represented so the visible-range effect does not retry it. `d-20261004-01` and `d-20261004-05` settle the page budget and the ordinary-failure discard; they do not settle this representation.

Verbatim finding:

One PGN game over 10 MiB blanks every row of the game list's load that reaches it.

* **ID:** f-20261004-06 · **Status:** open · **Area:** frontend-ui · **Root:** - · **Entry:** build · **Blocked:** none
* **Where:** `src/components/panels/info/GameSelector.tsx` (`loadPage`: any failed page discards every row of that load and resolves with none, `d-20261004-05`); `src-tauri/src/pgn.rs` (`read_games_core` always selects the first requested game, and `read_range_bytes` refuses a game over `MAX_PGN_BYTES` with `ResourceLimit`).
* **Defect:** when a visible range contains a game larger than 10 MiB, the continuation reaches a page whose first game is that one, the native call fails with `ResourceLimit`, and the whole load is discarded: every row of the range, including the readable games before and after it, stays `...` with one error notification, and the rows are only re-requested on the next visible-range change, which fails the same way. Before `f-20260914-05` the same file failed identically (the unbudgeted read hit the same per-game cap), so this is not a regression, but the byte-budgeted page contract now makes the unreadable game's position known exactly, which the renderer does not use.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` — fail the one item, not the whole operation. A file with one huge annotated game should still list its other games and let the user open them.
* **Open question:** how does the list represent an unreadable game without re-triggering the visible-range effect into a retry loop (the reason `d-20261004-05` merges nothing on failure): a native per-game placeholder result (`present: false` with an error label, changing the `StampedGame` contract and bindings), a renderer-side "unreadable" row recorded so the effect treats it as loaded, or skipping past the failing index and continuing the load?
* **Found by:** the orchestrator of the `f-20260914-05` build run while extending the real-app verification to an oversized game, 2026-10-04; derived from reading `loadPage` and `read_games_core`, not yet reproduced in the app.
* **Correction 2026-10-04:** the single-oversized-game case was reproduced (`1 ...` and two identical "Resource limit: PGN game exceeds 10 MiB" notifications). The mixed case, readable games before and after the oversized one, remains the unreproduced case this entry describes.

## Threat model and non-goals

The input is a local PGN the user already opened. Its cached index can name a game whose byte length is greater than 10 MiB, including a length past the end of the file and `u64::MAX`. The plan must decide that from the indexed length before any read, and must not allocate or return those bytes.

Not an adversary: a caller who matches on the English `ResourceLimit` display string, a second app instance, or a game that is under the cap but malformed. Cancellation, a revision change during the attempt, an inverted cached range, and a request past the end of the index stay on their existing error paths.

Non-goals: raising `MAX_PGN_BYTES` or `MAX_PAGE_BYTES`; opening or deleting the oversized game; changing `read_game`; renumbering the list; scanner boundary findings.

## Traced premises

- `StampedGame` is `{ pgn, stamp, revision, present }` in `src-tauri/src/pgn.rs:65-70` and `src/bindings/generated.ts:1388`. `present: false` is the empty slot past the last game on `read_game` (`src-tauri/src/pgn.rs:1276-1300`), not an unread body. `read_games_core` always sets `present: true` (`src-tauri/src/pgn.rs:1202-1209`).
- `MAX_PGN_BYTES` and `MAX_PAGE_BYTES` are both 10 MiB (`src-tauri/src/pgn.rs:88-90`, `d-20261004-02`).
- Selection always keeps the first requested range, then stops before a later range that would pass `MAX_PAGE_BYTES` (`src-tauri/src/pgn.rs:1183-1196`). `read_range_bytes` returns `ResourceLimit("PGN game exceeds 10 MiB")` when the length is over the cap, before reading (`src-tauri/src/pgn.rs:846-856`). `page_byte_budget_keeps_oversized_first_game_resource_limit` pins that error for `MAX_PGN_BYTES + 1` and `u64::MAX` on a file that is smaller than the seeded range (`src-tauri/src/pgn.rs:3040-3069`).
- `scan_and_read_ranges_blocking` reads only the ranges the selector returns, then keeps the attempt only when the revision is unchanged (`src-tauri/src/pgn.rs:931-956`). `d-20261008-08` discards a changed-revision attempt, up to three attempts, then `StaleGame`.
- `GameSelector.loadPage` loops `readGames` from `start` through `stop`, appends parsed rows, and on any throw notifies once unless the signal is already aborted and returns no rows (`src/components/panels/info/GameSelector.tsx:56-86`). The merge writes nothing when the list is empty (`src/components/panels/info/GameSelector.tsx:89-95`). The effect requests a visible span that still has a missing index (`src/components/panels/info/GameSelector.tsx:112-126`). A later-page failure is pinned to discard earlier rows (`src/components/panels/info/GameSelector.test.tsx:368-396`).
- `GameRow` activates on click through `setPage`, and on double-click and Enter through `onActivate` (`src/components/panels/info/GameSelector.tsx:202-215`, `src/components/common/gameOpen.tsx:40-54`). Delete requires a stamp and a revision (`src/components/panels/info/GameSelector.tsx:183-184`).
- InfoPanel's `setPage` loads that index with `readGame` (`src/components/panels/info/InfoPanel.tsx:357-399`). FileCard's `setPage` only changes the preview index. Its preview effect calls `readGames(page, page)` and stores `data[0].pgn`, notifying on throw (`src/components/files/FileCard.tsx:56-75`, `144-146`). Open uses `readGame` through `activateGame` (`src/components/files/FileCard.tsx:79-91`). Those are the only production `readGames` callers.
- `game_stamp` is the SHA-256 of the game bytes (`src-tauri/src/pgn.rs:961-963`). An optional Specta field is exported as an optional TypeScript property (`NormalizedGame.date` in `src/bindings/generated.ts:1317`).
- Supported locale ids are the sixteen names in `scripts/i18n-completeness.mjs`.

## Approach

### Omission row

`read_games` returns a successful one-element page when the first selected game's indexed length is greater than `MAX_PGN_BYTES`. The element is a `StampedGame` with `present: true`, `omission: TooLarge`, and empty `pgn` and `stamp`. The file revision is the attempt's revision. No game bytes are read and `game_stamp` is not computed. A later oversized game in the same request is still not selected, by the existing budget stop, so that call stays a short page of the preceding games and does not fail. The following call starts at the oversized index and returns the omission page. `read_game` still returns `ResourceLimit` and still reads nothing over the cap.

The selector returns the omission before `read_ranges`. An empty range list is the only input to that read. A changed revision discards the omission with the attempt, under `d-20261008-08`. Cancellation, an inverted range, a page over 1 000 games, and an index past the end stay errors.

`omission` is an optional Specta field. Absence means the body was returned. The only variant is `tooLarge`. Bindings are regenerated, not hand-edited.

This narrows `d-20261004-01` only for an oversized first game on `read_games`: the cap remains "do not materialise the body", and the call no longer fails. `d-20261004-02` and `d-20261004-05` stay. An ordinary failed page still discards the load and notifies once. A thrown `ResourceLimit` is not parsed.

### List and preview

`GameSelector.loadPage` maps each returned game on its own. `omission === "tooLarge"` becomes a row whose name is `Files.GameTooLarge`, with no identity and no `parsePGN`. Any other game in that array is mapped as today. The returned rows are merged, so the visible-range effect sees the index as loaded and does not request it again.

An omitted row does not call `setPage` or `onActivate` on click, double-click, or Enter. It stays in the list at its index, with the same index number. Delete stays unavailable because there is no identity. InfoPanel is unchanged: it never receives `setPage` for that row, so it does not call `read_game`.

FileCard's preview effect treats that result as the omitted state: no notification, the same label in place of `GamePreview`, and Open disabled. A readable preview is unchanged. An ordinary preview failure still notifies and clears the preview.

The key `Files.GameTooLarge` means "Too large to open" in English. Every supported locale has its own translation. `pnpm i18n:check` passes.

## Decisions and trade-offs

### Decided autonomously

Question: when the first game of a `read_games` page is over `MAX_PGN_BYTES`, does the call fail with `ResourceLimit`, or return one row whose body was not read?

Chosen: return one omitted `tooLarge` row, as Approach states. Supersedes only the "still fails with `ResourceLimit`" clause of `d-20261004-01`. The adopter records this with `record-decision` before implementation. Reversal: restore that error and `page_byte_budget_keeps_oversized_first_game_resource_limit`.

Rejected: matching the `ResourceLimit` display string in the renderer and skipping that index; skipping the index so later games move up; using `present: false` for an indexed game; hashing the body to mint a delete stamp; packing the omission and later games into one new selection type.

Reason: `d-20261004-01` rejected an over-budget page error because large-game files become unbrowsable, and required the body not to be materialised. It did not weigh `d-20261004-05`'s whole-load discard, which blanks the readable neighbours. The indexed length already identifies the game. A display string is not that contract.

### Left in force

`d-20261004-02`: both budgets stay 10 MiB. `d-20261004-05`: `GameSelector.loadPage` owns continuation; an ordinary failure discards the load, notifies once, and does not reject the promise. `d-20261008-08`: a changed revision discards the attempt.

## Risks / open questions

None for the adopter to ask Felix. The row label is the existing failure, shown on the row instead of a toast, and the neighbours become openable as the finding requires.

Known limit: the omitted row cannot be deleted or opened, because both need the body or its stamp. The list still shows it.

Co-located joiners `f-20260917-06`, `f-20260925-04`, `f-20261003-10`, and `f-20261004-05`. Scanner boundary behaviour. `read_game` success for an oversized game. Import, database search, and engine paths. A new IPC command or event.

## Threat model and non-goals

The input is a local PGN the user already opened. Its cached index can name a game whose byte length is greater than 10 MiB, including a length past the end of the file and `u64::MAX`. The plan must decide that from the indexed length before any read, and must not allocate or return those bytes.

Not an adversary: a caller who matches on the English `ResourceLimit` display string, a second app instance, or a game that is under the cap but malformed. Cancellation, a revision change during the attempt, an inverted cached range, and a request past the end of the index stay on their existing error paths.

Non-goals: raising `MAX_PGN_BYTES` or `MAX_PAGE_BYTES`; opening or deleting the oversized game; changing `read_game`; renumbering the list; scanner boundary findings.

## Approach

### Omission row

`read_games` returns a successful one-element page when the first selected game's indexed length is greater than `MAX_PGN_BYTES`. The element is a `StampedGame` with `present: true`, `omission: TooLarge`, and empty `pgn` and `stamp`. The file revision is the attempt's revision. No game bytes are read and `game_stamp` is not computed. A later oversized game in the same request is still not selected, by the existing budget stop, so that call stays a short page of the preceding games and does not fail. The following call starts at the oversized index and returns the omission page. `read_game` still returns `ResourceLimit` and still reads nothing over the cap.

The selector returns the omission before `read_ranges`. An empty range list is the only input to that read. A changed revision discards the omission with the attempt, under `d-20261008-08`. Cancellation, an inverted range, a page over 1 000 games, and an index past the end stay errors.

`omission` is an optional Specta field. Absence means the body was returned. The only variant is `tooLarge`. Bindings are regenerated, not hand-edited.

This narrows `d-20261004-01` only for an oversized first game on `read_games`: the cap remains "do not materialise the body", and the call no longer fails. `d-20261004-02` and `d-20261004-05` stay. An ordinary failed page still discards the load and notifies once. A thrown `ResourceLimit` is not parsed.

### List and preview

`GameSelector.loadPage` maps each returned game on its own. `omission === "tooLarge"` becomes a row whose name is `Files.GameTooLarge`, with no identity and no `parsePGN`. Any other game in that array is mapped as today. The returned rows are merged, so the visible-range effect sees the index as loaded and does not request it again.

An omitted row does not call `setPage` or `onActivate` on click, double-click, or Enter. It stays in the list at its index, with the same index number. Delete stays unavailable because there is no identity. InfoPanel is unchanged: it never receives `setPage` for that row, so it does not call `read_game`.

FileCard's preview effect treats that result as the omitted state: no notification, the same label in place of `GamePreview`, and Open disabled. A readable preview is unchanged. An ordinary preview failure still notifies and clears the preview.

The key `Files.GameTooLarge` means "Too large to open" in English. Every supported locale has its own translation. `pnpm i18n:check` passes.

## Decisions and trade-offs

### Decided autonomously

Question: when the first game of a `read_games` page is over `MAX_PGN_BYTES`, does the call fail with `ResourceLimit`, or return one row whose body was not read?

Chosen: return one omitted `tooLarge` row, as Approach states. Supersedes only the "still fails with `ResourceLimit`" clause of `d-20261004-01`. The adopter records this with `record-decision` before implementation. Reversal: restore that error and `page_byte_budget_keeps_oversized_first_game_resource_limit`.

Rejected: matching the `ResourceLimit` display string in the renderer and skipping that index; skipping the index so later games move up; using `present: false` for an indexed game; hashing the body to mint a delete stamp; packing the omission and later games into one new selection type.

Reason: `d-20261004-01` rejected an over-budget page error because large-game files become unbrowsable, and required the body not to be materialised. It did not weigh `d-20261004-05`'s whole-load discard, which blanks the readable neighbours. The indexed length already identifies the game. A display string is not that contract.

### Left in force

`d-20261004-02`: both budgets stay 10 MiB. `d-20261004-05`: `GameSelector.loadPage` owns continuation; an ordinary failure discards the load, notifies once, and does not reject the promise. `d-20261008-08`: a changed revision discards the attempt. `d-20261018-13` and `d-20261018-14` govern an unreadable workspace-listing child, including `Files.ChildUnreadable.TooLarge`. They do not supply the game-row label, and this plan does not reuse those keys.
