* **Dependencies:** none.

# Plan: Account export progress follows the operation

## Goal

A Chess.com or Lichess account export reports progress under the download ticket the renderer already holds, and a second export of the same account is refused while one is active, including from another window.

## MANDATE

f-20260914-14, verbatim:

Account game exports share one progress id per player across concurrent exports.

* **Where:** `src-tauri/src/chesscom.rs:290` emits `ProgressEvent` under `chesscom_${player}`; `src-tauri/src/fs.rs:1113` uses `lichess_${player}` for `download_to_destination`; `src/components/home/AccountCard.tsx:180-193` filters on that same id and ignores the command's unique `job_id`.
* **Defect (reported):** the progress id is derived from the account, not the operation. Two exports for the same player (repeated click, two windows) emit the same id, so both consumers see interleaved progress and one terminal state ends the other's bar.
* **Why it matters:** `.claude/rules/ipc-events.md` — anything broadcast carries an id that identifies the operation the receiver asked for.
* **Open question:** use the renderer-minted `job_id` as the progress id for account exports, or refuse a second concurrent export per account?

The line numbers in that Where clause have moved. The traced premises below are the current sites. The obligation is the defect and the open question, not those historical line numbers.

## Threat model and non-goals

Two ordinary windows, or two clicks in one window, start an export of the same account before the first export has finished. The renderer is not treated as an adversary that forges another window's ticket: `prepare_download` already binds the ticket to the calling webview, and `claim_download` rejects a ticket whose owner does not match. Deliberately evasive player strings that differ only by case stay distinct accounts, as they do today. No new capability scope, no new event, no bearer token in the renderer.

## Approach

### O1 — The export's progress id is the download ticket

`download_chess_com_games` and `download_lichess_games_runtime` pass `job_id` as the progress id to `begin_progress` / `download_to_destination` and store that same `job_id` on the accepted download. The canonical account string (`chesscom_{player}`, or `lichess_{}` plus the existing `lichess_user_segment` result) is no longer the event id. Lichess still validates the player through `lichess_user_segment` before `claim_download`. Chess.com keeps today's unvalidated player string. `download_file` and the engine-archive download are unchanged.

This is the open question's first option. The ticket is the operation the receiver asked for (`ipc-events.md`). A terminal frame for one ticket cannot finish another ticket's entry, because `progress.rs` keys the entry by id.

### O2 — One active export per account, across windows

`claim_download` gains an admission key and an exclusive flag, separate from the progress id.

* Account exports pass the canonical account string as the admission key and exclusive true.
* Every other caller passes its existing progress id as the admission key and exclusive false.

Under the registry mutex, a new claim is refused with the existing `Error::Conflict("download progress is already active")` when an uncancelled accepted download has the same admission key and either the new claim is exclusive or the owner matches. Exclusive therefore refuses a second window. Non-exclusive keeps today's owner-scoped behavior, including the test that two owners may share a progress id.

The refusal is the open question's second option, and it is required together with O1. O1 alone makes the progress id unique, so the current owner-and-progress-id check would stop refusing a repeated click. The check has to move to the account key. Making that key exclusive across owners is what stops two windows writing `${player}_${provider}.pgn` at once. The lease still ends when the download command returns (`OperationLease::drop`), so the refusal covers the export the finding names, not the later import.

### O3 — The card follows the ticket for both phases of that click

`downloadChessCom` and `downloadLichess` take an optional callback invoked with the ticket inside `withDownloadTicket` before the command is awaited. `AccountCard` stores that ticket in a ref the already-mounted progress listener reads. The listener applies a frame only when `payload.id` equals that ref. It does not apply `accountKey`.

After the download returns, the import phase calls `startProgress` with that same ticket, not `accountKey`. One click has one progress id from the first download frame through the import update. `accountKey` remains only the key of `accountDownloadsInFlightAtom`.

The listener stays mounted for the life of the card and reads the ref, so a frame that arrives before the next render is not dropped. Early frames are the failure this callback exists to prevent. `useProgress` is not added: it subscribes from render state, which is too late for the first frames, and this card is the only account-export consumer.

### O4 — What stays true when the second export is refused

The second click still surfaces the existing conflict through `notifyUnlessCancelled`. No new error variant and no new translated string. The in-flight set entry is still removed in the click handler's `finally`. A refused claim emits no progress frame.

## Decisions and trade-offs

### The progress id is the ticket, and the account is the admission key

Chosen: O1 and O2 together. Rejected: keeping `chesscom_{player}` / `lichess_{player}` as the event id and only refusing a second export. That would stop the interleaving by forbidding the second operation, and the id would still name the account. Rejected: the ticket as the event id with the admission check left owner-scoped on that ticket. The same-window Rust backstop would disappear, and two windows would still publish one filename. `d-20261004-06` does not apply its "do not refuse" half here: conversions do not share one output file; these exports do.

### The admission is not held across the import

Chosen: the exclusive claim ends when the download command's lease drops. Rejected: a new command or a detached lease that the renderer releases after import. That is a second lifetime protocol. The import writes the same ticket, so two overlapping imports do not share a progress id. They can still replace the published PGN if the second download starts during the first import. That replacement is a known limit, named below, not a new mechanism.

### Case-variant usernames stay distinct

Chosen: the admission key uses the same player string the progress id uses today (`chesscom_{player}` as supplied, Lichess through `lichess_user_segment`). Rejected: case-folding Chess.com for admission only. The published filename is not case-folded, so a folded key would refuse two exports that write two files.

## Decided autonomously

### Account export progress id

* **Question:** For a Chess.com or Lichess account export, is `ProgressEvent.id` the download ticket (`job_id`), or does the account string stay the id and a second export get refused instead?
* **Governs:** f-20260914-14
* **Chosen:** The event id is the download ticket. The account string is the admission key, not the event id.
* **Rejected:** Account string as the event id, with a refusal standing in for a distinct operation id.
* **Reason:** `ipc-events.md` requires the broadcast id to identify the operation the receiver asked for. The ticket is already that operation. The account string cannot tell two exports apart, which is the defect. Reversal path: pass the account string to `begin_progress` again and point `AccountCard`'s listener back at `accountKey`.

### Concurrent account exports

* **Question:** May two webviews export the same account at the same time once each export has its own progress id?
* **Governs:** f-20260914-14
* **Chosen:** No. `claim_download` refuses a second uncancelled exclusive claim with the same account admission key, whatever the owner.
* **Rejected:** Admitting both and giving each its own progress id only. The published file is still `${player}_${provider}.pgn` for both, and the same-window atomic refusal is what the current progress-id check provides.
* **Reason:** The finding's two windows are one shared filename, not only one shared bar. Owner-scoped admission is why the second window is admitted today. Reversal path: pass exclusive false from the two account commands.

## Risks / open questions

# Plan: Account export progress follows the operation

## Goal

A Chess.com or Lichess account export reports progress under the download ticket the renderer already holds, and a second export of the same account is refused while one is active, including from another window.

## MANDATE

f-20260914-14, verbatim:

Account game exports share one progress id per player across concurrent exports.

* **Where:** `src-tauri/src/chesscom.rs:290` emits `ProgressEvent` under `chesscom_${player}`; `src-tauri/src/fs.rs:1113` uses `lichess_${player}` for `download_to_destination`; `src/components/home/AccountCard.tsx:180-193` filters on that same id and ignores the command's unique `job_id`.
* **Defect (reported):** the progress id is derived from the account, not the operation. Two exports for the same player (repeated click, two windows) emit the same id, so both consumers see interleaved progress and one terminal state ends the other's bar.
* **Why it matters:** `.claude/rules/ipc-events.md` — anything broadcast carries an id that identifies the operation the receiver asked for.
* **Open question:** use the renderer-minted `job_id` as the progress id for account exports, or refuse a second concurrent export per account?

The line numbers in that Where clause have moved. The traced premises below are the current sites. The obligation is the defect and the open question, not those historical line numbers.

## Threat model and non-goals

Two ordinary windows, or two clicks in one window, start an export of the same account before the first export has finished. The renderer is not treated as an adversary that forges another window's ticket: `prepare_download` already binds the ticket to the calling webview, and `claim_download` rejects a ticket whose owner does not match. Deliberately evasive player strings that differ only by case stay distinct accounts, as they do today. No new capability scope, no new event, no bearer token in the renderer.

## Traced premises

This plan does not change those commands.

## Approach

### O1 — The export's progress id is the download ticket

`download_chess_com_games` and `download_lichess_games_runtime` pass `job_id` as the progress id to `begin_progress` / `download_to_destination` and store that same `job_id` on the accepted download. The canonical account string (`chesscom_{player}`, or `lichess_{}` plus the existing `lichess_user_segment` result) is no longer the event id. Lichess still validates the player through `lichess_user_segment` before `claim_download`. Chess.com keeps today's unvalidated player string. `download_file` and the engine-archive download are unchanged.

This is the open question's first option. The ticket is the operation the receiver asked for (`ipc-events.md`). A terminal frame for one ticket cannot finish another ticket's entry, because `progress.rs` keys the entry by id.

### O2 — One active export per account, across windows

`claim_download` gains an admission key and an exclusive flag, separate from the progress id.

* Account exports pass the canonical account string as the admission key and exclusive true.
* Every other caller passes its existing progress id as the admission key and exclusive false.

Under the registry mutex, a new claim is refused with the existing `Error::Conflict("download progress is already active")` when an uncancelled accepted download has the same admission key and either the new claim is exclusive or the owner matches. Exclusive therefore refuses a second window. Non-exclusive keeps today's owner-scoped behavior, including the test that two owners may share a progress id.

The refusal is the open question's second option, and it is required together with O1. O1 alone makes the progress id unique, so the current owner-and-progress-id check would stop refusing a repeated click. The check has to move to the account key. Making that key exclusive across owners is what stops two windows writing `${player}_${provider}.pgn` at once. The lease still ends when the download command returns (`OperationLease::drop`), so the refusal covers the export the finding names, not the later import.

### O3 — The card follows the ticket for both phases of that click, including after remount

`downloadChessCom` and `downloadLichess` take a callback invoked with the ticket inside `withDownloadTicket`, synchronously, before the command is awaited.

`accountDownloadsInFlightAtom` becomes `ReadonlyMap<string, string | null>`: the account key to that click's ticket, or null while the click is pending and the ticket is not known yet. It stays in-memory and is not persisted. Pending is map membership. At click start the handler inserts the account key with a null ticket, which is what disables the button and what the remount test already observes. The callback then sets that entry's ticket before the command is awaited. The update is functional and keeps every other account's entry. The click handler's existing `finally` deletes the entry after the import attempt, including when the card has unmounted. Unmount does not delete it.

The progress listener reads the map at event time through the jotai store. It does not read a render snapshot and it does not read a component ref. It applies a frame only when the stored ticket is a string and `payload.id` equals that string. It does not apply `accountKey`. A write in the callback is therefore visible to the listener that is already subscribed, and a card mounted later reads the same entry.

After the download returns, the import phase calls `startProgress` with the ticket that callback captured, not `accountKey`. One click has one progress id from the first download frame through the import update. `accountKey` remains only the map key.

The mandate's receiver is this card. Today it matches frames by `accountKey`, which a remounted card recomputes, so progress continues across the remount the picker test already requires. After O1 that id is the ticket and is not recomputable. The in-flight atom is the record that already outlives the card. A ref on the instance would be empty after remount, and the new listener would reject the rest of that operation's frames.

`useProgress` is not added. The listener is the card's existing subscription. Frames emitted while no card is mounted are not delivered. That gap exists today, because the subscription lives on the card. This plan does not add a listener outside the card.

Verification, which is part of this obligation:

* Each real helper test, `downloadChessCom` and `downloadLichess`: the mocked native command emits one progress frame synchronously when it is entered, before its promise resolves. The ticket callback has already installed a listener, and that listener observes the frame while the helper's returned promise is still pending. A callback that runs only after the command resolves fails this test.
* Card tests, one per provider: the mocked helper calls the callback and leaves its promise pending. A `ProgressEvent` for that ticket updates the percentage text before the promise resolves. A `ProgressEvent` for a different id does not.
* The existing remount test still refuses a second download. After remount, a `ProgressEvent` whose id is the ticket stored for that account updates the percentage text.

### O4 — What stays true when the second export is refused

The second click still surfaces the existing conflict through `notifyUnlessCancelled`. No new error variant and no new translated string. The in-flight set entry is still removed in the click handler's `finally`. A refused claim emits no progress frame.

## Decisions and trade-offs

### The progress id is the ticket, and the account is the admission key

Chosen: O1 and O2 together. Rejected: keeping `chesscom_{player}` / `lichess_{player}` as the event id and only refusing a second export. That would stop the interleaving by forbidding the second operation, and the id would still name the account. Rejected: the ticket as the event id with the admission check left owner-scoped on that ticket. The same-window Rust backstop would disappear, and two windows would still publish one filename. `d-20261004-06` does not apply its "do not refuse" half here: conversions do not share one output file; these exports do.

### The admission is not held across the import

Chosen: the exclusive claim ends when the download command's lease drops. Rejected: a new command or a detached lease that the renderer releases after import. That is a second lifetime protocol. The import writes the same ticket, so two overlapping imports do not share a progress id. They can still replace the published PGN if the second download starts during the first import. That replacement is a known limit, named below, not a new mechanism.

### The ticket lives in the in-flight map

Chosen: the account-key to ticket map in O3. Rejected: a ref on the mounted card. The remount test keeps the account pending after unmount and remount. A ref on the new card is empty, so the listener would reject the rest of that operation's frames. The map is the record that test already depends on. The null ticket covers the interval between click start and the callback, which is how the button becomes pending today, before any progress frame exists.

### Case-variant usernames stay distinct

Chosen: the admission key uses the same player string the progress id uses today (`chesscom_{player}` as supplied, Lichess through `lichess_user_segment`). Rejected: case-folding Chess.com for admission only. The published filename is not case-folded, so a folded key would refuse two exports that write two files.

## Decided autonomously

### Account export progress id

* **Question:** For a Chess.com or Lichess account export, is `ProgressEvent.id` the download ticket (`job_id`), or does the account string stay the id and a second export get refused instead?
* **Governs:** f-20260914-14
* **Chosen:** The event id is the download ticket. The account string is the admission key, not the event id.
* **Rejected:** Account string as the event id, with a refusal standing in for a distinct operation id.
* **Reason:** `ipc-events.md` requires the broadcast id to identify the operation the receiver asked for. The ticket is already that operation. The account string cannot tell two exports apart, which is the defect. Reversal path: pass the account string to `begin_progress` again and point `AccountCard`'s listener back at `accountKey`.

### Concurrent account exports

* **Question:** May two webviews export the same account at the same time once each export has its own progress id?
* **Governs:** f-20260914-14
* **Chosen:** No. `claim_download` refuses a second uncancelled exclusive claim with the same account admission key, whatever the owner.
* **Rejected:** Admitting both and giving each its own progress id only. The published file is still `${player}_${provider}.pgn` for both, and the same-window atomic refusal is what the current progress-id check provides.
* **Reason:** The finding's two windows are one shared filename, not only one shared bar. Owner-scoped admission is why the second window is admitted today. Reversal path: pass exclusive false from the two account commands.

### Where the in-flight ticket is kept

* **Question:** After the progress id becomes the download ticket, where does AccountCard keep that ticket so a remounted card still applies the operation's frames?
* **Governs:** f-20260914-14
* **Chosen:** `accountDownloadsInFlightAtom`, as a map from account key to ticket or null, read at event time.
* **Rejected:** A ref on the card instance.
* **Reason:** The mandate's receiver is the account card. The card is remounted while the download stays pending (`a remounted account stays pending and cannot start a second download`). The atom already survives that remount. A ref does not. Today the card recomputes `accountKey`, so remount still matches frames. After O1 that id is not recomputable. Reversal path: keep the ticket only on the instance and accept a remounted card that stays pending without further percentage updates.

# Plan: Account export progress follows the operation

## Goal

A Chess.com or Lichess account export reports progress under the download ticket the renderer already holds, and a second export of the same account is refused while one is active, including from another window.

## MANDATE

f-20260914-14, verbatim:

Account game exports share one progress id per player across concurrent exports.

* **Where:** `src-tauri/src/chesscom.rs:290` emits `ProgressEvent` under `chesscom_${player}`; `src-tauri/src/fs.rs:1113` uses `lichess_${player}` for `download_to_destination`; `src/components/home/AccountCard.tsx:180-193` filters on that same id and ignores the command's unique `job_id`.
* **Defect (reported):** the progress id is derived from the account, not the operation. Two exports for the same player (repeated click, two windows) emit the same id, so both consumers see interleaved progress and one terminal state ends the other's bar.
* **Why it matters:** `.claude/rules/ipc-events.md` — anything broadcast carries an id that identifies the operation the receiver asked for.
* **Open question:** use the renderer-minted `job_id` as the progress id for account exports, or refuse a second concurrent export per account?

The line numbers in that Where clause have moved. The traced premises below are the current sites. The obligation is the defect and the open question, not those historical line numbers.

## Threat model and non-goals

Two ordinary windows, or two clicks in one window, start an export of the same account before the first export has finished. The renderer is not treated as an adversary that forges another window's ticket: `prepare_download` already binds the ticket to the calling webview, and `claim_download` rejects a ticket whose owner does not match. Deliberately evasive player strings that differ only by case stay distinct accounts, as they do today. No new capability scope, no new event, no bearer token in the renderer.

## Traced premises

## Approach

### O1 — The export's progress id is the download ticket

`download_chess_com_games` and `download_lichess_games_runtime` pass `job_id` as the progress id to `begin_progress` / `download_to_destination` and store that same `job_id` on the accepted download. The canonical account string (`chesscom_{player}`, or `lichess_{}` plus the existing `lichess_user_segment` result) is no longer the event id. Lichess still validates the player through `lichess_user_segment` before `claim_download`. Chess.com keeps today's unvalidated player string. `download_file` and the engine-archive download are unchanged.

This is the open question's first option. The ticket is the operation the receiver asked for (`ipc-events.md`). A terminal frame for one ticket cannot finish another ticket's entry, because `progress.rs` keys the entry by id.

### O2 — One active export per account, across windows

`claim_download` gains an admission key and an exclusive flag, separate from the progress id.

* Account exports pass the canonical account string as the admission key and exclusive true.
* Every other caller passes its existing progress id as the admission key and exclusive false.

Under the registry mutex, a new claim is refused with the existing `Error::Conflict("download progress is already active")` when an uncancelled accepted download has the same admission key and either the new claim is exclusive or the owner matches. Exclusive therefore refuses a second window. Non-exclusive keeps today's owner-scoped behavior, including the test that two owners may share a progress id.

The refusal is the open question's second option, and it is required together with O1. O1 alone makes the progress id unique, so the current owner-and-progress-id check would stop refusing a repeated click. The check has to move to the account key. Making that key exclusive across owners is what stops two windows writing `${player}_${provider}.pgn` at once. The lease still ends when the download command returns (`OperationLease::drop`), so the refusal covers the export the finding names, not the later import.

### O3 — The card follows the ticket for both phases of that click, including after remount

`downloadChessCom` and `downloadLichess` take a callback invoked with the ticket inside `withDownloadTicket`, synchronously, before the command is awaited.

`accountDownloadsInFlightAtom` becomes `ReadonlyMap<string, string | null>`: the account key to that click's ticket, or null while the click is pending and the ticket is not known yet. It stays in-memory and is not persisted. Pending is map membership. At click start the handler inserts the account key with a null ticket, which is what disables the button and what the remount test already observes. The callback then sets that entry's ticket before the command is awaited. The update is functional and keeps every other account's entry. The click handler's existing `finally` deletes the entry after the import attempt, including when the card has unmounted. Unmount does not delete it.

The progress listener reads the map at event time through the jotai store. It does not read a render snapshot and it does not read a component ref. It applies a frame only when the stored ticket is a string and `payload.id` equals that string. It does not apply `accountKey`. A write in the callback is therefore visible to the listener that is already subscribed, and a card mounted later reads the same entry.

After the download returns, the import phase calls `startProgress` with the ticket that callback captured, not `accountKey`. One click has one progress id from the first download frame through the import update. `accountKey` remains only the map key.

The mandate's receiver is this card. Today it matches frames by `accountKey`, which a remounted card recomputes, so progress continues across the remount the picker test already requires. After O1 that id is the ticket and is not recomputable. The in-flight atom is the record that already outlives the card. A ref on the instance would be empty after remount, and the new listener would reject the rest of that operation's frames.

`useProgress` is not added. The listener is the card's existing subscription. Frames emitted while no card is mounted are not delivered. That gap exists today, because the subscription lives on the card. This plan does not add a listener outside the card.

Verification, which is part of this obligation:

* Each real helper test, `downloadChessCom` and `downloadLichess`: the mocked native command emits one progress frame synchronously when it is entered, before its promise resolves. The ticket callback has already installed a listener, and that listener observes the frame while the helper's returned promise is still pending. A callback that runs only after the command resolves fails this test.
* Card tests, one per provider: the mocked helper calls the callback and leaves its promise pending. A `ProgressEvent` for that ticket updates the percentage text before the promise resolves. A `ProgressEvent` for a different id does not.
* For both providers, a test asserts `startProgress` was called with the ticket that callback captured, and not with `accountKey`. The existing mock resolves a lease for any argument, so an injected frame does not prove this call. A call that still passes the account string fails the test.
* The existing remount test still refuses a second download. After remount, a `ProgressEvent` whose id is the ticket stored for that account updates the percentage text.

### O4 — What stays true when the second export is refused

The second click still surfaces the existing conflict through `notifyUnlessCancelled`. No new error variant and no new translated string. The in-flight set entry is still removed in the click handler's `finally`. A refused claim emits no progress frame.

## Decisions and trade-offs

### The progress id is the ticket, and the account is the admission key

Chosen: O1 and O2 together. Rejected: keeping `chesscom_{player}` / `lichess_{player}` as the event id and only refusing a second export. That would stop the interleaving by forbidding the second operation, and the id would still name the account. Rejected: the ticket as the event id with the admission check left owner-scoped on that ticket. The same-window Rust backstop would disappear, and two windows would still publish one filename. `d-20261004-06` does not apply its "do not refuse" half here: conversions do not share one output file; these exports do.

### The admission is not held across the import

Chosen: the exclusive claim ends when the download command's lease drops. Rejected: a new command or a detached lease that the renderer releases after import. That is a second lifetime protocol. The import writes the same ticket, so two overlapping imports do not share a progress id. They can still replace the published PGN if the second download starts during the first import. That replacement is a known limit, named below, not a new mechanism.

### The ticket lives in the in-flight map

Chosen: the account-key to ticket map in O3. Rejected: a ref on the mounted card. The remount test keeps the account pending after unmount and remount. A ref on the new card is empty, so the listener would reject the rest of that operation's frames. The map is the record that test already depends on. The null ticket covers the interval between click start and the callback, which is how the button becomes pending today, before any progress frame exists.

### Case-variant usernames stay distinct

Chosen: the admission key uses the same player string the progress id uses today (`chesscom_{player}` as supplied, Lichess through `lichess_user_segment`). Rejected: case-folding Chess.com for admission only. The published filename is not case-folded, so a folded key would refuse two exports that write two files.

## Decided autonomously

### Account export progress id

* **Question:** For a Chess.com or Lichess account export, is `ProgressEvent.id` the download ticket (`job_id`), or does the account string stay the id and a second export get refused instead?
* **Governs:** f-20260914-14
* **Chosen:** The event id is the download ticket. The account string is the admission key, not the event id.
* **Rejected:** Account string as the event id, with a refusal standing in for a distinct operation id.
* **Reason:** `ipc-events.md` requires the broadcast id to identify the operation the receiver asked for. The ticket is already that operation. The account string cannot tell two exports apart, which is the defect. Reversal path: pass the account string to `begin_progress` again and point `AccountCard`'s listener back at `accountKey`.

### Concurrent account exports

* **Question:** May two webviews export the same account at the same time once each export has its own progress id?
* **Governs:** f-20260914-14
* **Chosen:** No. `claim_download` refuses a second uncancelled exclusive claim with the same account admission key, whatever the owner.
* **Rejected:** Admitting both and giving each its own progress id only. The published file is still `${player}_${provider}.pgn` for both, and the same-window atomic refusal is what the current progress-id check provides.
* **Reason:** The finding's two windows are one shared filename, not only one shared bar. Owner-scoped admission is why the second window is admitted today. Reversal path: pass exclusive false from the two account commands.

### Where the in-flight ticket is kept

* **Question:** After the progress id becomes the download ticket, where does AccountCard keep that ticket so a remounted card still applies the operation's frames?
* **Governs:** f-20260914-14
* **Chosen:** `accountDownloadsInFlightAtom`, as a map from account key to ticket or null, read at event time.
* **Rejected:** A ref on the card instance.
* **Reason:** The mandate's receiver is the account card. The card is remounted while the download stays pending (`a remounted account stays pending and cannot start a second download`). The atom already survives that remount. A ref does not. Today the card recomputes `accountKey`, so remount still matches frames. After O1 that id is not recomputable. Reversal path: keep the ticket only on the instance and accept a remounted card that stays pending without further percentage updates.

## Risks / open questions

Known limit: after the download command returns, a second window may claim the account and replace `${player}_${provider}.pgn` while the first window is still importing. The bars do not interleave, because each click uses its own ticket. Closing that window needs a hold that outlives the download command. This plan does not add one.

Known limit: `chesscom_Foo` and `chesscom_foo` are different admission keys and different filenames, as today.

Known limit: between unmount and the next mount, no card is subscribed, so frames in that gap are not applied. The same gap exists today. This plan does not add a listener outside the card.

A refused second export shows the existing conflict text. No new user-facing copy.

# Plan: Account export progress follows the operation

## Goal

A Chess.com or Lichess account export reports progress under the download ticket the renderer already holds, and a second export of the same account is refused while one is active, including from another window.

## MANDATE

f-20260914-14, verbatim:

Account game exports share one progress id per player across concurrent exports.

* **Where:** `src-tauri/src/chesscom.rs:290` emits `ProgressEvent` under `chesscom_${player}`; `src-tauri/src/fs.rs:1113` uses `lichess_${player}` for `download_to_destination`; `src/components/home/AccountCard.tsx:180-193` filters on that same id and ignores the command's unique `job_id`.
* **Defect (reported):** the progress id is derived from the account, not the operation. Two exports for the same player (repeated click, two windows) emit the same id, so both consumers see interleaved progress and one terminal state ends the other's bar.
* **Why it matters:** `.claude/rules/ipc-events.md` — anything broadcast carries an id that identifies the operation the receiver asked for.
* **Open question:** use the renderer-minted `job_id` as the progress id for account exports, or refuse a second concurrent export per account?

The line numbers in that Where clause have moved. The traced premises below are the current sites. The obligation is the defect and the open question, not those historical line numbers.

## Threat model and non-goals

Two ordinary windows, or two clicks in one window, start an export of the same account before the first export has finished. The renderer is not treated as an adversary that forges another window's ticket: `prepare_download` already binds the ticket to the calling webview, and `claim_download` rejects a ticket whose owner does not match. Deliberately evasive player strings that differ only by case stay distinct accounts, as they do today. No new capability scope, no new event, no bearer token in the renderer.

## Traced premises

These citations are frozen. Obligations name symbols, not these line numbers.

* `src-tauri/src/chesscom.rs:229-236` sets `progress_id` to `format!("chesscom_{player}")` and passes that string, plus `job_id`, to `claim_download`. `download_chess_com_games_core` then `begin_progress` on `progress_id` (`chesscom.rs:302`).
* `src-tauri/src/fs.rs:1259-1266` sets the Lichess progress id to `format!("lichess_{}", lichess_user_segment(&player)?)` before `claim_download`. `download_to_destination` is called with that id (`fs.rs:1285-1286`). `download_file` (`fs.rs:739-744`) and the engine-archive download keep the caller-supplied `id` as their progress id. This plan does not change those commands.
* `src-tauri/src/infra/operations.rs:424-432` refuses a second download only when the same webview owner already has an uncancelled accepted download with the same `progress_id`. A different owner is admitted. `OperationLease::drop` (`operations.rs:938-948`) removes that accepted entry when the command's lease ends.

## Approach

### O1 — The export's progress id is the download ticket

`download_chess_com_games` and `download_lichess_games_runtime` pass `job_id` as the progress id to `begin_progress` / `download_to_destination` and store that same `job_id` on the accepted download. The canonical account string (`chesscom_{player}`, or `lichess_{}` plus the existing `lichess_user_segment` result) is no longer the event id. Lichess still validates the player through `lichess_user_segment` before `claim_download`. Chess.com keeps today's unvalidated player string. `download_file` and the engine-archive download are unchanged.

This is the open question's first option. The ticket is the operation the receiver asked for (`ipc-events.md`). A terminal frame for one ticket cannot finish another ticket's entry, because `progress.rs` keys the entry by id.

### O2 — One active export per account, across windows

`claim_download` gains an admission key and an exclusive flag, separate from the progress id.

* Account exports pass the canonical account string as the admission key and exclusive true.
* Every other caller passes its existing progress id as the admission key and exclusive false.

Under the registry mutex, a new claim is refused with the existing `Error::Conflict("download progress is already active")` when an uncancelled accepted download has the same admission key and either the new claim is exclusive or the owner matches. Exclusive therefore refuses a second window. Non-exclusive keeps today's owner-scoped behavior, including the test that two owners may share a progress id.

The refusal is the open question's second option, and it is required together with O1. O1 alone makes the progress id unique, so the current owner-and-progress-id check would stop refusing a repeated click. The check has to move to the account key. Making that key exclusive across owners is what stops two windows writing `${player}_${provider}.pgn` at once. The lease still ends when the download command returns (`OperationLease::drop`), so the refusal covers the export the finding names, not the later import.

### O3 — The card follows the ticket for both phases of that click, including after remount

`downloadChessCom` and `downloadLichess` take a callback invoked with the ticket inside `withDownloadTicket`, synchronously, before the command is awaited.

`accountDownloadsInFlightAtom` becomes `ReadonlyMap<string, string | null>`: the account key to that click's ticket, or null while the click is pending and the ticket is not known yet. It stays in-memory and is not persisted. Pending is map membership. At click start the handler inserts the account key with a null ticket, which is what disables the button and what the remount test already observes. The callback then sets that entry's ticket before the command is awaited. The update is functional and keeps every other account's entry. The click handler's existing `finally` deletes the entry after the import attempt, including when the card has unmounted. Unmount does not delete it.

The progress listener reads the map at event time through the jotai store. It does not read a render snapshot and it does not read a component ref. It applies a frame only when the stored ticket is a string and `payload.id` equals that string. It does not apply `accountKey`. A write in the callback is therefore visible to the listener that is already subscribed, and a card mounted later reads the same entry.

After the download returns, the import phase calls `startProgress` with the ticket that callback captured, not `accountKey`. One click has one progress id from the first download frame through the import update. `accountKey` remains only the map key.

The mandate's receiver is this card. Today it matches frames by `accountKey`, which a remounted card recomputes, so progress continues across the remount the picker test already requires. After O1 that id is the ticket and is not recomputable. The in-flight atom is the record that already outlives the card. A ref on the instance would be empty after remount, and the new listener would reject the rest of that operation's frames.

`useProgress` is not added. The listener is the card's existing subscription. Frames emitted while no card is mounted are not delivered. That gap exists today, because the subscription lives on the card. This plan does not add a listener outside the card.

Verification, which is part of this obligation:

* Each real helper test, `downloadChessCom` and `downloadLichess`: the mocked native command emits one progress frame synchronously when it is entered, before its promise resolves. The ticket callback has already installed a listener, and that listener observes the frame while the helper's returned promise is still pending. A callback that runs only after the command resolves fails this test.
* Card tests, one per provider: the mocked helper calls the callback and leaves its promise pending. A `ProgressEvent` for that ticket updates the percentage text before the promise resolves. A `ProgressEvent` for a different id does not.
* For both providers, a test asserts `startProgress` was called with the ticket that callback captured, and not with `accountKey`. The existing mock resolves a lease for any argument, so an injected frame does not prove this call. A call that still passes the account string fails the test.
* The existing remount test still refuses a second download. After remount, a `ProgressEvent` whose id is the ticket stored for that account updates the percentage text.

### O4 — What stays true when the second export is refused

The second click still surfaces the existing conflict through `notifyUnlessCancelled`. No new error variant and no new translated string. The in-flight set entry is still removed in the click handler's `finally`. A refused claim emits no progress frame.

## Decisions and trade-offs

### The progress id is the ticket, and the account is the admission key

Chosen: O1 and O2 together. Rejected: keeping `chesscom_{player}` / `lichess_{player}` as the event id and only refusing a second export. That would stop the interleaving by forbidding the second operation, and the id would still name the account. Rejected: the ticket as the event id with the admission check left owner-scoped on that ticket. The same-window Rust backstop would disappear, and two windows would still publish one filename. `d-20261004-06` does not apply its "do not refuse" half here: conversions do not share one output file; these exports do.

### The admission is not held across the import

Chosen: the exclusive claim ends when the download command's lease drops. Rejected: a new command or a detached lease that the renderer releases after import. That is a second lifetime protocol. The import writes the same ticket, so two overlapping imports do not share a progress id. They can still replace the published PGN if the second download starts during the first import. That replacement is a known limit, named below, not a new mechanism.

### The ticket lives in the in-flight map

Chosen: the account-key to ticket map in O3. Rejected: a ref on the mounted card. The remount test keeps the account pending after unmount and remount. A ref on the new card is empty, so the listener would reject the rest of that operation's frames. The map is the record that test already depends on. The null ticket covers the interval between click start and the callback, which is how the button becomes pending today, before any progress frame exists.

### Case-variant usernames stay distinct

Chosen: the admission key uses the same player string the progress id uses today (`chesscom_{player}` as supplied, Lichess through `lichess_user_segment`). Rejected: case-folding Chess.com for admission only. The published filename is not case-folded, so a folded key would refuse two exports that write two files.

## Decided autonomously

### Account export progress id

* **Question:** For a Chess.com or Lichess account export, is `ProgressEvent.id` the download ticket (`job_id`), or does the account string stay the id and a second export get refused instead?
* **Governs:** f-20260914-14
* **Chosen:** The event id is the download ticket. The account string is the admission key, not the event id.
* **Rejected:** Account string as the event id, with a refusal standing in for a distinct operation id.
* **Reason:** `ipc-events.md` requires the broadcast id to identify the operation the receiver asked for. The ticket is already that operation. The account string cannot tell two exports apart, which is the defect. Reversal path: pass the account string to `begin_progress` again and point `AccountCard`'s listener back at `accountKey`.

### Concurrent account exports

* **Question:** May two webviews export the same account at the same time once each export has its own progress id?
* **Governs:** f-20260914-14
* **Chosen:** No. `claim_download` refuses a second uncancelled exclusive claim with the same account admission key, whatever the owner.
* **Rejected:** Admitting both and giving each its own progress id only. The published file is still `${player}_${provider}.pgn` for both, and the same-window atomic refusal is what the current progress-id check provides.
* **Reason:** The finding's two windows are one shared filename, not only one shared bar. Owner-scoped admission is why the second window is admitted today. Reversal path: pass exclusive false from the two account commands.

### Where the in-flight ticket is kept

* **Question:** After the progress id becomes the download ticket, where does AccountCard keep that ticket so a remounted card still applies the operation's frames?
* **Governs:** f-20260914-14
* **Chosen:** `accountDownloadsInFlightAtom`, as a map from account key to ticket or null, read at event time.
* **Rejected:** A ref on the card instance.
* **Reason:** The mandate's receiver is the account card. The card is remounted while the download stays pending (`a remounted account stays pending and cannot start a second download`). The atom already survives that remount. A ref does not. Today the card recomputes `accountKey`, so remount still matches frames. After O1 that id is not recomputable. Reversal path: keep the ticket only on the instance and accept a remounted card that stays pending without further percentage updates.

## Risks / open questions

Known limit: after the download command returns, a second window may claim the account and replace `${player}_${provider}.pgn` while the first window is still importing. The bars do not interleave, because each click uses its own ticket. Closing that window needs a hold that outlives the download command. This plan does not add one.

Known limit: `chesscom_Foo` and `chesscom_foo` are different admission keys and different filenames, as today.

Known limit: between unmount and the next mount, no card is subscribed, so frames in that gap are not applied. The same gap exists today. This plan does not add a listener outside the card.

A refused second export shows the existing conflict text. No new user-facing copy.
