# Plan: Database export honours cancellation while decoding and writing rows (f-20260914-18)

## Goal

A cancelled database export (today: application shutdown sealing the native operation registry
while an export runs) stops promptly at the next row, returns `Error::Cancellation`, and never
publishes its destination; a cancellation that arrives after the temporary file was fully written
and synced but before the atomic rename is still honoured. Uncancelled exports behave exactly as
today.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-18`:

> * **Where:** src-tauri/src/db/mod.rs:2725 (the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks)
> * **Defect:** Cancelling an export, or shutting down during one, of a large database (hundreds of MB, millions of games) still processes every row and can publish the completed destination. Distinct from handled `f-20260904-04` (rows silently dropped on decode failure).
> * **Why it matters:** `.claude/rules/async-resource-invariants.md`: cancellation must be checked before use, and a cancelled export must not publish.
> * **Open question:** Where are cancellation checkpoints placed (per row, per chunk) and what happens to a partially written destination on cancel — discard the staging file, or never publish?

## Threat model and non-goals

* **Accidental input only.** The cancellation source is the native operation registry: the export
  is an *accepted* operation (`state.operations.accept("export_to_pgn")`), so its lease token is
  cancelled by `OperationRegistry::seal_and_request_cancellation` at shutdown (and by any future
  caller that cancels accepted operations). No adversary is modelled; the database and destination
  are the user's own files, already admitted through the path authority.
* **Environments:** the export runs only on unix (`off_unix_refusal("PGN atomic replacement", …)`
  at the command and in `replace_pgn_atomic`). Windows must compile and lint (the Windows clippy
  lane), and cross-platform tests must stay cross-platform; tests that reach the atomic rename stay
  `#[cfg(unix)]` like their existing neighbours.
* **Non-goals:** a renderer-side Cancel button for exports (a product surface; no renderer path
  cancels accepted exports today, d-20260908-13); a cancel *acknowledgement* contract like the
  download commit gate (d-20260920-02 / d-20261005-12) — nobody is told "export cancelled"; the
  class-wide regression anchor for forwarding a token into connection acquisition (`f-20261004-17`,
  open, owns that seam for every `get_db_or_create(…, Some(token), …)` call site including the one
  this plan adds).

## Approach

### O1 — The export worker owns and forwards its token

MANDATE: "the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks".

`export_to_pgn` passes the gateway's worker token into `export_to_pgn_blocking`, which takes a
`cancellation: &CancellationToken` parameter and forwards it into connection acquisition
(`get_db_or_create(…, Some(cancellation), …)`), the row writer (O2) and the atomic replacement (O3).
No new token, no clone detached from the lease: shutdown's seal reaches every checkpoint.

### O2 — Per-row checkpoint before the next row is pulled

MANDATE: "still processes every row"; open question "per row, per chunk".

`write_pgn_rows` takes the token and checks it once per row **before advancing the row iterator**
(so no further SQLite step, decode or write happens after a cancellation is observed), returning
`Error::Cancellation`. Granularity is per row: the check is one uncontended mutex read (P10) against
decoding and formatting a whole game, and per-row makes the bound exact ("at most the row in flight
completes") without a chunk constant. The early return propagates out of the `replace_pgn_atomic`
write closure, so the temporary is discarded by the driver (P7) and the destination stays as it was.

### O3 — The shared PGN replace primitive re-checks cancellation immediately before commit

MANDATE: "can publish the completed destination"; "a cancelled export must not publish".

`ResolvedPath::replace_pgn_atomic` takes `cancellation: &CancellationToken` and checks it as the
first step of the `precommit` closure it already builds (before the logical-parent revalidation),
returning `Error::Cancellation`. This covers the window after the last row — final flush, `sync_all`
of a possibly hundreds-of-MB temporary, metadata — that no row check can see. Both production
callers pass their token (`export_to_pgn_blocking`: the worker token; `edit_existing`: its existing
`cancellation`), so the second caller gets the same guarantee through the same primitive (rule 11);
`edit_existing`'s existing per-chunk and closure checks stay. The rename and every step after it stay
unchecked: a cancellation that arrives after the last check loses the race and the operation reports
its real outcome (`Ok`, or `CommittedDurabilityUncertain` through `require_durable`), as d-20260908-13
("commit tails report their actual outcome even after late cancellation") and d-20261004-14 (final
token check before commit, commit unarmed) already decided. The signature line keeps the exact
prefix `pub(crate) fn replace_pgn_atomic<F>(` so the P9 guard pin and the P8 call-site pin stay
valid unchanged.

### O4 — Outcome contract on cancellation

Answer to the open question: **never publish** — the existing atomic temporary is the staging file
and is discarded on every pre-rename error (P7); no new staging mechanism. On any cancellation
observed before the rename: the command returns `Error::Cancellation`; the previous destination is
byte-identical (or still absent); no `.atomic-*` residue remains in the destination directory. The
error mapping and renderer handling are unchanged (`Error::Cancellation` already exists and is
logged at debug by `run_native_operation`, P5).

## Decisions and trade-offs

* Per-row, not per-chunk, checkpoints (O2) — see O2 for the cost argument.
* No SQLite progress-handler scope (`with_sqlite_cancellation`) around the export query: the query
  has no `ORDER BY` (P2), so SQLite streams rows and the VM work between two pulls is one row's

  closes. Arming the scope would add a second cancellation mechanism for no reachable window.
* The pre-commit check lives in the shared primitive, not in an export-only wrapper (rule 11): two
  production callers, one window.
* No operation commit gate (`OperationCommitGate::begin_commit`): it is download-only by contract
  and exists to make a cancel *acknowledgement* exact; exports have no acknowledgement.

# Plan: Database export honours cancellation while decoding and writing rows (f-20260914-18)

## Goal

A cancelled database export (today: application shutdown sealing the native operation registry
while an export runs) stops promptly at the next row, returns `Error::Cancellation` (or, only when
removing the staging file itself fails, the existing `OperationAndCleanup` error — O4), and never
publishes its destination; a cancellation that arrives after the last row, while the temporary
file is flushed and synced, is still honoured by a final check immediately before the atomic
commit. Only a cancellation that arrives after that final check loses the race (O3). Uncancelled
exports behave exactly as today.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-18`:

> * **Where:** src-tauri/src/db/mod.rs:2725 (the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks)
> * **Defect:** Cancelling an export, or shutting down during one, of a large database (hundreds of MB, millions of games) still processes every row and can publish the completed destination. Distinct from handled `f-20260904-04` (rows silently dropped on decode failure).
> * **Why it matters:** `.claude/rules/async-resource-invariants.md`: cancellation must be checked before use, and a cancelled export must not publish.
> * **Open question:** Where are cancellation checkpoints placed (per row, per chunk) and what happens to a partially written destination on cancel — discard the staging file, or never publish?

## Threat model and non-goals

* **Accidental input only.** The cancellation source is the native operation registry: the export
  is an *accepted* operation (`state.operations.accept("export_to_pgn")`), so its lease token is
  cancelled by `OperationRegistry::seal_and_request_cancellation` at shutdown (and by any future
  caller that cancels accepted operations). No adversary is modelled; the database and destination
  are the user's own files, already admitted through the path authority.
* **Environments:** the export runs only on unix (`off_unix_refusal("PGN atomic replacement", …)`
  at the command and in `replace_pgn_atomic`). Windows must compile and lint (the Windows clippy
  lane), and cross-platform tests must stay cross-platform; tests that reach the atomic rename stay
  `#[cfg(unix)]` like their existing neighbours.
* **Non-goals:** a renderer-side Cancel button for exports (a product surface; no renderer path
  cancels accepted exports today, d-20260908-13); a cancel *acknowledgement* contract like the
  download commit gate (d-20260920-02 / d-20261005-12) — nobody is told "export cancelled"; the
  class-wide regression anchor for forwarding a token into connection acquisition (`f-20261004-17`,
  open, owns that seam for every `get_db_or_create(…, Some(token), …)` call site including the one
  this plan adds).

## Approach

### O1 — The export worker owns and forwards its token

MANDATE: "the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks".

`export_to_pgn` passes the gateway's worker token into `export_to_pgn_blocking`, which takes a
`cancellation: &CancellationToken` parameter and forwards it into connection acquisition
(`get_db_or_create(…, Some(cancellation), …)`), the row writer (O2) and the atomic replacement (O3).
No new token, no clone detached from the lease: shutdown's seal reaches every checkpoint.

### O2 — Per-row checkpoint before the next row is pulled

MANDATE: "still processes every row"; open question "per row, per chunk".

`write_pgn_rows` takes the token and checks it once per row **before advancing the row iterator**
(so no further SQLite step, decode or write happens after a cancellation is observed), returning
`Error::Cancellation`. Granularity is per row: the check is one uncontended mutex read (P10) against
decoding and formatting a whole game, and per-row makes the bound exact ("at most the row in flight
completes") without a chunk constant. The early return propagates out of the `replace_pgn_atomic`
write closure, so the temporary is discarded by the driver (P7) and the destination stays as it was.

### O3 — The shared PGN replace primitive re-checks cancellation immediately before commit

MANDATE: "can publish the completed destination"; "a cancelled export must not publish".

`ResolvedPath::replace_pgn_atomic` takes `cancellation: &CancellationToken` and checks it as the
first step of the `precommit` closure it already builds (before the logical-parent revalidation),
returning `Error::Cancellation`. This covers the window after the last row — final flush, `sync_all`
of a possibly hundreds-of-MB temporary, metadata — that no row check can see. Both production
callers pass their token (`export_to_pgn_blocking`: the worker token; `edit_existing`: its existing
`cancellation`), so the second caller gets the same guarantee through the same primitive (rule 11);
`edit_existing`'s existing per-chunk and closure checks stay. The rename and every step after it stay
unchecked: a cancellation that arrives after the last check loses the race and the operation reports
its real outcome (`Ok`, or `CommittedDurabilityUncertain` through `require_durable`), as d-20260908-13
("commit tails report their actual outcome even after late cancellation") and d-20261004-14 (final
token check before commit, commit unarmed) already decided. The signature line keeps the exact
prefix `pub(crate) fn replace_pgn_atomic<F>(` so the P9 guard pin and the P8 call-site pin stay
valid unchanged.

### O4 — Outcome contract on cancellation

Answer to the open question: **never publish** — the existing atomic temporary is the staging file
and is discarded on every pre-rename error (P7); no new staging mechanism. On any cancellation
observed before the rename: the previous destination is byte-identical (or still absent) and nothing
is renamed into place. When the temporary's unlink succeeds, the command returns
`Error::Cancellation` and no `.atomic-*` residue remains. When the unlink itself fails, the existing
driver mapping applies unchanged (`infra/fs.rs:1686-1704` `cleanup`): the result is
`Error::OperationAndCleanup { primary: "Cancellation", cleanup: … }`, logged at error, and the
staging file may remain — this plan does not remap it to `Cancellation`, because that would hide the
residue the user may need to remove; the renderer then shows its generic error instead of a silent
cancel, which is truthful. The error mapping and renderer handling are otherwise unchanged
(`Error::Cancellation` already exists and is logged at debug by `run_native_operation`, P5; the
renderer's export path treats a `"Cancellation"` error as silent).

# Plan: Database export honours cancellation while decoding and writing rows (f-20260914-18)

## Goal

A cancelled database export (today: application shutdown sealing the native operation registry
while an export runs) stops promptly at the next row, returns `Error::Cancellation` (or, only when
removing the staging file itself fails, the existing `OperationAndCleanup` error — O4), and never
publishes its destination; a cancellation that arrives after the last row, while the temporary
file is flushed and synced, is still honoured by a final check immediately before the atomic
commit. Only a cancellation that arrives after that final check loses the race (O3). Uncancelled
exports behave exactly as today.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-18`:

> * **Where:** src-tauri/src/db/mod.rs:2725 (the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks)
> * **Defect:** Cancelling an export, or shutting down during one, of a large database (hundreds of MB, millions of games) still processes every row and can publish the completed destination. Distinct from handled `f-20260904-04` (rows silently dropped on decode failure).
> * **Why it matters:** `.claude/rules/async-resource-invariants.md`: cancellation must be checked before use, and a cancelled export must not publish.
> * **Open question:** Where are cancellation checkpoints placed (per row, per chunk) and what happens to a partially written destination on cancel — discard the staging file, or never publish?

## Threat model and non-goals

* **Accidental input only.** The cancellation source is the native operation registry: the export
  is an *accepted* operation (`state.operations.accept("export_to_pgn")`), so its lease token is
  cancelled by `OperationRegistry::seal_and_request_cancellation` at shutdown (and by any future
  caller that cancels accepted operations). No adversary is modelled; the database and destination
  are the user's own files, already admitted through the path authority.
* **Environments:** the export runs only on unix (`off_unix_refusal("PGN atomic replacement", …)`
  at the command and in `replace_pgn_atomic`). Windows must compile and lint (the Windows clippy
  lane), and cross-platform tests must stay cross-platform; tests that reach the atomic rename stay
  `#[cfg(unix)]` like their existing neighbours.
* **Non-goals:** a renderer-side Cancel button for exports (a product surface; no renderer path
  cancels accepted exports today, d-20260908-13); a cancel *acknowledgement* contract like the
  download commit gate (d-20260920-02 / d-20261005-12) — nobody is told "export cancelled"; the
  class-wide regression anchor for forwarding a token into connection acquisition (`f-20261004-17`,
  open, owns that seam for every `get_db_or_create(…, Some(token), …)` call site including the one
  this plan adds).

## Approach

### O1 — The export worker owns and forwards its token

MANDATE: "the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks".

`export_to_pgn` passes the gateway's worker token into `export_to_pgn_blocking`, which takes a
`cancellation: &CancellationToken` parameter and forwards it into connection acquisition
(`get_db_or_create(…, Some(cancellation), …)`), the row writer (O2) and the atomic replacement (O3).
No new token, no clone detached from the lease: shutdown's seal reaches every checkpoint.

### O2 — Per-row checkpoint before the next row is pulled

MANDATE: "still processes every row"; open question "per row, per chunk".

`write_pgn_rows` takes the token and checks it once per row **before advancing the row iterator**
(so no further SQLite step, decode or write happens after a cancellation is observed), returning
`Error::Cancellation`. Granularity is per row: the check is one uncontended mutex read (P10) against
decoding and formatting a whole game, and per-row makes the bound exact ("at most the row in flight
completes") without a chunk constant. The early return propagates out of the `replace_pgn_atomic`
write closure, so the temporary is discarded by the driver (P7) and the destination stays as it was.

### O3 — The shared PGN replace primitive re-checks cancellation immediately before commit

MANDATE: "can publish the completed destination"; "a cancelled export must not publish".

`ResolvedPath::replace_pgn_atomic` takes `cancellation: &CancellationToken` and checks it as the
first step of the `precommit` closure it already builds (before the logical-parent revalidation),
returning `Error::Cancellation`. This covers the window after the last row — final flush, `sync_all`
of a possibly hundreds-of-MB temporary, metadata — that no row check can see. Both production
callers pass their token (`export_to_pgn_blocking`: the worker token; `edit_existing`: its existing
`cancellation`), so the second caller gets the same guarantee through the same primitive (rule 11);
`edit_existing`'s existing per-chunk and closure checks stay. The rename and every step after it stay
unchecked: a cancellation that arrives after the last check loses the race and the operation reports
its real outcome (`Ok`, or `CommittedDurabilityUncertain` through `require_durable`), as d-20260908-13
("commit tails report their actual outcome even after late cancellation") and d-20261004-14 (final
token check before commit, commit unarmed) already decided. The signature line keeps the exact
prefix `pub(crate) fn replace_pgn_atomic<F>(` so the P9 guard pin and the P8 call-site pin stay
valid unchanged.

### O4 — Outcome contract on cancellation

Answer to the open question: **never publish** — the existing atomic temporary is the staging file
and is discarded on every pre-rename error (P7); no new staging mechanism. On any cancellation
observed before the rename: the previous destination is byte-identical (or still absent) and nothing
is renamed into place. When the temporary's unlink succeeds, the command returns
`Error::Cancellation` and no `.atomic-*` residue remains. When the unlink itself fails, the existing
driver mapping applies unchanged (`infra/fs.rs:1686-1704` `cleanup`): the result is
`Error::OperationAndCleanup { primary: "Cancellation", cleanup: … }`, logged at error, and the
staging file may remain — this plan does not remap it to `Cancellation`, because that would hide the
residue the user may need to remove; the renderer then shows its generic error instead of a silent
cancel, which is truthful. The error mapping and renderer handling are otherwise unchanged
(`Error::Cancellation` already exists and is logged at debug by `run_native_operation`, P5; the
renderer's export path treats a `"Cancellation"` error as silent).

## Decisions and trade-offs

* Per-row, not per-chunk, checkpoints (O2) — see O2 for the cost argument.
* No SQLite progress-handler scope (`with_sqlite_cancellation`) around the export query: the query
  has no `ORDER BY` (P2), so SQLite streams rows and the VM work between two pulls is one row's
  joined primary-key lookups; the uncancellable gap the finding names is the Rust loop, which O2
  closes. Arming the scope would add a second cancellation mechanism for no reachable window.
* The pre-commit check lives in the shared primitive, not in an export-only wrapper (rule 11): two
  production callers, one window.
* No operation commit gate (`OperationCommitGate::begin_commit`): it is download-only by contract
  and exists to make a cancel *acknowledgement* exact; exports have no acknowledgement.

## Decided autonomously

* **Question:** Where are export cancellation checkpoints placed, and what happens to a partially
  written destination? **Chosen:** forward the gateway worker token; check it before pulling each
  row and once more in `replace_pgn_atomic`'s pre-commit hook (shared with the PGN edit path); never
  publish — the atomic temporary is discarded on cancellation; the rename stays unarmed and a later
  cancel reports the real outcome. **Rejected:** per-chunk checks (a chunk constant for no
  measurable gain over one uncontended mutex read per game); a SQLite progress-handler scope over
  the export query (no reachable long VM step: streaming query without `ORDER BY`); an export-only
  pre-commit check (leaves the PGN edit path's identical window open, rule 11); the download commit
  gate (acknowledgement contract exports do not have). **Reason:** the finding's two gaps are the
  Rust row loop and the post-write window; both close with existing primitives, consistent with
  d-20261004-14 and d-20260908-13. **Reversal path:** remove the `cancellation` parameters and the
  two checks.

# Plan: Database export honours cancellation while decoding and writing rows (f-20260914-18)

## Goal

A cancelled database export (today: application shutdown sealing the native operation registry
while an export runs) stops promptly at the next row, returns `Error::Cancellation` (or, only when
removing the staging file itself fails, the existing `OperationAndCleanup` error — O4), and never
publishes its destination; a cancellation that arrives after the last row, while the temporary
file is flushed and synced, is still honoured by a final check immediately before the atomic
commit. Only a cancellation that arrives after that final check loses the race (O3). Uncancelled
exports behave exactly as today.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-18`:

> * **Where:** src-tauri/src/db/mod.rs:2725 (the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks)
> * **Defect:** Cancelling an export, or shutting down during one, of a large database (hundreds of MB, millions of games) still processes every row and can publish the completed destination. Distinct from handled `f-20260904-04` (rows silently dropped on decode failure).
> * **Why it matters:** `.claude/rules/async-resource-invariants.md`: cancellation must be checked before use, and a cancelled export must not publish.
> * **Open question:** Where are cancellation checkpoints placed (per row, per chunk) and what happens to a partially written destination on cancel — discard the staging file, or never publish?

## Threat model and non-goals

* **Accidental input only.** The cancellation source is the native operation registry: the export
  is an *accepted* operation (`state.operations.accept("export_to_pgn")`), so its lease token is
  cancelled by `OperationRegistry::seal_and_request_cancellation` at shutdown (and by any future
  caller that cancels accepted operations). No adversary is modelled; the database and destination
  are the user's own files, already admitted through the path authority.
* **Environments:** the export runs only on unix (`off_unix_refusal("PGN atomic replacement", …)`
  at the command and in `replace_pgn_atomic`). Windows must compile and lint (the Windows clippy
  lane), and cross-platform tests must stay cross-platform; tests that reach the atomic rename stay
  `#[cfg(unix)]` like their existing neighbours.
* **Non-goals:** a renderer-side Cancel button for exports (a product surface; no renderer path
  cancels accepted exports today, d-20260908-13); a cancel *acknowledgement* contract like the
  download commit gate (d-20260920-02 / d-20261005-12) — nobody is told "export cancelled"; the
  class-wide regression anchor for forwarding a token into connection acquisition (`f-20261004-17`,
  open, owns that seam for every `get_db_or_create(…, Some(token), …)` call site including the one
  this plan adds).

## Approach

### O1 — The export worker owns and forwards its token

MANDATE: "the cancellable export worker discards its token; `export_to_pgn_blocking` has no checks".

`export_to_pgn` passes the gateway's worker token into `export_to_pgn_blocking`, which takes a
`cancellation: &CancellationToken` parameter and forwards it into connection acquisition
(`get_db_or_create(…, Some(cancellation), …)`), the row writer (O2) and the atomic replacement (O3).
No new token, no clone detached from the lease: shutdown's seal reaches every checkpoint.

### O2 — Per-row checkpoint before the next row is pulled

MANDATE: "still processes every row"; open question "per row, per chunk".

`write_pgn_rows` takes the token and checks it once per row **before advancing the row iterator**
(so no further SQLite step, decode or write happens after a cancellation is observed), returning
`Error::Cancellation`. Granularity is per row: the check is one uncontended mutex read (P10) against
decoding and formatting a whole game, and per-row makes the bound exact ("at most the row in flight
completes") without a chunk constant. The early return propagates out of the `replace_pgn_atomic`
write closure, so the temporary is discarded by the driver (P7) and the destination stays as it was.

### O3 — The shared PGN replace primitive re-checks cancellation immediately before commit

MANDATE: "can publish the completed destination"; "a cancelled export must not publish".

`ResolvedPath::replace_pgn_atomic` takes `cancellation: &CancellationToken` and checks it as the
first step of the `precommit` closure it already builds (before the logical-parent revalidation),
returning `Error::Cancellation`. This covers the window after the last row — final flush, `sync_all`
of a possibly hundreds-of-MB temporary, metadata — that no row check can see. Both production
callers pass their token (`export_to_pgn_blocking`: the worker token; `edit_existing`: its existing
`cancellation`), so the second caller gets the same guarantee through the same primitive (rule 11);
`edit_existing`'s existing per-chunk and closure checks stay. The rename and every step after it stay
unchecked: a cancellation that arrives after the last check loses the race and the operation reports
its real outcome (`Ok`, or `CommittedDurabilityUncertain` through `require_durable`), as d-20260908-13
("commit tails report their actual outcome even after late cancellation") and d-20261004-14 (final
token check before commit, commit unarmed) already decided. The signature line keeps the exact
prefix `pub(crate) fn replace_pgn_atomic<F>(` so the P9 guard pin and the P8 call-site pin stay
valid unchanged.

### O4 — Outcome contract on cancellation

Answer to the open question: **never publish** — the existing atomic temporary is the staging file
and is discarded on every pre-rename error (P7); no new staging mechanism. On any cancellation
observed before the rename: the previous destination is byte-identical (or still absent) and nothing
is renamed into place. When the temporary's unlink succeeds, the command returns
`Error::Cancellation` and no `.atomic-*` residue remains. When the unlink itself fails, the existing
driver mapping applies unchanged (`infra/fs.rs:1686-1704` `cleanup`): the result is
`Error::OperationAndCleanup { primary: "Cancellation", cleanup: … }`, logged at error, and the
staging file may remain — this plan does not remap it to `Cancellation`, because that would hide the
residue the user may need to remove; the renderer then shows its generic error instead of a silent
cancel, which is truthful. The error mapping and renderer handling are otherwise unchanged
(`Error::Cancellation` already exists and is logged at debug by `run_native_operation`, P5; the
renderer's export path treats a `"Cancellation"` error as silent).

## Decisions and trade-offs

* Per-row, not per-chunk, checkpoints (O2) — see O2 for the cost argument.
* No SQLite progress-handler scope (`with_sqlite_cancellation`) around the export query: the query
  has no `ORDER BY` (P2), so SQLite streams rows and the VM work between two pulls is one row's
  joined primary-key lookups; the uncancellable gap the finding names is the Rust loop, which O2
  closes. Arming the scope would add a second cancellation mechanism for no reachable window.
* The pre-commit check lives in the shared primitive, not in an export-only wrapper (rule 11): two
  production callers, one window.
* No operation commit gate (`OperationCommitGate::begin_commit`): it is download-only by contract
  and exists to make a cancel *acknowledgement* exact; exports have no acknowledgement.

## Decided autonomously

* **Question:** Where are export cancellation checkpoints placed, and what happens to a partially
  written destination? **Chosen:** forward the gateway worker token; check it before pulling each
  row and once more in `replace_pgn_atomic`'s pre-commit hook (shared with the PGN edit path); never
  publish — the atomic temporary is discarded on cancellation; the rename stays unarmed and a later
  cancel reports the real outcome. **Rejected:** per-chunk checks (a chunk constant for no
  measurable gain over one uncontended mutex read per game); a SQLite progress-handler scope over
  the export query (no reachable long VM step: streaming query without `ORDER BY`); an export-only
  pre-commit check (leaves the PGN edit path's identical window open, rule 11); the download commit
  gate (acknowledgement contract exports do not have). **Reason:** the finding's two gaps are the
  Rust row loop and the post-write window; both close with existing primitives, consistent with
  d-20261004-14 and d-20260908-13. **Reversal path:** remove the `cancellation` parameters and the
  two checks.
