#### I1 — A concurrent listing can register the PGN the rollback removes

* **Claim (review-plan r1 finding 1, blocker, confidence 95):** "Holding the mutation lock does not prevent a concurrent listing from registering the installed PGN during O1’s count. Listing takes no mutation lock and commits discovered children before counting (`src-tauri/src/file_workspace.rs:642`, `:551`); its existing test explicitly preserves registration after a count failure (`:5467`, `:5481`). If the create’s count then fails, O3 removes the files but leaves that persisted registration, contradicting O6’s “no registry record” result at plan line 326. Specify coordination between discovery and rollback, and require a concurrent-list/count-failure proof."
* **Witnesses:** plan r1 #1.
* **Evidence:** confirmed. `file_workspace.rs:536-551` registers discovered children under the path-authority lock only. `infra/path_authority/mod.rs:7700-7745` mints a fresh id unless path, identity, parent identity, kind and purpose all match, so a stale record never blocks a retry. `file_workspace.rs:5440-5462` shows the next listing prunes a vanished file's record. The same listing-versus-rollback window exists before this change for the sidecar-failure rollback (`:940-971`) and the directory-registration rollback (`:1065-1090`).
* **MANDATE:** "every exit path cleaned up or reported truthfully"; O6's "no registry record" claim was false under concurrency.
* **Disposition:** Fix. The hazard exists equally in the pre-change system, so under rule 12a it becomes a named known limit, not a new lock or registry-removal mechanism: O3 states it, O6 qualifies "no registry record" to the non-concurrent case and adds a proof that the race heals (create returns the count error, files gone, the next listing leaves no record, a retry succeeds), P21 records the evidence, Risks names it. The concurrent listing's own failure on the vanished file is `f-20261003-08` (filed, open).
* **Authority:** MANDATE "reported truthfully"; no new mechanism added.
* **Closure:** round 2 (review-plan, tests).

### plan-r1.md

# Plan: workspace create never reports a committed entry as a clean failure (f-20260914-02)

## Goal

After `create_workspace_file` or `create_workspace_directory` has made an entry visible on disk,
the command either returns that entry, or returns a typed outcome that truthfully says what was
left behind: nothing (rolled back), something the rollback could not remove
(`OperationAndCleanup`), or a committed entry whose durability is uncertain
(`CommittedDurabilityUncertain`, which the renderer already recovers by relisting). Every
fallible step that follows the on-disk creation runs before registration, so its failure is
rolled back; nothing fallible runs after registration.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260914-02:

> * **Where:** `src-tauri/src/file_workspace.rs:770-795` (`create_workspace_file` core): `register_created_entry(...)?` and `timestamp(&target)?` run after the PGN and its sidecar were installed; the analogous post-create steps in `create_workspace_directory` (~`:883`).
> * **Defect:** once the file and sidecar exist on disk (and, for the timestamp step, the registry record too), a registry-persistence or metadata error is returned through `?` as a plain failure. The renderer is told creation failed while a committed file remains, with no rollback and no `applied-despite-error` result, so a retry collides with the leftover name.
> * **Why it matters:** `.claude/rules/async-resource-invariants.md` (every exit path cleaned up or reported truthfully) and `d-20260906-03` (committed-but-uncertain outcomes are reported, never presented as clean failure).
> * **Open question:** after a committed create, should a later registry/metadata failure compensate (unlink the just-created entry, which d-20260906-03 warns can delete the only committed copy) or report an applied-despite-error outcome the renderer relists on?

## Threat model and non-goals

* **In scope (accidental faults in normal use):** I/O and `fsync` failures, a registry write that
  fails or whose parent sync fails, lock poisoning, the operation token cancelled by application
  shutdown (`RunEvent::ExitRequested` → `seal_and_request_cancellation`), malformed PGN text the
  user pasted or imported, and an external program (sync client, file manager) touching a
  just-created leaf between our steps: replacing it, removing it, or adding files inside a new
  directory. Such an external object is never deleted by a rollback; the only external object a
  rollback may remove is an *empty* directory substituted at the same name in the window between
  our directory create and its observation (no file data can be lost that way). Linux, macOS and
  Windows all count.
* **Out of scope:** a deliberate local adversary racing the identity check inside a removal on
  Unix (the terminal `unlinkat` is not inode-conditional; that window is `f-20260830-09`, open).
  Create-over-an-existing-name semantics (see "Not part of this task").

    `infra/path_authority/resolved.rs` that takes the open descriptor and the expected identity,
    refuses a mismatch, and otherwise builds the snapshot exactly as `pgn_snapshot_file` does
    (P10; that function and `PgnSnapshotIdentity`'s field stay private). It is the only way
    outside the module to obtain a snapshot without a resolved capability, and it never opens by
    pathname;
  * a snapshot's revision accepts a pre-1970 modification time as a negative nanosecond count,
    on both platforms, for **every** snapshot (one implementation in `pgn_snapshot_file`, the
    revision and cache-key `mtime_nanos` become signed). Today any pre-1970 PGN is refused by
    every read (P17); without this, O1 would turn a pre-1970 installed file into a failed create
    and break the tested `d-20261003-06`/`d-20261003-07` create contract. Revision strings of
    post-1970 files are byte-identical to today's;
  * through the repository's cache-or-scan sequence for that snapshot (P10): a synchronous scan
    with the existing strict scanner (no second boundary rule, `.claude/rules/pgn-scanning.md`)
    whose index is offered to the cache under the installed file's key with the existing budget
    rule, so the follow-up listing and the first open hit the cache exactly when today's
    post-install count would have left a hit — an index larger than the cache budget is not
    retained, as today. `scan_current` and this path share one implementation of the
    lookup/scan/retain sequence (rule 11), and the repository count hook (P19) sits in that
    shared step or is reached by both callers, so a test can still pause a create's count;
  * without any new `BLOCKING_GATEWAY` acquisition (it already runs inside the core's permit;
    `d-20260903-04`), observing the operation token.
* Any count failure (`Cancellation` including shutdown, `InvalidData`, `ResourceLimit`, I/O,
  `Conflict`, a poisoned repository lock) is an ordinary failure before registration and goes to
  O3's rollback.
* The returned `WorkspaceEntry.game_count` is `Some(that count)`, set by the core.
* Ownership: the workspace mutation lock is held across the count, as it already is across the
  copy; the count reads the file the copy just wrote.
* Supersedes `d-20260927-02`'s count clause (P15): a count failure no longer keeps the installed
  file. New evidence that decision did not weigh: P11 (a kept unscannable file makes every later
  listing of the workspace fail) and P13 (no renderer flow recovers a plain count error, so the
  kept file is reported as a failed create — this finding); its own rejection reason was the
  previous mandate's scope, and this mandate is where the question belongs.

### O2 — The command adds no fallible step after the core

MANDATE words: the renderer "is told creation failed while a committed file remains".

* `create_workspace_file` returns the blocking core's result directly. The post-core
  `resolve(..., ReadPgn)` and `count_pgn_games_core` (P1) are removed; there is no step between a
  committed core result and the command's return that can turn it into an error.
* The non-nesting proofs follow the count to its new side (`d-20260903-04`, P18): the
  `create_workspace_file` row of `s9_nested_awaits_stay_on_the_async_side` is removed, because
  the count deliberately leaves the async side; the synchronous count path O1 adds (the shared
  lookup/scan/retain step and anything it calls in `pgn.rs`) is placed under
  `s8_blocking_functions_do_not_nest_the_gateway`, by name in its explicit list or by a
  `_blocking` name in a scanned file, so a later `BLOCKING_GATEWAY`/`.await` inside it fails that
  test. The `infra/blocking.rs` doc comment's example of a legal sequential acquisition, which
  names `create_workspace_file` → `count_pgn_games_core`, is rewritten to a caller for which it
  remains true (`list_file_workspace_core` → `count_pgn_games_core`).

### O3 — One rollback policy for every ordinary failure after an on-disk create

MANDATE words: "should a later registry/metadata failure compensate … or report an
applied-despite-error outcome"; decided by precedent `d-20260901-06` and `d-20260906-03`.

* **Trigger.** Every ordinary (non-`CommittedDurabilityUncertain`) error after the first on-disk
  create and before a successful registration is rolled back: for files the sidecar install
  (P4), the O1 count, and registration; for directories the observation (O4) and registration.
* **Registration outcomes.** `Ok(handle)` → continue; `Err(CommittedDurabilityUncertain(_))` →
  the authority adopted the entry (P7), keep every created object, no rollback, report under O5;
  any other error → the registry is unchanged (P7), roll back.
* **What a rollback removes.** Only objects this call created, each checked against the identity
  it was created with:
  * file: the sidecar and the PGN, each identity-checked; the sidecar is installed through the
    identity-returning atomic replacement (P9) so it has an identity to check. When the O1 count
    already offered an index to the repository cache, the rollback also invalidates the cache
    entries of the PGN's identity (the repository's existing per-identity invalidation, P10), so a
    retry whose new file reuses that identity cannot hit a stale index; an invalidation failure is
    a cleanup failure;
  * directory: the directory only if it is **still the observed identity and still empty** —
    the removal never descends, so a file an external program placed inside is never deleted
    (today's `remove_entry_at(.., true)` is recursive, P8), and a different object now at the
    name (another directory, empty or not, or a file) is never removed. This is one
    identity-checked, empty-only directory removal in `infra/fs.rs` with the same parent-sync
    outcome as `remove_entry_at`, on both platforms (P20).
  * Nothing is ever removed by name alone: when the directory's identity was never observed
    (O4), there is nothing the rollback can prove is ours, so it removes nothing and reports that
    the created directory could not be identified and was not removed (without claiming it is
    still there: it may have been removed or replaced externally).
  * Every removal is attempted even if an earlier one failed.
* **Result.** `Error::with_cleanup(primary, cleanup)` (P12): the primary error when every removal
  succeeded, `OperationAndCleanup` when any removal failed or could not be attempted (a replaced
  or non-empty leaf, a failed unlink, a removal whose parent sync was uncertain, a failed cache
  invalidation, or an unidentified directory that was not removed). The existing sidecar-failure
  rollback and directory rollback route through this one fold, so no hand-written
  `OperationAndCleanup { primary, cleanup }` fold remains in the two create paths.
* **Rollback after an uncertain earlier step.** When an earlier step's parent sync was uncertain
  and a later ordinary error occurs, the rollback still runs and the later error is reported.
  This is `d-20260906-03`'s *combine* contract ("a later non-uncertainty error outranks it",
  workspace create), which was recorded with exactly this sidecar-failure rollback in place
  (P16). It is not the compensation `d-20260906-03` rejected: that one was triggered *by* the
  uncertainty, and removed the only copy of committed content; here the trigger is a failure that
  makes the create fail, and the created bytes still exist in the request (`Text`) or the
  unchanged source (`Copy`).

### O4 — Directory creation reports or rolls back every post-create step

MANDATE words: "the analogous post-create steps in `create_workspace_directory`"; `d-20260906-03`
assigns "workspace file/directory creation" to its *report* contract.

* `create_dir_at`'s create-then-sync is split so the workspace directory path learns the
  outcome: the create failing is an error (nothing created); the create succeeding and the parent
  sync failing is a `#[must_use]` committed-uncertain outcome, the same `AtomicFileOutcome` shape
  the file path already handles. Both platforms (P6) get the same split.
* `create_workspace_directory_inner` carries that uncertainty through observation and
  registration and reports it under O5 as
  `CommittedDurabilityUncertain(DurabilityStage::WorkspaceDirectoryCreation)`, a new stage
  displayed as "workspace directory creation". The renderer recovers it by refreshing, exactly as
  for the file stages (P13); no renderer change.
* An `entry_observation_at` failure after a successful create is reported, never a plain error:
  the leaf has no identity this call can prove is its own, so O3 removes nothing and returns
  `OperationAndCleanup` whose primary half is the observation error (whatever its cause: an I/O
  failure, the leaf gone, or the leaf replaced by a non-directory) and whose cleanup half says
  the created directory could not be identified and was not removed. Nothing is registered. If
  a directory is still at the name, the next listing registers it (P11 collection registers
  discovered children).
* The three other `create_dir_at` callers (P6) keep their current behaviour: a post-create sync
  failure is still returned to them as the same `Error::Io` it is today, through one adapter.

### O5 — Combined reporting order for the create paths

From `d-20260906-03` contract (3) *combine*, applied to the steps of one create:

* Operation order: PGN install, sidecar install, count, registration (file); directory create,
  observation, registration (directory).
* An ordinary error at any step after the first on-disk create outranks every earlier
  uncertainty and is handled by O3.
* Otherwise the **first** uncertain stage in operation order is reported, after all later steps
  completed: `WorkspacePgnCreation`, then `WorkspaceSidecarCreation`, then `RegistryReplacement`
  (file); `WorkspaceDirectoryCreation`, then `RegistryReplacement` (directory).
* With no uncertainty and no error the entry is returned.

## Decisions and trade-offs

* **Starting point.** A 2026-10-03 PLAN-ONLY run (drain session
  `b1d90b24-0cf0-4e7d-8d87-ab95faeee372`, BASE `1d0fc9ca`) converged on this design in five
  rounds; its publication was rejected by the supervisor's Defer-receipt check, not by review, and
  its plan file did not survive. This plan is that draft re-traced at `52e301ba` (all premises
  still hold, line numbers updated, P19/P20 added); it is reviewed here from round 1 with the full
  lens set and is not adopted as reviewed.
* **Compensate vs report (the finding's open question):** compensate on every *ordinary* failure
  after an on-disk create and before registration; report a *committed-uncertain* registration.
  Precedent `d-20260901-06` decided exactly this for `create_workspace_directory` and
  `create_database_child`.
* **Where the count is taken:** on the installed file before registration (O1), rather than (a)
  counting the request bytes / source snapshot before publication plus a post-install cache warm —
  two scans of a large import and a warm whose failure must be swallowed; (b) a new
  applied-despite-error variant for a post-registration count failure — the renderer would relist
  and the listing would hit the same count failure (P11); (c) a nullable count —
  `FileMetadata.numGames` is required by its consumers (P13).
* **Empty-only directory rollback** rather than today's recursive removal: a new directory's
  rollback has no business deleting anything an external program put inside it.
* **`create_dir_at` split with a behaviour-preserving adapter** rather than changing every caller's
  error: the other three callers are internal steps of larger operations whose current error is
  not a misreport of a committed user operation.

### plan-r2.md

# Plan: workspace create never reports a committed entry as a clean failure (f-20260914-02)

## Goal

After `create_workspace_file` or `create_workspace_directory` has made an entry visible on disk,
the command either returns that entry, or returns a typed outcome that truthfully says what was
left behind: nothing (rolled back), something the rollback could not remove
(`OperationAndCleanup`), or a committed entry whose durability is uncertain
(`CommittedDurabilityUncertain`, which the renderer already recovers by relisting). Every
fallible step that follows the on-disk creation runs before registration, so its failure is
rolled back; nothing fallible runs after registration.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260914-02:

> * **Where:** `src-tauri/src/file_workspace.rs:770-795` (`create_workspace_file` core): `register_created_entry(...)?` and `timestamp(&target)?` run after the PGN and its sidecar were installed; the analogous post-create steps in `create_workspace_directory` (~`:883`).
> * **Defect:** once the file and sidecar exist on disk (and, for the timestamp step, the registry record too), a registry-persistence or metadata error is returned through `?` as a plain failure. The renderer is told creation failed while a committed file remains, with no rollback and no `applied-despite-error` result, so a retry collides with the leftover name.
> * **Why it matters:** `.claude/rules/async-resource-invariants.md` (every exit path cleaned up or reported truthfully) and `d-20260906-03` (committed-but-uncertain outcomes are reported, never presented as clean failure).
> * **Open question:** after a committed create, should a later registry/metadata failure compensate (unlink the just-created entry, which d-20260906-03 warns can delete the only committed copy) or report an applied-despite-error outcome the renderer relists on?

## Threat model and non-goals

* **In scope (accidental faults in normal use):** I/O and `fsync` failures, a registry write that
  fails or whose parent sync fails, lock poisoning, the operation token cancelled by application
  shutdown (`RunEvent::ExitRequested` → `seal_and_request_cancellation`), malformed PGN text the
  user pasted or imported, and an external program (sync client, file manager) touching a
  just-created leaf between our steps: replacing it, removing it, or adding files inside a new
  directory. Such an external object is never deleted by a rollback; the only external object a
  rollback may remove is an *empty* directory substituted at the same name in the window between
  our directory create and its observation (no file data can be lost that way). Linux, macOS and
  Windows all count.
* **Out of scope:** a deliberate local adversary racing the identity check inside a removal on
  Unix (the terminal `unlinkat` is not inode-conditional; that window is `f-20260830-09`, open).
  Create-over-an-existing-name semantics (see "Not part of this task").

## Approach

### O1 — The installed PGN is counted before registration

MANDATE words: "a registry-persistence or metadata error is returned through `?` as a plain
failure" once "the file and sidecar exist on disk … and … the registry record too"; P1 is that
step today.

* `create_workspace_file_blocking` counts the games of the PGN it just installed **after the
  sidecar install and before registration**, inside the existing blocking worker:
  * it reads the installed object only: through a read descriptor opened relative to the
    retained parent and verified against the installed identity (P9's `identity`), never by
    pathname; a different object at the name is a `Conflict`;
  * the snapshot it counts is built from that descriptor by the same rule as every other
    snapshot of the file (P10), so its cache key and revision equal what a later listing or open
    computes for the untouched file; the path authority still grants no snapshot without either
    a resolved capability or a descriptor whose identity the caller has proved;
  * a snapshot's revision accepts a pre-1970 modification time as a negative nanosecond count,
    on both platforms, for **every** snapshot (one implementation in `pgn_snapshot_file`, the
    revision and cache-key `mtime_nanos` become signed). Today any pre-1970 PGN is refused by
    every read (P17); without this, O1 would turn a pre-1970 installed file into a failed create
    and break the tested `d-20261003-06`/`d-20261003-07` create contract. Revision strings of
    post-1970 files are byte-identical to today's;
  * through the repository's cache-or-scan sequence for that snapshot (P10): a synchronous scan
    with the existing strict scanner (no second boundary rule, `.claude/rules/pgn-scanning.md`)
    whose index is offered to the cache under the installed file's key with the existing budget
    rule, so the follow-up listing and the first open hit the cache exactly when today's
    post-install count would have left a hit — an index larger than the cache budget is not
    retained, as today. `scan_current` and this path share one implementation of the
    lookup/scan/retain sequence (rule 11), and the repository count hook (P19) sits in that
    shared step or is reached by both callers, so a test can still pause a create's count;
  * without any new `BLOCKING_GATEWAY` acquisition (it already runs inside the core's permit;
    `d-20260903-04`), observing the operation token.
* Any count failure (`Cancellation` including shutdown, `InvalidData`, `ResourceLimit`, I/O,
  `Conflict`, a poisoned repository lock) is an ordinary failure before registration and goes to
  O3's rollback.
* The returned `WorkspaceEntry.game_count` is `Some(that count)`, set by the core.
* Ownership: the workspace mutation lock is held across the count, as it already is across the
  copy; the count reads the file the copy just wrote.
* Supersedes `d-20260927-02`'s count clause (P15): a count failure no longer keeps the installed
  file. New evidence that decision did not weigh: P11 (a kept unscannable file makes every later
  listing of the workspace fail) and P13 (no renderer flow recovers a plain count error, so the
  kept file is reported as a failed create — this finding); its own rejection reason was the
  previous mandate's scope, and this mandate is where the question belongs.

### O2 — The command adds no fallible step after the core

MANDATE words: the renderer "is told creation failed while a committed file remains".

* `create_workspace_file` returns the blocking core's result directly. The post-core
  `resolve(..., ReadPgn)` and `count_pgn_games_core` (P1) are removed; there is no step between a
  committed core result and the command's return that can turn it into an error.
* The non-nesting proofs follow the count to its new side (`d-20260903-04`, P18): the
  `create_workspace_file` row of `s9_nested_awaits_stay_on_the_async_side` is removed, because
  the count deliberately leaves the async side; the synchronous count path O1 adds (the shared
  lookup/scan/retain step and anything it calls in `pgn.rs`) is placed under
  `s8_blocking_functions_do_not_nest_the_gateway`, by name in its explicit list or by a
  `_blocking` name in a scanned file, so a later `BLOCKING_GATEWAY`/`.await` inside it fails that
  test. The `infra/blocking.rs` doc comment's example of a legal sequential acquisition, which
  names `create_workspace_file` → `count_pgn_games_core`, is rewritten to a caller for which it
  remains true (`list_file_workspace_core` → `count_pgn_games_core`).

### O3 — One rollback policy for every ordinary failure after an on-disk create

MANDATE words: "should a later registry/metadata failure compensate … or report an
applied-despite-error outcome"; decided by precedent `d-20260901-06` and `d-20260906-03`.

* **Trigger.** Every ordinary (non-`CommittedDurabilityUncertain`) error after the first on-disk
  create and before a successful registration is rolled back: for files the sidecar install
  (P4), the O1 count, and registration; for directories the observation (O4) and registration.
* **Registration outcomes.** `Ok(handle)` → continue; `Err(CommittedDurabilityUncertain(_))` →
  the authority adopted the entry (P7), keep every created object, no rollback, report under O5;
  any other error → the registry is unchanged (P7), roll back.
* **What a rollback removes.** Only objects this call created, each checked against the identity
  it was created with:
  * file: the sidecar and the PGN, each identity-checked; the sidecar is installed through the
    identity-returning atomic replacement (P9) so it has an identity to check. When the O1 count
    already offered an index to the repository cache, the rollback also invalidates the cache
    entries of the PGN's identity (the repository's existing per-identity invalidation, P10), so a
    retry whose new file reuses that identity cannot hit a stale index; an invalidation failure is
    a cleanup failure;
  * directory: the directory only if it is **still the observed identity and still empty** —
    the removal never descends, so a file an external program placed inside is never deleted
    (today's `remove_entry_at(.., true)` is recursive, P8), and a different object now at the
    name (another directory, empty or not, or a file) is never removed. This is one
    identity-checked, empty-only directory removal in `infra/fs.rs` with the same parent-sync
    outcome as `remove_entry_at`, on both platforms (P20).
  * Nothing is ever removed by name alone: when the directory's identity was never observed
    (O4), there is nothing the rollback can prove is ours, so it removes nothing and reports that
    the created directory could not be identified and was not removed (without claiming it is
    still there: it may have been removed or replaced externally).
  * Every removal is attempted even if an earlier one failed.
* **Result.** `Error::with_cleanup(primary, cleanup)` (P12): the primary error when every removal
  succeeded, `OperationAndCleanup` when any removal failed or could not be attempted (a replaced
  or non-empty leaf, a failed unlink, a removal whose parent sync was uncertain, a failed cache
  invalidation, or an unidentified directory that was not removed). The existing sidecar-failure
  rollback and directory rollback route through this one fold, so no hand-written
  `OperationAndCleanup { primary, cleanup }` fold remains in the two create paths.
* **A concurrent listing is not excluded (known limit).** Listing walks and registers
  discovered children without the workspace mutation lock (P21), so a listing that runs between
  the PGN install and the rollback can register the installed PGN under its own fresh record. The
  rollback removes the files it created and does not touch that record; the record names a
  removed object, never blocks a retry (a different identity at the same path gets a fresh
  record), and the next listing prunes it. The same window exists today for the sidecar-failure
  and directory-registration rollbacks; O1 widens it by one scan. The listing that registered it
  fails its own count of the vanished file, which is `f-20261003-08`'s class. No new lock or
  registry-removal mechanism is part of this plan.
* **Rollback after an uncertain earlier step.** When an earlier step's parent sync was uncertain
  and a later ordinary error occurs, the rollback still runs and the later error is reported.
  This is `d-20260906-03`'s *combine* contract ("a later non-uncertainty error outranks it",
  workspace create), which was recorded with exactly this sidecar-failure rollback in place
  (P16). It is not the compensation `d-20260906-03` rejected: that one was triggered *by* the
  uncertainty, and removed the only copy of committed content; here the trigger is a failure that
  makes the create fail, and the created bytes still exist in the request (`Text`) or the
  unchanged source (`Copy`).

### O4 — Directory creation reports or rolls back every post-create step

MANDATE words: "the analogous post-create steps in `create_workspace_directory`"; `d-20260906-03`
assigns "workspace file/directory creation" to its *report* contract.

* `create_dir_at`'s create-then-sync is split so the workspace directory path learns the
  outcome: the create failing is an error (nothing created); the create succeeding and the parent
  sync failing is a `#[must_use]` committed-uncertain outcome, the same `AtomicFileOutcome` shape
  the file path already handles. Both platforms (P6) get the same split.
* `create_workspace_directory_inner` carries that uncertainty through observation and
  registration and reports it under O5 as
  `CommittedDurabilityUncertain(DurabilityStage::WorkspaceDirectoryCreation)`, a new stage
  displayed as "workspace directory creation". The renderer recovers it by refreshing, exactly as
  for the file stages (P13); no renderer change.
* An `entry_observation_at` failure after a successful create is reported, never a plain error:
  the leaf has no identity this call can prove is its own, so O3 removes nothing and returns
  `OperationAndCleanup` whose primary half is the observation error (whatever its cause: an I/O
  failure, the leaf gone, or the leaf replaced by a non-directory) and whose cleanup half says
  the created directory could not be identified and was not removed. Nothing is registered. If
  a directory is still at the name, the next listing registers it (P11 collection registers
  discovered children).
* The three other `create_dir_at` callers (P6) keep their current behaviour: a post-create sync
  failure is still returned to them as the same `Error::Io` it is today, through one adapter.

### O5 — Combined reporting order for the create paths

From `d-20260906-03` contract (3) *combine*, applied to the steps of one create:

* Operation order: PGN install, sidecar install, count, registration (file); directory create,
  observation, registration (directory).
* An ordinary error at any step after the first on-disk create outranks every earlier
  uncertainty and is handled by O3.
* Otherwise the **first** uncertain stage in operation order is reported, after all later steps
  completed: `WorkspacePgnCreation`, then `WorkspaceSidecarCreation`, then `RegistryReplacement`
  (file); `WorkspaceDirectoryCreation`, then `RegistryReplacement` (directory).
* With no uncertainty and no error the entry is returned.

## Decisions and trade-offs

* **Starting point.** A 2026-10-03 PLAN-ONLY run (drain session
  `b1d90b24-0cf0-4e7d-8d87-ab95faeee372`, BASE `1d0fc9ca`) converged on this design in five
  rounds; its publication was rejected by the supervisor's Defer-receipt check, not by review, and
  its plan file did not survive. This plan is that draft re-traced at `52e301ba` (all premises
  still hold, line numbers updated, P19/P20 added); it is reviewed here from round 1 with the full
  lens set and is not adopted as reviewed.
* **Compensate vs report (the finding's open question):** compensate on every *ordinary* failure
  after an on-disk create and before registration; report a *committed-uncertain* registration.
  Precedent `d-20260901-06` decided exactly this for `create_workspace_directory` and
  `create_database_child`.
* **Where the count is taken:** on the installed file before registration (O1), rather than (a)
  counting the request bytes / source snapshot before publication plus a post-install cache warm —
  two scans of a large import and a warm whose failure must be swallowed; (b) a new
  applied-despite-error variant for a post-registration count failure — the renderer would relist
  and the listing would hit the same count failure (P11); (c) a nullable count —
  `FileMetadata.numGames` is required by its consumers (P13).
* **Empty-only directory rollback** rather than today's recursive removal: a new directory's
  rollback has no business deleting anything an external program put inside it.
* **`create_dir_at` split with a behaviour-preserving adapter** rather than changing every caller's
  error: the other three callers are internal steps of larger operations whose current error is
  not a misreport of a committed user operation.

* **Q:** after an on-disk workspace create, does an ordinary later failure compensate or report?
  **Chosen:** compensate with identity-checked (directory: empty-only) removal of everything the
  call created; a committed-uncertain registration is kept and reported. **Rejected:** reporting
  every such failure as applied-despite-error (the registry is unchanged, so the relist would
  find an unregistered entry and register it behind the user's back); skipping the rollback when
  an earlier sync was uncertain (contradicts `d-20260906-03`'s combine contract, P16).
  **Reason:** `d-20260901-06` precedent; P7.
* **Q:** where is the created file's game count established? **Chosen:** on the installed file
  before registration, retained in the repository cache; a failure rolls back. **Supersedes:**
  `d-20260927-02`'s clause "a post-install count failure keeps the installed file and returns the
  error" (new evidence P11, P13; its rejection reason was the previous mandate's scope).

# Plan: workspace create never reports a committed entry as a clean failure (f-20260914-02)

## Goal

After `create_workspace_file` or `create_workspace_directory` has made an entry visible on disk,
the command either returns that entry, or returns a typed outcome that truthfully says what was
left behind: nothing (rolled back), something the rollback could not remove
(`OperationAndCleanup`), or a committed entry whose durability is uncertain
(`CommittedDurabilityUncertain`, which the renderer already recovers by relisting). Every
fallible step that follows the on-disk creation runs before registration, so its failure is
rolled back; nothing fallible runs after registration.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260914-02:

> * **Where:** `src-tauri/src/file_workspace.rs:770-795` (`create_workspace_file` core): `register_created_entry(...)?` and `timestamp(&target)?` run after the PGN and its sidecar were installed; the analogous post-create steps in `create_workspace_directory` (~`:883`).
> * **Defect:** once the file and sidecar exist on disk (and, for the timestamp step, the registry record too), a registry-persistence or metadata error is returned through `?` as a plain failure. The renderer is told creation failed while a committed file remains, with no rollback and no `applied-despite-error` result, so a retry collides with the leftover name.
> * **Why it matters:** `.claude/rules/async-resource-invariants.md` (every exit path cleaned up or reported truthfully) and `d-20260906-03` (committed-but-uncertain outcomes are reported, never presented as clean failure).
> * **Open question:** after a committed create, should a later registry/metadata failure compensate (unlink the just-created entry, which d-20260906-03 warns can delete the only committed copy) or report an applied-despite-error outcome the renderer relists on?

## Threat model and non-goals

  fails or whose parent sync fails, lock poisoning, the operation token cancelled by application
  shutdown (`RunEvent::ExitRequested` → `seal_and_request_cancellation`), malformed PGN text the
  user pasted or imported, and an external program (sync client, file manager) touching a

  Windows all count.
* **Out of scope:** a deliberate local adversary racing the identity check inside a removal on

## Approach

### O1 — The installed PGN is counted before registration

MANDATE words: "a registry-persistence or metadata error is returned through `?` as a plain
failure" once "the file and sidecar exist on disk … and … the registry record too"; P1 is that
step today.

* `create_workspace_file_blocking` counts the games of the PGN it just installed **after the
  sidecar install and before registration**, inside the existing blocking worker:
  * it reads the installed object only: through a read descriptor opened relative to the
    retained parent and verified against the installed identity (P9's `identity`), never by
    pathname; a different object at the name is a `Conflict`;
  * the snapshot it counts is built from that descriptor by the same rule as every other
    snapshot of the file (P10), so its cache key and revision equal what a later listing or open
    computes for the untouched file; the path authority still grants no snapshot without either
    a resolved capability or a descriptor whose identity the caller has proved;
  * a snapshot's revision accepts a pre-1970 modification time as a negative nanosecond count,
    on both platforms, for **every** snapshot (one implementation in `pgn_snapshot_file`, the
    revision and cache-key `mtime_nanos` become signed). Today any pre-1970 PGN is refused by
    every read (P17); without this, O1 would turn a pre-1970 installed file into a failed create
    and break the tested `d-20261003-06`/`d-20261003-07` create contract. Revision strings of
    post-1970 files are byte-identical to today's;
  * through the repository's cache-or-scan sequence for that snapshot (P10): a synchronous scan
    with the existing strict scanner (no second boundary rule, `.claude/rules/pgn-scanning.md`)
    whose index is offered to the cache under the installed file's key with the existing budget
    rule, so the follow-up listing and the first open hit the cache exactly when today's
    post-install count would have left a hit — an index larger than the cache budget is not
    retained, as today. `scan_current` and this path share one implementation of the
    lookup/scan/retain sequence (rule 11), and the repository count hook (P19) sits in that
    shared step or is reached by both callers, so a test can still pause a create's count;
  * without any new `BLOCKING_GATEWAY` acquisition (it already runs inside the core's permit;
    `d-20260903-04`), observing the operation token.
* Any count failure (`Cancellation` including shutdown, `InvalidData`, `ResourceLimit`, I/O,
  `Conflict`, a poisoned repository lock) is an ordinary failure before registration and goes to
  O3's rollback.
* The returned `WorkspaceEntry.game_count` is `Some(that count)`, set by the core.
* Ownership: the workspace mutation lock is held across the count, as it already is across the
  copy; the count reads the file the copy just wrote.
* Supersedes `d-20260927-02`'s count clause (P15): a count failure no longer keeps the installed
  file. New evidence that decision did not weigh: P11 (a kept unscannable file makes every later
  listing of the workspace fail) and P13 (no renderer flow recovers a plain count error, so the
  kept file is reported as a failed create — this finding); its own rejection reason was the
  previous mandate's scope, and this mandate is where the question belongs.

### O2 — The command adds no fallible step after the core

MANDATE words: the renderer "is told creation failed while a committed file remains".

* `create_workspace_file` returns the blocking core's result directly. The post-core
  `resolve(..., ReadPgn)` and `count_pgn_games_core` (P1) are removed; there is no step between a
  committed core result and the command's return that can turn it into an error.
* The non-nesting proofs follow the count to its new side (`d-20260903-04`, P18): the
  `create_workspace_file` row of `s9_nested_awaits_stay_on_the_async_side` is removed, because
  the count deliberately leaves the async side; the synchronous count path O1 adds (the shared
  lookup/scan/retain step and anything it calls in `pgn.rs`) is placed under
  `s8_blocking_functions_do_not_nest_the_gateway`, by name in its explicit list or by a
  `_blocking` name in a scanned file, so a later `BLOCKING_GATEWAY`/`.await` inside it fails that
  test. The `infra/blocking.rs` doc comment's example of a legal sequential acquisition, which
  names `create_workspace_file` → `count_pgn_games_core`, is rewritten to a caller for which it
  remains true (`list_file_workspace_core` → `count_pgn_games_core`).

### O3 — One rollback policy for every ordinary failure after an on-disk create

MANDATE words: "should a later registry/metadata failure compensate … or report an
applied-despite-error outcome"; decided by precedent `d-20260901-06` and `d-20260906-03`.

* **Trigger.** Every ordinary (non-`CommittedDurabilityUncertain`) error after the first on-disk
  create and before a successful registration is rolled back: for files the sidecar install
  (P4), the O1 count, and registration; for directories the observation (O4) and registration.
* **Registration outcomes.** `Ok(handle)` → continue; `Err(CommittedDurabilityUncertain(_))` →
  the authority adopted the entry (P7), keep every created object, no rollback, report under O5;
  any other error → the registry is unchanged (P7), roll back.
* **What a rollback removes.** Only objects this call created, each checked against the identity
  it was created with:
  * file: the sidecar and the PGN, each identity-checked; the sidecar is installed through the
    identity-returning atomic replacement (P9) so it has an identity to check. When the O1 count
    already offered an index to the repository cache, the rollback also invalidates the cache
    entries of the PGN's identity (the repository's existing per-identity invalidation, P10), so a
    retry whose new file reuses that identity cannot hit a stale index; an invalidation failure is
    a cleanup failure;
  * directory: the directory only if it is **still the observed identity and still empty** —
    the removal never descends, so a file an external program placed inside is never deleted
    (today's `remove_entry_at(.., true)` is recursive, P8), and a different object now at the
    name (another directory, empty or not, or a file) is never removed. This is one
    identity-checked, empty-only directory removal in `infra/fs.rs` with the same parent-sync
    outcome as `remove_entry_at`, on both platforms (P20).
  * Nothing is ever removed by name alone: when the directory's identity was never observed
    (O4), there is nothing the rollback can prove is ours, so it removes nothing and reports that
    the created directory could not be identified and was not removed (without claiming it is
    still there: it may have been removed or replaced externally).
  * Every removal is attempted even if an earlier one failed.
* **Result.** `Error::with_cleanup(primary, cleanup)` (P12): the primary error when every removal
  succeeded, `OperationAndCleanup` when any removal failed or could not be attempted (a replaced
  or non-empty leaf, a failed unlink, a removal whose parent sync was uncertain, a failed cache
  invalidation, or an unidentified directory that was not removed). The existing sidecar-failure
  rollback and directory rollback route through this one fold, so no hand-written
  `OperationAndCleanup { primary, cleanup }` fold remains in the two create paths.
* **A concurrent listing is not excluded (known limit).** Listing walks and registers
  discovered children without the workspace mutation lock (P21), so a listing that runs between
  the PGN install and the rollback can register the installed PGN under its own fresh record. The
  rollback removes the files it created and does not touch that record; the record names a
  removed object and the next listing prunes it. Until then it does not conflict with a retry at
  the same path (a different identity gets a fresh record, P21), but like the record of any file
  removed outside the app it counts toward the registry's 4,096-identifier bound (P22): a retry
  that would push a full registry past the bound is refused with `ResourceLimit` until a listing
  prunes the stale record. The same window exists today for the sidecar-failure
  and directory-registration rollbacks; O1 widens it by one scan. The listing that registered it
  fails its own count of the vanished file, which is `f-20261003-08`'s class. No new lock or
  registry-removal mechanism is part of this plan.
* **Rollback after an uncertain earlier step.** When an earlier step's parent sync was uncertain
  and a later ordinary error occurs, the rollback still runs and the later error is reported.
  This is `d-20260906-03`'s *combine* contract ("a later non-uncertainty error outranks it",
  workspace create), which was recorded with exactly this sidecar-failure rollback in place
  (P16). It is not the compensation `d-20260906-03` rejected: that one was triggered *by* the
  uncertainty, and removed the only copy of committed content; here the trigger is a failure that
  makes the create fail, and the created bytes still exist in the request (`Text`) or the
  unchanged source (`Copy`).

### O4 — Directory creation reports or rolls back every post-create step

MANDATE words: "the analogous post-create steps in `create_workspace_directory`"; `d-20260906-03`
assigns "workspace file/directory creation" to its *report* contract.

* `create_dir_at`'s create-then-sync is split so the workspace directory path learns the
  outcome: the create failing is an error (nothing created); the create succeeding and the parent
  sync failing is a `#[must_use]` committed-uncertain outcome, the same `AtomicFileOutcome` shape
  the file path already handles. Both platforms (P6) get the same split.
* `create_workspace_directory_inner` carries that uncertainty through observation and
  registration and reports it under O5 as
  `CommittedDurabilityUncertain(DurabilityStage::WorkspaceDirectoryCreation)`, a new stage
  displayed as "workspace directory creation". The renderer recovers it by refreshing, exactly as
  for the file stages (P13); no renderer change.
* An `entry_observation_at` failure after a successful create is reported, never a plain error:
  the leaf has no identity this call can prove is its own, so O3 removes nothing and returns
  `OperationAndCleanup` whose primary half is the observation error (whatever its cause: an I/O
  failure, the leaf gone, or the leaf replaced by a non-directory) and whose cleanup half says
  the created directory could not be identified and was not removed. Nothing is registered. If
  a directory is still at the name, the next listing registers it (P11 collection registers
  discovered children).
* The three other `create_dir_at` callers (P6) keep their current behaviour: a post-create sync
  failure is still returned to them as the same `Error::Io` it is today, through one adapter.

### O5 — Combined reporting order for the create paths

From `d-20260906-03` contract (3) *combine*, applied to the steps of one create:

* Operation order: PGN install, sidecar install, count, registration (file); directory create,
  observation, registration (directory).
* An ordinary error at any step after the first on-disk create outranks every earlier
  uncertainty and is handled by O3.
* Otherwise the **first** uncertain stage in operation order is reported, after all later steps
  completed: `WorkspacePgnCreation`, then `WorkspaceSidecarCreation`, then `RegistryReplacement`
  (file); `WorkspaceDirectoryCreation`, then `RegistryReplacement` (directory).
* With no uncertainty and no error the entry is returned.

## Decisions and trade-offs

* **Starting point.** A 2026-10-03 PLAN-ONLY run (drain session
  `b1d90b24-0cf0-4e7d-8d87-ab95faeee372`, BASE `1d0fc9ca`) converged on this design in five
  rounds; its publication was rejected by the supervisor's Defer-receipt check, not by review, and
  its plan file did not survive. This plan is that draft re-traced at `52e301ba` (all premises
  still hold, line numbers updated, P19/P20 added); it is reviewed here from round 1 with the full
  lens set and is not adopted as reviewed.
* **Compensate vs report (the finding's open question):** compensate on every *ordinary* failure
  after an on-disk create and before registration; report a *committed-uncertain* registration.
  Precedent `d-20260901-06` decided exactly this for `create_workspace_directory` and
  `create_database_child`.
* **Where the count is taken:** on the installed file before registration (O1), rather than (a)
  counting the request bytes / source snapshot before publication plus a post-install cache warm —
  two scans of a large import and a warm whose failure must be swallowed; (b) a new
  applied-despite-error variant for a post-registration count failure — the renderer would relist
  and the listing would hit the same count failure (P11); (c) a nullable count —
  `FileMetadata.numGames` is required by its consumers (P13).
* **Empty-only directory rollback** rather than today's recursive removal: a new directory's
  rollback has no business deleting anything an external program put inside it.
* **`create_dir_at` split with a behaviour-preserving adapter** rather than changing every caller's
  error: the other three callers are internal steps of larger operations whose current error is
  not a misreport of a committed user operation.

## Decided autonomously

`full auto` run; each entry is recorded by the adopting session through
`./scripts/findings.py record-decision`.

* **Q:** after an on-disk workspace create, does an ordinary later failure compensate or report?
  **Chosen:** compensate with identity-checked (directory: empty-only) removal of everything the
  call created; a committed-uncertain registration is kept and reported. **Rejected:** reporting
  every such failure as applied-despite-error (the registry is unchanged, so the relist would
  find an unregistered entry and register it behind the user's back); skipping the rollback when
  an earlier sync was uncertain (contradicts `d-20260906-03`'s combine contract, P16).
  **Reason:** `d-20260901-06` precedent; P7.
* **Q:** where is the created file's game count established? **Chosen:** on the installed file
  before registration, retained in the repository cache; a failure rolls back. **Supersedes:**
  `d-20260927-02`'s clause "a post-install count failure keeps the installed file and returns the
  error" (new evidence P11, P13; its rejection reason was the previous mandate's scope).
  **Rejected:** pre-publication count plus a post-install warm; a new applied-despite-error
  variant; a nullable count.
* **Q:** how is a directory whose post-create parent sync failed reported? **Chosen:** a new
  `DurabilityStage::WorkspaceDirectoryCreation` through the existing durability category.
  **Rejected:** reusing `DirectoryInstall` (it names the engine-archive install). **Reason:**
  `d-20260906-03` report contract for workspace directory creation.
* **Q:** what does a directory rollback remove? **Chosen:** the directory only, only while it is
  the observed identity and empty; an unobserved directory is never removed and is reported as
  not removed (`OperationAndCleanup`). **Rejected:** today's recursive removal (deletes files an
  external program placed inside); an empty-only removal by name after an observation failure
  (could remove a different empty directory an external program put there); creating the
  directory under a temporary name and publishing it with a no-replace rename to learn its
  identity at creation (a crash between the two leaves a hidden temporary directory in the user's
  workspace); a plain error over the left-in-place directory (the MANDATE defect).
* **Q:** how does a PGN snapshot represent a pre-1970 modification time? **Chosen:** a signed
  nanosecond count in the snapshot revision and the repository cache key, for every snapshot;

  `lastModified`); a signed variant only inside the new constructor (two revision encodings for
  one file, so the later listing's key would differ from the create's). **Reason:** one revision
  rule per file (rule 11); `d-20261003-07` already defines pre-1970 times as negative.

## Risks / open questions

* The count now holds the workspace mutation lock for one scan of the new file; other workspace
  mutations wait for it, as they already wait for the copy that wrote the file.
* The rollback removes a file the create had just written over an existing same-name entry; the
  previous bytes were already replaced at the rename. That is the create-over-existing-name
  semantics, filed separately as `f-20261003-07`.
* A listing that runs concurrently with a create that then rolls back can leave a registry
  record for the removed file until the next listing (O3 known limit); at the registry's
  identifier bound that record makes a retry fail with `ResourceLimit` until a listing prunes
  it. The same window exists for today's sidecar-failure and directory-registration rollbacks.
* An empty directory an external program substitutes at the same name between our create and our
  observation is the one the observation binds, so a later registration-failure rollback can
  remove it (no file data can be lost: the removal is empty-only).

# Plan: workspace create never reports a committed entry as a clean failure (f-20260914-02)

## Goal

After `create_workspace_file` or `create_workspace_directory` has made an entry visible on disk,
the command either returns that entry, or returns a typed outcome that truthfully says what was
left behind: nothing (rolled back), something the rollback could not remove
(`OperationAndCleanup`), or a committed entry whose durability is uncertain
(`CommittedDurabilityUncertain`, which the renderer already recovers by relisting). Every
fallible step that follows the on-disk creation runs before registration, so its failure is
rolled back; nothing fallible runs after registration.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260914-02:

> * **Where:** `src-tauri/src/file_workspace.rs:770-795` (`create_workspace_file` core): `register_created_entry(...)?` and `timestamp(&target)?` run after the PGN and its sidecar were installed; the analogous post-create steps in `create_workspace_directory` (~`:883`).
> * **Defect:** once the file and sidecar exist on disk (and, for the timestamp step, the registry record too), a registry-persistence or metadata error is returned through `?` as a plain failure. The renderer is told creation failed while a committed file remains, with no rollback and no `applied-despite-error` result, so a retry collides with the leftover name.
> * **Why it matters:** `.claude/rules/async-resource-invariants.md` (every exit path cleaned up or reported truthfully) and `d-20260906-03` (committed-but-uncertain outcomes are reported, never presented as clean failure).
> * **Open question:** after a committed create, should a later registry/metadata failure compensate (unlink the just-created entry, which d-20260906-03 warns can delete the only committed copy) or report an applied-despite-error outcome the renderer relists on?

## Threat model and non-goals

## Approach

### O1 — The installed PGN is counted before registration

MANDATE words: "a registry-persistence or metadata error is returned through `?` as a plain
failure" once "the file and sidecar exist on disk … and … the registry record too"; P1 is that
step today.

* `create_workspace_file_blocking` counts the games of the PGN it just installed **after the
  sidecar install and before registration**, inside the existing blocking worker:
  * it reads the installed object only: through a read descriptor opened relative to the
    retained parent and verified against the installed identity (P9's `identity`), never by
    pathname; a different object at the name is a `Conflict`;
  * the snapshot it counts is built from that descriptor by the same rule as every other
    snapshot of the file (P10), so its cache key and revision equal what a later listing or open
    computes for the untouched file; the path authority still grants no snapshot without either
    a resolved capability or a descriptor whose identity the caller has proved;
  * a snapshot's revision accepts a pre-1970 modification time as a negative nanosecond count,
    on both platforms, for **every** snapshot (one implementation in `pgn_snapshot_file`, the
    revision and cache-key `mtime_nanos` become signed). Today any pre-1970 PGN is refused by
    every read (P17); without this, O1 would turn a pre-1970 installed file into a failed create
    and break the tested `d-20261003-06`/`d-20261003-07` create contract. Revision strings of
    post-1970 files are byte-identical to today's;
  * through the repository's cache-or-scan sequence for that snapshot (P10): a synchronous scan
    with the existing strict scanner (no second boundary rule, `.claude/rules/pgn-scanning.md`)
    whose index is offered to the cache under the installed file's key with the existing budget
    rule, so the follow-up listing and the first open hit the cache exactly when today's
    post-install count would have left a hit — an index larger than the cache budget is not
    retained, as today. `scan_current` and this path share one implementation of the
    lookup/scan/retain sequence (rule 11), and the repository count hook (P19) sits in that
    shared step or is reached by both callers, so a test can still pause a create's count;
  * without any new `BLOCKING_GATEWAY` acquisition (it already runs inside the core's permit;
    `d-20260903-04`), observing the operation token.
* Any count failure (`Cancellation` including shutdown, `InvalidData`, `ResourceLimit`, I/O,
  `Conflict`, a poisoned repository lock) is an ordinary failure before registration and goes to
  O3's rollback.
* The returned `WorkspaceEntry.game_count` is `Some(that count)`, set by the core.
* Ownership: the workspace mutation lock is held across the count, as it already is across the
  copy; the count reads the file the copy just wrote.
* Supersedes `d-20260927-02`'s count clause (P15): a count failure no longer keeps the installed
  file. New evidence that decision did not weigh: P11 (a kept unscannable file makes every later
  listing of the workspace fail) and P13 (no renderer flow recovers a plain count error, so the
  kept file is reported as a failed create — this finding); its own rejection reason was the
  previous mandate's scope, and this mandate is where the question belongs.

### O2 — The command adds no fallible step after the core

MANDATE words: the renderer "is told creation failed while a committed file remains".

* `create_workspace_file` returns the blocking core's result directly. The post-core
  `resolve(..., ReadPgn)` and `count_pgn_games_core` (P1) are removed; there is no step between a
  committed core result and the command's return that can turn it into an error.
* The non-nesting proofs follow the count to its new side (`d-20260903-04`, P18): the
  `create_workspace_file` row of `s9_nested_awaits_stay_on_the_async_side` is removed, because

  lookup/scan/retain step and anything it calls in `pgn.rs`) is placed under

  remains true (`list_file_workspace_core` → `count_pgn_games_core`).

### O3 — One rollback policy for every ordinary failure after an on-disk create

MANDATE words: "should a later registry/metadata failure compensate … or report an
applied-despite-error outcome"; decided by precedent `d-20260901-06` and `d-20260906-03`.

* **Trigger.** Every ordinary (non-`CommittedDurabilityUncertain`) error after the first on-disk
  create and before a successful registration is rolled back: for files the sidecar install
  (P4), the O1 count, and registration; for directories the observation (O4) and registration.
* **Registration outcomes.** `Ok(handle)` → continue; `Err(CommittedDurabilityUncertain(_))` →
  the authority adopted the entry (P7), keep every created object, no rollback, report under O5;
  any other error → the registry is unchanged (P7), roll back.
* **What a rollback removes.** Only objects this call created, each checked against the identity
  it was created with:
  * file: the sidecar and the PGN, each identity-checked; the sidecar is installed through the
    identity-returning atomic replacement (P9) so it has an identity to check. When the O1 count
    already offered an index to the repository cache, the rollback also invalidates the cache
    entries of the PGN's identity (the repository's existing per-identity invalidation, P10), so a
    retry whose new file reuses that identity cannot hit a stale index; an invalidation failure is
    a cleanup failure;
  * directory: the directory only if it is **still the observed identity and still empty** —
    the removal never descends, so a file an external program placed inside is never deleted
    (today's `remove_entry_at(.., true)` is recursive, P8), and a different object now at the
    name (another directory, empty or not, or a file) is never removed. This is one
    identity-checked, empty-only directory removal in `infra/fs.rs` with the same parent-sync
    outcome as `remove_entry_at`, on both platforms (P20).
  * Nothing is ever removed by name alone: when the directory's identity was never observed
    (O4), there is nothing the rollback can prove is ours, so it removes nothing and reports that
    the created directory could not be identified and was not removed (without claiming it is
    still there: it may have been removed or replaced externally).
  * Every removal is attempted even if an earlier one failed.
* **Result.** `Error::with_cleanup(primary, cleanup)` (P12): the primary error when every removal
  succeeded, `OperationAndCleanup` when any removal failed or could not be attempted (a replaced
  or non-empty leaf, a failed unlink, a removal whose parent sync was uncertain, a failed cache
  invalidation, or an unidentified directory that was not removed). The existing sidecar-failure
  rollback and directory rollback route through this one fold, so no hand-written
  `OperationAndCleanup { primary, cleanup }` fold remains in the two create paths.
* **A concurrent listing is not excluded (known limit).** Listing walks and registers
  discovered children without the workspace mutation lock (P21), so a listing that runs between
  the PGN install and the rollback can register the installed PGN under its own fresh record. The
  rollback removes the files it created and does not touch that record; the record names a
  removed object and the next listing prunes it. Until then it does not conflict with a retry at
  the same path (a different identity gets a fresh record, P21), but like the record of any file
  removed outside the app it counts toward the registry's 4,096-identifier bound (P22): a retry
  that would push a full registry past the bound is refused with `ResourceLimit` until a listing
  prunes the stale record. The same window exists today for the sidecar-failure
  and directory-registration rollbacks; O1 widens it by one scan. The listing that registered it
  fails its own count of the vanished file, which is `f-20261003-08`'s class. No new lock or
  registry-removal mechanism is part of this plan.
* **Rollback after an uncertain earlier step.** When an earlier step's parent sync was uncertain
  and a later ordinary error occurs, the rollback still runs and the later error is reported.
  This is `d-20260906-03`'s *combine* contract ("a later non-uncertainty error outranks it",
  workspace create), which was recorded with exactly this sidecar-failure rollback in place
  (P16). It is not the compensation `d-20260906-03` rejected: that one was triggered *by* the
  uncertainty, and removed the only copy of committed content; here the trigger is a failure that
  makes the create fail, and the created bytes still exist in the request (`Text`) or the
  unchanged source (`Copy`).

### O4 — Directory creation reports or rolls back every post-create step

MANDATE words: "the analogous post-create steps in `create_workspace_directory`"; `d-20260906-03`
assigns "workspace file/directory creation" to its *report* contract.

* `create_dir_at`'s create-then-sync is split so the workspace directory path learns the
  outcome: the create failing is an error (nothing created); the create succeeding and the parent
  sync failing is a `#[must_use]` committed-uncertain outcome, the same `AtomicFileOutcome` shape
  the file path already handles. Both platforms (P6) get the same split.
* `create_workspace_directory_inner` carries that uncertainty through observation and
  registration and reports it under O5 as
  `CommittedDurabilityUncertain(DurabilityStage::WorkspaceDirectoryCreation)`, a new stage
  displayed as "workspace directory creation". The renderer recovers it by refreshing, exactly as
  for the file stages (P13); no renderer change.
* An `entry_observation_at` failure after a successful create is reported, never a plain error:
  the leaf has no identity this call can prove is its own, so O3 removes nothing and returns
  `OperationAndCleanup` whose primary half is the observation error (whatever its cause: an I/O
  failure, the leaf gone, or the leaf replaced by a non-directory) and whose cleanup half says
  the created directory could not be identified and was not removed. Nothing is registered. If
  a directory is still at the name, the next listing registers it (P11 collection registers
  discovered children).
* The three other `create_dir_at` callers (P6) keep their current behaviour: a post-create sync
  failure is still returned to them as the same `Error::Io` it is today, through one adapter.

### O5 — Combined reporting order for the create paths

From `d-20260906-03` contract (3) *combine*, applied to the steps of one create:

* Operation order: PGN install, sidecar install, count, registration (file); directory create,
  observation, registration (directory).
* An ordinary error at any step after the first on-disk create outranks every earlier
  uncertainty and is handled by O3.
* Otherwise the **first** uncertain stage in operation order is reported, after all later steps

## Decisions and trade-offs

* **Starting point.** A 2026-10-03 PLAN-ONLY run (drain session
  `b1d90b24-0cf0-4e7d-8d87-ab95faeee372`, BASE `1d0fc9ca`) converged on this design in five
  rounds; its publication was rejected by the supervisor's Defer-receipt check, not by review, and
  its plan file did not survive. This plan is that draft re-traced at `52e301ba` (all premises
  still hold, line numbers updated, P19/P20 added); it is reviewed here from round 1 with the full
  lens set and is not adopted as reviewed.
* **Compensate vs report (the finding's open question):** compensate on every *ordinary* failure
  after an on-disk create and before registration; report a *committed-uncertain* registration.
  Precedent `d-20260901-06` decided exactly this for `create_workspace_directory` and
  `create_database_child`.
* **Where the count is taken:** on the installed file before registration (O1), rather than (a)
  counting the request bytes / source snapshot before publication plus a post-install cache warm —
  two scans of a large import and a warm whose failure must be swallowed; (b) a new
  applied-despite-error variant for a post-registration count failure — the renderer would relist
  and the listing would hit the same count failure (P11); (c) a nullable count —
  `FileMetadata.numGames` is required by its consumers (P13).
* **Empty-only directory rollback** rather than today's recursive removal: a new directory's
  rollback has no business deleting anything an external program put inside it.
* **`create_dir_at` split with a behaviour-preserving adapter** rather than changing every caller's
  error: the other three callers are internal steps of larger operations whose current error is
  not a misreport of a committed user operation.

## Decided autonomously

`full auto` run; each entry is recorded by the adopting session through
`./scripts/findings.py record-decision`.

* **Q:** after an on-disk workspace create, does an ordinary later failure compensate or report?
  **Chosen:** compensate with identity-checked (directory: empty-only) removal of everything the
  call created; a committed-uncertain registration is kept and reported. **Rejected:** reporting
  every such failure as applied-despite-error (the registry is unchanged, so the relist would
  find an unregistered entry and register it behind the user's back); skipping the rollback when
  an earlier sync was uncertain (contradicts `d-20260906-03`'s combine contract, P16).
  **Reason:** `d-20260901-06` precedent; P7.
* **Q:** where is the created file's game count established? **Chosen:** on the installed file
  before registration, retained in the repository cache; a failure rolls back. **Supersedes:**
  `d-20260927-02`'s clause "a post-install count failure keeps the installed file and returns the
  error" (new evidence P11, P13; its rejection reason was the previous mandate's scope).
  **Rejected:** pre-publication count plus a post-install warm; a new applied-despite-error
  variant; a nullable count.
* **Q:** how is a directory whose post-create parent sync failed reported? **Chosen:** a new
  `DurabilityStage::WorkspaceDirectoryCreation` through the existing durability category.
  **Rejected:** reusing `DirectoryInstall` (it names the engine-archive install). **Reason:**
  `d-20260906-03` report contract for workspace directory creation.
* **Q:** what does a directory rollback remove? **Chosen:** the directory only, only while it is
  the observed identity and empty; an unobserved directory is never removed and is reported as
  not removed (`OperationAndCleanup`). **Rejected:** today's recursive removal (deletes files an
  external program placed inside); an empty-only removal by name after an observation failure
  (could remove a different empty directory an external program put there); creating the
  directory under a temporary name and publishing it with a no-replace rename to learn its
  identity at creation (a crash between the two leaves a hidden temporary directory in the user's
  workspace); a plain error over the left-in-place directory (the MANDATE defect).
* **Q:** how does a PGN snapshot represent a pre-1970 modification time? **Chosen:** a signed
  nanosecond count in the snapshot revision and the repository cache key, for every snapshot;
  post-1970 revision strings unchanged. **Rejected:** keeping the refusal (O1 would make a
  pre-1970 create fail, contradicting `d-20261003-06`/`d-20261003-07`'s tested negative
  `lastModified`); a signed variant only inside the new constructor (two revision encodings for
  one file, so the later listing's key would differ from the create's). **Reason:** one revision
  rule per file (rule 11); `d-20261003-07` already defines pre-1970 times as negative.

## Risks / open questions

* The count now holds the workspace mutation lock for one scan of the new file; other workspace
  mutations wait for it, as they already wait for the copy that wrote the file.
* The rollback removes a file the create had just written over an existing same-name entry; the
  previous bytes were already replaced at the rename. That is the create-over-existing-name
  semantics, filed separately as `f-20261003-07`.
* A listing that runs concurrently with a create that then rolls back can leave a registry
  record for the removed file until the next listing (O3 known limit); at the registry's
  identifier bound that record makes a retry fail with `ResourceLimit` until a listing prunes
  it. The same window exists for today's sidecar-failure and directory-registration rollbacks.
* An empty directory an external program substitutes at the same name between our create and our
  observation is the one the observation binds, so a later registration-failure rollback can
  remove it (no file data can be lost: the removal is empty-only).
