# Plan: Present database admission conflicts as a temporary other-name use

## Goal

When ChessFable refuses to open a second name of a database that is already open, the library shows that the file is in use under another name and can be opened after that use ends. It does not tell the user to check the file for corruption. Other per-database load failures keep the guidance they have today.

## MANDATE

Verbatim from `f-20261009-03` (status open, area frontend-ui, root `-`, entry build, blocked none). Pickup against the current tree: the defect still holds. No member of this slice has ceased to hold. Tier stays `build` after revalidation: the presentation contract crosses the native error payload, the renderer error facade, localized copy, and the library panel. `d-20261018-02` and `d-20260904-06` narrow the discriminator, and they do not turn the change into one already-decided edit mirrored into tests.

* **Defect:** `getDatabase` catches a typed native `Conflict`, normalizes it through `safeFailureContext`, and turns it into the generic database load title. `normalizeError` preserves the backend category, but `safeFailureContext` retains only the broad renderer category and redacted message. The selected failed database panel always adds the instruction to check that the file exists and is not corrupted. A deliberate binding admission refusal therefore loses its actionable distinction and reads as a broken database. This already affects cross-parent binding conflicts and would also affect the concurrent same-parent alias refusal planned for f-20260929-05.
* **Why it matters:** a user cannot distinguish a temporarily owned database alias from corrupt data or understand when retrying can work. Native safe refusal does not need corruption repair.
* **Open question:** which safe typed discriminator and localized recovery presentation should distinguish database admission conflicts from other per-database load failures, without matching backend message literals or exposing raw native errors? Keep ordinary corruption guidance for failures where it is appropriate.
* **Inherited review history (2026-10-11):** since f-20260929-05 (commit f1c56ef5) the native side returns a second admission conflict, `Conflict("database is open through another name")`, beside the existing `"database is open through another directory"`; both reach this per-database load panel as the generic corruption guidance.

The same-parent refusal now exists (`d-20261011-01`). This plan does not change that admission policy.

## Threat model and non-goals

The input is a native `ErrorPayload` produced by this process. The failure mode is misclassification: an admission refusal shown as corruption, or a different conflict, permission failure, missing file, unfinished import, or path-bearing diagnostic shown as an admission refusal. Message text is not a classifier. A payload may repeat an admission sentence, contain a path, or set lookalike fields (`databaseAdmission` other than exact `true`, `nameTaken`, `rootFailure`).

The renderer already receives the backend Display string. This change adds one boolean and does not add a new diagnostic channel, a path, or a raw cause. Logs stay on the existing redacted `safeFailureContext`.

Out of scope, and not a reason to change them:

- Who may hold a database binding (`d-20261011-01`), including cross-parent versus same-parent refusal, Windows case variants, and release on the last token.
- Cross-kind capability conflicts (`d-20261012-02`). Their messages stay ordinary conflicts and do not set the new flag.
- Unread listing categories, the database route's success-only resolution, collection-unavailable copy, and permission, missing, and generic load copy.
- A new retry control, a new `AppErrorCategory`, a new `Error` variant, or a new `ErrorCategory`.
- `f-20261010-01` and any session-storage writer.
- PGN scanning, engine protocol, and chess-tree state.

## Approach

### Native admission flag

Own the two admission sentences as constants beside the existing workspace-file constant. `BoundDatabase::acquire` returns those constants and does not change the admission predicate. `renderer_payload` sets optional `databaseAdmission` to `true` only when the unlabelled error is `Conflict` and its string is exactly one of those two constants. Every other conflict omits the field, including name-taken, poisoned registry, cross-kind inode refusals, and a string that merely contains an admission sentence. `nameTaken` and `databaseAdmission` are never both set. Serialization stays `skip_serializing_if` none, matching `nameTaken`. No new error variant, category, or event.

### Renderer preserves the flag and classifies only on it

`normalizeError` copies `databaseAdmission` only when the payload value is exactly `true`. Any other value omits the property. `safeFailureContext` stays category, redacted message, and optional engine snapshot. `getDatabase` classifies from `normalizeError` and still logs through `safeFailureContext`. Cancellation still rethrows before an error card. When the flag is exact `true`, the error entry's `error` string is the localized admission sentence and the entry carries `databaseAdmission: true`. The unfinished-import sentence, permission, missing, and generic title stay as they are when the flag is absent, including when the message text equals an admission sentence. The result never contains the backend message or a filesystem path.

### Library presentation

For a selected error entry with `databaseAdmission: true`, the detail shows the admission sentence as its title and the recovery sentence as its body. It does not show the generic load title, the `Reason:` line, or `Databases.LoadError.Description`. Every other selected error entry keeps today's title, reason line, and corruption description. The card and the account alert keep printing `error`, so they show the admission sentence without a separate corruption instruction. No new button. The database route's success-only resolution stays as it is.

### Localization

Add `Databases.LoadError.Admission` and `Databases.LoadError.AdmissionRecovery` through `t()` calls. English source:

- Admission: `This database is already open under another name`
- Recovery: `It can be opened again after that use ends.`

`en-GB` uses the same two sentences. Every other shipped catalogue gets a translation of those two sentences in that catalogue's language. Run `pnpm i18n:extract`, then `pnpm i18n:check`. Do not construct key names dynamically.

The corruption description is not an e2e scenario today; the library component test is the visible-state proof.

Chosen: optional `ErrorPayload.databaseAdmission`, omitted unless the conflict string is exactly one of the two owned admission constants, in which case serialization sends `true`. The renderer copies the flag only for exact `true` and selects the admission copy only from that flag.

When ChessFable refuses to open a second name of a database that is already open, the library shows that the file is in use under another name and can be opened after that use ends.
