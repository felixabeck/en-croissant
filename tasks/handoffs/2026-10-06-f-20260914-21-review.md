### plan-r1.md

# Plan: a failed engine-image cleanup is surfaced and retried, never only logged

## Goal

When `issue_engine_image` has installed a UUID image leaf and a later step fails, and removing
that leaf also fails, the leaf must not become an orphan nothing ever revisits, and the caller
must not receive an error that pretends the cleanup succeeded. After this change the removal
failure is part of the returned error, and — wherever the path authority is available — a
persisted cleanup intent makes the existing startup and shutdown cleanup retry the removal.

## MANDATE

Verbatim, `f-20260914-21` (the only member of this slice):

> ### A failed engine-image cleanup is logged but omitted from the returned error, orphaning the image file
>
> * **Where:** src-tauri/src/main.rs:1459-1462
> * **Defect:** When registering an engine image fails and the cleanup of the written image file also fails, only the primary error is returned and the cleanup failure is logged. The unregistered image stays on disk, and startup cleanup cannot recover it because it only tracks persisted cleanup records.
> * **Why it matters:** Unbounded orphaned files the user cannot see or remove; `.claude/rules/async-resource-invariants.md`.
> * **Open question:** Should the cleanup failure be persisted as a startup cleanup record, surfaced to the caller alongside the primary error, or both?

## Threat model and non-goals

* **Accidental failure only.** The removal fails because of an operating-system error (permission
  change, I/O error, a transiently busy file on Windows, a substituted directory entry). No
  adversary is modelled beyond what the existing identity-checked removal already handles
  (`f-20260830-09` owns the unlink-by-name residue and is cited, not re-derived).
* **One process.** The application has no single-instance guard (`f-20260922-07`); this plan,
  like every other path-authority mutation, assumes one process owns the registry.
* Environments: Linux, macOS, Windows release builds; the removal-fault tests run where the
  existing fault injector runs (`#[cfg(unix)]`).

## Traced premises

Frozen at BASE `101c0d87`; obligations below do not repeat these line numbers.

* P2 — It is reached from three branches after `atomic_replace_leaf_identified` commits the leaf

## Approach

### O1 — The removal failure is part of the returned error

MANDATE: "only the primary error is returned and the cleanup failure is logged"; "surfaced to the
caller alongside the primary error".

* When removing the installed leaf fails (any error other than a missing entry, which is success),
  every one of the three post-install error branches returns `Error::with_cleanup(original, …)`,
  i.e. `Error::OperationAndCleanup` whose `primary` is the original error's diagnostic and whose
  `cleanup` diagnostic names the removal failure **and** the O2 intent outcome (recorded,
  recorded but not durable, or not recorded with its reason, or "no authority available" for the
  poisoned and uninitialized branches).
* When the removal succeeds or the leaf is already absent, the original error is returned
  unchanged (today's behaviour; `engine_image_post_install_error_removes_the_orphan` stays).
* The full diagnostic is still written with `log::error!` on the native log only: the wire form
  omits diagnostics (P7) and the boundary does not log them, so the log line remains the only
  place the operator sees the cause. No path or raw OS text reaches the renderer (P7, `d-20260905-10`).
* Renderer impact: the toast is unchanged (P8); only the serialized category changes from the
  primary's category to `operation-and-cleanup` in this double-failure case. No renderer change.

### O2 — A failed removal leaves a persisted cleanup intent the existing cleanup retries

MANDATE: "startup cleanup cannot recover it because it only tracks persisted cleanup records";
"persisted as a startup cleanup record".

* A new `PathAuthority` method (name chosen by the executor) records a cleanup intent for one
  installed, unregistered engine-image leaf: it takes the caller-proven EngineImages
  `AuthorizedDir`, the leaf and the installed `VerifiedIdentity`, and inserts one
  `image_cleanup` record shaped exactly as P5 requires — a fresh UUID id that is not a persistent
  or retired entry, class `PersistentFile`, purpose `EngineImage`, canonical operations, the
  `dir.path().join(leaf)` native path, the installed identity, the directory identity as parent
  identity — then persists the registry through the existing save path.
* It refuses a leaf that is not a single UUID component (the only leaves `cleanup_engine_images`
  will ever act on, P3), so it can never schedule something cleanup would silently drop.
* It is permitted while engine attachments are **sealed**: the registration error during shutdown
  is exactly the case P4's drain waits for, and shutdown cleanup then retries the removal.
* Admission: the record goes through the same registry growth bound as every other record (P6).
  A refusal is reported as "not recorded" in the O1 cleanup diagnostic; the bound is not
  bypassed. (The capacity race that can refuse both registration and intent is `f-20261004-13`,
  not this plan.)
* Persistence outcome: `Durable` → recorded. `DurabilityUncertain` → the record is kept (the
  write committed) and `registry_durability_pending` is set as the other writers do. A save
  `Err` → the in-memory record is **kept**, so this process's shutdown cleanup still retries the
  removal and the next successful registry save persists it; the O1 diagnostic says the intent
  is not yet durable. Rationale under Decisions D3.
* Only the registration-failure branch can record (P2). The poisoned and uninitialized branches
  have no authority; they return the O1 error and remain a named known limit.
* The existing `cleanup_engine_images` is not changed: a recorded intent is indistinguishable from
  a retired-image intent and is removed by it on success, missing entry, or substituted leaf, and
  kept on any other failure (P3). Its startup and shutdown call sites are unchanged (P4).
* Registry load must accept such a record unchanged (P5); no schema change, no new field.

### O3 — Verification

MANDATE: "The unregistered image stays on disk, and startup cleanup cannot recover it".

Behavioural Rust tests, run by `cargo test` (the backend coverage ratchet measures the new lines):

1. Registration failure + removal failure, with an authority: the returned error is
   `OperationAndCleanup` whose `primary` contains the original diagnostic; the leaf is still on
   disk; a **fresh authority loaded from the persisted registry** holds the intent; with the fault
   removed, `cleanup_engine_images` on that reopened authority removes the leaf and the intent,
   and a further reload shows no intent. (This is the MANDATE's failure, reverted: without O2 the
   reopened authority has nothing to clean and the leaf survives.)
2. The same with the authority **sealed** (shutdown path): the intent is still recorded, and an
   in-process `cleanup_engine_images` removes the leaf.
3. Intent persistence failure (injected through the registry `replace` closure that
   `save_entries_with` already takes and that existing registry-fault tests in `mod.rs` use;
   the new method's save is routed so a test can supply that closure): the error still names
   both failures, the in-memory intent is
   kept, and an in-process `cleanup_engine_images` with the faults removed removes the leaf and
   persists the cleared set.
4. Admission refusal: an authority at the id bound refuses the intent; the error names
   "not recorded"; the leaf remains (documented limit, `f-20261004-13`).
5. A non-UUID or multi-component leaf is refused by the new method without touching the registry.
6. No-authority branches (poisoned / uninitialized) with a removal failure return
   `OperationAndCleanup`; no registry write occurs.
7. Removal success keeps returning the original error unchanged (existing test kept).
8. Wire form: serializing the composed error exposes neither the leaf name nor the app-data path
   (extends the existing `operation_and_cleanup_serialization_omits_both_diagnostics` property to
   this producer).

The source-scan pin `engine_image_install_and_post_install_cleanup_are_pinned_to_the_descriptor`
is updated to the new contract (three branches still route through the helper; the helper still
removes through `remove_leaf_identified`, logs natively, and composes with `Error::with_cleanup`),
not deleted. `engine_image_orphan_removal_failure_preserves_the_original_error` is replaced by
test 1/6, because its assertion is exactly the behaviour this MANDATE removes.

## Decisions and trade-offs

* **D1 — Both, not either (answers the finding's open question).** Surfacing alone leaves the
  orphan forever; persisting alone leaves the caller with an error that says the operation's
  side effects were cleaned up when they were not, and the async-resource rule requires an error
  path that does not swallow a failure. Each closes a different half of the MANDATE.
* **D2 — Supersedes the "logged" clause of `d-20260905-09`.** New evidence that decision did not
  consider: the logged-only orphan is unreachable by every later cleanup (P3), which is this
  finding. The rest of `d-20260905-09` stands — cleanup bound to `Err` alone, identity-checked
  removal, at most one leaf per failed install, the original error is never masked (it is the
  `primary` of the composed error and still decides the log line's first half).
* **D3 — On a failed intent save the in-memory intent is kept, not rolled back.** Rolling back
  (the reconcile path's convention) would drop the only in-process route to the leaf; keeping it
  lets shutdown cleanup retry and lets the next successful save persist it. Keeping an
  unpersisted cleanup record is safe because a cleanup record never resolves as authority (P5)
  and cleanup acts only on identity agreement (P3).
* **D4 — Remove first, record only on failure** (rejected: write the intent before the unlink).
  Recording first costs two registry saves on every failed registration and still does not cover
  the crash window before registration, which is `f-20261004-12`'s mechanism question.
* **D5 — Category on the wire becomes `operation-and-cleanup` in the double-failure case.** The
  renderer does not branch on it (P8); the fixed message is accurate.

## Risks / open questions

* The registration failure most likely to coincide with a failed removal is a registry write
  failure, in which case the intent save fails too (handled by D3 and test 3) — the leaf is then
  retried only in-process until a later save succeeds.
* Poisoned / uninitialized authority branches cannot record an intent (named limit; a poisoned
  authority refuses every path operation today).

## Not part of this task

* `f-20261004-12` — crash between install and registration (needs the single-instance guard
  `f-20260922-07` or a write-ahead intent).
* `f-20261004-13` — capacity reservation so registration and intent cannot both be refused.
* `f-20260830-09` — unlink-by-name residue.
* Any change to `cleanup_engine_images`, to the issuance lease, to the renderer, or to the
  generated bindings (no command signature or exported type changes).

## Phases

  `src-tauri/src/main.rs` (`engine_image_error_after_cleanup`, its three call sites, the two

## Approach

### O1 — The removal failure is part of the returned error

MANDATE: "only the primary error is returned and the cleanup failure is logged"; "surfaced to the
caller alongside the primary error".

* Removal outcome classification (P10): `Ok` → removed. `Err` with `Error::is_missing_entry` →
  removed (already absent). `Err(CommittedDurabilityUncertain(_))` → removed (the unlink happened;
  only the parent sync is uncertain, as `d-20260830-04` / `d-20260906-03` treat a committed step):
  logged as a warning, no intent, original error returned. Any other `Err` → **removal failed**.
* On **removal failed**, every one of the three post-install error branches returns
  `Error::with_cleanup(original, Err(cleanup))`, i.e. `Error::OperationAndCleanup` whose `primary`
  is the original error's diagnostic and whose `cleanup` diagnostic names the removal failure
  **and** the intent outcome, exactly one of:
  * `recorded` — the O2 intent is persisted durably;
  * `recorded, durability uncertain` — the registry write committed, its parent sync did not (P13);
  * `not recorded, retained in memory: <reason>` — the registry write failed; the intent lives in
    this process only and is retried by O2's persistence retry;
  * `not recorded: <reason>` — refused before insertion (admission bound, invalid leaf);
  * `not recorded: no path authority` — the poisoned and uninitialized branches (P2).
* On **removed**, the original error is returned unchanged (today's behaviour;
  `engine_image_post_install_error_removes_the_orphan` stays).
* The composed error's full `diagnostic()` (both halves, not its fixed `Display`) is written with
  `log::error!` on the native log only: the wire form omits diagnostics (P7) and the command
  boundary does not log them, so that log line is the only place the operator sees the cause.
  No path or raw OS text reaches the renderer (P7, `d-20260905-10`).
* Renderer impact (P8): no code change in either consumer. In the double-failure case the toast
  text becomes the fixed message "Operation failed; temporary cleanup also failed" instead of the
  primary error's text, and the category becomes `operation-and-cleanup` (mapped to `unexpected`).

### O2 — A failed removal leaves a persisted cleanup intent the existing cleanup retries

MANDATE: "startup cleanup cannot recover it because it only tracks persisted cleanup records";
"persisted as a startup cleanup record".

* **Producer.** A new `PathAuthority` method (name chosen by the executor) records a cleanup
  intent for one installed, unregistered engine-image leaf. Inputs: the caller-proven EngineImages
  `AuthorizedDir`, the leaf, the installed `VerifiedIdentity`. It inserts one `image_cleanup`
  record shaped exactly as P5 and P12 require: a fresh UUID id that is neither a persistent nor a
  retired entry nor an existing cleanup id; class `PersistentFile`; `target_is_dir: false`;
  purpose `EngineImage`; canonical `EngineImage` operations; a fixed non-empty `display_name`
  (a named constant, e.g. "Unregistered engine image"); native path `dir.path().join(leaf)`; the
  installed identity; the directory identity as `parent_identity`.
* **Leaf check.** It refuses, without touching any state, a leaf that is not a single UUID
  component — the only leaves `cleanup_engine_images` acts on (P3).
* **Sealing.** It is permitted while engine attachments are sealed: the registration error during
  shutdown is exactly the case P4's drain waits for.
* **Admission (P6, P11).** The admission snapshot is taken **before** the insert and passed as the
  save's baseline, so the growth bound applies to the new record exactly as to every other one. An
  admission refusal (or any other error before the registry write starts) restores
  `image_cleanup` to its pre-insert state and yields `not recorded: <reason>`. The bound is never
  bypassed. (The race that fills the bound during the copy is `f-20261004-13`.)
* **Persistence outcome.**
  * `Durable` → `recorded`; `registry_durability_pending` cleared as every durable save does.
  * `DurabilityUncertain` → `recorded, durability uncertain`; the record is kept and
    `registry_durability_pending` is set (P13).
  * Registry write `Err` → the record is **kept in memory** and `registry_durability_pending` is
    set, meaning "the in-memory registry is ahead of disk; re-save it" (P13); outcome
    `not recorded, retained in memory: <reason>`. Rationale: Decisions D3.
* **Persistence retry (the one change to `cleanup_engine_images`).** Today the pass re-saves a
  pending registry only when `image_cleanup` is empty (P13). It is generalised: when the pass
  wrote nothing (the set is unchanged) and `registry_durability_pending` is set, it calls the
  existing `retry_registry_durability`, and combines that result with the first removal failure
  exactly as its existing durability-uncertain branch combines them. So a retained intent whose
  removal still fails at shutdown is persisted by the shutdown pass, and startup finds it. Any
  other successful registry save in the session persists it as well (saves serialise
  `self.image_cleanup`, P11). Nothing else in `cleanup_engine_images` changes: a recorded intent is
  indistinguishable from a retired-image intent and is removed on success, missing entry or
  substituted leaf, and kept on any other failure (P3). Its startup and shutdown call sites are
  unchanged (P4).
* Only the registration-failure branch can record (P2). The poisoned and uninitialized branches
  return the O1 error with `not recorded: no path authority` — a named known limit.
* Registry load accepts such a record unchanged (P5, P12); no schema change, no new field.

### O3 — Verification

MANDATE: "The unregistered image stays on disk, and startup cleanup cannot recover it".

Behavioural Rust tests run by `cargo test`; the backend coverage ratchet measures the new lines.
Placement follows P14: everything that needs no removal fault lives in a module compiled on every
target (`portable_tests`, or `main.rs` tests without a unix-only import); tests that use the
removal injector are `#[cfg(unix)]` together with every helper and import they use, so the
Windows test binary neither fails to resolve them nor carries dead code under `-D warnings`.

Portable (every target):

1. **Persist and reload (MANDATE revert proof, injector-free).** Record an intent for a real
   installed UUID leaf through the new method; drop the authority; open a fresh authority from
   the persisted registry; re-acquire the EngineImages directory through `AppDataDir` +
   `ensure_app_owned_default_dir` on the canonical app-data spelling (not a raw tempdir path, which
   differs on Windows, P14); run `cleanup_engine_images`: the leaf is gone, and a further reload
   holds no intent. Without O2 the reopened authority has nothing to clean and the leaf survives.
2. **Sealed.** The same producer call on a sealed authority records the intent.
3. **Write failure.** With the registry replacement failing (injected through the `replace`
   closure that `save_entries_with` / `save_entries_with_baseline` already take, as the existing
   registry-fault tests do), the outcome is `not recorded, retained in memory`, the in-memory
   intent is kept and `registry_durability_pending` is set; then, with the replacement working
   and the leaf still present, a `cleanup_engine_images` pass removes the leaf and persists the
   cleared set. (The sub-case where the pass's removal still fails is test 12, unix-only.)
4. **Durability uncertain.** With the replacement reporting an uncertain parent sync, the outcome
   is `recorded, durability uncertain`, the record is kept and persisted, and
   `registry_durability_pending` is set.
5. **Admission refusal.** An authority at the id bound refuses: outcome `not recorded`, in-memory
   `image_cleanup` unchanged, registry file unchanged, leaf still on disk (known limit
   `f-20261004-13`).
6. **Invalid leaf.** A non-UUID or multi-component leaf is refused with no state change.
7. **Wire form.** Serialising the composed error exposes neither the leaf name nor the app-data path.

Unix (removal injector):

8. **End to end through the helper.** Registration failure + removal failure with an authority:
   the returned error is `OperationAndCleanup`, `primary` contains the original diagnostic, the
   cleanup diagnostic names the removal failure and `recorded`; the leaf is on disk; then the
   test-1 reload + cleanup removes it.
9. **No authority.** The poisoned/uninitialized path with a removal failure returns
   `OperationAndCleanup` whose cleanup diagnostic names `no path authority`; no registry write.
10. **Removed after unlink.** A `ParentSync` removal fault (unlink done, sync uncertain) returns
    the original error unchanged and records no intent.
11. **Removal success** keeps returning the original error unchanged (existing test kept).
12. **Persistence retry at shutdown.** After a test-3-style write failure, a `cleanup_engine_images`
    pass whose removal still fails (injector) writes the retained intent through the generalised
    retry, clears `registry_durability_pending`, and a reload holds the intent.

The source-scan pin `engine_image_install_and_post_install_cleanup_are_pinned_to_the_descriptor`
is updated to the new contract (three branches still route through the helper; the helper removes

`Error::with_cleanup`), not deleted. `engine_image_orphan_removal_failure_preserves_the_original_error`
is replaced by test 8, because its assertion is exactly the behaviour this MANDATE removes.

## Decisions and trade-offs

* **D1 — Both, not either (answers the finding's open question).** Surfacing alone leaves the
  orphan forever; persisting alone leaves the caller with an error that says the operation's side
  effects were cleaned up when they were not, and the async-resource rule requires an error path
  that does not swallow a failure. Each closes a different half of the MANDATE.
* **D2 — Supersedes the "logged" clause of `d-20260905-09`.** New evidence that decision did not
  consider: the logged-only orphan is unreachable by every later cleanup (P3), which is this
  finding. The rest of `d-20260905-09` stands — cleanup bound to `Err` alone, identity-checked
  removal, at most one leaf per failed install, the original error is never masked (it is the
  `primary` of the composed error).
* **D3 — On a failed intent write the in-memory intent is kept and the registry marked pending,
  not rolled back.** Rolling back (the reconcile path's convention) would drop the only route to
  the leaf when the likeliest companion failure — a registry write failure — occurs. Keeping it
  lets shutdown cleanup retry the removal and lets the generalised retry (O2) or any later save
  persist it. A cleanup record never resolves as authority (P5) and cleanup acts only on identity
  agreement (P3), so an unpersisted record cannot widen access. Admission refusals are rolled back
  (they are not write failures, and keeping them would bypass the bound, P11).
* **D4 — Remove first, record only on failure** (rejected: write the intent before the unlink).
  Recording first costs two registry saves on every failed registration and still does not cover
  the crash window before registration, which is `f-20261004-12`'s mechanism question.
* **D5 — Category and toast text change in the double-failure case only.** Both renderer
  consumers pass the rejection to `runUnlessCancelled` and do not branch on it (P8); the fixed
  message is accurate.
* **D6 — A post-unlink sync failure counts as removed.** The entry is gone; recording an intent
  for it would only be dropped as missing at startup, and reporting "cleanup also failed" would be
  false (P10).

## Risks / open questions

* If the registry stays unwritable for the whole session and the removal keeps failing, the
  retained intent is lost at process exit — the registry cannot hold anything then, and the
  composed error and log line say so.
* Poisoned / uninitialized authority branches cannot record an intent (named limit; a poisoned
  authority refuses every path operation today).

### plan-r3.md

# Plan: a failed engine-image cleanup is surfaced and retried, never only logged

## Goal

When `issue_engine_image` has installed a UUID image leaf and a later step fails, and removing
that leaf also fails, the leaf must not become an orphan nothing ever revisits, and the caller
must not receive an error that pretends the cleanup succeeded. After this change the removal
failure is part of the returned error, and — wherever the path authority is available — a
persisted cleanup intent makes the existing startup and shutdown cleanup retry the removal.

## MANDATE

Verbatim, `f-20260914-21` (the only member of this slice):

> ### A failed engine-image cleanup is logged but omitted from the returned error, orphaning the image file
>
> * **Where:** src-tauri/src/main.rs:1459-1462
> * **Defect:** When registering an engine image fails and the cleanup of the written image file also fails, only the primary error is returned and the cleanup failure is logged. The unregistered image stays on disk, and startup cleanup cannot recover it because it only tracks persisted cleanup records.
> * **Why it matters:** Unbounded orphaned files the user cannot see or remove; `.claude/rules/async-resource-invariants.md`.
> * **Open question:** Should the cleanup failure be persisted as a startup cleanup record, surfaced to the caller alongside the primary error, or both?

## Threat model and non-goals

* **Accidental failure only.** The removal fails because of an operating-system error (permission
  change, I/O error, a transiently busy file on Windows, a substituted directory entry). No
  adversary is modelled beyond what the existing identity-checked removal already handles
  (`f-20260830-09` owns the unlink-by-name residue and is cited, not re-derived).
* **One process.** The application has no single-instance guard (`f-20260922-07`); this plan,
  like every other path-authority mutation, assumes one process owns the registry.
* Environments: Linux, macOS, Windows release builds; the removal-fault tests run where the
  existing fault injector runs (`#[cfg(unix)]`).

  returns `original` unchanged.

## Approach

### O1 — The removal failure is part of the returned error

MANDATE: "only the primary error is returned and the cleanup failure is logged"; "surfaced to the
caller alongside the primary error".

* Removal outcome classification (P10): `Ok` → removed. `Err` with `Error::is_missing_entry` →
  removed (already absent). `Err(CommittedDurabilityUncertain(_))` → removed (the unlink happened;
  only the parent sync is uncertain, as `d-20260830-04` / `d-20260906-03` treat a committed step):
  logged as a warning, no intent, original error returned. Any other `Err` → **removal failed**.
* On **removal failed**, every one of the three post-install error branches returns
  `Error::with_cleanup(original, Err(cleanup))`, i.e. `Error::OperationAndCleanup` whose `primary`
  is the original error's diagnostic and whose `cleanup` diagnostic names the removal failure
  **and** the intent outcome, exactly one of:
  * `recorded` — the O2 intent is persisted durably;
  * `recorded, durability uncertain` — the registry write committed, its parent sync did not (P13);
  * `not recorded, retained in memory: <reason>` — the registry write failed; the intent lives in
    this process only and is retried by O2's persistence retry;
  * `not recorded: <reason>` — refused before insertion (admission bound, invalid leaf);
  * `not recorded: no path authority` — the poisoned and uninitialized branches (P2).
* On **removed**, the original error is returned unchanged (today's behaviour;
  `engine_image_post_install_error_removes_the_orphan` stays).
* **One log line, at the boundary.** The cleanup half of the composed error names the leaf (its
  UUID, never the directory path), the removal failure and the intent outcome, so the existing
  `run_native_operation` log line (P7) carries the whole story through `error.diagnostic()`. The
  helper therefore no longer emits its own `log::error!` for the failure it returns (that would log
  it twice); it keeps only the D6 warning for the unlinked-but-unsynced case, which is not
  returned. No path or raw OS text reaches the renderer (P7, `d-20260905-10`).
* Renderer impact (P8): no code change in either consumer. In the double-failure case the toast
  text becomes the fixed message "Operation failed; temporary cleanup also failed" instead of the
  primary error's text, and the category becomes `operation-and-cleanup` (mapped to `unexpected`).

### O2 — A failed removal leaves a persisted cleanup intent the existing cleanup retries

MANDATE: "startup cleanup cannot recover it because it only tracks persisted cleanup records";
"persisted as a startup cleanup record".

* **Producer.** A new `PathAuthority` method (name chosen by the executor) records a cleanup
  intent for one installed, unregistered engine-image leaf. Inputs: the caller-proven EngineImages
  `AuthorizedDir`, the leaf, the installed `VerifiedIdentity`. It inserts one `image_cleanup`
  record shaped exactly as P5 and P12 require: a fresh UUID id that is neither a persistent nor a
  retired entry nor an existing cleanup id; class `PersistentFile`; `target_is_dir: false`;
  purpose `EngineImage`; canonical `EngineImage` operations; a fixed non-empty `display_name`
  (a named constant, e.g. "Unregistered engine image"); native path `dir.path().join(leaf)`; the
  installed identity; the directory identity as `parent_identity`.
* **Leaf check.** It refuses, without touching any state, a leaf that is not a single UUID
  component — the only leaves `cleanup_engine_images` acts on (P3).
* **Sealing.** It is permitted while engine attachments are sealed: the registration error during
  shutdown is exactly the case P4's drain waits for.
* **Admission (P6, P11).** The admission snapshot is taken **before** the insert and passed as the
  save's baseline, so the growth bound applies to the new record exactly as to every other one. An
  admission refusal (or any other error before the registry write starts) restores
  `image_cleanup` to its pre-insert state and yields `not recorded: <reason>`. The bound is never
  bypassed. (The race that fills the bound during the copy is `f-20261004-13`.)
* **Persistence outcome.**
  * `Durable` → `recorded`; `registry_durability_pending` cleared as every durable save does.
  * `DurabilityUncertain` → `recorded, durability uncertain`; the record is kept and
    `registry_durability_pending` is set (P13).
  * Registry write `Err` → the record is **kept in memory** and `registry_durability_pending` is
    set, meaning "the in-memory registry is ahead of disk; re-save it" (P13); outcome
    `not recorded, retained in memory: <reason>`. Rationale: Decisions D3.
* **Persistence retry (the one change to `cleanup_engine_images`).** Today the pass re-saves a
  pending registry only when `image_cleanup` is empty (P13). It is generalised: when the pass
  wrote nothing (the set is unchanged) and `registry_durability_pending` is set, it calls the
  existing `retry_registry_durability`, and combines that result with the first removal failure
  exactly as its existing durability-uncertain branch combines them: a retry that ends `Ok`
  leaves the pass returning its first removal failure (as today), never `Ok` while a removal
  failed; a retry that errs or ends uncertain is combined with the first removal failure as
  `OperationAndCleanup`. So a retained intent whose
  removal still fails at shutdown is persisted by the shutdown pass, and startup finds it. Any
  other successful registry save in the session persists it as well (saves serialise
  `self.image_cleanup`, P11). Nothing else in `cleanup_engine_images` changes: a recorded intent is
  indistinguishable from a retired-image intent and is removed on success, missing entry or
  substituted leaf, and kept on any other failure (P3). Its startup and shutdown call sites are
  unchanged (P4).
* Only the registration-failure branch can record (P2). The poisoned and uninitialized branches
  return the O1 error with `not recorded: no path authority` — a named known limit.
* Registry load accepts such a record unchanged (P5, P12); no schema change, no new field.

### O3 — Verification

MANDATE: "The unregistered image stays on disk, and startup cleanup cannot recover it".

Behavioural Rust tests run by `cargo test`; the backend coverage ratchet measures the new lines.
Placement follows P14: everything that needs no removal fault lives in a module compiled on every
target (`portable_tests`, or `main.rs` tests without a unix-only import); tests that use the
removal injector are `#[cfg(unix)]` together with every helper and import they use, so the
Windows test binary neither fails to resolve them nor carries dead code under `-D warnings`.

Portable (every target):

1. **Persist and reload (MANDATE revert proof, injector-free).** Record an intent for a real
   installed UUID leaf through the new method; drop the authority; open a fresh authority from
   the persisted registry; re-acquire the EngineImages directory through `AppDataDir` +
   `ensure_app_owned_default_dir` on the canonical app-data spelling (not a raw tempdir path, which
   differs on Windows, P14); run `cleanup_engine_images`: the leaf is gone, and a further reload
   holds no intent. Without O2 the reopened authority has nothing to clean and the leaf survives.
2. **Sealed.** The same producer call on a sealed authority records the intent.
3. **Write failure.** With the registry replacement failing (injected through the `replace`
   closure that `save_entries_with` / `save_entries_with_baseline` already take, as the existing
   registry-fault tests do), the outcome is `not recorded, retained in memory`, the in-memory
   intent is kept and `registry_durability_pending` is set; then, with the replacement working
   and the leaf still present, a `cleanup_engine_images` pass removes the leaf and persists the
   cleared set. (The sub-case where the pass's removal still fails is test 12, unix-only.)
4. **Durability uncertain.** With the replacement reporting an uncertain parent sync, the outcome
   is `recorded, durability uncertain`, the record is kept and persisted, and
   `registry_durability_pending` is set.
5. **Admission refusal.** An authority at the id bound refuses: outcome `not recorded`, in-memory
   `image_cleanup` unchanged, registry file unchanged, leaf still on disk (known limit
   `f-20261004-13`).
6. **Invalid leaf.** A non-UUID or multi-component leaf is refused with no state change.
7. **Wire form.** Serialising the composed error exposes neither the leaf name nor the app-data path.

Unix (removal injector):

8. **End to end through the helper.** Registration failure + removal failure with an authority:
   the returned error is `OperationAndCleanup`, `primary` contains the original diagnostic, the
   cleanup diagnostic names the removal failure and `recorded`; the leaf is on disk; then the
   test-1 reload + cleanup removes it.
9. **No authority.** The poisoned/uninitialized path with a removal failure returns
   `OperationAndCleanup` whose cleanup diagnostic names `no path authority`; no registry write.
10. **Removed after unlink.** A `ParentSync` removal fault (unlink done, sync uncertain) returns
    the original error unchanged and records no intent.
11. **Removal success** keeps returning the original error unchanged (existing test kept).
12. **Persistence retry at shutdown.** After a test-3-style write failure, a `cleanup_engine_images`
    pass whose removal still fails (injector) writes the retained intent through the generalised
    retry, clears `registry_durability_pending`, **returns `Err` naming the removal failure**
    (not `Ok`), and a reload holds the intent.

The source-scan pin `engine_image_install_and_post_install_cleanup_are_pinned_to_the_descriptor`
is updated to the new contract (three branches still route through the helper; the helper removes
through `remove_leaf_identified` and composes with `Error::with_cleanup`; it no longer emits a
`log::error!` of its own, per O1 "One log line"), not deleted. `engine_image_orphan_removal_failure_preserves_the_original_error`
is replaced by test 8, because its assertion is exactly the behaviour this MANDATE removes.

## Decisions and trade-offs

* **D1 — Both, not either (answers the finding's open question).** Surfacing alone leaves the
  orphan forever; persisting alone leaves the caller with an error that says the operation's side
  effects were cleaned up when they were not, and the async-resource rule requires an error path
  that does not swallow a failure. Each closes a different half of the MANDATE.
* **D2 — Supersedes the "logged" clause of `d-20260905-09`.** New evidence that decision did not
  consider: the logged-only orphan is unreachable by every later cleanup (P3), which is this
  finding. The rest of `d-20260905-09` stands — cleanup bound to `Err` alone, identity-checked
  removal, at most one leaf per failed install, the original error is never masked (it is the
  `primary` of the composed error).
* **D3 — On a failed intent write the in-memory intent is kept and the registry marked pending,
  not rolled back.** Rolling back (the reconcile path's convention) would drop the only route to
  the leaf when the likeliest companion failure — a registry write failure — occurs. Keeping it
  lets shutdown cleanup retry the removal and lets the generalised retry (O2) or any later save
  persist it. A cleanup record never resolves as authority (P5) and cleanup acts only on identity
  agreement (P3), so an unpersisted record cannot widen access. Admission refusals are rolled back
  (they are not write failures, and keeping them would bypass the bound, P11).
* **D4 — Remove first, record only on failure** (rejected: write the intent before the unlink).
  Recording first costs two registry saves on every failed registration and still does not cover
  the crash window before registration, which is `f-20261004-12`'s mechanism question.
* **D5 — Category and toast text change in the double-failure case only.** Both renderer
  consumers pass the rejection to `runUnlessCancelled` and do not branch on it (P8); the fixed
  message is accurate.
* **D6 — A post-unlink sync failure counts as removed.** The entry is gone; recording an intent
  for it would only be dropped as missing at startup, and reporting "cleanup also failed" would be
  false (P10).

## Risks / open questions

* If the registry stays unwritable for the whole session and the removal keeps failing, the
  retained intent is lost at process exit — the registry cannot hold anything then, and the
  composed error and log line say so.
* Poisoned / uninitialized authority branches cannot record an intent (named limit; a poisoned
  authority refuses every path operation today).

## Not part of this task

* `f-20261004-12` — crash between install and registration (needs the single-instance guard
  `f-20260922-07` or a write-ahead intent).
* `f-20261004-13` — capacity reservation so registration and intent cannot both be refused.
* `f-20260830-09` — unlink-by-name residue.
* Any change to the issuance lease, the renderer, or the generated bindings (no command signature
  or exported type changes); `cleanup_engine_images` changes only as O2's persistence retry states.

### plan-r4.md

# Plan: a failed engine-image cleanup is surfaced and retried, never only logged

## Goal

When `issue_engine_image` has installed a UUID image leaf and a later step fails, and removing
that leaf also fails, the leaf must not become an orphan nothing ever revisits, and the caller
must not receive an error that pretends the cleanup succeeded. After this change the removal
failure is part of the returned error, and — wherever the path authority is available — a
persisted cleanup intent makes the existing startup and shutdown cleanup retry the removal.

## MANDATE

Verbatim, `f-20260914-21` (the only member of this slice):

> ### A failed engine-image cleanup is logged but omitted from the returned error, orphaning the image file
>
> * **Where:** src-tauri/src/main.rs:1459-1462
> * **Defect:** When registering an engine image fails and the cleanup of the written image file also fails, only the primary error is returned and the cleanup failure is logged. The unregistered image stays on disk, and startup cleanup cannot recover it because it only tracks persisted cleanup records.
> * **Why it matters:** Unbounded orphaned files the user cannot see or remove; `.claude/rules/async-resource-invariants.md`.
> * **Open question:** Should the cleanup failure be persisted as a startup cleanup record, surfaced to the caller alongside the primary error, or both?

## Threat model and non-goals

* **Accidental failure only.** The removal fails because of an operating-system error (permission
  change, I/O error, a transiently busy file on Windows, a substituted directory entry). No
  adversary is modelled beyond what the existing identity-checked removal already handles
  (`f-20260830-09` owns the unlink-by-name residue and is cited, not re-derived).
* **One process.** The application has no single-instance guard (`f-20260922-07`); this plan,
  like every other path-authority mutation, assumes one process owns the registry.
* Environments: Linux, macOS, Windows release builds; the removal-fault tests run where the
  existing fault injector runs (`#[cfg(unix)]`).

## Approach

### O1 — The removal failure is part of the returned error

MANDATE: "only the primary error is returned and the cleanup failure is logged"; "surfaced to the
caller alongside the primary error".

* Removal outcome classification (P10): `Ok` → removed. `Err` with `Error::is_missing_entry` →
  removed (already absent). `Err(CommittedDurabilityUncertain(_))` → removed (the unlink happened;
  only the parent sync is uncertain, as `d-20260830-04` / `d-20260906-03` treat a committed step):
  logged as a warning, no intent, original error returned. Any other `Err` → **removal failed**.
* On **removal failed**, every one of the three post-install error branches returns
  `Error::with_cleanup(original, Err(cleanup))`, i.e. `Error::OperationAndCleanup` whose `primary`
  is the original error's diagnostic and whose `cleanup` diagnostic names the removal failure
  **and** the intent outcome, exactly one of:
  * `recorded` — the O2 intent is persisted durably;
  * `recorded, durability uncertain` — the registry write committed, its parent sync did not (P13);
  * `not recorded, retained in memory: <reason>` — the registry write failed; the intent lives in
    this process only and is retried by O2's persistence retry;
  * `not recorded: <reason>` — refused before insertion (admission bound, invalid leaf);
  * `not recorded: no path authority` — the poisoned and uninitialized branches (P2).
* On **removed**, the original error is returned unchanged (today's behaviour;
  `engine_image_post_install_error_removes_the_orphan` stays).
* **One log line, at the boundary.** The cleanup half of the composed error names the leaf (its
  UUID, never the directory path), the removal failure and the intent outcome, so the existing
  `run_native_operation` log line (P7) carries the whole story through `error.diagnostic()`. The
  helper therefore no longer emits its own `log::error!` for the failure it returns (that would log
  it twice); it keeps only the D6 warning for the unlinked-but-unsynced case, which is not
  returned. No path or raw OS text reaches the renderer (P7, `d-20260905-10`).
* Renderer impact (P8): no code change in either consumer. In the double-failure case the toast
  text becomes the fixed message "Operation failed; temporary cleanup also failed" instead of the
  primary error's text, and the category becomes `operation-and-cleanup` (mapped to `unexpected`).

### O2 — A failed removal leaves a persisted cleanup intent the existing cleanup retries

MANDATE: "startup cleanup cannot recover it because it only tracks persisted cleanup records";
"persisted as a startup cleanup record".

* **Producer.** A new `PathAuthority` method (name chosen by the executor) records a cleanup
  intent for one installed, unregistered engine-image leaf. Inputs: the caller-proven EngineImages
  `AuthorizedDir`, the leaf, the installed `VerifiedIdentity`. It inserts one `image_cleanup`
  record shaped exactly as P5 and P12 require: a fresh UUID id that is neither a persistent nor a
  retired entry nor an existing cleanup id; class `PersistentFile`; `target_is_dir: false`;
  purpose `EngineImage`; canonical `EngineImage` operations; a fixed non-empty `display_name`
  (a named constant, e.g. "Unregistered engine image"); native path `dir.path().join(leaf)`; the
  installed identity; the directory identity as `parent_identity`.
* **Leaf check.** It refuses, without touching any state, a leaf that is not a single UUID
  component — the only leaves `cleanup_engine_images` acts on (P3).
* **Sealing.** It is permitted while engine attachments are sealed: the registration error during
  shutdown is exactly the case P4's drain waits for.
* **Admission (P6, P11).** The admission snapshot is taken **before** the insert and passed as the
  save's baseline, so the growth bound applies to the new record exactly as to every other one. An
  admission refusal (or any other error before the registry write starts) restores
  `image_cleanup` to its pre-insert state and yields `not recorded: <reason>`. The bound is never
  bypassed. (The race that fills the bound during the copy is `f-20261004-13`.)
* **Persistence outcome.**
  * `Durable` → `recorded`; `registry_durability_pending` cleared as every durable save does.
  * `DurabilityUncertain` → `recorded, durability uncertain`; the record is kept and
    `registry_durability_pending` is set (P13).
  * Registry write `Err` → the record is **kept in memory** and `registry_durability_pending` is
    set, meaning "the in-memory registry is ahead of disk; re-save it" (P13); outcome
    `not recorded, retained in memory: <reason>`. Rationale: Decisions D3.
* **Persistence retry (the one change to `cleanup_engine_images`).** Today the pass re-saves a
  pending registry only when `image_cleanup` is empty (P13). It is generalised: when the pass
  wrote nothing (the set is unchanged) and `registry_durability_pending` is set, it calls the
  existing `retry_registry_durability`, and combines that result with the first removal failure
  exactly as its existing durability-uncertain branch combines them: a retry that ends `Ok`
  leaves the pass returning its first removal failure (as today), never `Ok` while a removal
  failed; a retry that errs or ends uncertain is combined with the first removal failure as
  `OperationAndCleanup`. So a retained intent whose
  removal still fails at shutdown is persisted by the shutdown pass, and startup finds it. Any
  other successful registry save in the session persists it as well (saves serialise
  `self.image_cleanup`, P11). Nothing else in `cleanup_engine_images` changes: a recorded intent is
  indistinguishable from a retired-image intent and is removed on success, missing entry or
  substituted leaf, and kept on any other failure (P3). Its startup and shutdown call sites are
  unchanged (P4).
* Only the registration-failure branch can record (P2). The poisoned and uninitialized branches
  return the O1 error with `not recorded: no path authority` — a named known limit.
* Registry load accepts such a record unchanged (P5, P12); no schema change, no new field.

## Decisions and trade-offs

* **D1 — Both, not either (answers the finding's open question).** Surfacing alone leaves the
  orphan forever; persisting alone leaves the caller with an error that says the operation's side
  effects were cleaned up when they were not, and the async-resource rule requires an error path
  that does not swallow a failure. Each closes a different half of the MANDATE.
* **D2 — Supersedes the "logged" clause of `d-20260905-09`.** New evidence that decision did not
  consider: the logged-only orphan is unreachable by every later cleanup (P3), which is this
  finding. The rest of `d-20260905-09` stands — cleanup bound to `Err` alone, identity-checked
  removal, at most one leaf per failed install, the original error is never masked (it is the
  `primary` of the composed error).
* **D3 — On a failed intent write the in-memory intent is kept and the registry marked pending,
  not rolled back.** Rolling back (the reconcile path's convention) would drop the only route to
  the leaf when the likeliest companion failure — a registry write failure — occurs. Keeping it
  lets shutdown cleanup retry the removal and lets the generalised retry (O2) or any later save
  persist it. A cleanup record never resolves as authority (P5) and cleanup acts only on identity
  agreement (P3), so an unpersisted record cannot widen access. Admission refusals are rolled back
  (they are not write failures, and keeping them would bypass the bound, P11).
* **D4 — Remove first, record only on failure** (rejected: write the intent before the unlink).
  Recording first costs two registry saves on every failed registration and still does not cover
  the crash window before registration, which is `f-20261004-12`'s mechanism question.
* **D5 — Category and toast text change in the double-failure case only.** Both renderer
  consumers pass the rejection to `runUnlessCancelled` and do not branch on it (P8); the fixed
  message is accurate.
* **D6 — A post-unlink sync failure counts as removed.** The entry is gone; recording an intent
  for it would only be dropped as missing at startup, and reporting "cleanup also failed" would be
  false (P10).

## Risks / open questions

* If the registry stays unwritable for the whole session and the removal keeps failing, the
  retained intent is lost at process exit — the registry cannot hold anything then, and the
  composed error and log line say so.
* Poisoned / uninitialized authority branches cannot record an intent (named limit; a poisoned
  authority refuses every path operation today).

### plan-r5.md

# Plan: a failed engine-image cleanup is surfaced and retried, never only logged

## Goal

When `issue_engine_image` has installed a UUID image leaf and a later step fails, and removing
that leaf also fails, the leaf must not become an orphan nothing ever revisits, and the caller
must not receive an error that pretends the cleanup succeeded. After this change the removal
failure is part of the returned error, and — wherever the path authority is available — a
persisted cleanup intent makes the existing startup and shutdown cleanup retry the removal.

## MANDATE

Verbatim, `f-20260914-21` (the only member of this slice):

> ### A failed engine-image cleanup is logged but omitted from the returned error, orphaning the image file
>
> * **Where:** src-tauri/src/main.rs:1459-1462
> * **Defect:** When registering an engine image fails and the cleanup of the written image file also fails, only the primary error is returned and the cleanup failure is logged. The unregistered image stays on disk, and startup cleanup cannot recover it because it only tracks persisted cleanup records.
> * **Why it matters:** Unbounded orphaned files the user cannot see or remove; `.claude/rules/async-resource-invariants.md`.
> * **Open question:** Should the cleanup failure be persisted as a startup cleanup record, surfaced to the caller alongside the primary error, or both?

## Threat model and non-goals

* **Accidental failure only.** The removal fails because of an operating-system error (permission
  change, I/O error, a transiently busy file on Windows, a substituted directory entry). No
  adversary is modelled beyond what the existing identity-checked removal already handles
  (`f-20260830-09` owns the unlink-by-name residue and is cited, not re-derived).
* **One process.** The application has no single-instance guard (`f-20260922-07`); this plan,
  like every other path-authority mutation, assumes one process owns the registry.
* Environments: Linux, macOS, Windows release builds; the removal-fault tests run where the
  existing fault injector runs (`#[cfg(unix)]`).

## Approach

### O1 — The removal failure is part of the returned error

MANDATE: "only the primary error is returned and the cleanup failure is logged"; "surfaced to the
caller alongside the primary error".

* Removal outcome classification (P10): `Ok` → removed. `Err` with `Error::is_missing_entry` →
  removed (already absent). `Err(CommittedDurabilityUncertain(_))` → removed (the unlink happened;
  only the parent sync is uncertain, as `d-20260830-04` / `d-20260906-03` treat a committed step):
  logged as a warning, no intent, original error returned. Any other `Err` → **removal failed**.
* On **removal failed**, every one of the three post-install error branches returns
  `Error::with_cleanup(original, Err(cleanup))`, i.e. `Error::OperationAndCleanup` whose `primary`
  is the original error's diagnostic and whose `cleanup` diagnostic names the removal failure
  **and** the intent outcome, exactly one of:
  * `recorded` — the O2 intent is persisted durably;
  * `recorded, durability uncertain` — the registry write committed, its parent sync did not (P13);
  * `not recorded, retained in memory: <reason>` — the registry write failed; the intent lives in
    this process only and is retried by O2's persistence retry;
  * `not recorded: <reason>` — refused before insertion (admission bound, invalid leaf);
  * `not recorded: no path authority` — the poisoned and uninitialized branches (P2).
* On **removed**, the original error is returned unchanged (today's behaviour;
  `engine_image_post_install_error_removes_the_orphan` stays).
* **One log line, at the boundary.** The cleanup half of the composed error names the leaf (its
  UUID, never the directory path), the removal failure and the intent outcome, so the existing
  `run_native_operation` log line (P7) carries the whole story through `error.diagnostic()`. The
  helper therefore no longer emits its own `log::error!` for the failure it returns (that would log
  it twice); it keeps only the D6 warning for the unlinked-but-unsynced case, which is not
  returned. No path or raw OS text reaches the renderer (P7, `d-20260905-10`).
* Renderer impact (P8): no code change in either consumer. In the double-failure case the toast
  text becomes the fixed message "Operation failed; temporary cleanup also failed" instead of the
  primary error's text, and the category becomes `operation-and-cleanup` (mapped to `unexpected`).

### O2 — A failed removal leaves a persisted cleanup intent the existing cleanup retries

MANDATE: "startup cleanup cannot recover it because it only tracks persisted cleanup records";
"persisted as a startup cleanup record".

* **Producer.** A new `PathAuthority` method (name chosen by the executor) records a cleanup
  intent for one installed, unregistered engine-image leaf. Inputs: the caller-proven EngineImages
  `AuthorizedDir`, the leaf, the installed `VerifiedIdentity`. It inserts one `image_cleanup`
  record shaped exactly as P5 and P12 require: a fresh UUID id that is neither a persistent nor a
  retired entry nor an existing cleanup id; class `PersistentFile`; `target_is_dir: false`;
  purpose `EngineImage`; canonical `EngineImage` operations; a fixed non-empty `display_name`
  (a named constant, e.g. "Unregistered engine image"); native path `dir.path().join(leaf)`; the
  installed identity; the directory identity as `parent_identity`.
* **Leaf check.** It refuses, without touching any state, a leaf that is not a single UUID
  component — the only leaves `cleanup_engine_images` acts on (P3).
* **Sealing.** It is permitted while engine attachments are sealed: the registration error during
  shutdown is exactly the case P4's drain waits for.
* **Admission (P6, P11).** The admission snapshot is taken **before** the insert and passed as the
  save's baseline, so the growth bound applies to the new record exactly as to every other one. An
  admission refusal (or any other error before the registry write starts) restores
  `image_cleanup` to its pre-insert state and yields `not recorded: <reason>`. The bound is never
  bypassed. (The race that fills the bound during the copy is `f-20261004-13`.)
* **Persistence outcome.**
  * `Durable` → `recorded`; `registry_durability_pending` cleared as every durable save does.
  * `DurabilityUncertain` → `recorded, durability uncertain`; the record is kept and
    `registry_durability_pending` is set (P13).
  * Registry write `Err` → the record is **kept in memory** and `registry_durability_pending` is
    set, meaning "the in-memory registry is ahead of disk; re-save it" (P13); outcome
    `not recorded, retained in memory: <reason>`. Rationale: Decisions D3.
* **Persistence retry (the one change to `cleanup_engine_images`).** Today the pass re-saves a
  pending registry only when `image_cleanup` is empty (P13). It is generalised: when the pass
  wrote nothing (the set is unchanged) and `registry_durability_pending` is set, it calls the
  existing `retry_registry_durability`, and combines that result with the first removal failure
  exactly as its existing durability-uncertain branch combines them: a retry that ends `Ok`
  leaves the pass returning its first removal failure (as today), never `Ok` while a removal
  failed; a retry that errs or ends uncertain is combined with the first removal failure as
  `OperationAndCleanup`. So a retained intent whose
  removal still fails at shutdown is persisted by the shutdown pass, and startup finds it. Any
  other successful registry save in the session persists it as well (saves serialise
  `self.image_cleanup`, P11). Nothing else in `cleanup_engine_images` changes: a recorded intent is
  indistinguishable from a retired-image intent and is removed on success, missing entry or
  substituted leaf, and kept on any other failure (P3). Its startup and shutdown call sites are
  unchanged (P4).
* Only the registration-failure branch can record (P2). The poisoned and uninitialized branches
  return the O1 error with `not recorded: no path authority` — a named known limit.
* Registry load accepts such a record unchanged (P5, P12); no schema change, no new field.

## Decisions and trade-offs

* **D1 — Both, not either (answers the finding's open question).** Surfacing alone leaves the
  orphan forever; persisting alone leaves the caller with an error that says the operation's side
  effects were cleaned up when they were not, and the async-resource rule requires an error path
  that does not swallow a failure. Each closes a different half of the MANDATE.
* **D2 — Supersedes the "logged" clause of `d-20260905-09`.** New evidence that decision did not
  consider: the logged-only orphan is unreachable by every later cleanup (P3), which is this
  finding. The rest of `d-20260905-09` stands — cleanup bound to `Err` alone, identity-checked
  removal, at most one leaf per failed install, the original error is never masked (it is the
  `primary` of the composed error).
* **D3 — On a failed intent write the in-memory intent is kept and the registry marked pending,
  not rolled back.** Rolling back (the reconcile path's convention) would drop the only route to
  the leaf when the likeliest companion failure — a registry write failure — occurs. Keeping it
  lets shutdown cleanup retry the removal and lets the generalised retry (O2) or any later save
  persist it. A cleanup record never resolves as authority (P5) and cleanup acts only on identity
  agreement (P3), so an unpersisted record cannot widen access. Admission refusals are rolled back
  (they are not write failures, and keeping them would bypass the bound, P11).
* **D4 — Remove first, record only on failure** (rejected: write the intent before the unlink).
  Recording first costs two registry saves on every failed registration and still does not cover
  the crash window before registration, which is `f-20261004-12`'s mechanism question.
* **D5 — Category and toast text change in the double-failure case only.** Both renderer
  consumers pass the rejection to `runUnlessCancelled` and do not branch on it (P8); the fixed
  message is accurate.
* **D6 — A post-unlink sync failure counts as removed.** The entry is gone; recording an intent
  for it would only be dropped as missing at startup, and reporting "cleanup also failed" would be
  false (P10).

## Risks / open questions

* If the registry stays unwritable for the whole session and the removal keeps failing, the
  retained intent is lost at process exit — the registry cannot hold anything then, and the
  composed error and log line say so.
* Poisoned / uninitialized authority branches cannot record an intent (named limit; a poisoned
  authority refuses every path operation today).
