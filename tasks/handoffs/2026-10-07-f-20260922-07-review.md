## Mandate (fixed)

Close `f-20260922-07`: nothing prevents a second ChessFable process from starting; both share the
same `AppDataDir`, path-authority registry, webview data directory and therefore web storage, and
every in-process guard (per-resource mutexes, operation registry, practice per-deck lock,
credential registry journal) is scoped to one process. Open question: `tauri-plugin-single-instance`,
a lock file under the app-data directory with an explicit "another instance is running" message, or
per-resource cross-process locking.

## Planned answer

- **O1:** one exclusive advisory-lock primitive in `src-tauri/src/infra/fs.rs` (blocking and
  non-blocking; `rustix::fs::flock` / `LockFileEx`, not `std::fs::File::try_lock`, which does not
  compile on the coverage nightly); practice's deck lock and the macOS engine-launch sweep route
  through it. Unsupported locking = `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`, Windows `ERROR_NOT_SUPPORTED`,
  `ERROR_INVALID_FUNCTION`; `ENOLCK` is an ordinary error.
- **O2:** a non-blocking instance lock on `<app_data>/instance.lock` (descriptor door, never
  unlinked), held for the process lifetime; admission returns `Result<Admission, Error>` with
  owned guard / unguarded (unsupported FS, one warning) / held elsewhere, and logs each outcome.
- **O3:** main window `"create": false`; `.setup` runs app-data acquisition → admission
  (`.map_err(..)?`, unconditional at setup level) → refusal returns before credentials, authority
  and window → … → window built from config last. Source scans and a config test pin it.
- **O4:** a refused launch shows a native "ChessFable is already running" dialog and exits with
  `std::process::exit(0)` (no `RunEvent::Exit`, so window-state does not rewrite the running
  instance's file).
- **O5:** one bullet in `.claude/rules/async-resource-invariants.md` naming the enforced invariant.
- Rejected: the single-instance plugin (identifier-keyed — would refuse `verify:app` beside the
  daily app; fail-open on no bus, socket race and mutex race; forwards an argv nobody consumes);
  per-resource cross-process locking.
- Named limits: the one-time rollout transition from a still-running pre-guard build (I10); English
  dialog text; the dialog itself is native chrome only Felix can see.

# Plan: one ChessFable process per application-data directory

## Goal

Make the "one process" assumption that every native registry, journal and in-process lock already
relies on true, by refusing a second process that would share the same application-data directory
before it reads or writes any shared per-user state or creates its webview. The refused launch
tells the user that ChessFable is already running and exits.

## MANDATE

Verbatim from `f-20260922-07` (`tasks/findings.md`):

> ### The application has no single-instance guard, so two instances share one app-data directory
>
> * **Where:** `src-tauri/src/main.rs:2424-2437` (the Tauri builder's plugin set).
> * **Defect:** nothing prevents a second instance of ChessFable from starting. Both instances resolve
>   the same `AppDataDir`, the same path-authority registry
>   (`src-tauri/src/main.rs:2469`, `path-authority.json`) and the same webview data directory, and
>   therefore the same `localStorage`/`sessionStorage`. Every in-process guard in the codebase — the
>   per-resource mutexes, the operation registry, the planned per-deck lock of
>   `tasks/plans/2026-09-22-practice-durable-storage.md` — is scoped to one process and does not hold
>   across two.
> * **Why it matters:** the failure modes are silent rather than loud. Two instances appending to the
>   same newest review shard can lose one entry; two startup path-owner reconciliations can race; two
>   engine registries can disagree about which processes exist. Each subsystem currently states "one
>   process" as an assumption, and the assumption is not enforced anywhere.
> * **Open question:** is the answer `tauri-plugin-single-instance` (focus the running window and
>   exit), or a lock file under the app-data directory with an explicit "another instance is running"
>   message, or per-resource cross-process locking? The first is the smallest and matches what the
>   code already assumes; the third is the only one that would actually support two windows, and
>   nothing in the product asks for that. The answer decides whether every "one process" assumption in
>   the codebase becomes true or has to be replaced.
> * **Another consequence, found 2026-09-27 by `review-correctness` in the cumulative review for
>   `f-20260912-01`:** the Lichess credential registry (`src-tauri/src/credentials.rs`) is also a
>   one-process assumption. If two instances start with the same registry, instance A adds an
>   account, and instance B then adds one from its stale in-memory registry, B's journal replaces the
>   file without A's record. A's keyring secret then has no record a fresh startup can load: an
>   orphaned bearer token, the class `f-20260912-01` closed for a replaced directory. The
>   directory-identity checks added there cannot see it, because both instances write the same inode.
>   A single-instance guard would remove this case along with the others listed here.

## Threat model and non-goals

* **In scope (accidental):** the same OS user launches ChessFable a second time while it runs —
  from the application menu, a terminal, `pnpm tauri dev` / bare `cargo run` under the release
  identifier, or a freshly installed build launched while the previous one is still open — on
  Linux, macOS or Windows, including a crash of the first process (the lock must not outlive it).
* **In scope (environment):** a filesystem whose advisory locks are unsupported, and a desktop
  session without a D-Bus session bus. Neither may crash the app or make it unusable.
* **Not in scope:** an adversary of the same UID who deletes or replaces the lock file, or runs a
  patched binary; two processes that resolve *different* app-data directories (different HOME or
  XDG variables, the `.dev` identifier) but share a user-picked directory outside app data — those
  are different profiles by construction and not the shared state this finding names; two OS users.
* **Frozen with the MANDATE.** Changing this section needs the recorded focused judgment of build §4.

## Approach

### O1 — One advisory-lock primitive in `infra::fs`

MANDATE: "Every in-process guard in the codebase … is scoped to one process and does not hold
across two." The guard needs a cross-process lock; the codebase already has two hand-written copies
of the same primitive (P8), so the third use extracts it (rule 11, extract at the second copy).

* `infra/fs.rs` gains one function that takes an exclusive advisory lock on an already open regular
  file, with a blocking and a non-blocking mode, on unix (`rustix::fs::flock`) and Windows
  (`LockFileEx`, `LOCKFILE_EXCLUSIVE_LOCK`, plus `LOCKFILE_FAIL_IMMEDIATELY` in non-blocking mode,
  whole-file range as today). Not `std::fs::File::try_lock` (P9).
* Its result distinguishes three outcomes: **acquired**; **held elsewhere** (unix `EWOULDBLOCK`/`EAGAIN`;
  Windows `ERROR_LOCK_VIOLATION`); and **error** — with the unsupported-locking errors (unix
  `ENOLCK`, `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`; Windows `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`)
  classifiable by the caller as "this filesystem cannot lock". The lock is released by dropping the
  file (the kernel releases it on every process exit, including a crash).
* `practice.rs` `AdvisoryDeckLock::acquire` and the macOS engine-launch sweep's non-blocking probe
  route through it, behaviour unchanged (blocking for practice; held-elsewhere ⇒ `continue` in the
  sweep, any other error logged and skipped as today). The `O_EXLOCK` atomic create-and-lock of the
  launch root stays as is (P8: a different primitive, and splitting it would reopen the window
  between create and lock).

### O2 — The instance lock on the application-data directory

MANDATE: "Both instances resolve the same `AppDataDir` … The answer decides whether every 'one
process' assumption in the codebase becomes true."

* `infra/path_authority/mod.rs`, next to `AppDataDir`, gains an instance-lock type acquired from an
  `&AppDataDir`: it opens or creates the regular leaf `instance.lock` at the app-data root through the
  retained descriptor (P10; `NOFOLLOW`, `0600`) and takes the O1 lock **non-blocking**.
* Outcomes and their failure semantics:
  * acquired → returns a guard that owns the file; the caller keeps it alive for the whole process
    (managed state), so the lock is held until the process ends and released by the kernel then;
  * held elsewhere → "another ChessFable process owns this application-data directory" (O4);
  * locking unsupported on this filesystem → the app starts **without** the guard and logs one
    warning naming the condition — no worse than today, and never a refusal to start;
  * any other open or lock error → a startup error, mapped and logged exactly like the other
    app-data acquisition failures in `.setup` (fixed renderer-safe text, diagnostic in the log).
* The leaf is never deleted or truncated: unlinking a lock file lets a later process lock a new
  inode while an older one still holds the old (the classic advisory-lock race). Its content is
  empty and unused.
* The leaf sits at the app-data root, not in an `AppOwnedDefaultRoot` subdirectory; nothing
  enumerates the app-data root (P10, `d-20260905-02` governs the closed set of *directories*).
* Why the app-data directory and not `app_config_dir` or the bundle identifier: the shared state the
  MANDATE names — `AppDataDir`, the credentials registry, the webview storage — and the config
  directory all derive from the same identifier and user environment; the app-data directory is the
  one this code already acquires through a retained descriptor. An identifier key would refuse
  `verify:app` while the daily app runs (P6).

### O3 — Acquire before any shared state and before the webview exists

MANDATE: "the same webview data directory, and therefore the same `localStorage`/`sessionStorage`";
"two startup path-owner reconciliations can race".

* `src-tauri/tauri.conf.json`: the main window gets `"create": false` (P2, P3). Nothing else in the
  window config changes.
* `.setup` order becomes: `AppDataDir::for_app` (the existing single call, P11) → instance lock (O2)
  → on "held elsewhere" the O4 path and `return Ok(())` with nothing else initialised → credentials
  → path authority → events → sound → CLI plugin → **create the main window from
  `app.config().app.windows[0]`** (P3), last, so the renderer can reach no command before every
  backend state the setup installs exists.
* A failure to build the window is a setup error like any other (`?`), as it is today inside
  Tauri's own `setup`.
* The P11 source-scan tests stay green without being weakened: no second `AppDataDir::for_app(`,
  credentials still before the authority, no `target_os = "linux"` cfg inside the closure. Add one
  source-scan assertion (in the existing style next to
  `credential_initialization_precedes_path_authority_open`) that the instance-lock acquisition
  follows `AppDataDir::for_app(` and precedes the credential initialisation, and that the window
  is created from the config inside `.setup` after the CLI plugin registration.
* Plugins initialised during `build` (P2) run before the guard. Measured: window-state only reads
  there (P4); the log plugin opens its file (P12). Both are named limits below, not shared-state
  corruption: the refused process exits without running the window-state exit save (O4), and its
  two or three log lines are appended to the shared log file.

### O4 — The refused launch: tell the user, then exit without exit hooks

MANDATE: "a lock file under the app-data directory with an explicit 'another instance is running'
message".

* On "held elsewhere", `.setup` logs one line at `warn` ("another ChessFable process holds the
  application data directory; this launch exits") — the line `verify:app` asserts (O5) — and shows a
  native message dialog through the already registered dialog plugin (`MessageDialogBuilder::show`,
  asynchronous, no parent window; P2: the event loop is running at `Ready`), English text:
  title "ChessFable is already running", body "ChessFable is already open. Switch to its window to
  continue." The dialog's callback terminates the process with `std::process::exit(0)`.
* `std::process::exit` and not `AppHandle::exit`: the refused process owns nothing (no credentials,
  no authority, no engines, no sound server), and `RunEvent::Exit` would run the window-state save
  (P4), rewriting the running instance's window-state file from a stale cache.
* No window, no webview and no renderer are created for the refused process (O3).

### O5 — State the invariant where the next session looks

MANDATE: "Each subsystem currently states 'one process' as an assumption, and the assumption is not

## Decisions and trade-offs

* **Lock file on the app-data directory, not `tauri-plugin-single-instance`.** The plugin's key is
  the bundle identifier, not the shared directory: it would refuse `verify:app` (temporary HOME,
  same session bus) whenever the daily app is open and focus the daily window instead (P6). It is
  fail-open in three measured ways (P5), so a lock would be needed underneath it anyway. Its
  remaining benefit — focusing the running window and forwarding argv — carries nothing today
  (P7). It would also require a second dependency tree on Linux (zbus 5 is already present
  transitively) and a `tauri` 2.10-compatible older plugin line (2.4.x), or a `tauri` bump to 2.12.
* **Per-resource cross-process locking: rejected.** The finding itself notes it is the only option
  that would support two windows and that nothing in the product asks for that; it would have to
  replace every one-process assumption (credentials journal, path-authority snapshot, engine
  supervisor, operation registry, webview storage) instead of making it true.
* **Refusal UX: message dialog, then exit.** Precedent P13 (the app tells the user when it cannot
  start safely). Focusing the running window would need an inter-process channel keyed on the
  app-data directory on three platforms; the only off-the-shelf one is the plugin rejected above.
* **Unsupported locking ⇒ start unguarded with a warning,** not refuse: refusing would make the app
  unusable on such a filesystem, where today it works; unguarded is exactly today's behaviour.
* **Window created last in `.setup` via `create: false`.** The alternative — acquire in a plugin
  registered first (runs during `build`) — cannot show a dialog (the event loop is not running yet)
  and still leaves the webview to be created by Tauri before the app's `.setup`.
* **English dialog text.** The native process has no i18next catalogue before the renderer starts,
  and the refused process must not start a renderer (O3). Named limit.

## Approach

### O1 — One advisory-lock primitive in `infra::fs`

MANDATE: "Every in-process guard in the codebase … is scoped to one process and does not hold
across two." The guard needs a cross-process lock; the codebase already has two hand-written copies
of the same primitive (P8), so the third use extracts it (rule 11, extract at the second copy).

* `infra/fs.rs` gains one function that takes an exclusive advisory lock on an already open regular
  file, with a blocking and a non-blocking mode, on unix (`rustix::fs::flock`) and Windows
  (`LockFileEx`, `LOCKFILE_EXCLUSIVE_LOCK`, plus `LOCKFILE_FAIL_IMMEDIATELY` in non-blocking mode,
  whole-file range as today). Not `std::fs::File::try_lock` (P9).
* Its result distinguishes three outcomes: **acquired**; **held elsewhere** (unix `EWOULDBLOCK`/`EAGAIN`;
  Windows `ERROR_LOCK_VIOLATION`); and **error** — with the unsupported-locking errors (unix
  `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`; Windows `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`)
  classifiable by the caller as "this filesystem cannot lock". `ENOLCK` is **not** in that set:
  `flock(2)` defines it as the kernel running out of memory for lock records, which happens on a
  lock-capable filesystem, so it stays an ordinary error (startup error in O2). The lock is released by dropping the
  file (the kernel releases it on every process exit, including a crash).
* `practice.rs` `AdvisoryDeckLock::acquire` and the macOS engine-launch sweep's non-blocking probe
  route through it, behaviour unchanged (blocking for practice; held-elsewhere ⇒ `continue` in the
  sweep, any other error logged and skipped as today). The `O_EXLOCK` atomic create-and-lock of the
  launch root stays as is (P8: a different primitive, and splitting it would reopen the window
  between create and lock).

### O2 — The instance lock on the application-data directory

MANDATE: "Both instances resolve the same `AppDataDir` … The answer decides whether every 'one
process' assumption in the codebase becomes true."

* `infra/path_authority/mod.rs`, next to `AppDataDir`, gains an instance-lock type acquired from an
  `&AppDataDir`: it opens or creates the regular leaf `instance.lock` at the app-data root through the
  retained descriptor (P10; `NOFOLLOW`, `0600`) and takes the O1 lock **non-blocking**.
* Outcomes and their failure semantics:
  * acquired → returns a guard that owns the file; the caller keeps it alive for the whole process
    (managed state), so the lock is held until the process ends and released by the kernel then;
  * held elsewhere → "another ChessFable process owns this application-data directory" (O4);
  * locking unsupported on this filesystem → the app starts **without** the guard and logs one
    warning naming the condition — no worse than today, and never a refusal to start;
  * any other open or lock error → a startup error, mapped and logged exactly like the other
    app-data acquisition failures in `.setup` (fixed renderer-safe text, diagnostic in the log).
* The mapping from the O1 lock result to these four outcomes is one function with a unit test per
  outcome (acquired, held elsewhere, unsupported, other error — `ENOLCK` among the "other" cases),
  so a caller that refuses on "unsupported" or continues on "other error" fails a test.
* The leaf is never deleted or truncated: unlinking a lock file lets a later process lock a new
  inode while an older one still holds the old (the classic advisory-lock race). Its content is
  empty and unused.
* The leaf sits at the app-data root, not in an `AppOwnedDefaultRoot` subdirectory; nothing
  enumerates the app-data root (P10, `d-20260905-02` governs the closed set of *directories*).
* Why the app-data directory and not `app_config_dir` or the bundle identifier: the shared state the
  MANDATE names — `AppDataDir`, the credentials registry, the webview storage — and the config
  directory all derive from the same identifier and user environment; the app-data directory is the
  one this code already acquires through a retained descriptor. An identifier key would refuse
  `verify:app` while the daily app runs (P6).

### O3 — Acquire before any shared state and before the webview exists

MANDATE: "the same webview data directory, and therefore the same `localStorage`/`sessionStorage`";
"two startup path-owner reconciliations can race".

* `src-tauri/tauri.conf.json`: the main window gets `"create": false` (P2, P3). Nothing else in the
  window config changes.
* `.setup` order becomes: `AppDataDir::for_app` (the existing single call, P11) → instance lock (O2)
  → on "held elsewhere" the O4 path and `return Ok(())` with nothing else initialised → credentials
  → path authority → events → sound → CLI plugin → **create the main window from
  `app.config().app.windows[0]`** (P3), last, so the renderer can reach no command before every
  backend state the setup installs exists.
* A failure to build the window is a setup error like any other (`?`), as it is today inside
  Tauri's own `setup`.
* The P11 source-scan tests stay green without being weakened: no second `AppDataDir::for_app(`,
  credentials still before the authority, no `target_os = "linux"` cfg inside the closure. Add
  source-scan assertions (in the existing style next to
  `credential_initialization_precedes_path_authority_open`) that, inside `.setup`:
  the instance-lock acquisition follows `AppDataDir::for_app(` and precedes the credential
  initialisation; the held-elsewhere arm ends in `return Ok(())` **before** the first
  `.credentials` call and the first `PathAuthority::open_for_app(`; the unsupported arm does not
  return; and the window is created from the config after the CLI plugin registration. Identical
  registry bytes cannot prove the order (credential initialisation rewrites the registry
  deterministically, `credentials.rs:313`), so the order is proven by the scan.
* A unit test reads `src-tauri/tauri.conf.json` (`include_str!`) and asserts `app.windows[0].create`
  is `false`: reverting that line would let Tauri build the webview before `.setup` (P2) while every
  other assertion stays green.
* Plugins initialised during `build` (P2) run before the guard. Measured: window-state only reads
  there (P4); the log plugin opens its file (P12). Both are named limits below, not shared-state
  corruption: the refused process exits without running the window-state exit save (O4), and its

### O4 — The refused launch: tell the user, then exit without exit hooks

MANDATE: "a lock file under the app-data directory with an explicit 'another instance is running'
message".

* On "held elsewhere", `.setup` logs one line at `warn` ("another ChessFable process holds the
  application data directory; this launch exits") — the line `verify:app` asserts (O5) — and shows a
  native message dialog through the already registered dialog plugin (`MessageDialogBuilder::show`,

  continue." The dialog's callback terminates the process with `std::process::exit(0)`.
* `std::process::exit` and not `AppHandle::exit`: the refused process owns nothing (no credentials,
  no authority, no engines, no sound server), and `RunEvent::Exit` would run the window-state save

* No window, no webview and no renderer are created for the refused process (O3).

  engine images, practice) may rely on it; it does not cover a user-picked directory shared by two
  *different* app-data directories (release and `.dev` identifiers, a different HOME), nor a
  filesystem without advisory locks (logged at startup).

## Decisions and trade-offs

* **Lock file on the app-data directory, not `tauri-plugin-single-instance`.** The plugin's key is
  the bundle identifier, not the shared directory: it would refuse `verify:app` (temporary HOME,
  same session bus) whenever the daily app is open and focus the daily window instead (P6). It is
  fail-open in three measured ways (P5), so a lock would be needed underneath it anyway. Its
  remaining benefit — focusing the running window and forwarding argv — carries nothing today
  (P7). It would also require a second dependency tree on Linux (zbus 5 is already present
  transitively) and a `tauri` 2.10-compatible older plugin line (2.4.x), or a `tauri` bump to 2.12.
* **Per-resource cross-process locking: rejected.** The finding itself notes it is the only option
  that would support two windows and that nothing in the product asks for that; it would have to
  replace every one-process assumption (credentials journal, path-authority snapshot, engine
  supervisor, operation registry, webview storage) instead of making it true.
* **Refusal UX: message dialog, then exit.** Precedent P13 (the app tells the user when it cannot
  start safely). Focusing the running window would need an inter-process channel keyed on the
  app-data directory on three platforms; the only off-the-shelf one is the plugin rejected above.
* **Unsupported locking ⇒ start unguarded with a warning,** not refuse: refusing would make the app
  unusable on such a filesystem, where today it works; unguarded is exactly today's behaviour.
* **Window created last in `.setup` via `create: false`.** The alternative — acquire in a plugin
  registered first (runs during `build`) — cannot show a dialog (the event loop is not running yet)
  and still leaves the webview to be created by Tauri before the app's `.setup`.
* **English dialog text.** The native process has no i18next catalogue before the renderer starts,
  and the refused process must not start a renderer (O3). Named limit.

## Goal

relies on true, by refusing a second process that would share the same application-data directory

## Threat model and non-goals

* **In scope (accidental):** the same OS user launches ChessFable a second time while it runs —
  from the application menu, a terminal, `pnpm tauri dev` / bare `cargo run` under the release
  identifier, or a freshly installed build launched while the previous one is still open — on
  Linux, macOS or Windows, including a crash of the first process (the lock must not outlive it).
  Every one of these holds between builds that **both** carry the guard.
* **In scope (environment):** a filesystem whose advisory locks are unsupported, and a desktop
  session without a D-Bus session bus. Neither may crash the app or make it unusable.
* **Not in scope — one-time rollout transition (amended r3, issue I10):** a process of a build from
  before this change never takes `instance.lock`, so the first guarded launch while such a process
  is still running is unguarded exactly as today; a lock nobody took cannot be observed, and no
  other state the old build holds identifies it. Once that process ends, every later pair is
  guarded. Named limit, not a mechanism (build §4: a hazard equal to the pre-change system).
* **Not in scope:** an adversary of the same UID who deletes or replaces the lock file, or runs a

## Approach

### O1 — One advisory-lock primitive in `infra::fs`

MANDATE: "Every in-process guard in the codebase … is scoped to one process and does not hold
across two." The guard needs a cross-process lock; the codebase already has two hand-written copies
of the same primitive (P8), so the third use extracts it (rule 11, extract at the second copy).

* `infra/fs.rs` gains one function that takes an exclusive advisory lock on an already open regular
  file, with a blocking and a non-blocking mode, on unix (`rustix::fs::flock`) and Windows
  (`LockFileEx`, `LOCKFILE_EXCLUSIVE_LOCK`, plus `LOCKFILE_FAIL_IMMEDIATELY` in non-blocking mode,
  whole-file range as today). Not `std::fs::File::try_lock` (P9).
* Its result distinguishes three outcomes: **acquired**; **held elsewhere** (unix `EWOULDBLOCK`/`EAGAIN`;
  Windows `ERROR_LOCK_VIOLATION`); and **error** — with the unsupported-locking errors (unix
  `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`; Windows `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`)
  classifiable by the caller as "this filesystem cannot lock". `ENOLCK` is **not** in that set:
  `flock(2)` defines it as the kernel running out of memory for lock records, which happens on a
  lock-capable filesystem, so it stays an ordinary error (startup error in O2). The lock is released by dropping the
  file (the kernel releases it on every process exit, including a crash).
* `practice.rs` `AdvisoryDeckLock::acquire` and the macOS engine-launch sweep's non-blocking probe
  route through it, behaviour unchanged (blocking for practice; held-elsewhere ⇒ `continue` in the
  sweep, any other error logged and skipped as today). The `O_EXLOCK` atomic create-and-lock of the
  launch root stays as is (P8: a different primitive, and splitting it would reopen the window
  between create and lock).

### O2 — The instance lock on the application-data directory

MANDATE: "Both instances resolve the same `AppDataDir` … The answer decides whether every 'one
process' assumption in the codebase becomes true."

* `infra/path_authority/mod.rs`, next to `AppDataDir`, gains an instance-lock type acquired from an
  `&AppDataDir`: it opens or creates the regular leaf `instance.lock` at the app-data root through the
  retained descriptor (P10; `NOFOLLOW`, `0600`) and takes the O1 lock **non-blocking**.
* Outcomes and their failure semantics:
  * acquired → returns a guard that owns the file; the caller keeps it alive for the whole process
    (managed state), so the lock is held until the process ends and released by the kernel then;
  * held elsewhere → "another ChessFable process owns this application-data directory" (O4);
  * locking unsupported on this filesystem → the app starts **without** the guard and logs one
    warning naming the condition — no worse than today, and never a refusal to start;
  * any other open or lock error → a startup error, mapped and logged exactly like the other
    app-data acquisition failures in `.setup` (fixed renderer-safe text, diagnostic in the log).
* The instance-lock admission is one function that maps the O1 result to these outcomes **and emits
  each outcome's log line itself** — unsupported: exactly one `warn`; held elsewhere: the O4 refusal
  line; other error: the app-data failure log — so `.setup` only matches the returned outcome and
  has no logging of its own to forget. Its unit tests drive every lock result (real files for
  acquired and held elsewhere; `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`, `ENOLCK` and another error injected
  through the function's lock-result input) under `crate::error::LogCaptureScope` and assert the
  outcome and the captured lines: unsupported → unguarded admission plus exactly one warning;
  `ENOLCK` and any other error → an error and no unguarded admission; held elsewhere → refusal plus
  the refusal line. The O3 scan pins what `.setup` does with each outcome.
* The leaf is never deleted or truncated: unlinking a lock file lets a later process lock a new
  inode while an older one still holds the old (the classic advisory-lock race). Its content is
  empty and unused.
* The leaf sits at the app-data root, not in an `AppOwnedDefaultRoot` subdirectory; nothing
  enumerates the app-data root (P10, `d-20260905-02` governs the closed set of *directories*).
* Why the app-data directory and not `app_config_dir` or the bundle identifier: the shared state the
  MANDATE names — `AppDataDir`, the credentials registry, the webview storage — and the config
  directory all derive from the same identifier and user environment; the app-data directory is the
  one this code already acquires through a retained descriptor. An identifier key would refuse
  `verify:app` while the daily app runs (P6).

### O3 — Acquire before any shared state and before the webview exists

MANDATE: "the same webview data directory, and therefore the same `localStorage`/`sessionStorage`";
"two startup path-owner reconciliations can race".

* `src-tauri/tauri.conf.json`: the main window gets `"create": false` (P2, P3). Nothing else in the
  window config changes.
* `.setup` order becomes: `AppDataDir::for_app` (the existing single call, P11) → instance lock (O2)
  → on "held elsewhere" the O4 path and `return Ok(())` with nothing else initialised → credentials
  → path authority → events → sound → CLI plugin → **create the main window from
  `app.config().app.windows[0]`** (P3), last, so the renderer can reach no command before every
  backend state the setup installs exists.
* A failure to build the window is a setup error like any other (`?`), as it is today inside
  Tauri's own `setup`.
* The P11 source-scan tests stay green without being weakened: no second `AppDataDir::for_app(`,
  credentials still before the authority, no `target_os = "linux"` cfg inside the closure. Add
  source-scan assertions (in the existing style next to

### O4 — The refused launch: tell the user, then exit without exit hooks

MANDATE: "a lock file under the app-data directory with an explicit 'another instance is running'
message".

* On "held elsewhere", the O2 admission has logged one line at `warn` ("another ChessFable process
  holds the application data directory; this launch exits") — the line `verify:app` asserts — and
  `.setup` shows a native message dialog through the already registered dialog plugin (`MessageDialogBuilder::show`,
  asynchronous, no parent window; P2: the event loop is running at `Ready`), English text:
  title "ChessFable is already running", body "ChessFable is already open. Switch to its window to
  continue." The dialog's callback terminates the process with `std::process::exit(0)`.
* `std::process::exit` and not `AppHandle::exit`: the refused process owns nothing (no credentials,
  no authority, no engines, no sound server), and `RunEvent::Exit` would run the window-state save
  (P4), rewriting the running instance's window-state file from a stale cache.
* No window, no webview and no renderer are created for the refused process (O3).

MANDATE: "Each subsystem currently states 'one process' as an assumption, and the assumption is not

  at the start of `.setup`; in-process registries over app-data state (credentials, path authority,
  engine images, practice) may rely on it; it does not cover a user-picked directory shared by two
  *different* app-data directories (release and `.dev` identifiers, a different HOME), nor a
  filesystem without advisory locks (logged at startup).

## Decisions and trade-offs

* **Lock file on the app-data directory, not `tauri-plugin-single-instance`.** The plugin's key is
  the bundle identifier, not the shared directory: it would refuse `verify:app` (temporary HOME,
  same session bus) whenever the daily app is open and focus the daily window instead (P6). It is
  fail-open in three measured ways (P5), so a lock would be needed underneath it anyway. Its
  remaining benefit — focusing the running window and forwarding argv — carries nothing today
  (P7). It would also require a second dependency tree on Linux (zbus 5 is already present
  transitively) and a `tauri` 2.10-compatible older plugin line (2.4.x), or a `tauri` bump to 2.12.
* **Per-resource cross-process locking: rejected.** The finding itself notes it is the only option
  that would support two windows and that nothing in the product asks for that; it would have to
  replace every one-process assumption (credentials journal, path-authority snapshot, engine
  supervisor, operation registry, webview storage) instead of making it true.
* **Refusal UX: message dialog, then exit.** Precedent P13 (the app tells the user when it cannot
  start safely). Focusing the running window would need an inter-process channel keyed on the
  app-data directory on three platforms; the only off-the-shelf one is the plugin rejected above.
* **Unsupported locking ⇒ start unguarded with a warning,** not refuse: refusing would make the app
  unusable on such a filesystem, where today it works; unguarded is exactly today's behaviour.
* **Window created last in `.setup` via `create: false`.** The alternative — acquire in a plugin
  registered first (runs during `build`) — cannot show a dialog (the event loop is not running yet)
  and still leaves the webview to be created by Tauri before the app's `.setup`.
* **English dialog text.** The native process has no i18next catalogue before the renderer starts,
  and the refused process must not start a renderer (O3). Named limit.

### plan-r4.md

# Plan: one ChessFable process per application-data directory

## Goal

Make the "one process" assumption that every native registry, journal and in-process lock already
relies on true, by refusing a second process that would share the same application-data directory
before it reads or writes any shared per-user state or creates its webview. The refused launch
tells the user that ChessFable is already running and exits.

## MANDATE

Verbatim from `f-20260922-07` (`tasks/findings.md`):

> ### The application has no single-instance guard, so two instances share one app-data directory
>
> * **Where:** `src-tauri/src/main.rs:2424-2437` (the Tauri builder's plugin set).
> * **Defect:** nothing prevents a second instance of ChessFable from starting. Both instances resolve
>   the same `AppDataDir`, the same path-authority registry
>   (`src-tauri/src/main.rs:2469`, `path-authority.json`) and the same webview data directory, and
>   therefore the same `localStorage`/`sessionStorage`. Every in-process guard in the codebase — the
>   per-resource mutexes, the operation registry, the planned per-deck lock of
>   `tasks/plans/2026-09-22-practice-durable-storage.md` — is scoped to one process and does not hold
>   across two.
> * **Why it matters:** the failure modes are silent rather than loud. Two instances appending to the
>   same newest review shard can lose one entry; two startup path-owner reconciliations can race; two
>   engine registries can disagree about which processes exist. Each subsystem currently states "one
>   process" as an assumption, and the assumption is not enforced anywhere.
> * **Open question:** is the answer `tauri-plugin-single-instance` (focus the running window and
>   exit), or a lock file under the app-data directory with an explicit "another instance is running"
>   message, or per-resource cross-process locking? The first is the smallest and matches what the
>   code already assumes; the third is the only one that would actually support two windows, and
>   nothing in the product asks for that. The answer decides whether every "one process" assumption in
>   the codebase becomes true or has to be replaced.
> * **Another consequence, found 2026-09-27 by `review-correctness` in the cumulative review for
>   `f-20260912-01`:** the Lichess credential registry (`src-tauri/src/credentials.rs`) is also a
>   one-process assumption. If two instances start with the same registry, instance A adds an
>   account, and instance B then adds one from its stale in-memory registry, B's journal replaces the
>   file without A's record. A's keyring secret then has no record a fresh startup can load: an
>   orphaned bearer token, the class `f-20260912-01` closed for a replaced directory. The
>   directory-identity checks added there cannot see it, because both instances write the same inode.
>   A single-instance guard would remove this case along with the others listed here.

## Threat model and non-goals

* **In scope (accidental):** the same OS user launches ChessFable a second time while it runs —
  from the application menu, a terminal, `pnpm tauri dev` / bare `cargo run` under the release
  identifier, or a freshly installed build launched while the previous one is still open — on
  Linux, macOS or Windows, including a crash of the first process (the lock must not outlive it).
  Every one of these holds between builds that **both** carry the guard.
* **In scope (environment):** a filesystem whose advisory locks are unsupported, and a desktop
  session without a D-Bus session bus. Neither may crash the app or make it unusable.
* **Not in scope — one-time rollout transition (amended r3, issue I10):** a process of a build from
  before this change never takes `instance.lock`, so the first guarded launch while such a process
  is still running is unguarded exactly as today; a lock nobody took cannot be observed, and no
  other state the old build holds identifies it. Once that process ends, every later pair is
  guarded. Named limit, not a mechanism (build §4: a hazard equal to the pre-change system).
* **Not in scope:** an adversary of the same UID who deletes or replaces the lock file, or runs a
  patched binary; two processes that resolve *different* app-data directories (different HOME or
  XDG variables, the `.dev` identifier) but share a user-picked directory outside app data — those

## Approach

### O1 — One advisory-lock primitive in `infra::fs`

MANDATE: "Every in-process guard in the codebase … is scoped to one process and does not hold
across two." The guard needs a cross-process lock; the codebase already has two hand-written copies
of the same primitive (P8), so the third use extracts it (rule 11, extract at the second copy).

* `infra/fs.rs` gains one function that takes an exclusive advisory lock on an already open regular
  file, with a blocking and a non-blocking mode, on unix (`rustix::fs::flock`) and Windows
  (`LockFileEx`, `LOCKFILE_EXCLUSIVE_LOCK`, plus `LOCKFILE_FAIL_IMMEDIATELY` in non-blocking mode,
  whole-file range as today). Not `std::fs::File::try_lock` (P9).
* Its result distinguishes three outcomes: **acquired**; **held elsewhere** (unix `EWOULDBLOCK`/`EAGAIN`;
  Windows `ERROR_LOCK_VIOLATION`); and **error** — with the unsupported-locking errors (unix
  `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`; Windows `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`)
  classifiable by the caller as "this filesystem cannot lock". `ENOLCK` is **not** in that set:
  `flock(2)` defines it as the kernel running out of memory for lock records, which happens on a
  lock-capable filesystem, so it stays an ordinary error (startup error in O2). The lock is released by dropping the
  file (the kernel releases it on every process exit, including a crash).
* `practice.rs` `AdvisoryDeckLock::acquire` and the macOS engine-launch sweep's non-blocking probe
  route through it, behaviour unchanged (blocking for practice; held-elsewhere ⇒ `continue` in the
  sweep, any other error logged and skipped as today). The `O_EXLOCK` atomic create-and-lock of the
  launch root stays as is (P8: a different primitive, and splitting it would reopen the window
  between create and lock).

### O2 — The instance lock on the application-data directory

MANDATE: "Both instances resolve the same `AppDataDir` … The answer decides whether every 'one
process' assumption in the codebase becomes true."

* `infra/path_authority/mod.rs`, next to `AppDataDir`, gains an instance-lock type acquired from an
  `&AppDataDir`: it opens or creates the regular leaf `instance.lock` at the app-data root through the
  retained descriptor (P10; `NOFOLLOW`, `0600`) and takes the O1 lock **non-blocking**.
* Outcomes and their failure semantics:
  * acquired → returns a guard that owns the file; the caller keeps it alive for the whole process
    (managed state), so the lock is held until the process ends and released by the kernel then;
  * held elsewhere → "another ChessFable process owns this application-data directory" (O4);
  * locking unsupported on this filesystem → the app starts **without** the guard and logs one
    warning naming the condition — no worse than today, and never a refusal to start;
  * any other open or lock error → a startup error, mapped and logged exactly like the other
    app-data acquisition failures in `.setup` (fixed renderer-safe text, diagnostic in the log).
* The instance-lock admission returns `Result<Admission, Error>` with exactly three successful
  variants — owned guard, unguarded, held elsewhere. Every ordinary open or lock failure returns
  `Err`, with its diagnostic logged once. The admission maps the O1 result to these outcomes **and
  emits each outcome's log line itself** — unsupported: exactly one `warn`; held elsewhere: the O4 refusal
  line; other error: the app-data failure log — so `.setup` only matches the returned outcome and
  has no logging of its own to forget. Its unit tests drive every lock result (real files for
  acquired and held elsewhere; `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`, `ENOLCK` and another error injected
  through the function's lock-result input) under `crate::error::LogCaptureScope` and assert the
  outcome and the captured lines: unsupported → unguarded admission plus exactly one warning;
  `ENOLCK` and any other error → an error and no unguarded admission; held elsewhere → refusal plus
  the refusal line; an open failure of the leaf (for example a symlinked `instance.lock`) → an
  error. The O3 scan pins what `.setup` does with each outcome.
* The leaf is never deleted or truncated: unlinking a lock file lets a later process lock a new
  inode while an older one still holds the old (the classic advisory-lock race). Its content is
  empty and unused.
* The leaf sits at the app-data root, not in an `AppOwnedDefaultRoot` subdirectory; nothing
  enumerates the app-data root (P10, `d-20260905-02` governs the closed set of *directories*).
* Why the app-data directory and not `app_config_dir` or the bundle identifier: the shared state the
  MANDATE names — `AppDataDir`, the credentials registry, the webview storage — and the config
  directory all derive from the same identifier and user environment; the app-data directory is the
  one this code already acquires through a retained descriptor. An identifier key would refuse
  `verify:app` while the daily app runs (P6).

### O3 — Acquire before any shared state and before the webview exists

MANDATE: "the same webview data directory, and therefore the same `localStorage`/`sessionStorage`";
"two startup path-owner reconciliations can race".

* `src-tauri/tauri.conf.json`: the main window gets `"create": false` (P2, P3). Nothing else in the
  window config changes.
* The admission statement executes unconditionally and directly inside `.setup`, immediately after
  app-data acquisition. It maps errors to fixed renderer-safe text (no second log line: the
  admission already logged the diagnostic) and terminates with `?` — the same `.map_err(..)?` shape
  as the app-data step (`main.rs:2329-2333`) — before matching the three
  successful variants or initialising credentials, path authority or the window. A setup `Err`
  ends the process before anything else runs (Tauri 2.10.2 `app.rs:1298`).
* `.setup` order becomes: `AppDataDir::for_app` (the existing single call, P11) → instance lock (O2)
  → on "held elsewhere" the O4 path and `return Ok(())` with nothing else initialised → credentials
  → path authority → events → sound → CLI plugin → **create the main window from
  `app.config().app.windows[0]`** (P3), last, so the renderer can reach no command before every
  backend state the setup installs exists.
* A failure to build the window is a setup error like any other (`?`), as it is today inside
  Tauri's own `setup`.
* The P11 source-scan tests stay green without being weakened: no second `AppDataDir::for_app(`,
  credentials still before the authority, no `target_os = "linux"` cfg inside the closure. Add
  source-scan assertions (in the existing style next to
  `credential_initialization_precedes_path_authority_open`) that, inside `.setup`:
  the complete admission statement sits at setup level (not in a nested closure or a conditional
  fallback), immediately follows the `AppDataDir::for_app(` statement, and ends with `?` before
  the next statement, so propagation cannot become a fallback without failing the scan;
  the match after it names exactly the three successful variants;
  the instance-lock acquisition precedes the credential initialisation; the held-elsewhere arm ends in `return Ok(())` **before** the first
  `.credentials` call and the first `PathAuthority::open_for_app(`; the unsupported arm does not
  return; and the window is created from the config after the CLI plugin registration. Identical
  registry bytes cannot prove the order (credential initialisation rewrites the registry
  deterministically, `credentials.rs:313`), so the order is proven by the scan.
* A unit test reads `src-tauri/tauri.conf.json` (`include_str!`) and asserts `app.windows[0].create`
  is `false`: reverting that line would let Tauri build the webview before `.setup` (P2) while every
  other assertion stays green.
* Plugins initialised during `build` (P2) run before the guard. Measured: window-state only reads
  there (P4); the log plugin opens its file (P12). Both are named limits below, not shared-state
  corruption: the refused process exits without running the window-state exit save (O4), and its
  two or three log lines are appended to the shared log file.

### O4 — The refused launch: tell the user, then exit without exit hooks

MANDATE: "a lock file under the app-data directory with an explicit 'another instance is running'
message".

* On "held elsewhere", the O2 admission has logged one line at `warn` ("another ChessFable process
  holds the application data directory; this launch exits") — the line `verify:app` asserts — and
  `.setup` shows a native message dialog through the already registered dialog plugin (`MessageDialogBuilder::show`,
  asynchronous, no parent window; P2: the event loop is running at `Ready`), English text:
  title "ChessFable is already running", body "ChessFable is already open. Switch to its window to
  continue." The dialog's callback terminates the process with `std::process::exit(0)`.
* `std::process::exit` and not `AppHandle::exit`: the refused process owns nothing (no credentials,
  no authority, no engines, no sound server), and `RunEvent::Exit` would run the window-state save
  (P4), rewriting the running instance's window-state file from a stale cache.
* No window, no webview and no renderer are created for the refused process (O3).

### O5 — State the invariant where the next session looks

MANDATE: "Each subsystem currently states 'one process' as an assumption, and the assumption is not
enforced anywhere."

* `.claude/rules/async-resource-invariants.md`, section "What this means concretely", gains one
  bullet: one process per application-data directory is enforced by the instance lock acquired
  at the start of `.setup`; in-process registries over app-data state (credentials, path authority,
  engine images, practice) may rely on it; it does not cover a user-picked directory shared by two
  *different* app-data directories (release and `.dev` identifiers, a different HOME), nor a
  filesystem without advisory locks (logged at startup).

## Decisions and trade-offs

* **Lock file on the app-data directory, not `tauri-plugin-single-instance`.** The plugin's key is
  the bundle identifier, not the shared directory: it would refuse `verify:app` (temporary HOME,
  same session bus) whenever the daily app is open and focus the daily window instead (P6). It is
  fail-open in three measured ways (P5), so a lock would be needed underneath it anyway. Its
  remaining benefit — focusing the running window and forwarding argv — carries nothing today
  (P7). It would also require a second dependency tree on Linux (zbus 5 is already present
  transitively) and a `tauri` 2.10-compatible older plugin line (2.4.x), or a `tauri` bump to 2.12.
* **Per-resource cross-process locking: rejected.** The finding itself notes it is the only option
  that would support two windows and that nothing in the product asks for that; it would have to
  replace every one-process assumption (credentials journal, path-authority snapshot, engine
  supervisor, operation registry, webview storage) instead of making it true.
* **Refusal UX: message dialog, then exit.** Precedent P13 (the app tells the user when it cannot
  start safely). Focusing the running window would need an inter-process channel keyed on the
  app-data directory on three platforms; the only off-the-shelf one is the plugin rejected above.
* **Unsupported locking ⇒ start unguarded with a warning,** not refuse: refusing would make the app
  unusable on such a filesystem, where today it works; unguarded is exactly today's behaviour.
* **Window created last in `.setup` via `create: false`.** The alternative — acquire in a plugin
  registered first (runs during `build`) — cannot show a dialog (the event loop is not running yet)
  and still leaves the webview to be created by Tauri before the app's `.setup`.
* **English dialog text.** The native process has no i18next catalogue before the renderer starts,
  and the refused process must not start a renderer (O3). Named limit.

### plan-r5.md

# Plan: one ChessFable process per application-data directory

## Goal

Make the "one process" assumption that every native registry, journal and in-process lock already
relies on true, by refusing a second process that would share the same application-data directory
before it reads or writes any shared per-user state or creates its webview. The refused launch
tells the user that ChessFable is already running and exits.

## MANDATE

Verbatim from `f-20260922-07` (`tasks/findings.md`):

> ### The application has no single-instance guard, so two instances share one app-data directory
>
> * **Where:** `src-tauri/src/main.rs:2424-2437` (the Tauri builder's plugin set).
> * **Defect:** nothing prevents a second instance of ChessFable from starting. Both instances resolve
>   the same `AppDataDir`, the same path-authority registry
>   (`src-tauri/src/main.rs:2469`, `path-authority.json`) and the same webview data directory, and
>   therefore the same `localStorage`/`sessionStorage`. Every in-process guard in the codebase — the
>   per-resource mutexes, the operation registry, the planned per-deck lock of
>   `tasks/plans/2026-09-22-practice-durable-storage.md` — is scoped to one process and does not hold
>   across two.
> * **Why it matters:** the failure modes are silent rather than loud. Two instances appending to the
>   same newest review shard can lose one entry; two startup path-owner reconciliations can race; two
>   engine registries can disagree about which processes exist. Each subsystem currently states "one
>   process" as an assumption, and the assumption is not enforced anywhere.
> * **Open question:** is the answer `tauri-plugin-single-instance` (focus the running window and
>   exit), or a lock file under the app-data directory with an explicit "another instance is running"
>   message, or per-resource cross-process locking? The first is the smallest and matches what the
>   code already assumes; the third is the only one that would actually support two windows, and
>   nothing in the product asks for that. The answer decides whether every "one process" assumption in
>   the codebase becomes true or has to be replaced.
> * **Another consequence, found 2026-09-27 by `review-correctness` in the cumulative review for
>   `f-20260912-01`:** the Lichess credential registry (`src-tauri/src/credentials.rs`) is also a
>   one-process assumption. If two instances start with the same registry, instance A adds an
>   account, and instance B then adds one from its stale in-memory registry, B's journal replaces the
>   file without A's record. A's keyring secret then has no record a fresh startup can load: an
>   orphaned bearer token, the class `f-20260912-01` closed for a replaced directory. The
>   directory-identity checks added there cannot see it, because both instances write the same inode.
>   A single-instance guard would remove this case along with the others listed here.

## Threat model and non-goals

* **In scope (accidental):** the same OS user launches ChessFable a second time while it runs —
  from the application menu, a terminal, `pnpm tauri dev` / bare `cargo run` under the release
  identifier, or a freshly installed build launched while the previous one is still open — on
  Linux, macOS or Windows, including a crash of the first process (the lock must not outlive it).
  Every one of these holds between builds that **both** carry the guard.
* **In scope (environment):** a filesystem whose advisory locks are unsupported, and a desktop
  session without a D-Bus session bus. Neither may crash the app or make it unusable.
* **Not in scope — one-time rollout transition (amended r3, issue I10):** a process of a build from
  before this change never takes `instance.lock`, so the first guarded launch while such a process
  is still running is unguarded exactly as today; a lock nobody took cannot be observed, and no
  other state the old build holds identifies it. Once that process ends, every later pair is
  guarded. Named limit, not a mechanism (build §4: a hazard equal to the pre-change system).
* **Not in scope:** an adversary of the same UID who deletes or replaces the lock file, or runs a
  patched binary; two processes that resolve *different* app-data directories (different HOME or
  XDG variables, the `.dev` identifier) but share a user-picked directory outside app data — those
  are different profiles by construction and not the shared state this finding names; two OS users.
* **Frozen with the MANDATE.** Changing this section needs the recorded focused judgment of build §4.

## Approach

### O1 — One advisory-lock primitive in `infra::fs`

MANDATE: "Every in-process guard in the codebase … is scoped to one process and does not hold
across two." The guard needs a cross-process lock; the codebase already has two hand-written copies
of the same primitive (P8), so the third use extracts it (rule 11, extract at the second copy).

* `infra/fs.rs` gains one function that takes an exclusive advisory lock on an already open regular
  file, with a blocking and a non-blocking mode, on unix (`rustix::fs::flock`) and Windows
  (`LockFileEx`, `LOCKFILE_EXCLUSIVE_LOCK`, plus `LOCKFILE_FAIL_IMMEDIATELY` in non-blocking mode,
  whole-file range as today). Not `std::fs::File::try_lock` (P9).
* Its result distinguishes three outcomes: **acquired**; **held elsewhere** (unix `EWOULDBLOCK`/`EAGAIN`;
  Windows `ERROR_LOCK_VIOLATION`); and **error** — with the unsupported-locking errors (unix
  `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`; Windows `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`)
  classifiable by the caller as "this filesystem cannot lock". `ENOLCK` is **not** in that set:
  `flock(2)` defines it as the kernel running out of memory for lock records, which happens on a
  lock-capable filesystem, so it stays an ordinary error (startup error in O2). The lock is released by dropping the
  file (the kernel releases it on every process exit, including a crash).
* `practice.rs` `AdvisoryDeckLock::acquire` and the macOS engine-launch sweep's non-blocking probe
  route through it, behaviour unchanged (blocking for practice; held-elsewhere ⇒ `continue` in the
  sweep, any other error logged and skipped as today). The `O_EXLOCK` atomic create-and-lock of the
  launch root stays as is (P8: a different primitive, and splitting it would reopen the window
  between create and lock).

### O2 — The instance lock on the application-data directory

MANDATE: "Both instances resolve the same `AppDataDir` … The answer decides whether every 'one
process' assumption in the codebase becomes true."

* `infra/path_authority/mod.rs`, next to `AppDataDir`, gains an instance-lock type acquired from an
  `&AppDataDir`: it opens or creates the regular leaf `instance.lock` at the app-data root through the
  retained descriptor (P10; `NOFOLLOW`, `0600`) and takes the O1 lock **non-blocking**.
* Outcomes and their failure semantics:
  * acquired → returns a guard that owns the file; the caller keeps it alive for the whole process
    (managed state), so the lock is held until the process ends and released by the kernel then;
  * held elsewhere → "another ChessFable process owns this application-data directory" (O4);
  * locking unsupported on this filesystem → the app starts **without** the guard and logs one
    warning naming the condition — no worse than today, and never a refusal to start;
  * any other open or lock error → a startup error, mapped and logged exactly like the other
    app-data acquisition failures in `.setup` (fixed renderer-safe text, diagnostic in the log).
* The instance-lock admission returns `Result<Admission, Error>` with exactly three successful
  variants — owned guard, unguarded, held elsewhere. Every ordinary open or lock failure returns
  `Err`, with its diagnostic logged once. The admission maps the O1 result to these outcomes **and
  emits each outcome's log line itself** — unsupported: exactly one `warn`; held elsewhere: the O4 refusal
  line; other error: the app-data failure log — so `.setup` only matches the returned outcome and
  has no logging of its own to forget. Its unit tests drive every lock result (real files for
  acquired and held elsewhere; `EOPNOTSUPP`/`ENOTSUP`, `ENOSYS`, `ENOLCK` and another error injected
  through the function's lock-result input) under `crate::error::LogCaptureScope` and assert the
  outcome and the captured lines: unsupported → unguarded admission plus exactly one warning;
  `ENOLCK` and any other error → an error and no unguarded admission; held elsewhere → refusal plus
  the refusal line; an open failure of the leaf (for example a symlinked `instance.lock`) → an
  error. The O3 scan pins what `.setup` does with each outcome.
* The leaf is never deleted or truncated: unlinking a lock file lets a later process lock a new
  inode while an older one still holds the old (the classic advisory-lock race). Its content is
  empty and unused.
* The leaf sits at the app-data root, not in an `AppOwnedDefaultRoot` subdirectory; nothing
  enumerates the app-data root (P10, `d-20260905-02` governs the closed set of *directories*).
* Why the app-data directory and not `app_config_dir` or the bundle identifier: the shared state the
  MANDATE names — `AppDataDir`, the credentials registry, the webview storage — and the config
  directory all derive from the same identifier and user environment; the app-data directory is the
  one this code already acquires through a retained descriptor. An identifier key would refuse
  `verify:app` while the daily app runs (P6).

### O3 — Acquire before any shared state and before the webview exists

MANDATE: "the same webview data directory, and therefore the same `localStorage`/`sessionStorage`";
"two startup path-owner reconciliations can race".

* `src-tauri/tauri.conf.json`: the main window gets `"create": false` (P2, P3). Nothing else in the
  window config changes.
* The admission statement executes unconditionally and directly inside `.setup`, immediately after
  app-data acquisition. It maps errors to fixed renderer-safe text (no second log line: the
  admission already logged the diagnostic) and terminates with `?` — the same `.map_err(..)?` shape
  as the app-data step (`main.rs:2329-2333`) — before matching the three
  successful variants or initialising credentials, path authority or the window. A setup `Err`
  ends the process before anything else runs (Tauri 2.10.2 `app.rs:1298`).
* `.setup` order becomes: `AppDataDir::for_app` (the existing single call, P11) → instance lock (O2)
  → on "held elsewhere" the O4 path and `return Ok(())` with nothing else initialised → credentials
  → path authority → events → sound → CLI plugin → **create the main window from
  `app.config().app.windows[0]`** (P3), last, so the renderer can reach no command before every
  backend state the setup installs exists.
* A failure to build the window is a setup error like any other (`?`), as it is today inside
  Tauri's own `setup`.
* The P11 source-scan tests stay green without being weakened: no second `AppDataDir::for_app(`,
  credentials still before the authority, no `target_os = "linux"` cfg inside the closure. Add
  source-scan assertions (in the existing style next to
  `credential_initialization_precedes_path_authority_open`) that, inside `.setup`:
  the complete admission statement sits at setup level (not in a nested closure or a conditional
  fallback), immediately follows the `AppDataDir::for_app(` statement, and ends with `?` before
  the next statement, so propagation cannot become a fallback without failing the scan;
  the match after it names exactly the three successful variants;
  the instance-lock acquisition precedes the credential initialisation; the held-elsewhere arm ends in `return Ok(())` **before** the first
  `.credentials` call and the first `PathAuthority::open_for_app(`; the unsupported arm does not
  return; and the window is created from the config after the CLI plugin registration. Identical
  registry bytes cannot prove the order (credential initialisation rewrites the registry
  deterministically, `credentials.rs:313`), so the order is proven by the scan.
* A unit test reads `src-tauri/tauri.conf.json` (`include_str!`) and asserts `app.windows[0].create`
  is `false`: reverting that line would let Tauri build the webview before `.setup` (P2) while every
  other assertion stays green.
* Plugins initialised during `build` (P2) run before the guard. Measured: window-state only reads
  there (P4); the log plugin opens its file (P12). Both are named limits below, not shared-state
  corruption: the refused process exits without running the window-state exit save (O4), and its
  two or three log lines are appended to the shared log file.

### O4 — The refused launch: tell the user, then exit without exit hooks

MANDATE: "a lock file under the app-data directory with an explicit 'another instance is running'
message".

* On "held elsewhere", the O2 admission has logged one line at `warn` ("another ChessFable process
  holds the application data directory; this launch exits") — the line `verify:app` asserts — and
  `.setup` shows a native message dialog through the already registered dialog plugin (`MessageDialogBuilder::show`,
  asynchronous, no parent window; P2: the event loop is running at `Ready`), English text:
  title "ChessFable is already running", body "ChessFable is already open. Switch to its window to
  continue." The dialog's callback terminates the process with `std::process::exit(0)`.
* `std::process::exit` and not `AppHandle::exit`: the refused process owns nothing (no credentials,
  no authority, no engines, no sound server), and `RunEvent::Exit` would run the window-state save
  (P4), rewriting the running instance's window-state file from a stale cache.
* No window, no webview and no renderer are created for the refused process (O3).

### O5 — State the invariant where the next session looks

MANDATE: "Each subsystem currently states 'one process' as an assumption, and the assumption is not
enforced anywhere."

* `.claude/rules/async-resource-invariants.md`, section "What this means concretely", gains one
  bullet: one process per application-data directory is enforced by the instance lock acquired
  at the start of `.setup`; in-process registries over app-data state (credentials, path authority,
  engine images, practice) may rely on it; it does not cover a user-picked directory shared by two
  *different* app-data directories (release and `.dev` identifiers, a different HOME), nor a
  filesystem without advisory locks (logged at startup).

## Decisions and trade-offs

* **Lock file on the app-data directory, not `tauri-plugin-single-instance`.** The plugin's key is
  the bundle identifier, not the shared directory: it would refuse `verify:app` (temporary HOME,
  same session bus) whenever the daily app is open and focus the daily window instead (P6). It is
  fail-open in three measured ways (P5), so a lock would be needed underneath it anyway. Its
  remaining benefit — focusing the running window and forwarding argv — carries nothing today
  (P7). It would also require a second dependency tree on Linux (zbus 5 is already present
  transitively) and a `tauri` 2.10-compatible older plugin line (2.4.x), or a `tauri` bump to 2.12.
* **Per-resource cross-process locking: rejected.** The finding itself notes it is the only option
  that would support two windows and that nothing in the product asks for that; it would have to
  replace every one-process assumption (credentials journal, path-authority snapshot, engine
  supervisor, operation registry, webview storage) instead of making it true.
* **Refusal UX: message dialog, then exit.** Precedent P13 (the app tells the user when it cannot
  start safely). Focusing the running window would need an inter-process channel keyed on the
  app-data directory on three platforms; the only off-the-shelf one is the plugin rejected above.
* **Unsupported locking ⇒ start unguarded with a warning,** not refuse: refusing would make the app
  unusable on such a filesystem, where today it works; unguarded is exactly today's behaviour.
* **Window created last in `.setup` via `create: false`.** The alternative — acquire in a plugin
  registered first (runs during `build`) — cannot show a dialog (the event loop is not running yet)
  and still leaves the webview to be created by Tauri before the app's `.setup`.
* **English dialog text.** The native process has no i18next catalogue before the renderer starts,
  and the refused process must not start a renderer (O3). Named limit.

## Decided autonomously

Recorded by the adopting session through `./scripts/findings.py record-decision`:

1. **Q:** Which mechanism enforces one ChessFable process per profile — `tauri-plugin-single-instance`,
   an app-data lock file with a message, or per-resource cross-process locking?
   **Chosen:** an OS advisory lock on `<app_data>/instance.lock`, taken non-blocking at the start of
   `.setup` before credentials, path authority and window creation (main window `create: false`,
   built last in `.setup`); a refused launch logs, shows a native "already running" dialog and exits
   with `std::process::exit(0)`. **Rejected:** the single-instance plugin (identifier-keyed — refuses
   `verify:app` beside the daily app; fail-open on no bus, socket race and mutex race; forwards argv

   enforces every one-process assumption; supports two windows nobody asked for). **Reason:** the lock
   is keyed exactly on the shared state, is released by the kernel on any exit including a crash, and
   reuses primitives the crate already has. **Reversal path:** to focus the running window instead of
   showing a dialog, add a forwarding channel keyed on the app-data directory on top of the lock (the
   lock stays the authority); removing the guard is reverting the `.setup` acquisition and the
   `create: false` line.
2. **Q:** What does the app do on a filesystem without advisory locks? **Chosen:** start unguarded and
   log a warning. **Rejected:** refuse to start. **Reason:** refusal would turn a theoretical race into
   a guaranteed outage on that filesystem; unguarded is today's behaviour. **Reversal path:** change the
   unsupported branch in the instance-lock type to the refusal path.
3. **Q:** Where does the lock primitive live? **Chosen:** one function in `src-tauri/src/infra/fs.rs`,

## Risks / open questions

* **The dialog itself is native GTK/AppKit/Win32 chrome**, which `verify:app` cannot see (WebDriver
  sees the page only). The automated proof covers refusal, non-initialisation and exit-on-kill; that
  the dialog renders and its button exits the process is the one manual check left to Felix
  (`.claude/skills/verify-ui/SKILL.md`, "native GTK chrome").
* **A dialog that can never be shown** (no display reachable for the second process) would leave an
  invisible process waiting for the callback. It holds no lock and owns no state, so it is harmless
  but lingers; the plan accepts it as a named limit rather than adding a timer.
* **Log interleaving:** the refused process appends a few lines to the shared `en-croissant.log`
  before exiting (P12). Appends are atomic per line on the platforms in scope; rotation by the log
  plugin is the theoretical edge and costs at most diagnostic lines.
* **macOS:** LaunchServices already activates the running app for a Finder/Dock launch, so the guard
  matters there for `open -n` and terminal launches; its sweep change compiles only on macOS
  (the `rust-macos-test` CI job is its only compiler; Phase 1 names that proof).
