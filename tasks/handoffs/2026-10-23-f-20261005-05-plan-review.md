### I1 — successive upgrades overtake incomplete owner application

Witness: correctness r1, raw prefixed finding ordinal 1, blocker, confidence 91. No dependencies or withdrawal.

Raw claim: Successive upgrades lack an ordering contract across owner receipts. Let A→B commit the engine list while a player save fails. Then B→C commits, but skips that player because its snapshot still contains A, recording a skip receipt. Recovering A→B later changes the player to B, leaving the engine list at C permanently. Require per-engine application ordering through unfinished owner steps, or dependency-aware reconciliation before recording a skip.

Disposition: Fix. Root verified independent player saves at src/components/engines/UpgradeEngineModal.tsx:77-125 and engine-list-only serialization at src/state/atoms.ts:295-328. This violates the mandate's complete upgrade application under the frozen changed-selection/repeated-reload threat model.

Correction in plan-r2: O2 orders all unfinished application per immutable engine UUID through owner saves, cleanup and acknowledgement. Native admission refuses a successive upgrade until the first is complete or safely superseded for all remaining steps. Retry resumes the earlier record. Unrelated engine work and authoritative removal/preferences remain independent. O4 proves A→B→C convergence. This adds no unrelated product behavior.

### I2 — retirement replay disables a newly selected old binary

Witness: engine-protocol r1, raw prefixed finding ordinal 1, blocker, confidence 90. No dependencies or withdrawal.

Raw claim: Retirement replay is not fenced against a newer binary selection. Concrete sequence: upgrade A→B commits the engine list, retirement fails, the user upgrades B→A and starts analysis, then recovery retries the unfinished A→B retirement. EngineSupervisor::retire_engine_binary reinserts A's tombstone and scans currently matching actors, terminating the newly selected A and refusing further searches. Its generation checks protect captured actors within one invocation, not against a later stale invocation. Require recovery to retain exact cleanup generations and prevent obsolete workflows from changing current binary admission. Add the A→B→A replay case to O4.

Disposition: Fix. Root verified the per-invocation tombstone transition and actor scan at src-tauri/src/engine/process.rs:2794-2814. This violates upgrade completion without invalidating current user selection. The threat model already includes changed engine selection and native cleanup across reload.

Correction in plan-r2: O2 records one original admission transition and exact cleanup generations. A retry observes/retries only retained generation cleanup and never repeats broad tombstone changes or captures new actors. Phase 1 includes a narrowly scoped supervisor extension. O4 requires actor survival and further admission after reselecting A.

## Approach

### O1 — Native work retains a recoverable completion identity

Use the existing operation ownership boundary for a narrow, typed completion record for these workflows. Atomically admit an immutable request and unique operation ID before starting any effect. A record identifies its owning webview, progress identity, target identity and workflow kind. A lookup from the replacement document of that same webview can rejoin running work or read its terminal result. Repeated admission of the same operation joins or returns the same result, never repeats an effect. Different requests cannot reuse one identity. Native results carry opaque handles, safe typed outcomes and public metadata only.

Retain running and unacknowledged records under a fixed cap no larger than the existing accepted-operation cap of 128, with bounded payload fields. Never evict pending application work to make room. Refuse new admission before side effects when full. Acknowledgement removes only the exact owner's fully observed record and releases its retained resources. Cancellation and failed admission have explicit terminal cleanup. Shutdown seals admission, cancels pre-commit work and drains accepted tails using existing ownership. No second process, timer service or durable generic queue is added. Reuse this completion contract for engines and accounts rather than duplicating it.

### O2 — Engine installation has one resumable application path

Capture Add versus Upgrade intent, catalog identity and a preallocated Add UUID or Upgrade engine UUID plus expected old handle before transfer. Native completion owns archive verification, publication/adoption, installed-handle registration and supervised configuration collection. Reuse the existing authority and configuration cores. Retain the installed handle/configuration with the intent until renderer application is acknowledged, protecting it against startup owner pruning and catalog collection. Retain old-binary cleanup authority for upgrades until retirement completes.

A single application coordinator serves both live callers and startup recovery. It joins O1 after the previous-document sweep, account sanitization and required path-owner initialization, and applies terminal engine work before ordinary engine edits can race its startup snapshot. Work still running is observed without blocking the whole app on a network transfer. Completion observation uses a registered typed event or an existing subscription with snapshot-after-subscribe reconciliation so completion during subscription cannot be lost. Dispose document listeners on exit and fence stale callbacks.

Persist engine-list application and its operation receipt atomically in the same serialized owner value. Preserve receipt evidence across all subsequent edits until native acknowledgement is known. Do the same independently for each player owner when an upgrade changes it. Introduce a bounded versioned owner envelope only at this dedicated storage boundary, read legacy compressed/JSON values, and route every reader, migration, startup inspection and writer of the three keys through the same decoder/encoder. Keep existing serializer and compression. Malformed or unreadable values refuse recovery writes and retain native work, rather than being replaced by a clean fallback. Receipt pruning is based on a native snapshot of live pending IDs and cannot lose evidence before acknowledgement. Each owner has at most 128 pending receipts. No tokens, native paths or executable bytes enter storage.

An Add receipt prevents a repeated append even if the user later removed that engine. An Upgrade applies only to the intended UUID and expected old binary, preserves current user preferences, and never restores a deleted or superseded target. Player snapshots are refreshed only when their current engine identity and old binary still match and the live engine target remains compatible, retaining newer selections/settings. Each per-owner receipt distinguishes already applied work from work skipped because its target moved on. Engine-list save precedes old-binary retirement and player updates, following the shipped order. Native acknowledgement waits for every required application/skip receipt and retirement outcome. A failed save or retirement leaves the unfinished step recoverable, preserves committed steps and uses the existing localized error path. An existing Install/Upgrade retry rejoins pending application rather than starting another transfer.

Unfinished upgrade application is ordered per immutable engine UUID through all owner writes and cleanup, including failures and reloads. Native admission refuses a second upgrade of that UUID until the first workflow has completed or recorded a safe superseded disposition for every remaining step. The UI reflects that pending state and routes retry to the first workflow. Other engines remain independent. This prevents a partly applied A→B from running after B→C. Removal and unrelated user preference/selection edits remain authoritative and are checked before a pending step is applied.

Retirement records the original one-shot binary-admission transition and exact cleanup generations under its native workflow identity. Reconnecting or retrying a failed cleanup resumes only those retained generations and their immutable outcomes. It does not call the broad retired/current transition again, reinsert an old executable tombstone, clear a newer tombstone, or capture newly launched actors. If the engine was subsequently removed or selected another binary, preserve that latest admission state while still observing cleanup for already captured generations. This includes A→B, a later user selection of A, and recovery of an earlier failed retirement. Reuse the existing supervisor's generation cleanup ownership, extending its narrowly scoped workflow entry point if necessary.

Explicit Cancel keeps the existing truthful commit gate: a successful cancellation prevents publication/application, and a post-commit request reports that cancellation lost. Modal unmount may cancel only while cancellation can win and cannot silently abandon an admitted post-commit application. A document reload itself does not cancel accepted work.
