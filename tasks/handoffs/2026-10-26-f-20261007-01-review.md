# Plan: Delete a registered database whose primary is already missing

## Goal

A registered database whose primary file is already gone, while the stored parent directory is still the same directory, can be deleted. The command removes the sidecars that the existing deletion rules allow, prunes the registry entry, and returns success when nothing further fails. The same command still refuses to prune or unlink when the parent cannot be proved, and it does not change any other database mutation.

## MANDATE

### Deleting a registered database whose primary file is already missing fails resolution and leaves the registry entry behind

* **ID:** f-20261007-01 · **Status:** open · **Area:** db-search · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** eed08af5-58ff-40a1-9aa7-f2b51f9b1321
* **Where:** `delete_database_blocking` (`src-tauri/src/db/mod.rs:2860-2910` at `0e29f068`) calls `resolve_database` → `PathAuthority::database_file_target` (`src-tauri/src/infra/path_authority/mod.rs:7063-7093`), whose `acquire_target` fails when the stored path no longer exists; compare `delete_puzzle_database_blocking` (`src-tauri/src/puzzle.rs`), whose missing-binding arm treats an already-missing puzzle file as deleted and still prunes the registry.
* **Defect:** a database whose primary file vanished outside the app (deleted in a file manager, removable drive gone) cannot be deleted through the app: resolution returns the raw missing-entry error before any `CommittedRemoval` exists, so `remove_database` never runs and the registry entry stays. Puzzle deletion answers the same situation idempotently (success, registry pruned, `d-20261006-25` counts 0 removed entries). `f-20260917-08` made a primary that goes missing *during* the unlink step count as committed for both tails, which leaves this pre-resolution case as the remaining divergence.
* **Why it matters:** the user is told the delete failed for an entry that can never be removed, and the two deletion commands disagree on the same situation (`.claude/rules/async-resource-invariants.md`: one operation type has one error contract).
* **Open question:** should database deletion prune the registry entry when the stored primary is missing — and if so, through which authority operation (resolution for `DatabaseMutate` deliberately acquires and identity-checks the target, `d-20261002-08`), and what of the sidecars (`.ecsi` index, stamp, `-wal`/`-shm`) that may still exist beside the missing primary?
* **Related:** `f-20260917-08` (introduced `CommittedRemoval`; its cumulative review found this, correctness lens); `d-20261006-24`, `d-20261006-25`, `d-20261002-08`.
* **Found by:** the `f-20260917-08` cumulative diff review (Codex correctness and records lenses), source-checked by the orchestrator at the lines above, 2026-10-07.

The filing's line numbers are from `0e29f068` and are not the live sites. Obligations below name symbols. Traced premises cite this base, `385dbbd86e1de541d9bd1adc30338485e09caf22`.

The filing's comparison with puzzle deletion describes the post-resolution missing arm. A puzzle file that is already gone when the command starts still fails `resolve_puzzle`. That comparison is not a second change.

## Threat model and non-goals

The adversary can replace the parent directory or the leaf between the registry write and this delete. The leaf may be absent, a symlink, a different inode at the same name, or a different kind of node. Sidecars may remain beside the missing name. The parent may be unmounted, missing, replaced by another directory, or not writable. A drive that is gone is not proof that this registration's file was deleted.

This plan does not treat an unreachable parent as deletion. It does not follow a symlink. It does not delete a leaf whose identity is not the stored identity. It does not touch a sidecar whose leaf name is not the one this database name produces in the proved parent.

Round 1 freezes this adversary. A later round may narrow it only by the review procedure.

## Approach

### Recover only a proved-absent primary

`delete_database_blocking` is the only caller. The new arm runs only when `resolve_database` returns `is_missing_entry`. `Conflict` from `guard_database`, a missing collection cache recreated by `ensure_database`, and every other error return unchanged. Do not change `allows_missing_leaf`, `DatabaseMutate`, `validate_target`, or `PathOperation`. Do not add a renderer-visible operation.

The recovery function lives on `PathAuthority`, outside `delete_database_blocking`, so the blocking function's source does not gain a forbidden substring. Its name must not contain `database_file_target(`. It accepts the handle and the original missing error. It loads the stored `DatabaseMutate` entry and rejects a directory the same way `database_file_target` does.

Outcomes:

- `parent_identity` is `None`: return the original missing error. Do not open a directory and do not prune.
- Otherwise open the parent with `open_parent_no_follow` on the stored path. That is the production deletion descriptor: read-only on Unix, writable on Windows. Do not add a new Unix writable open.
- Parent open `is_missing_entry`: return the original missing error. Do not prune.
- Any other parent-open error, including `PermissionDenied`: return that error. Do not prune.
- `verify_parent_identity` failure: return its `Conflict`. Do not rewrite it into the original missing error, and do not prune or unlink.
- Re-stat the leaf with `entry_identity_at` against that parent. Absence (`is_missing_entry`): assemble one `DatabaseFileTarget` with the stored identity, the stored path, and this parent. Present and the identity equals the stored identity: a distinct present outcome, not an absent target. Present and the identity differs: `Conflict` using the existing "workspace entry is unavailable because its object changed" wording, and delete nothing. `InvalidInput` from the stat: return it and delete nothing. Any other stat error: return it and delete nothing.

`delete_database_blocking` calls this function once. A present outcome calls `resolve_database` exactly once more and then uses that target on the existing live path, including `identity_from_probe` and its sqlite-notadb fallback. If the second resolve also returns `is_missing_entry`, return that error. Do not call the recovery function again and do not write a retry loop.

The absent target is assembled with pathname validation. `probe_current` would map a missing leaf to `Conflict`. The absent arm therefore does not call `identity_from_probe`, `probe_current`, or any other pathname revalidation of the primary.

If the cancellation token is cancelled before recovery opens the parent, return `Cancellation` and do not prune or unlink.

### Join the existing deletion

After a target exists, the rest of `delete_database_blocking` stays one path. `begin_delete` runs on `target.path()`. The absent arm builds `expected_source` as specified below. The live arm keeps the current probe and `IndexSource::from_database_identity`.

The exclusive closure still contains exactly one `unlink_database_files(&target, &expected_source)` between the two `search_cache.invalidate_database(&target)` calls, then `let result = result?;`. `invalidate_database` still appears only inside that closure. The variable is named `expected_source`. `unlink_database_files`'s signature does not change.

On the absent arm the closure does not call `guard_database_mutation`, because that calls `database_file_target` and fails again on the missing leaf. It calls `guard_database` when a collection service is installed. `Conflict` from that guard returns before unlink, leaves `committed_removal` unset, and does not prune. The live arm still calls `guard_database_mutation` first. The branch sits before the first `invalidate_database`, outside the compact slice that forbids `for` and `while`.

`remove_database` and `committed_removal.finish()` stay where they are. Success is `Ok`. A registry or later sidecar failure stays the existing post-commit mapping. No new `Error` variant and no new renderer category (`d-20261002-08`).

### Sidecar provenance without a file probe

The absent `expected_source` uses `target.identity()` as `object`. `revision` and `database_length` are `u64::MAX`. `database_modified_nanos` is `u128::MAX`. It is not `IndexSource::default()` and it is not `from_database_identity`, because those values were not observed from a file. Full equality then fails for a legacy sidecar this app wrote, so that legacy name is kept. Preferred removal still follows object equality, so a preferred sidecar whose object is the stored identity is removed, and an undecodable preferred archive is still removed. `PermissionDenied`, `NotFound`, and other I/O stay inside `unlink_database_files` with their current effects. Stamp, `-wal`, and `-shm` stay name-and-identity removals in that same function and count when removed.

A sidecar with a different leaf name is not a candidate. A file that exists again at this leaf is the present outcome, not this source. Inode reuse can make a preferred sidecar's object equal the stored identity only for the leaf named from this database in the proved parent; that removal is the existing object rule.

### Failure outcomes that keep the registry

No registry removal and no sidecar unlink when recovery returns the original missing error, a parent-open error, a parent-identity `Conflict`, a leaf-identity `Conflict`, or `InvalidInput`. `PartialRemoval` happens only after `unlink_database_files` has returned a `CommittedRemoval`, which requires the primary to be gone or already missing and no earlier sidecar error to have aborted. A primary `Conflict` inside `unlink_database_files` still returns before `CommittedRemoval`. That existing window, where an earlier sidecar removal is not rolled back, stays as it is.

An unmounted volume, a missing parent, or a stored entry with no `parent_identity` keeps the row. The user can retry when the directory is observable again.

### Counts, cancellation, and the renderer

The absent primary does not increment the removed count. Sidecars that this call removes do. `Ok` means no retained error. A later failure uses the truthful count, including 0 when nothing was unlinked (`d-20261006-23`, the same truthfulness as `d-20261006-25`).

Cancellation before the absent observation returns `Cancellation` with the row still present. Cancellation inside `begin_delete` or `reserve_for_deletion` before unlink does the same. Once `unlink_database_files` has started, the existing committed-outcome rule stands.

`delete_database`'s signature stays `Result<(), Error>`. `Ok` already refreshes the renderer through `deleteDatabaseAndInvalidate`. No frontend edit, no binding edit, and no copy change.

verify-ui does not apply. The change is native deletion behavior. verify-ui cannot attach to the WebKitGTK webview, and there is no layout or route change.

## Decisions and trade-offs

### Decided autonomously

Question: when `delete_database` is asked to remove a registered database whose primary is already missing, does the registry entry stay, and what happens to sidecars beside that name?

Chosen: prune and unlink only when the stored parent is still that directory and a no-follow stat shows the leaf is absent. Use the stored object identity as the preferred-sidecar object. Keep a legacy sidecar because its full `IndexSource` was not observed. Remove the stamp and the SQLite sidecars by the existing name-and-identity rules. Return the current error and keep the row when the parent is missing, replaced, unrecorded, or not openable.

Rejected: letting `DatabaseMutate` allow a missing leaf for every mutation; adding `PathOperation::DatabaseDelete`; pruning on every `is_missing_entry` from `resolve_database`, including a gone or replaced parent; using `IndexSource::default()` so a zero legacy source would match; changing puzzle resolution.

Reason: a missing leaf in a proved parent can never be deleted by retrying the current resolve, so the row is stuck. A gone or replaced parent is ambiguous, and unlinking there is the rebind the parent identity check exists to stop. `d-20261002-08` still binds the sidecar order and the provenance checks once a parent descriptor and an expected source exist. `d-20261007-01` states the pre-resolution gap and leaves it undecided. The puzzle command-entry gap is the same resolve shape and is not the stuck database row this finding names.

Reversal path: a later decision may also prune when the parent is unreachable, and that later decision must not unlink sidecars there. Do not supersede `d-20261002-08`, `d-20261006-23`, `d-20261006-25`, or `d-20261007-01`. Record a new decision that governs `f-20261007-01`. The adopting run records it with `./scripts/findings.py record-decision` before implementation. This plan does not edit `tasks/decisions.md`.

The parent-identity mismatch returns `verify_parent_identity`'s `Conflict` rather than the original missing error, so a replaced directory is not reported as a missing file.

## Risks / open questions

A drive that never returns leaves the row in place. That is the reversal path above, not this change.

`ensure_database` still recreates a missing linked collection cache before resolution. The new arm does not see that case. The recreated file then follows the normal delete.

Between the sidecar removals and the primary `remove_entry_at`, a leaf that appears with a different identity still returns `Conflict` before `CommittedRemoval`. Sidecars already removed stay removed. That is the current `unlink_database_files` behavior.

A hand-built legacy sidecar whose four `IndexSource` fields equal the sentinel is removed. A sidecar written by `from_database_identity` does not have those fields.

## Goal

A registered database whose primary file is already gone, while the stored parent directory is still the same directory, can be deleted. ### Deleting a registered database whose primary file is already missing fails resolution and leaves the registry entry behind

* **ID:** f-20261007-01 · **Status:** open · **Area:** db-search · **Root:** - · **Entry:** build · **Blocked:** none

## Threat model and non-goals

The adversary can replace the parent directory or the leaf between the registry write and this delete. The leaf may be absent, a symlink, a different inode at the same name, or a different kind of node. Sidecars may remain beside the missing name. The parent may be unmounted, missing, replaced by another directory, or not writable. A drive that is gone is not proof that this registration's file was deleted.

This plan does not treat an unreachable parent as deletion. It does not follow a symlink. It does not delete a leaf whose identity is not the stored identity. It does not touch a sidecar whose leaf name is not the one this database name produces in the proved parent.

Round 1 freezes this adversary. A later round may narrow it only by the review procedure.

## Approach

### Recover only a proved-absent primary

`delete_database_blocking` is the only caller. The new arm runs only when `resolve_database` returns `is_missing_entry`. `Conflict` from `guard_database`, a missing collection cache recreated by `ensure_database`, and every other error return unchanged. Do not change `allows_missing_leaf`, `DatabaseMutate`, `validate_target`, or `PathOperation`. Do not add a renderer-visible operation.

The recovery function lives on `PathAuthority`, outside `delete_database_blocking`, so the blocking function's source does not gain a forbidden substring. Its name must not contain `database_file_target(`. It accepts the handle and the original missing error. It loads the stored `DatabaseMutate` entry and rejects a directory the same way `database_file_target` does.

Outcomes:

- `parent_identity` is `None`: return the original missing error. Do not open a directory and do not prune.
- Otherwise open the parent with `open_parent_no_follow` on the stored path. That is the production deletion descriptor: read-only on Unix, writable on Windows. Do not add a new Unix writable open.
- Parent open `is_missing_entry`: return the original missing error. Do not prune.
- Any other parent-open error, including `PermissionDenied`: return that error. Do not prune.
- `verify_parent_identity` failure: return its `Conflict`. Do not rewrite it into the original missing error, and do not prune or unlink.
- Re-stat the leaf with `entry_identity_at` against that parent. Absence (`is_missing_entry`): assemble one `DatabaseFileTarget` with the stored identity, the stored path, and this parent. Present and the identity equals the stored identity: a distinct present outcome, not an absent target. Present and the identity differs: `Conflict` using the existing "workspace entry is unavailable because its object changed" wording, and delete nothing. `InvalidInput` from the stat: return it and delete nothing. Any other stat error: return it and delete nothing.

`delete_database_blocking` calls this function once. A present outcome calls `resolve_database` exactly once more and then uses that target on the existing live path, including `identity_from_probe` and its sqlite-notadb fallback. If the second resolve also returns `is_missing_entry`, return that error. Do not call the recovery function again and do not write a retry loop.

The absent target is assembled with pathname validation. `probe_current` would map a missing leaf to `Conflict`. The absent arm therefore does not call `identity_from_probe`, `probe_current`, or any other pathname revalidation of the primary.

If the cancellation token is cancelled before recovery opens the parent, return `Cancellation` and do not prune or unlink.

### Join the existing deletion

After a target exists, the rest of `delete_database_blocking` stays one path. `begin_delete` runs on `target.path()`. The absent arm builds `expected_source` as specified below. The live arm keeps the current probe and `IndexSource::from_database_identity`.

The exclusive closure still contains exactly one `unlink_database_files(&target, &expected_source)` between the two `search_cache.invalidate_database(&target)` calls, then `let result = result?;`. `invalidate_database` still appears only inside that closure. The variable is named `expected_source`. `unlink_database_files`'s signature does not change.

On the absent arm the closure does not call `guard_database_mutation`, because that calls `database_file_target` and fails again on the missing leaf. It calls `guard_database` when a collection service is installed. `Conflict` from that guard returns before unlink, leaves `committed_removal` unset, and does not prune. The live arm still calls `guard_database_mutation` first. The branch sits before the first `invalidate_database`, outside the compact slice that forbids `for` and `while`.

`remove_database` and `committed_removal.finish()` stay where they are. Success is `Ok`. A registry or later sidecar failure stays the existing post-commit mapping. No new `Error` variant and no new renderer category (`d-20261002-08`).

### Sidecar provenance without a file probe

The absent `expected_source` uses `target.identity()` as `object`. `revision` and `database_length` are `u64::MAX`. `database_modified_nanos` is `u128::MAX`. It is not `IndexSource::default()` and it is not `from_database_identity`, because those values were not observed from a file. Full equality then fails for a legacy sidecar this app wrote, so that legacy name is kept. Preferred removal still follows object equality, so a preferred sidecar whose object is the stored identity is removed, and an undecodable preferred archive is still removed. `PermissionDenied`, `NotFound`, and other I/O stay inside `unlink_database_files` with their current effects. Stamp, `-wal`, and `-shm` stay name-and-identity removals in that same function and count when removed.

A sidecar with a different leaf name is not a candidate. A file that exists again at this leaf is the present outcome, not this source. Inode reuse can make a preferred sidecar's object equal the stored identity only for the leaf named from this database in the proved parent; that removal is the existing object rule.

### Failure outcomes that keep the registry

No registry removal and no sidecar unlink when recovery returns the original missing error, a parent-open error, a parent-identity `Conflict`, a leaf-identity `Conflict`, or `InvalidInput`. `PartialRemoval` happens only after `unlink_database_files` has returned a `CommittedRemoval`, which requires the primary to be gone or already missing and no earlier sidecar error to have aborted. A primary `Conflict` inside `unlink_database_files` still returns before `CommittedRemoval`. That existing window, where an earlier sidecar removal is not rolled back, stays as it is.

An unmounted volume, a missing parent, or a stored entry with no `parent_identity` keeps the row. The user can retry when the directory is observable again.

### Counts, cancellation, and the renderer

The absent primary does not increment the removed count. Sidecars that this call removes do. `Ok` means no retained error. A later failure uses the truthful count, including 0 when nothing was unlinked (`d-20261006-23`, the same truthfulness as `d-20261006-25`).

Cancellation before the absent observation returns `Cancellation` with the row still present. Cancellation inside `begin_delete` or `reserve_for_deletion` before unlink does the same. Once `unlink_database_files` has started, the existing committed-outcome rule stands.

`delete_database`'s signature stays `Result<(), Error>`. `Ok` already refreshes the renderer through `deleteDatabaseAndInvalidate`. No frontend edit, no binding edit, and no copy change.

verify-ui does not apply. The change is native deletion behavior. verify-ui cannot attach to the WebKitGTK webview, and there is no layout or route change.

## Decisions and trade-offs

### Decided autonomously

Question: when `delete_database` is asked to remove a registered database whose primary is already missing, does the registry entry stay, and what happens to sidecars beside that name?

Chosen: prune and unlink only when the stored parent is still that directory and a no-follow stat shows the leaf is absent. Use the stored object identity as the preferred-sidecar object. Keep a legacy sidecar because its full `IndexSource` was not observed. Remove the stamp and the SQLite sidecars by the existing name-and-identity rules. Return the current error and keep the row when the parent is missing, replaced, unrecorded, or not openable.

Rejected: letting `DatabaseMutate` allow a missing leaf for every mutation; adding `PathOperation::DatabaseDelete`; pruning on every `is_missing_entry` from `resolve_database`, including a gone or replaced parent; using `IndexSource::default()` so a zero legacy source would match; changing puzzle resolution.

Reason: a missing leaf in a proved parent can never be deleted by retrying the current resolve, so the row is stuck. A gone or replaced parent is ambiguous, and unlinking there is the rebind the parent identity check exists to stop. `d-20261002-08` still binds the sidecar order and the provenance checks once a parent descriptor and an expected source exist. `d-20261007-01` states the pre-resolution gap and leaves it undecided. The puzzle command-entry gap is the same resolve shape and is not the stuck database row this finding names.

Reversal path: a later decision may also prune when the parent is unreachable, and that later decision must not unlink sidecars there. Do not supersede `d-20261002-08`, `d-20261006-23`, `d-20261006-25`, or `d-20261007-01`. Record a new decision that governs `f-20261007-01`. The adopting run records it with `./scripts/findings.py record-decision` before implementation. This plan does not edit `tasks/decisions.md`.

The parent-identity mismatch returns `verify_parent_identity`'s `Conflict` rather than the original missing error, so a replaced directory is not reported as a missing file.

## Risks / open questions

A drive that never returns leaves the row in place. That is the reversal path above, not this change.

`ensure_database` still recreates a missing linked collection cache before resolution. The new arm does not see that case. The recreated file then follows the normal delete.

Between the sidecar removals and the primary `remove_entry_at`, a leaf that appears with a different identity still returns `Conflict` before `CommittedRemoval`. Sidecars already removed stay removed. That is the current `unlink_database_files` behavior.

A hand-built legacy sidecar whose four `IndexSource` fields equal the sentinel is removed. A sidecar written by `from_database_identity` does not have those fields.
