# Plan: Close f-20261002-02 — Unix inode reuse no longer holds

## Goal

Record that `f-20261002-02` no longer holds on the mechanism it names, and have the adopting session close it after the existing primary-pin tests pass. No product source change. No second decision.

## MANDATE

User request, fixed: `/next-finding --pin f-20261002-02 full auto`. Planner contract: PLAN-ONLY. This session cannot close the ledger. The adopting session closes a member this plan names as no longer holding.

Verbatim finding core (`tasks/findings.md`, entry `f-20261002-02`, status open, area `db-search`, entry `build`):

> Parallel tests can collide in the process-global SQLite binding registry through a reused inode.
>
> Where: `src-tauri/src/db/bound_sqlite.rs` (`REGISTRY` is process-global, and `BoundDatabase::acquire` refuses with `Conflict("database is open through another directory")` when any live binding has the same `(dev, ino)` identity under a different parent, `d-20260929-05`); `src-tauri/src/db/repository.rs` (`lru_evicts_the_least_recently_used_idle_entry`, the observed victim).
>
> Defect: the `pnpm gates:push -- --rust` coverage lane on `7f1488f9` (2026-10-02) failed once with `db::repository::tests::lru_evicts_the_least_recently_used_idle_entry` panicking on `Conflict("database is open through another directory")`. All unit tests share one process and therefore one binding registry. If any test keeps a binding alive after its database file is unlinked, the freed inode can be reused by another test's new database in a different tempdir, and that test's acquire is refused.
>
> Open question: is the fix test-side isolation (per-test registry scope, or tests guaranteeing every binding is dropped before their file is removed) or a product-side refinement of the identity key (e.g. also refusing only while the leaf inode is still linked), given that in the product an inode cannot be reused while a SQLite connection holds the leaf open?
>
> Fix shape: first find the binding holder that outlives its file, then decide the question above; a reproduction can force inode reuse by creating and deleting files in a loop on the same filesystem.

Later annotations in the same entry, through the 2026-10-13 witnesses, are fixed mandate evidence of the same mechanism. They add victims and, on 2026-10-12, a second symptom on the same registry: `Conflict("file is open through a SQLite binding")` and a refused sidecar open (`unable to open database file`), because ordinary capability opens consult the same `(dev, ino)` registry. They name the candidate product fix: pin each registration's leaf inode for the registration's lifetime. They do not add a second defect.

## Pickup

The defect no longer holds. `d-20261014-24` chose the product-side pin and landed it for `f-20261014-02` (handled). On Unix a live `creating` or `by_key` identity holds a `File` of that inode, so the kernel cannot reuse the inode for another test database. The open question is already decided. This plan does not re-decide it and does not record a second decision.

Entry stays `build` on the ledger until the adopter closes the finding. PLAN-ONLY cannot `set-header` or `close`. A `not-build` decline would leave the open `entry=build` finding for the next planner. The remaining work is that close, after the proof below. It is not a new design and not a product edit.

## Threat model and non-goals

Threat, frozen: one process, one `REGISTRY`. A registration stays live after its leaf name is unlinked (tempdir drop, test deletion, or an idle cached binding after an external delete). Another create reuses that inode number. Acquire of the new file, or an ordinary open of the new file, is refused because the stale identity is still in `by_key` or `creating`.

Non-goals: a Windows primary-file pin; test-only registry isolation; weakening `Error::Conflict` for genuine distinct keys; a new decision row; co-located joiners; PGN scanning, IPC, renderer storage, chess trees, or engine protocol.
