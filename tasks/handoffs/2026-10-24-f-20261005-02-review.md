P1. Classic `FileRenameInformation` replacement rejects an open destination. `target_stat` stores that handle (`src-tauri/src/infra/fs.rs:2932`). `replace_at_driver` keeps `original` and `current` through `adapter.rename` (`:1195`, `:1273–1279`, `:1354`). Witness: plan r1 finding 1, blocker, confidence 95. Fix: this plan does not implement classic replace. Closed round 2.

P2. The Windows `cargo test` command hides stdout from passing tests, so a printed NTSTATUS would not survive a green run. Witnesses: plan r1 finding 2, blocker, confidence 100; tests r1 finding 1, blocker, confidence 99; platform-semantics r1 finding 1, should-fix, confidence 99. Fix: the test writes `CHESSFABLE_VOLUME_MEASUREMENT`, and the workflow prints that file and fails if a required line is missing. Closed round 2.

P3. A replace status does not measure `FileDispositionInformationEx`. Witnesses: plan r1 finding 3, blocker, confidence 99; tests r1 finding 2, should-fix, confidence 96; platform-semantics r1 finding 2, should-fix, confidence 95. Fix: FAT32 and exFAT each record replace and unlink. Closed round 2.

P4. The mandate says to measure FAT32/exFAT before choosing the contract, and the first draft adopted a fallback with no prior volume measurement. Witness: plan r1 finding 4, blocker, confidence 99. Fix: no classic call, no (a) or (b) decision, finding stays open. Closed round 2.

P5. Root-cause r1 finding 1, should-fix, confidence 100, APPROVED: if both volumes accept `Ex`, injected fallback tests would not be a real rejection. Skip. The revision removed the fallback and the injected hook, so there is no close note that could conflate them.

## Round 2

Closure lenses were review-plan, review-tests, and review-platform-semantics. Each returned REVISE. Each closed the issues it witnessed among P1–P4.

P6. Reading the latest status does not prove the measured call reached `Ex`. `before_write` (`fs.rs:1201`) and the unlink open (`:3604`) can fail first and leave an earlier status in place. Witnesses: plan r2 finding 1, blocker, confidence 97; tests r2 finding 1, blocker, confidence 95. Fix: `note_test_ex_status` bumps a generation, and each measured call must observe exactly one new generation or the test fails and writes no line. Closed round 3.

P7. After a successful unlink, a parent-sync failure is `Err(CommittedDurabilityUncertain)` (`fs.rs:4393–4396`, `error.rs:702–705`) even though the name is gone. The draft said every `Err` keeps the name. Witnesses: plan r2 finding 2, blocker, confidence 99; platform-semantics r2 finding 1, should-fix, confidence 98. Fix: that result is `committed`, with the fresh `Ex` status kept. Closed round 3.

# Plan: Windows classic fallback when a volume rejects POSIX Ex rename or unlink

## Goal

On Windows, keep the current POSIX `Ex` rename and disposition as the first call, and issue one classic `FileRenameInformation` or `FileDispositionInformation` call only when that first call fails with a status Rust documents as "this volume does not support the information class". NTFS live-mapping behaviour stays. A volume that rejects the `Ex` class can still commit an unmapped replace, a no-replace collision, and an unlink. Durability reporting does not gain a new stage.

## MANDATE

* **Filed from:** 61452305-cee2-4bcc-a73a-aff67844bf80
* **Where:** `src-tauri/src/infra/fs.rs` `rename_child` (`NtSetInformationFile(.., FileRenameInformationEx)` with `FILE_RENAME_POSIX_SEMANTICS`, ~`:2602–2666`) and `unlink_posix` (`FileDispositionInformationEx` with `FILE_DISPOSITION_POSIX_SEMANTICS`, ~`:2795–2815`), at base `eec1da2b`.
* **Defect (unmeasured hypothesis):** every Windows atomic replace (search-index generation, downloads, registry persistence, PGN and workspace writes) and every identity-bound unlink goes through those two calls, and neither has a fallback. Non-NTFS volumes are expected to reject the `Ex` classes or the POSIX flags, in particular FAT32/exFAT removable drives and some SMB shares (Rust's `std::fs::rename` gained a fallback for this class). If they do, the app cannot write or delete anything that lives on such a volume, for example a database or workspace the user keeps on a USB stick. If a volume instead accepts the class but ignores the POSIX flag, a replace under any live mapping fails with `ERROR_USER_MAPPED_FILE` (classified `MappedFile`). (a) A typed refusal naming the unsupported volume, or (b) a fallback to `FileRenameInformation` / `FileDispositionInformation`, with which durability and identity guarantees (`d-20260906-03`) and which behaviour under live mappings? This must first be measured on a FAT32/exFAT volume (e.g. a VHD mounted on the Windows runner) and recorded under rule 12b.
* **Why it matters:** Windows is a supported platform (Felix, 2026-09-12). A user-chosen database or workspace on removable or network storage is an ordinary setup, and the failure would surface only as a generic `I/O failure`.

## Threat model and non-goals

Frozen at round 1. A later change needs a focused plan-review judgment.

The environment is a Windows volume the user already selected as a database, workspace, download, or registry location. NTFS is the common case and must keep POSIX semantics. FAT32 and exFAT are the volumes this finding names and the ones the Windows job must mount. SMB is named in the defect and is not measured here.

The failure this plan closes is: the `Ex` call returns a status that means the information class or the POSIX flag is unsupported, and today that status becomes a generic I/O error, so the replace or unlink never commits.

- A buffer laid out for `FileRenameInformationEx` is reused for classic `FileRenameInformation`, so a no-replace rename replaces.

- Sharing violation, name collision, access denied, or `ERROR_USER_MAPPED_FILE` (1224) starts a second call.
- A FAT/exFAT test is green only because the volume accepted `Ex`, and the classic path is never executed.

## Approach

### Ex first, one classic call

`rename_child_with_mode` and `unlink_posix` try the current `Ex` request first. Only when `RtlNtStatusToDosError` of that NTSTATUS is 87, 50, or 1 does the function issue one classic call. No third attempt, and no `Ex` call without the POSIX flag. `delete_temp` stays a single classic disposition and must not go through this fallback.

The unsupported predicate is one function in the Windows fs module. Its name is `ex_information_class_unsupported`. Tests and the source pin use that spelling. It takes the raw NTSTATUS, calls `RtlNtStatusToDosError`, and matches only those three DOS codes. Sharing violation, name collision, access denied, and 1224 do not match.

Collision classification is one function applied to the `Ex` status before any classic call, and applied again to the classic status if the classic call ran. Workspace-name taken and atomic-create collision stay the errors they are today. A collision is never a reason to fall back. The classic no-replace buffer has `ReplaceIfExists` false, so the classic call cannot overwrite the existing name either.

### Classic rename bytes

The classic rename builds a new zeroed `FILE_RENAME_INFORMATION` buffer. Byte 0 is `1` when `replace` is true and `0` when it is false. Bytes 1 through 3 of the `FILE_RENAME_INFORMATION_0` union stay zero. `RootDirectory`, `FileNameLength`, and `FileName` use the same `offset_of!` fields as the `Ex` buffer. The classic buffer is not the `Ex` flags word with a different information class. The information class is `FileRenameInformation`.

Classic `FileRenameInformation` has no ignore-readonly flag. This plan does not add an attribute-clearing pass. A read-only target that the `Ex` flags would have replaced can still fail on the classic call, and that failure is the classic status. The same limit applies to classic unlink: `FILE_DISPOSITION_INFORMATION { DeleteFile: true }` only, as `delete_temp` already does, with no ignore-readonly flag.

### Classic unlink

On the unsupported predicate, `unlink_posix` sends `FILE_DISPOSITION_INFORMATION { DeleteFile: true }` with `FileDispositionInformation`. Identity is still checked by `unlink_windows_child_at` before this function runs. Classic success is a committed namespace operation. An open handle can keep the directory entry until the last handle closes; that is the classic disposition behaviour already accepted for temp cleanup. The function does not retry. ### Production calls stay Ex-only

### Record the real Ex status

Under `cfg(test)` only, `rename_child_with_mode` and `unlink_posix` call `note_test_ex_status` with the NTSTATUS immediately after the real `NtSetInformationFile` returns. That function increments a thread-local generation and stores the status. `test_ex_generation()` returns the generation. `last_ex_ntstatus()` returns the stored status. The hook does not skip the syscall, does not inject a status, and does not exist in a non-test build. `delete_temp` does not call it. A production build has no generation.

### Retained volume record

The `rust-windows-test` job mounts one FAT32 VHD and one exFAT VHD, about 260MB each, and sets `CHESSFABLE_FAT32_ROOT` and `CHESSFABLE_EXFAT_ROOT`. If `New-VHD` or format fails, the job fails with that error. It does not skip. It sets `CHESSFABLE_VOLUME_MEASUREMENT` to a file under the runner temp directory. If it is not, the test fails and writes no line for that operation. `committed` for replace means `atomic_replace_at` returned `Ok`, including `CommittedDurabilityUncertain` inside that `Ok`, and the destination name holds the new bytes. `error` for replace means `Err` after the generation advanced by one, and the previous destination bytes are unchanged.

## Approach

### Production calls stay Ex-only

`rename_child_with_mode` and `unlink_posix` keep a single `NtSetInformationFile` using `FileRenameInformationEx` and `FileDispositionInformationEx`. No classic class, no second call, no status predicate, no destination-handle drop. `delete_temp` stays as it is. `windows_unlink_uses_posix_disposition_ex` stays as it is, including the rejection of `FileDispositionInformation)`.

Add `windows_rename_uses_rename_information_ex_only`. Its compact body of `rename_child_with_mode` must contain `FileRenameInformationEx` and must not contain `FileRenameInformation)` (the classic class). `FILE_RENAME_INFORMATION` as the struct name used for `offset_of!` stays allowed.

### Record the real Ex status

Under `cfg(test)` only, `rename_child_with_mode` and `unlink_posix` call `note_test_ex_status` with the NTSTATUS immediately after the real `NtSetInformationFile` returns. That function increments a thread-local generation and stores the status. `test_ex_generation()` returns the generation. `last_ex_ntstatus()` returns the stored status. The hook does not skip the syscall, does not inject a status, and does not exist in a non-test build. `delete_temp` does not call it. A production build has no generation.

### Retained volume record

The `rust-windows-test` job mounts one FAT32 VHD and one exFAT VHD, about 260MB each, and sets `CHESSFABLE_FAT32_ROOT` and `CHESSFABLE_EXFAT_ROOT`. If `New-VHD` or format fails, the job fails with that error. It does not skip. It sets `CHESSFABLE_VOLUME_MEASUREMENT` to a file under the runner temp directory. After `cargo test`, a step prints that file into the log and fails if any of the four required lines is missing. An `if: always()` step then dismounts both volumes. `cargo test` hides stdout from passing tests, so a `println` is not the record.

`windows_non_ntfs_volume_records_ex_status` is `cfg(all(test, windows))`. When `GITHUB_ACTIONS` is set and either root or the measurement path is missing or unusable, the test fails. When `GITHUB_ACTIONS` is unset and a root is missing, the test returns without writing, so a local Windows run without a VHD does not fail. The test uses `windows_test_parent` on a directory on that volume, not a junction, and calls production `atomic_replace_at` and `remove_entry_at`.

The replace target is an existing file, so `replace_at_driver` holds `original` and `current` during the `Ex` call. That is the production replace, not a rename onto a missing name. The unlink target is an existing file with no extra handle held by the test after `remove_entry_at`'s own open.

Before each of those two calls the test reads `test_ex_generation`. After the call it reads the generation again and `last_ex_ntstatus`. The generation must be exactly one greater. If it is not, the test fails and writes no line for that operation. A failure in `before_write` (`fs.rs:1201`, including the DACL copy at `4714`) or in `unlink_windows_child_at` before `unlink_posix` (`3604–3610`) does not reach `Ex`, leaves the generation unchanged, and fails the test. Recording a stale status with outcome `error` is not allowed. Reverting either `note_test_ex_status` call makes that operation's generation stay put, so the test fails.

`committed` for replace means `atomic_replace_at` returned `Ok`, including `CommittedDurabilityUncertain` inside that `Ok`, and the destination name holds the new bytes. `error` for replace means `Err` after the generation advanced by one, and the previous destination bytes are unchanged.

`committed` for unlink means the name is gone after the deleting handle drops. That includes `Ok` and `Err(CommittedDurabilityUncertain)`. `remove_entry_at` (`5694`) finishes through `CommittedRemoval::finish` (`error.rs:702–705`), and the Windows counted path records a parent-sync failure after a successful unlink (`fs.rs:4393–4396`). The name is already gone in that case. `error` for unlink means some other `Err` after the generation advanced by one, and the name is still present.

For each filesystem the test appends exactly these lines, status in decimal, only after that operation's generation check passed:

```
fat32 replace <ntstatus> <committed|error>
fat32 unlink <ntstatus> <committed|error>
exfat replace <ntstatus> <committed|error>
exfat unlink <ntstatus> <committed|error>
```

The test also appends one mapped-replace line per filesystem: `fat32 mapped-replace <ntstatus> <committed|error>` or `fat32 mapped-replace - unavailable`, and the exFAT twins. A line with a status uses the same generation check on that replace. Mapped `committed` requires the mapper's bytes to stay the old bytes and the name's new bytes to be the replacement. Mapped `error` requires the original bytes unchanged. `unavailable` is only for a failure to create the mapping, records no status, and does not fail the test. A missing unmapped line fails the test. The test does not branch on which status is "good". Status 0 and a rejecting status are both valid records. The job's print step is what keeps the record after the harness swallows test stdout.

Linux does not compile this test. A filter that matches zero tests is not a proof it ran.

A non-zero status is the rejection this finding hypothesized, still without a fallback. No code adds that status to a predicate. The finding stays open. ## Threat model and non-goals

Frozen at round 1. A later change needs a focused plan-review judgment.

The environment is a Windows volume the user already selected as a database, workspace, download, or registry location. NTFS is the common case and must keep POSIX semantics. FAT32 and exFAT are the volumes this finding names and the ones the Windows job must mount. SMB is named in the defect and is not measured here.

The failure the finding describes is: the `Ex` call returns a status that means the information class or the POSIX flag is unsupported, and today that status becomes a generic I/O error, so the replace or unlink never commits. This plan does not close that failure. It records the status.

These are hazards of a fallback this plan does not ship:

- A buffer laid out for `FileRenameInformationEx` is reused for classic `FileRenameInformation`, so a no-replace rename replaces.
- NTFS rejects a malformed `Ex` request with `STATUS_INVALID_PARAMETER`, the code treats that as "unsupported", and the classic call drops the POSIX behaviour `d-20260919-10` measured.
- Sharing violation, name collision, access denied, or `ERROR_USER_MAPPED_FILE` (1224) starts a second call.
- A FAT/exFAT test is green only because the volume accepted `Ex`, and the classic path is never executed.
- Classic success is reported as a new kind of uncertainty, or classic failure is reported as success.

Out of this threat model: a process that races the name after a correct status check, a junction or reparse escape, and a volume that accepts `Ex` but ignores the POSIX flag. The last case stays today's outcome (the `Ex` call's own status). SMB that returns a status outside the unsupported set stays today's failure. No new renderer string.

Round 2 narrowed this plan after review. The fallback described above is not an obligation of this plan. Shipping it before a retained volume measurement, or while `replace_at_driver` still holds the destination open, is the defect round 1 found. The measurement is the whole change.

## Approach

### Production calls stay Ex-only

`rename_child_with_mode` and `unlink_posix` keep a single `NtSetInformationFile` using `FileRenameInformationEx` and `FileDispositionInformationEx`. No classic class, no second call, no status predicate, no destination-handle drop. `delete_temp` stays as it is. `windows_unlink_uses_posix_disposition_ex` stays as it is, including the rejection of `FileDispositionInformation)`.

Add `windows_rename_uses_rename_information_ex_only`. Its compact body of `rename_child_with_mode` must contain `FileRenameInformationEx` and must not contain `FileRenameInformation)` (the classic class). `FILE_RENAME_INFORMATION` as the struct name used for `offset_of!` stays allowed.

### Record the real Ex status

Under `cfg(test)` only, `rename_child_with_mode` and `unlink_posix` call `note_test_ex_status` with the NTSTATUS immediately after the real `NtSetInformationFile` returns. That function increments a thread-local generation and stores the status. `test_ex_generation()` returns the generation. `last_ex_ntstatus()` returns the stored status. The hook does not skip the syscall, does not inject a status, and does not exist in a non-test build. `delete_temp` does not call it. A production build has no generation.

### Retained volume record

The `rust-windows-test` job mounts one FAT32 VHD and one exFAT VHD, about 260MB each, and sets `CHESSFABLE_FAT32_ROOT` and `CHESSFABLE_EXFAT_ROOT`. If `New-VHD` or format fails, the job fails with that error. It does not skip. It sets `CHESSFABLE_VOLUME_MEASUREMENT` to a file under the runner temp directory. After `cargo test`, a step prints that file into the log and fails if any of the four required lines is missing. An `if: always()` step then dismounts both volumes. `cargo test` hides stdout from passing tests, so a `println` is not the record.

`windows_non_ntfs_volume_records_ex_status` is `cfg(all(test, windows))`. When `GITHUB_ACTIONS` is set and either root or the measurement path is missing or unusable, the test fails. When `GITHUB_ACTIONS` is unset and a root is missing, the test returns without writing, so a local Windows run without a VHD does not fail. The test uses `windows_test_parent` on a directory on that volume, not a junction, and calls production `atomic_replace_at` and `remove_entry_at`.

The replace target is an existing file, so `replace_at_driver` holds `original` and `current` during the `Ex` call. That is the production replace, not a rename onto a missing name. The unlink target is an existing file with no extra handle held by the test after `remove_entry_at`'s own open.

Before each of those two calls the test reads `test_ex_generation`. After the call it reads the generation again and `last_ex_ntstatus`. The generation must be exactly one greater. If it is not, the test fails and writes no line for that operation. A failure in `before_write` (`fs.rs:1201`, including the DACL copy at `4714`) or in `unlink_windows_child_at` before `unlink_posix` (`3604–3610`) does not reach `Ex`, leaves the generation unchanged, and fails the test. Recording a stale status with outcome `error` is not allowed. Reverting either `note_test_ex_status` call makes that operation's generation stay put, so the test fails.

`committed` for replace means `atomic_replace_at` returned `Ok`, including `CommittedDurabilityUncertain` inside that `Ok`, and the destination name holds the new bytes. `error` for replace means `Err` after the generation advanced by one, and the previous destination bytes are unchanged.

`committed` for unlink means the name is gone after the deleting handle drops. That includes `Ok` and `Err(CommittedDurabilityUncertain)`. `remove_entry_at` (`5694`) finishes through `CommittedRemoval::finish` (`error.rs:702–705`), and the Windows counted path records a parent-sync failure after a successful unlink (`fs.rs:4393–4396`). The name is already gone in that case. `error` for unlink means some other `Err` after the generation advanced by one, and the name is still present.

For each filesystem the test appends exactly these lines, status in decimal, only after that operation's generation check passed:

```
fat32 replace <ntstatus> <committed|error>
fat32 unlink <ntstatus> <committed|error>
exfat replace <ntstatus> <committed|error>
exfat unlink <ntstatus> <committed|error>
```

The test also appends one mapped-replace line per filesystem: `fat32 mapped-replace <ntstatus> <committed|error>` or `fat32 mapped-replace - unavailable`, and the exFAT twins. A line with a status uses the same generation check on that replace. Mapped `committed` requires the mapper's bytes to stay the old bytes and the name's new bytes to be the replacement. Mapped `error` requires the original bytes unchanged. `unavailable` is only for a failure to create the mapping, records no status, and does not fail the test. A missing unmapped line fails the test. The test does not branch on which status is "good". Status 0 and a rejecting status are both valid records. The job's print step is what keeps the record after the harness swallows test stdout.

Linux does not compile this test. A filter that matches zero tests is not a proof it ran.

### What the record does not decide

A status of 0 on this runner means that image accepted `Ex` for that operation. It does not prove every FAT32 or exFAT volume accepts `Ex`, and it does not prove a classic call would commit. A non-zero status is the rejection this finding hypothesized, still without a fallback. No code adds that status to a predicate. The finding stays open. The close note must not say the fallback was implemented or measured.

## Decisions and trade-offs

### Decided autonomously

Question: what is the contract on a volume without POSIX rename or disposition semantics? (a) a typed refusal naming the unsupported volume, or (b) a fallback to `FileRenameInformation` / `FileDispositionInformation`, and which durability and identity guarantees does the fallback carry?

Chosen for this plan: neither (a) nor (b). The mandate says the volume must be measured before that contract is chosen. This change mounts FAT32 and exFAT, calls the existing production replace and unlink, and writes the raw `Ex` NTSTATUS to a file the Windows job prints. Production behaviour is unchanged. `f-20261005-02` stays open. The adopter does not mark it handled and does not record a decision that chooses (a) or (b).

Rejected: adopting (b) in this change. Round 1 showed two independent reasons. The mandate's own sentence requires the measurement first, and the current job has no volume measurement to read. Separately, `replace_at_driver` keeps the destination open in `original` and `current` through `adapter.rename` (`fs.rs:1195`, `1273–1279`, `1354–1360`, handle stored at `2932`). Classic replacement rejects an open destination, so a fallback that promised an unmapped replace would fail on the operation's own handles. Also rejected for this change: (a) a typed refusal, classic-first, an `Ex` retry without the POSIX flag, and treating a green run whose stdout was swallowed as a measurement.

Reason: choosing (b) before the record exists contradicts the fixed mandate. Choosing it without dropping those two handles would also report success for a replace the classic call cannot commit. `d-20260919-10` still requires the POSIX `Ex` path to be the call NTFS actually runs; this plan does not touch that path. `d-20260906-03` and `d-20261004-25` stay input for the later contract and are not amended.

Reversal path: a later plan may adopt (b) only after this measurement file exists in a Windows log, and only if classic replace drops `original` and `current` after the `Ex` status is known to be unsupported and before the classic call. That later plan owns the BOOLEAN layout, the DOS 87/50/1 predicate, and the durability assignment. A later plan may adopt (a) if the measurement shows a rejection and a classic commit would break an identity or durability obligation the callers already have. This plan does not write `tasks/decisions.md`.
