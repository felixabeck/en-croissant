### I1: cancellation hides secondary cleanup failure

Witness: error-handling r1 raw finding ordinal 1, should-fix, confidence 92, plan r1 body line 61.

Claim: O3 leaves secondary failure surfacing unspecified when Cancellation is silent. The reused AddDatabase catches only log deletion and refresh failures, then rethrow Cancellation, which suppresses the notification. If deletion and refresh both fail, the progress row disappears while the unfinished database remains absent from the displayed library, leaving no visible recovery cue. Require a visible cleanup/refresh failure outcome while preserving the primary cancellation, and cover this combined failure in O5.

Disposition: Fix. Source evidence: the AddDatabase cleanup and failure refresh catches log and rethrow the primary cause, and notifyError suppresses Cancellation. Failing MANDATE obligation: a newly created database must be deleted on cancellation, with an honest failure/recovery outcome when deletion fails. O3 and O5 were corrected to show renderer-safe secondary failure and allow load retry while preserving cancellation and existing diagnostics. No new native mechanism or authority expansion. Dependencies: none. No withdrawal or rejected alternative.

### I2: cancellation proof excludes Windows runtime

Witness: platform-semantics r1 raw finding ordinal 1, should-fix, confidence 94, plan r1 body line 69.

Claim: O5 reuses rollback tests without requiring Windows coverage. Those tests, including mid-file cancellation and shutdown cancellation, live under cfg(all(test, unix)) at src-tauri/src/db/mod.rs:4078. Consequently, rust-windows-test cannot run them, and verify:app uses Linux WebKitGTK. Require Windows-runnable native tests for ticketed cancellation, retained content/revision and deletion of the cancelled new target after worker settlement. Name rust-windows-test and rust-macos-test as runtime proof, with rust-platform providing compilation/lint coverage.

Disposition: Fix. Source evidence: the Unix-gated importer test module and the existing Test workflow's platform test jobs. Failing MANDATE obligation: the new cancellation command must preserve target data and cleanup on supported platforms. O5 and the phase scope/proof were corrected to add a narrow portable native test module and distinguish runtime CI from compilation. No new runtime mechanism or whole-suite migration. Dependencies: none. No withdrawal or rejected alternative.

Unknown/retired cancel returns false, owner/kind mismatch refuses, active release never removes a live worker, and capacity/TTL are bounded by existing registry limits. ## Approach

### O1: owner-bound conversion ticket and native lifetime

Add a Conversion reservation kind to the existing OperationRegistry with prepare, claim, cancel and release operations, and Specta commands to prepare/cancel/release conversion tickets. Add an optional ticket to convert_pgn. Ticketed calls claim the exact ticket for the invoking webview before any asynchronous wait. Unticketed calls keep the existing accepted-operation route. Share common prepared-to-accepted validation, promotion, cancellation and release with downloads at the second implementation, preserving download-specific admission, progress-clear and commit rules.

Reserved cancellation is remembered until claim or release, so cancel-before-claim returns typed Cancellation and never begins parsing. Unknown/retired cancel returns false, owner/kind mismatch refuses, active release never removes a live worker, and capacity/TTL are bounded by existing registry limits. Active conversion tickets remain completion-owned, survive request abandonment and renderer reload like today's imports, and are canceled by application shutdown. Webview destruction preserves today's accepted-import behavior rather than introducing automatic conversion cancellation. Cancel affects exactly one conversion even when another uses the same database. Native lease retirement occurs only after worker settlement.

### O2: cancellation preserves transaction outcome

Pass the claimed conversion token through the existing blocking gateway, lock wait, parsing and revision transaction. A cancelled transaction returns typed Cancellation and retains the pre-import database content and revision. Cancellation delivery is a request acknowledgement, never a promise of rollback. A late request may lose to transaction commit. The actual command result decides whether the import succeeded, and the renderer must never replace a successful conversion result with Cancellation solely because cancel was requested. Keep native success/cache invalidation/final progress behavior tied to the transaction result. Do not add a new commit barrier or change Diesel's existing commit protocol.

### O3: one local conversion owner from preparation through cleanup

Extend the existing runDatabaseConversion owner with opt-in local cancellation, a prepared native conversion ticket passed to the callback, an operation-specific cancel action and request-pending state. All three routes keep their unique progress IDs. The new local database and Add games routes opt in, while AccountCard retains its unticketed conversion behavior with an explicit null argument where required. Reuse the platform's prepared-ticket lifecycle for abandoned preparation and failure release. The owner records cancel-before-ticket/pre-convert intent and checks it before invoking native conversion, including after creating a new target. It must not release its entry until conversion, created-database cleanup and library refresh settle.

Keep new-database deletion in convertLocalDatabase, scoped to its just-created handle, after a failed/cancelled conversion. If canceled after target creation but before native dispatch, enter that same cleanup path. Never delete an existing Add games target. A successful conversion that wins a cancellation race keeps the new database. Secondary cleanup/refresh errors cannot mask the primary result, and an undeleted unfinished target remains recoverable under the existing Delete surface after a successful library reload. Cancellation itself is silent through the established error mapping. If deletion or the failure-path library refresh fails during cancellation, surface the real secondary failure through the existing renderer-safe notification mapping before retiring the operation row. Combined deletion/refresh failure must leave a visible error and a way to retry the library load, never silent removal of the only progress cue. Preserve the original cancellation object and existing diagnostic logging. Ordinary conversion failure remains reported by its existing owner exactly once. A rejected cancel IPC is a real request failure, is surfaced once and permits retry while the operation is still live. Repeated clicks deduplicate the pending request.

### O4: cancel control belongs to the operation row

Render a localized, accessible Cancel control on each cancellable local conversion row in useDatabaseLibrary. It stays bound to the entry ID through concurrent same-target operations, modal dismissal and route navigation. Show a pending/disabled state only for that entry while its cancellation request is unresolved, retaining progress until the owner settles. A stale action cannot retire or cancel a newer import. Rows belonging to account conversion remain visible with their existing counters and no new cancel control. Reuse Mantine controls and Common.Cancel text where suitable, and run i18n extraction for new keys.
