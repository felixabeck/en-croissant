### plan-r1.md

# Plan: Per-operation conversion progress (f-20260914-06)

## Goal

Every PGN-to-database conversion the renderer starts is tracked as its own operation, from the
first click to its settled result, whatever the target database and whatever else is running. Its
live counters come only from its own `ConvertProgress` frames. Its completion or failure removes
only its own entry, never another operation's.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260914-06:

> * **Where:** `src/utils/db.ts:111` derives `conversion:${databaseHandleKey(database)}`; Rust emits it as `ConvertProgress.id` (`src-tauri/src/db/mod.rs:753,852,875`); `useConversionProgress` filters on it.
> * **Defect (reported):** `f-20260901-04` gave `ConvertProgress` an id and filtered on it, but the id is derived from the target database, not from the operation. Two imports into the same database therefore emit the same id; both frames pass the filter, counts and source names interleave, and one completion clears the other operation's state.
> * **Related:** `f-20260901-04` (handled 2026-09-04) — this is new evidence that its discriminator is per database, not per operation; not a reopening of a decision.
> * **Open question:** should concurrent conversions into one database be refused (one conversion per target) or tracked separately with a renderer-minted per-operation id and a per-operation progress entry?

## Threat model and non-goals

Accidental concurrency by one local user of the desktop app: concurrent clicks on the three
conversion routes (AddDatabase local conversion, DatabasesPage "Add games", AccountCard "Download
games"), including two that target the same database. No adversarial renderer, no forged IPC
frame. A frame whose id the renderer did not mint (or minted and has since retired) counts as
foreign. Environments: the Tauri app on every supported OS; the logic is renderer-only and
platform-independent.

## Traced premises

Frozen at BASE `2946d8bc`.

* `src/utils/db.ts:120-123`: `conversionProgressId(database)` returns
  `conversion:${databaseHandleKey(database)}`, one id per target database.
* `src/hooks/useConversionProgress.ts:30-49`: a frame is applied only when
  `payload.id === conversionProgressId(previous.targetDatabase)` and overwrites the single slot's
  `totalGames`, `elapsedSeconds` and `sourceFileName`.
* `src/state/atoms.ts:496-521`: `databaseConversionStateAtom` is an in-memory (not persisted)
  single slot `{ inProgress, totalGames, elapsedSeconds, targetDatabase, targetDatabaseTitle,
  sourceFileName }`. `clearOwnedConversion(handle)` resets the slot when its target equals
  `handle`.
* `src-tauri/src/db/mod.rs:1003`: `convert_pgn_blocking` runs inside
  `repository.with_write_lock_cancellable(&target, …)`. A second conversion into the same target
  waits for the lock and is not refused. `:1052-1059` and `:1081-1087` emit `ConvertProgress`
  frames with `id: progress_id` exactly as the renderer passed it. Rust needs no change to carry a
  per-operation id.
* `src/components/databases/AddDatabase.tsx:108-143`: `convertDB` raises `inProgress` before the
  database handle exists, fills `targetDatabase` through `onCreated` (`:64`), and clears with
  `clearOwnedConversion(thisHandle)` (`:142`). `convertLocalDatabase` passes
  `conversionProgressId(dbPath)` (`:66-67`).
* `src/components/home/AccountCard.tsx:140-173`: `convert()` writes the slot, calls `convertPgn`
  with `conversionProgressId(databaseHandle)`, and clears with
  `clearOwnedConversion(databaseHandle)` in its `finally` (`:171`). The download button is gated
  only by its own `loading` (`:254`).
* `src/components/databases/DatabasesPage.tsx:474-505`: "Add games" calls `runAddGamesToDatabase`
  (`databaseMutation.ts:57-75`, `begin`/`finish` around `convertPgn`). It passes
  `conversionProgressId(destination)` and clears with `clearOwnedConversion(dest)`. The button is
  not disabled while a conversion runs. `selectedDatabase` derives from `databases`, not
  `visibleDatabases` (`:82-85`), so it stays clickable for a database already being converted
  into.
* `src/components/databases/DatabasesPage.tsx:86-94,185,225,231-252`: the page hides the target
  database from the list, disables "Add new" and local conversion, and renders one progress row,
  all from the single slot.
* Consequence 1 (same target): A and B both import into D. Both use id `conversion:D`. B waits on
  the write lock. A's `finally` clears the slot because its handle equals D. B's frames are then
  all dropped (`targetDatabase` is null), and "Add new" re-enables while B is still running.
* Consequence 2 (different targets): the slot's last writer wins. Whichever operation finishes
  first clears the slot or leaves it showing only the other, so the survivor runs unseen. This is
  covered by "one completion clears the other operation's state" whenever the two operations
  share one slot.
* `.claude/rules/ipc-events.md:82-85` describes `ConvertProgress` without its `id` and lists a
  `collect_events!` set that no longer matches `src-tauri/src/main.rs:2403-2411` (it names the
  deleted `DatabaseProgress` and omits `DatabaseContentFailure`).

## Approach

### O1 — Per-operation identity minted by the renderer

MANDATE: "the id is derived from the target database, not from the operation"; "a renderer-minted
per-operation id".

* Each conversion start mints a fresh, unique id (`conversion:` plus `crypto.randomUUID()`) before
  any IPC call. That same string is passed as `convertPgn`'s `progressId` and keys the operation's
  renderer entry.
* No conversion id is derived from a database handle any more. `conversionProgressId(handle)` is
  removed together with its tests; no caller remains.
* Rust, `ConvertProgress`, `convert_pgn`'s signature and `src/bindings/generated.ts` are
  unchanged. `pnpm bindings:check` must stay byte-identical.

### O2 — A per-operation conversion registry replaces the single slot

MANDATE: "a per-operation progress entry"; "one completion clears the other operation's state".

* `databaseConversionStateAtom` becomes an in-memory ordered collection of active conversion
  entries, keyed by the O1 id, in start order. Each entry carries `id`, `targetDatabase`
  (`DatabaseHandle | null`, null until AddDatabase's handle exists), `targetDatabaseTitle`,
  `sourceFileName`, `totalGames` and `elapsedSeconds`. "A conversion is in progress" is derived:
  the collection is non-empty. No stored `inProgress` flag can disagree with it.
* It stays non-persisted, so the rule "never restore a stale snapshot" (atoms.ts comment) holds
  unchanged.
* **Ownership:** only the route that minted an id adds, patches the target of, or removes that
  entry. Removal compares by id, never by handle. `clearOwnedConversion` and every handle-compare
  teardown go away.
* **Bound:** one entry per in-flight `convertPgn` call. Each entry is removed on every exit path
  of its owning route: success, `convertPgn` rejection (including cancellation), and a throw
  before `convertPgn` after the entry was added (for example AddDatabase's
  `createWorkspaceDatabase` failure, AccountCard's `startProgress` failure). Removal of an id that
  is already absent is a no-op.

# Plan: Per-operation conversion progress (f-20260914-06)

## Goal

Every PGN-to-database conversion the renderer starts is tracked as its own operation, from the
first click to its settled result, whatever the target database and whatever else is running. Its
live counters come only from its own `ConvertProgress` frames. Its completion or failure removes
only its own entry, never another operation's.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260914-06:

> * **Where:** `src/utils/db.ts:111` derives `conversion:${databaseHandleKey(database)}`; Rust emits it as `ConvertProgress.id` (`src-tauri/src/db/mod.rs:753,852,875`); `useConversionProgress` filters on it.
> * **Defect (reported):** `f-20260901-04` gave `ConvertProgress` an id and filtered on it, but the id is derived from the target database, not from the operation. Two imports into the same database therefore emit the same id; both frames pass the filter, counts and source names interleave, and one completion clears the other operation's state.

## Threat model and non-goals

Accidental concurrency by one local user of the desktop app: concurrent clicks on the three

frame. A frame whose id the renderer did not mint (or minted and has since retired) counts as
foreign. Environments: the Tauri app on every supported OS; the logic is renderer-only and
platform-independent.

# Plan: Per-operation conversion progress (f-20260914-06)

## Goal

Every PGN-to-database conversion the renderer starts is tracked as its own operation, from the
first click to its settled result, whatever the target database and whatever else is running. Its
live counters come only from its own `ConvertProgress` frames. Its completion or failure removes
only its own entry, never another operation's.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260914-06:

> * **Where:** `src/utils/db.ts:111` derives `conversion:${databaseHandleKey(database)}`; Rust emits it as `ConvertProgress.id` (`src-tauri/src/db/mod.rs:753,852,875`); `useConversionProgress` filters on it.
> * **Defect (reported):** `f-20260901-04` gave `ConvertProgress` an id and filtered on it, but the id is derived from the target database, not from the operation. Two imports into the same database therefore emit the same id; both frames pass the filter, counts and source names interleave, and one completion clears the other operation's state.
> * **Related:** `f-20260901-04` (handled 2026-09-04) — this is new evidence that its discriminator is per database, not per operation; not a reopening of a decision.
> * **Open question:** should concurrent conversions into one database be refused (one conversion per target) or tracked separately with a renderer-minted per-operation id and a per-operation progress entry?

## Threat model and non-goals

Accidental concurrency by one local user of the desktop app: concurrent clicks on the three
conversion routes (AddDatabase local conversion, DatabasesPage "Add games", AccountCard "Download
games"), including two that target the same database. No adversarial renderer, no forged IPC
frame. A frame whose id the renderer did not mint (or minted and has since retired) counts as
foreign. Environments: the Tauri app on every supported OS; the logic is renderer-only and
platform-independent.

## Approach

### O1 — Per-operation identity minted by the renderer

MANDATE: "the id is derived from the target database, not from the operation"; "a renderer-minted
per-operation id".

* Each conversion start mints a fresh, unique id (`conversion:` plus `crypto.randomUUID()`) before
  any IPC call. That same string is passed as `convertPgn`'s `progressId` and keys the operation's
  renderer entry.
* No conversion id is derived from a database handle any more. `conversionProgressId(handle)` is
  removed together with its tests; no caller remains.
* Rust, `ConvertProgress`, `convert_pgn`'s signature and `src/bindings/generated.ts` are
  unchanged. `pnpm bindings:check` must stay byte-identical.

### O2 — A per-operation conversion registry replaces the single slot

MANDATE: "a per-operation progress entry"; "one completion clears the other operation's state".

* `databaseConversionStateAtom` becomes an in-memory ordered collection of active conversion
  entries, keyed by the O1 id, in start order. Each entry carries `id`, `targetDatabase`
  (`DatabaseHandle | null`, null until AddDatabase's handle exists), `targetDatabaseTitle`,
  `sourceFileName`, `totalGames` and `elapsedSeconds`. "A conversion is in progress" is derived:
  the collection is non-empty. No stored `inProgress` flag can disagree with it.
* It stays non-persisted, so the rule "never restore a stale snapshot" (atoms.ts comment) holds
  unchanged.
* **Ownership:** only the route that minted an id adds, patches the target of, or removes that
  entry. Removal compares by id, never by handle. `clearOwnedConversion` and every handle-compare
  teardown go away.
* **Bound:** one entry per in-flight `convertPgn` call. Each entry is removed on every exit path
  of its owning route: success, `convertPgn` rejection (including cancellation), and a throw
  before `convertPgn` after the entry was added (for example AddDatabase's
  `createWorkspaceDatabase` failure, AccountCard's `startProgress` failure). Removal of an id that
  is already absent is a no-op.
* The add / set-target / remove lifecycle is one shared primitive used by all three routes
  (rule 11; three copies of the lifecycle exist today). It owns minting the id and guarantees
  removal in `finally`. Its shape (store helper, hook, or updater functions) is the executor's
  choice, but one implementation serves all three routes.

### O3 — Frames update only their own live entry

MANDATE: "both frames pass the filter, counts and source names interleave".

* `useConversionProgress` applies a frame only to the entry whose id equals `payload.id`. It
  overwrites that entry's `totalGames`, `elapsedSeconds`, and `sourceFileName` when the payload
  value is non-null (today's `??` fallback).
* A frame never creates an entry. A frame for an unknown or already-removed id, including the
  final frame that can arrive after the owning route's `finally`, leaves the state referentially
  unchanged.
* The hook stays mounted application-wide (`App.tsx:207`), through the platform facade, and keeps
  its listener-error handling.

### O4 — Databases page renders every active conversion

MANDATE: "a per-operation progress entry"; and keeps today's user-visible rules per operation.

* The progress area renders one row per active entry, in start order. Each row shows the same
  text and counters a single row shows today (`Databases.Add.Convert: <source or title>`, game
  count, games/s), computed from that entry alone. No new translation key unless a row needs one;
  if one is added, it goes through i18next and `pnpm i18n:extract`.
* The list hides every database that is the target of any active entry (today it hides one).
* "Add new" and local conversion stay disabled while any conversion is active (today's behaviour,
  now derived from the collection).
* "Add games" and the AccountCard download stay available while other conversions run, as today.
  A same-target import queues behind the native write lock and shows its own row.

### O5 — Rule text matches the contract

MANDATE: the finding is about the `ConvertProgress` discriminator. `ipc-events.md` is the
write-time rule for that event.

* `.claude/rules/ipc-events.md`'s `convert_progress` section states that `ConvertProgress` carries
  a renderer-minted per-operation `id` that `useConversionProgress` filters on, and that the id is
  never derived from the target database (this incident). The `collect_events!` list in that
  paragraph is corrected to the current registry.

## Decisions and trade-offs

* **Track, not refuse** (the finding's open question). Refusing a second conversion into the same
  target is rejected for four reasons:
  1. The native side already serializes same-target writes correctly
     (`with_write_lock_cancellable`), so a refusal removes a working capability.
  2. A refusal kept in renderer state is not authoritative
     (`async-resource-invariants.md`: "Renderer state is not authoritative for native jobs").
     A native refusal would need a new per-target registry and a new error surface.
  3. A refusal changes what a user gets: an error instead of a queued import.
  4. A refusal leaves the different-target single-slot loss (consequence 2) unfixed.
  Tracking per operation fixes both consequences, with no Rust or binding change.
* **Supersedes d-20260904-16 (conversion half only).** The deterministic per-database id was
  chosen because "the identity is known before the call". The new evidence: the target database
  is not unique per operation, because the backend queues rather than refuses. The
  `get_players_game_info` per-call UUID half is unaffected.
* **Supersedes d-20260904-18.** Teardown ownership moves from handle comparison to the
  operation's own id. That decision's constraints still hold, but by construction now:
  * The `setLoading` bridge and AccountCard's `onClick` `finally` still do not write conversion
    state.
  * AddDatabase still registers its entry before the handle exists (closing the double-submit
    window).
  * AccountCard's removal still sits inside `convert()`.
* **d-20260904-15 stands.** `ConvertProgress` stays its own counter event with no lease.
* **Collection rather than single slot with a per-operation id:** with a single slot, the
  earlier of two concurrent operations is overwritten and runs unseen, so the mandate's "one
  completion clears the other operation's state" survives in a different order.
