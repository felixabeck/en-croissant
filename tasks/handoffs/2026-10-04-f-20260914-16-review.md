# Plan: terminal behaviour when legacy session sanitisation cannot be persisted (f-20260914-16)

## Goal

When ChessFable starts and the legacy `sessions` record still carries a Lichess bearer token, but
Web Storage refuses both the sanitised overwrite and the removal of that key, the launch ends in a
defined, visible, fail-closed terminal state: the token is never handed to native migration or to
any feature, the user sees why the app did not start and can retry, every later launch retries the
scrub automatically, and no other saved user data is destroyed.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-16`:

* **Where:** `src/utils/session.ts:79` (sanitised `setItem`, then fallback `removeItem`), startup abort at `:132`.
* **Defect (reported):** when rewriting a legacy serialised session record without its `accessToken`, a failing `setItem` falls back to `removeItem`; if that also throws, the original record — including the bearer token — stays in Web Storage. Startup aborts but neither erases nor retries, so the token remains renderer-readable.
* **Why it matters:** `CLAUDE.md` Conventions and `.claude/rules/async-resource-invariants.md` — a bearer token must never remain in the renderer; the sanitisation's failure path is exactly where it matters.
* **Open question:** what is the terminal behaviour when storage refuses both the sanitised write and the removal — clear the whole storage area, retry on next start with a persistent "must erase" marker, or refuse to continue with an explicit user-visible reset?

## Threat model and non-goals

Frozen in round 1.

* **Accidental input only.** Web Storage that throws on `setItem` and `removeItem` because of
  quota, I/O or a disabled/denied storage area, on the user's own machine, on Linux (WebKitGTK),
  macOS (WKWebView) and Windows (WebView2). The design must not depend on *which* storage operation
  throws on which engine: every combination of the two operations throwing or returning is handled.
* **No adversary.** Script already executing in the renderer could read the record before any
  sanitiser runs; that is outside this finding. The renderer's CSP and the IPC boundary are unchanged.
* **Not in scope:** fields nested inside `lichess.account` / `chessCom.stats` (`z.custom`, not
  recursively stripped — `src/utils/session.ts:33`, `:42`). No producer writes a token there; the
  legacy token lives at `lichess.accessToken`, which is what this finding is about.

## Traced premises

Locate evidence, frozen. Obligations below cite these by number, never by line.

* **P1** `src/utils/session.ts:79-89` — `persistSanitizedSessions` tries `setItem(sessions)`, on
  throw tries `removeItem(sessions)`, on throw raises `SessionSanitizationError`.
* **P2** `src/utils/session.ts:95-134` — `sanitizeLegacySessions` reads, extracts tokens into an
  in-memory `migrations` list, then calls P1 synchronously before any `await`; a throw discards the
  list unreturned. `src/utils/session.ts:141-152` — native migration (`migrateLegacyLichessToken`)
  and `listLichessAccounts` run only after P2 returns.
* **P3** `src/index.tsx:19-39` — `applicationStartup` awaits `initializePersistedSessions`; on
  `SessionSanitizationError` it rethrows, so neither i18n nor `<App />` is initialised and the

## Decisions and trade-offs

### Decided autonomously

* **D1 — Terminal behaviour.** Question: when storage refuses both the sanitised write and the
  removal, what ends the launch? Chosen: fail closed visibly (O3), retry automatically on every
  launch with the legacy record as its own marker plus an in-session "Try again" (O2), and accept
  the token at rest until a later launch succeeds (known limit K1). Rejected: (a) automatic
  `localStorage.clear()` — wipes un-migrated practice progress and review logs, engine
  registrations, keybinds and player settings that nothing can rebuild, and bypasses the
  user-confirmed migration guard (P5); (b) a persistent "must erase" marker — needs a successful
  write to the same failing storage, and the record already marks itself; (c) a native wipe of the
  webview's browsing data — the same data loss as (a) plus a new IPC command and capability; (d) a
  "reset" button on the failure view that clears storage — the same data loss and guard bypass as
  (a); the guarded Help → Clear saved data stays the reset route once the app starts. Reason: the
  security property that matters — the token is never used, migrated or shown — is held by failing
  closed before mount (P4), while every rejected option trades irreplaceable user data for an erase
  that runs through the storage that has just failed. Reversal path: add a guarded erase step to
  `persistSanitizedSessions` if a storage engine is measured where removal throws but a wider erase
  succeeds.
* **D2 — The fail-closed launch shows a view rather than a blank window**, with title, one
  explanation and "Try again". Technical under rule 33: it changes only what a broken-storage
  launch shows (an explanation instead of nothing); nothing is charged, promised or withheld that
  the blank window did not already withhold. Reversal path: revert the O3 render branch in
  `src/index.tsx`.

### Known limits

* **K1** — while both operations keep failing, the token stays at rest in the webview's storage,
  where it has been since the legacy version wrote it. No feature reads it (P4) and no IPC receives
  it (O1). Not worse than today.

# Plan: terminal behaviour when legacy session sanitisation cannot be persisted (f-20260914-16)

## Goal

When ChessFable starts and Web Storage refuses both the sanitised overwrite and the removal of the
`sessions` key, the launch ends in a defined, visible, fail-closed terminal state:

* a legacy Lichess bearer token this launch read is never handed to migration or to any feature;
* a token that could not be erased is revoked at Lichess, so the copy left at rest no longer works;
* the user sees why the app did not start, in a window that is actually shown, and can retry;
* every later launch retries the scrub automatically;
* no other saved user data is destroyed.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-16`:

* **Where:** `src/utils/session.ts:79` (sanitised `setItem`, then fallback `removeItem`), startup abort at `:132`.
* **Defect (reported):** when rewriting a legacy serialised session record without its `accessToken`, a failing `setItem` falls back to `removeItem`; if that also throws, the original record — including the bearer token — stays in Web Storage.   irreplaceable user data for an erase that runs through the storage that has just failed. Cost to
  the user: after such a launch they sign in to Lichess again. Reversal path: drop the O5 call in
  `src/utils/session.ts` and the command in `src-tauri/src/oauth.rs`.
  *Correction to the round-1 briefing:* revision 1 chose (a)-(d)'s rejection but left the token
  working at rest (its known limit K1). `review-tauri-security` showed that this leaves the
  reported defect unresolved; O5 replaces that limit.
* **D2 — The fail-closed launch shows a view rather than a blank window**, with title, one
  explanation in three states and "Try again". Technical under rule 33: it changes only what a
  broken-storage launch shows (an explanation instead of nothing); nothing is charged or promised,

### Known limits

* **K1** — a token stays *working* at rest only while both erases fail **and** revocation fails
  (for example offline); the view says so, and every retry repeats both. A token the renderer could
  not read at all (storage access refused for reads too) is neither readable by any renderer code
  nor revocable from it; it is scrubbed or migrated on the first launch whose storage works.

# Plan: terminal behaviour when legacy session sanitisation cannot be persisted (f-20260914-16)

## Goal

When ChessFable starts and Web Storage refuses both the sanitised overwrite and the removal of the
`sessions` key, the launch ends in a defined, visible, fail-closed terminal state:

* a legacy Lichess bearer token this launch read is never handed to migration or to any feature;
* a token that could not be erased is revoked at Lichess, so the copy left at rest no longer works;
* the user sees why the app did not start, in a window that is actually shown, and can retry;
* every later launch retries the scrub automatically;
* no other saved user data is destroyed.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-16`:

* **Where:** `src/utils/session.ts:79` (sanitised `setItem`, then fallback `removeItem`), startup abort at `:132`.
* **Defect (reported):** when rewriting a legacy serialised session record without its `accessToken`, a failing `setItem` falls back to `removeItem`; if that also throws, the original record — including the bearer token — stays in Web Storage. Startup aborts but neither erases nor retries, so the token remains renderer-readable.
* **Why it matters:** `CLAUDE.md` Conventions and `.claude/rules/async-resource-invariants.md` — a bearer token must never remain in the renderer; the sanitisation's failure path is exactly where it matters.
* **Open question:** what is the terminal behaviour when storage refuses both the sanitised write and the removal — clear the whole storage area, retry on next start with a persistent "must erase" marker, or refuse to continue with an explicit user-visible reset?

## Threat model and non-goals

Frozen in round 1.

* **Accidental input only.** Web Storage that throws on `setItem` and `removeItem` because of
  quota, I/O or a disabled/denied storage area, on the user's own machine, on Linux (WebKitGTK),
  macOS (WKWebView) and Windows (WebView2). The design must not depend on *which* storage operation
  throws on which engine: every combination of the two operations throwing or returning is handled.
* **No adversary.** Script already executing in the renderer could read the record before any
  sanitiser runs; that is outside this finding. The renderer's CSP and the IPC boundary are unchanged.
* **Not in scope:** fields nested inside `lichess.account` / `chessCom.stats` (`z.custom`, not
  recursively stripped — `src/utils/session.ts:33`, `:42`). No producer writes a token there; the
  legacy token lives at `lichess.accessToken`, which is what this finding is about.

## Approach

### O1 — Both erase operations failing ends the launch's credential handling

MANDATE: "a failing `setItem` falls back to `removeItem`; if that also throws … Startup aborts".

* The erase attempts stay exactly the sanitised overwrite, then removal of the `sessions` key
  (P1). No further storage operation is added (D1).
* When both throw, `initializePersistedSessions` rejects with `SessionSanitizationError`, and in
  that call: no `migrateLegacyLichessToken` call, no `listLichessAccounts` call, no Lichess profile
  fetch, no further write to `sessions`. The tokens this launch read go to O5 and nowhere else.
* When either operation succeeds, behaviour is unchanged from today.
* **Verification (unit, `src/utils/session.test.ts`):** a legacy record with a token, both
  `Storage.prototype.setItem` and `removeItem` throwing: the call rejects with
  `SessionSanitizationError`; the migration and account-list mocks were not called. This case has
  no unit test today; `src/index.test.tsx` only mocks the rejection.

### O5 — A token that could not be erased is revoked at Lichess

MANDATE: "a bearer token must never remain in the renderer"; "refuse to continue with an explicit
user-visible reset". Depends on O1.

* When O1's failure occurs and this launch read one or more legacy tokens (P2), each token is sent
  to a new native command, `revoke_legacy_lichess_token(token)`, before the rejection settles. The
  command revokes the token through the existing `OAuthServices::revoke_token` (P10); it writes no
  keyring, registry or file, needs no handle, and is not platform-gated (plain HTTPS, unlike the
  migration door). Its error is the existing generic `OAuthFailure` and never echoes the token.
* The renderer never makes the HTTP request itself and never logs, displays or persists a token;
  each token leaves `src/utils/session.ts` only as the argument of that one command.
* Each revocation failure is caught. `SessionSanitizationError` carries only a summary for the
  view: whether a legacy Lichess sign-in was found in this launch, and whether every found token
  was revoked. It carries no token and no username.
* After a successful revocation the record is still at rest (storage refused both erases), but it
  is a dead credential: on a later launch with working storage, P2's migration fails Lichess's
  identity check and the sanitiser scrubs it as today.
* The command's `#[tauri::command]` entry point is a single delegation with no logic of its own —
  `<internal>(token, &ProdOAuthServices::new(state.json_http_client.clone()))` — the shape of
  `migrate_legacy_lichess_token` and `remove_lichess_account` (P10); the internal function owns
  the behaviour and is what the unit tests drive.
* The production transport is proven, not trusted: `ProdOAuthServices` takes the token URL it
  revokes against as a field — the production constructor keeps `LICHESS_TOKEN_URL`, a test-only
  constructor injects a loopback URL — mirroring the exchange path's existing
  `token_url_override` (`src-tauri/src/oauth.rs:426`, `:433`). This changes no production URL.
* **Verification:** Rust — the command's internal function, generic over `OAuthServices`, calls
  `revoke_token` exactly once with the supplied token and maps a revocation failure to the generic
  error without the token in its text (`src-tauri/src/oauth.rs` tests, `MockServices`). Rust
  transport — `ProdOAuthServices::revoke_token` against a loopback HTTP server built in the test:
  the request is `DELETE` on the token path with `Authorization: Bearer <token>`; a 2xx answer is
  `Ok`; a non-2xx answer and a refused connection are the generic error, whose text does not
  contain the token. Replacing the production body with an unconditional `Ok(())` fails this test.
  Unit
  (`src/utils/session.test.ts`) — both erases failing with a token: the revoke command is called
  once per token with that token, migration/list are not called, and the error reports
  found-and-revoked; with the revoke command rejecting, the error reports found-not-revoked; with no
  token in storage, no revoke call and the error reports nothing found.

### O2 — Retry happens on every launch and on request, with no marker

MANDATE: "neither erases nor retries"; "retry on next start with a persistent 'must erase' marker".

* The legacy record itself is the marker: `sanitizeLegacySessions` detects a token under
  `lichess.accessToken` and runs on every launch before anything mounts (P2, P3, P4). No marker key
  is written — writing one needs the same storage write that just failed.
* In-session retry is the "Try again" action of O3, which reloads the window and so re-runs O1
  and O5.
* **Verification (unit, `src/utils/session.test.ts`):** after an O1 failure, with storage working
  again, the next `initializePersistedSessions` scrubs the token from storage and migrates it
  exactly once.

### O3 — The fail-closed launch is visible instead of a blank, hidden window

MANDATE: "refuse to continue with an explicit user-visible reset". Depends on O5's summary.

* On `SessionSanitizationError`, `src/index.tsx` never renders `<App />` (no router, no feature
  route, no Jotai-backed feature mounts). It attempts `initializeI18n` (its failure does not prevent
  the view), renders a standalone view inside a `MantineProvider` built from the app's theme
  factory (P6) and an `I18nextProvider`, and then reveals the native window through the existing
  `tauri.closeSplashscreen()` (P8), because `<App />`, which owns that reveal, does not mount. A
  failed reveal is logged like the diagnostic below and does not reject the startup promise.
* The view has a title, one explanation and one "Try again" action that reloads the window. The
  explanation is correct for every `SessionSanitizationError` (P2: the error also occurs when no
  record carried a token), in three states from O5's summary:
  * no legacy sign-in found — ChessFable could not update its saved account data and did not start;
  * found and revoked — a saved Lichess sign-in could not be removed from local storage, so

  There is no storage-reset action (D1).
* It logs one sanitised diagnostic through `logFailureSafely` naming the failure class and O5's

* `applicationStartup` settles without an unhandled rejection once the view is rendered and the

* The view is a new component in `src/components/home/`, claimed by the existing

* Strings go through i18next; each new key is added to all 16 catalogues in `src/translation/`

* **Verification (unit):** `src/index.test.tsx` — sanitisation failure renders the view and not

## Decisions and trade-offs

### Decided autonomously

* **D1 — Terminal behaviour.** Question: when storage refuses both the sanitised write and the
  removal, what ends the launch? Chosen: fail closed visibly (O3); revoke at Lichess every token
  this launch read and could not erase (O5); retry automatically on every launch with the legacy
  record as its own marker, plus an in-session "Try again" (O2). Rejected: (a) automatic
  `localStorage.clear()` — wipes un-migrated practice progress and review logs, engine
  registrations, keybinds and player settings that nothing can rebuild, and bypasses the
  user-confirmed migration guard (P5); (b) a persistent "must erase" marker — needs a successful
  write to the same failing storage, and the record already marks itself; (c) a native wipe of the
  webview's browsing data — the same data loss as (a); (d) a "reset" button on the failure view
  that clears storage — the same data loss and guard bypass as (a); the guarded Help → Clear saved
  data stays the reset route once the app starts; (e) revoking only after the user confirms on the
  failure view — leaves a working token at rest for as long as the user keeps choosing "Try
  again", and adds a consent state to a screen that otherwise has one action; (f) invalidating
  through the existing `migrate_legacy_lichess_token` then `remove_lichess_account` — the migration
  door refuses off unix, so Windows would keep a working token, and it writes the token into the
  keyring only to delete it (P10). Reason: the security property — no working legacy token outlives
  a launch that could not erase it, and none is used, migrated or shown — holds without trading
  irreplaceable user data for an erase that runs through the storage that has just failed. Cost to
  the user: after such a launch they sign in to Lichess again. Reversal path: drop the O5 call in
  `src/utils/session.ts` and the command in `src-tauri/src/oauth.rs`.
  *Correction to the round-1 briefing:* revision 1 chose (a)-(d)'s rejection but left the token
  working at rest (its known limit K1). `review-tauri-security` showed that this leaves the
  reported defect unresolved; O5 replaces that limit.
* **D2 — The fail-closed launch shows a view rather than a blank window**, with title, one
  explanation in three states and "Try again". Technical under rule 33: it changes only what a
  broken-storage launch shows (an explanation instead of nothing); nothing is charged or promised,
  and the one user-facing consequence (signing in to Lichess again) follows from D1's security
  property, which `CLAUDE.md` Conventions already fix. Reversal path: revert the O3 render branch
  in `src/index.tsx`.

### Known limits

* **K1** — a token stays *working* at rest only while both erases fail **and** revocation fails
  (for example offline); the view says so, and every retry repeats both. A token the renderer could
  not read at all (storage access refused for reads too) is neither readable by any renderer code
  nor revocable from it; it is scrubbed or migrated on the first launch whose storage works.

### plan-r4.md

# Plan: terminal behaviour when legacy session sanitisation cannot be persisted (f-20260914-16)

## Goal

When ChessFable starts and Web Storage refuses both the sanitised overwrite and the removal of the
`sessions` key, the launch ends in a defined, visible, fail-closed terminal state:

* a legacy Lichess bearer token this launch read is never handed to migration or to any feature;
* a token that could not be erased is revoked at Lichess, so the copy left at rest no longer works;
* the user sees why the app did not start, in a window that is actually shown, and can retry;
* every later launch retries the scrub automatically;
* no other saved user data is destroyed.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-16`:

* **Where:** `src/utils/session.ts:79` (sanitised `setItem`, then fallback `removeItem`), startup abort at `:132`.
* **Defect (reported):** when rewriting a legacy serialised session record without its `accessToken`, a failing `setItem` falls back to `removeItem`; if that also throws, the original record — including the bearer token — stays in Web Storage. Startup aborts but neither erases nor retries, so the token remains renderer-readable.
* **Why it matters:** `CLAUDE.md` Conventions and `.claude/rules/async-resource-invariants.md` — a bearer token must never remain in the renderer; the sanitisation's failure path is exactly where it matters.
* **Open question:** what is the terminal behaviour when storage refuses both the sanitised write and the removal — clear the whole storage area, retry on next start with a persistent "must erase" marker, or refuse to continue with an explicit user-visible reset?

## Threat model and non-goals

Frozen in round 1.

* **Accidental input only.** Web Storage that throws on `setItem` and `removeItem` because of
  quota, I/O or a disabled/denied storage area, on the user's own machine, on Linux (WebKitGTK),
  macOS (WKWebView) and Windows (WebView2). The design must not depend on *which* storage operation
  throws on which engine: every combination of the two operations throwing or returning is handled.
* **No adversary.** Script already executing in the renderer could read the record before any
  sanitiser runs; that is outside this finding. The renderer's CSP and the IPC boundary are unchanged.
* **Not in scope:** fields nested inside `lichess.account` / `chessCom.stats` (`z.custom`, not
  recursively stripped — `src/utils/session.ts:33`, `:42`). No producer writes a token there; the
  legacy token lives at `lichess.accessToken`, which is what this finding is about.

## Approach

### O1 — Both erase operations failing ends the launch's credential handling

MANDATE: "a failing `setItem` falls back to `removeItem`; if that also throws … Startup aborts".

* The erase attempts stay exactly the sanitised overwrite, then removal of the `sessions` key
  (P1). No further storage operation is added (D1).
* When both throw, `initializePersistedSessions` rejects with `SessionSanitizationError`, and in
  that call: no `migrateLegacyLichessToken` call, no `listLichessAccounts` call, no Lichess profile
  fetch, no further write to `sessions`. The tokens this launch read go to O5 and nowhere else.
* When either operation succeeds, behaviour is unchanged from today.
* **Verification (unit, `src/utils/session.test.ts`):** a legacy record with a token, both
  `Storage.prototype.setItem` and `removeItem` throwing: the call rejects with
  `SessionSanitizationError`; the migration and account-list mocks were not called. This case has
  no unit test today; `src/index.test.tsx` only mocks the rejection.

### O5 — A token that could not be erased is revoked at Lichess

MANDATE: "a bearer token must never remain in the renderer"; "refuse to continue with an explicit
user-visible reset". Depends on O1.

* When O1's failure occurs and this launch read one or more legacy tokens (P2), each token is sent
  to a new native command, `revoke_legacy_lichess_token(token)`, before the rejection settles. The
  command revokes the token through the existing `OAuthServices::revoke_token` (P10); it writes no
  keyring, registry or file, needs no handle, and is not platform-gated (plain HTTPS, unlike the
  migration door). Its error is the existing generic `OAuthFailure` and never echoes the token.
* The renderer never makes the HTTP request itself and never logs, displays or persists a token;
  each token leaves `src/utils/session.ts` only as the argument of that one command.
* Each revocation failure is caught. `SessionSanitizationError` carries only a summary for the
  view: whether a legacy Lichess sign-in was found in this launch, and whether every found token
  was revoked. It carries no token and no username.
* After a successful revocation the record is still at rest (storage refused both erases), but it
  is a dead credential: on a later launch with working storage, P2's migration fails Lichess's
  identity check and the sanitiser scrubs it as today.
* The command's `#[tauri::command]` entry point is a single delegation with no logic of its own —
  `<internal>(token, &ProdOAuthServices::new(state.json_http_client.clone()))` — the shape of
  `migrate_legacy_lichess_token` and `remove_lichess_account` (P10); the internal function owns
  the behaviour and is what the unit tests drive.
* The production transport is proven, not trusted: `ProdOAuthServices` takes the token URL it
  revokes against as a field — the production constructor keeps `LICHESS_TOKEN_URL`, a test-only
  constructor injects a loopback URL — mirroring the exchange path's existing
  `token_url_override` (`src-tauri/src/oauth.rs:426`, `:433`). This changes no production URL.
* **Verification:** Rust — the command's internal function, generic over `OAuthServices`, calls
  `revoke_token` exactly once with the supplied token and maps a revocation failure to the generic
  error without the token in its text (`src-tauri/src/oauth.rs` tests, `MockServices`). Rust
  transport — `ProdOAuthServices::revoke_token` against a loopback HTTP server built in the test:
  the request is `DELETE` on the token path with `Authorization: Bearer <token>`; a 2xx answer is
  `Ok`; a non-2xx answer and a refused connection are the generic error, whose text does not
  contain the token. Replacing the production body with an unconditional `Ok(())` fails this test.
  Unit
  (`src/utils/session.test.ts`) — both erases failing with a token: the revoke command is called
  once per token with that token, migration/list are not called, and the error reports
  found-and-revoked; with the revoke command rejecting, the error reports found-not-revoked; with no
  token in storage, no revoke call and the error reports nothing found.

### O2 — Retry happens on every launch and on request, with no marker

MANDATE: "neither erases nor retries"; "retry on next start with a persistent 'must erase' marker".

* The legacy record itself is the marker: `sanitizeLegacySessions` detects a token under
  `lichess.accessToken` and runs on every launch before anything mounts (P2, P3, P4). No marker key
  is written — writing one needs the same storage write that just failed.
* In-session retry is the "Try again" action of O3, which reloads the window and so re-runs O1
  and O5.
* **Verification (unit, `src/utils/session.test.ts`):** after an O1 failure, with storage working
  again, the next `initializePersistedSessions` scrubs the token from storage and migrates it
  exactly once.

### O3 — The fail-closed launch is visible instead of a blank, hidden window

MANDATE: "refuse to continue with an explicit user-visible reset". Depends on O5's summary.

* On `SessionSanitizationError`, `src/index.tsx` never renders `<App />` (no router, no feature
  route, no Jotai-backed feature mounts). It attempts `initializeI18n` (its failure does not prevent
  the view), renders a standalone view inside a `MantineProvider` built from the app's theme
  factory (P6) and an `I18nextProvider`, and then reveals the native window through the existing
  `tauri.closeSplashscreen()` (P8), because `<App />`, which owns that reveal, does not mount. A
  failed reveal is logged like the diagnostic below and does not reject the startup promise.
* The view has a title, one explanation and one "Try again" action that reloads the window. The
  explanation is correct for every `SessionSanitizationError` (P2: the error also occurs when no
  record carried a token), in three states from O5's summary:
  * no legacy sign-in found — ChessFable could not update its saved account data and did not start;
  * found and revoked — a saved Lichess sign-in could not be removed from local storage, so
    ChessFable signed it out at Lichess; signing in again is possible once ChessFable starts;
  * found, not revoked — the same, but signing it out at Lichess also failed (for example without a
    connection); "Try again" repeats both.
  There is no storage-reset action (D1).
* It logs one sanitised diagnostic through `logFailureSafely` naming the failure class and O5's
  summary only — never storage contents, a username or a token.
* `applicationStartup` settles without an unhandled rejection once the view is rendered and the
  reveal attempted. Non-sanitisation session failures keep today's behaviour (the app mounts).
* The view is a new component in `src/components/home/`, claimed by the existing
  `accounts-remote` coverage area (P7): no edit to `coverage-areas.json` or any baseline. Every new
  line, function and branch is covered by unit tests so no area ratio drops.
* Strings go through i18next; each new key is added to all 16 catalogues in `src/translation/`
  with a real translation (P7); `pnpm i18n:check` and `pnpm i18n:jsx` green.

## Decisions and trade-offs

### Decided autonomously

* **D1 — Terminal behaviour.** Question: when storage refuses both the sanitised write and the
  removal, what ends the launch? Chosen: fail closed visibly (O3); revoke at Lichess every token
  this launch read and could not erase (O5); retry automatically on every launch with the legacy
  record as its own marker, plus an in-session "Try again" (O2). Rejected: (a) automatic
  `localStorage.clear()` — wipes un-migrated practice progress and review logs, engine
  registrations, keybinds and player settings that nothing can rebuild, and bypasses the
  user-confirmed migration guard (P5); (b) a persistent "must erase" marker — needs a successful
  write to the same failing storage, and the record already marks itself; (c) a native wipe of the
  webview's browsing data — the same data loss as (a); (d) a "reset" button on the failure view
  that clears storage — the same data loss and guard bypass as (a); the guarded Help → Clear saved
  data stays the reset route once the app starts; (e) revoking only after the user confirms on the
  failure view — leaves a working token at rest for as long as the user keeps choosing "Try
  again", and adds a consent state to a screen that otherwise has one action; (f) invalidating
  through the existing `migrate_legacy_lichess_token` then `remove_lichess_account` — the migration
  door refuses off unix, so Windows would keep a working token, and it writes the token into the
  keyring only to delete it (P10). Reason: the security property — no working legacy token outlives
  a launch that could not erase it, and none is used, migrated or shown — holds without trading
  irreplaceable user data for an erase that runs through the storage that has just failed. Cost to
  the user: after such a launch they sign in to Lichess again. Reversal path: drop the O5 call in
  `src/utils/session.ts` and the command in `src-tauri/src/oauth.rs`.
  *Correction to the round-1 briefing:* revision 1 chose (a)-(d)'s rejection but left the token
  working at rest (its known limit K1). `review-tauri-security` showed that this leaves the
  reported defect unresolved; O5 replaces that limit.
* **D2 — The fail-closed launch shows a view rather than a blank window**, with title, one
  explanation in three states and "Try again". Technical under rule 33: it changes only what a
  broken-storage launch shows (an explanation instead of nothing); nothing is charged or promised,
  and the one user-facing consequence (signing in to Lichess again) follows from D1's security
  property, which `CLAUDE.md` Conventions already fix. Reversal path: revert the O3 render branch
  in `src/index.tsx`.

### Known limits

* **K1** — a token stays *working* at rest only while both erases fail **and** revocation fails
  (for example offline); the view says so, and every retry repeats both. A token the renderer could
  not read at all (storage access refused for reads too) is neither readable by any renderer code
  nor revocable from it; it is scrubbed or migrated on the first launch whose storage works.
