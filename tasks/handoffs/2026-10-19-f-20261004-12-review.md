# Plan: Sweep crash-orphaned engine-image leaves

## Goal

After a crash between installing an engine-image leaf and registering it, the next startup or shutdown cleanup removes that unreferenced regular file, and the same pass removes a crash-left `.atomic-<uuid>` temporary sibling. A leaf that is still referenced, still being issued, or living in a directory this process does not hold the application-data lock for stays on disk.

## MANDATE

### A crash between engine-image install and registration leaves an unreferenced image nothing ever removes

* **ID:** f-20261004-12 · **Status:** open · **Area:** native-fs · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** 4178af2d-b3e9-4852-871b-436172468f49
* **Where:** `src-tauri/src/main.rs:1768-1806` (`issue_engine_image_blocking`: `atomic_replace_leaf_identified` commits the UUID leaf, then `register_engine_image` persists it); `src-tauri/src/infra/fs.rs:1664-1724` (Unix `.atomic-<UUID>` temporary siblings, Windows equivalent near `:3787`).
* **Defect:** if the process dies after the image leaf is renamed into the EngineImages directory and before the registry save that registers it, the leaf has no registry entry and no `image_cleanup` intent. Startup and shutdown cleanup (`cleanup_engine_images`, `src-tauri/src/infra/path_authority/mod.rs:7235`) visit only recorded intents, and nothing enumerates that directory (the reason `d-20260905-09` gives). The same holds for an `.atomic-<UUID>` temporary sibling left by a crash during the copy. Each such crash leaves one file the user can neither see nor remove from the app.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` (cleanup on every exit path, bounded retention). This finding is the crash half of `f-20260914-21`. The plan for that finding (`tasks/plans/2026-10-04-engine-image-cleanup-intent.md`, drain planner 2026-10-04) records an intent only when an in-process removal fails, and treats the crash window as out of scope.
* **Open question:** how is ownership of an unreferenced UUID leaf or `.atomic-*` sibling proven at startup, so that a sweep can delete it? A directory sweep is unsafe today: there is no single-instance guard (`f-20260922-07`), so a second instance's in-memory registry does not know the first instance's freshly registered or in-flight images, and its sweep would delete them. The candidates are (a) a sweep gated on the single-instance guard from `f-20260922-07` plus the issuance lease count, or (b) a write-ahead intent whose identity comes from the temporary inode before the rename (rename preserves the inode). Option (b) changes the atomic-replace protocol and still leaves temporary siblings from a crash before the intent is written.
* **Found by:** drain planner for `f-20260914-21` (Claude Code, 2026-10-04, session 4178af2d-b3e9-4852-871b-436172468f49), from the locate probe facts: no single-instance plugin (`src-tauri/Cargo.toml`, `src-tauri/src/main.rs:2460`), no startup enumeration of the EngineImages directory. Not reproduced.
* **Prerequisite status (2026-10-08, drain session fa6786ed-3e23-4701-b1a3-05a243d9a80b):** the single-instance guard this entry names as missing now exists — `f-20260922-07`, commits `cd058c1a` and `870da73b`: `.setup` takes a non-blocking advisory lock (`instance.lock`) in every distinct per-user root the app writes (application data, configuration, local data) before credentials, the path authority or any window exist, and refuses a second process sharing any of them (`d-20261007-31`, `d-20261008-01`). The sweep may rely on one process per root except on a filesystem without advisory locks, where startup logs a warning and runs unguarded (`d-20261007-32`). The open question about proving ownership of an unreferenced leaf is otherwise unchanged.

## Threat model and non-goals

Adversary and environment, frozen for round 1:

- One ChessFable process holds the advisory lock on the application-data directory that parents `engine-images`. A second process that shares that directory is refused at admission (`d-20261008-01`). The sweep may delete only while that lock is held by this process.
- `engine-images` contains only leaves this process writes: UUID-named image files and `.atomic-<uuid>` temps from `atomic_replace`. The only production writer is `issue_engine_image_blocking`.
- A crash, kill, or power loss can leave a renamed UUID leaf with no registry row and no `image_cleanup` intent, or an `.atomic-<uuid>` regular file whose rename never happened.
- Another root (configuration or local data) can be locked while the application-data filesystem cannot take an advisory lock. `InstanceAdmission::Owned` is then true and the application-data directory is not locked (`d-20261008-01`). The sweep must stay off in that case.
- An issuance lease can be in flight across the unlocked copy. The sweep must not delete that leaf.
- A name in the directory can be a directory, a symlink, or another non-regular node. Those are not deleted and not recursed into.
- Listing can exceed the sweep's cap. A partial list is not a safe deletion set.
- Registry paths can fail to parse. An unknown referenced name is not a license to delete.
- Logs must not emit `Error::diagnostic()` from this sweep (native path text).

Non-goals: changing `atomic_replace`, reserving registry capacity, merging with the macOS engine-launch sibling sweep, IPC or Specta changes, and deleting anything outside `engine-images`.

## Approach

### When the sweep runs

`cleanup_engine_images` gains one pass over `engine-images`, after the existing intent walk, on the same `&mut self` and the same `image_dir` the caller already passed. Call sites stay `cleanup_engine_images(&image_dir, false)`. No signature change, no new cancellation token, no IPC change.

The pass runs only when both gates hold:

1. This authority has been told the application-data lock is held. The flag lives on `PathAuthority`, default `false`, and is not serialized. `set_engine_image_sweep_permitted(bool)` is the only writer. Tests and every `open` / `open_for_app` stay false until setup sets it.
2. `self.active_image_issuances.active.load(Ordering::Acquire) == 0` while this method holds `&mut self`. Do not add a public counter. The field stays private. Same-module reads are enough.

If the flag is false, skip the pass with no new log. The unguarded-filesystem warning already exists. If the lease count is non-zero, skip the whole pass. `log::debug` is allowed; the production filter is Info, so users do not see it. Orphans wait for a later pass. Shutdown already seals, waits until the count is zero, then calls cleanup, and a sealed authority refuses new issuances, so shutdown is the pass that runs when startup skipped an in-flight issuance.

### What the sweep deletes

List with `read_directory_entries_at(image_dir.directory.as_file(), &CancellationToken::new(), Some(MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)), &mut |_| true)`. Do not call `AuthorizedDir::entries`. The limit is 8192. 8192 entries succeed. The 8193rd makes the call return `Err` and yields no partial list.

Build the protected-name set after the intent walk has updated `image_cleanup`. A name is protected when it is `file_name()` of any `persistent`, `retired_attachments`, or `image_cleanup` entry. Match the leaf name, not the parent path. `provisional_attachments` are ids, not paths, and do not protect a file by themselves. If any of those three collections has an entry whose path cannot be turned into a leaf name, skip the whole pass, log the category, and delete nothing.

On a listing `Err`, `log::warn` with `error.category()` only and delete nothing this pass. Do not fail `cleanup_engine_images` for a sweep listing failure.

For each listed entry, delete only when all of these hold:

- `kind` is `DirectoryEntryKind::RegularFile`.
- The name is either a UUID (`Uuid::parse_str` on the whole name) or a production temp: the name starts with `.atomic-` and the remainder parses as `Uuid`. No other prefix. This is the same `temp_name()` text on Unix and Windows.
- The name is not in the protected set.
- `open_leaf_identified` returns an identity equal to the listed `DirectoryEntry.identity`. Missing, `Conflict`, or a different identity skips that name and does not unlink. Any other open error logs the leaf name and `error.category()` and continues.
- `remove_leaf_identified` then unlinks that identity. One unlink error logs the leaf name and `error.category()` and does not abort the rest of the pass.

No recursive delete. No deletion of directories, symlinks, junctions, or `Other`. Do not log `diagnostic()`.

A dropped identity-mismatched intent no longer protects its leaf name. The file that remains is not the registered inode. If it is still an unreferenced UUID regular file, this pass may delete it. That is intentional.

### Failure and reconcile

Existing intent-walk errors still return `Err` and still fail the caller. The sweep does not run on that `Err` path. When `image_cleanup` is empty, today's early return must not skip the sweep: a pending durability retry still runs first; if that retry returns `Err`, return it and do not sweep; if it returns `Ok`, or there is nothing to retry, run the sweep and then return `Ok`. Sweep list and unlink failures are logged and left for the next startup or shutdown pass. They must not turn a successful reconcile into `Err` after attachments were already committed.

## Threat model and non-goals

Adversary and environment, frozen for round 1:

- One ChessFable process holds the advisory lock on the application-data directory that parents `engine-images`. A second process that shares that directory is refused at admission (`d-20261008-01`). The sweep may delete only while that lock is held by this process.

- Listing can exceed the sweep's cap. A partial list is not a safe deletion set.
- Registry paths can fail to parse. An unknown referenced name is not a license to delete.
- Logs must not emit `Error::diagnostic()` from this sweep (native path text).

Non-goals: changing `atomic_replace`, reserving registry capacity, merging with the macOS engine-launch sibling sweep, IPC or Specta changes, and deleting anything outside `engine-images`.

## Approach

### When the sweep runs

`cleanup_engine_images` gains one pass over `engine-images`, after the existing intent walk, on the same `&mut self` and the same `image_dir` the caller already passed. Call sites stay `cleanup_engine_images(&image_dir, false)`. No signature change, no new cancellation token, no IPC change.

The pass runs only when both gates hold:

1. This authority has been told the application-data lock is held. The flag lives on `PathAuthority`, default `false`, and is not serialized. `set_engine_image_sweep_permitted(bool)` is the only writer. Tests and every `open` / `open_for_app` stay false until setup sets it.
2. `self.active_image_issuances.active.load(Ordering::Acquire) == 0` while this method holds `&mut self`. Do not add a public counter. The field stays private. Same-module reads are enough.

If the flag is false, skip the pass with no new log. The unguarded-filesystem warning already exists. If the lease count is non-zero, skip the whole pass. `log::debug` is allowed; the production filter is Info, so users do not see it. Orphans wait for a later pass. Shutdown already seals, waits until the count is zero, then calls cleanup, and a sealed authority refuses new issuances, so shutdown is the pass that runs when startup skipped an in-flight issuance.

### What the sweep deletes

List with `read_directory_entries_at(image_dir.directory.as_file(), &CancellationToken::new(), Some(MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)), &mut |_| true)`. Do not call `AuthorizedDir::entries`. The limit is 8192. 8192 entries succeed. The 8193rd makes the call return `Err` and yields no partial list.

Build the protected-name set after the intent walk has updated `image_cleanup`. A name is protected when it is the normal leaf name of any `persistent`, `retired_attachments`, or `image_cleanup` entry. A normal leaf name is `file_name()` when that name is non-empty and not `.` or `..`. Match the leaf name, not the parent path. `provisional_attachments` are ids, not paths, and do not protect a file by themselves. If any of those three collections has an entry whose `to_path()` fails, or whose path has no normal leaf name, skip the whole pass, log the category, and delete nothing.

On a success path the existing intent walk leaves `image_cleanup` empty: an identity-matching intent is unlinked and dropped, and a parent or identity mismatch drops the row without unlinking. A successful `cleanup_engine_images` therefore does not keep an intent target on disk. Rows that remain are still part of the protected set. Today they remain only when the walk is about to return `Err`, and that path does not sweep.

On a listing `Err`, `log::warn` with `error.category()` only and delete nothing this pass. Do not fail `cleanup_engine_images` for a sweep listing failure.

For each listed entry, delete only when all of these hold:

- `kind` is `DirectoryEntryKind::RegularFile`.
- The name is either a UUID (`Uuid::parse_str` on the whole name) or a production temp: the name starts with `.atomic-` and the remainder parses as `Uuid`. No other prefix. This is the same `temp_name()` text on Unix and Windows.
- The name is not in the protected set.
- `open_leaf_identified` returns an identity equal to the listed `DirectoryEntry.identity`. Missing, `Conflict`, or a different identity skips that name and does not unlink. Any other open error logs the leaf name and `error.category()` and continues.
- `remove_leaf_identified` then unlinks that identity. One unlink error logs the leaf name and `error.category()` and does not abort the rest of the pass.

No recursive delete. No deletion of directories, symlinks, junctions, or `Other`. Do not log `diagnostic()`.

A dropped identity-mismatched intent no longer protects its leaf name. The file that remains is not the registered inode. If it is still an unreferenced UUID regular file, this pass may delete it. That is intentional.

### Failure and reconcile

Existing intent-walk errors still return `Err` and still fail the caller. The sweep does not run on that `Err` path. When `image_cleanup` is empty, today's early return must not skip the sweep: a pending durability retry still runs first; if that retry returns `Err`, return it and do not sweep; if it returns `Ok`, or there is nothing to retry, run the sweep and then return `Ok`. Sweep list and unlink failures are logged and left for the next startup or shutdown pass. They must not turn a successful reconcile into `Err` after attachments were already committed.

## Threat model and non-goals

Adversary and environment, frozen for round 1:

- One ChessFable process holds the advisory lock on the application-data directory that parents `engine-images`. A second process that shares that directory is refused at admission (`d-20261008-01`). The sweep may delete only while that lock is held by this process.

- Registry paths can fail to parse. An unknown referenced name is not a license to delete.

## Approach

### When the sweep runs

`cleanup_engine_images` gains one pass over `engine-images`, after the existing intent walk, on the same `&mut self` and the same `image_dir` the caller already passed. Call sites stay `cleanup_engine_images(&image_dir, false)`. No signature change, no new cancellation token, no IPC change.

The pass runs only when both gates hold:

1. This authority has been told the application-data lock is held. The flag lives on `PathAuthority`, default `false`, and is not serialized. `set_engine_image_sweep_permitted(bool)` is the only writer. Tests and every `open` / `open_for_app` stay false until setup sets it.
2. `self.active_image_issuances.active.load(Ordering::Acquire) == 0` while this method holds `&mut self`. Do not add a public counter. The field stays private. Same-module reads are enough.

If the flag is false, skip the pass with no new log. The unguarded-filesystem warning already exists. If the lease count is non-zero, skip the whole pass. `log::debug` is allowed; the production filter is Info, so users do not see it. Orphans wait for a later pass. Shutdown already seals, waits until the count is zero, then calls cleanup, and a sealed authority refuses new issuances, so shutdown is the pass that runs when startup skipped an in-flight issuance.

### What the sweep deletes

List with `read_directory_entries_at(image_dir.directory.as_file(), &CancellationToken::new(), Some(MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)), &mut |_| true)`. Do not call `AuthorizedDir::entries`. The limit is 8192. 8192 entries succeed. The 8193rd makes the call return `Err` and yields no partial list.

Build the protected-name set after the intent walk has updated `image_cleanup`. A name is protected when it is the normal leaf name of any `persistent`, `retired_attachments`, or `image_cleanup` entry. A normal leaf name is `file_name()` when that name is non-empty and not `.` or `..`. Match the leaf name, not the parent path. `provisional_attachments` are ids, not paths, and do not protect a file by themselves. If any of those three collections has an entry whose `to_path()` fails, or whose path has no normal leaf name, skip the whole pass, log the category, and delete nothing.

On a success path the existing intent walk leaves `image_cleanup` empty: an identity-matching intent is unlinked and dropped, and a parent or identity mismatch drops the row without unlinking. A successful `cleanup_engine_images` therefore does not keep an intent target on disk. Rows that remain are still part of the protected set. Today they remain only when the walk is about to return `Err`, and that path does not sweep.

On a listing `Err`, `log::warn` with `error.category()` only and delete nothing this pass. Do not fail `cleanup_engine_images` for a sweep listing failure.

For each listed entry, delete only when all of these hold:

- `kind` is `DirectoryEntryKind::RegularFile`.
- The name is either a UUID (`Uuid::parse_str` on the whole name) or a production temp: the name starts with `.atomic-` and the remainder parses as `Uuid`. No other prefix. This is the same `temp_name()` text on Unix and Windows.
- The name is not in the protected set.
- `open_leaf_identified` returns an identity equal to the listed `DirectoryEntry.identity`. Missing, `Conflict`, or a different identity skips that name and does not unlink. Any other open error logs the leaf name and `error.category()` and continues.
- `remove_leaf_identified` then unlinks that identity. One unlink error logs the leaf name and `error.category()` and does not abort the rest of the pass.

No recursive delete. No deletion of directories, symlinks, junctions, or `Other`. Do not log `diagnostic()`.

A dropped identity-mismatched intent no longer protects its leaf name. The file that remains is not the registered inode. If it is still an unreferenced UUID regular file, this pass may delete it. That is intentional.

### Failure and reconcile

Existing intent-walk errors still return `Err` and still fail the caller. The sweep does not run on that `Err` path. When `image_cleanup` is empty, today's early return must not skip the sweep: a pending durability retry still runs first; if that retry returns `Err`, return it and do not sweep; if it returns `Ok`, or there is nothing to retry, run the sweep and then return `Ok`. Sweep list and unlink failures are logged and left for the next startup or shutdown pass. They must not turn a successful reconcile into `Err` after attachments were already committed.

## Threat model and non-goals

Adversary and environment, frozen for round 1:

- One ChessFable process holds the advisory lock on the application-data directory that parents `engine-images`. A second process that shares that directory is refused at admission (`d-20261008-01`). The sweep may delete only while that lock is held by this process.
- `engine-images` contains only leaves this process writes: UUID-named image files and `.atomic-<uuid>` temps from `atomic_replace`. The only production writer is `issue_engine_image_blocking`.
- A crash, kill, or power loss can leave a renamed UUID leaf with no registry row and no `image_cleanup` intent, or an `.atomic-<uuid>` regular file whose rename never happened.
- Another root (configuration or local data) can be locked while the application-data filesystem cannot take an advisory lock. `InstanceAdmission::Owned` is then true and the application-data directory is not locked (`d-20261008-01`). The sweep must stay off in that case.
- An issuance lease can be in flight across the unlocked copy. The sweep must not delete that leaf.
- A name in the directory can be a directory, a symlink, or another non-regular node. Those are not deleted and not recursed into.
- Listing can exceed the sweep's cap. A partial list is not a safe deletion set.
- Registry paths can fail to parse. An unknown referenced name is not a license to delete.
- Logs must not emit `Error::diagnostic()` from this sweep (native path text).

Non-goals: changing `atomic_replace`, reserving registry capacity, merging with the macOS engine-launch sibling sweep, IPC or Specta changes, and deleting anything outside `engine-images`.

## Approach

### When the sweep runs

`cleanup_engine_images` gains one pass over `engine-images`, after the existing intent walk, on the same `&mut self` and the same `image_dir` the caller already passed. Call sites stay `cleanup_engine_images(&image_dir, false)`. No signature change, no new cancellation token, no IPC change.

The pass runs only when both gates hold:

1. This authority has been told the application-data lock is held. The flag lives on `PathAuthority`, default `false`, and is not serialized. `set_engine_image_sweep_permitted(bool)` is the only writer. Tests and every `open` / `open_for_app` stay false until setup sets it.
2. `self.active_image_issuances.active.load(Ordering::Acquire) == 0` while this method holds `&mut self`. Do not add a public counter. The field stays private. Same-module reads are enough.

If the flag is false, skip the pass with no new log. The unguarded-filesystem warning already exists. If the lease count is non-zero, skip the whole pass. `log::debug` is allowed; the production filter is Info, so users do not see it. Orphans wait for a later pass. Shutdown already seals, waits until the count is zero, then calls cleanup, and a sealed authority refuses new issuances, so shutdown is the pass that runs when startup skipped an in-flight issuance.

### What the sweep deletes

List with `read_directory_entries_at(image_dir.directory.as_file(), &CancellationToken::new(), Some(MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)), &mut |_| true)`. Do not call `AuthorizedDir::entries`. The limit is 8192. 8192 entries succeed. The 8193rd makes the call return `Err` and yields no partial list.

Build the protected-name set after the intent walk has updated `image_cleanup`. A name is protected when it is the normal leaf name of any `persistent`, `retired_attachments`, or `image_cleanup` entry. A normal leaf name is `file_name()` when that name is non-empty and not `.` or `..`. Match the leaf name, not the parent path. `provisional_attachments` are ids, not paths, and do not protect a file by themselves. If any of those three collections has an entry whose `to_path()` fails, or whose path has no normal leaf name, skip the whole pass, log the category, and delete nothing.

On a success path the existing intent walk leaves `image_cleanup` empty: an identity-matching intent is unlinked and dropped, and a parent or identity mismatch drops the row without unlinking. A successful `cleanup_engine_images` therefore does not keep an intent target on disk. Rows that remain are still part of the protected set. Today they remain only when the walk is about to return `Err`, and that path does not sweep.

On a listing `Err`, `log::warn` with `error.category()` only and delete nothing this pass. Do not fail `cleanup_engine_images` for a sweep listing failure.

For each listed entry, delete only when all of these hold:

- `kind` is `DirectoryEntryKind::RegularFile`.
- The name is either a UUID (`Uuid::parse_str` on the whole name) or a production temp: the name starts with `.atomic-` and the remainder parses as `Uuid`. No other prefix. This is the same `temp_name()` text on Unix and Windows.
- The name is not in the protected set.
- `open_leaf_identified` returns an identity equal to the listed `DirectoryEntry.identity`. Missing, `Conflict`, or a different identity skips that name and does not unlink. Any other open error logs the leaf name and `error.category()` and continues.
- `remove_leaf_identified` then unlinks that identity. One unlink error logs the leaf name and `error.category()` and does not abort the rest of the pass.

No recursive delete. No deletion of directories, symlinks, junctions, or `Other`. Do not log `diagnostic()`.

A dropped identity-mismatched intent no longer protects its leaf name. The file that remains is not the registered inode. If it is still an unreferenced UUID regular file, this pass may delete it. That is intentional.

### Failure and reconcile

Existing intent-walk errors still return `Err` and still fail the caller. The sweep does not run on that `Err` path. When `image_cleanup` is empty, today's early return must not skip the sweep: a pending durability retry still runs first; if that retry returns `Err`, return it and do not sweep; if it returns `Ok`, or there is nothing to retry, run the sweep and then return `Ok`. Sweep list and unlink failures are logged and left for the next startup or shutdown pass. They must not turn a successful reconcile into `Err` after attachments were already committed.

### Setup wiring and the source pin

`admit_instance_with_lock` records whether the application-data root's own lock returned `Ok`. Application data is the `None` root and is first, so a later duplicate cannot skip it. `InstanceLockGuard` exposes that bool through `app_data_locked()`. The field is false when that root's lock was unsupported, even if another root locked and the admission is `Owned`.

Setup becomes:

```rust

        app_data_locked

    crate::infra::path_authority::InstanceAdmission::Unguarded => false,

After both `PathAuthority::open_for_app` bindings and before `pgn_path_authority.install(authority)`:

```rust

That call appears once in the source, outside the macOS `cfg` split, so the installed value carries the flag. `install` moves the value in. Setting the flag after `install` would not see it.

`instance_admission_is_unconditional_and_precedes_shared_state` is updated in the same change. Keep the admission-before-credentials and admission-before-`open_for_app` checks, the single `admit_instance(` count, the three arms, and the held-elsewhere dialog assertions. Change only what the new source requires:

## Decisions and trade-offs

### Decided autonomously

Question: how is ownership of an unreferenced UUID leaf or `.atomic-<uuid>` sibling proved so a sweep can delete it?

Chosen: a directory sweep inside `cleanup_engine_images`, gated on the application-data advisory lock being held by this process and on the issuance count being zero.

Rejected: a write-ahead intent from the temporary inode before rename (`d-20261006-13` already rejected it for the in-process path; it also misses temps created before the intent write, and it changes atomic-replace). A capacity reservation for `f-20261004-13` (a second admission protocol; the sweep removes the same orphan on the existing startup and shutdown schedule). Sweeping whenever `InstanceAdmission::Owned` (configuration or local data can lock while application data did not). Sweeping while the issuance count is non-zero. Deleting by name without `open_leaf_identified` plus `remove_leaf_identified`. Recursive or non-regular deletion. Failing startup reconcile on a sweep error. Merging with `sweep_engine_launch_root`. A public issuance counter. Making `AuthorizedDir::entries` bounded for every caller. Logging `diagnostic()`.

Reason: the single-instance guard now exists, the lease already covers the unlocked copy, and the directory is app-owned. The sweep answers the finding's option (a) and the sibling finding's question without a new protocol.

Reversal path: remove the sweep pass and the setup setter, and restore the source pin's `match admission {` / `app.manage(guard);` / `Unguarded => {}` assertions. Intent cleanup stays.

Question: which lock bit enables the sweep?

Chosen: `app_data_locked` on the guard, true only when the application-data root's lock returned `Ok`, copied onto the authority with `set_engine_image_sweep_permitted` before `install`.

Rejected: treating `Owned` as sufficient.

Reason: `d-20261008-01` admits `Owned` when any root locked. Engine images live under application data.

Reversal path: stop recording the per-root bit and stop calling the setter.

Question: what listing limit does the sweep use?

Chosen: `MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)` (8192). On `Err`, delete nothing.

Rejected: 4096 (skips a full registry plus one orphan plus temps) and an unbounded list (a partial or huge listing is not a deletion set).

Reason: `check_directory_listing_bound` fails the whole call before it returns a `Vec`. 8192 covers 4096 registered ids plus 4096 orphans or temps.

Reversal path: change the limit expression and the 4097 / 8193 tests together.

## Risks / open questions

Known limits, accepted:

- If the application-data filesystem cannot take an advisory lock, the sweep never runs and crash orphans remain. `d-20261008-01` already starts that root unguarded and logs one warning. A second process could exist. Deleting would be unsafe.
- A directory with 8193 or more entries is skipped until a later pass sees fewer. 8192 covers a full 4096-id registry plus 4096 orphans or temps.
- An in-flight issuance defers the pass until the next cleanup after the count is zero. Shutdown drains the count first.
- The authority mutex is held for up to 8192 stat operations plus the unlinks. Intent cleanup already holds that mutex for its own unlinks. The work stays on the blocking gateway. No lock is held across `.await`.
- One unlink error leaves that leaf until the next pass. The rest of the pass still runs.
- An intent-walk `Err` skips the sweep until the next call. The existing error still reaches the caller.
- The open-versus-listed identity race is skipped per name and is not race-tested.

No product question remains. The finding's open question is answered by the decisions above.

## Goal

After a crash between installing an engine-image leaf and registering it, the next startup or shutdown cleanup removes that unreferenced regular file, and the same pass removes a crash-left `.atomic-<uuid>` temporary sibling. A leaf that is still referenced, still being issued, or living in a directory this process does not hold the application-data lock for stays on disk.

## Threat model and non-goals

Adversary and environment, frozen for round 1:

- One ChessFable process holds the advisory lock on the application-data directory that parents `engine-images`. A second process that shares that directory is refused at admission (`d-20261008-01`). The sweep may delete only while that lock is held by this process.
- `engine-images` contains only leaves this process writes: UUID-named image files and `.atomic-<uuid>` temps from `atomic_replace`. The only production writer is `issue_engine_image_blocking`.
- A crash, kill, or power loss can leave a renamed UUID leaf with no registry row and no `image_cleanup` intent, or an `.atomic-<uuid>` regular file whose rename never happened.
- Another root (configuration or local data) can be locked while the application-data filesystem cannot take an advisory lock. `InstanceAdmission::Owned` is then true and the application-data directory is not locked (`d-20261008-01`). The sweep must stay off in that case.
- An issuance lease can be in flight across the unlocked copy. The sweep must not delete that leaf.
- A name in the directory can be a directory, a symlink, or another non-regular node. Those are not deleted and not recursed into.
- Listing can exceed the sweep's cap. A partial list is not a safe deletion set.
- Registry paths can fail to parse. An unknown referenced name is not a license to delete.
- Logs must not emit `Error::diagnostic()` from this sweep (native path text).

Non-goals: changing `atomic_replace`, reserving registry capacity, merging with the macOS engine-launch sibling sweep, IPC or Specta changes, and deleting anything outside `engine-images`.

## Approach

### When the sweep runs

`cleanup_engine_images` gains one pass over `engine-images`, after the existing intent walk, on the same `&mut self` and the same `image_dir` the caller already passed. Call sites stay `cleanup_engine_images(&image_dir, false)`. No signature change, no new cancellation token, no IPC change.

The pass runs only when both gates hold:

1. This authority has been told the application-data lock is held. The flag lives on `PathAuthority`, default `false`, and is not serialized. `set_engine_image_sweep_permitted(bool)` is the only writer. Tests and every `open` / `open_for_app` stay false until setup sets it.
2. `self.active_image_issuances.active.load(Ordering::Acquire) == 0` while this method holds `&mut self`. Do not add a public counter. The field stays private. Same-module reads are enough.

If the flag is false, skip the pass with no new log. The unguarded-filesystem warning already exists. If the lease count is non-zero, skip the whole pass. `log::debug` is allowed; the production filter is Info, so users do not see it. Orphans wait for a later pass. Shutdown already seals, waits until the count is zero, then calls cleanup, and a sealed authority refuses new issuances, so shutdown is the pass that runs when startup skipped an in-flight issuance.

### What the sweep deletes

List with `read_directory_entries_at(image_dir.directory.as_file(), &CancellationToken::new(), Some(MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)), &mut |_| true)`. Do not call `AuthorizedDir::entries`. The limit is 8192. 8192 entries succeed. The 8193rd makes the call return `Err` and yields no partial list.

Build the protected-name set after the intent walk has updated `image_cleanup`. A name is protected when it is the normal leaf name of any `persistent`, `retired_attachments`, or `image_cleanup` entry. A normal leaf name is `file_name()` when that name is non-empty and not `.` or `..`. Match the leaf name, not the parent path. `provisional_attachments` are ids, not paths, and do not protect a file by themselves. If any of those three collections has an entry whose `to_path()` fails, or whose path has no normal leaf name, skip the whole pass, log the category, and delete nothing.

On a success path the existing intent walk leaves `image_cleanup` empty: an identity-matching intent is unlinked and dropped, and a parent or identity mismatch drops the row without unlinking. A successful `cleanup_engine_images` therefore does not keep an intent target on disk. Rows that remain are still part of the protected set. Today they remain only when the walk is about to return `Err`, and that path does not sweep.

On a listing `Err`, `log::warn` with `error.category()` only and delete nothing this pass. Do not fail `cleanup_engine_images` for a sweep listing failure.

For each listed entry, delete only when all of these hold:

- `kind` is `DirectoryEntryKind::RegularFile`.
- The name is either a UUID (`Uuid::parse_str` on the whole name) or a production temp: the name starts with `.atomic-` and the remainder parses as `Uuid`. No other prefix. This is the same `temp_name()` text on Unix and Windows.
- The name is not in the protected set.
- `open_leaf_identified` returns an identity equal to the listed `DirectoryEntry.identity`. Missing, `Conflict`, or a different identity skips that name and does not unlink. Any other open error logs the leaf name and `error.category()` and continues.
- `remove_leaf_identified` then unlinks that identity. One unlink error logs the leaf name and `error.category()` and does not abort the rest of the pass.

No recursive delete. No deletion of directories, symlinks, junctions, or `Other`. Do not log `diagnostic()`.

A dropped identity-mismatched intent no longer protects its leaf name. The file that remains is not the registered inode. If it is still an unreferenced UUID regular file, this pass may delete it. That is intentional.

### Failure and reconcile

Existing intent-walk errors still return `Err` and still fail the caller. The sweep does not run on that `Err` path. When `image_cleanup` is empty, today's early return must not skip the sweep: a pending durability retry still runs first; if that retry returns `Err`, return it and do not sweep; if it returns `Ok`, or there is nothing to retry, run the sweep and then return `Ok`. Sweep list and unlink failures are logged and left for the next startup or shutdown pass. They must not turn a successful reconcile into `Err` after attachments were already committed.

## Decisions and trade-offs

### Decided autonomously

Question: how is ownership of an unreferenced UUID leaf or `.atomic-<uuid>` sibling proved so a sweep can delete it?

Chosen: a directory sweep inside `cleanup_engine_images`, gated on the application-data advisory lock being held by this process and on the issuance count being zero.

Rejected: a write-ahead intent from the temporary inode before rename (`d-20261006-13` already rejected it for the in-process path; it also misses temps created before the intent write, and it changes atomic-replace). A capacity reservation for `f-20261004-13` (a second admission protocol; the sweep removes the same orphan on the existing startup and shutdown schedule). Sweeping whenever `InstanceAdmission::Owned` (configuration or local data can lock while application data did not). Sweeping while the issuance count is non-zero. ## Threat model and non-goals

Adversary and environment, frozen for round 1:

- One ChessFable process holds the advisory lock on the application-data directory that parents `engine-images`. A second process that shares that directory is refused at admission (`d-20261008-01`). The sweep may delete only while that lock is held by this process.
- `engine-images` contains only leaves this process writes: UUID-named image files and `.atomic-<uuid>` temps from `atomic_replace`. The only production writer is `issue_engine_image_blocking`.
- A crash, kill, or power loss can leave a renamed UUID leaf with no registry row and no `image_cleanup` intent, or an `.atomic-<uuid>` regular file whose rename never happened.
- Another root (configuration or local data) can be locked while the application-data filesystem cannot take an advisory lock. `InstanceAdmission::Owned` is then true and the application-data directory is not locked (`d-20261008-01`). The sweep must stay off in that case.
- An issuance lease can be in flight across the unlocked copy. The sweep must not delete that leaf.
- A name in the directory can be a directory, a symlink, or another non-regular node. Those are not deleted and not recursed into.
- Listing can exceed the sweep's cap. A partial list is not a safe deletion set.
- Registry paths can fail to parse. An unknown referenced name is not a license to delete.
- Logs must not emit `Error::diagnostic()` from this sweep (native path text).

Non-goals: changing `atomic_replace`, reserving registry capacity, merging with the macOS engine-launch sibling sweep, IPC or Specta changes, and deleting anything outside `engine-images`.

## Approach

### When the sweep runs

`cleanup_engine_images` gains one pass over `engine-images`, after the existing intent walk, on the same `&mut self` and the same `image_dir` the caller already passed. Call sites stay `cleanup_engine_images(&image_dir, false)`. No signature change, no new cancellation token, no IPC change.

The pass runs only when both gates hold:

1. This authority has been told the application-data lock is held. The flag lives on `PathAuthority`, default `false`, and is not serialized. `set_engine_image_sweep_permitted(bool)` is the only writer. Tests and every `open` / `open_for_app` stay false until setup sets it.
2. `self.active_image_issuances.active.load(Ordering::Acquire) == 0` while this method holds `&mut self`. Do not add a public counter. The field stays private. Same-module reads are enough.

If the flag is false, skip the pass with no new log. The unguarded-filesystem warning already exists. If the lease count is non-zero, skip the whole pass. `log::debug` is allowed; the production filter is Info, so users do not see it. Orphans wait for a later pass. Shutdown already seals, waits until the count is zero, then calls cleanup, and a sealed authority refuses new issuances, so shutdown is the pass that runs when startup skipped an in-flight issuance.

### What the sweep deletes

List with `read_directory_entries_at(image_dir.directory.as_file(), &CancellationToken::new(), Some(MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)), &mut |_| true)`. Do not call `AuthorizedDir::entries`. The limit is 8192. 8192 entries succeed. The 8193rd makes the call return `Err` and yields no partial list.

Build the protected-name set after the intent walk has updated `image_cleanup`. A name is protected when it is the normal leaf name of any `persistent`, `retired_attachments`, or `image_cleanup` entry. A normal leaf name is `file_name()` when that name is non-empty and not `.` or `..`. Match the leaf name, not the parent path. `provisional_attachments` are ids, not paths, and do not protect a file by themselves. If any of those three collections has an entry whose `to_path()` fails, or whose path has no normal leaf name, skip the whole pass, log the category, and delete nothing.

On a success path the existing intent walk leaves `image_cleanup` empty: an identity-matching intent is unlinked and dropped, and a parent or identity mismatch drops the row without unlinking. A successful `cleanup_engine_images` therefore does not keep an intent target on disk. Rows that remain are still part of the protected set. Today they remain only when the walk is about to return `Err`, and that path does not sweep.

On a listing `Err`, `log::warn` with `error.category()` only and delete nothing this pass. Do not fail `cleanup_engine_images` for a sweep listing failure.

For each listed entry, delete only when all of these hold:

- `kind` is `DirectoryEntryKind::RegularFile`.
- The name is either a UUID (`Uuid::parse_str` on the whole name) or a production temp: the name starts with `.atomic-` and the remainder parses as `Uuid`. No other prefix. This is the same `temp_name()` text on Unix and Windows.
- The name is not in the protected set.
- `open_leaf_identified` returns an identity equal to the listed `DirectoryEntry.identity`. Missing, `Conflict`, or a different identity skips that name and does not unlink. Any other open error logs the leaf name and `error.category()` and continues.
- `remove_leaf_identified` then unlinks that identity. One unlink error logs the leaf name and `error.category()` and does not abort the rest of the pass.

No recursive delete. No deletion of directories, symlinks, junctions, or `Other`. Do not log `diagnostic()`.

A dropped identity-mismatched intent no longer protects its leaf name. The file that remains is not the registered inode. If it is still an unreferenced UUID regular file, this pass may delete it. That is intentional.

### Failure and reconcile

Existing intent-walk errors still return `Err` and still fail the caller. The sweep does not run on that `Err` path. When `image_cleanup` is empty, today's early return must not skip the sweep: a pending durability retry still runs first; if that retry returns `Err`, return it and do not sweep; if it returns `Ok`, or there is nothing to retry, run the sweep and then return `Ok`. ## Threat model and non-goals

Adversary and environment, frozen for round 1:

- One ChessFable process holds the advisory lock on the application-data directory that parents `engine-images`. A second process that shares that directory is refused at admission (`d-20261008-01`). The sweep may delete only while that lock is held by this process.
- `engine-images` contains only leaves this process writes: UUID-named image files and `.atomic-<uuid>` temps from `atomic_replace`. The only production writer is `issue_engine_image_blocking`.
- A crash, kill, or power loss can leave a renamed UUID leaf with no registry row and no `image_cleanup` intent, or an `.atomic-<uuid>` regular file whose rename never happened.
- Another root (configuration or local data) can be locked while the application-data filesystem cannot take an advisory lock. `InstanceAdmission::Owned` is then true and the application-data directory is not locked (`d-20261008-01`). The sweep must stay off in that case.
- An issuance lease can be in flight across the unlocked copy. The sweep must not delete that leaf.
- A name in the directory can be a directory, a symlink, or another non-regular node. Those are not deleted and not recursed into.
- Listing can exceed the sweep's cap. A partial list is not a safe deletion set.
- Registry paths can fail to parse. An unknown referenced name is not a license to delete.
- Logs must not emit `Error::diagnostic()` from this sweep (native path text).

Non-goals: changing `atomic_replace`, reserving registry capacity, merging with the macOS engine-launch sibling sweep, IPC or Specta changes, and deleting anything outside `engine-images`.

## Approach

### When the sweep runs

`cleanup_engine_images` gains one pass over `engine-images`, after the existing intent walk, on the same `&mut self` and the same `image_dir` the caller already passed. Call sites stay `cleanup_engine_images(&image_dir, false)`. No signature change, no new cancellation token, no IPC change.

The pass runs only when both gates hold:

1. This authority has been told the application-data lock is held. The flag lives on `PathAuthority`, default `false`, and is not serialized. `set_engine_image_sweep_permitted(bool)` is the only writer. Tests and every `open` / `open_for_app` stay false until setup sets it.
2. `self.active_image_issuances.active.load(Ordering::Acquire) == 0` while this method holds `&mut self`. Do not add a public counter. The field stays private. Same-module reads are enough.

If the flag is false, skip the pass with no new log. The unguarded-filesystem warning already exists. If the lease count is non-zero, skip the whole pass. `log::debug` is allowed; the production filter is Info, so users do not see it. Orphans wait for a later pass. Shutdown already seals, waits until the count is zero, then calls cleanup, and a sealed authority refuses new issuances, so shutdown is the pass that runs when startup skipped an in-flight issuance.

### What the sweep deletes

List with `read_directory_entries_at(image_dir.directory.as_file(), &CancellationToken::new(), Some(MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)), &mut |_| true)`. Do not call `AuthorizedDir::entries`. The limit is 8192. 8192 entries succeed. The 8193rd makes the call return `Err` and yields no partial list.

Build the protected-name set after the intent walk has updated `image_cleanup`. A name is protected when it is the normal leaf name of any `persistent`, `retired_attachments`, or `image_cleanup` entry. A normal leaf name is `file_name()` when that name is non-empty and not `.` or `..`. Match the leaf name, not the parent path. `provisional_attachments` are ids, not paths, and do not protect a file by themselves. If any of those three collections has an entry whose `to_path()` fails, or whose path has no normal leaf name, skip the whole pass, log the category, and delete nothing.

On a success path the existing intent walk leaves `image_cleanup` empty: an identity-matching intent is unlinked and dropped, and a parent or identity mismatch drops the row without unlinking. A successful `cleanup_engine_images` therefore does not keep an intent target on disk. Rows that remain are still part of the protected set. Today they remain only when the walk is about to return `Err`, and that path does not sweep.

On a listing `Err`, `log::warn` with `error.category()` only and delete nothing this pass. Do not fail `cleanup_engine_images` for a sweep listing failure.

For each listed entry, delete only when all of these hold:

- `kind` is `DirectoryEntryKind::RegularFile`.
- The name is either a UUID (`Uuid::parse_str` on the whole name) or a production temp: the name starts with `.atomic-` and the remainder parses as `Uuid`. No other prefix. This is the same `temp_name()` text on Unix and Windows.
- The name is not in the protected set.
- `open_leaf_identified` returns an identity equal to the listed `DirectoryEntry.identity`. Missing, `Conflict`, or a different identity skips that name and does not unlink. Any other open error logs the leaf name and `error.category()` and continues.
- `remove_leaf_identified` then unlinks that identity. One unlink error logs the leaf name and `error.category()` and does not abort the rest of the pass.

No recursive delete. No deletion of directories, symlinks, junctions, or `Other`. Do not log `diagnostic()`.

A dropped identity-mismatched intent no longer protects its leaf name. The file that remains is not the registered inode. If it is still an unreferenced UUID regular file, this pass may delete it. That is intentional.

### Failure and reconcile

Existing intent-walk errors still return `Err` and still fail the caller. The sweep does not run on that `Err` path. When `image_cleanup` is empty, today's early return must not skip the sweep: a pending durability retry still runs first; if that retry returns `Err`, return it and do not sweep; if it returns `Ok`, or there is nothing to retry, run the sweep and then return `Ok`. Sweep list and unlink failures are logged and left for the next startup or shutdown pass. They must not turn a successful reconcile into `Err` after attachments were already committed.

## Decisions and trade-offs

### Decided autonomously

Question: how is ownership of an unreferenced UUID leaf or `.atomic-<uuid>` sibling proved so a sweep can delete it?

Chosen: a directory sweep inside `cleanup_engine_images`, gated on the application-data advisory lock being held by this process and on the issuance count being zero.

Rejected: a write-ahead intent from the temporary inode before rename (`d-20261006-13` already rejected it for the in-process path; it also misses temps created before the intent write, and it changes atomic-replace). A capacity reservation for `f-20261004-13` (a second admission protocol; the sweep removes the same orphan on the existing startup and shutdown schedule). Sweeping whenever `InstanceAdmission::Owned` (configuration or local data can lock while application data did not). Sweeping while the issuance count is non-zero. Deleting by name without `open_leaf_identified` plus `remove_leaf_identified`. Recursive or non-regular deletion. Failing startup reconcile on a sweep error. Merging with `sweep_engine_launch_root`. A public issuance counter. Making `AuthorizedDir::entries` bounded for every caller. Logging `diagnostic()`.

Reason: the single-instance guard now exists, the lease already covers the unlocked copy, and the directory is app-owned. The sweep answers the finding's option (a) and the sibling finding's question without a new protocol.

Reversal path: remove the sweep pass and the setup setter, and restore the source pin's `match admission {` / `app.manage(guard);` / `Unguarded => {}` assertions. Intent cleanup stays.

Question: which lock bit enables the sweep?

Chosen: `app_data_locked` on the guard, true only when the application-data root's lock returned `Ok`, copied onto the authority with `set_engine_image_sweep_permitted` before `install`.

Rejected: treating `Owned` as sufficient.

Reason: `d-20261008-01` admits `Owned` when any root locked. Engine images live under application data.

Reversal path: stop recording the per-root bit and stop calling the setter.

Question: what listing limit does the sweep use?

Chosen: `MAX_DIRECTORY_LISTING_ENTRIES.saturating_mul(2)` (8192). On `Err`, delete nothing.

Rejected: 4096 (skips a full registry plus one orphan plus temps) and an unbounded list (a partial or huge listing is not a deletion set).

Reason: `check_directory_listing_bound` fails the whole call before it returns a `Vec`. 8192 covers 4096 registered ids plus 4096 orphans or temps.

Reversal path: change the limit expression and the 4097 / 8193 tests together.

## Risks / open questions

Known limits, accepted:

- If the application-data filesystem cannot take an advisory lock, the sweep never runs and crash orphans remain. `d-20261008-01` already starts that root unguarded and logs one warning. A second process could exist. Deleting would be unsafe.
- A directory with 8193 or more entries is skipped until a later pass sees fewer. 8192 covers a full 4096-id registry plus 4096 orphans or temps.
- An in-flight issuance defers the pass until the next cleanup after the count is zero. Shutdown drains the count first.
- The authority mutex is held for up to 8192 stat operations plus the unlinks. Intent cleanup already holds that mutex for its own unlinks. The work stays on the blocking gateway. No lock is held across `.await`.
- One unlink error leaves that leaf until the next pass. The rest of the pass still runs.
- An intent-walk `Err` skips the sweep until the next call. The existing error still reaches the caller.
- The open-versus-listed identity race is skipped per name and is not race-tested.

No product question remains. The finding's open question is answered by the decisions above.
