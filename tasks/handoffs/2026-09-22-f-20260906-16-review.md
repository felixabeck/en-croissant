## Decided autonomously

Under `full auto` for the drain that wrote r1-r3; Felix was not asked about these. Each is recorded
in `tasks/decisions.md` by this run's closing step.

1. **`bool`, not `Option<PathAvailability>` and not a new three-variant enum.** *Rejected:* both.
   *Because:* the renderer's only decision is re-pick or proceed, so a `Some(availability)` payload
   would be exported with no consumer — the shape `d-20260906-05` deleted three commands for — and a
   new enum would additionally restate a type the registry already exports. The mandate's required
   distinction (missing authority versus every other failure) is exactly `false` versus `true`.
   *Reversal path:* the first consumer that must *show* why a known destination is unusable turns
   the return into `Option<PathAvailability>`, with that surface as its evidence.
2. **The predicate is `EntryPurpose::DownloadDestination`, not `operations.contains(DownloadFile)`.**
   *Rejected:* the operation test. *Because:* measured — database roots and puzzle roots carry
   `DownloadFile` too (`mod.rs:2047-2064`), and a `PersistentFile` entry has no directory for the
   filename child `AccountCard` passes, so the operation test would report a foreign capability
   usable and send an account's PGN into it.
3. **`&self`, so the query cannot have a side effect.** *Rejected:* `&mut self` with a
   `refresh_persistent_id` call and a `session_protected_ids` insert, mirroring
   `download_operations`. *Because:* a query is not a use; making it extend startup retention would
   let a page render silently defeat `reconcile_startup_owners`' reclamation, and taking `&self`
   makes that structural rather than a promise. It also removes all filesystem access from the
   query. *Reversal path:* if reclamation is later found to drop an id between the query and the
   download, the protection moves in, with that race as its evidence.
4. **Dialog grants are excluded** (A3). *Rejected:* mirroring `download_operations`' dialog
   fallback. *Because:* the renderer never persists a dialog id, and dialog entries are never
   refreshed, so a dialog answer would be stale by construction.
5. **No shared lookup helper with `download_operations`.** *Rejected:* extracting one, as
   `review-minimalism` proposed at confidence 96. *Because:* once dialog grants are excluded (A3),
   the purpose predicate replaces the operation test (A2) and the query takes `&self` (A4), the two
   functions share only a `pending_unpersisted_removals` membership test and a `BTreeMap::get`.
   Universal rule 11 governs a second copy of a domain concept, and this is not one: the concepts
   differ — "may this id serve a download right now, including a one-shot grant, and mark it
   protected" versus "is this id a known download-destination root". *Reversal path:* if a third
   caller needs the same predicate, it is extracted then.
6. **The seven new renderer cases go into the existing test file, not a new one.** *Rejected:* a
   separate `AccountCard.destination.test.tsx`, as r2 proposed. *Because:* everything except the
   state mock — module mocks, DOM setup, render helper, button lookup — already exists in
   `AccountCard.picker.test.tsx:1-134`, and a second harness would be the second copy rule 11
   forbids. The state mock is replaced there by a real `Provider` and real `localStorage`, which the
   four existing tests tolerate because an empty store hydrates to the `null` they already assume.
