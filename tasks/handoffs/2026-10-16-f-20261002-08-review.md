# Plan: Repeatable verification of real signed catalog engines

## Goal

Close f-20261002-08 with an opt-in network check that installs the actual signed engine catalog artifacts through the production backend and completes the production UCI configuration handshake for their nested executables. Run it automatically for catalog changes and periodically on the three supported operating systems without adding network dependency or unused generic instantiations to ordinary coverage builds.

## MANDATE

### No repeatable check installs the real signed catalog engines and talks UCI to them

* **ID:** f-20261002-08 · **Status:** open · **Area:** native-fs · **Root:** - · **Entry:** build · **Blocked:** none
* **Where:** `src/catalogs/engines.json` (+ `.minisig`), `src-tauri/src/fs.rs` `download_engine_archive_core`, the removed `#[ignore]` test `real_stockfish19_catalog_install_answers_uci` (added in `f19e14ac`, removed in `32c4be8f`).
* **Defect:** every automated test exercises the install chain with fixtures (`accept_any_integrity`, generated tar/zip payloads, shell-script engines). Nothing repeatable downloads the real signed catalog artefacts, verifies them, installs them into the version-unique directory, registers the nested executable and completes a `uci`/`uciok` handshake. The Stockfish 19 build proved that chain once (commit `f19e14ac` message, handoff `tasks/handoffs/2026-10-01-stockfish-19-upgrade-review.md`), but a later catalog edit (SF20, a changed archive layout, a moved nested path) would only be caught by a user.
* **Why it matters:** the catalog is the trust root of the "Upgrade from catalog" flow; a wrong nested `path` or archive layout makes install or upgrade fail for every user on that platform.
* **Open question:** where a network-dependent check belongs without distorting the backend coverage ratchet — an `#[ignore]` unit test inside the crate instantiates its own uncovered copy of the generic infra chain (22 records, which reddened `app-infrastructure` functions in that build) — e.g. a scheduled workflow job running a dedicated binary/script against every catalog entry for the runner's OS, or a mode of `scripts/app-driver.mjs`; and whether it should run on every catalog change (path filter on `src/catalogs/**`).
* **Found by:** Stockfish 19 upgrade build, closure round 10 (`review-correctness`, `review-tests`) after the coverage-gate repair, 2026-10-02.

User execution contract: `--pin f-20261002-08 full auto`, `PLAN-ONLY: /home/felixb/.claude/drain-plans/drain-90a2aa88/slot-1/run`, base `754626713f73f6887a99aaa4296ed4e40a7e166e`, scratch `/tmp/drain-plan-drain-90a2aa88-slot1/build`. ## Threat model and non-goals

The bundled catalog and detached signatures are repository inputs. Accidental catalog mistakes, changed upstream archive contents/layouts, unavailable downloads and ordinary platform/runtime incompatibility are in scope. The existing production signature, digest, host, archive and path-authority checks must run unchanged. This check adds no hostile local writer threat model and no authority widening.

Environments are native Linux x86_64, Windows x86_64 and macOS on an architecture supported by the catalog's universal binary. A cross-compile never counts as a successful executable handshake. CPU variants must be accounted for explicitly. An unsupported architecture or a required instruction set or native library missing from the runner is a failed prerequisite with the affected entry identified, never a silent skip or a passing platform check.

No gameplay, evaluation-strength benchmark, bestmove, GPU inference, UI redesign, release signing, catalog content change, application installation or new IPC surface is required. This backend integration check does not claim to validate renderer selection, settings persistence, first-run application setup or native dialogs.

### O1 — Explicit network compilation boundary

### O2 — Real artifact to registered executable

Verify the exact committed catalog bytes and detached signature using the production release key before parsing or choosing entries. Select every entry for the native OS from the catalog itself, rejecting zero selection and unsupported native environments. Do not hardcode engine names, versions, URLs or an expected entry count. Represent all selected entries in results. Identical `(URL, digest, signature, nested path)` entries may share one execution, with all aliases reported. A shared archive with different nested paths must verify each path.

Use fresh canonical scratch roots for authority state and artifacts, never Felix's profile or engines. Exercise the actual production signed artifact validator, `ProdTransport`, digest verification, extraction/publication, `register_installed_engine` and `get_engine_config_core`. Registration owns execute permission under d-20260920-06. Derive the same version-unique directory contract as `installCatalogEngine`, without copying the installer or crypto implementation. The scratch root must start without an existing artifact directory so adoption cannot bypass transport/hash verification. Report the catalog entry, artifact digest, nested path, registered handle and successful UCI configuration result. Success requires a nonempty engine identity and completed production `uci`/`uciok`, not a guessed stdout string or merely a returned handle.

### O3 — Bounded ownership and honest failure

Sequential cases own their download lease, state, supervisor, temporary directories and cleanup. Keep the existing network size/deadline, UCI deadlines and OS child-reaping contracts. Always run and inspect supervisor cleanup before removing its executable tree, including install failure, registration failure, UCI error and assertion failure. Release/finish operation ownership on every exit through the existing operation machinery. Do not wrap a future in a timeout that silently abandons a child or blocking installer.

Failures identify the entry and stage, retain the error for the final nonzero result and cannot be converted to skipped success. No automatic retry that conceals an upstream failure. Run all independent selected cases when safe after cleanup so one failed artifact does not hide the others. Keep stdout and error evidence bounded using existing infrastructure. CI enforces a finite whole-job timeout as an outer stop, alongside the production operation deadlines. Cleanup failures fail the check and identify remaining ownership. Scratch artifacts may be retained only with an explicit path and failure reason when deleting them would violate the resource lease contract.

### O4 — Automatic native execution

Add one separate `Catalog engines` workflow with Linux x86_64, Windows x86_64 and macOS native jobs. Trigger manual dispatch, weekly schedule and pushes/pull requests changing `src/catalogs/**`, the verification implementation/feature/command, the workflow itself or the production installer/authority/network/engine paths it exercises. Maintain one canonical workflow, no new per-push heavyweight gate. Use least privilege `contents: read`, repository-pinned tool setup and existing Rust cache conventions. Build prerequisites must exist on each OS, including Tauri's frontend directory and canonical macOS temp root. Ensure the command actually runs one enabled network test. Upload bounded per-OS verification output on success and failure and use native job exit status as the verdict. No signing secrets, release permissions or persisted artifact/download cache that could bypass a fresh install.

### O5 — Evidence that catches breakage and preserves coverage

The check itself is the regression evidence for O2. Validate the verifier's rejection assertions with staged changes to owned real inputs in a disposable snapshot, never by editing verifier assertions or real user state. Record each distinguishing message and observed exit code in `docs/catalog-engine-verification.md`, enumerate source failure exits, and mark genuinely unstageable platform/environment refusals as argued. Never claim staged proof for such rows. Existing fixture tests remain the offline refusal tests for the production integrity/archive/authority contracts.

Prove O1 with enabled/disabled test discovery and a full default backend coverage run with the feature disabled. The new network test must be absent from ordinary coverage execution and no coverage baseline, floor or source scope changes are permitted. Use real Linux network execution locally. Native macOS and Windows workflow results are the runtime evidence for those OS claims and must be green before final completion. Cross-compilation is additional compile proof only. No browser proof is required because no renderer or visible UI behavior changes.
