# Plan: `parseLcov` rejects malformed LCOV instead of coercing it (f-20260922-05)

Plan path: `tasks/plans/2026-10-07-lcov-malformed-input-rejection.md`. Base `8702b5ec7ce7a03b1708a0ddc254751302857cec`. Planner session `53979f11-e37a-4c9a-a58d-9ec18b68357b`, PLAN-ONLY, `full auto`.

## Goal

The coverage gate (`scripts/coverage-report.mjs`) stops producing a plausible report from LCOV it could not parse. Every counter field and every record boundary the parser consumes is checked against the LCOV grammar that both instruments emit. The first violation fails the whole run with a message that names the input line, the rule, and the raw text. Real output from `@vitest/coverage-v8` and from `llvm-cov export -format=lcov` still parses, and the gate stays green on it.

## MANDATE

Verbatim ledger entry `f-20260922-05`, `tasks/findings.md:11347-11358` at `BASE`:

> * **ID:** f-20260922-05 · **Status:** open · **Area:** gate-scripts · **Root:** - · **Entry:** build · **Blocked:** none
> * **Where:** `scripts/coverage-report.mjs`, `parseLcov` — the `DA`, `FN`, `FNDA` and `BRDA` branches and the `addCounter` helper they share.
> * **Defect:** every counter value is passed through `Number(...)` and every identity is built by string concatenation, with no validation that either is well-formed. Measured 2026-09-22 on this parser: `DA:bogus,1` is accepted and counted as a **covered** line under the identity `bogus:`, inventing a covered record for a line number that does not exist; `DA:1,bogus` yields `Number("bogus")` → `NaN`, which `Math.max(0, NaN)` propagates as `NaN`, and `NaN > 0` is false, so the line is silently counted as uncovered instead of reported. A truncated or corrupt LCOV therefore produces a plausible report rather than a failure, and the gate can be **green on input it could not parse**.
> * **Why it matters:** two coverage ratchets and both area-floor gates cite this script's exit status as evidence, in CI and on every local push, and the numbers they compare come entirely from this parser. A corrupt LCOV that yields *higher* covered counts passes the ratchet and then becomes the baseline the next run is measured against — the same shape as `f-20260920-18`, where a broken measurement was green in the direction that mattered. The blank-measurement guard added for `f-20260920-19` does not help: it fires on a record with no counters at all, not on one whose counters are nonsense.
> * **Candidate fix:** decide, and then enforce, what this parser must reject — at minimum a non-integer line number, block or branch index, and a non-integer hit count where the format does not permit one. `BRDA` already has a legitimate non-numeric hit value (`-`, meaning "not taken"), so the rule is per field rather than blanket, and the answer has to be measured against **both** instruments this one script serves: `@vitest/coverage-v8` for the frontend and `llvm-cov` for the backend. That measurement is the work — a blanket "reject anything non-numeric" risks a false red on a valid variant one of the two emits, which is why this is filed rather than fixed inline.
> * **Open question:** which counter fields must be rejected rather than coerced, and is rejection even the right answer for a *partially* corrupt LCOV? A parser that throws on the first malformed line turns a salvageable report into a red gate, while one that drops the offending record silently shrinks the denominator — which is the class `f-20260920-19` exists to stop. A third option is to count malformed lines and fail only above a threshold, which needs a threshold nobody has evidence for. The answer decides whether this is a guard inside `parseLcov`, a separate validation pass over the LCOV text before parsing, or a per-record diagnostic that the blank-measurement check consumes.
> * **Known limit to pin either way:** whatever is decided, the failure matrix in `scripts/coverage-report.mjs`'s header must gain the rows, since it currently names this tolerance as the one thing it does not cover.
> * **Found by:** `review-error-handling` (blocker, confidence 98) in the `$push` review of `f5d27fda..HEAD`, 2026-09-22, and reproduced by the orchestrator against the parser before filing. Deferred rather than fixed in that run because the repair is a design question about what an LCOV parser must reject, needing its own measurement against two instruments — not because of effort or scope. The run that found it hardened the same file and recorded the gap in the artefact's own header at the same time.
>
> **A second shape of the same class, found in the `$push` review of `f5d27fda..HEAD`, 2026-09-22, and measured.** `review-correctness` (blocker, 96): an `FNDA` line with no matching `FN` in the same record creates a phantom function rather than being rejected, and the phantom makes two records for one file disagree with a single record carrying the union of their counters. Measured — `SF:a.ts` + `FN:1,f` in one record and `SF:a.ts` + `FNDA:1,f` in another merge to `{covered: 1, total: 2}`, while one record carrying both lines gives `{covered: 1, total: 1}`. The pairing of `FNDA` to `FN` is per record by construction, which is the LCOV convention, so this is malformed input reaching the same unvalidated path as the coerced counter values above rather than a separate defect.
>
> It matters more since 2026-09-22 than before: `buildCoverageReport` now merges records for one file across `SF` spellings, so a malformed record no longer has to duplicate a whole file's spelling to interact with a well-formed one. Whatever this finding decides about rejecting malformed counters must decide this case with it — reject the record, drop the unmatched `FNDA`, or keep the phantom and say so — and the answer belongs in the same measurement against both instruments.

## Approach

One guard inside `parseLcov`, enforced where each field is consumed. It is not a second pass over the text, because that would be a second copy of the grammar, and not a per-record diagnostic, because a malformed record is not a blank one. Every rule below is one row of the failure matrix and has its own message.

**Message contract (applies to every rule):** `parseLcov` throws an `Error` whose message starts `Malformed LCOV`. It names the 1-based line number in the input string, a reason text unique to the violated rule, and the raw offending line quoted unambiguously, for example JSON-quoted. A violation inside an open record also names that record's raw `SF` value. The end-of-input rule names the open record's `SF` value instead of a line. Nothing is returned, merged or partially counted once a violation is found. "Canonical decimal" below means exactly `0|[1-9][0-9]*`: no sign, no leading zero, no whitespace, no exponent, no fraction, not empty.

### O1 — Counter-line field grammar

Rests on: "decide, and then enforce, what this parser must reject — at minimum a non-integer line number, block or branch index, and a non-integer hit count where the format does not permit one"; "`BRDA` already has a legitimate non-numeric hit value (`-` …), so the rule is per field".

Fields are the value split on `,`. The field count is part of the rule, because a dropped or extra field is how truncation and the LCOV 2.x variants show up. Lines start at 1, as both instruments' minimum shows; block and branch indices start at 0.

| key | fields | rules (each bullet its own reason) |
|---|---|---|
| `DA` | `line,hits` or `line,hits,checksum` | field count is 2 or 3 · `line` canonical decimal ≥ 1 · `hits` canonical decimal · a present checksum is non-empty (the checksum stays opaque text otherwise) |
| `FN` | `line,name` | field count exactly 2 · `line` canonical decimal ≥ 1 · `name` non-empty |
| `FNDA` | `hits,name` | field count exactly 2 · `hits` canonical decimal · `name` non-empty |
| `BRDA` | `line,block,branch,taken` | field count exactly 4 · `line` canonical decimal ≥ 1 · `block` canonical decimal · `branch` canonical decimal · `taken` canonical decimal or exactly `-` |

The identity keeps being built from the raw field text (`identity(...)` at `:348`). Once the fields are canonical, the raw text and the numeric value are the same key, so `DA:01,1` and `DA:1,1` can no longer be two counters for one line.

### O2 — Record structure

Rests on: "A truncated or corrupt LCOV therefore produces a plausible report rather than a failure"; "one that drops the offending record silently shrinks the denominator".

A record opens at `SF` and closes at `end_of_record`. Each of these is its own reason:

* an `SF` whose path value is empty;
* an `SF` while a record is still open (today the open record is discarded without being merged, `:392`);
* a `DA`, `FN`, `FNDA` or `BRDA` line with no open record (today dropped, `:403`);
* an `end_of_record` with no open record;
* input that ends while a record is open (today merged, `:446`). This is the rule that makes a truncation at a line boundary detectable. A mid-line truncation is caught by O1's field rules or by this one.

Every other key keeps today's behaviour inside and outside a record: `TN`, `VER`, the six summary keys and any unknown key are ignored. Blank lines are skipped, and CRLF is normalised.

### O3 — `FNDA` pairing

Rests on: "an `FNDA` line with no matching `FN` in the same record creates a phantom function rather than being rejected … Whatever this finding decides about rejecting malformed counters must decide this case with it".

The k-th `FNDA` for a name pairs with the k-th earlier `FN` of that name in the same record, as `functionIdsByName` already does. An `FNDA` with no such `FN` is a violation with its own reason, and the `identity(null, name, occurrence)` phantom branch is removed. An `FN` with no `FNDA` stays legal (a declared, unexecuted function, total +1 and covered +0), as does an `FNDA` paired to an `FN` on an excluded line (dropped together with it, `:433-438`).

### O4 — Whole-input rejection semantics

Rests on: "is rejection even the right answer for a *partially* corrupt LCOV? … The answer decides whether this is a guard inside `parseLcov`, a separate validation pass …, or a per-record diagnostic".

The first violation throws, and no salvage, partial result or threshold exists (the reasons are in Decided autonomously, A1). Through the CLI the throw reaches `main().catch`: exit 1, message on stderr, nothing on stdout (row 41). On the `--write-baseline` path the same throw happens inside `buildCoverageReport`, before `guardBaselineWrite`. A malformed LCOV therefore can no longer become a baseline, and the scratch baseline's bytes stay unchanged. `--mapping-only` reads no LCOV and is unaffected.

## Approach

One guard inside `parseLcov`, enforced where each field is consumed. It is not a second pass over the text, because that would be a second copy of the grammar, and not a per-record diagnostic, because a malformed record is not a blank one. Every rule below is one row of the failure matrix and has its own message.

**Message contract (applies to every rule):** `parseLcov` throws an `Error` whose message starts `Malformed LCOV`. It names the 1-based line number in the input string, a reason text unique to the violated rule, and the raw offending line quoted unambiguously, for example JSON-quoted. A violation inside an open record also names that record's raw `SF` value. The end-of-input rule names the open record's `SF` value instead of a line. Nothing is returned, merged or partially counted once a violation is found. "Canonical decimal" below means exactly `0|[1-9][0-9]*`: no sign, no leading zero, no whitespace, no exponent, no fraction, not empty.

### O1 — Counter-line field grammar

Rests on: "decide, and then enforce, what this parser must reject — at minimum a non-integer line number, block or branch index, and a non-integer hit count where the format does not permit one"; "`BRDA` already has a legitimate non-numeric hit value (`-` …), so the rule is per field".

Fields are the value split on `,`. The field count is part of the rule, because a dropped or extra field is how truncation and the LCOV 2.x variants show up. Lines start at 1, as both instruments' minimum shows; block and branch indices start at 0.

| key | fields | rules (each bullet its own reason) |
|---|---|---|
| `DA` | `line,hits` or `line,hits,checksum` | field count is 2 or 3 · `line` canonical decimal ≥ 1 · `hits` canonical decimal · a present checksum is non-empty (the checksum stays opaque text otherwise) |
| `FN` | `line,name` | field count exactly 2 · `line` canonical decimal ≥ 1 · `name` non-empty |
| `FNDA` | `hits,name` | field count exactly 2 · `hits` canonical decimal · `name` non-empty |
| `BRDA` | `line,block,branch,taken` | field count exactly 4 · `line` canonical decimal ≥ 1 · `block` canonical decimal · `branch` canonical decimal · `taken` canonical decimal or exactly `-` |

**Validation is unconditional and comes before line exclusion.** Every `DA`, `FN`, `FNDA` and `BRDA` line is checked against its rules as soon as it is read, independent of `includeLine`. Today counter consumption sits behind that filter (`:407`, `:435`, `:441`), and production feeds it the Rust test-only exclusions (`:579`). An excluded line is dropped only after it has passed. An `FNDA` whose paired `FN` sits on an excluded line is still checked in full: field count, `hits`, `name` and pairing (O3).

The identity keeps being built from the raw field text (`identity(...)` at `:348`). Once the fields are canonical, the raw text and the numeric value are the same key, so `DA:01,1` and `DA:1,1` can no longer be two counters for one line.

### O2 — Record structure

Rests on: "A truncated or corrupt LCOV therefore produces a plausible report rather than a failure"; "one that drops the offending record silently shrinks the denominator".

A record opens at `SF` and closes at `end_of_record`. Each of these is its own reason:

* an `SF` whose path value is empty;
* an `SF` while a record is still open (today the open record is discarded without being merged, `:392`);
* a `DA`, `FN`, `FNDA` or `BRDA` line with no open record (today dropped, `:403`);
* an `end_of_record` with no open record;
* input that ends while a record is open (today merged, `:446`). This is the rule that makes a truncation at a line boundary detectable. A mid-line truncation is caught by O1's field rules or by this one.

Every other key keeps today's behaviour inside and outside a record: `TN`, `VER`, the six summary keys and any unknown key are ignored. Blank lines are skipped, and CRLF is normalised.

Rests on: "an `FNDA` line with no matching `FN` in the same record creates a phantom function rather than being rejected … Whatever this finding decides about rejecting malformed counters must decide this case with it".

The k-th `FNDA` for a name pairs with the k-th earlier `FN` of that name in the same record, as `functionIdsByName` already does. An `FN` with no `FNDA` stays legal (a declared, unexecuted function, total +1 and covered +0), as does an `FNDA` paired to an `FN` on an excluded line (dropped together with it, `:433-438`).

## Decisions and trade-offs

The contested points, named so the lenses can attack them:

1. Reject the whole input on the first violation, rather than dropping the record, salvaging, or applying a threshold (O4, A1).
2. Reject the LCOV 2.x variants (`FN` end line, exception-prefixed or expression `BRDA` fields) rather than support them, because neither pinned instrument emits them (A2).

## Approach

One guard inside `parseLcov`, enforced where each field is consumed. It is not a second pass over the text, because that would be a second copy of the grammar, and not a per-record diagnostic, because a malformed record is not a blank one. Every rule below is one row of the failure matrix and has its own message.

**Message contract (applies to every rule):** `parseLcov` throws an `Error` whose message starts `Malformed LCOV`. It names the 1-based line number in the input string, a reason text unique to the violated rule, and the raw offending line quoted unambiguously, for example JSON-quoted. A violation inside an open record also names that record's raw `SF` value. The end-of-input rule names the open record's `SF` value instead of a line. Nothing is returned, merged or partially counted once a violation is found. "Canonical decimal" below means exactly `0|[1-9][0-9]*`: no sign, no leading zero, no whitespace, no exponent, no fraction, not empty.

### O1 — Counter-line field grammar

Rests on: "decide, and then enforce, what this parser must reject — at minimum a non-integer line number, block or branch index, and a non-integer hit count where the format does not permit one"; "`BRDA` already has a legitimate non-numeric hit value (`-` …), so the rule is per field".

Fields are the value split on `,`. The field count is part of the rule, because a dropped or extra field is how truncation and the LCOV 2.x variants show up. Lines start at 1, as both instruments' minimum shows; block and branch indices start at 0.

| key | fields | rules (each bullet its own reason) |
|---|---|---|
| `DA` | `line,hits` or `line,hits,checksum` | field count is 2 or 3 · `line` canonical decimal ≥ 1 · `hits` canonical decimal · a present checksum is non-empty (the checksum stays opaque text otherwise) |
| `FN` | `line,name` | field count exactly 2 · `line` canonical decimal ≥ 1 · `name` non-empty |
| `FNDA` | `hits,name` | field count exactly 2 · `hits` canonical decimal · `name` non-empty |
| `BRDA` | `line,block,branch,taken` | field count exactly 4 · `line` canonical decimal ≥ 1 · `block` canonical decimal · `branch` canonical decimal · `taken` canonical decimal or exactly `-` |

**Validation is unconditional and comes before line exclusion.** Every `DA`, `FN`, `FNDA` and `BRDA` line is checked against its rules as soon as it is read, independent of `includeLine`. Today counter consumption sits behind that filter (`:407`, `:435`, `:441`), and production feeds it the Rust test-only exclusions (`:579`). An excluded line is dropped only after it has passed. An `FNDA` whose paired `FN` sits on an excluded line is still checked in full: field count, `hits`, `name` and pairing (O3).

The identity keeps being built from the raw field text (`identity(...)` at `:348`). Once the fields are canonical, the raw text and the numeric value are the same key, so `DA:01,1` and `DA:1,1` can no longer be two counters for one line.

### O2 — Record structure

Rests on: "A truncated or corrupt LCOV therefore produces a plausible report rather than a failure"; "one that drops the offending record silently shrinks the denominator".

A record opens at `SF` and closes at `end_of_record`. Each of these is its own reason:

* an `SF` whose path value is empty;
* an `SF` while a record is still open (today the open record is discarded without being merged, `:392`);
* a `DA`, `FN`, `FNDA` or `BRDA` line with no open record (today dropped, `:403`);
* an `end_of_record` with no open record;
* input that ends while a record is open (today merged, `:446`). This is the rule that makes a truncation at a line boundary detectable. A mid-line truncation is caught by O1's field rules or by this one.

Every other key keeps today's behaviour inside and outside a record: `TN`, `VER`, the six summary keys and any unknown key are ignored. Blank lines are skipped, and CRLF is normalised.

### O3 — `FNDA` pairing

Rests on: "an `FNDA` line with no matching `FN` in the same record creates a phantom function rather than being rejected … Whatever this finding decides about rejecting malformed counters must decide this case with it".

The k-th `FNDA` for a name pairs with the k-th earlier `FN` of that name in the same record, as `functionIdsByName` already does. An `FNDA` with no such `FN` is a violation with its own reason, and the `identity(null, name, occurrence)` phantom branch is removed. An `FN` with no `FNDA` stays legal (a declared, unexecuted function, total +1 and covered +0), as does an `FNDA` paired to an `FN` on an excluded line (dropped together with it, `:433-438`).

### O4 — Whole-input rejection semantics

Rests on: "is rejection even the right answer for a *partially* corrupt LCOV? … The answer decides whether this is a guard inside `parseLcov`, a separate validation pass …, or a per-record diagnostic".

The first violation throws, and no salvage, partial result or threshold exists (the reasons are in Decided autonomously, A1). Through the CLI the throw reaches `main().catch`: exit 1, message on stderr, nothing on stdout (row 41). A malformed LCOV therefore can no longer become a baseline, and the scratch baseline's bytes stay unchanged. `--mapping-only` reads no LCOV and is unaffected.

## Decisions and trade-offs

The contested points, named so the lenses can attack them:

1. Reject the whole input on the first violation, rather than dropping the record, salvaging, or applying a threshold (O4, A1).
2. Reject the LCOV 2.x variants (`FN` end line, exception-prefixed or expression `BRDA` fields) rather than support them, because neither pinned instrument emits them (A2).
3. Line numbers ≥ 1 (measured minimum 1 and 5) versus accepting 0: line 0 "does not exist" in the MANDATE's own words.
4. Unknown keys remain ignored rather than rejected: they feed no counter, so they cannot inflate or shrink a metric (A3).
5. No cross-check of summary lines: measured to false-red the backend in 45 of 49 records.

## Decided autonomously

Recorded by the adopting session through `./scripts/findings.py record-decision` before implementation. Each entry governs f-20260922-05.

* **A1 — What does `parseLcov` do with malformed LCOV: throw, drop the offending record or line, or count violations and fail above a threshold?** Chosen: throw on the first violation, inside `parseLcov` where the field is consumed, failing the whole run. Rejected: (a) dropping the record or line, because it shrinks the denominator silently, which is the `f-20260920-19` class; (b) a threshold, because no evidence exists for any number, and both instruments were measured to emit zero violations across 115,859 `DA`, 15,926 `FN`, 15,926 `FNDA` and 31,545 `BRDA` lines; (c) a separate validation pass, because it would be a second copy of the grammar that can drift from the parser; (d) a per-record diagnostic feeding the blank-measurement check, because a malformed record is not a blank one. Reason: a malformed line means the instrument run or the file is broken. The remedy is to re-run the instrument, and a red gate is the correct report for a measurement that could not be read. Aggregating every violation adds nothing the operator can act on. Reversal path: if a pinned instrument is ever measured to emit an occasional malformed line it cannot be configured away from, add a per-rule exception for that measured shape, never a threshold.
* **A2 — Are LCOV 2.x forms (`FN:<start>,<end>,<name>`, `e`-prefixed `BRDA` blocks, branch expressions) and comma-bearing function names supported or rejected?** Chosen: rejected by O1's field-count and canonical-decimal rules, with their own messages. Rejected: supporting them now, because neither pinned instrument emits them (measured: 0 of 15,926 `FN` lines with a third field or a comma in the name), and today's `split(",")` silently misreads `FN:10,20,f` as a function named `20`. Reason: an instrument upgrade that starts emitting one of them fails loudly and names the line, so the parser change becomes a deliberate edit measured against the new output, never a silent reinterpretation. Reversal path: extend O1's table for the measured form.
* **A3 — Are keys outside `TN SF FN FNDA FNF FNH DA LF LH BRDA BRF BRH end_of_record` rejected?** Chosen: no, they stay ignored as today. Rejected: a key whitelist, because a future instrument's informational key (`VER`, `FNL`) would red the gate without any counter being affected. Reason: an ignored key contributes no counter, so it cannot inflate or shrink a metric. A counter line whose key bytes were corrupted is accepted as a residual and named in the matrix's "does not cover" paragraph. Reversal path: a whitelist in the same key dispatch.
