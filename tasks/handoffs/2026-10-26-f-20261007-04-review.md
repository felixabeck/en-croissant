# Plan: Files Move dialog destination at 320px / 200%

## Goal

The Files Move dialog shows the full selected destination at a 320px viewport and a 200% app font scale, including one unbroken directory name, and the existing move, refusal, and retained-destination behaviour stays the same.

## MANDATE

The Files Move dialog clips its destination Select at 320px / 200%, even full-screen.

* **ID:** f-20261007-04 · **Status:** open · **Area:** frontend-ui · **Root:** - · **Entry:** build · **Blocked:** none
* **Where:** `src/components/files/FilesPage.tsx`, the Move `AppModal` and its "Destination folder" `Select` (data: `Files.CollectionRoot` plus every directory label of the collection).
* **Defect:** at a 320px viewport and a 200% font scale (the `database-files` e2e project) the dialog's destination input cannot show its default value: `assertNothingClipped(dialog)` (`e2e/fixtures.ts`) reports `mantine-Select-input: x 271px > 220px` for "Collection root" in the default modal, and still 271px > 252px when the modal is made `fullScreen` below 30em (measured 2026-10-07 in the pinned container by the f-20260919-07 fix leaf, test "Move dialog fits 320px and selects a destination", not committed). Directory labels are user-chosen and unbounded, so any single-line Select clips a long one; the user cannot read which destination is selected.
* **Open question:** how should the Move dialog present open-ended destination names at narrow widths — a wrapping list (radio group or tree of directories) instead of a single-line Select, a Select whose options and selected value wrap, or a shorter fixed root label plus ellipsis with the full name on focus/title? The answer applies to any future Files form that picks a directory.
* **Why it matters:** `d-20260919-12` holds the Files page to the 320px / 200% layout discipline; this dialog is the one Files form that still fails it, and the e2e suite has no assertion over it.
* **Related:** `f-20260919-07` (its push review, tests lens R2-3, asked for the browser assertion that exposed this; that change makes only the edit/create/rename dialog full-screen below 30em, constant `COMPACT_DIALOG_QUERY`), `f-20260829-02` (handled; the 320px / 200% clipping class and `assertNothingClipped`).
* **Found by:** the f-20260919-07 cumulative diff review, closure round 2, 2026-10-07.

Pickup at BASE `b60ae5a4e662ebe06caa62a8a1343f3c87eec343`: the defect still holds. The dialog now lives in `useFileWorkspace`, not `FilesPage.tsx`. Nothing in this cluster is closed or rejected. Tier stays `build`: the open question is which presentation mechanism makes an unbounded name readable, and the proof has to cross the dialog, the unit harness, and the clipping instrument. That is the plan, not a one-line mirror.

## Threat model and non-goals

The user is someone using the Files page at a 320px CSS viewport with the app font scale at 200%, in English or German, with a directory whose name is one long unbroken token. A destination can also disappear from the listing while the dialog is open; that case is already specified and must keep working. This is not an attacker, a storage adversary, or a native-filesystem boundary.

Frozen with this section: no new locale strings, no second directory tree, no shared picker component, no change to drag-move or to the move IPC.

## Traced premises

* The Move dialog is `AppModal` in `src/components/files/useFileWorkspace.tsx` around the `opened={moveTarget !== null}` block. It does not set `fullScreen`. The create/rename/edit dialog above it does set `fullScreen={compactDialog}`.
* `compactDialog` is `useScaledMaxWidth(COMPACT_DIALOG_WIDTH_EM)` with `COMPACT_DIALOG_WIDTH_EM = 30`. The constant comment still describes the type Select, not Move.
* Destinations are the collection root, labelled with `Files.CollectionRoot` ("Collection root"), plus every directory from a depth-first walk, labelled with `entry.name` only. A destination that leaves the listing is appended back as `presentation.destination` so the chosen label stays visible and is not a new write target.
* `openMove` selects the collection root. The Move button submits `moveEntry` with that handle. Choosing an empty Select value calls `closePresentation`. Drag-move calls `moveEntry` directly and never opens this dialog.
* The Move submit button already passes `styles={libraryButtonProps.styles}` (`wrappingButton`). The sibling Confirm button also passes `miw={0}` and the rest of `libraryButtonProps`.
* `DirectoryTree` renders each name with `miw={0}` and `overflowWrap: "anywhere"`. `src/styles/global.css` defines `.wrap-anywhere` for the same break. `d-20260927-28` chose that break over ellipsis for text that does not fit at 320px / 200%.
* `assertNothingClipped` default mode is horizontal-only and counts a box narrower than its content, scroll containers included. `mode: "reachable"` returns early for a non-empty `HTMLInputElement` of type `text`, so a Select input can pass the reachable checks in `e2e/async-errors.spec.ts` while failing the default mode the finding measured.
* The unit harness mocks `@mantine/core` `Select` as a native `<select>`. `FilesPage.test.tsx` drives the Move dialog through `[role="dialog"] select` in "move retains a removed destination and refuses a second write", and several move cases assert that the first `[role="dialog"] input` has value `undefined`.
* `e2e/async-errors.spec.ts` opens Move, chooses the destination through a textbox named with `Files.DestinationFolder` and an option, then asserts that textbox's value. Its dialog check is `assertNothingClipped(dialog, { mode: "reachable" })`. It screenshots `workspace-refusal-move-{retained,relist-failed}-320-200-{en-US,de-DE}`.
* No test in `e2e/database-files.spec.ts` opens Move. That project's font scale is already 200%. Its viewport default is 800px; the metadata test sets 320px itself.
* `FilesPage.tsx` is gone. The page renders this hook. `d-20260919-12` still governs the page: two columns, no `overflow: hidden` on a column, content at 320px / 200% must not be absorbed by a scroll container. It does not choose the Move destination control. Its Select-versus-chips choice is the file-type filter.

## Approach

### Destination control

Replace the Move dialog's Mantine `Select` with a Mantine `Radio.Group` of one `Radio` per current destination. The group label is the existing `Files.DestinationFolder` string. Each radio's visible label is the same string the Select shows today: `Files.CollectionRoot` for the root, `entry.name` for a directory. The radio value is `fileWorkspaceKey(entry.handle)`.

The selected label is ordinary wrapping text, using the existing `wrap-anywhere` behaviour (`overflow-wrap: anywhere`) and `miw={0}` on the group, each option, and the label, the same way the Files tree keeps a long name inside its row. The full selected name is visible without horizontal scrolling and without a `title` tooltip. An unbroken name wraps mid-word, which `d-20260927-28` already accepts.

Do not extract a picker component. The mandate's sentence about a future Files form is a constraint on this choice, not a second caller. A later form repeats this pattern.

### Dialog layout

Give the Move `AppModal` `fullScreen={compactDialog}` and put its body in a `Stack` with `miw={0}`, matching the create/rename/edit dialog in the same hook. Full-screen alone does not fix the clip; the 2026-10-07 measurement already showed 271px against 252px. It only gives the wrapping list the same width the sibling dialogs already use. Do not add a breakpoint.

The Move submit button keeps `libraryButtonProps` and gains `miw={0}`, matching Confirm, so the button cannot force the stack wider than the dialog. Do not change its label, colour, or disabled rule.

A long destination list may scroll vertically inside the dialog. It must not scroll horizontally and must not use `overflow: hidden` to swallow a wide label. Default `assertNothingClipped` counts a horizontal scroll container as clipped.

### Selection and failure behaviour

Opening Move still selects the collection root. Choosing another radio selects that destination and does not submit and does not close. Activating the already selected radio does not close the dialog. The empty-Select close path goes away with the Select; the dialog still closes through its close button, through `closePresentation` after a successful move, and through the existing refusal paths.

`moveEntry`, the in-flight guard, the owner check, the retained destination after it disappears from the listing, and the refusal copy stay as they are. A retained destination remains one selected radio whose label is still the name it had, and a second Move press still does not call native move again.

Drag-move is untouched.

# Plan: Files Move dialog destination at 320px / 200%

## Goal

The Files Move dialog shows the full selected destination at a 320px viewport and a 200% app font scale, including one unbroken directory name, and the existing move, refusal, and retained-destination behaviour stays the same.

## MANDATE

The Files Move dialog clips its destination Select at 320px / 200%, even full-screen.

* **ID:** f-20261007-04 · **Status:** open · **Area:** frontend-ui · **Root:** - · **Entry:** build · **Blocked:** none
* **Where:** `src/components/files/FilesPage.tsx`, the Move `AppModal` and its "Destination folder" `Select` (data: `Files.CollectionRoot` plus every directory label of the collection).
* **Defect:** at a 320px viewport and a 200% font scale (the `database-files` e2e project) the dialog's destination input cannot show its default value: `assertNothingClipped(dialog)` (`e2e/fixtures.ts`) reports `mantine-Select-input: x 271px > 220px` for "Collection root" in the default modal, and still 271px > 252px when the modal is made `fullScreen` below 30em (measured 2026-10-07 in the pinned container by the f-20260919-07 fix leaf, test "Move dialog fits 320px and selects a destination", not committed). Directory labels are user-chosen and unbounded, so any single-line Select clips a long one; the user cannot read which destination is selected.
* **Open question:** how should the Move dialog present open-ended destination names at narrow widths — a wrapping list (radio group or tree of directories) instead of a single-line Select, a Select whose options and selected value wrap, or a shorter fixed root label plus ellipsis with the full name on focus/title? The answer applies to any future Files form that picks a directory.
* **Why it matters:** `d-20260919-12` holds the Files page to the 320px / 200% layout discipline; this dialog is the one Files form that still fails it, and the e2e suite has no assertion over it.
* **Related:** `f-20260919-07` (its push review, tests lens R2-3, asked for the browser assertion that exposed this; that change makes only the edit/create/rename dialog full-screen below 30em, constant `COMPACT_DIALOG_QUERY`), `f-20260829-02` (handled; the 320px / 200% clipping class and `assertNothingClipped`).
* **Found by:** the f-20260919-07 cumulative diff review, closure round 2, 2026-10-07.

Pickup at BASE `b60ae5a4e662ebe06caa62a8a1343f3c87eec343`: the defect still holds. The dialog now lives in `useFileWorkspace`, not `FilesPage.tsx`. Nothing in this cluster is closed or rejected. Tier stays `build`: the open question is which presentation mechanism makes an unbounded name readable, and the proof has to cross the dialog, the unit harness, and the clipping instrument. That is the plan, not a one-line mirror.

## Threat model and non-goals

The user is someone using the Files page at a 320px CSS viewport with the app font scale at 200%, in English or German, with a directory whose name is one long unbroken token. A destination can also disappear from the listing while the dialog is open; that case is already specified and must keep working. This is not an attacker, a storage adversary, or a native-filesystem boundary.

Frozen with this section: no new locale strings, no second directory tree, no shared picker component, no change to drag-move or to the move IPC.

## Traced premises

* The Move dialog is `AppModal` in `src/components/files/useFileWorkspace.tsx` around the `opened={moveTarget !== null}` block. It does not set `fullScreen`. The create/rename/edit dialog above it does set `fullScreen={compactDialog}`.
* `compactDialog` is `useScaledMaxWidth(COMPACT_DIALOG_WIDTH_EM)` with `COMPACT_DIALOG_WIDTH_EM = 30`. The constant comment still describes the type Select, not Move.
* Destinations are the collection root, labelled with `Files.CollectionRoot` ("Collection root"), plus every directory from a depth-first walk, labelled with `entry.name` only. A destination that leaves the listing is appended back as `presentation.destination` so the chosen label stays visible and is not a new write target.
* `openMove` selects the collection root. The Move button submits `moveEntry` with that handle. Choosing an empty Select value calls `closePresentation`. Drag-move calls `moveEntry` directly and never opens this dialog.
* The Move submit button already passes `styles={libraryButtonProps.styles}` (`wrappingButton`). The sibling Confirm button also passes `miw={0}` and the rest of `libraryButtonProps`.
* `DirectoryTree` renders each name with `miw={0}` and `overflowWrap: "anywhere"`. `src/styles/global.css` defines `.wrap-anywhere` for the same break. `d-20260927-28` chose that break over ellipsis for text that does not fit at 320px / 200%.
* `assertNothingClipped` default mode is horizontal-only and counts a box narrower than its content, scroll containers included. `mode: "reachable"` returns early for a non-empty `HTMLInputElement` of type `text`, so a Select input can pass the reachable checks in `e2e/async-errors.spec.ts` while failing the default mode the finding measured.
* The unit harness mocks `@mantine/core` `Select` as a native `<select>`. `FilesPage.test.tsx` drives the Move dialog through `[role="dialog"] select` in "move retains a removed destination and refuses a second write", and several move cases assert that the first `[role="dialog"] input` has value `undefined`.
* `e2e/async-errors.spec.ts` opens Move, chooses the destination through a textbox named with `Files.DestinationFolder` and an option, then asserts that textbox's value. Its dialog check is `assertNothingClipped(dialog, { mode: "reachable" })`. It screenshots `workspace-refusal-move-{retained,relist-failed}-320-200-{en-US,de-DE}`.
* No test in `e2e/database-files.spec.ts` opens Move. That project's font scale is already 200%. Its viewport default is 800px; the metadata test sets 320px itself.
* `FilesPage.tsx` is gone. The page renders this hook. `d-20260919-12` still governs the page: two columns, no `overflow: hidden` on a column, content at 320px / 200% must not be absorbed by a scroll container. It does not choose the Move destination control. Its Select-versus-chips choice is the file-type filter.

## Approach

### Destination control

Replace the Move dialog's Mantine `Select` with a Mantine `Radio.Group` of one `Radio` per current destination. The group label is the existing `Files.DestinationFolder` string. Each radio's visible label is the same string the Select shows today: `Files.CollectionRoot` for the root, `entry.name` for a directory. The radio value is `fileWorkspaceKey(entry.handle)`.

The selected label is ordinary wrapping text, using the existing `wrap-anywhere` behaviour (`overflow-wrap: anywhere`) and `miw={0}` on the group, each option, and the label, the same way the Files tree keeps a long name inside its row. The full selected name is visible without horizontal scrolling and without a `title` tooltip. An unbroken name wraps mid-word, which `d-20260927-28` already accepts.

Do not extract a picker component. The mandate's sentence about a future Files form is a constraint on this choice, not a second caller. A later form repeats this pattern.

### Dialog layout

Give the Move `AppModal` `fullScreen={compactDialog}` and put its body in a `Stack` with `miw={0}`, matching the create/rename/edit dialog in the same hook. Full-screen alone does not fix the clip; the 2026-10-07 measurement already showed 271px against 252px. It only gives the wrapping list the same width the sibling dialogs already use. Do not add a breakpoint.

The Move submit button keeps `libraryButtonProps` and gains `miw={0}`, matching Confirm, so the button cannot force the stack wider than the dialog. Do not change its label, colour, or disabled rule.

A long destination list may scroll vertically inside the dialog. It must not scroll horizontally and must not use `overflow: hidden` to swallow a wide label. Default `assertNothingClipped` counts a horizontal scroll container as clipped.

### Selection and failure behaviour

Opening Move still selects the collection root. Choosing another radio selects that destination and does not submit and does not close. Activating the already selected radio does not close the dialog. The empty-Select close path goes away with the Select; the dialog still closes through its close button, through `closePresentation` after a successful move, and through the existing refusal paths.

`moveEntry`, the in-flight guard, the owner check, the retained destination after it disappears from the listing, and the refusal copy stay as they are. A retained destination remains one selected radio whose label is still the name it had, and a second Move press still does not call native move again.

Drag-move is untouched.

### Tests that already drive the Select

Update `FilesPage.test.tsx` so the retained-destination test chooses the destination radio whose label is `destination.name` and whose value is that handle, then still asserts one native move, the refusal copy, and that the same radio stays selected with that label after the listing drops the directory.

Any assertion that the Move dialog's first `input` has value `undefined` is an assertion about the old Select, which rendered no text input. Point those assertions at the name field of the dialogs that have one. Do not require the Move dialog to contain no `input`.

The typed-refusal cases also read the dialog `select` and, for Move, expect that value to be the collection-root workspace key. Point that Move expectation at the checked destination radio. Metadata tests still use `[role="dialog"] select`. Rename still has no select.

The unit harness keeps the existing `@mantine/core` mock as its boundary. Each destination is a labelled radio whose value is the handle key. How that mock draws the radio is the executor's, inside that boundary.

Update `e2e/async-errors.spec.ts` so the Move cases choose `getByRole("radio", { name: destination.name })` instead of the destination textbox and option, and assert that radio is checked after the refusal. Keep the reachable-mode dialog check, the single native `move_workspace_entry`, the relist behaviour, and the four screenshot names. Re-record only those four screenshots, in the pinned container, under `d-20260919-13`: read each diff, predict that set, and stop if any other snapshot moves.

### Clipping proof

Add one test to `e2e/database-files.spec.ts`. Set the viewport to 320×900. The project already sets the 200% font scale. Open Move on a file in a collection whose directories include the collection root and one directory named with a single unbroken token wider than the dialog. Before changing the selection, the dialog shows the full `Collection root` label as text. Choose the long directory. The dialog shows that full token as text. Call `assertNothingClipped(dialog)` with the default mode, not `reachable`. Submit Move and assert the native command's target directory is that directory's handle.

This is the assertion the finding asked for. The reachable-mode exemption for a text input must not be the proof.

Default mode is horizontal only, so it does not see a label clipped to one line on the vertical axis. Also call `assertNothingClipped` in `reachable` mode on the element that shows the long directory name. A one-line box with vertical `overflow: hidden` fails that call. Do not add a clipping helper. The short-name refusal screenshots are not this check.

## Decisions and trade-offs

Question: how should the Move dialog present an open-ended destination name at 320px / 200%?

Chosen: a wrapping radio group of the current destination labels, inside the existing Move dialog, with that dialog full-screen below the existing 30em scaled width. The selected name is wrapping text.

Rejected: a Select whose selected value wraps. The closed Mantine Select value is an `input`, and an input does not wrap. The 2026-10-07 measurement is that input's scroll width.

Rejected: ellipsis, a shorter root label, or the full name on `title` or focus. `d-20260927-28` rejected ellipsis because it hides the word. A `title` is not available as readable text at 320px. Default `assertNothingClipped` still fails a Select input whose scroll width exceeds its box, and the reachable mode's text-input exemption would hide that failure.

Rejected: a second directory tree in the dialog. The page tree selects an entry to act on. The dialog needs one destination. A tree would be a second selection model for the same handles.

Rejected: building the shared picker the mandate says a future form should follow. There is one caller. The decision is the pattern, not a component.

This is a mechanism choice. `d-20260927-28` already chose mid-word wrapping over a cut or an ellipsis, and test 3 of the ledger's park rule keeps a choice between working mechanisms technical. The adopter records it with `./scripts/findings.py record-decision`. Reversal path: the Move dialog block in `useFileWorkspace.tsx` and the Move branches in `FilesPage.test.tsx` and `e2e/async-errors.spec.ts`.

`d-20260919-12` is applied, not reopened. It requires the Files surface to be readable at 320px / 200% and does not specify this control.
