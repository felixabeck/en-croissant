# Plan: engine-list publication after durable saves

## Goal

Close f-20261001-17 by keeping ordinary engine-list updates out of the authoritative renderer list until the owner receipt confirms persistence, while keeping engine editing responsive and preserving permanent removal's already decided failure contract.

## MANDATE

### `enginesAtom` publishes a new engine list before its owner save resolves, so a refused save leaves memory ahead of storage

* **ID:** f-20261001-17 · **Status:** open · **Area:** frontend-state · **Root:** - · **Entry:** build · **Blocked:** none
* **Where:** `src/state/atoms.ts:244-260` (`set(storedEnginesAtom, next)` publishes in memory first), `src/state/engineOwnerStorage.ts:166-228` (receipt `saved:false` without restoring), callers `src/components/engines/EnginesPage.tsx:385-397` (settings edits), `:649-662` (Duplicate selects `selected + 1` immediately), `:676-683` (Remove retires the id before the save, per `d-20260901-17`).
* **Defect:** after a refused save (attachment prepare failure, quota, invalid record) the in-memory list keeps the unsaved value for the rest of the session while storage holds the old one. The refusal is notified (`reportPersistError` → `notifyListenerError`), but the UI keeps showing and using state that will vanish on restart.
* **Why it matters:** violates the persisted-state write/read symmetry the rules ask for; the user acts on a list that is not durable.
* **Open question:** a general fix interacts with three callers: restoring the old value after refusal makes Remove (which retires the id first, `d-20260901-17`) leave a visible but tombstoned engine and makes Duplicate's immediate selection index a missing entry; publishing only after the save makes per-keystroke settings edits wait on an IPC round trip. Which contract — optimistic with restore plus reordered Remove/Duplicate, or staged publication with a local draft for edits — and does it supersede `d-20260901-17`'s ordering?
* **Context:** the Stockfish 19 upgrade plan (`tasks/plans/2026-10-01-stockfish-19-upgrade.md`) gives catalog install and upgrade a publish-after-save path of their own; this finding covers every other caller.
* **Found by:** Codex lenses `review-correctness`, `review-persisted-state`, `review-error-handling`, `review-plan` (rounds 1-2 of that plan review), confirmed by the orchestrator from source, 2026-10-01.

## Approach

### O1 — ordinary updates commit before publishing

Make after-save publication the ordinary `enginesAtom` write contract, including existing explicit `after-save` callers. Use the existing serializer, strict validation, owner coordinator and correlated receipt. Do not publish either through Jotai's optimistic storage setter or the override before the owner save confirms `saved:true`. Preserve prepare → renderer storage → reconcile ordering. Publish saved-but-unsynchronized values because they are durable, with the existing error reporting.

Functional updates calculate from the latest authoritative list after prior queued updates settle, including after a refused predecessor. Hydration cannot overwrite a published result. Candidate construction is immutable, including nested settings. A refusal or unexpected rejection leaves the pre-operation authoritative list intact. The update sequence remains usable after failure. Both legacy migration and player-owner coordination retain their existing behavior. No second persistence coordinator.

### O2 — permanent local removal has an explicit exception

Preserve d-20261007-10, which already superseded only d-20260901-17's retire-before-drop clause. Introduce a narrowly typed local-id removal operation through the same engine-list owner, rather than a caller-selectable generic optimistic publication mode. It removes only the captured existing local engine id from the latest list and publishes that omission before awaiting its owner save. The omission remains on every failed-save exit. Local removal still clears selection, attempts persistence, then invokes native retirement on every exit, with the existing resolved-receipt versus rejected-setter notification behavior. Retirement failure never restores the id.

This is the existing documented session-safety exception to durability symmetry: on a refused save the old durable registration may reappear after application restart, when the native tombstone also resets. Do not claim removal persisted when `saved:false`. Other fields and ordinary adds never receive this exception. Keep one renderer liveness authority, without a parallel pending-retirement set. Queued ordinary edits and reorder intents must not reinsert an absent target. Confirmation captures immutable id, not a later selection index.

### O3 — responsive editing uses isolated drafts

Extract one engine-edit draft contract shared by local and cloud inline editors. Its immediate controlled values belong only to the editor, keyed by immutable engine id, never to `enginesAtom` or engine/game consumers. Capture event values synchronously. Submit immutable field or named-option intents against the latest queued authoritative record, never an entire stale displayed snapshot. Merge only the fields the action actually changes, preserving newly committed attachments, upgrade handle/catalog metadata, other options and legacy assessment. A target that disappeared cannot be re-created by a late draft.

Keep retained draft state bounded to current editable fields/options and their latest intent identity, rather than a growing edit history. Accepted edits enter the existing save sequence immediately. Older success/failure results cannot overwrite newer input. Once the newest edit settles, a failed field returns to the authoritative value and a saved field follows the committed value. A failed earlier edit does not get implicitly carried into a later unrelated edit. Defaults and Reset are deliberate option intents with the same receipt contract, and must not loop on a refused save. Unmount/identity swap ends UI ownership, guards late callbacks, and releases settled draft state while already accepted writes finish and report failures. No debounce that strands unsent edits on navigation.

Attachment issuance/adoption remains with `EngineAttachmentDraft`. Only a persisted attachment is shown in the authoritative engine record. Refusal preserves the previous image/resources, and draft cleanup retains its current ownership/correlation safeguards. Form and JSON submissions await their own receipt, retain the editor on refusal, and close only after a saved result. JSON replacement preserves the target id and legacy identity contract.

### O4 — action completion follows receipt and identity

Duplicate creates one new id per action and inserts relative to the captured source id in the latest list. Selection changes only after a saved insertion and resolves the created id's then-current index. A refused insertion preserves the current selection. A source removed before insertion is not silently duplicated from its captured snapshot. Scope busy/stale guards to the action owner so a late completion cannot steal selection after navigation or another selection. Cloud add/remove follow the ordinary publication contract and contain rejected promises, with no second error notification for receipts already reported by persistence.

Cover all production writers: EnginesPage, AddEngine, EditEngine, UpgradeEngineModal, EngineSelection, BestMoves, and AnalysisPanel. Existing catalog after-save behavior stays compatible. Analysis drag reorder submits identity/order intent against current records, preserves current membership and fields, and discards only its own optimistic presentation on refusal. Engine load state and persisted synced defaults become authoritative only after a saved receipt. Existing per-tab unsynced analysis settings remain separate user state.

## Approach

### O1 — ordinary updates commit before publishing

Make after-save publication the ordinary `enginesAtom` write contract, including existing explicit `after-save` callers. Use the existing serializer, strict validation, owner coordinator and correlated receipt. Do not publish either through Jotai's optimistic storage setter or the override before the owner save confirms `saved:true`. Preserve prepare → renderer storage → reconcile ordering. Publish saved-but-unsynchronized values because they are durable, with the existing error reporting.

Functional updates calculate from the latest authoritative list after prior queued updates settle, including after a refused predecessor. Hydration cannot overwrite a published result. Candidate construction is immutable, including nested settings. A refusal or unexpected rejection leaves the pre-operation authoritative list intact. The update sequence remains usable after failure. Both legacy migration and player-owner coordination retain their existing behavior. No second persistence coordinator.

### O2 — permanent local removal has an explicit exception

Preserve d-20261007-10, which already superseded only d-20260901-17's retire-before-drop clause. Introduce a narrowly typed local-id removal operation through the same engine-list owner, rather than a caller-selectable generic optimistic publication mode. It removes only the captured existing local engine id from the latest list and publishes that omission before awaiting its owner save. The omission remains on every failed-save exit. Local removal still clears selection, attempts persistence, then invokes native retirement on every exit, with the existing resolved-receipt versus rejected-setter notification behavior. Retirement failure never restores the id.

This is the existing documented session-safety exception to durability symmetry: on a refused save the old durable registration may reappear after application restart, when the native tombstone also resets. Do not claim removal persisted when `saved:false`. Other fields and ordinary adds never receive this exception. Keep one renderer liveness authority, without a parallel pending-retirement set. Queued ordinary edits and reorder intents must not reinsert an absent target. Confirmation captures immutable id, not a later selection index.

### O3 — responsive editing uses isolated drafts

Extract one engine-edit draft contract shared by local and cloud inline editors. Its immediate controlled values belong only to the editor, keyed by immutable engine id, never to `enginesAtom` or engine/game consumers. Capture event values synchronously. Submit immutable field or named-option intents against the latest queued authoritative record, never an entire stale displayed snapshot. Merge only the fields the action actually changes, preserving newly committed attachments, upgrade handle/catalog metadata, other options and legacy assessment. A target that disappeared cannot be re-created by a late draft.

Keep retained draft state bounded to current editable fields/options and their latest intent identity, rather than a growing edit history. Accepted edits enter the existing save sequence immediately. Older success/failure results cannot overwrite newer input. Once the newest edit settles, a failed field returns to the authoritative value and a saved field follows the committed value. A failed earlier edit does not get implicitly carried into a later unrelated edit. Defaults and Reset are deliberate option intents with the same receipt contract, and must not loop on a refused save. Unmount/identity swap ends UI ownership, guards late callbacks, and releases settled draft state while already accepted writes finish and report failures. No debounce that strands unsent edits on navigation.

Attachment issuance/adoption remains with `EngineAttachmentDraft`. Only a persisted attachment is shown in the authoritative engine record. Refusal preserves the previous image/resources, and draft cleanup retains its current ownership/correlation safeguards. Form and JSON submissions await their own receipt, retain the editor on refusal, and close only after a saved result. JSON replacement preserves the target id and legacy identity contract.

Duplicate creates one new id per action and inserts relative to the captured source id in the latest list. Cloud add/remove follow the ordinary publication contract and contain rejected promises, with no second error notification for receipts already reported by persistence. Cloud add preserves one registration per provider type: admission is guarded while its save is pending, and its queued updater checks the latest list for an existing provider before insertion. Refusal releases admission so a deliberate retry can succeed. The committed-list disabled state alone is insufficient during preparation.

## Approach

### O1 — ordinary updates commit before publishing

Make after-save publication the ordinary `enginesAtom` write contract, including existing explicit `after-save` callers. Use the existing serializer, strict validation, owner coordinator and correlated receipt. Do not publish either through Jotai's optimistic storage setter or the override before the owner save confirms `saved:true`. Preserve prepare → renderer storage → reconcile ordering. Publish saved-but-unsynchronized values because they are durable, with the existing error reporting.

Functional updates calculate from the latest authoritative list after prior queued updates settle, including after a refused predecessor. Hydration cannot overwrite a published result. Candidate construction is immutable, including nested settings. A refusal or unexpected rejection leaves the pre-operation authoritative list intact. The update sequence remains usable after failure. Both legacy migration and player-owner coordination retain their existing behavior. No second persistence coordinator.

### O2 — permanent local removal has an explicit exception

Preserve d-20261007-10, which already superseded only d-20260901-17's retire-before-drop clause. Introduce a narrowly typed local-id removal operation through the same engine-list owner, rather than a caller-selectable generic optimistic publication mode. It removes only the captured existing local engine id from the latest list and publishes that omission before awaiting its owner save. The omission remains on every failed-save exit. Local removal still clears selection, attempts persistence, then invokes native retirement on every exit, with the existing resolved-receipt versus rejected-setter notification behavior. Retirement failure never restores the id.

This is the existing documented session-safety exception to durability symmetry: on a refused save the old durable registration may reappear after application restart, when the native tombstone also resets. Do not claim removal persisted when `saved:false`. Other fields and ordinary adds never receive this exception. Keep one renderer liveness authority, without a parallel pending-retirement set. Queued ordinary edits and reorder intents must not reinsert an absent target. Confirmation captures immutable id, not a later selection index.

### O3 — responsive editing uses isolated drafts

Extract one engine-edit draft contract shared by local and cloud inline editors. Its immediate controlled values belong only to the editor, keyed by immutable engine id, never to `enginesAtom` or engine/game consumers. Capture event values synchronously. Submit immutable field or named-option intents against the latest queued authoritative record, never an entire stale displayed snapshot. Merge only the fields the action actually changes, preserving newly committed attachments, upgrade handle/catalog metadata, other options and legacy assessment. A target that disappeared cannot be re-created by a late draft.

Keep retained draft state bounded to current editable fields/options and their latest intent identity, rather than a growing edit history. Accepted edits enter the existing save sequence immediately. Older success/failure results cannot overwrite newer input. Once the newest edit settles, a failed field returns to the authoritative value and a saved field follows the committed value. A failed earlier edit does not get implicitly carried into a later unrelated edit. Defaults and Reset are deliberate option intents with the same receipt contract, and must not loop on a refused save. Unmount/identity swap ends UI ownership, guards late callbacks, and releases settled draft state while already accepted writes finish and report failures. No debounce that strands unsent edits on navigation.

Attachment issuance/adoption remains with `EngineAttachmentDraft`. Only a persisted attachment is shown in the authoritative engine record. Refusal preserves the previous image/resources, and draft cleanup retains its current ownership/correlation safeguards. Form and JSON submissions await their own receipt, retain the editor on refusal, and close only after a saved result. JSON replacement preserves the target id and legacy identity contract.

### O4 — action completion follows receipt and identity

Duplicate creates one new id per action and inserts relative to the captured source id in the latest list. Selection changes only after a saved insertion and resolves the created id's then-current index. A refused insertion preserves the current selection. A source removed before insertion is not silently duplicated from its captured snapshot. Scope busy/stale guards to the action owner so a late completion cannot steal selection after navigation or another selection. Cloud add/remove follow the ordinary publication contract and contain rejected promises, with no second error notification for receipts already reported by persistence. Cloud add preserves one registration per provider type: admission is guarded while its save is pending, and its queued updater checks the latest list for an existing provider before insertion. Refusal releases admission so a deliberate retry can succeed. The committed-list disabled state alone is insufficient during preparation.

Cover all production writers: EnginesPage, AddEngine, EditEngine, UpgradeEngineModal, EngineSelection, BestMoves, and AnalysisPanel. Existing catalog after-save behavior stays compatible. Analysis drag reorder submits identity/order intent against current records, preserves current membership and fields, and discards only its own optimistic presentation on refusal. Engine load state and persisted synced defaults become authoritative only after a saved receipt. An unload must not issue a generationless native stop before saving.
