## Approach

### O1 — One legal search description

`analysisSearch` owns derivation of the actual final position and a typed available or unavailable search description. An available description contains one searched FEN, move sequence, side to move and key. An unavailable result contains no usable search identity. Keep root validation and game-over information available for their existing precedence.

For threat mode, derive the actual final position through legal replay, change the side to move, clear the expired en-passant field and validate the hypothetical setup with chessops before publishing its description. In-check positions cannot skip their turn and therefore have no threat search. Invalid root/replay also yields no threat search, with no initial-position fallback and no exception escaping render. Preserve the board, valid castling rights and existing analysis clock convention. This is a hypothetical setup, not a move appended to the game tree. Valid normal analysis retains its exact root-FEN and move-sequence request/key contract and searched turn.

Verification level: real chessops unit tests assert cleared threat en-passant, rejected opposite check and no fabricated fallback, while normal keys and normal en-passant rights remain unchanged. Both root colours and Chess960 castling remain representable. Reverting the producer fix with the tests retained must fail on the expired en-passant or unavailable-check assertion.

### O2 — Availability is a search lifecycle boundary

`EvalListener` consumes O1's description for local, Lichess and ChessDB analysis. Entering unavailable cancels the prior transient attempt, stops its exact predecessor generation and handles retained/preparing owners through existing cleanup ownership. It reserves no new generation and dispatches no local or remote search for an unavailable position. Pending preparation, payloads, successful completions and errors from a retired attempt cannot publish lines, score, progress or a terminal failure for the unavailable position. Progress becomes idle. A real stop/release failure retains the existing error reporting and native ownership policy.

Navigating to an available position or turning threat mode off uses the ordinary current-attempt lifecycle again. Preserve tab, immutable engine id, executable identity, settings, go mode and generation guards. Do not clear the selected threat mode or engine-enabled preference merely because one position is unavailable.

Verification level: listener integration tests exercise available → unavailable → available, including an in-flight preparation and a late payload or completion. They assert the generation being stopped, absence of preparation/search dispatch while unavailable, absence of new cached lines/score/terminal/progress and successful recovery. Exercise remote result suppression too. Keep the actual search derivation and chessops in the regression path, repairing null-position legacy mocks as needed.

### O3 — All readers agree on absence and source position

`useDisplayedEngineLines` consumes O1 for cache lookup and waiting. Unavailable analysis exposes no current or historical PV, evaluation, matching engine failure, delayed loading or retry state. It is not an engine crash. Invalid-root and original game-over displays keep their established precedence. Preserve bounded, per-mode previous-line retention and dimmed/inert fallback for transitions between available searches.

The display result supplies the board belonging to displayed lines from the shared description, including the remembered description for a historical fallback. `BestMoves` uses that supplied board directly for SAN rows and previews and no longer independently calls `swapMove`. Retain the corresponding source halfMoves and threat numbering convention. Its existing `NoAnalysisAvailable` empty state is used for unavailable threat positions, and its progress/loading affordances are idle. DetachedEval retains its existing empty dash, and EngineSummary retains its existing empty-score presentation. Both must show no stale PV or evaluation through the shared hook. No new translation keys or copy are proposed.

`createBestMovesAtom` and `createFirstEngineWithLinesAtom` return empty arrows and null owner when O1 has no search. Otherwise they use its exact key and searched turn. No alternate key, sentinel starting FEN, per-consumer turn flip or independent legality check is introduced. Availability is derived ephemeral state and is never persisted.

Verification level: hook, selector and DOM integration tests seed current and historical threat lines, enter an unavailable position and prove they are absent across the list, detached view, summary and arrows. Returning to legal threat analysis restores the proper key and lines. Tests also retain the old dimmed-fallback behavior between available positions and assert that the row FEN belongs to its displayed PV.

## Decisions and trade-offs

### Decided autonomously — shared absence

Optimal: one typed available/unavailable search description → I recommend it. It resolves the finding's open question at the producer and makes every reader consume the same answer. Rejected: retaining a fabricated initial-FEN key, relying on a backend error, or disabling the mode permanently when check occurs. Those retain wrong identity, noise or lost user intent. Reversal path: replace the internal representation while preserving O1–O3 and all consumer tests. The adopter records this decision through `findings.py record-decision` before implementation.

### Decided autonomously — existing empty presentation

Use the shipped no-analysis row, detached dash and summary empty score for a legal board whose threat search is unavailable. Existing invalid-board and game-over states keep priority. Rejected: inventing a threat-specific message or a new user option. The existing empty displays already communicate unavailable analysis, and the defect requires accurate availability rather than a new product promise. Reversal path: a separately authorized copy decision can replace that presentation without changing legality or ownership. The adopter records this technical mapping with its precedent in BestMoves and DetachedEval.

### Decided autonomously — separate editor operation

Keep `swapMove`'s explicit position-editor contract separate. Put validated threat derivation in the existing shared analysis producer and route both search and display through it. Rejected: returning null from the editor helper or retaining a second threat-board derivation in BestMoves. Reversal path: a later editor-specific change may replace its helper after all its callers are traced. No general editor repair is proposed here.
