# Plan: cancellable required-index DDL (f-20260914-19)

## Goal

`create_indexes` and `delete_indexes` observe cancellation while waiting for the per-database
index lock and while SQLite executes the index DDL, roll the DDL back when cancellation wins, and
report `Error::Cancellation` exactly when nothing was committed. Success is reported only when the
DDL transaction committed.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-19`:

* **Where:** src-tauri/src/db/mod.rs:1190 (`create_indexes`, `delete_indexes`)
* **Defect:** Cancellation is checked only when the worker is admitted; the SQLite DDL and the
  index-lock wait are not cancellable. On a large database, cancelling during index creation can
  still mutate the database and report success.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` (cancellation before use,
  truthful terminal state).
* **Open question:** Can the DDL be interrupted safely (SQLite progress handler /
  `sqlite3_interrupt`) with a defined rollback, or must cancellation be refused once DDL starts and
  reported as such?

## Threat model and non-goals

Accidental input only: a large but well-formed user database, a concurrent search-index build
holding the index lock, and application shutdown cancelling accepted operations. No adversarial
SQL or crafted database is in scope; the DDL text is the fixed `indexes.sql` /
`delete_indexes.sql` contract. All three desktop platforms count; the mechanism is SQLite's
platform-independent progress callback, so no `cfg(target_os)` code is added.

## Traced premises

Frozen Locate citations (BASE `0e179a9a`):

1. `src-tauri/src/db/mod.rs:1435-1451` / `1472-1488` — both commands call
   `BLOCKING_GATEWAY.spawn_cancellable(cancellation, move |_| …)` and discard the worker token.
   `src-tauri/src/infra/blocking.rs:484-512` checks the token only before the permit and once at
   worker start.
2. `src-tauri/src/db/mod.rs:1453-1470` / `1490-1507` — the blocking bodies take
   `repository.with_index_lock` (uncancellable `parking_lot` lock,
   `src-tauri/src/db/repository.rs:735-744`) and `get_db_or_create(…, None, …)`. These two are the
   only callers of `with_index_lock`; `with_index_lock_cancellable`

   `generate_search_index` (`mod.rs:1101-1102`), which holds the same index lock for a whole

   uncancellable index build to finish today.
6. Diesel 2.1.4 `AnsiTransactionManager::transaction` (registry source
   `diesel-2.1.4/src/connection/transaction_manager.rs`): on a callback error it issues `ROLLBACK`;
   if that `ROLLBACK` fails at depth 1 it calls `set_in_error()` and returns the **rollback** error,
   replacing the callback's error. `SqliteConnection::is_broken` returns true for an in-error
   manager, and `BoundConnectionManager::has_broken` (`repository.rs:256-261`) delegates to it, so
   r2d2 discards such a pooled connection instead of reusing it.
7. Measured SQLite behaviour (rule 12b) — probe run 2026-10-04 with Python `sqlite3` against SQLite

   ```text
   create err: interrupted
   in_transaction after interrupt: False
   rollback err: cannot rollback - no transaction is active
   indexes: [('ia',)]                          # the DROP INDEX earlier in the txn was undone
   select err: interrupted
   in_transaction after interrupted SELECT: True
   commit under N=1 handler err: interrupted
     in_transaction: True rows(2,2): (2,)
   rollback under N=1 handler err: interrupted
     in_transaction: True rows(2,2): (2,)
   ```

   So: an interrupted **write/DDL** statement inside an explicit transaction makes SQLite roll the
   whole transaction back by itself; an interrupted **read** leaves the transaction open; and with
   the handler armed, `COMMIT` and `ROLLBACK` themselves are interrupted and leave the transaction
   open — the same hazard `d-20260926-04` recorded for `ROLLBACK`.

## Approach

### O1 — Cancellable DDL transaction primitive

Rests on "Can the DDL be interrupted safely … with a defined rollback" and "truthful terminal
state".

One helper beside `with_sqlite_cancellation` in `src-tauri/src/db/sqlite_cancellation.rs` runs a
caller body inside one Diesel transaction on a given connection, with this contract:

* **Scope boundary.** The progress-callback scope covers only the body's statements. `BEGIN`,
  `COMMIT` and `ROLLBACK` always execute with no scope active (premise 7: armed `COMMIT`/`ROLLBACK`
  are themselves interruptible and would strand an open transaction).
* **Pre-commit check.** After the body succeeds and before the transaction commits, the token is
  checked once more; a cancellation observed there fails the transaction, so Diesel's ordinary
  `ROLLBACK` (unarmed, transaction still open) undoes it.
* **Outcome mapping.** If the body's scope reported `Error::Cancellation`, or the pre-commit check
  failed, the helper returns `Error::Cancellation` — including when Diesel's subsequent `ROLLBACK`
  fails with "no transaction is active" because SQLite already rolled the interrupted DDL back
  (premise 6 would otherwise surface that rollback error instead). Every other body error and
  every commit error is returned unchanged. Success is returned only after `COMMIT` succeeded;
  a cancellation arriving after the commit does not turn a committed result into an error
  (`d-20260908-13`: commit tails report their actual outcome).
* **Connection state.** After the SQLite-auto-rollback path the Diesel manager is in error, so the
  connection must not be reused for a transaction; for repository pooled connections this is
  satisfied by `has_broken` discarding it (premise 6). The helper's doc comment states this
  requirement for callers. The explicit-rollback path leaves a valid, reusable connection.
* **Nesting.** The helper is for a top-level transaction only. It is not used inside an existing
  transaction or inside another `with_sqlite_cancellation` scope (the existing nested-scope
  refusal stays).

The doc comment of `with_sqlite_cancellation` is updated so it no longer forbids all schema work
in a scope: it points schema DDL at the new helper and keeps "connection acquisition and
migration/validation before the scope".

Verification (unit, `sqlite_cancellation.rs` tests, real SQLite): (a) a cancellation that
interrupts a DDL statement in the body returns `Error::Cancellation`, leaves the schema exactly as
before the transaction, and a fresh repository pooled connection to the same file then completes
a transaction; (b) a cancellation observed by the pre-commit check returns `Error::Cancellation`,
rolls back, and the **same** connection then completes a transaction; (c) an uncancelled body
commits; (d) a non-cancellation body error is returned unchanged and not reclassified. Each test
must go red if its guarded behaviour is removed (scope around `COMMIT`/`ROLLBACK`, missing
pre-commit check, or missing outcome mapping).

### O2 — Index commands use cancellation end to end

Rests on "Cancellation is checked only when the worker is admitted; the SQLite DDL and the
index-lock wait are not cancellable" and "can still mutate the database and report success".
Depends on O1.

* Both commands pass the gateway's worker token into their blocking bodies instead of `|_|`.
* Both blocking bodies wait for the index lock through `with_index_lock_cancellable` and open the
  connection with `get_db_or_create(…, Some(token), …)`. `with_index_lock` loses its last
  production caller and is removed (or made test-only if a test still needs it).
* `create_required_indexes` and `drop_required_indexes` keep one definition each (DDL, then the
  `check_index_exists` contract check). The command paths run them through the O1 helper with the
  token. The import path's call inside its outer transaction keeps its current, uncancellable
  behaviour (it must not open a nested O1 transaction or scope); the executor routes both callers
  through one body per operation rather than duplicating the SQL sequence.
* Terminal states: lock wait cancelled → `Error::Cancellation`, database untouched; DDL
  interrupted or pre-commit cancellation → `Error::Cancellation`, index set exactly as before the
  command; committed → `Ok(())`. A non-cancellation failure keeps its current error.

Verification (`src-tauri/src/db/mod.rs` tests, real repository, the existing
`blocking_database_case` fixtures): (a) `create_indexes_blocking` cancelled while SQLite executes
its DDL returns `Error::Cancellation` and `check_index_exists` plus the full index list equal the
pre-command state — run from a state where the required set is absent and from one where a
same-name wrong-definition index exists (the repair case of
`required_indexes_have_an_exact_status_and_can_be_repaired_atomically`); (b) the same for
`delete_indexes_blocking` starting from a complete set, which must remain complete; (c) each
command, run again uncancelled on the same database afterwards, succeeds (pool recovery);
(d) each command blocked on an index lock held by another thread returns `Error::Cancellation`
after its token is cancelled, without mutating the index set — the wait is proven entered through
the existing `cancellable_lock` wait observer, not a sleep. The DDL-interruption tests must prove
the cancellation was taken inside the DDL transaction rather than by an earlier pre-DDL check:
they must go red if the O1 helper is replaced by the plain transaction (cancellation then lands
after the pre-DDL checks and the DDL commits).

## Decisions and trade-offs

* **Interrupt with SQLite's own rollback, not "refuse once DDL starts".** The open question is
  answered by premise 7: an interrupted DDL statement in an explicit transaction is rolled back
  atomically by SQLite, and the required-index DDL is already one transaction (premise 3), so the
  rollback is defined. Refusing cancellation after DDL start would keep shutdown blocked behind a
  full index build on a large database (premise 5), which is the defect.
* **Scope the callback around the body only.** Rejected: wrapping the whole `conn.transaction`
  in `with_sqlite_cancellation`. Premise 7 and `d-20260926-04` show armed `COMMIT`/`ROLLBACK` are
  interruptible and can leave a pooled connection inside a transaction.
* **Accept discarding the connection after SQLite's auto-rollback.** Rejected: issuing raw
  `BEGIN`/`COMMIT` around Diesel's manager to avoid its in-error state — it bypasses the manager
  the rest of the repository relies on. Discarding one pooled connection on a cancelled index
  command costs one reconnect.
* **Import path unchanged.** Its index creation runs inside the import's outer transaction; an
  interrupt there would roll back the whole import, a separate behaviour change outside MANDATE.
* **Extends `d-20260908-14`, does not reverse it.** That decision scoped the callback to reads and
  preserved mutation behaviour; this plan adds a separately contracted write use with measured
  rollback semantics (premise 7). The read scope's behaviour is unchanged.

## Decided autonomously

* **Question:** Can required-index DDL be interrupted safely, or must cancellation be refused once
  DDL starts? **Chosen:** interrupt through the existing progress callback, scoped to the DDL body
  inside one top-level transaction, with `BEGIN`/`COMMIT`/`ROLLBACK` unarmed, a pre-commit token
  check, and outcome mapping to `Error::Cancellation` when nothing committed. **Rejected:**
  refusing cancellation after DDL start (keeps shutdown blocked); arming the whole transaction
  (interruptible `COMMIT`/`ROLLBACK`, `d-20260926-04`); raw `BEGIN`/`COMMIT` outside Diesel's
  manager. **Reason:** measured SQLite auto-rollback of an interrupted write statement in an
  explicit transaction (premise 7) plus Diesel 2.1.4's rollback-error replacement (premise 6).
  **Governs:** f-20260914-19. **Reversal path:** drop the helper and return to admission-only
  cancellation.

## Risks / open questions

* SQLite 3.39.2 (bundled) versus 3.45.1 (probe): the auto-rollback of an interrupted write
  statement is long-documented behaviour of `sqlite3_interrupt`, and the O1/O2 tests run on the
  bundled library, so a difference turns a test red rather than shipping silently.
* With `SQLITE_PROGRESS_VM_STEPS = 1000` in production, a very short DDL may finish before a
  callback fires; it then commits and reports success, which is truthful.

## Not part of this task

* Cancellability of the import path's index creation, or of migrations/validation in connection
  acquisition.
* Whether index commands should also take the database write lock.
* Renderer changes: accepted operations stay renderer-uncancellable (`d-20260908-13`); the
  Databases page already ignores `Cancellation` through `notifyUnlessCancelled`.

   r2d2 discards such a pooled connection instead of reusing it.
7. Measured SQLite behaviour (rule 12b) — probe run 2026-10-04 with Python `sqlite3` against SQLite
   3.45.1 (the bundled crate is 3.39.2; the phase tests re-measure on the bundled library):

   ```text
   create err: interrupted
   in_transaction after interrupt: False
   rollback err: cannot rollback - no transaction is active
   indexes: [('ia',)]                          # the DROP INDEX earlier in the txn was undone
   select err: interrupted
   in_transaction after interrupted SELECT: True
   commit under N=1 handler err: interrupted
     in_transaction: True rows(2,2): (2,)
   rollback under N=1 handler err: interrupted
     in_transaction: True rows(2,2): (2,)
   ```

   So: an interrupted **write/DDL** statement inside an explicit transaction makes SQLite roll the
   whole transaction back by itself; an interrupted **read** leaves the transaction open; and with
   the handler armed, `COMMIT` and `ROLLBACK` themselves are interrupted and leave the transaction
   open — the same hazard `d-20260926-04` recorded for `ROLLBACK`.

## Approach

### O1 — Cancellable DDL transaction primitive

Rests on "Can the DDL be interrupted safely … with a defined rollback" and "truthful terminal
state".

One helper beside `with_sqlite_cancellation` in `src-tauri/src/db/sqlite_cancellation.rs` runs a
caller body inside one Diesel transaction on a given connection, with this contract:

* **Scope boundary.** The progress-callback scope covers only the body's statements. `BEGIN`,
  `COMMIT` and `ROLLBACK` always execute with no scope active (premise 7: armed `COMMIT`/`ROLLBACK`
  are themselves interruptible and would strand an open transaction).
* **Pre-commit check.** After the body succeeds and before the transaction commits, the token is
  checked once more; a cancellation observed there fails the transaction, so Diesel's ordinary
  `ROLLBACK` (unarmed, transaction still open) undoes it.
* **Outcome mapping.** When the body's scope reported `Error::Cancellation`, or the pre-commit
  check failed, the helper returns `Error::Cancellation` in exactly two cases: Diesel's `ROLLBACK`
  succeeded, or it failed with SQLite's "cannot rollback - no transaction is active" (the verified
  auto-rollback case of premise 7, which premise 6 would otherwise surface as a Diesel error). Any
  other rollback failure after a cancellation is returned as that failure, not as cancellation, so
  its diagnostic is logged and shown (`run_native_operation` logs `Cancellation` only at debug and
  `notifyUnlessCancelled` hides it). Every other body error and every commit error is returned
  unchanged. Success is returned only after `COMMIT` succeeded; a cancellation arriving after the
  commit does not turn a committed result into an error (`d-20260908-13`: commit tails report
  their actual outcome).
* **Connection state.** After the SQLite-auto-rollback path the Diesel manager is in error, so the
  connection must not be reused for a transaction; for repository pooled connections this is
  satisfied by `has_broken` discarding it (premise 6). The helper's doc comment states this
  requirement for callers. The explicit-rollback path leaves a valid, reusable connection.
* **Nesting.** The helper is for a top-level transaction only. It is not used inside an existing
  transaction or inside another `with_sqlite_cancellation` scope (the existing nested-scope
  refusal stays).

The doc comment of `with_sqlite_cancellation` is updated so it no longer forbids all schema work
in a scope: it points schema DDL at the new helper and keeps "connection acquisition and
migration/validation before the scope".

Verification (unit, `sqlite_cancellation.rs` tests, real SQLite): (a) a cancellation that
interrupts a DDL statement in the body returns `Error::Cancellation`, leaves the schema exactly as
before the transaction, and a fresh repository pooled connection to the same file then completes
a transaction; (b) a cancellation observed by the pre-commit check returns `Error::Cancellation`,
rolls back, and the **same** connection then completes a transaction; (c) an uncancelled body
commits; (d) a non-cancellation body error is returned unchanged and not reclassified; (e) after a
cancellation, a rollback failure other than "no transaction is active" is returned as that
failure and not as `Error::Cancellation` (the executor may prove this through the classification
step with constructed Diesel errors, since a real `ROLLBACK` failure such as `SQLITE_NOMEM` cannot
be induced reliably). Each test must go red if its guarded behaviour is removed (scope around
`COMMIT`/`ROLLBACK`, missing pre-commit check, missing or over-broad outcome mapping).

Platform level (threat model: all three desktop platforms count): the O1 tests, and any test
helper they need such as `cancel_on_callback`, compile and run under plain `cfg(test)`, not
`cfg(all(test, unix))`, so the `rust-windows-test` and `rust-macos-test` CI jobs execute them.

### O2 — Index commands use cancellation end to end

Rests on "Cancellation is checked only when the worker is admitted; the SQLite DDL and the
index-lock wait are not cancellable" and "can still mutate the database and report success".
Depends on O1.

* Both commands pass the gateway's worker token into their blocking bodies instead of `|_|`.
* Both blocking bodies wait for the index lock through `with_index_lock_cancellable` and open the
  connection with `get_db_or_create(…, Some(token), …)`. `with_index_lock` loses its last
  production caller and is removed (or made test-only if a test still needs it).
* `create_required_indexes` and `drop_required_indexes` keep one definition each (DDL, then the
  `check_index_exists` contract check). The command paths run them through the O1 helper with the
  token. The import path's call inside its outer transaction keeps its current, uncancellable
  behaviour (it must not open a nested O1 transaction or scope); the executor routes both callers
  through one body per operation rather than duplicating the SQL sequence.
* Terminal states: lock wait cancelled → `Error::Cancellation`, database untouched; DDL
  interrupted or pre-commit cancellation → `Error::Cancellation`, index set exactly as before the
  command; committed → `Ok(())`. A non-cancellation failure keeps its current error.

Verification (`src-tauri/src/db/mod.rs` tests, real repository, the existing
`blocking_database_case` fixtures): (a) `create_indexes_blocking` cancelled while SQLite executes
its DDL returns `Error::Cancellation` and `check_index_exists` plus the full index list equal the
pre-command state — run from a state where the required set is absent and from one where a
same-name wrong-definition index exists (the repair case of
`required_indexes_have_an_exact_status_and_can_be_repaired_atomically`); (b) the same for
`delete_indexes_blocking` starting from a complete set, which must remain complete; (c) each
command, run again uncancelled on the same database afterwards, succeeds (pool recovery);
(d) each command blocked on an index lock held by another thread returns `Error::Cancellation`
after its token is cancelled, without mutating the index set — the wait is proven entered through
the existing `cancellable_lock::observe_lock_wait` observer on the entry's index lock (a
`cfg(test)` accessor in `repository.rs` is allowed), not a sleep. The DDL-interruption tests must prove
the cancellation was taken inside the DDL transaction rather than by an earlier pre-DDL check:
they must go red if the O1 helper is replaced by the plain transaction (cancellation then lands
after the pre-DDL checks and the DDL commits). (e) Token wiring through the public commands: each
of `create_indexes` and `delete_indexes`, invoked as the async command with the test app's
`AppState`, blocks on an index lock held by the test, the wait is proven entered through the
`cancellable_lock` wait observer, then the app's `OperationRegistry` cancels it through
`seal_and_request_cancellation` (the shutdown path of premise 5); the command returns
`Error::Cancellation` and the index set is unchanged. This test must go red if a command passes
any token other than the gateway worker token into its blocking body.

Platform level: the O2 tests live in a plain `cfg(test)` module (the fixtures
`blocking_database_case`, `schema_database_case` and `database_app_with_grant` are already
`cfg(test)`, and `mod deletion_tests` is the existing cross-platform precedent), not in the
`cfg(all(test, unix))` `mod tests`, so the Windows and macOS CI jobs execute them.

## Decisions and trade-offs

* **Interrupt with SQLite's own rollback, not "refuse once DDL starts".** The open question is
  answered by premise 7: an interrupted DDL statement in an explicit transaction is rolled back
  atomically by SQLite, and the required-index DDL is already one transaction (premise 3), so the
  rollback is defined. Refusing cancellation after DDL start would keep shutdown blocked behind a
  full index build on a large database (premise 5), which is the defect.
* **Scope the callback around the body only.** Rejected: wrapping the whole `conn.transaction`
  in `with_sqlite_cancellation`. Premise 7 and `d-20260926-04` show armed `COMMIT`/`ROLLBACK` are
  interruptible and can leave a pooled connection inside a transaction.
* **Accept discarding the connection after SQLite's auto-rollback.** Rejected: issuing raw
  `BEGIN`/`COMMIT` around Diesel's manager to avoid its in-error state — it bypasses the manager
  the rest of the repository relies on. Discarding one pooled connection on a cancelled index
  command costs one reconnect.
* **Import path unchanged.** Its index creation runs inside the import's outer transaction; an
  interrupt there would roll back the whole import, a separate behaviour change outside MANDATE.
* **Extends `d-20260908-14`, does not reverse it.** That decision scoped the callback to reads and
  preserved mutation behaviour; this plan adds a separately contracted write use with measured
  rollback semantics (premise 7). The read scope's behaviour is unchanged.

## Decided autonomously

* **Question:** Can required-index DDL be interrupted safely, or must cancellation be refused once
  DDL starts? **Chosen:** interrupt through the existing progress callback, scoped to the DDL body
  inside one top-level transaction, with `BEGIN`/`COMMIT`/`ROLLBACK` unarmed, a pre-commit token
  check, and outcome mapping to `Error::Cancellation` when nothing committed. **Rejected:**
  refusing cancellation after DDL start (keeps shutdown blocked); arming the whole transaction
  (interruptible `COMMIT`/`ROLLBACK`, `d-20260926-04`); raw `BEGIN`/`COMMIT` outside Diesel's
  manager. **Reason:** measured SQLite auto-rollback of an interrupted write statement in an
  explicit transaction (premise 7) plus Diesel 2.1.4's rollback-error replacement (premise 6).
  **Governs:** f-20260914-19. **Reversal path:** drop the helper and return to admission-only
  cancellation.

## Approach

### O1 — Cancellable DDL transaction primitive

Rests on "Can the DDL be interrupted safely … with a defined rollback" and "truthful terminal
state".

One helper beside `with_sqlite_cancellation` in `src-tauri/src/db/sqlite_cancellation.rs` runs a
caller body inside one Diesel transaction on a given connection, with this contract:

* **Scope boundary.** The progress-callback scope covers only the body's statements. `BEGIN`,
  `COMMIT` and `ROLLBACK` always execute with no scope active (premise 7: armed `COMMIT`/`ROLLBACK`
  are themselves interruptible and would strand an open transaction).
* **Pre-commit check.** After the body succeeds and before the transaction commits, the token is
  checked once more; a cancellation observed there fails the transaction, so Diesel's ordinary
  `ROLLBACK` (unarmed, transaction still open) undoes it.
* **Outcome mapping.** When the body's scope reported `Error::Cancellation`, or the pre-commit
  check failed, the helper returns `Error::Cancellation` in exactly two cases: Diesel's `ROLLBACK`
  succeeded, or it failed with SQLite's "cannot rollback - no transaction is active" (the verified
  auto-rollback case of premise 7, which premise 6 would otherwise surface as a Diesel error). Any
  other rollback failure after a cancellation is returned as that failure, not as cancellation, so
  its diagnostic is logged and shown (`run_native_operation` logs `Cancellation` only at debug and
  `notifyUnlessCancelled` hides it). Every other body error and every commit error is returned
  unchanged. Success is returned only after `COMMIT` succeeded; a cancellation arriving after the
  commit does not turn a committed result into an error (`d-20260908-13`: commit tails report
  their actual outcome).
* **Connection state.** After the SQLite-auto-rollback path the Diesel manager is in error, so the
  connection must not be reused for a transaction; for repository pooled connections this is
  satisfied by `has_broken` discarding it (premise 6). The helper's doc comment states this
  requirement for callers. The explicit-rollback path leaves a valid, reusable connection.
* **Nesting.** The helper is for a top-level transaction only. It is not used inside an existing
  transaction or inside another `with_sqlite_cancellation` scope (the existing nested-scope
  refusal stays).

The doc comment of `with_sqlite_cancellation` is updated so it no longer forbids all schema work
in a scope: it points schema DDL at the new helper and keeps "connection acquisition and
migration/validation before the scope".

Verification (unit, `sqlite_cancellation.rs` tests, real SQLite): (a) a cancellation that
interrupts a DDL statement in the body returns `Error::Cancellation`, leaves the schema exactly as
before the transaction, and a fresh repository pooled connection to the same file then completes
a transaction; (b) a cancellation observed by the pre-commit check returns `Error::Cancellation`,
rolls back, and the **same** connection then completes a transaction; (c) an uncancelled body
commits; (d) a non-cancellation body error is returned unchanged and not reclassified; (e) after a
cancellation, a rollback failure other than "no transaction is active" is returned as that
failure and not as `Error::Cancellation` (the executor may prove this through the classification
step with constructed Diesel errors, since a real `ROLLBACK` failure such as `SQLITE_NOMEM` cannot
be induced reliably). Each test must go red if its guarded behaviour is removed (scope around
`COMMIT`/`ROLLBACK`, missing pre-commit check, missing or over-broad outcome mapping).

Platform level (threat model: all three desktop platforms count): the O1 tests, and any test
helper they need such as `cancel_on_callback`, compile and run under plain `cfg(test)`, not
`cfg(all(test, unix))`, so the `rust-windows-test` and `rust-macos-test` CI jobs execute them.

### O2 — Index commands use cancellation end to end

Rests on "Cancellation is checked only when the worker is admitted; the SQLite DDL and the
index-lock wait are not cancellable" and "can still mutate the database and report success".
Depends on O1.

* Both commands pass the gateway's worker token into their blocking bodies instead of `|_|`.
* Both blocking bodies wait for the index lock through `with_index_lock_cancellable` and open the
  connection with `get_db_or_create(…, Some(token), …)`. `with_index_lock` loses its last
  production caller and is removed (or made test-only if a test still needs it).
* `create_required_indexes` and `drop_required_indexes` keep one definition each (DDL, then the
  `check_index_exists` contract check). The command paths run them through the O1 helper with the
  token. The import path's call inside its outer transaction keeps its current, uncancellable
  behaviour (it must not open a nested O1 transaction or scope); the executor routes both callers
  through one body per operation rather than duplicating the SQL sequence.
* Terminal states: lock wait cancelled → `Error::Cancellation`, database untouched; DDL
  interrupted or pre-commit cancellation → `Error::Cancellation`, index set exactly as before the
  command; committed → `Ok(())`. A non-cancellation failure keeps its current error.

## Decisions and trade-offs

* **Interrupt with SQLite's own rollback, not "refuse once DDL starts".** The open question is
  answered by premise 7: an interrupted DDL statement in an explicit transaction is rolled back
  atomically by SQLite, and the required-index DDL is already one transaction (premise 3), so the
  rollback is defined. Refusing cancellation after DDL start would keep shutdown blocked behind a
  full index build on a large database (premise 5), which is the defect.
* **Scope the callback around the body only.** Rejected: wrapping the whole `conn.transaction`
  in `with_sqlite_cancellation`. Premise 7 and `d-20260926-04` show armed `COMMIT`/`ROLLBACK` are
  interruptible and can leave a pooled connection inside a transaction.
* **Accept discarding the connection after SQLite's auto-rollback.** Rejected: issuing raw
  `BEGIN`/`COMMIT` around Diesel's manager to avoid its in-error state — it bypasses the manager
  the rest of the repository relies on. Discarding one pooled connection on a cancelled index
  command costs one reconnect.
* **Import path unchanged.** Its index creation runs inside the import's outer transaction; an
  interrupt there would roll back the whole import, a separate behaviour change outside MANDATE.
* **Extends `d-20260908-14`, does not reverse it.** That decision scoped the callback to reads and
  preserved mutation behaviour; this plan adds a separately contracted write use with measured
  rollback semantics (premise 7). The read scope's behaviour is unchanged.

## Decided autonomously

* **Question:** Can required-index DDL be interrupted safely, or must cancellation be refused once
  DDL starts? **Chosen:** interrupt through the existing progress callback, scoped to the DDL body
  inside one top-level transaction, with `BEGIN`/`COMMIT`/`ROLLBACK` unarmed, a pre-commit token
  check, and outcome mapping to `Error::Cancellation` when nothing committed. **Rejected:**
  refusing cancellation after DDL start (keeps shutdown blocked); arming the whole transaction
  (interruptible `COMMIT`/`ROLLBACK`, `d-20260926-04`); raw `BEGIN`/`COMMIT` outside Diesel's
  manager. **Reason:** measured SQLite auto-rollback of an interrupted write statement in an
  explicit transaction (premise 7) plus Diesel 2.1.4's rollback-error replacement (premise 6).
  **Governs:** f-20260914-19. **Reversal path:** drop the helper and return to admission-only
  cancellation.

# Plan: cancellable required-index DDL (f-20260914-19)

## Goal

`create_indexes` and `delete_indexes` observe cancellation while waiting for the per-database
index lock and while SQLite executes the index DDL, roll the DDL back when cancellation wins, and
report `Error::Cancellation` exactly when nothing was committed. Success is reported only when the
DDL transaction committed.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260914-19`:

* **Where:** src-tauri/src/db/mod.rs:1190 (`create_indexes`, `delete_indexes`)
* **Defect:** Cancellation is checked only when the worker is admitted; the SQLite DDL and the
  index-lock wait are not cancellable. On a large database, cancelling during index creation can
  still mutate the database and report success.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` (cancellation before use,
  truthful terminal state).
* **Open question:** Can the DDL be interrupted safely (SQLite progress handler /
  `sqlite3_interrupt`) with a defined rollback, or must cancellation be refused once DDL starts and
  reported as such?

## Threat model and non-goals

Accidental input only: a large but well-formed user database, a concurrent search-index build
holding the index lock, and application shutdown cancelling accepted operations. No adversarial
SQL or crafted database is in scope; the DDL text is the fixed `indexes.sql` /
`delete_indexes.sql` contract. All three desktop platforms count; the mechanism is SQLite's
platform-independent progress callback, so no `cfg(target_os)` code is added.

   (non-read) operations: no renderer cancel reaches them (`d-20260908-13`); their token is
   cancelled by the shutdown seal-cancel-drain (`src-tauri/src/main.rs:3362` test
   `shutdown_seals_cancels_and_drains_a_real_native_owned_tail`). Shutdown therefore waits for an
   uncancellable index build to finish today.
6. Diesel 2.1.4 `AnsiTransactionManager::transaction` (registry source
   `diesel-2.1.4/src/connection/transaction_manager.rs`): on a callback error it issues `ROLLBACK`;
   if that `ROLLBACK` fails at depth 1 it calls `set_in_error()` and returns the **rollback** error,
   replacing the callback's error. `SqliteConnection::is_broken` returns true for an in-error
   manager, and `BoundConnectionManager::has_broken` (`repository.rs:256-261`) delegates to it, so
   r2d2 discards such a pooled connection instead of reusing it.
7. Measured SQLite behaviour (rule 12b) — probe run 2026-10-04 with Python `sqlite3` against SQLite
   3.45.1 (the bundled crate is 3.39.2; the phase tests re-measure on the bundled library):

   ```text
   create err: interrupted
   in_transaction after interrupt: False
   rollback err: cannot rollback - no transaction is active
   indexes: [('ia',)]                          # the DROP INDEX earlier in the txn was undone
   select err: interrupted
   in_transaction after interrupted SELECT: True
   commit under N=1 handler err: interrupted
     in_transaction: True rows(2,2): (2,)
   rollback under N=1 handler err: interrupted
     in_transaction: True rows(2,2): (2,)
   ```

   So: an interrupted **write/DDL** statement inside an explicit transaction makes SQLite roll the
   whole transaction back by itself; an interrupted **read** leaves the transaction open; and with
   the handler armed, `COMMIT` and `ROLLBACK` themselves are interrupted and leave the transaction
   open — the same hazard `d-20260926-04` recorded for `ROLLBACK`.

## Approach

### O1 — Cancellable DDL transaction primitive

Rests on "Can the DDL be interrupted safely … with a defined rollback" and "truthful terminal
state".

One helper beside `with_sqlite_cancellation` in `src-tauri/src/db/sqlite_cancellation.rs` runs a
caller body inside one Diesel transaction on a given connection, with this contract:

* **Scope boundary.** The progress-callback scope covers only the body's statements. `BEGIN`,
  `COMMIT` and `ROLLBACK` always execute with no scope active (premise 7: armed `COMMIT`/`ROLLBACK`
  are themselves interruptible and would strand an open transaction).
* **Pre-commit check.** After the body succeeds and before the transaction commits, the token is
  checked once more; a cancellation observed there fails the transaction, so Diesel's ordinary
  `ROLLBACK` (unarmed, transaction still open) undoes it.
* **Outcome mapping.** When the body's scope reported `Error::Cancellation`, or the pre-commit
  check failed, the helper returns `Error::Cancellation` in exactly two cases: Diesel's `ROLLBACK`
  succeeded, or it failed with SQLite's "cannot rollback - no transaction is active" (the verified
  auto-rollback case of premise 7, which premise 6 would otherwise surface as a Diesel error). Any
  other rollback failure after a cancellation is returned as that failure, not as cancellation, so
  its diagnostic is logged and shown (`run_native_operation` logs `Cancellation` only at debug and
  `notifyUnlessCancelled` hides it). Every other body error and every commit error is returned
  unchanged. Success is returned only after `COMMIT` succeeded; a cancellation arriving after the
  commit does not turn a committed result into an error (`d-20260908-13`: commit tails report
  their actual outcome).
* **Connection state.** After the SQLite-auto-rollback path the Diesel manager is in error, so the
  connection must not be reused for a transaction; for repository pooled connections this is
  satisfied by `has_broken` discarding it (premise 6). The helper's doc comment states this
  requirement for callers. The explicit-rollback path leaves a valid, reusable connection.
* **Nesting.** The helper is for a top-level transaction only. It is not used inside an existing
  transaction or inside another `with_sqlite_cancellation` scope (the existing nested-scope
  refusal stays).

The doc comment of `with_sqlite_cancellation` is updated so it no longer forbids all schema work
in a scope: it points schema DDL at the new helper and keeps "connection acquisition and
migration/validation before the scope".

Verification (unit, `sqlite_cancellation.rs` tests, real SQLite): (a) a cancellation that
interrupts a DDL statement in the body returns `Error::Cancellation`, leaves the schema exactly as
before the transaction, and a fresh repository pooled connection to the same file then completes
a transaction; (b) a cancellation observed by the pre-commit check returns `Error::Cancellation`,
rolls back, and the **same** connection then completes a transaction; (c) an uncancelled body
commits; (d) a non-cancellation body error is returned unchanged and not reclassified; (e) after a
cancellation, a rollback failure other than "no transaction is active" is returned as that
failure and not as `Error::Cancellation` (the executor may prove this through the classification
step with constructed Diesel errors, since a real `ROLLBACK` failure such as `SQLITE_NOMEM` cannot
be induced reliably). Each test must go red if its guarded behaviour is removed (scope around
`COMMIT`/`ROLLBACK`, missing pre-commit check, missing or over-broad outcome mapping).

Platform level (threat model: all three desktop platforms count): the O1 tests, and any test
helper they need such as `cancel_on_callback`, compile and run under plain `cfg(test)`, not
`cfg(all(test, unix))`, so the `rust-windows-test` and `rust-macos-test` CI jobs execute them.

### O2 — Index commands use cancellation end to end

Rests on "Cancellation is checked only when the worker is admitted; the SQLite DDL and the
index-lock wait are not cancellable" and "can still mutate the database and report success".
Depends on O1.

* Both commands pass the gateway's worker token into their blocking bodies instead of `|_|`.
* Both blocking bodies wait for the index lock through `with_index_lock_cancellable` and open the
  connection with `get_db_or_create(…, Some(token), …)`. `with_index_lock` loses its last
  production caller and is removed (or made test-only if a test still needs it).
* `create_required_indexes` and `drop_required_indexes` keep one definition each (DDL, then the
  `check_index_exists` contract check). The command paths run them through the O1 helper with the
  token. The import path's call inside its outer transaction keeps its current, uncancellable
  behaviour (it must not open a nested O1 transaction or scope); the executor routes both callers
  through one body per operation rather than duplicating the SQL sequence.
* Terminal states: lock wait cancelled → `Error::Cancellation`, database untouched; DDL
  interrupted or pre-commit cancellation → `Error::Cancellation`, index set exactly as before the
  command; committed → `Ok(())`. A non-cancellation failure keeps its current error.

Verification (`src-tauri/src/db/mod.rs` tests, real repository, the existing
`blocking_database_case` fixtures): (a) `create_indexes_blocking` cancelled while SQLite executes
its DDL returns `Error::Cancellation` and `check_index_exists` plus the full index list equal the
pre-command state — run from a state where the required set is absent and from one where a
same-name wrong-definition index exists (the repair case of
`required_indexes_have_an_exact_status_and_can_be_repaired_atomically`); (b) the same for
`delete_indexes_blocking` starting from a complete set, which must remain complete; (c) each
command, run again uncancelled on the same database afterwards, succeeds (pool recovery);
(d) each command blocked on an index lock held by another thread returns `Error::Cancellation`
after its token is cancelled, without mutating the index set — the wait is proven entered through
the existing `cancellable_lock::observe_lock_wait` observer on the entry's index lock (a
`cfg(test)` accessor in `repository.rs` is allowed), not a sleep. The DDL-interruption tests must prove
the cancellation was taken inside the DDL transaction rather than by an earlier pre-DDL check:
they must go red if the O1 helper is replaced by the plain transaction (cancellation then lands
after the pre-DDL checks and the DDL commits). (e) Token wiring through the public commands: each
of `create_indexes` and `delete_indexes`, invoked as the async command with the test app's
`AppState`, blocks on an index lock held by the test, the wait is proven entered through the
`cancellable_lock` wait observer, then the app's `OperationRegistry` cancels it through
`seal_and_request_cancellation` (the shutdown path of premise 5); the command returns
`Error::Cancellation` and the index set is unchanged. This test must go red if a command passes
any token other than the gateway worker token into its blocking body.

Platform level: the O2 tests live in a plain `cfg(test)` module (the fixtures
`blocking_database_case`, `schema_database_case` and `database_app_with_grant` are already
`cfg(test)`, and `mod deletion_tests` is the existing cross-platform precedent), not in the
`cfg(all(test, unix))` `mod tests`, so the Windows and macOS CI jobs execute them.
Every test-only helper the O1 and O2 tests use that is currently gated `cfg(all(test, unix))` is
re-gated to plain `cfg(test)` in this phase — at least `cancellable_lock::observe_lock_wait`
(`src-tauri/src/infra/cancellable_lock.rs`) and `sqlite_cancellation::cancel_on_callback` — and
any new test-only accessor (such as the index-lock accessor in `repository.rs`) is plain
`cfg(test)`. Phase 1's Windows clippy proof (`pnpm checks:pre-review`, which runs
`pnpm rust:windows:check`) must compile the new tests for the Windows target.

## Decisions and trade-offs

* **Interrupt with SQLite's own rollback, not "refuse once DDL starts".** The open question is
  answered by premise 7: an interrupted DDL statement in an explicit transaction is rolled back
  atomically by SQLite, and the required-index DDL is already one transaction (premise 3), so the
  rollback is defined. Refusing cancellation after DDL start would keep shutdown blocked behind a
  full index build on a large database (premise 5), which is the defect.
* **Scope the callback around the body only.** Rejected: wrapping the whole `conn.transaction`
  in `with_sqlite_cancellation`. Premise 7 and `d-20260926-04` show armed `COMMIT`/`ROLLBACK` are
  interruptible and can leave a pooled connection inside a transaction.
* **Accept discarding the connection after SQLite's auto-rollback.** Rejected: issuing raw
  `BEGIN`/`COMMIT` around Diesel's manager to avoid its in-error state — it bypasses the manager
  the rest of the repository relies on. Discarding one pooled connection on a cancelled index
  command costs one reconnect.
* **Import path unchanged.** Its index creation runs inside the import's outer transaction; an
  interrupt there would roll back the whole import, a separate behaviour change outside MANDATE.
* **Extends `d-20260908-14`, does not reverse it.** That decision scoped the callback to reads and
  preserved mutation behaviour; this plan adds a separately contracted write use with measured
  rollback semantics (premise 7). The read scope's behaviour is unchanged.

## Decided autonomously

* **Question:** Can required-index DDL be interrupted safely, or must cancellation be refused once
  DDL starts? **Chosen:** interrupt through the existing progress callback, scoped to the DDL body
  inside one top-level transaction, with `BEGIN`/`COMMIT`/`ROLLBACK` unarmed, a pre-commit token
  check, and outcome mapping to `Error::Cancellation` when nothing committed. **Rejected:**
  refusing cancellation after DDL start (keeps shutdown blocked); arming the whole transaction
  (interruptible `COMMIT`/`ROLLBACK`, `d-20260926-04`); raw `BEGIN`/`COMMIT` outside Diesel's
  manager. **Reason:** measured SQLite auto-rollback of an interrupted write statement in an
  explicit transaction (premise 7) plus Diesel 2.1.4's rollback-error replacement (premise 6).
  **Governs:** f-20260914-19. **Reversal path:** drop the helper and return to admission-only
  cancellation.

## Risks / open questions

* SQLite 3.39.2 (bundled) versus 3.45.1 (probe): the auto-rollback of an interrupted write
  statement is long-documented behaviour of `sqlite3_interrupt`, and the O1/O2 tests run on the
  bundled library, so a difference turns a test red rather than shipping silently.
* Windows and macOS runtime evidence cannot be produced on this Linux host: `pnpm
  checks:pre-review` gives Windows compile/clippy evidence only, and the runtime authority is the
  `rust-windows-test` and `rust-macos-test` CI jobs after push. Unavailable local evidence is not
  approval; a red CI job is a red gate for this change.
* With `SQLITE_PROGRESS_VM_STEPS = 1000` in production, a very short DDL may finish before a
  callback fires; it then commits and reports success, which is truthful.

* Whether index commands should also take the database write lock.
* Renderer changes: accepted operations stay renderer-uncancellable (`d-20260908-13`); the

## Correction after implementation (2026-10-04, adopting session 42548d18)

The plan's risk bullet quoted above in every plan snapshot ("a very short DDL may finish before a
callback fires; it then commits and reports success") is imprecise and is superseded here; the
snapshots stay verbatim as the record of what was reviewed. A short DDL that finishes before any
progress callback does not commit unconditionally: `with_sqlite_cancellation_transaction`
(`src-tauri/src/db/sqlite_cancellation.rs`, commit `1aefb546`) checks the token once more after the
body and before `COMMIT`, so a cancellation that arrived during such a DDL still rolls it back and
returns `Cancellation`. Only a cancellation arriving after that pre-commit check lets the
transaction commit and report success, which is the truthful outcome. Reported by the records lens
on the push range `aaa04caf..1aefb546` (confidence 98).
