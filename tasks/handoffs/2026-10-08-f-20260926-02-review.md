## Mandate (fixed)

Close `f-20260926-02`: `collectSequential` keeps successful siblings and only logs a failed item by
index, so the home personal summary renders reduced statistics (or "No games found" when everything
failed) with no sign that a database's `getPlayersGameInfo` failed, and the log does not name the
database. Open question: per-database notice, anonymous "incomplete" marker, or failing the whole
summary; and which of the three `collectSequential` callers share that contract.

## Planned answer

- **O1:** `collectSequential` resolves to `{ values, failures }` (item, original index, redacted
  failure); optional `describe` names the item in the log (`… item N (label) failed: …`, the
  `getDatabase` shape); cancellation unchanged. `getDatabases` and `convertToNormalized` take
  `values` (D2).
- **O2:** personal databases are identified by the account filename (`<username>_lichess.db3` /
  `<username>_chesscom.db3`) through one helper in a new `src/utils/accountDatabase.ts` used by
  `AccountCard.tsx`, `AccountCards.tsx` and `Databases.tsx` (D5); metadata error records and
  rejected statistics reads are failed databases; a yellow notice inside `PersonalPlayerCard`
  (new optional `notice` prop, D4) names them over the remaining statistics; when everything
  failed the empty state says "Could not load statistics" instead of "No games found" (D1);
  player-not-found is an empty contribution, not a failure (D3). New keys in all 16 catalogues.
- **O3:** collector unit tests; mounted `Databases.test.tsx` cases (partial, all-failed,
  player-not-found, metadata error beside a healthy database, only metadata errors, non-account
  database excluded); two pixel tests in the registered `e2e/accounts-puzzles-engines.spec.ts`
  using a per-call outcome sequence added to `e2e/fixtures.ts` `MockCommand`, snapshots recorded
  only in the pinned container.
- **Phases:** 1 = O1+O2+unit/component tests (role sensitive); 2 = e2e pixels.
- Filed out of area during Locate: the Lichess explorer game list's silent drop of failed games
  (inbox `20261007-235057-25289-1791409857389174253-6.md`).

# Plan: Home personal summary marks per-database statistics failures

## Goal

The home personal summary must never present statistics from a subset of the player's databases as
if they were complete. When a database's statistics cannot be read, the user sees which database is
missing from the totals, and the native log names that database. The shared sequential collector
stops discarding its failures, so every caller receives them and decides what to show.

## MANDATE

Verbatim from `f-20260926-02` (`tasks/findings.md`):

* **Where:** `src/components/home/Databases.tsx:121` (the personal summary is built through `collectSequential`), `src/utils/collectSequential.ts:9-35`.
* **Defect:** `collectSequential` deliberately keeps the successful siblings and only logs a failed item, by its index and a generic message. The home personal summary therefore renders the statistics of the databases that succeeded, or the empty state when all failed, with no sign that one database's `getPlayersGameInfo` call failed. Since f-20260907-05, a `load_iter` row error fails that command closed. The user still sees the reduced totals as if they were complete, and the log does not name the database.
* **Open question:** how should the personal summary mark partial statistics? Options: a per-database error notice, an inline "incomplete" marker on the totals, or failing the whole summary. Which of the three `collectSequential` callers (`Databases.tsx`, `src/utils/db.ts:229`, `src/utils/lichess/api.tsx:195`) should share that contract?
* **Why deferred:** it is a UI/UX design question outside the fixed f-20260907-05 mandate (bounded statistics memory). The retain-siblings contract predates that change, which only makes a DB read failure reach it as an error instead of a skipped row.
* **Proof sought:** a component test with two databases, one rejecting, that asserts the visible partial-data indication, and the logged context names the failed database.

## Threat model and non-goals

Accidental failures only: a database file that is locked, unreadable, corrupt (a `load_iter` row
error now fails `get_players_game_info` closed, `d-20260926-03`), or removed between listing and the
statistics read; a player lookup that throws. No adversarial input is in scope — database titles and
filenames come from the user's own workspace. Environments: the desktop app on Linux, macOS and
Windows (renderer-only change; no platform-specific code). Cancellation (`AbortError` from the owner
signal on unmount/key change) is not a failure and keeps its current behaviour.

## Approach

### O1 — The collector returns its failures (shared contract)

Rests on: "`collectSequential` deliberately keeps the successful siblings and only logs a failed
item, by its index and a generic message" and "Which of the three `collectSequential` callers …
should share that contract?"

* `collectSequential` resolves to `{ values: R[]; failures: SequentialFailure<T>[] }`, where a
  failure carries the original `item`, its input `index`, and its `SafeFailureContext`. `values`
  keeps input order exactly as today. Cancellation semantics are unchanged: an aborted signal or a
  `cancelled` category still rejects the whole collection and logs nothing.
* New optional option `describe?: (item: T) => string`. When given, the log message names the item —
  `${operation} item ${index} (${label}) failed: ${message}`, the same shape `getDatabase` already
  logs at `src/utils/db.ts:251` — and the log context carries `item: label`. Without `describe` the
  message stays byte-identical to today. `FailureLogContext` gains the optional `item?: string`.
* All three callers share the contract (the type forces each to take `values` explicitly):
  * `Databases.tsx` consumes `failures` (O2).
  * `getDatabases` (`db.ts`) takes `values`. Its mapper already converts every ordinary failure into
    a visible per-database error record (Traced premises), so its `failures` are empty in every
    ordinary case; behaviour is unchanged and pinned by the existing `db.test.ts` cases.
  * `convertToNormalized` (`lichess/api.tsx`) takes `values`, behaviour unchanged. Its user-visible
    indication is a separate panel surface, filed (Not part of this task).

### O2 — The home summary shows which databases are missing

Rests on: "the home personal summary therefore renders the statistics of the databases that
succeeded, or the empty state when all failed, with no sign that one database's
`getPlayersGameInfo` call failed" and "The user still sees the reduced totals as if they were
complete". Depends on O1.

* The SWR fetcher resolves to `{ entries: PersonalInfo[]; failed: DatabaseInfo[] }` (`failed` =
  the `item`s of O1's failures, in input order) and passes `describe: (db) => db.title || db.filename`
  so the log names the database.
* A player lookup that finds no row is **not** a failure: that database contributes no statistics,
  no notice and no error log (decision D3). Every other rejection of the mapper is a failure.
* **Partial state** (`entries` non-empty, `failed` non-empty): `PersonalPlayerCard` renders the
  merged statistics of `entries` and, between its header and its tabs, one yellow warning notice
  titled `Home.Databases.Incomplete.Title` ("Statistics are incomplete") whose body
  `Home.Databases.Incomplete.Description` names every failed database
  ("These databases could not be read: {{databases}}", names joined with ", "). The notice reaches
  the card through a new optional `notice?: ReactNode` prop of `PersonalPlayerCard`, rendered inside
  the card's `Paper` so it stays visible under the `overflow: hidden` layout; `PlayerCard.tsx`
  passes nothing and is unchanged.
* **All-failed state** (`entries` empty, `failed` non-empty): the empty-state paper keeps its layout
  and player `Select`, but shows `Home.Databases.Failed.Title` ("Could not load statistics") and the
  same notice body instead of "No games found" and `Home.Databases.Empty.Description`. The UI never
  claims there are no games when databases failed.
* **No failures**: rendering is unchanged (empty state or card without a notice).
* One file-local notice component renders the description for both states (rule 11).
* A whole-collection rejection still renders `Home.Databases.ErrorLoading` as today.
* New keys are added through `pnpm i18n:extract` with a translated, non-empty value in all 16
  catalogues; `{{databases}}` is the only interpolation token and appears in every translation.

### O3 — Verification

Rests on: "**Proof sought:** a component test with two databases, one rejecting, that asserts the
visible partial-data indication, and the logged context names the failed database." Depends on O1, O2.

* `collectSequential.test.ts`: failures carry original `index`, `item` and redacted failure context;
  `values` order unchanged; with `describe` the native log message contains the label and the
  context's `item` equals it; without `describe` the message is unchanged; cancellation still
  rejects with no failure recorded and no log.
* `Databases.test.tsx` (mounted component, existing harness, `Alert` added to the Mantine mock):
  * two databases, the second's `getPlayersGameInfo` rejects → the rendered output contains the
    incomplete title and the failed database's title; `PersonalCard` receives only the first
    database's records and a notice; the native log message names the failed database. This test
    goes red if O1's `failures` or O2's notice is reverted.
  * every database rejects → `Home.Databases.Failed.Title` and the failed names render;
    `Home.Databases.Empty.Title` does not.
  * player not found in the only database → empty state as before, no notice, no error log.
  * the existing test at `:355` is updated to assert the rendered indication for its rejected
    `query_players` item.
* Renderer pixels: a Playwright spec under `e2e/` records the partial and the all-failed states of
  the home page from the mocked IPC surface (two databases, one failing). This needs a per-call
  scripted outcome in the e2e mock (`MockCommand` gains a sequence of `{ result }` / `{ error }`
  outcomes consumed in call order); the existing `results` sequence cannot express "first call
  succeeds, second rejects". Snapshots are recorded only inside the pinned container
  (`d-20260829-01`, `d-20260919-13`); no existing snapshot may move.

## Decisions and trade-offs

* **Presentation (a) per-database notice** over (b) an anonymous "incomplete" marker and (c) failing
  the whole summary — see D1.
* **Return failures from the primitive** rather than an `onFailure` callback or a second collector —
  see D2.
* **Player-not-found is an empty contribution, not a failure** — see D3.
* **Notice inside the card** rather than above it — see D4.
* **e2e harness growth (rule 6d):** the one new piece of test tooling is the per-call outcome
  sequence in `e2e/fixtures.ts`'s `MockCommand`. Cheap alternative considered: prove only the
  all-failed state in e2e (a plain `error` needs no harness change) and leave the partial state to
  the mounted test. Rejected because the partial state is the one with layout risk (a notice inside
  an `overflow: hidden` card above flex tabs) and the mounted test stubs both Mantine and the card.
  Removal path: delete the field; no existing scenario uses it.

## Decided autonomously

Each entry is recorded by the adopting session through `./scripts/findings.py record-decision`.

### D1 — How does the home personal summary mark statistics from a subset of databases?

* **Question:** f-20260926-02 asks whether partial statistics get a per-database notice, an inline "incomplete" marker on the totals, or fail the whole summary.
* **Governs:** f-20260926-02

# Plan: Home personal summary marks per-database statistics failures

## Goal

The home personal summary must never present statistics from a subset of the player's databases as
if they were complete. When a database's statistics cannot be read, the user sees which database is
missing from the totals, and the native log names that database. The shared sequential collector
stops discarding its failures, so every caller receives them and decides what to show.

## MANDATE

Verbatim from `f-20260926-02` (`tasks/findings.md`):

* **Where:** `src/components/home/Databases.tsx:121` (the personal summary is built through `collectSequential`), `src/utils/collectSequential.ts:9-35`.
* **Defect:** `collectSequential` deliberately keeps the successful siblings and only logs a failed item, by its index and a generic message. The home personal summary therefore renders the statistics of the databases that succeeded, or the empty state when all failed, with no sign that one database's `getPlayersGameInfo` call failed. Since f-20260907-05, a `load_iter` row error fails that command closed. The user still sees the reduced totals as if they were complete, and the log does not name the database.
* **Open question:** how should the personal summary mark partial statistics? Options: a per-database error notice, an inline "incomplete" marker on the totals, or failing the whole summary. Which of the three `collectSequential` callers (`Databases.tsx`, `src/utils/db.ts:229`, `src/utils/lichess/api.tsx:195`) should share that contract?
* **Why deferred:** it is a UI/UX design question outside the fixed f-20260907-05 mandate (bounded statistics memory). The retain-siblings contract predates that change, which only makes a DB read failure reach it as an error instead of a skipped row.
* **Proof sought:** a component test with two databases, one rejecting, that asserts the visible partial-data indication, and the logged context names the failed database.

## Threat model and non-goals

Accidental failures only: a database file that is locked, unreadable, corrupt (a `load_iter` row
error now fails `get_players_game_info` closed, `d-20260926-03`), or removed between listing and the
statistics read; a player lookup that throws. No adversarial input is in scope — database titles and
filenames come from the user's own workspace. Environments: the desktop app on Linux, macOS and
Windows (renderer-only change; no platform-specific code). Cancellation (`AbortError` from the owner
signal on unmount/key change) is not a failure and keeps its current behaviour.

## Approach

### O1 — The collector returns its failures (shared contract)

Rests on: "`collectSequential` deliberately keeps the successful siblings and only logs a failed
item, by its index and a generic message" and "Which of the three `collectSequential` callers …
should share that contract?"

* `collectSequential` resolves to `{ values: R[]; failures: SequentialFailure<T>[] }`, where a
  failure carries the original `item`, its input `index`, and its `SafeFailureContext`. `values`
  keeps input order exactly as today. Cancellation semantics are unchanged: an aborted signal or a
  `cancelled` category still rejects the whole collection and logs nothing.
* New optional option `describe?: (item: T) => string`. When given, the log message names the item —
  `${operation} item ${index} (${label}) failed: ${message}`, the same shape `getDatabase` already
  logs at `src/utils/db.ts:251` — and the log context carries `item: label`. Without `describe` the
  message stays byte-identical to today. `FailureLogContext` gains the optional `item?: string`.
* All three callers share the contract (the type forces each to take `values` explicitly):
  * `Databases.tsx` consumes `failures` (O2).
  * `getDatabases` (`db.ts`) takes `values`. Its mapper already converts every ordinary failure into
    a visible per-database error record (Traced premises), so its `failures` are empty in every
    ordinary case; behaviour is unchanged and pinned by the existing `db.test.ts` cases.
  * `convertToNormalized` (`lichess/api.tsx`) takes `values`, behaviour unchanged. Its user-visible
    indication is a separate panel surface, filed (Not part of this task).

### O2 — The home summary shows which databases are missing

Rests on: "the home personal summary therefore renders the statistics of the databases that
succeeded, or the empty state when all failed, with no sign that one database's
`getPlayersGameInfo` call failed" and "The user still sees the reduced totals as if they were
complete". Depends on O1.

* **Which databases belong to the summary.** A personal database is identified by its account
  filename, the identity the account cards already create and look up (Traced premises), not by
  display title or a filename substring. One helper derives that filename from a username and an
  account type, and `AccountCard.tsx`, `AccountCards.tsx` and `Databases.tsx` all use it (rule 11;
  decision D5). The `personalDatabases` fetcher keeps **every** metadata record — success or error —
  whose filename is a session's account filename, and keeps the owning username beside the record
  instead of mutating the record.
* **What counts as a failed database.** For the selected player: a metadata **error** record is a
  failed database without any statistics call; a success record whose statistics mapper rejects
  (O1 failure) is a failed database. Each failed database is named by its title when it has one,
  otherwise by its filename.
* The SWR fetcher resolves to `{ entries: PersonalInfo[]; failed: <failed databases> }` (input
  order) and passes `describe` so the log names the database; metadata failures are already logged
  by `getDatabase` with their filename and are not logged a second time.
* A player lookup that finds no row is **not** a failure: that database contributes no statistics,
  no notice and no error log (decision D3). Every other rejection of the mapper is a failure.
* **Partial state** (`entries` non-empty, `failed` non-empty): `PersonalPlayerCard` renders the
  merged statistics of `entries` and, between its header and its tabs, one yellow warning notice
  titled `Home.Databases.Incomplete.Title` ("Statistics are incomplete") whose body
  `Home.Databases.Incomplete.Description` names every failed database
  ("These databases could not be read: {{databases}}", names joined with ", "). The notice reaches
  the card through a new optional `notice?: ReactNode` prop of `PersonalPlayerCard`, rendered inside
  the card's `Paper` so it stays visible under the `overflow: hidden` layout; `PlayerCard.tsx`
  passes nothing and is unchanged.
* **All-failed state** (`entries` empty, `failed` non-empty): the empty-state paper keeps its layout
  and player `Select`, but shows `Home.Databases.Failed.Title` ("Could not load statistics") and the
  same notice body instead of "No games found" and `Home.Databases.Empty.Description`. The UI never
  claims there are no games when databases failed.
* **No failures**: rendering is unchanged (empty state or card without a notice).
* One file-local notice component renders the description for both states (rule 11).
* A whole-collection rejection still renders `Home.Databases.ErrorLoading` as today.
* New keys are added through `pnpm i18n:extract` with a translated, non-empty value in all 16
  catalogues; `{{databases}}` is the only interpolation token and appears in every translation.

## Decisions and trade-offs

* **Presentation (a) per-database notice** over (b) an anonymous "incomplete" marker and (c) failing
  the whole summary — see D1.
* **Return failures from the primitive** rather than an `onFailure` callback or a second collector —
  see D2.
* **Player-not-found is an empty contribution, not a failure** — see D3.
* **Notice inside the card** rather than above it — see D4.
* **Personal databases identified by account filename** so a metadata failure is attributable —
  see D5.
* **e2e harness growth (rule 6d):** the one new piece of test tooling is the per-call outcome
  sequence in `e2e/fixtures.ts`'s `MockCommand`. Cheap alternative considered: prove only the
  all-failed state in e2e (a plain `error` needs no harness change) and leave the partial state to
  the mounted test. Rejected because the partial state is the one with layout risk (a notice inside
  an `overflow: hidden` card above flex tabs) and the mounted test stubs both Mantine and the card.
  Removal path: delete the field; no existing scenario uses it.

# Plan: Home personal summary marks per-database statistics failures

## Goal

The home personal summary must never present statistics from a subset of the player's databases as
if they were complete. When a database's statistics cannot be read, the user sees which database is
missing from the totals, and the native log names that database. The shared sequential collector
stops discarding its failures, so every caller receives them and decides what to show.

## MANDATE

Verbatim from `f-20260926-02` (`tasks/findings.md`):

* **Where:** `src/components/home/Databases.tsx:121` (the personal summary is built through `collectSequential`), `src/utils/collectSequential.ts:9-35`.
* **Defect:** `collectSequential` deliberately keeps the successful siblings and only logs a failed item, by its index and a generic message. ## Approach

### O1 — The collector returns its failures (shared contract)

Rests on: "`collectSequential` deliberately keeps the successful siblings and only logs a failed
item, by its index and a generic message" and "Which of the three `collectSequential` callers …
should share that contract?"

* `collectSequential` resolves to `{ values: R[]; failures: SequentialFailure<T>[] }`, where a
  failure carries the original `item`, its input `index`, and its `SafeFailureContext`. `values`
  keeps input order exactly as today. Cancellation semantics are unchanged: an aborted signal or a
  `cancelled` category still rejects the whole collection and logs nothing.
* New optional option `describe?: (item: T) => string`. When given, the log message names the item —
  `${operation} item ${index} (${label}) failed: ${message}`, the same shape `getDatabase` already
  logs at `src/utils/db.ts:251` — and the log context carries `item: label`. Without `describe` the
  message stays byte-identical to today. `FailureLogContext` gains the optional `item?: string`.
* All three callers share the contract (the type forces each to take `values` explicitly):
  * `Databases.tsx` consumes `failures` (O2).
  * `getDatabases` (`db.ts`) takes `values`. Its mapper already converts every ordinary failure into
    a visible per-database error record (Traced premises), so its `failures` are empty in every
    ordinary case; behaviour is unchanged and pinned by the existing `db.test.ts` cases.
  * `convertToNormalized` (`lichess/api.tsx`) takes `values`, behaviour unchanged. Its user-visible
    indication is a separate panel surface, filed (Not part of this task).

### O2 — The home summary shows which databases are missing

Rests on: "the home personal summary therefore renders the statistics of the databases that
succeeded, or the empty state when all failed, with no sign that one database's
`getPlayersGameInfo` call failed" and "The user still sees the reduced totals as if they were
complete". Depends on O1.

* **Which databases belong to the summary.** A personal database is identified by its account
  filename, the identity the account cards already create and look up (Traced premises), not by
  display title or a filename substring. One helper derives that filename from a username and an
  account type, and `AccountCard.tsx`, `AccountCards.tsx` and `Databases.tsx` all use it (rule 11;
  decision D5). The helper lives in its own module, `src/utils/accountDatabase.ts`, not in
  `src/utils/db.ts`: `AccountCard.test.tsx:24` and `Accounts.test.tsx:24` replace `@/utils/db`
  wholesale with a factory that exports only `getDatabases`, so a helper
  exported from `db.ts` would be `undefined` under those tests. The `personalDatabases` fetcher keeps **every** metadata record — success or error —
  whose filename is a session's account filename, and keeps the owning username beside the record
  instead of mutating the record.
* **What counts as a failed database.** For the selected player: a metadata **error** record is a
  failed database without any statistics call; a success record whose statistics mapper rejects
  (O1 failure) is a failed database. Each failed database is named by its title when it has one,
  otherwise by its filename.
* The SWR fetcher resolves to `{ entries: PersonalInfo[]; failed: <failed databases> }` (input
  order) and passes `describe` so the log names the database; metadata failures are already logged
  by `getDatabase` with their filename and are not logged a second time.
* A player lookup that finds no row is **not** a failure: that database contributes no statistics,
  no notice and no error log (decision D3). Every other rejection of the mapper is a failure.
* **Partial state** (`entries` non-empty, `failed` non-empty): `PersonalPlayerCard` renders the
  merged statistics of `entries` and, between its header and its tabs, one yellow warning notice
  titled `Home.Databases.Incomplete.Title` ("Statistics are incomplete") whose body
  `Home.Databases.Incomplete.Description` names every failed database
  ("These databases could not be read: {{databases}}", names joined with ", "). The notice reaches
  the card through a new optional `notice?: ReactNode` prop of `PersonalPlayerCard`, rendered inside
  the card's `Paper` so it stays visible under the `overflow: hidden` layout; `PlayerCard.tsx`
  passes nothing and is unchanged.
* **All-failed state** (`entries` empty, `failed` non-empty): the empty-state paper keeps its layout
  and player `Select`, but shows `Home.Databases.Failed.Title` ("Could not load statistics") and the
  same notice body instead of "No games found" and `Home.Databases.Empty.Description`. The UI never
  claims there are no games when databases failed.
* **No failures**: rendering is unchanged (empty state or card without a notice).
* One file-local notice component renders the description for both states (rule 11).
* A whole-collection rejection still renders `Home.Databases.ErrorLoading` as today.
* New keys are added through `pnpm i18n:extract` with a translated, non-empty value in all 16
  catalogues; `{{databases}}` is the only interpolation token and appears in every translation.

# Plan: Home personal summary marks per-database statistics failures

## Goal

The home personal summary must never present statistics from a subset of the player's databases as
if they were complete. When a database's statistics cannot be read, the user sees which database is
missing from the totals, and the native log names that database. The shared sequential collector
stops discarding its failures, so every caller receives them and decides what to show.

## MANDATE

Verbatim from `f-20260926-02` (`tasks/findings.md`):

* **Where:** `src/components/home/Databases.tsx:121` (the personal summary is built through `collectSequential`), `src/utils/collectSequential.ts:9-35`.
* **Defect:** `collectSequential` deliberately keeps the successful siblings and only logs a failed item, by its index and a generic message. The home personal summary therefore renders the statistics of the databases that succeeded, or the empty state when all failed, with no sign that one database's `getPlayersGameInfo` call failed. Since f-20260907-05, a `load_iter` row error fails that command closed. The user still sees the reduced totals as if they were complete, and the log does not name the database.
* **Open question:** how should the personal summary mark partial statistics? Options: a per-database error notice, an inline "incomplete" marker on the totals, or failing the whole summary. Which of the three `collectSequential` callers (`Databases.tsx`, `src/utils/db.ts:229`, `src/utils/lichess/api.tsx:195`) should share that contract?
* **Why deferred:** it is a UI/UX design question outside the fixed f-20260907-05 mandate (bounded statistics memory). The retain-siblings contract predates that change, which only makes a DB read failure reach it as an error instead of a skipped row.
* **Proof sought:** a component test with two databases, one rejecting, that asserts the visible partial-data indication, and the logged context names the failed database.

## Threat model and non-goals

Accidental failures only: a database file that is locked, unreadable, corrupt (a `load_iter` row
error now fails `get_players_game_info` closed, `d-20260926-03`), or removed between listing and the
statistics read; a player lookup that throws. No adversarial input is in scope — database titles and
filenames come from the user's own workspace. Environments: the desktop app on Linux, macOS and
Windows (renderer-only change; no platform-specific code). Cancellation (`AbortError` from the owner
signal on unmount/key change) is not a failure and keeps its current behaviour.

## Approach

### O1 — The collector returns its failures (shared contract)

Rests on: "`collectSequential` deliberately keeps the successful siblings and only logs a failed
item, by its index and a generic message" and "Which of the three `collectSequential` callers …
should share that contract?"

* `collectSequential` resolves to `{ values: R[]; failures: SequentialFailure<T>[] }`, where a
  failure carries the original `item`, its input `index`, and its `SafeFailureContext`. `values`
  keeps input order exactly as today. Cancellation semantics are unchanged: an aborted signal or a
  `cancelled` category still rejects the whole collection and logs nothing.
* New optional option `describe?: (item: T) => string`. When given, the log message names the item —
  `${operation} item ${index} (${label}) failed: ${message}`, the same shape `getDatabase` already
  logs at `src/utils/db.ts:251` — and the log context carries `item: label`. Without `describe` the
  message stays byte-identical to today. `FailureLogContext` gains the optional `item?: string`.
* All three callers share the contract (the type forces each to take `values` explicitly):
  * `Databases.tsx` consumes `failures` (O2).
  * `getDatabases` (`db.ts`) takes `values`. Its mapper already converts every ordinary failure into
    a visible per-database error record (Traced premises), so its `failures` are empty in every
    ordinary case; behaviour is unchanged and pinned by the existing `db.test.ts` cases.
  * `convertToNormalized` (`lichess/api.tsx`) takes `values`, behaviour unchanged. Its user-visible
    indication is a separate panel surface, filed (Not part of this task).

### O2 — The home summary shows which databases are missing

Rests on: "the home personal summary therefore renders the statistics of the databases that
succeeded, or the empty state when all failed, with no sign that one database's
`getPlayersGameInfo` call failed" and "The user still sees the reduced totals as if they were
complete". Depends on O1.

* **Which databases belong to the summary.** A personal database is identified by its account
  filename, the identity the account cards already create and look up (Traced premises), not by
  display title or a filename substring. One helper derives that filename from a username and an
  account type, and `AccountCard.tsx`, `AccountCards.tsx` and `Databases.tsx` all use it (rule 11;
  decision D5). The helper lives in its own module, `src/utils/accountDatabase.ts`, not in
  `src/utils/db.ts`: `AccountCard.test.tsx:24` and `Accounts.test.tsx:24` replace `@/utils/db`
  wholesale with a factory that exports only `getDatabases`, so a helper
  exported from `db.ts` would be `undefined` under those tests. The `personalDatabases` fetcher keeps **every** metadata record — success or error —
  whose filename is a session's account filename, and keeps the owning username beside the record
  instead of mutating the record.
* **What counts as a failed database.** For the selected player: a metadata **error** record is a
  failed database without any statistics call; a success record whose statistics mapper rejects
  (O1 failure) is a failed database. Each failed database is named by its title when it has one,
  otherwise by its filename.
* The SWR fetcher resolves to `{ entries: PersonalInfo[]; failed: <failed databases> }` (input
  order) and passes `describe` so the log names the database; metadata failures are already logged
  by `getDatabase` with their filename and are not logged a second time.
* A player lookup that finds no row is **not** a failure: that database contributes no statistics,
  no notice and no error log (decision D3). Every other rejection of the mapper is a failure.
* **Partial state** (`entries` non-empty, `failed` non-empty): `PersonalPlayerCard` renders the
  merged statistics of `entries` and, between its header and its tabs, one yellow warning notice
  titled `Home.Databases.Incomplete.Title` ("Statistics are incomplete") whose body
  `Home.Databases.Incomplete.Description` names every failed database
  ("These databases could not be read: {{databases}}", names joined with ", "). The notice reaches
  the card through a new optional `notice?: ReactNode` prop of `PersonalPlayerCard`, rendered inside
  the card's `Paper` so it stays visible under the `overflow: hidden` layout; `PlayerCard.tsx`
  passes nothing and is unchanged.
* **All-failed state** (`entries` empty, `failed` non-empty): the empty-state paper keeps its layout
  and player `Select`, but shows `Home.Databases.Failed.Title` ("Could not load statistics") and the
  same notice body instead of "No games found" and `Home.Databases.Empty.Description`. The UI never
  claims there are no games when databases failed.
* **No failures**: rendering is unchanged (empty state or card without a notice).
* One file-local notice component renders the description for both states (rule 11).
* A whole-collection rejection still renders `Home.Databases.ErrorLoading` as today.
* New keys are added through `pnpm i18n:extract` with a translated, non-empty value in all 16
  catalogues; `{{databases}}` is the only interpolation token and appears in every translation.

## Decisions and trade-offs

* **Presentation (a) per-database notice** over (b) an anonymous "incomplete" marker and (c) failing
  the whole summary — see D1.
* **Return failures from the primitive** rather than an `onFailure` callback or a second collector —
  see D2.
* **Player-not-found is an empty contribution, not a failure** — see D3.
* **Notice inside the card** rather than above it — see D4.
* **Personal databases identified by account filename** so a metadata failure is attributable —
  see D5.
* **e2e harness growth (rule 6d):** the one new piece of test tooling is the per-call outcome
  sequence in `e2e/fixtures.ts`'s `MockCommand`. Cheap alternative considered: prove only the
  all-failed state in e2e (a plain `error` needs no harness change) and leave the partial state to
  the mounted test. Rejected because the partial state is the one with layout risk (a notice inside
  an `overflow: hidden` card above flex tabs) and the mounted test stubs both Mantine and the card.
  Removal path: delete the field; no existing scenario uses it.
