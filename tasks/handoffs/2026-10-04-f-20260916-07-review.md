# Plan: surface and record the download-target durability that both download paths drop (f-20260916-07)

## Goal

A Lichess or Chess.com game download whose target rename committed but whose parent-directory
sync could not be proven tells the user so, instead of reporting plain success; and the two
backend download sites that currently lose that uncertain stage when a later activation error
outranks it record it in the native log, as every other *combine* site already does.

## MANDATE

Verbatim, `tasks/findings.md` entry `f-20260916-07` (open, `frontend-state`, `Entry: build`):

> * **Where:** `src/utils/lichess/api.tsx:397-399` and `src/utils/chess.com/api.tsx:65-68`; the backend sets `ArtifactPublication.durability` at `src-tauri/src/fs.rs:936` and then returns `Ok` at `:949-950`.
> * **Defect:** a reserved download whose parent-directory sync could not be proven produces `CommittedDurabilityUncertain`, which the backend carries in `ArtifactPublication.durability`. Both renderer adapters drop that field, so the interface reports an unqualified success and the user proceeds with no warning.
> * **Why it matters:** `d-20260906-03` defines three durability contracts — *report*, *record*, *combine* — and this path is a *report* contract with no reporting surface. The uncertainty is computed, typed and then thrown away at the last step, which is indistinguishable from never having measured it.
> * **Related:** `f-20260914-10` (the Windows port makes this path newly reachable there), `d-20260906-03` (the contract being broken).
> * **Open question:** which layer owns surfacing an uncertain durability, and what is its typed contract? Either the adapters return a discriminated result the callers must handle, so dropping it becomes a type error, or the platform facade raises it once as a distinct event that no adapter can swallow. `d-20260906-03` already settles *that* it must be reported, so this is the mechanism, not whether. The answer also decides whether the *record* and *combine* contracts need the same treatment.
>
> **Annotated 2026-09-16 (round 8 of the `f-20260914-10` plan review; status stays open):** the same dropped-durability shape exists on **two backend sites**, not only in the renderer adapters, and both are named here rather than folded into `f-20260914-10` under its A6 slice boundary. (a) `download_to_destination_inner` (`src-tauri/src/fs.rs:936-944`) sets `artifact.durability` only on the `Ok` arm of `activate_download_artifact_runtime`; the `Err` arm reports and returns the activation error, discarding `target_durability`. (b) `install_staged_pgn_artifact` (`src-tauri/src/fs.rs:1012-1021`) does `activate_download_artifact_runtime(...).await?`, so the `?` discards `target_durability.outcome` before the durability is attached at `:1021`. Its production caller is Chess.com export (`src-tauri/src/chesscom.rs:379`). **The precedence itself is correct and must not be changed:** `d-20260906-03` clause (3) *combine* states that "a later non-uncertainty error outranks" the earlier uncertain stage, and commit `9d450dc5` pins exactly that `(Some(stage), Err(other))` arm — "must report the hard error, not the uncertainty". A round-8 proposal to surface both was **rejected** for that reason; it would have reintroduced the defect `9d450dc5` fixed. What is missing is not precedence but **observability**: the uncertain stage is dropped without being recorded anywhere, which is this finding's open question ("whether the *record* and *combine* contracts need the same treatment").

## Threat model and non-goals

Accidental input only: a filesystem whose parent-directory `fsync` fails or is interrupted after
the atomic rename landed (`AtomicFileOutcome::CommittedDurabilityUncertain`), followed — on the
backend half — by an ordinary activation failure (verification mismatch, poisoned/uninitialised
authority, I/O). No adversary is modelled: the renderer is the app's own UI, and these commands'
inputs are already validated upstream (`lichess_games_url`, `first_archive_month`, path
authority). Environments that count: every platform the Rust crate compiles for (Linux, macOS,
Windows — `f-20260914-10` ported the atomic install to Windows, so the uncertain outcome is
reachable there too). Non-goals: changing *when* the uncertainty arises, changing combine
precedence, changing any error text the renderer classifies.

## Approach

### O1 — Backend combine sites record the outranked uncertain stage

Rests on MANDATE: "the uncertain stage is dropped without being recorded anywhere" and "**The
precedence itself is correct and must not be changed**".

* **Behaviour.** In both `download_to_destination_inner` (reservation branch) and
  `install_staged_pgn_artifact`, the target install's `AtomicFileOutcome` is mapped through the
  existing `download_target_durability` **immediately after the install succeeds and before
  `activate_download_artifact_runtime` is awaited**, mirroring P9. The mapping emits the existing
  warning; the resulting `Option<CommitDurability>` is attached to the artifact on the activation
  `Ok` path exactly as today.
* **Failure semantics.** On an activation `Err`, the activation error is returned unchanged (and,
  in `download_to_destination_inner`, still reported through `report_download_error` first). The
  uncertain stage never replaces it and is never added to the error payload — *combine* precedence
  per `d-20260906-03` (3) and `9d450dc5`. The only change on that path is that the warning has
  already been written.
* **Ownership / boundary.** No signature, no Specta type, no IPC payload, no error text changes.
  The non-reservation branch (P7, *report* contract) is untouched. The warning text stays
  `download target replacement parent sync failed: {error}` (it already exists and is what
  `map_atomic_file_outcome`'s callback writes); no path or token is added to it.
* **Verification level.** Rust unit tests in `src-tauri/src/fs.rs`'s test module, one per site,
  each combining `TargetParentSyncFault` (failing the target replacement's parent sync) with a
  `SharedActivationObserver { corrupt_target }` activation failure, under `LogCaptureScope`, in a
  current-thread `#[tokio::test]`. Each asserts: (i) the returned error is the activation error
  (`Error::Conflict`), **not** `CommittedDurabilityUncertain`; (ii) exactly one captured record at
  `Warn` contains `download target replacement parent sync failed`; (iii) for
  `download_to_destination`, progress ends `Failed`/finished as in the existing verification-failure
  test. Each test must go red when O1 is reverted (no warning is captured today, P7/P8). The
  existing success-path test (P11) stays green unchanged, proving the `Ok` attachment did not
  regress.

unqualified success and the user proceeds with no warning", "`d-20260906-03` already settles
*that* it must be reported, so this is the mechanism".

* **Typed contract.** `downloadLichess` and `downloadChessCom` return the generated

* **Surfacing owner.** `AccountCard`'s download handler (P4), the single consumer of both

Rests on MANDATE: "The answer also decides whether the *record* and *combine* contracts need the

* *Combine*: the two download sites are the only combine sites that dropped the uncertain stage

* *Record*: the record contract is "log, keep going, carry the uncertainty in the result"

  results from user-initiated actions are already surfaced (P5). The startup legacy-token migration

## Decisions and trade-offs

* **Caller surfaces from a typed result, not a facade event.** Chosen because the backend already
  returns the discriminated value in the command result (P3) and all existing renderer durability
  warnings follow this shape (P5). A facade-level event would add a second channel for information
  the command result already carries, a new renderer event mechanism with its own listener
  lifetime, and correlation back to the job — more surface for the same signal.
* **The caller, not an adapter-level helper, shows the notification.** Both adapters have exactly
  one consumer, which already owns the download's error notification; a shared helper would be a new
  module with a single call site after convergence, and a utils-layer notification diverges from
  the P5 precedents. Adapters returning the publication whole removes the only point where the field
  was stripped.
* **Map before activation, not "map in both arms".** Mapping once before the activation await is
  the P9 shape, logs exactly once on every path, and keeps the `Option<CommitDurability>` handling
  identical on the success path. Adding a second `download_target_durability` call inside the `Err`
  arm would duplicate the mapping and cannot work at the `?` site without restructuring anyway.
* **Precedence unchanged** — see MANDATE; surfacing both was rejected in round 8 of `f-20260914-10`.

## Decided autonomously

1. **Question:** which layer owns surfacing an uncertain download durability, and what is its typed
   contract? **Chosen:** the adapters return the generated `ArtifactPublication` unchanged and the
   single caller (`AccountCard`) shows an orange "Do not retry" notification before continuing the
   import, as `Accounts.tsx` and `AccountCards.tsx` already do for account link/removal.
   **Rejected:** a platform-facade event (second channel and a new listener lifetime for data the
   command result already carries); an adapter-level notifying helper (new single-caller module,
   diverges from the durability precedents); a new renderer-side wrapper type (the generated union
   already discriminates). **Reason:** least new mechanism, consistent with every existing
   durability warning; the remaining TypeScript limit is pinned by tests. **Governs:** f-20260916-07.
2. **Question:** do the *combine* sites need the same treatment, and how without changing
   precedence? **Chosen:** the two download sites map the target outcome (warning included) before
   activation, as workspace create/rename do; the activation error still outranks and the payload
   is unchanged. **Rejected:** carrying both stages in the error (reverses `9d450dc5`); a new error
   variant (IPC/classifier change for an observability gap); mapping inside the error arm only (two
   mappings, impossible at the `?` site without the same restructuring). **Governs:** f-20260916-07.
3. **Question:** does the *record* contract need renderer surfacing? **Chosen:** no — record sites
   log natively and user-initiated record results are already surfaced; the startup legacy-token
   migration is background reconciliation whose uncertainty is already logged natively.
   **Rejected:** a startup notification for migration durability (no user action to qualify; the
   native log satisfies `d-20260906-03` (2)). **Reversal path:** a finding showing a user acting on
   a migrated account's uncertain persistence. **Governs:** f-20260916-07.

## Goal

### O1 — Backend combine sites record the outranked uncertain stage

Rests on MANDATE: "the uncertain stage is dropped without being recorded anywhere" and "**The

## Decisions and trade-offs

* **Caller surfaces from a typed result, not a facade event.** Chosen because the backend already
  returns the discriminated value in the command result (P3) and all existing renderer durability
  warnings follow this shape (P5). A facade-level event would add a second channel for information
  the command result already carries, a new renderer event mechanism with its own listener
  lifetime, and correlation back to the job — more surface for the same signal.
* **The caller, not an adapter-level helper, shows the notification.** Both adapters have exactly
  one consumer, which already owns the download's error notification; a shared helper would be a new
  module with a single call site after convergence, and a utils-layer notification diverges from
  the P5 precedents. Adapters returning the publication whole removes the only point where the field
  was stripped.
* **Map before activation, not "map in both arms".** Mapping once before the activation await is
  the P9 shape, logs exactly once on every path, and keeps the `Option<CommitDurability>` handling
  identical on the success path. Adding a second `download_target_durability` call inside the `Err`
  arm would duplicate the mapping and cannot work at the `?` site without restructuring anyway.
* **Precedence unchanged** — see MANDATE; surfacing both was rejected in round 8 of `f-20260914-10`.

## Decided autonomously

1. **Question:** which layer owns surfacing an uncertain download durability, and what is its typed
   contract? **Chosen:** the adapters return the generated `ArtifactPublication` unchanged and the
   single caller (`AccountCard`) shows an orange "Do not retry" notification before continuing the
   import, as `Accounts.tsx` and `AccountCards.tsx` already do for account link/removal.
   **Rejected:** a platform-facade event (second channel and a new listener lifetime for data the
   command result already carries); an adapter-level notifying helper (new single-caller module,
   diverges from the durability precedents); a new renderer-side wrapper type (the generated union
   already discriminates). **Reason:** least new mechanism, consistent with every existing
   durability warning; the remaining TypeScript limit is pinned by tests. **Governs:** f-20260916-07.
2. **Question:** do the *combine* sites need the same treatment, and how without changing
   precedence? **Chosen:** the two download sites map the target outcome (warning included) before
   activation, as workspace create/rename do; the activation error still outranks and the payload
   is unchanged. **Rejected:** carrying both stages in the error (reverses `9d450dc5`); a new error
   variant (IPC/classifier change for an observability gap); mapping inside the error arm only (two
   mappings, impossible at the `?` site without the same restructuring). **Governs:** f-20260916-07.
3. **Question:** does the *record* contract need renderer surfacing? **Chosen:** no — record sites
   log natively and user-initiated record results are already surfaced; the startup legacy-token
   migration is background reconciliation whose uncertainty is already logged natively.
   **Rejected:** a startup notification for migration durability (no user action to qualify; the
   native log satisfies `d-20260906-03` (2)). **Reversal path:** a finding showing a user acting on
   a migrated account's uncertain persistence. **Governs:** f-20260916-07.

## Decisions and trade-offs

* **Caller surfaces from a typed result, not a facade event.** Chosen because the backend already
  returns the discriminated value in the command result (P3) and all existing renderer durability
  warnings follow this shape (P5). A facade-level event would add a second channel for information
  the command result already carries, a new renderer event mechanism with its own listener
  lifetime, and correlation back to the job — more surface for the same signal.
* **The caller, not an adapter-level helper, shows the notification.** Both adapters have exactly
  one consumer, which already owns the download's error notification; a shared helper would be a new
  module with a single call site after convergence, and a utils-layer notification diverges from
  the P5 precedents. Adapters returning the publication whole removes the only point where the field
  was stripped.
* **Map before activation, not "map in both arms".** Mapping once before the activation await is
  the P9 shape, logs exactly once on every path, and keeps the `Option<CommitDurability>` handling
  identical on the success path. Adding a second `download_target_durability` call inside the `Err`
  arm would duplicate the mapping and cannot work at the `?` site without restructuring anyway.
* **Precedence unchanged** — see MANDATE; surfacing both was rejected in round 8 of `f-20260914-10`.

## Decided autonomously

1. **Question:** which layer owns surfacing an uncertain download durability, and what is its typed
   contract? **Chosen:** the adapters return the generated `ArtifactPublication` unchanged and the
   single caller (`AccountCard`) shows an orange "Do not retry" notification before continuing the
   import, as `Accounts.tsx` and `AccountCards.tsx` already do for account link/removal.
   **Rejected:** a platform-facade event (second channel and a new listener lifetime for data the
   command result already carries); an adapter-level notifying helper (new single-caller module,
   diverges from the durability precedents); a new renderer-side wrapper type (the generated union
   already discriminates). **Reason:** least new mechanism, consistent with every existing
   durability warning; the remaining TypeScript limit is pinned by tests. **Governs:** f-20260916-07.
2. **Question:** do the *combine* sites need the same treatment, and how without changing
   precedence? **Chosen:** the two download sites map the target outcome (warning included) before
   activation, as workspace create/rename do; the activation error still outranks and the payload
   is unchanged. **Rejected:** carrying both stages in the error (reverses `9d450dc5`); a new error
   variant (IPC/classifier change for an observability gap); mapping inside the error arm only (two
   mappings, impossible at the `?` site without the same restructuring). **Governs:** f-20260916-07.
3. **Question:** does the *record* contract need renderer surfacing? **Chosen:** no — record sites
   log natively and user-initiated record results are already surfaced; the startup legacy-token
   migration is background reconciliation whose uncertainty is already logged natively.
   **Rejected:** a startup notification for migration durability (no user action to qualify; the
   native log satisfies `d-20260906-03` (2)). **Reversal path:** a finding showing a user acting on
   a migrated account's uncertain persistence. **Governs:** f-20260916-07.
