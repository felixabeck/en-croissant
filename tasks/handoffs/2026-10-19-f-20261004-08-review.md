# Plan: Surface a failed Lichess account read

## Goal

A failed Lichess account read must not look like a successful reload or a successful add. `getLichessAccount` stops turning a request or parse failure into `null`. The four existing callers keep the presentation they already have for a rejection.

## MANDATE

### `getLichessAccount` turns an invalid account response into `null`, so a failed reload or add looks like success

* **ID:** f-20261004-08 · **Status:** open · **Area:** oauth-credentials · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** 0fa004d0-93e4-4004-86d2-6652e891bd6e
* **Where:** `src/utils/lichess/api.tsx:235-258` (`getLichessAccount`: both branches `try { return parseNativeJson(result, lichessAccountSchema) } catch { return null; }`); callers `src/components/common/AccountCards.tsx:251` (reload: `if (!account) return;`), `src/components/home/Accounts.tsx:109` (add account), `src/utils/session.ts:190` (startup reconciliation), `src/utils/lichess/authentication.ts:40`.
* **Defect:** a Lichess response that arrives (HTTP 200, valid JSON) but does not match `lichessAccountSchema` is swallowed into `null` with no log and no notification. The reload button then completes normally, so the user sees the old statistics and no error, and nothing is written to the native log. The Chess.com counterpart (`src/utils/chess.com/api.tsx:36-50`) logs and notifies on the same case.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` — return typed errors and surface the failure; an error returned as success hides a broken provider contract.
* **Open question:** should `getLichessAccount` throw a typed validation error (and each of its four callers, including startup reconciliation and the authentication flow, decide how to present or tolerate it), or keep `null` for "no account" and log plus notify on a shape failure like the Chess.com helper — and which callers must distinguish "absent" from "invalid"?
* **Related:** found while repairing `f-20260914-06`'s review findings, which made AccountCard's reload report rejections (`runUnlessCancelled`); this swallow sits below that and never rejects.
* **Found by:** `review-error-handling` closure-round lens (Codex), 2026-10-04, confidence 98, during the f-20260914-06 build run (range `8730105c..b7396bb6`); confirmed by the orchestrator by reading `api.tsx:235-258` and grepping the four callers. Pre-existing; deferred because the fix changes a contract shared with session reconciliation and the OAuth flow, which that run did not read.

The filed `Where` lines have moved. The traced premises name the current lines. The behavior the finding describes is still present. This plan does not edit the ledger.

## Threat model and non-goals

The input is a Lichess account read that does not yield a schema-valid account: the native command rejects (non-success HTTP, invalid JSON, missing `id` or `username`, identity mismatch, unavailable credential, transport failure), or it returns a string that `parseNativeJson` rejects. The renderer must not treat that outcome as an account.

No bearer token, response body, Zod issue list, or backend diagnostic is written to the native log or shown beyond the redaction `notifyUnlessCancelled` and `runUnlessCancelled` already apply. This plan does not change native commands, generated bindings, the Chess.com helper, or the session schema.

## Traced premises

* `getLichessAccount` (`src/utils/lichess/api.tsx:241-264`) returns `null` when neither `handle` nor `username` is set, before any request. Both request branches `await` the native command and `parseNativeJson` inside one `try` and `return null` on any throw. `parseNativeJson` (`api.tsx:171-176`) throws `new Error("Lichess returned an invalid response")` and does not include the body.
* `get_public_lichess_json` (`src-tauri/src/lichess.rs:164-169`, `public_json` at `122-134`) rejects a non-success HTTP status and invalid JSON. It does not require `id` and `username`. A public `200` body of `{}` reaches the renderer schema.
* `get_authenticated_lichess_account` (`lichess.rs:257-296`) rejects invalid JSON, a missing `id` or `username`, an unknown handle, and a username that does not match the stored account (`Error::OAuthFailure`, "Lichess account identity changed"). A body that passes this check also passes `lichessAccountSchema`. The renderer `catch` still turns those native errors into `null`.
* Reload is already wrapped: `AccountCard.tsx:292-295` calls `runUnlessCancelled(t("Common.Error"), () => reload())`. `AccountCards.tsx:243-249` returns without writing sessions when `getLichessAccount` returns `null`. A rejection from `reload` therefore notifies and leaves the card unchanged. The swallow is what prevents that notification.
* Public add: `Accounts.tsx:98-108` returns `false` on `null` and calls `notifyUnlessCancelled` only on a throw. `Accounts.tsx:194-205` leaves the modal open when the result is `false`. `Accounts.test.tsx:216-235` already expects a rejected Lichess lookup to notify with `Common.Error` and keep the modal open.
* Startup: `session.ts:247-262` calls `getLichessAccount` only for a native account whose username is not already in the sanitized list. `null` skips the card. A throw is caught and skipped, with the comment that the credential stays and the card appears on a later successful reconciliation. No notification is shown. `d-20261004-22` keeps startup reconciliation off the notification path.
* Authentication: `authentication.ts:40-45` does `getLichessAccount({ handle }).catch(() => null) ?? { id: metadata.username.toLocaleLowerCase(), username: metadata.username }` after `completed.state === "succeeded"`. `authentication.test.ts:64-78` pins that an unavailable profile still links and stores that synthesized account. `d-20260831-18` keeps a succeeded authentication linked rather than showing authentication failed.
* `api.test.ts:16-18` already mocks `@/platform/native`'s `error`. `logFailureSafely` (`src/platform/errors.ts:311-324`) logs one message and, if that logger rejects, writes a sanitized console fallback. `safeFailureContext` (`errors.ts:284-293`) redacts the cause message.
* Chess.com (`src/utils/chess.com/api.tsx:36-50`) logs the Zod error and notifies inside the helper, then returns `null`. Its callers are the public add and the reload. It is not on the startup or authentication path.

## Approach

### Failure leaves the helper as a rejection

`getLichessAccount` still returns `null` only when the caller passes neither `handle` nor `username`. That call makes no request and writes no log.

Every other failure rejects with the original cause. The helper does not notify. Before rethrowing it logs exactly once through `logFailureSafely`, with the fixed message `Lichess account response was rejected`, operation `Lichess account lookup`, and `safeFailureContext` of the cause. The log message does not interpolate the cause, the response body, or a Zod issue list. A logger failure must not replace the original rejection.

`null` means the caller did not name an account. A rejection means the named account was not read. No new result type and no new error class.

### Callers keep their existing presentation

No production edit to these callers:

* Reload already notifies through `runUnlessCancelled` when `reload` rejects, and it does not write the session when the read fails.
* Public add already notifies through `notifyUnlessCancelled` when `getLichessAccount` rejects, and it does not close the modal.
* Startup already catches a rejection, does not add a card, and does not notify. The new log is the startup record.
* Authentication already turns a rejection into the metadata fallback and still returns `{ ok: true }` after a succeeded native job. An identity mismatch is one of those rejections: the native command refuses the body before the renderer can read the other username, and the stored card uses the authenticate job's username. The next user-initiated reload rejects and notifies. Startup does not synthesize a card for an account that is not already in the session list.

### What this plan does not change

The Chess.com helper stays as it is. Its notify-inside-the-helper shape is safe only because it has no startup or authentication caller. Copying that shape into `getLichessAccount` would toast during launch and during a successful sign-in.

Native account validation, bindings, session schema, and translation catalogues stay as they are. The user-facing text is the existing `Common.Error` title plus the redacted message of the rejection. The schema rejection message remains `Lichess returned an invalid response`.

## Decisions and trade-offs

### Decided autonomously

* **Question:** throw a validation failure from `getLichessAccount`, or return `null` and notify inside the helper the way Chess.com does?
  **Chosen:** reject with the original cause, log one fixed line in the helper, and do not notify there.
  **Rejected:** notify inside the helper and return `null` — startup and authentication would show a toast for a read the user did not request, against `d-20261004-22` and `d-20260831-18`. A new typed result — the four callers already branch on rejection versus account. A new error subclass — `parseNativeJson` and the native command already throw, and the user-facing path redacts `unknown`.
  **Reason:** `d-20261008-04` leaves presentation to each caller. `d-20261004-19` surfaces a user-initiated outcome at the caller that owns the action. Reload and add already do that for a rejection. The missing piece is that the helper never rejects.
  **Reversal:** notify inside `getLichessAccount` only if startup and authentication stop calling it.

* **Question:** which callers distinguish "no account was named" from "the named account was not read"?
  **Chosen:** only the helper's `null` versus rejection split. Reload and add treat rejection as a visible failed action and treat `null` as "do not write". Startup treats both as "do not add a card" and does not notify. Authentication treats rejection and `null` as "link the metadata account".
  **Rejected:** making authentication fail on identity mismatch — the credential is already stored by the succeeded job, and `d-20260831-18` rejected turning that success into authentication failed. Making startup synthesize a profile — `session.ts` already refuses that.
  **Reason:** the callers already implement those choices. The defect is that a failed read never arrives as a rejection.
  **Reversal:** branch authentication on the native identity-mismatch string only with a new finding that the stored token and the displayed username can belong to different people after a succeeded job.

## Risks / open questions

None that block implementation. The filed `Where` line for startup (`session.ts:190`) is the legacy-revocation `catch`, not the profile read. The profile read is the startup caller this plan covers.

## Not part of this task

Chess.com account parsing, native Lichess HTTP validation, OAuth token storage, download durability, and the database-list rejoin findings filed beside this one.

# Plan: Surface a failed Lichess account read

## Goal

A failed Lichess account read must not look like a successful reload or a successful add. `getLichessAccount` stops turning a parse failure into `null`. A native command rejection already rejects and is left as it is. The four existing callers keep the presentation they already have for a rejection.

## MANDATE

### `getLichessAccount` turns an invalid account response into `null`, so a failed reload or add looks like success

* **ID:** f-20261004-08 · **Status:** open · **Area:** oauth-credentials · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** 0fa004d0-93e4-4004-86d2-6652e891bd6e
* **Where:** `src/utils/lichess/api.tsx:235-258` (`getLichessAccount`: both branches `try { return parseNativeJson(result, lichessAccountSchema) } catch { return null; }`); callers `src/components/common/AccountCards.tsx:251` (reload: `if (!account) return;`), `src/components/home/Accounts.tsx:109` (add account), `src/utils/session.ts:190` (startup reconciliation), `src/utils/lichess/authentication.ts:40`.
* **Defect:** a Lichess response that arrives (HTTP 200, valid JSON) but does not match `lichessAccountSchema` is swallowed into `null` with no log and no notification. The reload button then completes normally, so the user sees the old statistics and no error, and nothing is written to the native log. The Chess.com counterpart (`src/utils/chess.com/api.tsx:36-50`) logs and notifies on the same case.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` — return typed errors and surface the failure; an error returned as success hides a broken provider contract.
* **Open question:** should `getLichessAccount` throw a typed validation error (and each of its four callers, including startup reconciliation and the authentication flow, decide how to present or tolerate it), or keep `null` for "no account" and log plus notify on a shape failure like the Chess.com helper — and which callers must distinguish "absent" from "invalid"?
* **Related:** found while repairing `f-20260914-06`'s review findings, which made AccountCard's reload report rejections (`runUnlessCancelled`); this swallow sits below that and never rejects.
* **Found by:** `review-error-handling` closure-round lens (Codex), 2026-10-04, confidence 98, during the f-20260914-06 build run (range `8730105c..b7396bb6`); confirmed by the orchestrator by reading `api.tsx:235-258` and grepping the four callers. Pre-existing; deferred because the fix changes a contract shared with session reconciliation and the OAuth flow, which that run did not read.

The filed `Where` lines have moved. The traced premises name the current lines. The behavior the finding describes is still present. This plan does not edit the ledger.

## Threat model and non-goals

The input is a Lichess account read that does not yield a schema-valid account: the native command rejects (non-success HTTP, invalid JSON, missing `id` or `username`, identity mismatch, unavailable credential, transport failure), or it returns a string that `parseNativeJson` rejects. The renderer must not treat that outcome as an account.

No bearer token, response body, Zod issue list, or backend diagnostic is written to the native log or shown beyond the redaction `notifyUnlessCancelled` and `runUnlessCancelled` already apply. This plan does not change native commands, generated bindings, the Chess.com helper, or the session schema.

## Traced premises

* `getLichessAccount` (`src/utils/lichess/api.tsx:241-264`) returns `null` when neither `handle` nor `username` is set, before any request. Each request branch `await`s the native command outside `try`. The `try` covers only `parseNativeJson`, and its `catch` returns `null`. A native command rejection already rejects from `getLichessAccount` and already reaches the callers. `parseNativeJson` (`api.tsx:171-176`) throws `new Error("Lichess returned an invalid response")` and does not include the body.
* `get_public_lichess_json` (`src-tauri/src/lichess.rs:164-169`, `public_json` at `122-134`) rejects a non-success HTTP status and invalid JSON. It does not require `id` and `username`. A public `200` body of `{}` reaches the renderer schema and is the swallowed success.
* `get_authenticated_lichess_account` (`lichess.rs:257-296`) rejects invalid JSON, a missing `id` or `username`, an unknown handle, and a username that does not match the stored account (`Error::OAuthFailure`, "Lichess account identity changed") before any body is returned. Those errors already reject from the renderer helper. A body that passes this check also passes `lichessAccountSchema`. The authenticated `catch` still returns `null` if `parseNativeJson` throws on a body the command did return.
* Reload is already wrapped: `AccountCard.tsx:292-295` calls `runUnlessCancelled(t("Common.Error"), () => reload())`. `AccountCards.tsx:243-249` returns without writing sessions when `getLichessAccount` returns `null`. A rejection from `reload` therefore notifies and leaves the card unchanged. The swallow is what prevents that notification.
* Public add: `Accounts.tsx:98-108` returns `false` on `null` and calls `notifyUnlessCancelled` only on a throw. `Accounts.tsx:194-205` leaves the modal open when the result is `false`. `Accounts.test.tsx:220-239` already expects a rejected Lichess lookup to notify with `Common.Error` and keep the modal open.
* Startup: `session.ts:247-262` calls `getLichessAccount` only for a native account whose username is not already in the sanitized list. `null` skips the card. A throw is caught and skipped, with the comment that the credential stays and the card appears on a later successful reconciliation. No notification is shown. `d-20261004-22` keeps startup reconciliation off the notification path.
* Authentication: `authentication.ts:40-45` does `getLichessAccount({ handle }).catch(() => null) ?? { id: metadata.username.toLocaleLowerCase(), username: metadata.username }` after `completed.state === "succeeded"`. `authentication.test.ts:64-78` pins that an unavailable profile still links and stores that synthesized account. `d-20260831-18` keeps a succeeded authentication linked rather than showing authentication failed.
* `api.test.ts:16-18` already mocks `@/platform/native`'s `error`. `logFailureSafely` (`src/platform/errors.ts:311-324`) logs one message and, if that logger rejects, writes a sanitized console fallback. `safeFailureContext` (`errors.ts:284-293`) redacts the cause message.
* Chess.com (`src/utils/chess.com/api.tsx:36-50`) logs the Zod error and notifies inside the helper, then returns `null`. Its callers are the public add and the reload. It is not on the startup or authentication path.

## Approach

### Failure leaves the helper as a rejection

`getLichessAccount` still returns `null` only when the caller passes neither `handle` nor `username`. That call makes no request and writes no log.

The `await` of each native command stays outside `try`. A native rejection propagates as it does now, with no added log and no added notification.

The parse `catch` stops returning `null`. It logs exactly once through `logFailureSafely`, with the fixed message `Lichess account response was rejected`, operation `Lichess account lookup`, and `safeFailureContext` of the parse cause, then rethrows that cause. The log message does not interpolate the cause, the response body, or a Zod issue list. A logger failure must not replace the parse rejection. The helper does not notify.

`null` means the caller did not name an account. A parse rejection means the returned body was not an account. No new result type and no new error class.

### Callers keep their existing presentation

No production edit to these callers:

* Reload already notifies through `runUnlessCancelled` when `reload` rejects, and it does not write the session when the read fails.
* Public add already notifies through `notifyUnlessCancelled` when `getLichessAccount` rejects, and it does not close the modal.
* Startup already catches a rejection, does not add a card, and does not notify. A swallowed parse failure becomes a rejection, so this catch is what keeps launch quiet, and the new log is the record of that parse failure.
* Authentication already turns a rejection into the metadata fallback and still returns `{ ok: true }` after a succeeded native job. Identity mismatch is already a native rejection on that path: the command refuses the body before the renderer can read another username, and the stored card uses the authenticate job's username. This plan does not change that. Startup does not synthesize a card for an account that is not already in the session list.

### What this plan does not change

The Chess.com helper stays as it is. Its notify-inside-the-helper shape is safe only because it has no startup or authentication caller. Copying that shape into `getLichessAccount` would toast during launch and during a successful sign-in.

Native account validation, bindings, session schema, and translation catalogues stay as they are. The user-facing text is the existing `Common.Error` title plus the redacted message of the rejection. The schema rejection message remains `Lichess returned an invalid response`.

## Decisions and trade-offs

### Decided autonomously

* **Question:** throw a validation failure from `getLichessAccount`, or return `null` and notify inside the helper the way Chess.com does?
  **Chosen:** reject with the original cause, log one fixed line in the helper, and do not notify there.
  **Rejected:** notify inside the helper and return `null` — startup and authentication would show a toast for a read the user did not request, against `d-20261004-22` and `d-20260831-18`. A new typed result — the four callers already branch on rejection versus account. A new error subclass — `parseNativeJson` and the native command already throw, and the user-facing path redacts `unknown`.
  **Reason:** `d-20261008-04` leaves presentation to each caller. `d-20261004-19` surfaces a user-initiated outcome at the caller that owns the action. Reload and add already do that for a native rejection. The missing piece is the parse `catch`, which still returns `null`.
  **Reversal:** notify inside `getLichessAccount` only if startup and authentication stop calling it.

* **Question:** which callers distinguish "no account was named" from "the named account was not read"?
  **Chosen:** only the helper's `null` versus rejection split. Reload and add treat rejection as a visible failed action and treat `null` as "do not write". Startup treats both as "do not add a card" and does not notify. Authentication treats rejection and `null` as "link the metadata account".
  **Rejected:** making authentication fail on identity mismatch — the credential is already stored by the succeeded job, and `d-20260831-18` rejected turning that success into authentication failed. Making startup synthesize a profile — `session.ts` already refuses that.
  **Reason:** the callers already implement those choices. The defect is that a parse failure arrives as `null`, so reload and add take the success-shaped branch. Native failures already arrive as rejections.
  **Reversal:** branch authentication on the native identity-mismatch string only with a new finding that the stored token and the displayed username can belong to different people after a succeeded job.
