# Plan: Exact account player identity in home statistics

## Goal
Home statistics include only the account owner's games, including stored casing variants of that same account identifier.

## MANDATE
### The home summary picks the account player by substring match, so another player's statistics can be shown

* **ID:** f-20261008-04 · **Status:** open · **Area:** db-search · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** d26408c9-455d-4640-a682-2db58367a729
* **Where:** `src/components/home/Databases.tsx` statistics mapper (`query_players(db.file, { name: username, options: { pageSize: 1, direction: "asc", sort: "id" } })`, then `players.data[0]`); `src-tauri/src/db/mod.rs:2133-2134` `get_players_blocking` filters `players::name.like(format!("%{}%", name))`.
* **Defect:** the account owner's row is looked up with a substring `LIKE '%name%'` and the first row by ascending id is taken. In an account database where an opponent whose name contains the account name (account `alex`, opponent `alexander`) was inserted before the owner, the summary computes and displays the opponent's statistics as the account's. `LIKE` also treats `_` and `%` in the username as wildcards (`_` is common in Lichess and Chess.com usernames) and is ASCII-case-insensitive, so `a_b` matches `axb`. When the owner has no row at all, a substring hit turns "no games" (d-20261008-05) into another player's games.
* **Evidence:** read at HEAD 595b415c; reported by `review-correctness` (confidence 100) in the cumulative diff review of f-20260926-02, drain session d26408c9-455d-4640-a682-2db58367a729, 2026-10-08. Pre-existing; f-20260926-02 kept the lookup unchanged. Other `query_players` callers (`PlayerSearchInput.tsx:76`, `PlayerTable.tsx:32`) want the substring search, so the predicate itself is correct for them.
* **Open question:** how does the renderer obtain an exact player identity — an exact-name option on `PlayerQuery` (Specta contract and generated bindings change, wildcard-free equality), a dedicated exact lookup command, or resolving the account owner once at import time and storing its id with the account database? And is the comparison case-sensitive (Lichess usernames are case-insensitive identifiers, Chess.com usernames too)?
* **Proof required:** a backend test with an account database holding `alexander` (id 1) and `alex` (id 2) plus a `a_b`/`axb` pair, where the account lookup returns exactly the owner; and a `Databases.test.tsx` case where the lookup must not fall back to a substring hit.
* **Related:** f-20260926-02 (handled by this session; its summary consumes the lookup), d-20261008-05 (player-not-found is an empty contribution).

Preserve read snapshot, cancellation and resource ownership. Regenerate Specta bindings and forward the field through query_players.

## Decisions and trade-offs
Decided autonomously, pending plan review and ledger recording:
* Extend the existing query with an optional exact mode rather than adding a command or persisted import-time id. This preserves one query lifecycle and avoids a new stale identity. Reversal path is removal of the field and its home caller.
* Use ASCII case-insensitive literal equality for account identifiers, preserving substring defaults for human-name browsing. Reject case-sensitive account matching because display casing is not identity. SQL parameters remain bound. No Unicode case folding or database migration.
* Include every exact case variant, because imports preserve them as distinct rows. Reject choosing the lowest id or exact-case preference because either omits real owner games. Failure stays atomic per database. Reversal is the home mapper only, the query mode remains independently useful.
* Publish session spelling as the home statistics account identity. This is required by the existing account-selector boundary and keeps imported database display names unchanged. Reversal is removal of that mapper field rewrite alongside a coordinated account-filter change.

## Risks / open questions
Exact mode scans names when SQLite cannot use its binary name index. It replaces an existing leading-wildcard scan, adds no schema obligation, and returns matching player rows rather than materializing games. Real-app verification may expose independent existing failures, which must be attributed honestly.
