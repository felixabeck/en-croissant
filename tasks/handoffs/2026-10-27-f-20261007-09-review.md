# Plan: Stale engine attachment ids must not fail every save

## Goal

One persisted attachment id that the native registry does not know must stop failing engine-owner prepare and startup attachment reconcile. Live attachments, retired in-process attachments, and known non-attachment capabilities keep the behavior they have today.

## MANDATE

One stale engine attachment id makes every engine-settings save and the startup attachment reconcile fail with InvalidInput.

* **ID:** f-20261007-09 · **Status:** open · **Area:** native-fs · **Root:** - · **Entry:** build · **Blocked:** none
* **Filed from:** 2a22787f-5af5-4f83-a7b0-3e9cbecbc726
* **Where:** `src-tauri/src/infra/path_authority/mod.rs:7366-7377` (`reconcile_engine_attachments`: every retained id must be in `persistent` or `retired_attachments`, otherwise the whole action returns `InvalidInput("unknown retained engine attachment")`), `:7354-7358` (the raw-count limit precedes any filtering); `src/state/engineOwnerStorage.ts:180-196` (`enqueueEngineOwnerSave` prepares the union of every owner key's attachment ids), `:271-283` (`reconcileStartupEngineAttachments` forwards the persisted snapshot unchanged with `startup: true`), `:110-130` (the startup snapshot validates shape only, never native membership).
* **Defect:** renderer engine-owner records are validated for shape, not for registry membership, so a persisted attachment id whose native record is gone (registry replaced or reset, a retired attachment surviving in a record written outside the coordinator, legacy state) stays in localStorage. Every later engine-settings save sends the union of all owner keys' ids through `prepare`, which rejects the whole action on that one unknown id, so the save is refused (`saved: false`) for every engine edit until the stale id is removed by hand; the startup `reconcile` with the same snapshot fails the same way, so omitted attachments are never retired and managed-image cleanup never runs.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` — fail the one item, not the process; here one dead reference blocks every save of an unrelated engine and the whole cleanup path.
* **Open question:** which side owns stale attachment references — should native `prepare`/startup `reconcile` discard ids it does not know (and what then stops a save from durably naming a capability that does not exist), or should the renderer prune ids native reports as unknown from its owner records (a typed per-id result instead of one `InvalidInput`), and how does that interact with the prepare-before-save ordering of `d-20260906-10`?
* **Related:** `f-20260924-01` (same stale-renderer-id class for `reconcile_startup_owners`; its plan keeps engine attachments out of scope and its fix also stops a rejected path-owner reconcile from skipping the startup attachment reconcile), `f-20260901-13` (handled, introduced the attachment protocol), `d-20260906-10`.
* **Found by:** locate probe of the `f-20260924-01` plan-only run, drain session 2a22787f-5af5-4f83-a7b0-3e9cbecbc726, 2026-10-07.
* **Correction (2026-10-08, records lens of the f-20260922-07 cumulative review, drain session fa6786ed-3e23-4701-b1a3-05a243d9a80b):** two consequences in **Defect** are overstated. (1) A stale id does not refuse *every* engine edit: `enqueueEngineOwnerSave` (`src/state/engineOwnerStorage.ts:180-187`) builds the `prepare` set from the changed key's *proposed* ids plus the other keys' persisted ids, so a save that replaces or removes the sole stale id held by that key succeeds; the refusal hits every save whose resulting union still contains the stale id. (2) Managed-image cleanup is not lost entirely: a failed startup reconcile skips its own cleanup call, but `shutdown_engine_attachments` (`src-tauri/src/main.rs`) runs `cleanup_engine_images` independently at exit, so already recorded cleanup intents are still processed. The open question is unchanged.

The line numbers in **Where** are the filing day's. The traced premises below are the current code. The correction is binding: a save whose resulting union no longer contains the stale id already succeeds, and shutdown still runs image cleanup when startup reconcile did not.

## Threat model and non-goals

The input is a renderer-supplied retained-id list on `prepare` or `reconcile`. It can contain ids the registry still has, ids held only in this process's retired-attachment map, ids the registry does not have, known ids whose purpose is not an engine attachment, and more ids than the action allows. The renderer is not treated as authority for native files. An unknown id must not become a registry entry, a retired entry, a provisional attachment, or a cleanup intent, and must not cancel an existing cleanup intent.

Out of scope for the threat model: a caller who already holds a live attachment id (that id is in the persistent registry), and UUID collision between a newly minted id and a dangling renderer string.

Non-goals: pruning or rewriting renderer owner documents; changing the Specta command, its `Result<(), Error>` return, or `src/bindings/generated.ts`; changing abandon-id limits; changing startup path-owner reconciliation; changing engine-executable ownership; deleting resource or image bytes; taking any other open `native-fs` finding.

## Approach

### O1. Unknown retained ids are ignored

An id absent from both `persistent` and `retired_attachments` is not a retained attachment. `prepare` and `reconcile` drop it and continue. They do not insert it into `persistent`, `retired_attachments`, `provisional_attachments`, or `image_cleanup`, and they do not remove an existing `image_cleanup` intent because of it.

`prepare` of a set whose only unknown members are dropped is a successful no-op when the remaining known set also changes nothing. `reconcile` with `Some(ids)` uses the known subset as the retained set. A `Some` that becomes empty after the drop is an empty retained snapshot, not `None`: startup reconcile may retire omitted loaded attachments under the rules already in the function. `None` stays abandon-only.

This is what stops a save from naming a capability that does not exist. The renderer may keep the stale string in its owner record. That string is not a registry entry. Prepare of a retired in-memory id still readopts that entry and cancels its cleanup before the renderer write, which is the `d-20260906-10` ordering. An unknown id has no retired entry to readopt. New ids are UUID v4 and the existing mint skips ids already in the registry maps, so the dangling string is not reissued as a new capability.

### O2. Known non-attachments still fail closed

A retained id that is present and is not an engine attachment still returns `InvalidInput` for the whole action and mutates nothing, including when the same list also contains live attachment ids and unknown ids. The check stays before any candidate is committed. Abandoned ids keep their current type check.

### O3. Raw caps

The retained-id raw `Vec` length is refused with `ResourceLimit` when it exceeds `authority_id_input_limit().saturating_add(MAX_STARTUP_OWNER_UNKNOWN_IDS)`, before classification. Abandoned ids stay capped at `authority_id_input_limit()` with no added headroom. `startup && retained.is_none()` stays `ResourceLimit`. Update the constant's comment so the headroom is the stale-renderer allowance for startup path owners and for this attachment action. Do not rename the constant and do not change `reconcile_startup_owners`.

Known attachment ids are a subset of maps the registry limit already bounds. No second cap on the known subset.

### O4. Live and retired attachments stay on the current transaction

Classification does not change prepare's refusal to retire omitted ids, reconcile's retirement rules, session protection, provisional marking, readopt of retired entries, durability, or the sealed-attachment `Conflict` that already returns before this logic. A live attachment id, including one marked provisional because issuance inserted it into `persistent` first, remains known and is still retained when the caller names it.

### O5. Renderer and IPC stay

No edit to `engineOwnerStorage.ts`, `pathOwners.ts`, `main.rs`, or `src/bindings/generated.ts`. Prepare success still means the renderer may `setItem` the owner record, stale string included. Startup reconcile `Ok` is what lets the existing command reach `cleanup_engine_images`. Shutdown cleanup stays as it is.

### O6. Proof

Update the two existing tests named in the premises, and add the two tests in Phase 1. Refusal cases still compare registry bytes and the persistent, provisional, retired, and image-cleanup maps to the pre-call snapshot.

## Decisions and trade-offs

## Approach

### O1. Unknown retained ids are ignored

An id absent from both `persistent` and `retired_attachments` is not a retained attachment. `prepare` and `reconcile` drop it and continue. They do not insert it into `persistent`, `retired_attachments`, `provisional_attachments`, or `image_cleanup`. The known subset is the only set that readopts a retired entry and the only set that removes a provisional mark or an `image_cleanup` intent. An id that is present only in `image_cleanup` stays there. An id in `retired_attachments` is known: naming it readopts that entry and cancels its cleanup intent, including when the same list also contains unknown ids. `PathAuthority::open` restores `image_cleanup` and starts with an empty `retired_attachments`, so a retired entry exists only in the process that retired it.

`prepare` of a set whose only unknown members are dropped is a successful no-op when the remaining known set also changes nothing. `reconcile` with `Some(ids)` uses the known subset as the retained set. A `Some` that becomes empty after the drop is an empty retained snapshot, not `None`: startup reconcile retires omitted loaded attachments under the rules already in the function, including when every supplied id was unknown. `None` stays abandon-only.

This is what stops a save from naming a capability that does not exist. The renderer may keep the stale string in its owner record. That string is not a registry entry. Prepare of a retired in-memory id still readopts that entry and cancels its cleanup before the renderer write, which is the `d-20260906-10` ordering. An unknown id has no retired entry to readopt. New ids are UUID v4 and the existing mint skips ids already in the registry maps, so the dangling string is not reissued as a new capability.

### O2. Known non-attachments still fail closed

A retained id that is present and is not an engine attachment still returns `InvalidInput` for the whole action and mutates nothing, including when the same list also contains live attachment ids and unknown ids. The check stays before any candidate is committed. Abandoned ids keep their current type check.

Abandoned ids stay capped at `authority_id_input_limit()` with no added headroom. `startup && retained.is_none()` stays `ResourceLimit`.

Rename `MAX_STARTUP_OWNER_UNKNOWN_IDS` to `MAX_OWNER_UNKNOWN_IDS`. The value stays `16 * MAX_AUTHORITY_IDS`. The comment states that this headroom is the stale-renderer allowance on a raw retained-id list for startup path-owner reconciliation and for this attachment action. Known attachment ids are a subset of maps the registry limit already bounds. No second cap on the known subset.

### O4. Live and retired attachments stay on the current transaction

Classification does not change prepare's refusal to retire omitted ids, reconcile's retirement rules, session protection, provisional marking, readopt of retired entries, durability, or the sealed-attachment `Conflict` that already returns before this logic. A live attachment id, including one marked provisional because issuance inserted it into `persistent` first, remains known and is still retained when the caller names it.

### O5. Renderer and IPC stay

No edit to `engineOwnerStorage.ts`, `pathOwners.ts`, `main.rs`, or `src/bindings/generated.ts`. Prepare success still means the renderer may `setItem` the owner record, stale string included. ## Approach

### O1. Unknown retained ids are ignored

An id absent from both `persistent` and `retired_attachments` is not a retained attachment. `prepare` and `reconcile` drop it and continue. They do not insert it into `persistent`, `retired_attachments`, `provisional_attachments`, or `image_cleanup`. The known subset is the only set that readopts a retired entry and the only set that removes a provisional mark or an `image_cleanup` intent. An id that is present only in `image_cleanup` stays there. An id in `retired_attachments` is known: naming it readopts that entry and cancels its cleanup intent, including when the same list also contains unknown ids. `PathAuthority::open` restores `image_cleanup` and starts with an empty `retired_attachments`, so a retired entry exists only in the process that retired it.

`prepare` of a set whose only unknown members are dropped is a successful no-op when the remaining known set also changes nothing. `reconcile` with `Some(ids)` uses the known subset as the retained set. A `Some` that becomes empty after the drop is an empty retained snapshot, not `None`: startup reconcile retires omitted loaded attachments under the rules already in the function, including when every supplied id was unknown. `None` stays abandon-only.

This is what stops a save from naming a capability that does not exist. The renderer may keep the stale string in its owner record. That string is not a registry entry. Prepare of a retired in-memory id still readopts that entry and cancels its cleanup before the renderer write, which is the `d-20260906-10` ordering. An unknown id has no retired entry to readopt. New ids are UUID v4 and the existing mint skips ids already in the registry maps, so the dangling string is not reissued as a new capability.

### O2. Known non-attachments still fail closed

A retained id that is present and is not an engine attachment still returns `InvalidInput` for the whole action and mutates nothing, including when the same list also contains live attachment ids and unknown ids. The check stays before any candidate is committed. Abandoned ids keep their current type check.

### O3. Raw caps

The retained-id raw `Vec` length is refused with `ResourceLimit` when it exceeds `authority_id_input_limit().saturating_add(MAX_OWNER_UNKNOWN_IDS)`, before classification. Abandoned ids stay capped at `authority_id_input_limit()` with no added headroom. `startup && retained.is_none()` stays `ResourceLimit`.

Rename `MAX_STARTUP_OWNER_UNKNOWN_IDS` to `MAX_OWNER_UNKNOWN_IDS`. The value stays `16 * MAX_AUTHORITY_IDS`. The comment states that this headroom is the stale-renderer allowance on a raw retained-id list for startup path-owner reconciliation and for this attachment action. Update every reference in this module, including `reconcile_startup_owners` and the tests that name the old constant. Do not change that function's filtering or its arithmetic. Do not edit `tasks/decisions.md` or `tasks/findings.md`. `d-20261008-02` keeps the historical constant name.

Known attachment ids are a subset of maps the registry limit already bounds. No second cap on the known subset.

### O4. Live and retired attachments stay on the current transaction

Classification does not change prepare's refusal to retire omitted ids, reconcile's retirement rules, session protection, provisional marking, readopt of retired entries, durability, or the sealed-attachment `Conflict` that already returns before this logic. A live attachment id, including one marked provisional because issuance inserted it into `persistent` first, remains known and is still retained when the caller names it.

### O5. Renderer and IPC stay

No edit to `engineOwnerStorage.ts`, `pathOwners.ts`, `main.rs`, or `src/bindings/generated.ts`. Prepare success still means the renderer may `setItem` the owner record, stale string included. Startup reconcile `Ok` is what lets the existing command reach `cleanup_engine_images`. Shutdown cleanup stays as it is.

### O6. Proof

Update the two existing tests named in the premises, and add the tests in Phase 1. Refusal cases still compare registry bytes and the persistent, provisional, retired, and image-cleanup maps to the pre-call snapshot.

## Decisions and trade-offs

### Decided autonomously

**D1. Native discard, not a renderer prune.** Question: which side owns a stale attachment id, and what stops a save from durably naming a capability that does not exist? Chosen: native `prepare` and `reconcile` drop unknown ids under O1–O3; the IPC type and the renderer documents stay. Rejected: a typed per-id result and a renderer rewrite that strips those ids out of engine records before `setItem`. That changes the Specta contract and deletes a user's image or resource reference from the saved engine. `d-20261008-02` already chose native discard, an unchanged IPC type, and no renderer truncation for the same stale-renderer-id class. Rejected: keeping today's `InvalidInput`, which is the defect. Reason: `d-20260906-10` protects a durable owner from naming a registry cleanup intent. An id in `retired_attachments` is that in-process entry and is still readopted before the renderer write. An id in neither `persistent` nor `retired_attachments` is not readopted; when `image_cleanup` already holds that id, the drop leaves the intent in place and does not insert the id. Reversal path: add an explicit unknown-id list to the command and prune those ids from owner documents before `setItem`, with the same prepare-before-write proof and with retired in-memory ids still readopted rather than pruned. An id in `retired_attachments` is known: naming it readopts that entry and cancels its cleanup intent, including when the same list also contains unknown ids. `PathAuthority::open` restores `image_cleanup` and starts with an empty `retired_attachments`, so a retired entry exists only in the process that retired it.

`prepare` of a set whose only unknown members are dropped is a successful no-op when the remaining known set also changes nothing. `reconcile` with `Some(ids)` uses the known subset as the retained set. A `Some` that becomes empty after the drop is an empty retained snapshot, not `None`: startup reconcile retires omitted loaded attachments under the rules already in the function, including when every supplied id was unknown. `None` stays abandon-only.

This is what stops a save from naming a capability that does not exist. The renderer may keep the stale string in its owner record. That string is not a registry entry. Prepare of a retired in-memory id still readopts that entry and cancels its cleanup before the renderer write, which is the `d-20260906-10` ordering. An unknown id has no retired entry to readopt. New ids are UUID v4 and the existing mint skips ids already in the registry maps, so the dangling string is not reissued as a new capability.

## Decisions and trade-offs

### Decided autonomously

**D1. Native discard, not a renderer prune.** Question: which side owns a stale attachment id, and what stops a save from durably naming a capability that does not exist? Chosen: native `prepare` and `reconcile` drop unknown ids under O1–O3; the IPC type and the renderer documents stay. Rejected: a typed per-id result and a renderer rewrite that strips those ids out of engine records before `setItem`. Rejected: keeping today's `InvalidInput`, which is the defect. Reason: `d-20260906-10` protects a durable owner from naming a registry cleanup intent.
