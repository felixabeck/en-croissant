## Goal

On Windows, the database carrier, the database identity probe, database deletion, search-index
loading and promotion, and puzzle-database open and delete work through the already-ported
descriptor-relative primitives, with no pathname-based mutation anywhere. The six commands
`get_db_info`, `delete_database`, `search_position`, `preload_reference_db`, `get_puzzle` and
`delete_puzzle_database` stop refusing off unix, and database/puzzle directory enumeration stops
refusing.

**The slice additionally carries `f-20260916-02` and `f-20260916-03`, and closes them** (R1-16).
`create_database_child` takes a renderer-supplied filename, its caller rejects only `/`, `\` and
emptiness (`main.rs:1058-1060`), and `validate_components` has no Windows branch at all
(`infra/path_authority/mod.rs`, pinned by `check_helper`). Enabling database creation on Windows
therefore puts `a:stream.db3` and a 40 000-character component on a live renderer-driven route into
`open_windows_child`, where the first names an NTFS alternate data stream and the second wraps the
`u16` length cast and opens a different object. Shipping that is the reachable identity break this
slice may not leave behind, so O9 fixes both at the shared gate — which is exactly where
`f-20260916-02`'s own open question asks for the answer.

**What this slice cannot prove, stated once and repeated in the closing note.** No Windows runtime
evidence is obtainable: `rust-windows-test` currently dies with `STATUS_ACCESS_VIOLATION`
(`f-20260917-02`, open, not this slice's job), and this machine has no Windows runtime at all —
`wine` is absent (`which wine wine64` → nothing, measured 2026-09-17). The ceiling is therefore
a Linux test run, a Windows-target `cargo check --all-targets`, a Windows-target
`clippy -D warnings`, the `infra/platform_support.rs` source pins, and — the part that actually
carries weight — **the Linux suite executing the same shared function bodies** wherever the port
shares rather than duplicates. No claim in this plan or its commits says a Windows behaviour was
observed.

## Evidence

Measured against this checkout on 2026-09-17. Every line is `path:line` verified by the
orchestrator, not quoted from a leaf report.

**E1 — SQLite is pathname-bound on unix too.** `DatabaseRepository` builds its pool from
`sqlite_uri(target.path(), …)` (`db/repository.rs:708`) and its read-only probe from the same
(`db/repository.rs:446`). The retained descriptor is never handed to SQLite. So the open question's
premise — "bind SQLite to a retained handle identity" — has an answer that is already the unix
answer: **the identity guarantee comes from `DatabaseFileTarget::open_current`
(`infra/path_authority/mod.rs:509-546`) re-verifying parent identity, leaf identity and regular-file
type around every probe, not from the connection.** Windows needs the same re-verification, not a
descriptor-bound SQLite.

**E2 — `sqlite_uri` is unix-shaped and is the real porting item.**
`db/repository.rs:1061` refuses any path not starting with `/`
(`"SQLite database path must be absolute"`) and percent-encodes everything but
`[A-Za-z0-9-._~/]`. A Windows path (`C:\…`, and after canonicalization the verbatim
`\\?\C:\…`) is refused by that guard today. `SqliteMode::ReadOnly` is itself `#[cfg(unix)]`
(`db/repository.rs`, `enum SqliteMode`), so the read-only probe mode does not exist off unix.

**E3 — the Windows filesystem primitives already exist and already dispatch.** `infra/fs.rs`
carries paired `#[cfg(unix)]` / `#[cfg(windows)]` arms for every primitive this port needs:
`open_verified_parent` (3286/3295), `assert_entry_identity` (3380/3402), `entry_identity_at`
(3412/3430), `open_regular_at` (3480/3512), `create_regular_at` (3524/3546), `rename_entry_at`
(3551/3580), `rename_optional_regular_at` (3599/3631), `remove_entry_at` (3641/3693),
`remove_optional_regular_at` (3703/3720). They were ported by `f-20260914-10` and
`f-20260914-08`.

**E4 — the Windows delete is strictly stronger than the unix one.** `win::remove_entry_at`
(`infra/fs.rs:2862`) opens the exact child relative to the retained parent with `DELETE`, compares
the handle identity to `expected`, and deletes **through that handle** with
`FILE_DISPOSITION_INFORMATION_EX` (`FILE_DISPOSITION_DELETE | POSIX_SEMANTICS |
IGNORE_READONLY_ATTRIBUTE`, `infra/fs.rs:2329`). There is no second pathname lookup, so the
check-to-unlink window the unix arm documents (`db/mod.rs:2417-2419`,
`infra/path_authority/resolved.rs:522-527`) does not exist on Windows. **This is what keeps the
TOCTOU the finding warns about from coming back:** the pre-slice-1 Windows puzzle delete compared
identity and then deleted by pathname; nothing in this port deletes by pathname.

**E5 — the identity type is already common.** `Identity { a, b }`
(`infra/path_authority/mod.rs:2729`) is `(dev, ino)` on unix and
`(dwVolumeSerialNumber, nFileIndexHigh<<32|nFileIndexLow)` from `GetFileInformationByHandle` on
Windows (`:2912`), exposed through `opened_file_identity` (`:2883`) as `(u64, u64)`. Every
carrier field keeps its meaning unchanged.

**E6 — three structural cfg gates sit above the refusals.** `AcquiredTarget.parent_and_leaf` is
`#[cfg(unix)]` (`infra/path_authority/mod.rs:3130-3135`); `acquire_target`'s proving-descriptor
branch is `#[cfg(unix)]` (`:3168-3197`); `DatabaseFileTarget::assemble` is `#[cfg(unix)]`
(`:480`). No Windows arm of `database_file_target` can exist until these three open.

**E7 — the accounting as it stands today, counted in source, not copied from prose.**
`platform_support.rs` declares **15 body rows** (`:1213-1324`) and **9 guard rows**
(`:1417-1483`) — 24, after `f-20260914-08` retired eleven (`platform_support.rs:4-9`).
`grep -c "unported on this platform"` over `src-tauri/src` gives **22 markers**: 4 owned by
`f-20260914-10` (all in `pgn.rs`), 18 by `f-20260914-11`. **Zero markers are owned by
`f-20260914-09`**, so this port removes no ignore marker; it removes rows.
`d-20260916-06`'s 48/36 predate `f-20260914-08` and are already stale.

**E8 — `capability_directory`'s non-`ReadPgn` refusal is explicitly this finding's.** Its own
doc comment says so: *"`list_database_children_cancellable` is the other caller and belongs to
`f-20260914-09`"* (`infra/path_authority/mod.rs:3431-3434`). The refusal covers `PuzzleRead` and
`DatabaseRead`; the only other caller is the PGN workspace listing, which already works.

**E9 — the repository already answers "SQLite takes a pathname", twice, and neither answer is
platform-specific.** `DatabaseRepository::schema_specific_connection_expected_file_cancellable`
(`db/repository.rs:268-300`) has **no `cfg` at all** and its own doc says why it exists: *"SQLite's
API accepts pathnames, not file descriptors, and resolves `/proc/self/fd` back to a mutable
filename; a private snapshot is therefore the portable way to prevent an A→B→A replacement from
redirecting the connection."* That is the puzzle read path. The game-database path instead uses a
pooled pathname connection sandwiched between two `open_current` probes — `acquire_probed`
(`db/repository.rs:881-905`) probes before `entry.pool.get()` and again after, retiring the pool
entry on conflict. **So the finding's open question (a) has no new mechanism to invent:** the
Windows arm inherits whichever of the two the caller already uses, because both are pathname-based
by design and both are already platform-neutral or become so by O2.

**E10 — the Windows `open_verified_parent` opens the parent WRITABLE** (`infra/fs.rs:2686`, via
`win::open_writable_parent`), while the unix arm opens it read-only. `open_current` is a read
probe and runs for `DatabaseRead`, so sharing it unchanged would require write access to the
parent directory of every database that is merely being read (R1-03, confidence 93, verified).

**E11 — `remove_optional_regular_at` compares no identity on either platform**
(`infra/fs.rs:3703` unix, `:3720` → `win::remove_optional_regular_at`, `:2915`). The unix database
deletion path therefore already observes a sidecar with `statat` and then removes it by name
(`db/mod.rs:2396-2408`), which is a check-to-unlink window on a file the caller has just
identified. Its four callers are `db/mod.rs` (2), `db/search_index.rs` (1) and `file_workspace.rs`
(1) — the first three are in this slice (R1-04).

**E12 — promotion holds a mapping of the file it then deletes.** `promote_legacy_index_sidecar_at`
maps the legacy sidecar into `archive` (`db/search_index.rs:939`) and that binding is still live at
the `remove_optional_regular_at(parent, legacy_leaf)` on `:969`. Windows refuses to delete or
rename over a file with a live section (`ERROR_USER_MAPPED_FILE`), so this is a Windows-only
failure the unix arm never shows (R1-14).

**E13 — the search cache retains mappings.** `cache_loaded_index` inserts `index.clone()` into
`SearchCache` keyed by `SearchIndexIdentity::for_database(database, source)`
(`db/search.rs:358-376`), so a *stale-source* entry for the same database keeps a mapping on the
same preferred sidecar object that promotion or generation then replaces (R1-14).

**E14 — the deletion tail is skipped on a post-delete flush failure.**
`delete_database_blocking` assigns `unlinked` inside the closure and `primary_gone = true` after it
(`db/mod.rs:2347-2351`); an `Err` from `unlink_database_files` therefore returns
`finish_database_deletion(false, 0, Err(…))` and never reaches `search_cache.invalidate_database`
(`:2354`) or the registry removal (`:2356-2362`). On unix this state cannot arise, because
`unlinkat` does not flush the parent. On Windows `remove_entry_at` deletes and *then* flushes
(`infra/fs.rs:2904-2912`), so it can. `delete_puzzle_database_resolved` has the same shape
(`puzzle.rs:665-701`). (R2-06/R2-12)

**E15 — the cache already has the eviction seam; it is called too late.**
`SearchCache::invalidate_database` (`main.rs:387-399`) canonicalizes and retains-out both the
result cache and the **index** cache for that database. It is called *after* index generation
(`db/mod.rs:990`) and *after* the unlink (`db/mod.rs:2354`). No new method is needed; the calls
have to happen **before** the replacement, which is exactly where a live mapping blocks Windows.
(R2-17/R2-25)

**E16 — `single_leaf` is the last gate, and `validate_components` is not on every route.**
`open_windows_child` gates its name through `single_leaf` (`infra/fs.rs:1534`), and persisted or
dialog-selected paths reach it without passing `validate_components`. A Windows component rule
placed only in `validate_components` therefore does not hold for every caller. Both bodies are
pinned byte-exactly by `check_helper` (`platform_support.rs:1853-1868`). (R2-20)

**E17 — Windows OS error codes are ordinary `i32` and match on Linux.**
`std::io::Error::from_raw_os_error(1224)` constructs `ERROR_USER_MAPPED_FILE` on any platform, and
`raw_os_error()` compares equal there. A classifier written over `io::ErrorKind` plus raw codes is
therefore **cfg-free and unit-testable on Linux**, which is what turns the two Windows-only error
predicates of r2 into executed code. (R2-21)

**E18 — `ERROR_USER_MAPPED_FILE` is already an `Error::Io`, not a `Conflict`.**
`windows_open_status_error` (`infra/path_authority/mod.rs:2926-2947`) maps only
`STATUS_OBJECT_NAME_COLLISION` and `STATUS_SHARING_VIOLATION` to `Error::Conflict`; the not-found
statuses become `Error::Io` with the DOS code, and **everything else** falls through
`RtlNtStatusToDosError` to `Error::Io(<dos code>)`. A mapped-file refusal therefore already arrives
as `Error::Io` carrying raw code 1224, which is exactly the class the search paths need and is not
the class `acquire_probed` consumes. r3 asserted the opposite and invented a remapping for it; the
remapping is withdrawn (R3-02).

**E19 — the unix optional-sidecar removal refuses a non-regular entry, it does not skip it.**
`remove_optional_regular_at` (`infra/fs.rs:3703-3717`) returns `Ok(())` only for `NOENT` and
answers `Error::InvalidInput("workspace sidecar must be a regular file")` for anything that exists
and is not a regular file. `d-20260831-24` makes that deliberate: *"sidecar-only failures stay
`Io`/`InvalidInput` and are retryable"*. So "absent" and "wrong kind" are **different** answers on
the deletion path, and r3's single "treat as absent" rule was wrong there (R3-01).

## Approach

### O0 — the un-gating is transitive, and the cross-target check is its oracle

Every obligation below that removes a `#[cfg(unix)]` from a function also removes it from that
function's transitive callees, imports and types, or it does not compile for the Windows target.
Round 1 named these and the orchestrator verified them; a phase that finds more extends this list
rather than working around it:

* `database_file_target` → `is_database_file_operation`, `ResolvedPath::create_database_file`,
  `cleanup_created_database_child` (`infra/path_authority/mod.rs`).
* `puzzle_database_target` → the `canonical_binding` import in `resolved.rs`.
* `identity_from_probe` → `probe_schema_and_revision`, `probe_schema`, `read_revision`,
  `tombstone_conflict` (`db/repository.rs:359-470`).
* `unlink_database_files` → `legacy_sidecar_matches`, which is in **`db/mod.rs:2436`**, not
  `db/search_index.rs` — r2 named the wrong file and therefore gave the wrong phase its ownership
  (R2-05). Plus the `remove_optional_regular_at` import.
* `identity_from_probe` → also `crate::error::map_sqlite_establish` (`error.rs:332`), which r2
  omitted (R2-11).
* `AcquiredTarget.parent_and_leaf` → the Windows `create_pgn_export_destination`
  (`infra/path_authority/mod.rs:3544-3551`) constructs `AcquiredTarget` **without** that field, so
  un-gating it breaks a function this slice does not otherwise touch; it gets the field (R2-02).
* `open_valid_preferred` / promotion → `MmapSearchIndex::open_file_inner`, `open_file`, the
  `source` field and `source()`, and the archive-parsing helpers, all `#[cfg(any(test, unix))]`
  (`db/search_index.rs:569-615, 766-769`).

**The oracle is `cargo check --target x86_64-pc-windows-gnu --all-targets`**, which resolves the
whole closure and is a phase proof, not an afterthought. A helper whose body is POSIX-only gets a
Windows arm under the sharing rule of O2; a helper whose body is neutral simply loses its gate.

### O1 — the carrier's Windows arm, and what its `path()` means

`acquire_target` gains a Windows branch that produces `parent_and_leaf` exactly as unix does:
`canonical_binding(path)` then `infra::fs::open_verified_parent(&canonical, (id.a, id.b),
target_is_dir)` — subject to O1b. `AcquiredTarget.parent_and_leaf` and
`DatabaseFileTarget::assemble` lose their `#[cfg(unix)]`; `database_file_target`'s
`#[cfg(not(unix))]` counterpart is deleted and the remaining body loses its `#[cfg(unix)]`.
`canonical_binding` (`infra/path_authority/mod.rs:1602`) is already platform-neutral and
canonicalizes only the parent (`d-20260912-04`), which stays true.

**Contract this obligation publishes, consumed by O3:** on Windows, `DatabaseFileTarget::path()`
is `std::fs::canonicalize` of the parent plus the unchanged leaf — that is, a **verbatim** path
(`\\?\C:\…` for a drive, `\\?\UNC\server\share\…` for a share). O3 handles both shapes and
neither assumes nor forbids the prefix.

`create_database_child` (`:5296`) loses its refusal the same way; its unix body is already written
in `create_regular_at` / `remove_entry_at`, both of which dispatch (E3). O9 is its precondition.

### O1b — a read path must not demand a writable parent, anywhere on it

Windows `open_verified_parent` opens the parent writable (E10). Round 2 showed that fixing
`open_current` alone is not enough: `database_file_target` reaches the same helper through
`acquire_target(&path, AcquireShape::File)` (`mod.rs:5413`), so a `DatabaseRead` acquisition would
already have failed under a read-only parent (R2-03, witnessed by four lenses).

The access choice is therefore made **once, as a parameter, not as a twin helper** (R2-24):
`infra::fs::open_verified_parent` gains a parent-access argument, its unix arm ignores it (it
already opens read-only), and its Windows arm passes the corresponding mask.

**The rule is one predicate, not a list of operations** (R7-02, R7-06 — r7 enumerated
`DatabaseRead`/`PuzzleRead`/`OpeningBookRead` and the enumeration was wrong twice in one round,
missing `EngineResourceRead` and `ImageRead`). **A parent is opened readable when no operation in
the set needs a writable parent, and writable otherwise** — and the predicate is
`d-20260916-04`'s own `parent_writable`, that is
`is_write_operation(op) || allows_missing_leaf(op)`, not `is_write_operation` alone (R8-01,
confidence 99). r8 used the narrower one and would have given `DownloadFile`, `DownloadArchive`
and `DatabaseCreate` a read-only retained parent: none of the three is a write operation
(`mod.rs:3285-3297`), and all three are exactly the missing-leaf operations that must *create* a
child in that parent and then flush it (`resolved.rs:869-895`). That is the defect
`d-20260916-04` was recorded to prevent, one level up, and reusing its predicate means this plan
cannot drift from it. There is no list to keep in sync.

**It applies to every shape that opens a parent on Windows, not only to `File`** (R7-02,
confidence 97-98). This matters because O1 *adds* the parent open to the Windows arm: today the
non-unix `acquire_target` returns without one (`mod.rs:3194`), so a `Dialog` grant for
`ImageRead`, `OpeningBookRead` or `EngineResourceRead` currently needs no parent access at all.
Applying "everything but `File` stays writable", as r7 did, would therefore have *introduced* a
writable-parent requirement for read-only dialog grants that do not have one now — a regression
this slice would have caused in three other findings' territory. The access travels with the shape
for `File`, `Dialog` and `Root` alike.

**The type enumerates the call sites; prose does not.** `AcquireShape` carries
`ParentAccess`, so every construction site must state it and the compiler lists them rather than a
reviewer having to. r7 also asserted that `promote_dialog` has no operation; it does
(`mod.rs:4121-4127`), and it derives its access from it like every other site. `registration_target`
genuinely does not (`:4289-4303`, its caller drops the vector at `:4374-4376`), so the vector is
threaded through to it and the same predicate is applied to the whole set. `open_current` asks for
readable.

Changing that signature touches all ten existing `open_verified_parent` call sites — in
`infra/fs.rs`, `infra/path_authority/mod.rs` and **`db/search_index.rs` (`:895`, `:1613`)**. Phase A
updates every one of them mechanically in its own commit, because a signature change owns its call
sites; otherwise Phase A's own `cargo test` could not be green and the phase would not be
independently committable (R4-03, confidence 99).

### O2 — `open_current` becomes one shared body, and the error classifier is cfg-free

Its unix body (`:509-546`) is already written entirely in `infra::fs` wrappers that dispatch (E3);
the only unix-specific part is `map_probe_error`, which matches `rustix::io::Errno::LOOP`/`NOTDIR`.
The function loses its `#[cfg(unix)]` and its `#[cfg(not(unix))]` counterpart.

**The classifier stops being a Windows-only arm** (R2-21, E17). `map_probe_error` becomes one
cfg-free function over `&Error`, matching `io::ErrorKind::NotFound`, the unix `LOOP`/`NOTDIR` raw
codes **and** the Windows raw codes for the same conditions, plus the `Error::InvalidInput`
messages the Windows wrappers produce for a reparse point or a wrong object kind. Because Windows
error codes are ordinary integers, every arm is unit-testable on Linux with
`io::Error::from_raw_os_error`, so this predicate is executed rather than merely pinned.

**Error-class parity is part of the contract** (R1-13): the Windows wrappers report a reparse point
or a substituted directory as `Error::InvalidInput`, while the unix arm maps the equivalent races to
`Error::Conflict`. The classifier maps both to the same `CONFLICT` text, because `acquire_probed`
retires a pool entry on `Conflict` and propagates anything else — a class change would silently turn
a retryable substitution into a hard failure. **One classifier, three call-site mappings** (R2-27, R3-01, R3-09). The predicate answers a
*class* — `NotFound`, `WrongKind` (a reparse point, a directory, or any other non-regular object),
`Malformed` (`io::ErrorKind::InvalidData`, which is what `MmapSearchIndex::open_file_cancellable`
returns for a corrupt archive — R4-05), `MappedFile`, or `Other` — and each caller chooses what
that class means, because they genuinely
differ and r3 was wrong to give them one rule:

| caller | `NotFound` | `WrongKind` | `Malformed` | `MappedFile` | `Other` |
|---|---|---|---|---|---|
| `open_current` probe | `Conflict` | `Conflict` | propagate | propagate | propagate |
| index loader and promotion probe | `Ok(None)` / `Ok(false)` | `Ok(None)` / `Ok(false)` | `Ok(None)` / `Ok(false)` | propagate as `Error::Io` | propagate |
| deletion's optional sidecar | absent, count nothing | **`InvalidInput`, retryable** | propagate | propagate | propagate |

The `Malformed` column is the existing unix behaviour of both loader arms, which map
`InvalidData` to "no index" so a corrupt sidecar is regenerated rather than failing the search; r4
had no such class and would have propagated it (R4-05).

The deletion row is `d-20260831-24`'s own rule and the unix arm's measured behaviour (E19): a
sidecar that exists but is not a regular file must not be silently skipped while the primary is
deleted and the registry cleaned. The loader row is the unix arm's behaviour too, where a symlinked
sidecar reaches `openat(NOFOLLOW)` and comes back `LOOP` ⇒ "no index"; `WrongKind` additionally
covers a **directory** named as the sidecar, which unix simply does not find as a regular file.
**On Windows that classification needs an explicit probe, not a raw error code** (R8-02, confidence
96): `open_regular_at` opens with `FILE_NON_DIRECTORY_FILE`, so a directory at that name fails
inside `NtCreateFile` and `RtlNtStatusToDosError` collapses `STATUS_FILE_IS_A_DIRECTORY` onto
`ERROR_ACCESS_DENIED`, which is indistinguishable from a real permission failure. The classifier
therefore answers `WrongKind` for a directory **only** after an explicit
`entry_identity_at(parent, leaf, true)` succeeds at the same name; if that probe also fails, the
original error propagates as `Other`. **That means the classifier is not a pure `fn(&Error)`**
(R9-03, confidence 95): it takes the error *and* the parent descriptor and leaf it came from, so it
can ask the follow-up question. The pure part — the raw-code-to-class mapping — stays a separate
cfg-free function the table test drives; the context-taking wrapper is what callers use, and the
directory probe is the only thing it adds. A permission failure stays a permission failure, and a
directory is recognised for what it is.

**This is the plan's sharing rule, and it applies to every item below:** *share one body wherever
the unix arm is already expressed in dispatching `infra::fs` wrappers; add a separate Windows arm
only where the unix arm calls a POSIX-only syscall directly; and make every platform* policy *(a
URI shape, a component rule, an error class) a cfg-free function so Linux executes it.*

**What that leaves unexecuted, stated plainly** (R3-03 — r3 claimed nothing was left, and that was
false). Exactly one Windows-only *body* remains in this slice: `acquire_target`'s Windows branch
(O1), which is three statements — `canonical_binding`, `open_verified_parent`, and the struct
literal — each of which is separately exercised on Linux through its unix twin, but whose
composition is not. It is held by an exact source pin asserting those three statements in that
order, and the pin is named in O10 as a pin, not as behaviour. Every other platform difference in
this slice is either a dispatching `infra::fs` primitive that predates it or a cfg-free policy
function Linux runs.

### O3 — the SQLite URI, as a pure function tested on Linux

`sqlite_uri` (`db/repository.rs:1061`) delegates to a **cfg-free** `sqlite_uri_for(path, mode,
style)`, where `style` is `PathStyle::Posix | PathStyle::Windows`; the production `sqlite_uri`
selects the style by `cfg` at that one line, and a source pin asserts that selection so a Windows
wrapper cannot silently keep the POSIX rule (R2-21). Linux tests call `sqlite_uri_for(…,
PathStyle::Windows)` directly:

* verbatim drive `\\?\C:\dir\db.db3` → `file:///C:/dir/db.db3`
* verbatim UNC `\\?\UNC\server\share\db.db3` → `file://server/share/db.db3` (R1-07: the `UNC\`
  segment becomes the URI authority; stripping only `\\?\` would leave the literal `UNC\server\…`)
* plain `C:\dir\db.db3` → `file:///C:/dir/db.db3`; plain UNC `\\server\share\db.db3` →
  `file://server/share/db.db3`
* a relative path, a drive-less path, and a drive-relative `C:dir\db.db3` are refused with the
  existing `"SQLite database path must be absolute"` text
* percent-encoding keeps the existing allowlist; `:` stays literal only in the drive position
* **every component of the path it emits is checked by `windows_component_refusal`, ancestors
  included** (R5-03, tauri-security 92 / correctness 89). O9's gate sees renderer-supplied
  components and final leaves; it never sees the *ancestors* of a canonical path, and this
  conversion is where they stop being verbatim. A root or ancestor named `Data.` or `Data ` would
  otherwise be verified as `\\?\C:\Data.\games.db3` by the authority while SQLite opened the
  normalised `C:\Data\games.db3` sibling, which is R4-01's defect one level up. The rule lives
  here because the conversion is what creates the exposure: a path the authority resolved
  verbatim is refused for the URI rather than silently normalised.
* a non-verbatim result longer than 259 characters is refused with its **own** message naming the
  Windows path-length limit, so the user sees the real reason instead of an opaque SQLite failure
  (R2-16 — the workspace picker accepts arbitrary user-selected folders at `main.rs:904-945`, so
  this is reachable and the earlier revision was wrong to call it a shape the product never
  generates)

`SqliteMode::ReadOnly` loses its `#[cfg(unix)]`. The round-trip `establish` tests stay unix-only
because they need a real file; the shape tests do not.

### O4 — identity probing and deletion

`identity_from_probe` (`db/repository.rs:398`) loses its refusal and its `#[cfg(unix)]`, together
with `probe_schema_and_revision`, `probe_schema`, `read_revision`, `tombstone_conflict` **and
`crate::error::map_sqlite_establish` (`error.rs:332`), which round 2 found still gated** (R2-11).
Its body is `open_current` plus SQLite probes (O2, E9), with no POSIX call of its own.

`unlink_database_files` (`db/mod.rs:2383`) keeps **one** body, with only the primitive calls
dispatching:

* **Sidecars go through the identity-checked removal** (R1-04, E11): `entry_identity_at(parent,
  leaf, false)`, and on `Ok(identity)` a `remove_entry_at(parent, leaf, identity, false)`, which is
  the repository's own identity-checked removal. **This changes the unix path too, and that is a
  deliberate, recorded scope decision rather than an accident** (R12-01): unix currently uses
  `remove_optional_regular_at` with no identity recheck and no parent sync
  (`infra/fs.rs:3703-3717`), and moving it to `remove_entry_at` adds both. It is adopted because
  acceptance criterion 2 — every namespace mutation identity-checked — would otherwise be false for
  half the operations this slice enables, because the files are already open in this run (rule 4b),
  and because the Windows primitive makes the stronger form the cheaper one. The cost is named in
  trade-off 5 and the new unix behaviour is covered by O10 items 4 and 6. On Windows it re-opens
  the named child, compares the handle identity and deletes **through that handle**, closing the
  window entirely; on unix it
  narrows it to `remove_entry_at`'s own residual — the final `unlinkat` is by name, which
  `f-20260830-09` records as unfixable on Linux and blocks on
  `inode-conditional-unlink-unavailable`. The claim is "the same identity discipline the rest of the
  repository uses", never "no window on unix". **No separate `assert_entry_identity` precedes it**:
  `remove_entry_at` already performs exactly that check on both arms (`infra/fs.rs:2868`, `:3649`),
  and adding one would be a second open for nothing (R2-22).
* **Absence and a lost race are benign; a wrong object kind is not** (R1-11, R2-15, R3-01, E19).
  The probe's not-found *and* the removal's not-found both mean "absent, count nothing", so a
  database with no sidecar deletes normally and a sidecar that vanishes between the two calls does
  not abort the deletion of the primary. A sidecar that **exists and is not a regular file**
  answers `InvalidInput` and stops the deletion, which is the unix arm's measured behaviour and
  `d-20260831-24`'s explicit rule that sidecar-only failures stay retryable. r3 collapsed these two
  into "absent" and would have deleted the primary, cleaned the registry and returned success while
  leaving the object behind.
* **A malformed legacy sidecar is "not ours", and that is the one exception to the deletion row**
  (R5-06a, correctness 91). O2's table says deletion propagates `Malformed`, but the *provenance*
  question is asked by `legacy_sidecar_matches`, whose whole job is to answer "is this our
  sidecar" — and a corrupt archive is not ours by any reading. It therefore answers "no match" for
  `InvalidData` and the file is left alone, while an I/O or permission failure still propagates
  (below). The exception is stated here, and O10 item 5 covers it, because r5 had the table and the
  provenance rule disagreeing silently.
* **`legacy_sidecar_matches` is ported and its provenance identity is carried into the removal**
  (R2-19, tauri-security 99). Today it returns `bool` (`db/mod.rs:2436`), so the sidecar is
  re-opened afterwards and a replacement between the two opens would be deleted on the strength of
  a provenance check that was performed on a different object. It returns the verified identity
  instead, and that identity — not a fresh `entry_identity_at` — is what `remove_entry_at`
  receives. **Its `is_ok_and` also stops swallowing every I/O and permission failure as "does not
  match"** (R2-13): only `InvalidData` means "not our sidecar"; an I/O or permission error
  propagates, so deletion no longer succeeds while silently leaving an unreadable sidecar behind.
* **The primary** uses `remove_entry_at(parent, leaf, target.identity(), false)`, which folds the
  regular-file check, the identity check and the delete into one handle operation (E4) and keeps the
  `"database changed before deletion"` conflict text.
* **A sidecar's durability uncertainty must not be reported before the primary is gone**
  (R7-01, confidence 96). `remove_entry_at` can delete a *sidecar* and then fail the parent flush,
  and the durability category is what the renderer reads as "applied despite error" and refreshes
  on — which would tell the user the database was removed while it is still there. A durability
  uncertainty raised by a sidecar removal is therefore **retained, not returned**: the deletion
  proceeds to the primary, and the retained uncertainty is folded into the outcome only once
  `primary_gone` is true. If the primary removal then fails outright, the sidecar's uncertainty is
  logged and the primary's own error is what the caller sees, because nothing was applied.
* **Two sidecar failures in sequence have a stated precedence** (R12-02). The preferred and legacy
  sidecars are handled one after the other (`db/mod.rs:2394-2408`), so the preferred removal can
  report `CommittedDurabilityUncertain` and the legacy step can then fail outright. The uncertainty
  is **retained** (it is not returned yet — see the rule above), and a subsequent `InvalidInput`
  from a wrong-kind legacy sidecar, or any other hard failure, **stops the deletion and is what the
  caller sees**, with the retained uncertainty logged: nothing was applied to the primary, so
  nothing may report the applied-despite-error category. If both sidecar steps merely report
  uncertainty, the uncertainties collapse into one and follow the primary rule below. O10 item 6
  carries this as its fourth injection case.
* **A completed delete with an uncertain flush must not skip the tail** (R1-12, R2-06, E14).
  `unlink_database_files` returns the count **and** an optional durability error rather than losing
  the count inside an `Err`; `delete_database_blocking` records `primary_gone` and `unlinked` from
  that value, runs `search_cache.invalidate_database` and the registry removal as it does on
  success, and only then folds the durability error in through the existing
  `finish_database_deletion` arm. `delete_puzzle_database_resolved` (`puzzle.rs:665-701`) takes the
  same treatment, and **the precedence between the two possible tail failures is stated rather than
  left to evaluation order** (R5-06b, corrected in r7 by R6-01): a deletion can end with both a
  durability uncertainty and a registry-cleanup failure. **`CommittedDurabilityUncertain` is
  returned and the registry-cleanup failure is logged.** r6 said the cleanup failure was "folded in
  through `Error::OperationAndCleanup`", and five lenses showed that inverts the outcome: that
  variant carries category `OperationAndCleanup` (`error.rs:298`), which `src/platform/errors.ts:46`
  maps to `unexpected`, so `runDestructiveWithRefresh` would **not** refresh — the user would see a
  generic error for a database that is in fact gone. The durability category is the only one that
  carries "applied despite error" to the renderer, so it is the one returned; the cleanup failure
  is not silently dropped but it is not allowed to change the category. O10 item 6 asserts exactly
  that: the returned error is the durability one, and the cleanup failure appears in the log. `delete_puzzle_database` returns the durability error as a value rather than
  through `?`, `delete_puzzle_database_resolved` runs its cache and registry cleanup
  (`puzzle.rs:692-713`) and only then returns it, so the puzzle registry and cache cannot retain an
  entry whose file is gone (R3-04). Its own regression test is O10 item 9 — r3 specified the
  database tail only, and "the same treatment" is not a specification (R3-04, tests 97).

`ResolvedPath::delete_puzzle_database` (`resolved.rs:529`) takes the identical primitive treatment,
keeping `"puzzle database changed before deletion"`. `ResolvedPath::puzzle_database_target`
(`:504`) loses its refusal and its cfg.

`puzzle.rs`'s two `off_unix_refusal` guards — `get_puzzle` (`:292`) and `delete_puzzle_database`
(`:618`) — are deleted, and their two guard rows with them.

### O5 — the search index

`open_valid_preferred` (`db/search.rs:315`) becomes **one body** whose "missing, reparse, malformed
or stale ⇒ `Ok(None)`" decision is the cfg-free classifier of O2, so the whole fallback contract is
preserved and executed on Linux: an absent, symlinked, malformed or stale-source sidecar is "no
index", never an error, and an ordinary search falls through to promotion and generation exactly as
on unix (R1-11, R2-08).

`promote_legacy_index_sidecar_at` (`db/search_index.rs:909`) keeps one body with dispatching
primitives:

* the preferred-exists probe is `entry_identity_at(parent, preferred_leaf, false)`, and **anything
  that exists — in any form — means `return Ok(false)`**; only not-found continues (R7-04,
  confidence 93/98). This is the unix arm's behaviour: its `statat` returns `Ok` for a symlink or a
  directory at that name and it stops (`db/search_index.rs:921-925`). r7 classified wrong-kind as
  "absent, continue" here, which would have let promotion replace a symlinked or directory
  preferred entry **and then delete the legacy archive** — the one irreversible step in this
  function. The probe therefore does not share the loader's row: "exists" and "is a regular file"
  are different questions, and promotion asks the first.
* the legacy open is `open_regular_at`, with the same classification ⇒ `Ok(false)`
* **`legacy_file_identity_at` is deleted** and its call sites use `assert_entry_identity`, which is
  the same check and already dispatches (R1-15); the removal itself passes the identity to
  `remove_entry_at` and adds no extra assertion (R2-22)
* publication stays `atomic_replace_at`; `d-20260831-23` stands, so promotion still returns
  `CommittedDurabilityUncertain` rather than unlinking the last durable copy
* **the legacy mapping is dropped before the legacy file is removed** (R1-14, E12). `archive` is
  used only for its `source()` comparison, so it is dropped as soon as that comparison is made.

`MmapSearchIndex::open_file_cancellable`, `open_file_inner`, `open_file`, the `source` field,
`source()` and the archive-parsing helpers lose their `#[cfg(any(test, unix))]` / `#[cfg(unix)]`
gates, and so does the loader's `#[cfg(unix)]` promotion call site (`db/search.rs:250`) and its
imports (`:26`) (O0).

**Eviction before replacement, through the seam that already exists** (R1-14, R2-17, R2-25, E15).
`SearchCache::invalidate_database` already evicts the index cache for a database; no new method is
added. It is called **before** each of the three replacements, in addition to wherever it is called
today: before promotion's `atomic_replace_at`, before index generation's `write_entries_to_at`
(`db/mod.rs:982`, which is why Phase D owns `db/mod.rs` as well), and before
`unlink_database_files` in `delete_database_blocking` (`db/mod.rs:2349`). Without the third, a
cached mapping keeps the sidecar mapped and Windows refuses its deletion — the case round 2 found
the r2 text had missed.

**Residual, named rather than hidden:** a *concurrent reader* holding its own clone of a mapping is
not reachable by eviction. On Windows the replacement then fails — and **it already fails in the
right class, so no remapping is added** (R3-02, E18): `windows_open_status_error` sends everything
outside the two collision/sharing statuses through `RtlNtStatusToDosError`, so a mapped-file
refusal arrives as `Error::Io` carrying raw code 1224 with the OS's own description. r3 asserted
that the mapper returned `Conflict` here and invented a remapping on that basis; both the
assertion and the remapping are withdrawn. What is added instead is an **assertion**: the
classifier of O2 answers `MappedFile` for raw code 1224, every caller propagates it, and no caller
folds it into "absent" or into `Conflict` — because "absent" would retry the same blocked mutation
for ever and `Conflict` is what `acquire_probed` consumes as "the database was substituted"
(R3-08, O10 item 8). Nothing is corrupted and nothing is silently skipped. Removing the class
entirely needs a reader/writer protocol over the sidecar, which is filed as its own finding
(`push-review-policy` §4, open-design-question `Defer`).

### O8 — what replaces a deleted row

A deleted row deletes its regression protection, so each phase adds, in the same commit, one
**positive, cfg-free** assertion per ported function: exactly one ungated definition, no

### O9 — the component gate this slice may not leave open

The Windows component rules become **one cfg-free predicate** —
`windows_component_refusal(name) -> Option<&'static str>` — which is *called* on Windows and
*compiled and unit-tested everywhere* (R2-04, R2-21: a `#[cfg(windows)]` validation branch cannot
be asserted by a Linux test, which is what made the r2 wording unprovable). It is routed through
**both** gates, because `single_leaf` is the last one every Windows caller passes and
`validate_components` is not on every route (R2-20, E16): `validate_components` calls it for each
component, `single_leaf` calls it for the leaf, and neither restates the rule (R2-23). Both pinned
bodies change, so the two `check_helper` pin strings are updated in the same commit — that is the
designed behaviour of the pin (R3 in Risks).

The predicate rejects, on Windows:

* a component containing `:`, `/`, `\\` or NUL — `:` is what names an NTFS alternate data stream,
  so `existing.db3:stream` stops being a valid leaf before `resolve_windows` or `open_windows_child`
  can open it (`f-20260916-02`)
* a component longer than **255 UTF-16 units**, the NTFS/ReFS maximum component length. This is
  the *generic* gate and it applies to every component, derived sidecar leaves included.
* a component with a **trailing dot or trailing space** (R4-01). Win32 strips both when it resolves
  a non-verbatim path, so the authority can verify `foo.db3.` while SQLite — which O3 deliberately
  hands a non-verbatim path — opens `foo.db3`, an unverified sibling. Like the device-name rule
  below, this exists because O3 gives up verbatim semantics; the two rules are the price of that
  choice and are named as such.

**The database filename is bounded more tightly than a component, and that distinction is the
correction r4 needed** (R4-04, confidence 99). r4 put 250 in the shared predicate, which then
rejected the *derived sidecars* of an accepted 250-unit database name — a 250-unit leaf produces a
255-unit `<leaf>.ecsi` and the shared gate refused it, so search could not load or generate an index
for a database whose name it had just accepted. The shared predicate therefore keeps the real
filesystem limit of 255, and a **separate database-leaf rule** carries the extra bound: a database
filename longer than `255 - len(".ecsi")` = 250 units is refused, with an error naming the sidecar
as the reason.

**That rule belongs to every route by which a database leaf enters the authority, not only to
creation** (R5-01, three witnesses at 97-99). r5 applied it in `create_database_child` alone, so a
database *already on disk* with a 251-255-unit name — enumerated by
`list_database_children_cancellable` and admitted by `register_database_child`
(`mod.rs:5167-5203`) — would be registered happily and then fail deep inside `single_leaf` the
first time its 256-unit `.ecsi` sidecar was probed, promoted or generated. Both entry points
therefore apply the same rule, and both assert it by calling the shared predicate on the two
derived sidecar leaves rather than by repeating the arithmetic. A database in that range is refused
at registration with a message naming the Windows limit, instead of appearing in the list and then
failing every search.

* a component whose stem is a **reserved DOS device name** — `CON`, `PRN`, `AUX`, `NUL`,
  `COM1`-`COM9`, `LPT1`-`LPT9`, **and the superscript aliases `COM¹`/`COM²`/`COM³` and
  `LPT¹`/`LPT²`/`LPT³`** that Windows also reserves (R8-03, confidence 92), case-insensitively,
  with or without an extension (R3-05, confidence 94). Win32 resolves `NUL.db3` to the device, not to a file, and O3 deliberately hands
  SQLite a **non-verbatim** path, which is the form in which that resolution happens. Without this
  rule a renderer-supplied database filename could make the authority verify a regular file while
  SQLite opens a device. The alternative — preserving verbatim semantics through SQLite — was
  rejected in O3 for the URI-parser reason, so the rejection has to live here.

`open_windows_child`'s `u16` length cast additionally gets an explicit bound check
(`f-20260916-03`). Round 2 called that redundant, since `single_leaf` now runs first
(minimalism 96, nit). **Rejected, with reason:** the cast is the literal subject of
`f-20260916-03`, its failure mode is a silent truncation that opens a *different* object with no
error anywhere, and the check is one comparison. A guard whose absence is unobservable is exactly
the kind this repository keeps.

### O10 — the behavioural proof, and what it cannot reach

Round 2's strongest finding was that nothing in r2 would go red if the port were reverted to a stub
(`review-tests`, five blockers); round 3 found four more places where that was still true. Every
item below is a Linux-executing test unless it is explicitly marked a pin.

1. **The URI**, `sqlite_uri_for(…, PathStyle::Windows)` over every case in O3 including the
   path-length refusal and the ancestor rule, plus a pin that production `sqlite_uri` selects the
   style by `cfg`, **and an assertion that `SqliteMode::ReadOnly` emits `?mode=ro` and
   `ReadWrite` `?mode=rw`** — a Windows builder that always emitted `rw` would otherwise pass every
   shape case and the cross-target check while opening databases writable (R6-04d, confidence 90).
2. **The component predicate**, `windows_component_refusal` over `a:stream.db3`, a 251-unit name, a
   250-unit name and its two derived sidecar leaves, `a/b`, `a\\b`, NUL, and each reserved device
   stem with and without an extension (`NUL`, `nul.db3`, `COM1.db3`, `lpt9`), plus a test that both
   `validate_components` and `single_leaf` route through it.
3. **The classifier's mappings**, in two layers (R9-02, R9-03):
   (a) the pure raw-code-to-class function, as a table test over `io::Error::from_raw_os_error`
   values for the Windows not-found, reparse and mapped-file codes and the unix `LOOP`/`NOTDIR`
   codes, **and over the `Error::InvalidInput("reparse points cannot be authorized")` value the
   Windows walk actually emits** (`mod.rs:3038-3042`) — a message case, not a code case, which r10
   specified in O2 and never tested (R10-01, confidence 94) — with each caller's mapping asserted — `Conflict` for the `open_current` probe, absence for
   the loader, and **`InvalidInput` for the deletion sidecar on `WrongKind`**, the row r3 got wrong;
   and (b) **the directory split**, which the table alone cannot reach: with a real **directory** at
   the sidecar name the wrapper answers `WrongKind`, and with an injected permission failure at the
   same name it answers `Other`. On Linux the directory fixture is buildable directly; the Windows
   ambiguity it stands in for is additionally held by a pin that `open_regular_at`'s caller performs
   the `entry_identity_at(..., true)` probe before classifying. Without (b), an implementation that
   mapped `ERROR_ACCESS_DENIED` straight to `WrongKind` would pass everything and silently turn
   every permission failure into "no index".
4. **The captured identity reaches the removal:** replace a sidecar between the identity
   observation and the removal and assert the deletion refuses instead of deleting the replacement;
   and that a sidecar which merely vanished does not stop the primary deletion.
5. **The provenance identity is the one removed:** start with a legacy sidecar that **does**
   match, let `legacy_sidecar_matches` capture its identity, replace the file before the removal,
   and assert the removal refuses. r4's version started from a non-matching sidecar, so no removal
   was ever attempted and both the fixed and the reverted code passed it (R4-07, confidence 99).
   **A promotion-preferred regression** (R8-06, confidence 96): with a **matching** legacy archive
   and a **symlink or directory** at the preferred name, assert that promotion does nothing — the
   preferred entry is untouched and the legacy archive still exists. Reverting R7-04 would
   otherwise replace the preferred entry and delete the only durable copy with no test failing.
   **Two further provenance cases** (R6-04b, confidence 98): a **corrupt** legacy sidecar is left
   untouched and the primary deletion still succeeds, and an **I/O or permission failure** reading
   it propagates instead of being swallowed as "not ours". Without these the malformed/I/O split
   this plan introduced has no anchor at all.
6. **The database durability tail:** inject a post-delete parent-flush failure and assert the cache
   invalidation and the registry removal still ran and that the returned error is the durability
   one, **and the dual-failure case** where the registry cleanup also fails: assert that the
   returned error is `CommittedDurabilityUncertain` — not `OperationAndCleanup`, which would change
   the renderer category and stop the refresh — and that the cleanup failure was logged
   (R5-06b, R6-01, R6-04c), **including the returned error's own type** — a regression that cleaned
   up correctly but returned `PartialRemoval` would otherwise pass (R11-02, confidence 96); the
   puzzle case of item 9 asserts the same. **A third injection point is required** (R8-05, confidence 95): make a
   **sidecar** flush fail *before* the primary is deleted and assert that the call does **not**
   return a durability category at that point — it proceeds to the primary, and only the completed
   primary deletion may report one. r8's item covered the primary only, so reverting R7-01 would
   have stayed green while the renderer refreshed a database that was still there.
7. **Eviction precedes replacement, at all three call sites** (R3-06): seed the index cache for a
   database, then separately run promotion, index generation **and database deletion**, asserting in
   each case that the cache no longer holds the mapping *before* the mutation. The observable hook
   is the repository's existing test-hook style — the mutation's own injector observes the cache
   state at the moment it is entered — so that reverting any one of the three `invalidate_database`
   calls reddens its own test. r3 listed only promotion and generation, and the deletion call site
   was the one round 2 had just added.
8. **The mapped-file class is neither absence nor `Conflict`** (R3-08): assert that raw code 1224
   classifies as `MappedFile`, that the loader propagates it instead of answering "no index", and
   that `open_current` does not turn it into the substitution `Conflict` — **and the same for the
   two remaining callers, promotion and sidecar deletion** (R11-03, confidence 95), which are
   precisely the mutations a live mapping blocks and where answering "absent" would retry the
   blocked operation for ever.
   Item 6's fourth case is the sequential-sidecar precedence of R12-02: a preferred removal that
   reports uncertainty followed by a failing legacy step returns the legacy error, not the
   durability category, and logs the uncertainty — **and asserts that the primary database file is
   still present and that the registry and cache entries for it are unchanged** (R13-01). Without
   that half, an implementation that recorded the legacy failure, went on to unlink the primary and
   then returned the legacy error would pass, which is the opposite of O4's "stops the deletion".
9. **The puzzle durability tail** (R3-04): the same injection as item 6 against
   `delete_puzzle_database_resolved`, asserting the puzzle cache and registry cleanup ran **and
   that the returned error is `CommittedDurabilityUncertain`** (R11-02).
10. **The operation→parent-access rule, at the call sites and not only in the abstract**
    (R3-07, R6-04a, R7-02): a cfg-free test that the access is `Readable` exactly when **no
    operation in the set satisfies `parent_writable = is_write_operation(op) || allows_missing_leaf(op)`**
    — `d-20260916-04`'s predicate, not `is_write_operation` alone, which r9 still named here after
    O1b had been corrected (R9-01, confidence 99) — driven over the whole `PathOperation` enum so a
    new variant cannot silently default, **plus** an assertion per call site that `database_file_target`,

    `DownloadArchive` and `DatabaseCreate` named explicitly because r8's predicate missed exactly

    other assertion in this list.

## Decisions and trade-offs

1. **SQLite stays pathname-opened on Windows, exactly as on unix, because the repository already
   solved this twice and neither answer is platform-specific** (E9). The puzzle path copies a
   private snapshot from the retained descriptor — its own doc calls that "the portable way to
   prevent an A→B→A replacement from redirecting the connection" — and the game-database path
   sandwiches a pooled pathname connection between two `open_current` probes. The Windows arm
   inherits whichever the caller already uses. Rejected: a descriptor-bound VFS shim, which would
   add a mechanism for a guarantee the unix arm does not have either. **Against this choice:** the
   pooled path's residual A→B→A window between `open_current` and SQLite's own open is real; it is
   unchanged by this slice, cross-platform, and belongs to whoever revisits `acquire_probed`.
2. **Share the body where the wrappers already dispatch, duplicate only over raw syscalls**
   (O2), tightened by round 1 to share `unlink_database_files`, `open_valid_preferred` and the
   promotion as well. Against it: a shared body means a Windows-only regression can be introduced
   by a Linux-motivated edit. That is the trade accepted, because the alternative is a second copy
   that no test on this machine executes at all.
3. **Verbatim-prefix and UNC normalisation happen in a pure function tested on Linux** (O3), with
   the `MAX_PATH` consequence named rather than engineered around.
4. **`capability_directory` is ported in full rather than narrowed** (O6), because its own comment
   makes the remaining refusal this finding's.
5. **Sidecar deletion becomes identity-checked on both platforms** (O4), rather than porting the
   unix check-to-unlink window to Windows. Against it: it changes unix behaviour in a slice whose
   mandate is Windows. It is adopted because acceptance criterion 2 would otherwise be false, the
   files are already open in this run (rule 4b), and the Windows primitive makes the stronger form
   the cheaper one.
6. **`f-20260916-02` and `f-20260916-03` are carried and closed** (O9), because this slice is what
   makes them reachable from a renderer-supplied filename. Against it: it grows the slice by two
   findings. Rejected alternative: validating the colon and the length inside
   `create_database_child` only, which would leave every other Windows caller of the same gate
   exposed and would answer `f-20260916-02`'s open question with the narrower of the two options
   it names.
