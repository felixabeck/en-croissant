# Plan: one post-commit removal policy for database and puzzle deletion (f-20260917-08)

## Goal

Database deletion and puzzle deletion report every failure that happens after their primary file is
gone through one type, `CommittedRemoval` in `src-tauri/src/error.rs`, so the rule "which error
reaches the renderer once the file is gone" exists once. Both tails keep their own cache
invalidation and registry removal. The renderer contract (`applied-despite-error` for
`durability` and `partial-removal`) is unchanged.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260917-08`:

* **Where:** `delete_database_blocking`'s tail (`src-tauri/src/db/mod.rs:2345-2372`) and `delete_puzzle_database_resolved`'s tail (`src-tauri/src/puzzle.rs:700-735`).
* **Defect:** both tails now encode the same policy, arrived at independently in two phases of the same run: a removal that completed but left durability uncertain must still run its cache invalidation and its registry removal, must return `CommittedDurabilityUncertain` rather than `PartialRemoval` or `OperationAndCleanup` — it is the only category the renderer's `runDestructiveWithRefresh` reads as applied-despite-error — and must log, never substitute, a registry-cleanup failure that follows it. Two copies of a policy whose whole point is which of two errors reaches the renderer is exactly the shape that drifts: a later change to one tail leaves the other reporting a deleted database as a generic failure, and nothing would fail.
* **Why it matters:** the failure mode is invisible in tests that check one tail at a time, and its symptom is a user being told nothing happened to a database that is gone — the case `d-20260831-24` and the renderer's `applied-despite-error` contract exist to prevent.
* **Open question:** where does the policy live? A shared helper in `db/mod.rs` that both tails call would put puzzle deletion's error handling in the database module; a helper in `infra/` would give a filesystem module a renderer-category concern; a small `DeletionOutcome` type carrying `(count, Option<durability>)` with the precedence as its own method is the third option and is the only one that also removes the duplicated tuple-threading both tails now do. The cache invalidation and the registry call must stay at the call sites either way, because they differ.
* **Related:** `f-20260914-09` (the run that created the second copy, in its Phase B and Phase C); `d-20260831-24` (partial-removal reporting) and `d-20260830-05` (every backend error crosses IPC as a plain string) constrain any answer.

(The finding's line numbers predate later commits; the current lines are under Traced premises.)

## Threat model and non-goals

Accidental failures only: I/O errors, a parent-directory sync that fails after an unlink, a
registry save that fails before or after its rename, and a poisoned mutex (a panic on another
thread). No adversarial input; the paths were already resolved and authorised before either tail
runs. Every supported OS (Linux, macOS, Windows): neither tail has `cfg` branches, and neither
does this change. Not in scope: making the registry and the filesystem transactional, retrying
any step, or a structured (Specta-typed) error (`d-20260830-05` rejected that for this repo).

## Approach

### O1 — `CommittedRemoval` owns the post-commit precedence

MANDATE words: "must return `CommittedDurabilityUncertain` rather than `PartialRemoval` or
`OperationAndCleanup` … and must log, never substitute, a registry-cleanup failure that follows
it"; "where does the policy live? … a small `DeletionOutcome` type … with the precedence as its own
method".

A crate-private, `#[must_use]` type `CommittedRemoval` in `src-tauri/src/error.rs`, beside
`Error::with_cleanup`. Contract:

* It exists only once the primary entry of a removal is gone (or was already gone); a failure
  before that point never becomes one and keeps its raw error (T1's `!primary_gone` arm,
  `d-20260831-24`/`d-20261002-08`: sidecar-only failures stay retryable `Io`/`InvalidInput`).
* It carries the number of entries the operation removed and at most one failure.
* Recording a later step's outcome: the **first** failure is kept whatever its class; a later
  failure is logged at `warn` with the operation's subject, the path, the kept failure's
  category and the later failure's `diagnostic()`, and is dropped. It never combines the two into
  `OperationAndCleanup` and never replaces the kept failure.
* Finishing: no failure → `Ok(())`; a kept `CommittedDurabilityUncertain(stage)` → returned
  unchanged; any other kept failure → `PartialRemoval { removed_entries, cause }`.
* Unit tests in `error.rs` cover each finishing arm, both orders of a durability and a hard
  failure (first wins, second logged), and that the serialized category of each outcome is
  `durability` / `partial-removal` (the two categories T6 maps to `applied-despite-error`).

`finish_database_deletion` is deleted; nothing else outside the two tails calls it.

### O2 — Database deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: "must still run its cache invalidation and its registry removal"; "a user being
told nothing happened to a database that is gone". Depends on O1.

* While the primary is not gone, every failure returns raw, as today.
* Once `primary_gone`, the tail builds one `CommittedRemoval` from `unlinked` and
  `deletion_error`, records a failure of `delete_exclusive_cancellable` itself (T4: the lease
  release after the closure succeeded), **then always runs the registry removal** and records its
  outcome, and finishes. The registry removal therefore also runs on the T4 path, which today
  returns before it.
* `search_cache.invalidate_database` (both calls inside the closure) and
  `content_validation::forget` stay where they are and keep their order; the source-scan tests of
  T8 are updated to the new shape, keeping every property they assert today (fd-relative target,
  no `remove_file`, one unlink between two invalidations, no retry loop) and asserting
  `CommittedRemoval` use in place of `finish_database_deletion`.
* Today's observable outcomes in T7 stay identical: `PartialRemoval { 1, Conflict }` for a
  post-primary sidecar failure with or without a registry failure (the registry text still logged),
  durability uncertainty passed through with cache and registry cleanup run, and raw errors before
  the primary is touched.

### O3 — Puzzle deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: as O2. Depends on O1; independent of O2.

* The blocking closure records whether this call found the puzzle file gone: unlinked by this call
  (removed count 1, possibly with a `CommittedDurabilityUncertain`), or already missing (removed
  count 0).
* Once it is gone, a non-cancellation failure of `delete_exclusive_cancellable` after the closure
  succeeded (T4) is recorded as a post-commit failure instead of returning raw; the registry
  removal still runs inside the blocking closure and the cache invalidation still runs after the
  await, for every committed outcome.
* Failures before the file is gone keep today's behaviour (raw error, no cleanup): T7's 1457 and
  1515 stay green unchanged.
* The tail returns `CommittedRemoval::finish`; the hand-written `match registry_cleanup` and the
  `(Result, Option<PathBuf>, Option<Error>)` tuple are gone. The registry-failure log line is the
  one O1 emits (it now carries `diagnostic()` instead of `Display`).
* T7's 1370 and 1579 stay green with unchanged assertions.

### O4 — Verification

MANDATE words: "the failure mode is invisible in tests that check one tail at a time … and nothing
would fail".

* The policy is tested once, at O1's unit tests. Each tail additionally has behavioural tests for
  each committed outcome it can produce, so a tail that stops routing through the type fails a
  test of its own:
  * database: existing 4294, 12209, 12214 (unchanged assertions); new — lease-release failure
    after the primary is gone returns `PartialRemoval { unlinked, Conflict }` **and** the registry
    entry is removed and the cache invalidated.
  * puzzle: existing 1370, 1579 (unchanged); new — durability uncertainty plus a registry failure
    returns `CommittedDurabilityUncertain` and logs the registry failure (closes T7's gap); new —
    lease-release failure after unlink returns `PartialRemoval { 1, Conflict }` with cache
    invalidated and registry entry removed; new — an already-missing puzzle file with a registry
    failure returns `PartialRemoval { removed_entries: 0, .. }` with cache invalidated.
* A lease-release failure needs a test-only seam in `DatabaseRepository::release_deletion`
  (`#[cfg(test)]`, thread-local or per-repository, one-shot, reset on drop like the existing
  injectors in `infra/fs.rs`); it must not change release behaviour outside tests, and it must
  reach the blocking worker the same way `CapturedInjectors` (`infra/blocking.rs:477`) carries the
  other injectors, or be per-repository so no capture is needed.
* Every removed `finish_database_deletion_*` unit test has its case covered by an O1 unit test.

* **Why it matters:** the failure mode is invisible in tests that check one tail at a time, and its symptom is a user being told nothing happened to a database that is gone — the case `d-20260831-24` and the renderer's `applied-despite-error` contract exist to prevent.
* **Open question:** where does the policy live? A shared helper in `db/mod.rs` that both tails call would put puzzle deletion's error handling in the database module; a helper in `infra/` would give a filesystem module a renderer-category concern; a small `DeletionOutcome` type carrying `(count, Option<durability>)` with the precedence as its own method is the third option and is the only one that also removes the duplicated tuple-threading both tails now do. The cache invalidation and the registry call must stay at the call sites either way, because they differ.
* **Related:** `f-20260914-09` (the run that created the second copy, in its Phase B and Phase C); `d-20260831-24` (partial-removal reporting) and `d-20260830-05` (every backend error crosses IPC as a plain string) constrain any answer.

## Approach

### O1 — `CommittedRemoval` owns the post-commit precedence

MANDATE words: "must return `CommittedDurabilityUncertain` rather than `PartialRemoval` or
`OperationAndCleanup` … and must log, never substitute, a registry-cleanup failure that follows
it"; "where does the policy live? … a small `DeletionOutcome` type … with the precedence as its own
method".

A crate-private, `#[must_use]` type `CommittedRemoval` in `src-tauri/src/error.rs`, beside
`Error::with_cleanup`. Contract:

* It exists only once the primary entry of a removal is gone (or was already gone); a failure
  before that point never becomes one and keeps its raw error (T1's `!primary_gone` arm,
  `d-20261002-08`: sidecar-only failures stay retryable `Io`/`InvalidInput`).
* It carries the number of entries the operation removed and at most one failure.
* Recording a later step's outcome: the **first** failure is kept whatever its class; a later
  failure is logged at `warn` with the operation's subject, the path, the kept failure's
  category and the later failure's `diagnostic()`, and is dropped. It never combines the two into
  `OperationAndCleanup` and never replaces the kept failure.
* Counting: a later step that removes an entry (a SQLite sidecar after the primary) increments the
  count, also when that removal's durability is uncertain.
* Finishing: no failure → `Ok(())`; a kept `CommittedDurabilityUncertain(stage)` → returned
  unchanged; any other kept failure → `PartialRemoval { removed_entries, cause }`.
* "First" is first in operation order across the whole committed removal, including steps that
  run inside a producer (`unlink_database_files`) or inside the exclusive-lease closure: no layer
  may drop or replace an earlier post-commit failure before it reaches the type (T11).
* Unit tests in `error.rs` cover each finishing arm, both orders of a durability and a hard
  failure (first wins, second logged), and that the serialized category of each outcome is
  `durability` / `partial-removal` (the two categories T6 maps to `applied-despite-error`).

`finish_database_deletion` is deleted; nothing else outside the two tails calls it.

### O2 — Database deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: "must still run its cache invalidation and its registry removal"; "a user being
told nothing happened to a database that is gone". Depends on O1.

* While the primary is not gone, every failure returns raw, as today (including an earlier
  sidecar durability uncertainty, which stays logged when the primary removal then fails).
* The commit boundary is where the primary is removed: from that point `unlink_database_files`
  carries a `CommittedRemoval` seeded with the entries removed so far and any durability
  uncertainty retained from the sidecars or the primary, and records each SQLite-sidecar outcome
  into it instead of returning the first hard sidecar failure in place of a retained uncertainty
  (T11). Its result tells the caller "not committed: raw error" apart from "committed: this
  `CommittedRemoval`".
* The exclusive-lease closure hands the `CommittedRemoval` out and returns `Ok`, so an `Err` from
  `delete_exclusive_cancellable` after commit can only be the lease release (T4); the tail records
  it **after** the deletion's own failure, **then always runs the registry removal** and records
  its outcome, and finishes. The registry removal therefore also runs on the T4 path, which today
  returns before it.
* `search_cache.invalidate_database` (both calls inside the closure) and
  `content_validation::forget` stay where they are and keep their order; the source-scan tests of
  T8 are updated to the new shape, keeping every property they assert today (fd-relative target,
  no `remove_file`, one unlink between two invalidations, no retry loop) and asserting
  `CommittedRemoval` use in place of `finish_database_deletion`.
* Today's observable outcomes in T7 stay identical: `PartialRemoval { 1, Conflict }` for a
  post-primary sidecar failure with or without a registry failure (the registry text still logged),
  durability uncertainty passed through with cache and registry cleanup run, and raw errors before
  the primary is touched. The one intended change is T11's combination, which now returns the
  durability uncertainty.

### O3 — Puzzle deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: as O2. Depends on O1; independent of O2.

* The blocking closure records whether this call found the puzzle file gone: unlinked by this call
  (removed count 1, possibly with a `CommittedDurabilityUncertain`), or already missing (removed
  count 0). Inside the exclusive lease it hands that `CommittedRemoval` out and returns `Ok`, so the
  durability uncertainty no longer travels as the closure's `Err` and cannot be replaced by a
  lease-release error (T11).
* Once it is gone, a non-cancellation failure of `delete_exclusive_cancellable` (T4) is recorded
  after the deletion's own failure instead of returning raw; the registry removal still runs inside
  the blocking closure and the cache invalidation still runs after the await, for every committed
  outcome.
* Failures before the file is gone keep today's behaviour (raw error, no cleanup): T7's 1457 and
  1515 stay green unchanged.
* The tail returns `CommittedRemoval::finish`; the hand-written `match registry_cleanup` and the
  `(Result, Option<PathBuf>, Option<Error>)` tuple are gone. The registry-failure log line is the
  one O1 emits (it now carries `diagnostic()` instead of `Display`).
* T7's 1370 and 1579 stay green with unchanged assertions.

### O4 — Verification

MANDATE words: "the failure mode is invisible in tests that check one tail at a time … and nothing
would fail". Threat model: every supported OS.

* The policy is tested once, at O1's unit tests. Each tail additionally has behavioural tests for
  each committed outcome it can produce, so a tail that stops routing through the type fails a

  * puzzle: existing 1370, 1579 (unchanged); new — durability uncertainty plus a registry failure

* **DA1 — Where does the post-commit removal policy live?** Chosen: a `CommittedRemoval` type in

  the only option that also removes both tails' tuple threading (the finding's own analysis).
  Reversal path: move the type; the call sites do not change shape. Governs `f-20260917-08`.
* **DA2 — Which failure wins when two post-commit steps fail?** Chosen: the first, whatever its
  class; the later one is logged with its diagnostic. Rejected: durability uncertainty outranks a
  hard failure; a hard failure outranks durability uncertainty (`d-20260906-03`'s *combine*
  contract for workspace create/rename). Reason: both tails already keep the first failure (T1,
  T3); both outcomes map to the same renderer category (T6); and the first failure is the one
  closest to the primary unlink, which is what the user asked for. This also retires the one place
  that did otherwise, `unlink_database_files`'s post-primary SQLite-sidecar loop, which let a later
  hard failure replace a retained durability uncertainty (T11) — the MANDATE's "must return
  `CommittedDurabilityUncertain` rather than `PartialRemoval`". Reversal path: change one method in
  `error.rs`. Governs `f-20260917-08`.
* **DA3 — When is a removal committed?** Chosen: when the primary entry is gone — unlinked by this
  call or already missing; every later failure, including the exclusive-lease release (T4), is a

  ("told nothing happened to a database that is gone") and `.claude/rules/async-resource-invariants.md`
  (cleanup on every exit path). Governs `f-20260917-08`.
* **DA4 — What does a puzzle deletion count when the file was already missing?** Chosen: 0
  removed entries. Rejected: today's constant 1. Reason: the count is shown to the user in the
  `PartialRemoval` message (T6) and must be true; the type requires the site to supply it.
  Governs `f-20260917-08`.

# Plan: one post-commit removal policy for database and puzzle deletion (f-20260917-08)

## Goal

Database deletion and puzzle deletion report every failure that happens after their primary file is
gone through one type, `CommittedRemoval` in `src-tauri/src/error.rs`, so the rule "which error
reaches the renderer once the file is gone" exists once. Both tails keep their own cache
invalidation and registry removal. The renderer contract (`applied-despite-error` for
`durability` and `partial-removal`) is unchanged.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260917-08`:

* **Where:** `delete_database_blocking`'s tail (`src-tauri/src/db/mod.rs:2345-2372`) and `delete_puzzle_database_resolved`'s tail (`src-tauri/src/puzzle.rs:700-735`).
* **Defect:** both tails now encode the same policy, arrived at independently in two phases of the same run: a removal that completed but left durability uncertain must still run its cache invalidation and its registry removal, must return `CommittedDurabilityUncertain` rather than `PartialRemoval` or `OperationAndCleanup` — it is the only category the renderer's `runDestructiveWithRefresh` reads as applied-despite-error — and must log, never substitute, a registry-cleanup failure that follows it. Two copies of a policy whose whole point is which of two errors reaches the renderer is exactly the shape that drifts: a later change to one tail leaves the other reporting a deleted database as a generic failure, and nothing would fail.
* **Why it matters:** the failure mode is invisible in tests that check one tail at a time, and its symptom is a user being told nothing happened to a database that is gone — the case `d-20260831-24` and the renderer's `applied-despite-error` contract exist to prevent.
* **Open question:** where does the policy live? A shared helper in `db/mod.rs` that both tails call would put puzzle deletion's error handling in the database module; a helper in `infra/` would give a filesystem module a renderer-category concern; a small `DeletionOutcome` type carrying `(count, Option<durability>)` with the precedence as its own method is the third option and is the only one that also removes the duplicated tuple-threading both tails now do. The cache invalidation and the registry call must stay at the call sites either way, because they differ.
* **Related:** `f-20260914-09` (the run that created the second copy, in its Phase B and Phase C); `d-20260831-24` (partial-removal reporting) and `d-20260830-05` (every backend error crosses IPC as a plain string) constrain any answer.

(The finding's line numbers predate later commits; the current lines are under Traced premises.)

## Threat model and non-goals

Accidental failures only: I/O errors, a parent-directory sync that fails after an unlink, a
registry save that fails before or after its rename, and a poisoned mutex (a panic on another
thread). No adversarial input; the paths were already resolved and authorised before either tail
runs. Every supported OS (Linux, macOS, Windows): neither tail has `cfg` branches, and neither
does this change. Not in scope: making the registry and the filesystem transactional, retrying
any step, or a structured (Specta-typed) error (`d-20260830-05` rejected that for this repo).

## Approach

### O1 — `CommittedRemoval` owns the post-commit precedence

MANDATE words: "must return `CommittedDurabilityUncertain` rather than `PartialRemoval` or
`OperationAndCleanup` … and must log, never substitute, a registry-cleanup failure that follows
it"; "where does the policy live? … a small `DeletionOutcome` type … with the precedence as its own
method".

A crate-private, `#[must_use]` type `CommittedRemoval` in `src-tauri/src/error.rs`, beside
`Error::with_cleanup`. Contract:

* It exists only once the primary entry of a removal is gone (or was already gone); a failure
  before that point never becomes one and keeps its raw error (T1's `!primary_gone` arm,
  `d-20261002-08`: sidecar-only failures stay retryable `Io`/`InvalidInput`).
* It carries the number of entries the operation removed and at most one failure.
* Recording a later step's outcome: the **first** failure is kept whatever its class; a later
  failure is logged at `warn` with the operation's subject, the path, the kept failure's
  category and the later failure's `diagnostic()`, and is dropped. It never combines the two into
  `OperationAndCleanup` and never replaces the kept failure.
* Counting: a later step that removes an entry (a SQLite sidecar after the primary) increments the
  count, also when that removal's durability is uncertain.
* Finishing: no failure → `Ok(())`; a kept `CommittedDurabilityUncertain(stage)` → returned
  unchanged; any other kept failure → `PartialRemoval { removed_entries, cause }`.
* "First" is first in operation order across the whole committed removal, including steps that
  run inside a producer (`unlink_database_files`) or inside the exclusive-lease closure: no layer
  may drop or replace an earlier post-commit failure before it reaches the type (T11).
* Unit tests in `error.rs` cover each finishing arm, both orders of a durability and a hard
  failure (first wins, second logged), and that the serialized category of each outcome is
  `durability` / `partial-removal` (the two categories T6 maps to `applied-despite-error`).

`finish_database_deletion` is deleted; nothing else outside the two tails calls it.

### O2 — Database deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: "must still run its cache invalidation and its registry removal"; "a user being
told nothing happened to a database that is gone". Depends on O1.

* While the primary is not gone, every failure returns raw, as today (including an earlier
  sidecar durability uncertainty, which stays logged when the primary removal then fails).
* The commit boundary is where the primary is removed: from that point `unlink_database_files`
  carries a `CommittedRemoval` seeded with the entries removed so far and any durability
  uncertainty retained from the sidecars or the primary, and records each SQLite-sidecar outcome
  into it instead of returning the first hard sidecar failure in place of a retained uncertainty
  (T11). Its result tells the caller "not committed: raw error" apart from "committed: this
  `CommittedRemoval`".
* The exclusive-lease closure hands the `CommittedRemoval` out and returns `Ok`, so an `Err` from
  `delete_exclusive_cancellable` after commit can only be the lease release (T4); the tail records
  it **after** the deletion's own failure, **then always runs the registry removal** and records
  its outcome, and finishes. The registry removal therefore also runs on the T4 path, which today
  returns before it.
* `search_cache.invalidate_database` (both calls inside the closure) and
  `content_validation::forget` stay where they are and keep their order; the source-scan tests of
  T8 are updated to the new shape, keeping every property they assert today (fd-relative target,
  no `remove_file`, one unlink between two invalidations, no retry loop) and asserting
  `CommittedRemoval` use in place of `finish_database_deletion`.
* Today's observable outcomes in T7 stay identical: `PartialRemoval { 1, Conflict }` for a
  post-primary sidecar failure with or without a registry failure (the registry text still logged),
  durability uncertainty passed through with cache and registry cleanup run, and raw errors before
  the primary is touched. The one intended change is T11's combination, which now returns the
  durability uncertainty.

### O3 — Puzzle deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: as O2. Depends on O1; independent of O2.

* The blocking closure records whether this call found the puzzle file gone: unlinked by this call
  (removed count 1, possibly with a `CommittedDurabilityUncertain`), or already missing (removed
  count 0). Inside the exclusive lease it hands that `CommittedRemoval` out and returns `Ok`, so the
  durability uncertainty no longer travels as the closure's `Err` and cannot be replaced by a
  lease-release error (T11).
* Once it is gone, a non-cancellation failure of `delete_exclusive_cancellable` (T4) is recorded
  after the deletion's own failure instead of returning raw; the registry removal still runs inside
  the blocking closure and the cache invalidation still runs after the await, for every committed
  outcome.
* Failures before the file is gone keep today's behaviour (raw error, no cleanup): T7's 1457 and
  1515 stay green unchanged.
* The tail returns `CommittedRemoval::finish`; the hand-written `match registry_cleanup` and the
  `(Result, Option<PathBuf>, Option<Error>)` tuple are gone. The registry-failure log line is the
  one O1 emits (it now carries `diagnostic()` instead of `Display`).
* T7's 1370 and 1579 stay green with unchanged assertions.

### O4 — Verification

MANDATE words: "the failure mode is invisible in tests that check one tail at a time … and nothing
would fail". Threat model: every supported OS.

* The policy is tested once, at O1's unit tests. Each tail additionally has behavioural tests for
  each committed outcome it can produce, so a tail that stops routing through the type fails a
  test of its own:
  * database: existing 4294, 12209, 12214 (unchanged assertions); new — lease-release failure
    after the primary is gone returns `PartialRemoval { unlinked, Conflict }` **and** the registry
    entry is removed and the cache invalidated; new — primary durability uncertainty followed by a
    hard `-wal`/`-shm` failure returns `CommittedDurabilityUncertain`, logs the sidecar failure, and
    runs cache and registry cleanup (T11); new — durability uncertainty followed by a lease-release
    failure returns `CommittedDurabilityUncertain`, logs the release failure, and runs cleanup.
  * puzzle: existing 1370, 1579 (unchanged); new — durability uncertainty plus a registry failure
    returns `CommittedDurabilityUncertain` and logs the registry failure (closes T7's gap); new —
    lease-release failure after unlink returns `PartialRemoval { 1, Conflict }` with cache
    invalidated and registry entry removed; new — durability uncertainty plus a lease-release
    failure returns `CommittedDurabilityUncertain`, logs the release failure, and runs cleanup; new
    — an already-missing puzzle file with a registry failure returns
    `PartialRemoval { removed_entries: 0, .. }` with cache invalidated.
* Placement: every database and puzzle tail test that needs no Unix-only machinery runs on every
  target — database tests in the existing `#[cfg(test)] mod deletion_tests`, puzzle tests in a
  `#[cfg(test)]` module of `puzzle.rs` that is not gated to Unix (T12's precedent); tests that use
  the Unix-only removal injector stay in the Unix module. That puts 1579 and the new lease-release
  and already-missing puzzle tests on Windows. How the shared fixture reaches that module is CR-1.
* A lease-release failure needs a test-only seam in `DatabaseRepository::release_deletion`
  (`#[cfg(test)]`, one-shot); it must not change release behaviour outside tests, and it must
  reach the blocking worker the puzzle tail runs on — either per-repository, so no capture is
  needed, or carried the way `CapturedInjectors` (`infra/blocking.rs:477`) carries the other
  injectors.
* The removed `finish_database_deletion_*` unit tests: their committed cases (success, hard failure
  → `PartialRemoval`, durability pass-through) are O1 unit tests; their pre-commit case (raw error
  while the primary still exists) stays covered at the caller by the existing database tests 4353
  and 12351 and by `delete_database_stops_at_invalid_preferred_sidecar_before_primary`.

## Decisions and trade-offs

## Decided autonomously

Recorded here for the adopting session to write into `tasks/decisions.md`; no Felix decision is
open (the question is technical: no user sees, gets or is promised anything different between
these placements).

* **DA1 — Where does the post-commit removal policy live?** Chosen: a `CommittedRemoval` type in
  `src-tauri/src/error.rs`. Rejected: a helper in `db/mod.rs` (puzzle deletion's error policy would
  live in the database module, and the tuple threading would stay); a helper in `infra/` (a
  filesystem module would own a renderer-category concern). Reason: `error.rs` already owns the
  mapping from `Error` to the wire category and `with_cleanup`, the sibling combinator; a type is
  the only option that also removes both tails' tuple threading (the finding's own analysis).
  Reversal path: move the type; the call sites do not change shape. Governs `f-20260917-08`.
* **DA2 — Which failure wins when two post-commit steps fail?** Chosen: the first, whatever its
  class; the later one is logged with its diagnostic. Rejected: durability uncertainty outranks a
  hard failure; a hard failure outranks durability uncertainty (`d-20260906-03`'s *combine*
  contract for workspace create/rename). Reason: both tails already keep the first failure (T1,
  T3); both outcomes map to the same renderer category (T6); and the first failure is the one
  closest to the primary unlink, which is what the user asked for. This also retires the one place
  that did otherwise, `unlink_database_files`'s post-primary SQLite-sidecar loop, which let a later
  hard failure replace a retained durability uncertainty (T11) — the MANDATE's "must return
  `CommittedDurabilityUncertain` rather than `PartialRemoval`". Reversal path: change one method in
  `error.rs`. Governs `f-20260917-08`.
* **DA3 — When is a removal committed?** Chosen: when the primary entry is gone — unlinked by this
  call or already missing; every later failure, including the exclusive-lease release (T4), is a
  post-commit failure and cleanup still runs. Rejected: committed only when the closure returned
  `Ok` (today's accident: a lease-release failure after the unlink skips registry cleanup, and in
  the puzzle tail also cache invalidation, and reports a raw error). Reason: the MANDATE's symptom
  ("told nothing happened to a database that is gone") and `.claude/rules/async-resource-invariants.md`
  (cleanup on every exit path). Governs `f-20260917-08`.
* **DA4 — What does a puzzle deletion count when the file was already missing?** Chosen: 0
  removed entries. Rejected: today's constant 1. Reason: the count is shown to the user in the
  `PartialRemoval` message (T6) and must be true; the type requires the site to supply it.
  Governs `f-20260917-08`.

# Plan: one post-commit removal policy for database and puzzle deletion (f-20260917-08)

## Goal

Database deletion and puzzle deletion report every failure that happens after their primary file is
gone through one type, `CommittedRemoval` in `src-tauri/src/error.rs`, so the rule "which error
reaches the renderer once the file is gone" exists once. Both tails keep their own cache
invalidation and registry removal. The renderer contract (`applied-despite-error` for
`durability` and `partial-removal`) is unchanged.

## MANDATE

Verbatim from `tasks/findings.md`, `f-20260917-08`:

* **Where:** `delete_database_blocking`'s tail (`src-tauri/src/db/mod.rs:2345-2372`) and `delete_puzzle_database_resolved`'s tail (`src-tauri/src/puzzle.rs:700-735`).
* **Defect:** both tails now encode the same policy, arrived at independently in two phases of the same run: a removal that completed but left durability uncertain must still run its cache invalidation and its registry removal, must return `CommittedDurabilityUncertain` rather than `PartialRemoval` or `OperationAndCleanup` — it is the only category the renderer's `runDestructiveWithRefresh` reads as applied-despite-error — and must log, never substitute, a registry-cleanup failure that follows it. Two copies of a policy whose whole point is which of two errors reaches the renderer is exactly the shape that drifts: a later change to one tail leaves the other reporting a deleted database as a generic failure, and nothing would fail.
* **Why it matters:** the failure mode is invisible in tests that check one tail at a time, and its symptom is a user being told nothing happened to a database that is gone — the case `d-20260831-24` and the renderer's `applied-despite-error` contract exist to prevent.
* **Open question:** where does the policy live? A shared helper in `db/mod.rs` that both tails call would put puzzle deletion's error handling in the database module; a helper in `infra/` would give a filesystem module a renderer-category concern; a small `DeletionOutcome` type carrying `(count, Option<durability>)` with the precedence as its own method is the third option and is the only one that also removes the duplicated tuple-threading both tails now do. The cache invalidation and the registry call must stay at the call sites either way, because they differ.
* **Related:** `f-20260914-09` (the run that created the second copy, in its Phase B and Phase C); `d-20260831-24` (partial-removal reporting) and `d-20260830-05` (every backend error crosses IPC as a plain string) constrain any answer.

## Approach

### O1 — `CommittedRemoval` owns the post-commit precedence

MANDATE words: "must return `CommittedDurabilityUncertain` rather than `PartialRemoval` or
`OperationAndCleanup` … and must log, never substitute, a registry-cleanup failure that follows
it"; "where does the policy live? … a small `DeletionOutcome` type … with the precedence as its own
method".

A crate-private, `#[must_use]` type `CommittedRemoval` in `src-tauri/src/error.rs`, beside
`Error::with_cleanup`. Contract:

* It exists only once the primary entry of a removal is gone (or was already gone); a failure
  before that point never becomes one and keeps its raw error (T1's `!primary_gone` arm,
  `d-20261002-08`: sidecar-only failures stay retryable `Io`/`InvalidInput`).
* It carries the number of entries the operation removed and at most one failure.
* Recording a later step's outcome: the **first** failure is kept whatever its class; a later
  failure is logged at `warn` with the operation's subject, the path, the kept failure's
  category and the later failure's `diagnostic()`, and is dropped. It never combines the two into
  `OperationAndCleanup` and never replaces the kept failure.
* Counting: a later step that removes an entry (a SQLite sidecar after the primary) increments the
  count, also when that removal's durability is uncertain.
* Finishing: no failure → `Ok(())`; a kept `CommittedDurabilityUncertain(stage)` → returned
  unchanged; any other kept failure → `PartialRemoval { removed_entries, cause }`.
* "First" is first in operation order across the whole committed removal, including steps that
  run inside a producer (`unlink_database_files`) or inside the exclusive-lease closure: no layer
  may drop or replace an earlier post-commit failure before it reaches the type (T11).
* Unit tests in `error.rs` cover each finishing arm, both orders of a durability and a hard
  failure (first wins, second logged), and that the serialized category of each outcome is
  `durability` / `partial-removal` (the two categories T6 maps to `applied-despite-error`).

`finish_database_deletion` is deleted; nothing else outside the two tails calls it.

### O2 — Database deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: "must still run its cache invalidation and its registry removal"; "a user being
told nothing happened to a database that is gone". Depends on O1.

* While the primary is not gone, every failure returns raw, as today (including an earlier
  sidecar durability uncertainty, which stays logged when the primary removal then fails).
* The commit boundary is where the primary is removed: from that point `unlink_database_files`
  carries a `CommittedRemoval` seeded with the entries removed so far and any durability
  uncertainty retained from the sidecars or the primary, and records each SQLite-sidecar outcome
  into it instead of returning the first hard sidecar failure in place of a retained uncertainty
  (T11). Its result tells the caller "not committed: raw error" apart from "committed: this
  `CommittedRemoval`".
* The exclusive-lease closure hands the `CommittedRemoval` out and returns `Ok`, so an `Err` from
  `delete_exclusive_cancellable` after commit can only be the lease release (T4); the tail records
  it **after** the deletion's own failure, **then always runs the registry removal** and records
  its outcome, and finishes. The registry removal therefore also runs on the T4 path, which today
  returns before it.
* `search_cache.invalidate_database` (both calls inside the closure) and
  `content_validation::forget` stay where they are and keep their order; the source-scan tests of
  T8 are updated to the new shape, keeping every property they assert today (fd-relative target,
  no `remove_file`, one unlink between two invalidations, no retry loop) and asserting
  `CommittedRemoval` use in place of `finish_database_deletion`.
* Today's observable outcomes in T7 stay identical: `PartialRemoval { 1, Conflict }` for a
  post-primary sidecar failure with or without a registry failure (the registry text still logged),
  durability uncertainty passed through with cache and registry cleanup run, and raw errors before
  the primary is touched. The one intended change is T11's combination, which now returns the
  durability uncertainty.

### O3 — Puzzle deletion routes every post-commit failure through `CommittedRemoval`

MANDATE words: as O2. Depends on O1; independent of O2.

* The blocking closure records whether this call found the puzzle file gone: unlinked by this call
  (removed count 1, possibly with a `CommittedDurabilityUncertain`), or already missing (removed
  count 0). Inside the exclusive lease it hands that `CommittedRemoval` out and returns `Ok`, so the
  durability uncertainty no longer travels as the closure's `Err` and cannot be replaced by a
  lease-release error (T11).
* Once it is gone, a non-cancellation failure of `delete_exclusive_cancellable` (T4) is recorded
  after the deletion's own failure instead of returning raw; the registry removal still runs inside
  the blocking closure and the cache invalidation still runs after the await, for every committed
  outcome.
* Failures before the file is gone keep today's behaviour (raw error, no cleanup): T7's 1457 and
  1515 stay green unchanged.
* The tail returns `CommittedRemoval::finish`; the hand-written `match registry_cleanup` and the
  `(Result, Option<PathBuf>, Option<Error>)` tuple are gone. The registry-failure log line is the
  one O1 emits (it now carries `diagnostic()` instead of `Display`).
* T7's 1370 and 1579 stay green with unchanged assertions.

## Decided autonomously

open (the question is technical: no user sees, gets or is promised anything different between

* **DA1 — Where does the post-commit removal policy live?** Chosen: a `CommittedRemoval` type in
  `src-tauri/src/error.rs`. Rejected: a helper in `db/mod.rs` (puzzle deletion's error policy would
  live in the database module, and the tuple threading would stay); a helper in `infra/` (a
  filesystem module would own a renderer-category concern). Reason: `error.rs` already owns the
  mapping from `Error` to the wire category and `with_cleanup`, the sibling combinator; a type is
  the only option that also removes both tails' tuple threading (the finding's own analysis).
  Reversal path: move the type; the call sites do not change shape. Governs `f-20260917-08`.
* **DA2 — Which failure wins when two post-commit steps fail?** Chosen: the first, whatever its
  class; the later one is logged with its diagnostic. Rejected: durability uncertainty outranks a
  hard failure; a hard failure outranks durability uncertainty (`d-20260906-03`'s *combine*
  contract for workspace create/rename). Reason: both tails already keep the first failure (T1,
  T3); both outcomes map to the same renderer category (T6); and the first failure is the one
  closest to the primary unlink, which is what the user asked for. This also retires the one place
  that did otherwise, `unlink_database_files`'s post-primary SQLite-sidecar loop, which let a later
  hard failure replace a retained durability uncertainty (T11) — the MANDATE's "must return
  `CommittedDurabilityUncertain` rather than `PartialRemoval`". Reversal path: change one method in
  `error.rs`. Governs `f-20260917-08`.
* **DA3 — When is a removal committed?** Chosen: when the primary entry is gone — unlinked by this
  call or already missing; every later failure, including the exclusive-lease release (T4), is a
  post-commit failure and cleanup still runs. Rejected: committed only when the closure returned
  `Ok` (today's accident: a lease-release failure after the unlink skips registry cleanup, and in
  the puzzle tail also cache invalidation, and reports a raw error). Reason: the MANDATE's symptom
  ("told nothing happened to a database that is gone") and `.claude/rules/async-resource-invariants.md`
  (cleanup on every exit path). Governs `f-20260917-08`.
* **DA4 — What does a puzzle deletion count when the file was already missing?** Chosen: 0
  removed entries. Rejected: today's constant 1. Reason: the count is shown to the user in the
  `PartialRemoval` message (T6) and must be true; the type requires the site to supply it.
  Governs `f-20260917-08`.
