## What the plan settled

The open question is answered **typed refusal**: an active-root accessor returns `Ok(None)` only
when no selection is recorded; a recorded but unusable selection is re-proved through
`workspace_root` and returned as an `Err` labelled by the existing `rootFailure` mapping
(`d-20261003-21`, `d-20261003-22`), so the three commands create an app-owned default only for "no
selection" and keep the selection for a later remount. Availability reaches the renderer as that
label, not as a descriptor field. One shared renderer primitive maps the label to a database,
puzzle or engine sentence; a `verify:app` check proves the real IPC path.

Settled dispositions a successor should not relitigate without new evidence:

* **Coverage is exactly `refresh_entry`'s unusable states.** A root that still resolves but whose
  own directory cannot be read refreshes `Available` and is never replaced by a default, so it is
  not this MANDATE's defect (U1-01, filed). Re-proving on every resolution was rejected because
  `workspace_root` refuses a raw app-owned spelling that `refresh_entry` exempts (`f-20260917-13`
  R3-06).
* **Windows absent drive / network share** (`ERROR_INVALID_DRIVE`, `ERROR_BAD_NETPATH`,
  `ERROR_BAD_NET_NAME`) is labelled `missing` at root sites by `root_failure_reason`'s `NotFound`
  arm; `is_missing_entry_io` stays narrow (U1-04, decision 6).

### plan-r1.md

# Plan: an unavailable persisted active root is refused and surfaced, never replaced by a default

## Goal

When the user has a database, puzzle or engine root selected and that selection is currently
unusable, the native command that resolves the active root returns a typed, `rootFailure`-labelled
refusal instead of silently creating and activating an app-owned default. The renderer turns that
refusal into a sentence that tells the user the chosen folder is unavailable and where to choose
another. "No selection yet" keeps today's default creation. The selection itself is kept, so a
remounted or restored folder becomes usable again without re-selection.

Finding: `f-20260917-12` (cluster of one, area `app-startup`, entry `build`). Inherited issue IDs
from `tasks/handoffs/2026-09-17-f-20260914-36-review.md`: **R2-03** (behaviour half: the
`Ok(None)` mapping and the silent default), **R12-01** and **R13-01** (no renderer availability
channel; production descriptors hard-code `Available`). This plan closes all three.

## MANDATE

Verbatim from `f-20260917-12` in `tasks/findings.md`:

* **Defect:** `active_*_root()` refreshes the entry and returns `Ok(None)` whenever it is not `Available`. The caller cannot tell "the root the user chose is currently unusable" from "the user never chose one", and answers both by creating and activating an app-owned default directory. A user whose chosen database, puzzle or engine root is temporarily unavailable — an unmounted volume, a renamed parent, a changed identity, or a path-authority entry the registry could not bind — is therefore silently moved to a different, empty workspace instead of being told. Nothing in the descriptor surface or the renderer can express the difference: the production descriptors report `Available` unconditionally, so even a correct backend availability answer never reaches the user.
* **Why it matters:** the user's data appears to have vanished and their selection appears to have been forgotten; the recovery — re-selecting the original root — is exactly the action the UI gives them no reason to take. It is also the reason a backend that correctly marks an entry unavailable cannot improve matters on its own.
* **Open question:** does an unavailable persisted active root become a typed refusal that the command surfaces and the renderer renders as a re-selection prompt, or does the default-creation path stay and gain a distinct "your previous workspace is unavailable" signal beside it — and what carries availability to the renderer, given that `PathDescriptor` is test-only and the production descriptors hard-code `Available`?
* **Annotation (2026-09-18):** this finding inherits issue IDs from `f-20260914-36`'s run; load `tasks/handoffs/2026-09-17-f-20260914-36-review.md` before plan review.

## Threat model and non-goals

* **Accidental input only.** The unusable states are the ones the MANDATE names: an unmounted
  volume, a renamed or deleted folder or parent, an identity change (folder replaced), a permission
  change, a registry entry that cannot be decoded or bound. No adversary racing the filesystem
  between refresh and re-proof is modelled; such a race must fail closed (a refusal), never open
  (a default).
* **Environments:** Linux, macOS and Windows. Labels come from `Error::root_failure_reason`
  (`io::ErrorKind`-based, already Windows-aware per `d-20261003-22`), so no platform-specific code
  is added.
* Not a security boundary change: no capability, scope, or path-containment rule moves.

## Approach

### A1 — Active-root resolution distinguishes "no selection" from "unusable selection"

*MANDATE: "The caller cannot tell 'the root the user chose is currently unusable' from 'the user
never chose one'"; Open question: "a typed refusal that the command surfaces".*

* Required behaviour, for each of `active_database_root`, `active_puzzle_root`,
  `active_engine_root` (signatures unchanged: `Result<Option<_>, Error>`):
  * no active id recorded → `Ok(None)` (unchanged);
  * active id recorded, entry refreshes `Available` with directory shape and the domain's operation
    bit → `Ok(Some(..))` (unchanged);
  * active id recorded, anything else → `Err(e)` where `e` is the error from re-proving the root
    through `workspace_root` with the domain's operation, passed through `label_root_failure`. If
    the re-proof unexpectedly succeeds while the refresh said unusable, the result is
    `Err(Error::Conflict(..))` labelled `changed` (fail closed; the next request re-refreshes and
    recovers by itself). An error the mapping does not label (e.g. an unclassified `Io`) stays
    unlabelled, per `d-20261003-22`, and reaches the renderer's retry sentence.
* Ownership: the three accessors route through **one** private resolution helper in
  `PathAuthority` parameterised by the active id and the operation (rule 11 — three copies today);
  each accessor only wraps the returned `PathRef` into its handle/descriptor.
* State: the active id is **not** cleared on refusal, and no registry write happens on this path —
  the selection survives so P2's recomputation restores it after a remount. Nothing else in the
  registry changes.
* The load-time active-id filter (P6) is unchanged: it drops ids only for states no setter
  writes, and loading never skips an entry, so it cannot hide a user's selection behind `None`.

### A2 — Commands propagate the refusal and create a default only for "no selection"

*MANDATE: "answers both by creating and activating an app-owned default directory"; "silently
moved to a different, empty workspace".*

* `get_database_workspace`, `get_engine_workspace`, and every command reaching
  `active_or_default_puzzle_workspace` propagate A1's `Err` unchanged (already the shape of their
  `?`), so no app-owned default directory is created, registered or activated when a selection
  exists but is unusable. The default path runs only on `Ok(None)`.
* `issue_puzzle_workspace_blocking`'s post-activation read keeps its contract; an `Err` from it
  now carries the label instead of the generic `Conflict("selected puzzle workspace became
  unavailable")`.
* Doc comments on these commands state the new contract (the `get_database_workspace` comment
  "Returns the active database root when set and available. Otherwise …" is wrong after A1).
* The source test `app_owned_default_roots_are_pinned_to_their_call_sites` (`main.rs`
  `blocking_offload_scans` module) and the gateway-nesting scans must stay green; if a phase moves
  a default-creation call, the pin moves with it in the same phase.

### A3 — The renderer says which folder is unavailable and where to choose another

*MANDATE: "instead of being told"; Open question: "the renderer renders as a re-selection
prompt"; "what carries availability to the renderer".*

* Carrier: the optional `rootFailure` field on the error payload (`d-20261003-21`) — the renderer
  reads only that field, never message text. Descriptor `availability` fields are not the carrier
  (decision D2).
* One shared renderer primitive maps a `rootFailure` label to a domain sentence, for three domains
  (database, puzzle, engine). The Databases page's existing five-sentence record moves into it
  unchanged (same keys, same text), and `notifyUnlessCancelled`'s single `changedMessage` override
  generalises to that per-label record, with every existing `changedMessage` caller migrated
  (rule 11; no second override mechanism remains).
* Sentences (en-US source; every catalogue gets the key):
  * database: the existing `Databases.LoadError.*` sentences (no new strings).
  * puzzle (new): changed — "This puzzle folder changed. Choose another in Settings."; missing —
    "This puzzle folder is no longer available. Choose another in Settings."; unusable — "This
    puzzle folder cannot be opened. Choose another in Settings."; permission — "ChessFable is not
    allowed to read this puzzle folder. Choose another in Settings."
  * engine (new): the same four, with "engine folder".

## Decisions and trade-offs

The contested points; every one is also listed under `## Decided autonomously`.

* D1 — refusal, not default-plus-signal. Creating the default while signalling would still move
  the user's new work into a different folder and split their data across two roots on recovery,
  and would require a second state to present beside the existing `rootFailure` channel.
* D2 — `rootFailure` on the error, not descriptor `availability`. A descriptor is minted only on
  success, so carrying "unavailable" in it would need a success path that hands the renderer an
  unusable handle. The existing descriptor `availability` fields are truthful at construction (P9)
  and stay as they are.
* D3 — label derived from re-proving through `workspace_root`, not from making `refresh_entry`
  return its reason. `refresh_entry` has five call sites (`f-20260914-36` R8-02) and its result is
  a cache; re-proof only runs on the refusal path and reuses the exact mapping `d-20261003-22`
  already validated.
* D4 — keep the selection on refusal (no clearing), so a remounted volume recovers without user
  action.
* D5 — renderer copy points to Settings for puzzle/engine (where `DirectorySetting` re-selects
  all three domains) and keeps the Databases page's in-alert chooser; no new chooser buttons on
  puzzle/engine surfaces.

### plan-r2.md

# Plan: an unavailable persisted active root is refused and surfaced, never replaced by a default

## Goal

When the user has a database, puzzle or engine root selected and that selection is currently
unusable, the native command that resolves the active root returns a typed, `rootFailure`-labelled
refusal instead of silently creating and activating an app-owned default. The renderer turns that
refusal into a sentence that tells the user the chosen folder is unavailable and where to choose
another. "No selection yet" keeps today's default creation. The selection itself is kept, so a
remounted or restored folder becomes usable again without re-selection.

Finding: `f-20260917-12` (cluster of one, area `app-startup`, entry `build`). Inherited issue IDs
from `tasks/handoffs/2026-09-17-f-20260914-36-review.md`: **R2-03** (behaviour half: the
`Ok(None)` mapping and the silent default), **R12-01** and **R13-01** (no renderer availability
channel; production descriptors hard-code `Available`). This plan closes all three.

## MANDATE

Verbatim from `f-20260917-12` in `tasks/findings.md`:

* **Defect:** `active_*_root()` refreshes the entry and returns `Ok(None)` whenever it is not `Available`. The caller cannot tell "the root the user chose is currently unusable" from "the user never chose one", and answers both by creating and activating an app-owned default directory. A user whose chosen database, puzzle or engine root is temporarily unavailable — an unmounted volume, a renamed parent, a changed identity, or a path-authority entry the registry could not bind — is therefore silently moved to a different, empty workspace instead of being told. Nothing in the descriptor surface or the renderer can express the difference: the production descriptors report `Available` unconditionally, so even a correct backend availability answer never reaches the user.
* **Why it matters:** the user's data appears to have vanished and their selection appears to have been forgotten; the recovery — re-selecting the original root — is exactly the action the UI gives them no reason to take. It is also the reason a backend that correctly marks an entry unavailable cannot improve matters on its own.
* **Open question:** does an unavailable persisted active root become a typed refusal that the command surfaces and the renderer renders as a re-selection prompt, or does the default-creation path stay and gain a distinct "your previous workspace is unavailable" signal beside it — and what carries availability to the renderer, given that `PathDescriptor` is test-only and the production descriptors hard-code `Available`?
* **Annotation (2026-09-18):** this finding inherits issue IDs from `f-20260914-36`'s run; load `tasks/handoffs/2026-09-17-f-20260914-36-review.md` before plan review.

## Threat model and non-goals

* **Accidental input only.** The unusable states are the ones the MANDATE names: an unmounted
  volume, a renamed or deleted folder or parent, an identity change (folder replaced), a permission
  change, a registry entry that cannot be decoded or bound. No adversary racing the filesystem
  between refresh and re-proof is modelled; such a race must fail closed (a refusal), never open
  (a default).
* **Environments:** Linux, macOS and Windows. Labels come from `Error::root_failure_reason`
  (`io::ErrorKind`-based, already Windows-aware per `d-20261003-22`), so no platform-specific code
  is added.
* Not a security boundary change: no capability, scope, or path-containment rule moves.

    unlabelled, per `d-20261003-22`, and reaches the renderer's retry sentence.
* Root-site classification (P11): `root_failure_reason` labels any `Io` whose `ErrorKind` is
  `NotFound` as `missing`, which adds Windows' absent-drive and absent-network-path codes for
  root sites only. `is_missing_entry_io` and every other consumer of the narrow missing-entry
  class stay unchanged. This also applies to the existing listing probe and default-root
  labelling, where an absent drive is equally a missing root (decision 6).
* Coverage: A1 refuses exactly the states `refresh_entry` classifies as unusable (P2) — a
  missing or renamed root or parent, an identity change, a parent that lost search permission, an
  undecodable stored path, and on Windows an absent drive or network share. A root that still
  resolves but whose own directory cannot be read or written refreshes `Available` (`refresh_entry`
  never opens it), is never replaced by a default today, and fails later at use time with an
  unlabelled error on the puzzle listing and engine install paths; no silent substitution happens
  there, so it is not this MANDATE's defect, and it is filed through the inbox
  (`20261004-201558-1657850-1791137758838966573-4.md`, issue U1-01).
* Ownership: the three accessors route through **one** private resolution helper in
  `PathAuthority` parameterised by the active id and the operation (rule 11 — three copies today);
  each accessor only wraps the returned `PathRef` into its handle/descriptor.
* State: the active id is **not** cleared on refusal, and no registry write happens on this path —
  the selection survives so P2's recomputation restores it after a remount. Nothing else in the
  registry changes.
* The load-time active-id filter (P6) is unchanged: it drops ids only for states no setter
  writes, and loading never skips an entry, so it cannot hide a user's selection behind `None`.

## Decisions and trade-offs

The contested points; every one is also listed under `## Decided autonomously`.

* D1 — refusal, not default-plus-signal. Creating the default while signalling would still move
  the user's new work into a different folder and split their data across two roots on recovery,
  and would require a second state to present beside the existing `rootFailure` channel.
* D2 — `rootFailure` on the error, not descriptor `availability`. A descriptor is minted only on
  success, so carrying "unavailable" in it would need a success path that hands the renderer an
  unusable handle. The existing descriptor `availability` fields are truthful at construction (P9)
  and stay as they are.
* D3 — label derived from re-proving through `workspace_root`, not from making `refresh_entry`
  return its reason. `refresh_entry` has five call sites (`f-20260914-36` R8-02) and its result is
  a cache; re-proof only runs on the refusal path and reuses the exact mapping `d-20261003-22`
  already validated.
* D4 — keep the selection on refusal (no clearing), so a remounted volume recovers without user
  action.
* D5 — renderer copy points to Settings for puzzle/engine (where `DirectorySetting` re-selects
  all three domains) and keeps the Databases page's in-alert chooser; no new chooser buttons on
  puzzle/engine surfaces.

### plan-r3.md

# Plan: an unavailable persisted active root is refused and surfaced, never replaced by a default

## Goal

When the user has a database, puzzle or engine root selected and that selection is currently
unusable, the native command that resolves the active root returns a typed, `rootFailure`-labelled
refusal instead of silently creating and activating an app-owned default. The renderer turns that
refusal into a sentence that tells the user the chosen folder is unavailable and where to choose
another. "No selection yet" keeps today's default creation. The selection itself is kept, so a
remounted or restored folder becomes usable again without re-selection.

Finding: `f-20260917-12` (cluster of one, area `app-startup`, entry `build`). Inherited issue IDs
from `tasks/handoffs/2026-09-17-f-20260914-36-review.md`: **R2-03** (behaviour half: the
`Ok(None)` mapping and the silent default), **R12-01** and **R13-01** (no renderer availability
channel; production descriptors hard-code `Available`). This plan closes all three.

## MANDATE

Verbatim from `f-20260917-12` in `tasks/findings.md`:

* **Defect:** `active_*_root()` refreshes the entry and returns `Ok(None)` whenever it is not `Available`. The caller cannot tell "the root the user chose is currently unusable" from "the user never chose one", and answers both by creating and activating an app-owned default directory. A user whose chosen database, puzzle or engine root is temporarily unavailable — an unmounted volume, a renamed parent, a changed identity, or a path-authority entry the registry could not bind — is therefore silently moved to a different, empty workspace instead of being told. Nothing in the descriptor surface or the renderer can express the difference: the production descriptors report `Available` unconditionally, so even a correct backend availability answer never reaches the user.
* **Why it matters:** the user's data appears to have vanished and their selection appears to have been forgotten; the recovery — re-selecting the original root — is exactly the action the UI gives them no reason to take. It is also the reason a backend that correctly marks an entry unavailable cannot improve matters on its own.
* **Open question:** does an unavailable persisted active root become a typed refusal that the command surfaces and the renderer renders as a re-selection prompt, or does the default-creation path stay and gain a distinct "your previous workspace is unavailable" signal beside it — and what carries availability to the renderer, given that `PathDescriptor` is test-only and the production descriptors hard-code `Available`?
* **Annotation (2026-09-18):** this finding inherits issue IDs from `f-20260914-36`'s run; load `tasks/handoffs/2026-09-17-f-20260914-36-review.md` before plan review.

## Threat model and non-goals

* **Accidental input only.** The unusable states are the ones the MANDATE names: an unmounted
  volume, a renamed or deleted folder or parent, an identity change (folder replaced), a permission
  change, a registry entry that cannot be decoded or bound. No adversary racing the filesystem
  between refresh and re-proof is modelled; such a race must fail closed (a refusal), never open
  (a default).
* **Environments:** Linux, macOS and Windows. Labels come from `Error::root_failure_reason`
  (`io::ErrorKind`-based, already Windows-aware per `d-20261003-22`), so no platform-specific code
  is added.
* Not a security boundary change: no capability, scope, or path-containment rule moves.

## Approach

### A1 — Active-root resolution distinguishes "no selection" from "unusable selection"

*MANDATE: "The caller cannot tell 'the root the user chose is currently unusable' from 'the user
never chose one'"; Open question: "a typed refusal that the command surfaces".*

* Required behaviour, for each of `active_database_root`, `active_puzzle_root`,
  `active_engine_root` (signatures unchanged: `Result<Option<_>, Error>`):
  * no active id recorded → `Ok(None)` (unchanged);
  * active id recorded, entry refreshes `Available` with directory shape and the domain's operation
    bit → `Ok(Some(..))` (unchanged);
  * active id recorded, anything else → `Err(e)` where `e` is the error from re-proving the root
    through `workspace_root` with the domain's operation, passed through `label_root_failure`. If
    the re-proof unexpectedly succeeds while the refresh said unusable, the result is
    `Err(Error::Conflict(..))` labelled `changed` (fail closed; the next request re-refreshes and
    recovers by itself). An error the mapping does not label (e.g. an unclassified `Io`) stays
    unlabelled, per `d-20261003-22`, and reaches the renderer's retry sentence.
* Root-site classification (P11): `root_failure_reason` labels any `Io` whose `ErrorKind` is
  `NotFound` as `missing`, which adds Windows' absent-drive and absent-network-path codes for
  root sites only. `is_missing_entry_io` and every other consumer of the narrow missing-entry
  class stay unchanged. This also applies to the existing listing probe and default-root
  labelling, where an absent drive is equally a missing root (decision 6).
* Coverage: A1 refuses exactly the states `refresh_entry` classifies as unusable (P2) — a
  missing or renamed root or parent, an identity change, a parent that lost search permission, an
  undecodable stored path, and on Windows an absent drive or network share. A root that still
  resolves but whose own directory cannot be read or written refreshes `Available` (`refresh_entry`
  never opens it), is never replaced by a default today, and fails later at use time with an
  unlabelled error on the puzzle listing and engine install paths; no silent substitution happens
  there, so it is not this MANDATE's defect, and it is filed through the inbox
  (`20261004-201558-1657850-1791137758838966573-4.md`, issue U1-01).
* Ownership: the three accessors route through **one** private resolution helper in
  `PathAuthority` parameterised by the active id and the operation (rule 11 — three copies today);
  each accessor only wraps the returned `PathRef` into its handle/descriptor.
* State: the active id is **not** cleared on refusal, and no registry write happens on this path —
  the selection survives so P2's recomputation restores it after a remount. Nothing else in the
  registry changes.
* The load-time active-id filter (P6) is unchanged: it drops ids only for states no setter
  writes, and loading never skips an entry, so it cannot hide a user's selection behind `None`.

### A2 — Commands propagate the refusal and create a default only for "no selection"

*MANDATE: "answers both by creating and activating an app-owned default directory"; "silently
moved to a different, empty workspace".*

* `get_database_workspace`, `get_engine_workspace`, and every command reaching
  `active_or_default_puzzle_workspace` propagate A1's `Err` unchanged (already the shape of their
  `?`), so no app-owned default directory is created, registered or activated when a selection
  exists but is unusable. The default path runs only on `Ok(None)`.
* `issue_puzzle_workspace_blocking`'s post-activation read keeps its contract; an `Err` from it
  now carries the label instead of the generic `Conflict("selected puzzle workspace became
  unavailable")`.
* Doc comments on these commands state the new contract (the `get_database_workspace` comment
  "Returns the active database root when set and available. Otherwise …" is wrong after A1).
* The source test `app_owned_default_roots_are_pinned_to_their_call_sites` (`main.rs`
  `blocking_offload_scans` module) and the gateway-nesting scans must stay green; if a phase moves
  a default-creation call, the pin moves with it in the same phase.

### A3 — The renderer says which folder is unavailable and where to choose another

*MANDATE: "instead of being told"; Open question: "the renderer renders as a re-selection
prompt"; "what carries availability to the renderer".*

* Carrier: the optional `rootFailure` field on the error payload (`d-20261003-21`) — the renderer
  reads only that field, never message text. Descriptor `availability` fields are not the carrier
  (decision D2).
* One shared renderer primitive maps a `rootFailure` label to a domain sentence, for three domains
  (database, puzzle, engine). The Databases page's existing five-sentence record moves into it
  unchanged (same keys, same text), and `notifyUnlessCancelled`'s single `changedMessage` override
  generalises to that per-label record, with every existing `changedMessage` caller migrated
  (rule 11; no second override mechanism remains).
* Sentences (en-US source; every catalogue gets the key):
  * database: the existing `Databases.LoadError.*` sentences (no new strings).
  * puzzle (new): changed — "This puzzle folder changed. Choose another in Settings."; missing —
    "This puzzle folder is no longer available. Choose another in Settings."; unusable — "This
    puzzle folder cannot be opened. Choose another in Settings."; permission — "ChessFable is not
    allowed to read this puzzle folder. Choose another in Settings."
  * engine (new): the same four, with "engine folder".
  * No `too-large` sentence for puzzle/engine: A1 never produces that label (it is raised only at
    listing bounds, `d-20261003-21`), and the primitive falls back to the backend message for any
    label a domain record does not carry.
* Surfaces (P7, P8), each passing its domain to the shared notifier or primitive:
  * Databases page: unchanged presentation (alert + "Choose database folder"); proven to render
    for a `get_database_workspace` rejection, not only a listing rejection.
  * `AddDatabase` (both root-acquisition sites) and `AccountCard`'s import acquisition: database
    sentences.
  * `Puzzles` listing (workspace + list), `AddPuzzle` folder pick and download destination: puzzle
    sentences; on refusal the list is cleared as today.
  * `AddEngine`, `UpgradeEngineModal` (catalog install) and `OpenFolderButton`: engine sentences.
    `OpenFolderButton` gains a rejection path through the shared notifier (today an unhandled
    rejection — `async-resource-invariants.md`: every async operation has an error path).
* Unlabelled refusals keep today's behaviour on every surface (backend message, or the retry
  sentence on the Databases page).

### A4 — Real-IPC proof that the refusal reaches the page and no default is created

*MANDATE: "a backend that correctly marks an entry unavailable cannot improve matters on its own".*

* One committed `pnpm verify:app` check in `scripts/verify-app.mjs`, in the style of the
  `default-root-unusable` check (`d-20261003-26`): in an isolated profile, the Databases page
  activates a database root; the harness then makes that root's folder missing (rename it away)
  and revisits the Databases page; the page must show the RootMissing sentence and the "Choose
  database folder" chooser, and `<app-data>/db` must not have been (re)created by that visit. A
  staged-failure record (A1 reverted → FAIL) is added beside the existing one.
* Not a push gate (needs a compositor); run in the browser-verification stage after `pnpm build`.

## Decisions and trade-offs

The contested points; every one is also listed under `## Decided autonomously`.

* D1 — refusal, not default-plus-signal. Creating the default while signalling would still move
  the user's new work into a different folder and split their data across two roots on recovery,
  and would require a second state to present beside the existing `rootFailure` channel.
* D2 — `rootFailure` on the error, not descriptor `availability`. A descriptor is minted only on
  success, so carrying "unavailable" in it would need a success path that hands the renderer an
  unusable handle. The existing descriptor `availability` fields are truthful at construction (P9)
  and stay as they are.
* D3 — label derived from re-proving through `workspace_root`, not from making `refresh_entry`
  return its reason. `refresh_entry` has five call sites (`f-20260914-36` R8-02) and its result is
  a cache; re-proof only runs on the refusal path and reuses the exact mapping `d-20261003-22`
  already validated.
* D4 — keep the selection on refusal (no clearing), so a remounted volume recovers without user
  action.
* D5 — renderer copy points to Settings for puzzle/engine (where `DirectorySetting` re-selects
  all three domains) and keeps the Databases page's in-alert chooser; no new chooser buttons on
  puzzle/engine surfaces.

## Decided autonomously

Recorded here for the adopting session, which records each through
`./scripts/findings.py record-decision` before implementation (`full auto`).

1. **Question:** Does an unavailable persisted active root become a typed refusal, or does the
   default stay with a distinct signal? **Chosen:** typed refusal (A1/A2); default only when no
   selection exists. **Rejected:** default plus signal (splits user data across two roots; two
   states to present); clearing the selection on refusal (loses the recovery P2 gives for free).
   **Reason:** precedent `d-20261003-21`–`d-20261003-23` (root failures are refusals presented as
   "… Choose another."), MANDATE "instead of being told". **Governs:** f-20260917-12.
   **Reversal path:** an explicit "use the default folder" action on the refusal presentation.
2. **Question:** What carries availability to the renderer? **Chosen:** the existing
   `rootFailure` label on the refusal. **Rejected:** a production `PathDescriptor` or relying on
   descriptor `availability` (a descriptor exists only for a usable root). **Governs:**
   f-20260917-12. **Reversal path:** a command that lists registered roots with their
   availability, at which point a descriptor field becomes meaningful.
3. **Question:** Where does the refusal's label come from? **Chosen:** re-prove through
   `workspace_root` and `label_root_failure`; fail closed to `changed` if the re-proof disagrees
   with the refresh. **Rejected:** returning the reason from `refresh_entry` (five call sites, a
   cache result); a fixed label for every unusable selection (tells a user with a permission
   problem to look for a missing folder). **Governs:** f-20260917-12.
4. **Question:** What do puzzle and engine surfaces say? **Chosen:** four sentences per domain
   ending "Choose another in Settings.", through one shared label→sentence primitive that also
   absorbs the Databases page record and `notifyUnlessCancelled`'s `changedMessage`.
   **Rejected:** raw backend message (untranslated, says nothing about re-selection); new chooser
   buttons on puzzle/engine surfaces (no MANDATE need: Settings already re-selects all three).

5. **Question:** How is the real IPC path proven? **Chosen:** one `verify:app` check with a
   staged-failure record. **Rejected:** container e2e only (mocked IPC); a scratch script (not
   re-runnable). **Governs:** f-20260917-12. Precedent `d-20261003-26`.
6. **Question:** Does an absent Windows drive or network share on a root get a `rootFailure`
   label? **Chosen:** yes — `root_failure_reason` labels every `Io` of kind `NotFound` as
   `missing` at root sites; `is_missing_entry_io` stays narrow. **Rejected:** widening
   `is_missing_entry_io` (it also drives non-root consumers and the `MissingResource` category,
   deliberately narrow); leaving them unlabelled (an unmounted volume, the MANDATE's first
   example, would get "Please try again" and no chooser on Windows). **Reason:** new evidence for
   `d-20261003-22`'s `Io(NotFound) → missing` row: its implementation used the narrow class, which
   omits Windows' `ERROR_INVALID_DRIVE`, `ERROR_BAD_NETPATH`, `ERROR_BAD_NET_NAME` (`error.rs`
