# Plan: refuse to write a keyring secret whose registry record startup cannot find (f-20260912-01)

## Goal

MANDATE (fixed across rounds): a credential directory can be renamed and recreated, or removed,
while the application runs. The retained `AuthorizedDir` in `CredentialManager`
(`src-tauri/src/credentials.rs`, `registry_dir`) then keeps journalling into the detached inode.
`store_lichess_token` stores a bearer token in the OS keyring whose only registry record is in
the detached directory. The next startup opens the replacement directory, finds an empty
registry, and that keyring entry becomes an orphaned live Lichess token that nothing can
enumerate or revoke. Close this so that **no keyring write the application performs leaves a
secret whose governing registry record is not at the location a fresh startup resolves**, on
both the add path and the re-authentication path, on every platform that compiles today.

Acceptance ("tracked" = a record for the handle exists in the registry at the location a fresh
startup resolves; "untracked" = the opposite):

1. Add after the credential directory was replaced (renamed away + recreated, or renamed away
   and absent) → the call fails and `CredentialStore::set` is never called. Re-auth under the
   same condition → the call fails, `set` is never called, and the pre-existing secret is
   unchanged (the call wrote nothing).
2. Replacement at any point after the pre-check — during `set` (success or write-then-error),
   or before/during the final `Active` journal write (whether that write succeeds or fails) —
   → the call fails and, except in the acceptance-4 edge, leaves no untracked secret for the
   handle: the secret is deleted, or (acceptance 3) a `PendingDelete` for it is at the startup
   location.
3. If the compensating `delete` fails and the tombstone path succeeds (durable commit,
   verified at the startup location after the write), the call still fails, and the next
   `initialize` deletes the secret through that `PendingDelete`.
4. If the keyring `delete` fails **and** the tombstone path does not end in a durable, verified
   write (reacquire, load or write fails; the post-write check finds the directory replaced;
   or the write commits with `CommittedDurabilityUncertain`), the call returns
   `Error::CredentialRecoveryRequired` (the irreducible double-storage-failure edge; see
   "Why the double failure is irreducible").
5. No replacement → behaviour unchanged; every existing test except the one that pins the
   defect (`retained_credential_directory_descriptor_is_used_after_rename`,
   `credentials.rs:1257`) stays green unmodified.

## Approach

### O1 — Startup-location verification in `infra::path_authority`

Startup resolves the credential directory by pathname: `AppDataDir::for_app` takes
`app.path().app_data_dir()` (the *requested* spelling), canonicalises its existing prefix, and
`ensure_app_owned_default_dir` opens the `credentials` leaf no-follow beneath it
(`mod.rs:2416-2460`, `:2516-2537`). The ground truth for "will startup find this record" is
therefore that **pathname**, not any retained descriptor. A retained app-data *parent
descriptor* (the finding's first suggestion) would not detect a replaced app-data directory or a
retargeted ancestor symlink, both of which also move startup away from the records.

* `AppDataDir` retains the requested spelling in a private field beside the canonical path and
  descriptor. It is used **only** to name the startup location; it never derives a registered
  path, so the canonical-derivation property its doc comment states is unchanged (update the
  doc comment to say exactly that).
* New opaque, `Clone` value `DefaultRootLocation` (holds `requested.join(root.leaf())`),
  obtained from `AppDataDir::startup_location(root: AppOwnedDefaultRoot)`. Its constructor is
  that method only; no caller can build one from an arbitrary path.
* `AuthorizedDir::resides_at(&self, location: &DefaultRootLocation) -> Result<bool, Error>`:
  reads the pathname's identity with the existing cross-platform `identity(path)` helper
  (`mod.rs:3182`; lstat on unix, no-follow handle on Windows) and compares it with this
  directory's retained identity. `NotFound` → `Ok(false)` (startup would create an empty
  directory). A link-like leaf → `Ok(false)` (startup refuses a symlinked leaf, so no record
  there is findable). Any other error propagates. Read-only: creates, opens for write, and
  modifies nothing.
* `DefaultRootLocation::reacquire(&self) -> Result<AuthorizedDir, Error>`: performs exactly
  startup's resolution (`AppDataDir::acquire(requested)` then `ensure_app_owned_default_dir`),
  including its creation of missing components and the root's private mode. Used only by the
  O2 tombstone fallback. It routes through the existing helpers; no second resolution
  implementation.
* Identity soundness: the retained descriptor keeps the old inode allocated for the manager's
  lifetime, so a replacement directory cannot receive the same `(dev, ino)` / volume+index pair.

Obstacles recorded in the finding, re-measured: (1) no parent descriptor — not needed, the
pathname is the truth; (2) `VerifiedIdentity` opaque — the comparison lives inside the module
that owns it; (3) `entry_identity_at` `#[cfg(unix)]` — no longer true (`infra/fs.rs:4303` has a
Windows impl), and O1 uses `identity(path)`, which has both; (4) non-atomic check — O2
brackets the keyring write; (5) re-auth branch missed — O2 puts the check in both
secret-writing branches, not in `persist_locked`.

### O2 — Checked keyring writes in `CredentialManager` (depends on O1)

* `registry_dir` holds the retained `Arc<AuthorizedDir>` together with its
  `DefaultRootLocation`; `initialize` obtains the location from the `AppDataDir` it already
  receives. Holding the `Arc` keeps `d-20260912-02`'s deadlock reasoning.
* **Location check** (private): `Ok(())` when no directory is bound (the uninitialised
  default path, identical to `persist_locked`'s `None` branch); otherwise `resides_at`, where
  `Ok(false)` is "detached". A verification *error* is treated as detached (fail closed) — before
  `set` it refuses, after `set` it compensates.
* **One shared checked-write helper** used by both secret-writing branches (add and
  re-authentication) — never two copies of the sequence. Contract, in order:
  1. Pre-check **before any write of the call** (before the add path's `PendingAdd` journal,
     before the re-auth `set`). Detached → return
     `Error::CredentialFailure("credential directory was replaced while the application was
     running")` (renderer sees the fixed "Credential operation failed"; `error.rs:1071-1075`,
     no binding change). Nothing was written, nothing to compensate.
  2. Caller's pre-`set` journal step (add: `PendingAdd`, unchanged), then `store.set`.
  3. Caller's post-`set` journal step on success (add: `Active`, unchanged; re-auth: none).
  4. **Final check after the last registry write of the call, on every exit path once `set`
     was attempted** — `set` success, `set` error (write-then-error is a documented outcome,
     `credentials.rs:390-395`, `WriteThenErrorStore`), and the `Active` journal error. Live →
     the existing outcome of that path is returned unchanged (including today's
     `CredentialRecoveryRequired` on a `set` error with a live `PendingAdd`). Detached →
     compensate (next bullet), remove the add path's in-memory entry, and return the
     replaced-directory error.
* **Compensation** for a detached outcome: `store.delete(key)` (idempotent on `NoEntry`,
  `credentials.rs:134-138`). This deletes a secret this call may have written; the existing
  no-compensation comment (`:391-395`) forbids dropping the *journal record* after a failed
  `set`, not deleting the secret, and stays true. If `delete` fails → **tombstone**:
  `location.reacquire()`, `load_registry` on it, insert `PendingDelete(metadata)` for the
  handle, write it through `persistence.write`, then **`resides_at` on the reacquired
  directory** — the tombstone counts only if that directory is still the startup location
  after the write. The next `initialize` then deletes the secret in `reconcile` (`:512-518`).
  Any failure on the tombstone path (reacquire, load, write, the post-write check) and a
  `RegistryCommit::CommittedDurabilityUncertain` tombstone commit (visible but not durable, so
  a crash can lose it) → `Error::CredentialRecoveryRequired`; an uncertain tombstone is left in
  place, never compensated, matching `AtomicRegistryPersistence`'s rule (`:221-226`).
* **Why the double failure is irreducible.** A keyring `set` is an external call of unbounded
  duration (a Secret Service unlock prompt), and the user can replace the directory at any
  instant during it. Once `set` has returned — successfully or write-then-error — a secret may
  exist, and exactly two operations can make it non-orphaned: delete it from the keyring, or
  record it at the startup location. If both stores refuse the write, no code path in the
  process can establish either, whatever the design; the only thing left is to report it. The
  plan therefore guarantees "no untracked secret unless both the keyring and the startup
  location refuse a write in the same call", and reports that edge as
  `CredentialRecoveryRequired`. A keyring-side handle index (rejected below) has the same edge:
  its own write can fail after the secret's.
* After the final check passes, the governing record is verified at the startup location
  after the call's last write; a later rename carries the record with it, exactly like moving
  the directory while the app is closed — a user data-location action, not an application
  write.
* `remove`, `reconcile`, `initialize` and `persist_locked` are unchanged.

### O3 — Tests (unix-gated where they rename a directory; logic is cross-platform)

In `credentials.rs` tests, driving a real `AppDataDir::for_test(tempdir)` and store /
persistence doubles that perform the replacement at the named moment:
* acceptance 1, add: "renamed + recreated" and "renamed, absent" → replaced-directory
  `CredentialFailure`, a recording store shows no `set`, and a recording persistence double
  shows no registry write (the pre-check precedes the `PendingAdd` journal). Re-auth: an `Active` account with a
  stored secret; after replacement the call fails, no `set`, and the stored value is unchanged.
* acceptance 1, verification error: the app-data directory made unreadable (`chmod 000`,
  restored in the test's cleanup) so `resides_at` errors → the call fails before `set`.
* acceptance 2 (add and re-auth): replacement inside a successful `set`; inside a
  write-then-error `set`; replacement in a persistence double before it delegates the
  `Active` write successfully; and replacement followed by a failing `Active` write → each
  call fails and the store holds no secret for the handle.
* acceptance 3: a store whose `delete` fails → the call returns an error; the recording store
  shows `set` succeeded and `delete` was attempted; a fresh `CredentialManager::initialize` on
  the same app-data directory, with a working store seeded with that secret, deletes it.
* acceptance 2, verification error after `set` (add and re-auth): the store double's `set`
  makes the app-data directory unreadable (`chmod 000`, restored in cleanup) → the call fails
  and the store holds no secret for the handle.
* acceptance 3, leaf absent: the directory is renamed away inside `set` and not recreated,
  `delete` fails → `reacquire` recreates the leaf and the tombstone is found by a fresh
  `initialize`.
* acceptance 4, each with a recording persistence double that proves the tombstone write was
  attempted — except (b) and (e), where it proves it was not: (a) the tombstone write fails after a successful
  `reacquire`; (b) the startup leaf is a regular file, so `reacquire` refuses; (c) the
  persistence double renames the reacquired directory away and recreates it right after a
  successful tombstone write, so the post-write check fails; (d) the tombstone write returns
  `CommittedDurabilityUncertain` → each returns `CredentialRecoveryRequired`; (e) the startup
  location's registry file holds invalid JSON, so `load_registry` fails → tombstone write not
  attempted, `CredentialRecoveryRequired`. In (d) a fresh `initialize` on the same app-data
  directory with a store seeded with the secret deletes it, proving the uncertain tombstone was
  left in place.
* acceptance 5: rewrite `retained_credential_directory_descriptor_is_used_after_rename`
  (`credentials.rs:1257`) into the refusal anchor for acceptance 1; every other existing
  test unmodified.
In `path_authority` tests: `resides_at` true for the freshly ensured root, false after rename
+ recreate, false after rename with nothing recreated, false for a symlink at the leaf, `Err`
for an unreadable parent; `reacquire` yields a directory `resides_at` accepts.

## Decisions and trade-offs

* **Detect-and-refuse by pathname identity, bracketed around the keyring write** — chosen.
* Rejected: **declaring the replaced directory unsupported and documenting the orphan** — the
  guard is writable; rule 4.
* Rejected: **a keyring-side index of handles** so startup can delete secrets absent from the
  registry. It would be a second source of truth for which accounts exist, with no transaction
  across the two stores, and Windows Credential Manager caps a credential blob at 2560 bytes, so
  it imposes a user-visible account limit; the registry already is the journal.
* Rejected: **a retained app-data parent descriptor + `entry_identity_at`** — misses a replaced
  app-data directory and retargeted ancestors, because startup resolves by pathname.
* Rejected: **rebinding the manager to the replacement directory** — the in-memory registry
  would describe a directory it was not loaded from; restart is the recovery and reloads it.
  The tombstone touches the startup location only on the double-failure path and writes one
  `PendingDelete`, which `reconcile` already knows how to finish.
* Accepted consequence of identity comparison: a directory **copied** and swapped in (same
  records, new inode) is treated as detached, so the call deletes the secret it wrote — on
  re-auth too, where the copied registry still holds the `Active` record, so the next startup
  drops that account. That is the safe direction (a login the user repeats, never an orphaned
  token); a content comparison of the live registry would avoid it at the cost of parsing the
  startup registry on every keyring write, which the MANDATE does not require.
* Rejected: **the check inside `persist_locked`** — misses the re-auth branch and does not
  bracket the keyring write.

## Risks / open questions

* **Residual (irreducible, argued in O2):** the keyring `delete` and the verified
  startup-location tombstone write both failing inside one call → `CredentialRecoveryRequired`.
* **Residual (accepted, outside the MANDATE):** once a record is verified at the startup
  location, a later user rename/restore of the directory moves or drops it — identical to doing
  so while the app is closed. Documented in the `store_lichess_token` comment and in the
  decision record.
* Windows: renaming a directory with an open handle generally fails there, so the rename tests
  are unix-only; the code path compiles and runs on Windows through `identity()`.

## Not part of this task

* `remove` — deleting a secret never creates an orphan; unchanged.
* A new renderer-visible error variant for the replaced-directory case (binding change).
* Enumerating or cleaning pre-existing orphans. `f-20260830-06` (Windows OAuth doors).
* Any change to `remove`, reconciliation, or registry format.
