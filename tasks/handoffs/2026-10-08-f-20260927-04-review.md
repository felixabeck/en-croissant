### plan-r1.md

# Plan: a recorded tree-removal intent keeps its authority over undecodable bytes (f-20260927-04)

## Goal

A tab id that has left the workspace keeps its recorded removal intent until the stored value under
that id is actually gone, whether or not the value decodes as a tree, so a failed first removal of
undecodable bytes is retried on the next load instead of leaking session quota for the rest of the
session. The startup orphan sweep stays decodable-only.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260927-04:

> * **Where:** `src/state/workspace.ts` `reconcilePendingTreeRemovals` (the `tabStorage.isStoredTree(id)` filter on prior intents); `src/state/store/tabStorage.ts` `removeOrphanedTrees` / `storedTreeKeys` (sweep only yields keys that decode as trees).
> * **Defect:** when a tab id leaves the workspace (tab close through `closeWorkspaceTabAtom`, or the owner of an import replaced by `replaceNewTab`), its id is recorded in `treeOwnershipPendingRemovalIds`. If the immediate `tabStorage.remove` also fails and the stored bytes under that id are undecodable, the next workspace commit or load drops the intent, because `reconcilePendingTreeRemovals` keeps only prior ids for which `isStoredTree` is true. The startup orphan sweep also skips undecodable values. The bytes then stay in sessionStorage for the rest of the session, counted against the shared ~5 MB quota.
> * **Evidence:** `workspace.ts:147` filters prior intents with `tabStorage.isStoredTree(id)`; `tabStorage.ts:677-682` returns false for an undecodable value; `tabStorage.ts:685-687,720` sweeps only keys that pass `isStoredTree`. Reported by `review-persisted-state` (confidence 88) on the f-20260910-09 cumulative diff; this pre-existing behaviour of the shared close/reclaim path is not introduced by that diff.
> * **Open question:** once no workspace tab owns an id, may its undecodable bytes be removed by the recorded intent, or must `persisted-state.md`'s "keep undecodable bytes; only an explicit discard removes the last workspace-owned unreadable value" still apply to an id that is no longer workspace-owned? If yes, the intent must survive undecodability; if no, the leak is by design and needs a bound.

## Approach

### O1 — Removal-intent authority predicate

MANDATE: "once no workspace tab owns an id, may its undecodable bytes be removed by the recorded
intent … If yes, the intent must survive undecodability".

Answer (decided autonomously, see Decisions): yes, for an id in the tree repository's own key
namespace. `TabStorageRepository` gains one public predicate (executor names it) that answers
"does a recorded removal intent for this id still have a value to remove":

* `true` when the value decodes as a tree (today's `isStoredTree`), whatever the id;
* `true` when the value is present (non-null) but undecodable **and** the id is a UUID
  (`tabIdSchema`, the namespace `newWorkspaceId` and repair allocate from, P8/P10);
* `false` when the value is absent, and `false` for a present undecodable value under a non-UUID
  id (a legacy id that may coincide with another store's key — P11/P12's protection stays).

A `getItem` that throws propagates exactly as `isStoredTree` does today (no new failure
semantics). `isStoredTree` keeps its meaning and stays the predicate of the sweep and the
ownership snapshot (O3).

### O2 — Both explicit-intent replays use O1

MANDATE: "the next workspace commit or load drops the intent, because
`reconcilePendingTreeRemovals` keeps only prior ids for which `isStoredTree` is true".

* `reconcilePendingTreeRemovals` filters prior ids with O1 instead of `isStoredTree`. Effect at
  commit (P4): an undecodable UUID intent survives every later commit; at load (P6) it survives
  reconciliation and is removed by the existing `removeKnownTreesSafely(pendingRemovalIds)`; a
  removal that fails again keeps it pending for the next load; once the key is absent the next
  reconcile prunes it. The overflow branch (P1) retries such ids like any other prior id.
* `replayFailedAdmissions` (P7) uses the same O1 predicate for its marked, unretained UUID id, so
  undecodable bytes under a refused-admission marker are removed rather than abandoned when the
  marker is cleared. Authority: rule 4b (same file, same defect class — an explicit removal intent
  ended by undecodability) and global rule 11 (the second consumer of the same "intent still has
  something to remove" check goes through the same predicate). Marker ids are UUIDs by
  construction (P7), so for this caller O1 reduces to "value present".

Bound: intents remain capped by `MAX_PENDING_TREE_REMOVALS` (100) with the existing overflow
error; an undecodable intent whose removal keeps failing occupies a slot exactly as a decodable
one does today. No new persisted field, schema change or state file.

### O3 — The orphan sweep stays decodable-only

MANDATE: "The startup orphan sweep also skips undecodable values."

## Decisions and trade-offs

* **D1 (decided autonomously; recorded by the adopting session).** Question: once no workspace
  tab owns an id, may a recorded removal intent remove its undecodable bytes? Chosen: yes for a
  UUID id, through intent replay only; the sweep stays decodable-only; a non-UUID id keeps the
  decodable-tree requirement. Rejected: (a) keep d-20260925-07 as is and bound the leak — the
  bytes are already deleted by the *first* attempt (P5, P6 call `remove` without a decodability
  check), so the retry having less authority than the first attempt is the defect, not a policy,
  and "bound" would only mean "leak until the session ends"; (b) let the sweep remove undecodable
  unowned UUID keys — no intent proves ownership, and d-20260925-03 already rejected UUID-based
  sweeping; (c) persist a fingerprint of the bytes with each intent — a schema change and a
  synchronous hash of up to megabytes per close for protection only against the crafted-writer
  case the threat model excludes. New evidence relative to d-20260925-07: that decision treated
  "undecodable" and "non-tree" as one class; this finding shows a UUID-keyed undecodable value
  under a recorded intent is the repository's own abandoned tree, which d-20260925-07's
  `"other-session-value"` concern (a non-UUID foreign key) does not cover. Product impact: none
  visible — it changes only whether already-closed bytes keep consuming session quota.
  Reversal path: restore `isStoredTree` in the two O2 call sites and revert the O4 sentence.
* **Persisted-state rule scope.** "Only an explicit successful discard may remove the last
  workspace-owned unreadable value" is about workspace-owned ids; every O2 replay excludes
  retained ids (P1, P7), so no workspace-owned value becomes removable by this change.
* **Tier.** Stays `build`: the change reverses part of a recorded decision on a persistence
  trust boundary (deleting session values), an area whose previous plans needed five push-review
  repairs (d-20260925-03 → -08).

## Risks / open questions

* A non-UUID legacy migrated source whose first removal fails (P6) still loses its intent on the
  next load if its bytes are undecodable — named known limit, kept deliberately by O1's third row
  to preserve P11/P12. It needs a legacy workspace, a refused removal and undecodable bytes at

* An undecodable UUID value that is *not* the repository's (a foreign store that happens to
  write a key equal to a closed tab's random UUID) would be removed by the intent — accepted:
  infeasible by accident (P8 allocation, 122 random bits), and the crafted case is out of the

# Plan: a recorded tree-removal intent keeps its authority over undecodable bytes (f-20260927-04)

## Goal

A tab id that has left the workspace keeps its recorded removal intent until the stored value under
that id is actually gone, whether or not the value decodes as a tree, so a failed first removal of
undecodable bytes is retried on the next load instead of leaking session quota for the rest of the
session. The startup orphan sweep stays decodable-only.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260927-04:

> * **Where:** `src/state/workspace.ts` `reconcilePendingTreeRemovals` (the `tabStorage.isStoredTree(id)` filter on prior intents); `src/state/store/tabStorage.ts` `removeOrphanedTrees` / `storedTreeKeys` (sweep only yields keys that decode as trees).
> * **Defect:** when a tab id leaves the workspace (tab close through `closeWorkspaceTabAtom`, or the owner of an import replaced by `replaceNewTab`), its id is recorded in `treeOwnershipPendingRemovalIds`. If the immediate `tabStorage.remove` also fails and the stored bytes under that id are undecodable, the next workspace commit or load drops the intent, because `reconcilePendingTreeRemovals` keeps only prior ids for which `isStoredTree` is true. The startup orphan sweep also skips undecodable values. The bytes then stay in sessionStorage for the rest of the session, counted against the shared ~5 MB quota.
> * **Evidence:** `workspace.ts:147` filters prior intents with `tabStorage.isStoredTree(id)`; `tabStorage.ts:677-682` returns false for an undecodable value; `tabStorage.ts:685-687,720` sweeps only keys that pass `isStoredTree`. Reported by `review-persisted-state` (confidence 88) on the f-20260910-09 cumulative diff; this pre-existing behaviour of the shared close/reclaim path is not introduced by that diff.
> * **Open question:** once no workspace tab owns an id, may its undecodable bytes be removed by the recorded intent, or must `persisted-state.md`'s "keep undecodable bytes; only an explicit discard removes the last workspace-owned unreadable value" still apply to an id that is no longer workspace-owned? If yes, the intent must survive undecodability; if no, the leak is by design and needs a bound.
> * **Proof required:** real-store test: a tab with undecodable stored bytes is closed while `removeItem` fails; after reload and a later commit the bytes are either removed or retained under an explicit, bounded, tested rule.

## Approach

### O1 — Removal-intent authority predicate

MANDATE: "once no workspace tab owns an id, may its undecodable bytes be removed by the recorded
intent … If yes, the intent must survive undecodability".

Answer (decided autonomously, see Decisions): yes, for an id in the tree repository's own key
namespace. `TabStorageRepository` gains one public predicate (executor names it) that answers
"does a recorded removal intent for this id still have a value to remove":

* `true` when the value decodes as a tree (today's `isStoredTree`), whatever the id;
* `true` when the value is present (non-null) but undecodable **and** the id is a UUID
  (`tabIdSchema`, the namespace `newWorkspaceId` and repair allocate from, P8/P10);
* `false` when the value is absent, and `false` for a present undecodable value under a non-UUID
  id (a legacy id that may coincide with another store's key — P11/P12's protection stays).

A `getItem` that throws propagates exactly as `isStoredTree` does today (no new failure
semantics). `isStoredTree` keeps its meaning and stays the predicate of the sweep and the
ownership snapshot (O3).

### O2 — The pending-removal replay uses O1

MANDATE: "the next workspace commit or load drops the intent, because
`reconcilePendingTreeRemovals` keeps only prior ids for which `isStoredTree` is true".

* `reconcilePendingTreeRemovals` filters prior ids with O1 instead of `isStoredTree`. Effect at
  commit (P4): an undecodable UUID intent survives every later commit; at load (P6) it survives
  reconciliation and is removed by the existing `removeKnownTreesSafely(pendingRemovalIds)`; a
  removal that fails again keeps it pending for the next load; once the key is absent the next
  reconcile prunes it. The overflow branch (P1) retries such ids like any other prior id.
* `replayFailedAdmissions` (P7) is **not** changed and keeps `isStoredTree` (corrected in round 2,
  R1-01). A marker's owner wrote either nothing or a decodable tree (P13), so undecodable bytes
  under a marked id were not written by that owner and P13's pinned contract protects them. A closed tab
  differs: its key is its own tree key for the whole life of the tab and may legitimately hold
  undecodable bytes when it leaves the workspace (P9: `new` tabs and `closeWorkspaceTabAtom` are
  ungated), which is why the first removal attempt (P5) already deletes them unconditionally. The
  two replays therefore use different predicates on purpose: the evidence each intent carries
  differs, so this is not a second copy of one concept (rule 11).

Bound: intents remain capped by `MAX_PENDING_TREE_REMOVALS` (100) with the existing overflow
error; an undecodable intent whose removal keeps failing occupies a slot exactly as a decodable
one does today. No new persisted field, schema change or state file.

### O3 — The orphan sweep stays decodable-only

MANDATE: "The startup orphan sweep also skips undecodable values."

No change to `removeOrphanedTrees`, `storedTreeKeys` or `snapshotStoredTreeKeys`. Without a
recorded intent nothing establishes that an unowned undecodable value belongs to the tree
repository (d-20260925-03's rejection of UUID-based sweeping stands); the intent, not the sweep,
is the authority. This is the explicit, bounded rule the MANDATE's proof allows for the sweep
case, and the persisted-state rule text says so (O4). O5's T6 pins it.

# Plan: a recorded tree-removal intent keeps its authority over undecodable bytes (f-20260927-04)

## Goal

A tab id that has left the workspace keeps its recorded removal intent until the stored value under
that id is actually gone, whether or not the value decodes as a tree, so a failed first removal of
undecodable bytes is retried on the next load instead of leaking session quota for the rest of the
session. The startup orphan sweep stays decodable-only.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260927-04:

> * **Where:** `src/state/workspace.ts` `reconcilePendingTreeRemovals` (the `tabStorage.isStoredTree(id)` filter on prior intents); `src/state/store/tabStorage.ts` `removeOrphanedTrees` / `storedTreeKeys` (sweep only yields keys that decode as trees).
> * **Defect:** when a tab id leaves the workspace (tab close through `closeWorkspaceTabAtom`, or the owner of an import replaced by `replaceNewTab`), its id is recorded in `treeOwnershipPendingRemovalIds`. If the immediate `tabStorage.remove` also fails and the stored bytes under that id are undecodable, the next workspace commit or load drops the intent, because `reconcilePendingTreeRemovals` keeps only prior ids for which `isStoredTree` is true. The startup orphan sweep also skips undecodable values. The bytes then stay in sessionStorage for the rest of the session, counted against the shared ~5 MB quota.
> * **Evidence:** `workspace.ts:147` filters prior intents with `tabStorage.isStoredTree(id)`; `tabStorage.ts:677-682` returns false for an undecodable value; `tabStorage.ts:685-687,720` sweeps only keys that pass `isStoredTree`. Reported by `review-persisted-state` (confidence 88) on the f-20260910-09 cumulative diff; this pre-existing behaviour of the shared close/reclaim path is not introduced by that diff.
> * **Open question:** once no workspace tab owns an id, may its undecodable bytes be removed by the recorded intent, or must `persisted-state.md`'s "keep undecodable bytes; only an explicit discard removes the last workspace-owned unreadable value" still apply to an id that is no longer workspace-owned? If yes, the intent must survive undecodability; if no, the leak is by design and needs a bound.
> * **Proof required:** real-store test: a tab with undecodable stored bytes is closed while `removeItem` fails; after reload and a later commit the bytes are either removed or retained under an explicit, bounded, tested rule.

## Threat model and non-goals

Frozen in round 1.

* **Accidental input only.** Covered: `sessionStorage.removeItem`/`getItem` throwing (quota or
  security refusal), stored tree bytes that fail tree validation (`decodeLegacyOrCompressed`
  returns null — garbage, an empty string, a tree shape the current schema rejects), legacy
  workspaces whose tab ids are arbitrary non-UUID strings that may coincide with another store's
  session key, and a persisted pending-removal list that names such a legacy id.
* **Not covered: a writer that crafts session-storage values.** Code that can write a
  schema-valid `workspace` envelope naming an arbitrary UUID already executes inside the renderer
  origin and can call `sessionStorage.removeItem` itself; this plan grants it nothing new.
* Environments: the Tauri webview (WebKitGTK on Linux, WKWebView on macOS, WebView2 on Windows),
  all with one origin-scoped `sessionStorage`; vitest with the repository's DOM test environment
  for proof. No platform-specific code is touched.

## Approach

### O1 — Removal-intent authority predicate

MANDATE: "once no workspace tab owns an id, may its undecodable bytes be removed by the recorded
intent … If yes, the intent must survive undecodability".

Answer (decided autonomously, see Decisions): yes, for an id in the tree repository's own key
namespace. `TabStorageRepository` gains one public predicate (executor names it) that answers
"does a recorded removal intent for this id still have a value to remove":

* `true` when the value decodes as a tree (today's `isStoredTree`), whatever the id;
* `true` when the value is present (non-null) but undecodable **and** the id is a UUID
  (`tabIdSchema`, the namespace `newWorkspaceId` and repair allocate from, P8/P10);
* `false` when the value is absent, and `false` for a present undecodable value under a non-UUID
  id (a legacy id that may coincide with another store's key — P11/P12's protection stays).

A `getItem` that throws propagates exactly as `isStoredTree` does today (no new failure
semantics). `isStoredTree` keeps its meaning and stays the predicate of the sweep and the
ownership snapshot (O3).

### O2 — The pending-removal replay uses O1

MANDATE: "the next workspace commit or load drops the intent, because
`reconcilePendingTreeRemovals` keeps only prior ids for which `isStoredTree` is true".

* `reconcilePendingTreeRemovals` filters prior ids with O1 instead of `isStoredTree`. Effect at
  commit (P4): an undecodable UUID intent survives every later commit; at load (P6) it survives
  reconciliation and is removed by the existing `removeKnownTreesSafely(pendingRemovalIds)`; a
  removal that fails again keeps it pending for the next load; once the key is absent the next
  reconcile prunes it. The overflow branch (P1) retries such ids like any other prior id.
* `replayFailedAdmissions` (P7) is **not** changed and keeps `isStoredTree` (corrected in round 2,
  R1-01). A marker's owner wrote either nothing or a decodable tree (P13), so undecodable bytes
  under a marked id were not written by that owner and P13's pinned contract protects them. A closed tab
  differs: its key is its own tree key for the whole life of the tab and may legitimately hold
  undecodable bytes when it leaves the workspace (P9: `new` tabs and `closeWorkspaceTabAtom` are
  ungated), which is why the first removal attempt (P5) already deletes them unconditionally. The
  two replays therefore use different predicates on purpose: the evidence each intent carries
  differs, so this is not a second copy of one concept (rule 11).

Bound: intents remain capped by `MAX_PENDING_TREE_REMOVALS` (100) with the existing overflow
error; an undecodable intent whose removal keeps failing occupies a slot exactly as a decodable
one does today. No new persisted field, schema change or state file.

### O3 — The orphan sweep stays decodable-only

MANDATE: "The startup orphan sweep also skips undecodable values."

No change to `removeOrphanedTrees`, `storedTreeKeys` or `snapshotStoredTreeKeys`. Without a
recorded intent nothing establishes that an unowned undecodable value belongs to the tree
repository (d-20260925-03's rejection of UUID-based sweeping stands); the intent, not the sweep,
is the authority. This is the explicit, bounded rule the MANDATE's proof allows for the sweep
case, and the persisted-state rule text says so (O4). O5's T6 pins it.

### O4 — Rule text and decision record

MANDATE: "must `persisted-state.md`'s 'keep undecodable bytes; only an explicit discard removes
the last workspace-owned unreadable value' still apply to an id that is no longer
workspace-owned?"

`.claude/rules/persisted-state.md`, the tab-tree bullet under DO: add one sentence — once
workspace metadata no longer owns a UUID tree key, its recorded pending-removal intent (tab
close, replaced import owner, migrated source) removes the stored value whether or not it
decodes, and retries until the key is absent; an unowned undecodable value with no recorded
intent is never swept, an intent under a non-UUID id still needs a decodable tree, and a
refused-admission marker removes only a decodable tree.
The adopting session records the decision (Decisions → D1) with `findings.py record-decision`,
superseding d-20260925-07 for its "non-tree value ends that authorization" clause only.

## Decisions and trade-offs

* **D1 (decided autonomously; recorded by the adopting session).** Question: once no workspace
  tab owns an id, may a recorded removal intent remove its undecodable bytes? Chosen: yes for a
  UUID id, through pending-removal replay only; the sweep and the refused-admission marker replay
  stay decodable-only; a non-UUID id keeps the decodable-tree requirement. Rejected: (a) keep d-20260925-07 as is and bound the leak — the
  bytes are already deleted by the *first* attempt (P5, P6 call `remove` without a decodability
  check), so the retry having less authority than the first attempt is the defect, not a policy,
  and "bound" would only mean "leak until the session ends"; (b) let the sweep remove undecodable
  unowned UUID keys — no intent proves ownership, and d-20260925-03 already rejected UUID-based
  sweeping; (c) persist a fingerprint of the bytes with each intent — a schema change and a
  synchronous hash of up to megabytes per close for protection only against the crafted-writer
  case the threat model excludes. New evidence relative to d-20260925-07: that decision treated
  "undecodable" and "non-tree" as one class; this finding shows a UUID-keyed undecodable value
  under a recorded intent is the repository's own abandoned tree, which d-20260925-07's
  `"other-session-value"` concern (a non-UUID foreign key) does not cover. Product impact: none
  visible — it changes only whether already-closed bytes keep consuming session quota.
  Reversal path: restore `isStoredTree` in `reconcilePendingTreeRemovals` and revert the O4
  sentence.
* **Persisted-state rule scope.** "Only an explicit successful discard may remove the last
  workspace-owned unreadable value" is about workspace-owned ids; the O2 replay excludes retained
  ids (P1), so no workspace-owned value becomes removable by this change.
* **Tier.** Stays `build`: the change reverses part of a recorded decision on a persistence
  trust boundary (deleting session values), an area whose previous plans needed five push-review
  repairs (d-20260925-03 → -08).

## Risks / open questions

* A non-UUID legacy migrated source whose first removal fails (P6) still loses its intent on the
  next load if its bytes are undecodable — named known limit, kept deliberately by O1's third row
  to preserve P11/P12. It needs a legacy workspace, a refused removal and undecodable bytes at
  once, and lasts at most until the session ends.
* An undecodable UUID value that is *not* the repository's (a foreign store that happens to
  write a key equal to a closed tab's random UUID) would be removed by the intent — accepted:
  infeasible by accident (P8 allocation, 122 random bits), and the crafted case is out of the
  threat model.

* A refused `getItem` for a pending-removal id (or the workspace key) during the module-load
  `loadWorkspace` keeps today's propagation and aborts renderer startup — pre-existing and not
  worse with O1 (O1 reads exactly the key `isStoredTree` reads). Filed through the spool as a
