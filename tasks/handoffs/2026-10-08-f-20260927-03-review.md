# Plan: bind PGN read results to the revision whose bytes they carry (f-20260927-03)

Plan path: `tasks/plans/2026-10-08-pgn-read-revision-binding.md`

## Goal

A `read_game` / `read_games` result (`StampedGame`) carries bytes, a `present` flag and a stamp
that all come from the file revision named in its `revision` field. A file rewritten in place
while a read is in progress never produces a result that pairs the new bytes with the old ranges
and the old revision. The repository's offset cache never holds ranges under a revision they were
not scanned from.

## MANDATE

Verbatim, `tasks/findings.md` f-20260927-03:

* **Where:** `src-tauri/src/pgn.rs` — `scan_and_read_ranges` (snapshot → `scan_current` → `read_ranges`), `read_game_core`, `read_games_core`.
* **Defect:** `pgn_snapshot()` pins the inode and records size/mtime/ctime, and `scan_current` returns the ranges cached for that revision. The bytes are then read through the same descriptor later. If another program rewrites the file in place (same inode) between the snapshot and the read — e.g. a two-game file rewritten to one game plus padding — the read returns the new bytes cut at the old ranges, stamped with the old revision, and `present: true`.

  change time / Windows `ChangeTime`) as observed through the open descriptor.
* **Environments:** Linux, macOS and Windows desktop builds; the same tests run on all three CI
  runners.
* **Known limit, not closed here (same as the revision model of `d-20260924-02`):** a rewrite that
  leaves `size`, `mtime` *and* the change time identical as seen by `fstat` (a same-length rewrite
  inside one timestamp tick of a coarse-clock filesystem) is invisible to any revision check. No
  cross-process lock exists. This plan adds no mechanism for it.
* **Out of threat model:** a rename-replace (new inode). The capability's retained descriptor pins
  the old inode; that is existing behaviour and is detected by `file_revision` polling, not here.

## Approach

### O1 — Scan results are bound to the revision they were scanned from

MANDATE: "`scan_current` returns the ranges cached for that revision".

* After a fresh scan (cache miss) in the blocking scan path, the descriptor's current revision is
  compared with the revision of the key the scan was started under (the same comparison
  `PgnSnapshot::current_revision` performs). Equal → the ranges are retained and returned under
  that key, as today. Different → the ranges are **not** retained and not returned; the scan path
  takes a fresh snapshot of the **same descriptor** (new revision, same identity), consults the
  cache for the new key, and scans again on a miss.
* At most `MAX_REVISION_ATTEMPTS` (= 3) scans per scan-path invocation; exhausting them returns
  `Error::StaleGame`. A cache hit needs no re-check: every retained entry was verified at
  retention (O1), and a hit is looked up under a key derived from a snapshot taken immediately
  before.
* Every scan-only consumer inherits this unchanged: `count_pgn_games_core`,
  `count_pgn_games_core_blocking`, and the range selection in `delete_game_core` /
  `write_game_core`. Their downstream checks (`revision_string_for_key(&key) != expected_revision`,
  `commit_pgn_mutation`'s commit-snapshot comparison) keep working against the returned key, which
  is now the revision the ranges really describe.
* Cancellation keeps its existing precedence: a cancelled token returns `Error::Cancellation`
  before and after each scan attempt, never `StaleGame`.
* Blocking-boundary invariant (`d-20260903-04`, `async-resource-invariants.md` DO): the check and
  the retry live on the blocking side and acquire no gateway permit; any new blocking helper on
  this path is added to `s8_blocking_functions_do_not_nest_the_gateway`'s inventory in
  `src-tauri/src/main.rs`.

### O2 — Read results are bound to the revision their bytes were read from

MANDATE: "the read returns the new bytes cut at the old ranges, stamped with the old revision, and
`present: true`"; "a result must be bound to the state that produced it".

* One read attempt = snapshot of the capability's retained descriptor → scan (O1, cache or fresh)
  → `select` → read the selected ranges through a clone of that descriptor → compare the
  descriptor's current revision with the attempt's key revision **after the last byte was read**.
  Equal → return `(key, selection, values)` exactly as today. Different → discard the attempt's
  selection and bytes and start a new attempt with a fresh snapshot.
* The post-read comparison runs for every attempt, including one that selects no ranges
  (`read_game_core`'s `present: false` path and `read_games_core`'s empty-file opening range), so a
  result's `present`/out-of-bounds outcome also describes the revision it carries.
* `select` runs once per attempt against that attempt's ranges, so it must be callable more than
  once (its error results — `InvalidInput` for an out-of-bounds index — are returned from the
  attempt that produced them, without retry: they describe a revision that was verified by O1).
* At most `MAX_REVISION_ATTEMPTS` (= 3) read attempts per `read_game` / `read_games` call; the
  O1 scan bound applies inside each attempt. Exhaustion returns `Error::StaleGame`.
* Cancellation precedence as in O1; the existing per-chunk cancellation checks stay.
* `read_game_core`, `read_games_core` and every internal caller (`write_game_core`'s post-commit
  readback) keep their signatures and success shapes; the readback's existing "any error →
  `stamp: None`" handling covers exhaustion.

### O3 — One retry bound, one exhaustion mapping

Rule 11 (extract at the second copy): the O1 scan retry and the O2 read retry are the same
concept — "repeat while the descriptor's revision moved underneath, bounded, then `StaleGame`".
One constant `MAX_REVISION_ATTEMPTS` and one revision-comparison helper serve both; the
exhaustion error is produced in one place. `file_workspace.rs`'s existing post-copy comparison is
a different contract (publication precommit, `Conflict`, no retry) and is not routed through it.

## Decisions and trade-offs

* **Bounded internal retry, `StaleGame` on exhaustion** (the MANDATE's open question). A read has
  no side effects, so retrying with a fresh snapshot yields a result bound to a real revision and
  leaves every renderer consumer's contract untouched. On exhaustion, `StaleGame` ("The game
  changed on disk") keeps every consumer recoverable: `FileFreshnessGate` shows the error with
  Retry, `tabs.ts` returns `failed` without changing freshness. `Conflict` would set
  `FileFreshnessGate` to the sticky `unavailable` state for a file that is present and merely
  churning. Bare `StaleGame` without retry would surface an error to the user for every ordinary
  external save that happens to overlap a read.
* **Bound = 3 attempts.** One overlapping save is absorbed by the second attempt; a third covers a
  save that writes in two steps (truncate, then write). A larger bound only prolongs a read of a
  file that never settles (each attempt may rescan a large file).
* **Retry reuses the capability's retained descriptor**, not a path re-open: the capability
  semantics (pinned inode) stay exactly as today.

## Decided autonomously

* **Question:** What does a PGN read return when the file's revision changes between the snapshot

  **Chosen:** up to 3 attempts, each with a fresh snapshot of the same retained descriptor, scan,
  selection, read and a post-read revision comparison; the first attempt whose revision is
  unchanged after its last read is returned; exhaustion returns `Error::StaleGame`. The same bound

  **Rejected:** `Error::StaleGame` on the first change (every external save overlapping a read

  retry), and the exhaustion error at its single construction site.
  **Governs:** f-20260927-03

## Threat model and non-goals

* **Accidental, not adversarial.** Another local program (an editor, a sync client, a second
  ChessFable instance on a user-picked directory) rewrites the PGN file in place — same inode —
  while a read or scan is running. That rewrite changes `size`, `mtime` or `ctime` (Unix inode
  change time / Windows `ChangeTime`) as observed through the open descriptor.
* **Environments:** Linux, macOS and Windows desktop builds; the same tests run on all three CI
  runners.
* **Known limit, not closed here (same as the revision model of `d-20260924-02`):** a rewrite that
  leaves `size`, `mtime` *and* the change time identical as seen by `fstat` (a same-length rewrite
  inside one timestamp tick of a coarse-clock filesystem) is invisible to any revision check. No
  cross-process lock exists. This plan adds no mechanism for it.
* **Out of threat model:** a rename-replace (new inode). The capability's retained descriptor pins
  the old inode; that is existing behaviour and is detected by `file_revision` polling, not here.

## Approach

### O1 — Scan results are bound to the revision they were scanned from

MANDATE: "`scan_current` returns the ranges cached for that revision".

* After a fresh scan (cache miss) in the blocking scan path, the descriptor's current revision is
  compared with the revision of the key the scan was started under (the same comparison
  `PgnSnapshot::current_revision` performs). Equal → the ranges are retained and returned under
  that key, as today. Different → the ranges are **not** retained and not returned; the scan path
  takes a fresh snapshot of the **same descriptor** (new revision, same identity), consults the
  cache for the new key, and scans again on a miss.
* A scan attempt that **fails** (I/O error, malformed-PGN error such as invalid UTF-8 or an
  unclosed brace comment produced by mixed bytes) is judged the same way: the descriptor's revision
  is compared with the attempt's key revision; changed → the failure is discarded and the scan is
  retried like a changed success; unchanged → the genuine error is returned as today. A failure of
  the revision comparison itself (the `fstat`) is returned as that error.
* Every scan attempt reads from byte 0 of the file: the descriptor's position is reset before
  BOM detection, because a fresh snapshot is a clone of the same descriptor and shares its file
  offset with the previous attempt's scan or read (`pgn_snapshot_file` does not seek). This makes
  the scanner's BOM handling independent of where any earlier attempt left the shared offset.
* At most `MAX_REVISION_ATTEMPTS` (= 3) scans per scan-path invocation; exhausting them returns
  `Error::StaleGame`. A cache hit needs no re-check: every retained entry was verified at
  retention (O1), and a hit is looked up under a key derived from a snapshot taken immediately
  before.
* Every scan-only consumer inherits this unchanged: `count_pgn_games_core`,
  `count_pgn_games_core_blocking`, and the range selection in `delete_game_core` /
  `write_game_core`. Their downstream checks (`revision_string_for_key(&key) != expected_revision`,
  `commit_pgn_mutation`'s commit-snapshot comparison) keep working against the returned key, which
  is now the revision the ranges really describe.
* Cancellation keeps its existing precedence: a cancelled token returns `Error::Cancellation`
  before and after each scan attempt, never `StaleGame`.
* Blocking-boundary invariant (`d-20260903-04`, `async-resource-invariants.md` DO): the check and
  the retry live on the blocking side and acquire no gateway permit; any new blocking helper on
  this path is added to `s8_blocking_functions_do_not_nest_the_gateway`'s inventory in
  `src-tauri/src/main.rs`.

### O2 — Read results are bound to the revision their bytes were read from

MANDATE: "the read returns the new bytes cut at the old ranges, stamped with the old revision, and
`present: true`"; "a result must be bound to the state that produced it".

* One read attempt = snapshot of the capability's retained descriptor → scan (O1, cache or fresh)
  → `select` → read the selected ranges through a clone of that descriptor → compare the
  descriptor's current revision with the attempt's key revision **after the last byte was read**.
  Equal → return `(key, selection, values)` exactly as today. Different → discard the attempt's
  selection and bytes and start a new attempt with a fresh snapshot.
* The post-attempt comparison runs for **every attempt outcome**: a success, including one that
  selects no ranges (`read_game_core`'s `present: false` path and `read_games_core`'s empty-file
  opening range), and every non-cancellation failure of the attempt — a scan failure (O1), a
  `select` failure (`InvalidInput` for an out-of-bounds index), or a read failure such as the
  `UnexpectedEof` I/O error `read_exact` raises when a shortening rewrite moved EOF before an old
  range's end. Changed revision → the outcome is discarded and a new attempt starts; unchanged →
  the outcome (result or genuine error) is returned as today. A failure of the comparison itself
  is returned as that error.
* `select` runs once per attempt against that attempt's ranges, so it must be callable more than
  once.
* At most `MAX_REVISION_ATTEMPTS` (= 3) read attempts per `read_game` / `read_games` call; the
  O1 scan bound applies inside each attempt. Exhaustion returns `Error::StaleGame`.
* Cancellation precedence as in O1; the existing per-chunk cancellation checks stay.
* `read_game_core`, `read_games_core` and every internal caller (`write_game_core`'s post-commit
  readback) keep their signatures and success shapes; the readback's existing "any error →
  `stamp: None`" handling covers exhaustion.

### O3 — One retry bound, one exhaustion mapping

Rule 11 (extract at the second copy): the O1 scan retry and the O2 read retry are the same
concept — "repeat while the descriptor's revision moved underneath, bounded, then `StaleGame`".
One constant `MAX_REVISION_ATTEMPTS` and one revision-comparison helper serve both; the
exhaustion error is produced in one place. `file_workspace.rs`'s existing post-copy comparison is
a different contract (publication precommit, `Conflict`, no retry) and is not routed through it.

## Decisions and trade-offs

* **Bounded internal retry, `StaleGame` on exhaustion** (the MANDATE's open question). A read has
  no side effects, so retrying with a fresh snapshot yields a result bound to a real revision and
  leaves every renderer consumer's contract untouched. On exhaustion, `StaleGame` ("The game
  changed on disk") keeps every consumer recoverable: `FileFreshnessGate` shows the error with
  Retry, `tabs.ts` returns `failed` without changing freshness. `Conflict` would set
  `FileFreshnessGate` to the sticky `unavailable` state for a file that is present and merely
  churning. Bare `StaleGame` without retry would surface an error to the user for every ordinary
  external save that happens to overlap a read.
* **Bound = 3 attempts.** One overlapping save is absorbed by the second attempt; a third covers a
  save that writes in two steps (truncate, then write). A larger bound only prolongs a read of a
  file that never settles (each attempt may rescan a large file).
* **Retry reuses the capability's retained descriptor**, not a path re-open: the capability
  semantics (pinned inode) stay exactly as today.

## Decided autonomously

* **Question:** What does a PGN read return when the file's revision changes between the snapshot
  and the end of the read (f-20260927-03's open question)?
  **Chosen:** up to 3 attempts, each with a fresh snapshot of the same retained descriptor, scan,
  selection, read and a post-attempt revision comparison; the outcome (result or genuine error) of
  the first attempt whose revision is unchanged when it ends is returned, and an attempt that
  ended on a changed revision — successfully or with an error — is discarded; exhaustion returns
  `Error::StaleGame`. The same bound and comparison guard the offset scan before its ranges are
  cached.
  **Rejected:** `Error::StaleGame` on the first change (every external save overlapping a read
  becomes a visible error); `Error::Conflict` (sets `FileFreshnessGate`'s `unavailable` state,
  which no later revision poll clears, for a file that is present); no change to the scan cache
  (mixed ranges stay cached under the pre-change key and feed `count_pgn_games`).
  **Reason:** a read has no side effects, so a retry binds the result to a real revision without
  changing any renderer contract; `StaleGame` is the one category every read consumer already
  treats as recoverable. Reversal path: `MAX_REVISION_ATTEMPTS` in `src-tauri/src/pgn.rs` (1 = no
  retry), and the exhaustion error at its single construction site.
  **Governs:** f-20260927-03

## Risks / open questions

* Timestamp granularity — the known limit in the threat model. The proofs therefore change the
  file's size so they are deterministic on every CI runner.
* Worst case under continuous churn: 3 read attempts × up to 3 scans each. Bounded; acceptable for
  a file that never settles, and each scan observes cancellation per line.

## Threat model and non-goals

* **Accidental, not adversarial.** Another local program (an editor, a sync client, a second
  ChessFable instance on a user-picked directory) rewrites the PGN file in place — same inode —
  while a read or scan is running. That rewrite changes `size`, `mtime` or `ctime` (Unix inode
  change time / Windows `ChangeTime`) as observed through the open descriptor.
* **Environments:** Linux, macOS and Windows desktop builds; the same tests run on all three CI
  runners.
* **Known limit, not closed here (same as the revision model of `d-20260924-02`):** a rewrite that
  leaves `size`, `mtime` *and* the change time identical as seen by `fstat` (a same-length rewrite
  inside one timestamp tick of a coarse-clock filesystem) is invisible to any revision check. No
  cross-process lock exists. This plan adds no mechanism for it.
* **Out of threat model:** a rename-replace (new inode). The capability's retained descriptor pins
  the old inode; that is existing behaviour and is detected by `file_revision` polling, not here.

## Approach

### O1 — Scan results are bound to the revision they were scanned from

MANDATE: "`scan_current` returns the ranges cached for that revision".

* After a fresh scan (cache miss) in the blocking scan path, the descriptor's current revision is
  compared with the revision of the key the scan was started under (the same comparison
  `PgnSnapshot::current_revision` performs). Equal → the ranges are retained and returned under
  that key, as today. Different → the ranges are **not** retained and not returned; the scan path
  takes a fresh snapshot of the **same descriptor** (new revision, same identity), consults the
  cache for the new key, and scans again on a miss.
* A scan attempt that **fails** (I/O error, malformed-PGN error such as invalid UTF-8 or an
  unclosed brace comment produced by mixed bytes) is judged the same way: the descriptor's revision
  is compared with the attempt's key revision; changed → the failure is discarded and the scan is
  retried like a changed success; unchanged → the genuine error is returned as today. A failure of
  the revision comparison itself (the `fstat`) is returned as that error.
* Every scan attempt reads from byte 0 of the file: the descriptor's position is reset before
  BOM detection, because a fresh snapshot is a clone of the same descriptor and shares its file
  offset with the previous attempt's scan or read (`pgn_snapshot_file` does not seek). This makes
  the scanner's BOM handling independent of where any earlier attempt left the shared offset.
* At most `MAX_REVISION_ATTEMPTS` (= 3) scans per scan-path invocation; exhausting them returns
  `Error::StaleGame`. A cache hit needs no re-check: every retained entry was verified at
  retention (O1), and a hit is looked up under a key derived from a snapshot taken immediately
  before.
* Every scan-only consumer inherits this unchanged: `count_pgn_games_core`,
  `count_pgn_games_core_blocking`, and the range selection in `delete_game_core` /
  `write_game_core`. Their downstream checks (`revision_string_for_key(&key) != expected_revision`,
  `commit_pgn_mutation`'s commit-snapshot comparison) keep working against the returned key, which
  is now the revision the ranges really describe.
* Cancellation keeps its existing precedence: a cancelled token returns `Error::Cancellation`
  before and after each scan attempt, never `StaleGame`.
* Blocking-boundary invariant (`d-20260903-04`, `async-resource-invariants.md` DO): the check and
  the retry live on the blocking side and acquire no gateway permit; any new blocking helper on
  this path is added to `s8_blocking_functions_do_not_nest_the_gateway`'s inventory in
  `src-tauri/src/main.rs`.

### O2 — Read results are bound to the revision their bytes were read from

MANDATE: "the read returns the new bytes cut at the old ranges, stamped with the old revision, and
`present: true`"; "a result must be bound to the state that produced it".

* One read attempt = snapshot of the capability's retained descriptor → scan (O1, cache or fresh)
  → `select` → read the selected ranges through a clone of that descriptor → compare the
  descriptor's current revision with the attempt's key revision **after the last byte was read**.
  Equal → return `(key, selection, values)` exactly as today. Different → discard the attempt's
  selection and bytes and start a new attempt with a fresh snapshot.
* The post-attempt comparison runs for **every attempt outcome**: a success, including one that
  selects no ranges (`read_game_core`'s `present: false` path and `read_games_core`'s empty-file
  opening range), and every non-cancellation failure of the attempt — a scan failure (O1), a
  `select` failure (`InvalidInput` for an out-of-bounds index), or a read failure such as the
  `UnexpectedEof` I/O error `read_exact` raises when a shortening rewrite moved EOF before an old
  range's end. Changed revision → the outcome is discarded and a new attempt starts; unchanged →
  the outcome (result or genuine error) is returned as today. A failure of the comparison itself
  is returned as that error.
* `select` runs once per attempt against that attempt's ranges, so it must be callable more than
  once.
* At most `MAX_REVISION_ATTEMPTS` (= 3) read attempts per `read_game` / `read_games` call; the
  O1 scan bound applies inside each attempt. Exhaustion returns `Error::StaleGame`.
* Cancellation precedence as in O1; the existing per-chunk cancellation checks stay.
* `read_game_core`, `read_games_core` and every internal caller (`write_game_core`'s post-commit
  readback) keep their signatures and success shapes; the readback's existing "any error →
  `stamp: None`" handling covers exhaustion.

### O3 — One retry bound, one exhaustion mapping

Rule 11 (extract at the second copy): the O1 scan retry and the O2 read retry are the same
concept — "repeat while the descriptor's revision moved underneath, bounded, then `StaleGame`".
One constant `MAX_REVISION_ATTEMPTS` and one revision-comparison helper serve both; the
exhaustion error is produced in one place. `file_workspace.rs`'s existing post-copy comparison is
a different contract (publication precommit, `Conflict`, no retry) and is not routed through it.

## Decisions and trade-offs

* **Bounded internal retry, `StaleGame` on exhaustion** (the MANDATE's open question). A read has
  no side effects, so retrying with a fresh snapshot yields a result bound to a real revision and
  leaves every renderer consumer's contract untouched. On exhaustion, `StaleGame` ("The game
  changed on disk") keeps every consumer recoverable: `FileFreshnessGate` shows the error with
  Retry, `tabs.ts` returns `failed` without changing freshness. `Conflict` would set
  `FileFreshnessGate` to the sticky `unavailable` state for a file that is present and merely
  churning. Bare `StaleGame` without retry would surface an error to the user for every ordinary
  external save that happens to overlap a read.
* **Bound = 3 attempts.** One overlapping save is absorbed by the second attempt; a third covers a
  save that writes in two steps (truncate, then write). A larger bound only prolongs a read of a
  file that never settles (each attempt may rescan a large file).
* **Retry reuses the capability's retained descriptor**, not a path re-open: the capability
  semantics (pinned inode) stay exactly as today.

## Decided autonomously

* **Question:** What does a PGN read return when the file's revision changes between the snapshot
  and the end of the read (f-20260927-03's open question)?
  **Chosen:** up to 3 attempts, each with a fresh snapshot of the same retained descriptor, scan,
  selection, read and a post-attempt revision comparison; the outcome (result or genuine error) of
  the first attempt whose revision is unchanged when it ends is returned, and an attempt that
  ended on a changed revision — successfully or with an error — is discarded; exhaustion returns
  `Error::StaleGame`. The same bound and comparison guard the offset scan before its ranges are
  cached.
  **Rejected:** `Error::StaleGame` on the first change (every external save overlapping a read
  becomes a visible error); `Error::Conflict` (sets `FileFreshnessGate`'s `unavailable` state,
  which no later revision poll clears, for a file that is present); no change to the scan cache
  (mixed ranges stay cached under the pre-change key and feed `count_pgn_games`).
  **Reason:** a read has no side effects, so a retry binds the result to a real revision without
  changing any renderer contract; `StaleGame` is the one category every read consumer already
  treats as recoverable. Reversal path: `MAX_REVISION_ATTEMPTS` in `src-tauri/src/pgn.rs` (1 = no
  retry), and the exhaustion error at its single construction site.
  **Governs:** f-20260927-03

## Risks / open questions

* Timestamp granularity — the known limit in the threat model. The proofs therefore change the
  file's size so they are deterministic on every CI runner.
* Worst case under continuous churn: 3 read attempts × up to 3 scans each. Bounded; acceptable for
  a file that never settles, and each scan observes cancellation per line.

# Plan: bind PGN read results to the revision whose bytes they carry (f-20260927-03)

Plan path: `tasks/plans/2026-10-08-pgn-read-revision-binding.md`

## Goal

A `read_game` / `read_games` result (`StampedGame`) carries bytes, a `present` flag and a stamp
that all come from the file revision named in its `revision` field. A file rewritten in place
while a read is in progress never produces a result that pairs the new bytes with the old ranges
and the old revision. The repository's offset cache never holds ranges under a revision they were
not scanned from.

## MANDATE

Verbatim, `tasks/findings.md` f-20260927-03:

* **Where:** `src-tauri/src/pgn.rs` — `scan_and_read_ranges` (snapshot → `scan_current` → `read_ranges`), `read_game_core`, `read_games_core`.
* **Defect:** `pgn_snapshot()` pins the inode and records size/mtime/ctime, and `scan_current` returns the ranges cached for that revision. The bytes are then read through the same descriptor later. If another program rewrites the file in place (same inode) between the snapshot and the read — e.g. a two-game file rewritten to one game plus padding — the read returns the new bytes cut at the old ranges, stamped with the old revision, and `present: true`.
* **Why it matters:** `.claude/rules/pgn-scanning.md` (byte offsets drifting from the file) and `async-resource-invariants.md` (a result must be bound to the state that produced it). The stamp/revision is what the renderer's freshness and write-expectation logic trusts.
* **Open question:** what the read returns when the descriptor's revision after reading differs from the snapshot's: `Error::StaleGame` (renderer reloads), `Error::Conflict`, or one bounded internal retry with a fresh snapshot — each changes renderer freshness behaviour differently. The same post-read revision check is already used by workspace file copies (`PgnSnapshot::current_revision`, f-20260908-04).
* **Proof:** a hook-driven test that rewrites the file in place between snapshot and `read_ranges` (the existing `read_chunk_hook`) and asserts the chosen outcome; reverting the check makes it fail.

Same-area obligation taken into this plan (next-finding planner contract: "Same-area findings
become obligations of the plan"): the MANDATE premise "`scan_current` returns the ranges cached
for that revision" is false when the scan itself races an in-place rewrite — `scan_file` derives
the key before scanning and `scan_current_blocking` retains the result with no post-scan revision
check, so mixed-revision ranges can be cached under the pre-rewrite key and handed to every
scan-only consumer (`count_pgn_games_core`, `count_pgn_games_core_blocking`, the range selection in

## Threat model and non-goals

* **Accidental, not adversarial.** Another local program (an editor, a sync client, a second
  ChessFable instance on a user-picked directory) rewrites the PGN file in place — same inode —
  while a read or scan is running. That rewrite changes `size`, `mtime` or `ctime` (Unix inode
  change time / Windows `ChangeTime`) as observed through the open descriptor.
* **Environments:** Linux, macOS and Windows desktop builds; the same tests run on all three CI
  runners.
* **Known limit, not closed here (same as the revision model of `d-20260924-02`):** a rewrite that
  leaves `size`, `mtime` *and* the change time identical as seen by `fstat` (a same-length rewrite
  inside one timestamp tick of a coarse-clock filesystem) is invisible to any revision check. No
  cross-process lock exists. This plan adds no mechanism for it.
* **Out of threat model:** a rename-replace (new inode). The capability's retained descriptor pins
  the old inode; that is existing behaviour and is detected by `file_revision` polling, not here.

## Approach

### O1 — Scan results are bound to the revision they were scanned from

MANDATE: "`scan_current` returns the ranges cached for that revision".

* After a fresh scan (cache miss) in the blocking scan path, the descriptor's current revision is
  compared with the revision of the key the scan was started under (the same comparison
  `PgnSnapshot::current_revision` performs). Equal → the ranges are retained and returned under
  that key, as today. Different → the ranges are **not** retained and not returned; the scan path
  takes a fresh snapshot of the **same descriptor** (new revision, same identity), consults the
  cache for the new key, and scans again on a miss.
* A scan attempt that **fails** (I/O error, malformed-PGN error such as invalid UTF-8 or an
  unclosed brace comment produced by mixed bytes) is judged the same way: the descriptor's revision
  is compared with the attempt's key revision; changed → the failure is discarded and the scan is
  retried like a changed success; unchanged → the genuine error is returned as today. A failure of
  the revision comparison itself (the `fstat`) is returned as that error.
* Every scan attempt reads from byte 0 of the file: the descriptor's position is reset before
  BOM detection, because a fresh snapshot is a clone of the same descriptor and shares its file
  offset with the previous attempt's scan or read (`pgn_snapshot_file` does not seek). This makes
  the scanner's BOM handling independent of where any earlier attempt left the shared offset.
* At most `MAX_REVISION_ATTEMPTS` (= 3) scans per scan-path invocation; exhausting them returns
  `Error::StaleGame`. A cache hit needs no re-check: every retained entry was verified at
  retention (O1), and a hit is looked up under a key derived from a snapshot taken immediately
  before.
* Every scan-only consumer inherits this unchanged: `count_pgn_games_core`,
  `count_pgn_games_core_blocking`, and the range selection in `delete_game_core` /
  `write_game_core`. Their downstream checks (`revision_string_for_key(&key) != expected_revision`,
  `commit_pgn_mutation`'s commit-snapshot comparison) keep working against the returned key, which
  is now the revision the ranges really describe.
* Cancellation keeps its existing precedence: a cancelled token returns `Error::Cancellation`
  before and after each scan attempt, never `StaleGame`.
* Blocking-boundary invariant (`d-20260903-04`, `async-resource-invariants.md` DO): the check and
  the retry live on the blocking side and acquire no gateway permit; any new blocking helper on
  this path is added to `s8_blocking_functions_do_not_nest_the_gateway`'s inventory in
  `src-tauri/src/main.rs`.

### O2 — Read results are bound to the revision their bytes were read from

MANDATE: "the read returns the new bytes cut at the old ranges, stamped with the old revision, and
`present: true`"; "a result must be bound to the state that produced it".

* One read attempt = snapshot of the capability's retained descriptor → scan (O1, cache or fresh)
  → `select` → read the selected ranges through a clone of that descriptor → compare the
  descriptor's current revision with the attempt's key revision **after the last byte was read**.
  Equal → return `(key, selection, values)` exactly as today. Different → discard the attempt's
  selection and bytes and start a new attempt with a fresh snapshot.
* The post-attempt comparison runs for **every attempt outcome**: a success, including one that
  selects no ranges (`read_game_core`'s `present: false` path and `read_games_core`'s empty-file
  opening range), and every non-cancellation failure of the attempt — a scan failure (O1), a
  `select` failure (`InvalidInput` for an out-of-bounds index), or a read failure such as the
  `UnexpectedEof` I/O error `read_exact` raises when a shortening rewrite moved EOF before an old
  range's end. Changed revision → the outcome is discarded and a new attempt starts; unchanged →
  the outcome (result or genuine error) is returned as today. A failure of the comparison itself
  is returned as that error.
* `select` runs once per attempt against that attempt's ranges, so it must be callable more than
  once.
* At most `MAX_REVISION_ATTEMPTS` (= 3) read attempts per `read_game` / `read_games` call; the
  O1 scan bound applies inside each attempt. Exhaustion returns `Error::StaleGame`.
* Cancellation precedence as in O1; the existing per-chunk cancellation checks stay.
* `read_game_core`, `read_games_core` and every internal caller (`write_game_core`'s post-commit
  readback) keep their signatures and success shapes; the readback's existing "any error →
  `stamp: None`" handling covers exhaustion.

### O3 — One retry bound, one exhaustion mapping

Rule 11 (extract at the second copy): the O1 scan retry and the O2 read retry are the same
concept — "repeat while the descriptor's revision moved underneath, bounded, then `StaleGame`".
One constant `MAX_REVISION_ATTEMPTS` and one revision-comparison helper serve both; the
exhaustion error is produced in one place. `file_workspace.rs`'s existing post-copy comparison is
a different contract (publication precommit, `Conflict`, no retry) and is not routed through it.

## Decisions and trade-offs

* **Bounded internal retry, `StaleGame` on exhaustion** (the MANDATE's open question). A read has
  no side effects, so retrying with a fresh snapshot yields a result bound to a real revision and
  leaves every renderer consumer's contract untouched. On exhaustion, `StaleGame` ("The game
  changed on disk") keeps every consumer recoverable: `FileFreshnessGate` shows the error with
  Retry, `tabs.ts` returns `failed` without changing freshness. `Conflict` would set
  `FileFreshnessGate` to the sticky `unavailable` state for a file that is present and merely
  churning. Bare `StaleGame` without retry would surface an error to the user for every ordinary
  external save that happens to overlap a read.
* **Bound = 3 attempts.** One overlapping save is absorbed by the second attempt; a third covers a
  save that writes in two steps (truncate, then write). A larger bound only prolongs a read of a
  file that never settles (each attempt may rescan a large file).
* **Retry reuses the capability's retained descriptor**, not a path re-open: the capability
  semantics (pinned inode) stay exactly as today.

## Decided autonomously

* **Question:** What does a PGN read return when the file's revision changes between the snapshot
  and the end of the read (f-20260927-03's open question)?
  **Chosen:** up to 3 attempts, each with a fresh snapshot of the same retained descriptor, scan,
  selection, read and a post-attempt revision comparison; the outcome (result or genuine error) of
  the first attempt whose revision is unchanged when it ends is returned, and an attempt that
  ended on a changed revision — successfully or with an error — is discarded; exhaustion returns
  `Error::StaleGame`. The same bound and comparison guard the offset scan before its ranges are
  cached.
  **Rejected:** `Error::StaleGame` on the first change (every external save overlapping a read
  becomes a visible error); `Error::Conflict` (sets `FileFreshnessGate`'s `unavailable` state,
  which no later revision poll clears, for a file that is present); no change to the scan cache
  (mixed ranges stay cached under the pre-change key and feed `count_pgn_games`).
  **Reason:** a read has no side effects, so a retry binds the result to a real revision without
  changing any renderer contract; `StaleGame` is the one category every read consumer already
  treats as recoverable. Reversal path: `MAX_REVISION_ATTEMPTS` in `src-tauri/src/pgn.rs` (1 = no
  retry), and the exhaustion error at its single construction site.
  **Governs:** f-20260927-03

## Risks / open questions

* Timestamp granularity — the known limit in the threat model. The proofs therefore change the
  file's size so they are deterministic on every CI runner.
* Worst case under continuous churn: 3 read attempts × up to 3 scans each. Bounded; acceptable for
  a file that never settles, and each scan observes cancellation per line.
