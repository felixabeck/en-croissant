## Goal

`LocalImage` currently hands `<img>` an object URL. The application CSP is

```
img-src 'self' data: https://lichess.org https://www.chess.com https://api.chess.com
```

which does not list `blob:`, and Tauri 2.10.2 rewrites only `script-src` and `style-src`
(`tauri-2.10.2/src/manager/mod.rs:78-100`), so nothing injects it. Measured 2026-09-06 in the real
WebKitGTK window: `securitypolicyviolation` with `violatedDirective: img-src`,
`blockedURI: blob`, then `error`.

**Every portrait that goes through a registered `imageHandle` is therefore invisible** — the
settings card (`EnginesPage.tsx:481`), the engine list row (`EnginesPage.tsx:779`) and the
analysis-panel row (`EngineSelection.tsx:38`) all fall back silently, because the failure branch is
`.catch(() => setSrc(undefined))`, which is visually identical to "this engine has no image".
Bundled **catalogue** portraits on the Add-engine cards are a different route and are *not*
affected: `AddEngine.tsx:241-244` renders Mantine `Image` directly from `engine.imageUrl`, a
`public/engines/` path that `img-src 'self'` already permits.

After this change a registered engine image renders, a read failure is visible in the log, and no
CSP directive has been widened.

## Approach

One file changes in production code: `src/components/common/LocalImage.tsx`. Nothing in
`src-tauri/` and nothing in `tauri.conf.json`.

1. **Build a `data:` URL, not an object URL.** `img-src` already permits `data:`. The bytes arrive
   as `EngineImageData = { bytes: number[]; mimeType: string }` and the backend has already
   sniffed the magic bytes (`engine_image_mime_type`, `main.rs:1618-1632`: PNG, JPEG, GIF, WebP
   only — a non-image is rejected natively, so `mimeType` is one of four `&'static str` literals
   and never attacker-chosen text interpolated into the URL).
2. **Encode with a chunked `btoa`, and exactly one `btoa`.** `btoa(String.fromCharCode(...bytes))`
   dies on a large image, because the spread is a stack-depth limit, not an argument-count one.
   **Measured on this machine (Node v24.21.0), and deliberately reported as a range, because it is
   not stable:** 100,000 arguments succeed; 125,154 throws `RangeError: Maximum call stack size
   exceeded`. A binary search in the same runtime put the boundary one higher at 125,155, and a
   round-3 lens measured 125,155 *succeeding*. Three measurements, three boundaries — so no exact
   threshold is claimed. What is stable across all of them is that **200,000 throws every time**,
   and the backend's `MAX_ENGINE_IMAGE_BYTES = 10 MiB` cap (`main.rs:110`) is fifty times past
   even the most generous of them.

   The encoder therefore walks the array in chunks of **8192**, accumulating a **binary string**,
   and calls `btoa` **once** over the finished string. The single `btoa` is the contract: `btoa`
   per chunk and concatenating the results is **wrong** at any chunk length that is not a multiple
   of 3, because each call pads its own tail. Measured:

   ```
   bytes 01..0a   btoa once      = AQIDBAUGBwgJCg==
                  btoa per chunk = AQIDBA==BQYHCAkK     (split after 4 bytes)
   ```

   **8192 is deliberately not a multiple of 3.** Revision r3 used 8190 as "defence in depth", on
   the reasoning that a later refactor to per-chunk `btoa` would then still be correct. All six
   round-3 lenses independently refuted it (K1, confidence 99–100) and they are right: a
   3-aligned chunk makes per-chunk `btoa` produce byte-identical output, so the regression becomes
   **invisible to any output-based test**. Measured directly — at chunk 8190 one-call and
   per-chunk agree, at 8192 they differ. The two protections are mutually exclusive, and the
   testable one is worth more than the silent one: an invariant enforced by a red test beats an
   invariant preserved by a coincidence that hides the mistake. The chunk constant carries that
   sentence as its comment.

   It stays synchronous inside the existing `.then`, so the effect keeps **one** promise chain and
   **one** cancellation flag.

3. **Delete the object-URL lifecycle.** `URL.createObjectURL` / `URL.revokeObjectURL` and the
   `objectUrl` variable go away entirely; the cleanup function reduces to `cancelled = true`.
4. **Surface the failure.** Replace `.catch(() => setSrc(undefined))` with a `warn` through
   `@/platform/native`, in the promise-safe form `void warn(...).catch(() => undefined)` — the
   precedent is `src/hooks/downloadJobs.ts:47`. `warn` comes from `@tauri-apps/plugin-log` and its
   promise **rejects** when Tauri is absent, which is exactly the situation in a Vitest render, so
   the bare `warn(...)` form used in `src/App.tsx` would produce an unhandled rejection here.
   `setSrc(undefined)` is kept alongside the log so a failed *re*-read clears a stale image.
   **Message content: the normalized error, and nothing else. The image id is never logged.**
   Revision r2 logged it raw; r3 logged it behind a UUID-shape guard; both are wrong, and round 3
   said so (K3 — `review-tauri-security` 96, `review-root-cause` 91). **UUID syntax is not
   provenance.** `imageHandle` is rehydrated from `localStorage` through `engineImageHandleSchema`,
   which accepts `z.string().min(1)` (`src/utils/engines.ts:86-89`, hydrated at
   `src/state/engineOwnerStorage.ts:399-410`), so a persisted record can carry a native path or a
   bearer token in that field — and a *UUID-shaped* secret passes the r3 guard untouched. The
   renderer cannot establish that an id came from the path registry, so the only sound answer is
   not to put it in the message. The backend's normalized error already carries the reason the
   read failed, which is the diagnostic that matters; which image it was is recoverable from the
   engine list. A unit case pins this with a UUID-shaped secret as the persisted id.

5. The dependency list stays `[image, key]`. See D4 for why the r1 proposal to change it was
   withdrawn.

## The current code, for the reviewer

```tsx
const [src, setSrc] = useState<string>();
const key = image.id.id;

useEffect(() => {
  let cancelled = false;
  let objectUrl: string | undefined;
  void tauri
    .readEngineImage(image)
    .then(({ bytes, mimeType }) => {
      if (cancelled) return;
      objectUrl = URL.createObjectURL(new Blob([new Uint8Array(bytes)], { type: mimeType }));
      setSrc(objectUrl);
    })
    .catch(() => {
      if (!cancelled) setSrc(undefined);
    });
  return () => {
    cancelled = true;
    if (objectUrl) URL.revokeObjectURL(objectUrl);
  };
}, [image, key]);
```

## Decisions and trade-offs

### D1 — `data:` URL, **not** `blob:` added to `img-src`

* **Chosen:** (a) from the finding — build `data:${mimeType};base64,…`.
* **Rejected:** (b) adding `blob:` to `img-src`.
* **Reason:** `blob:` in `img-src` is unscoped — it permits *any* blob any script in the page can
  mint, so it widens the policy for the whole renderer to fix one component. The repository's
  recorded posture is the opposite one, in three places, all verified by round-1 lenses:
  `src/utils/engines.ts:186-187` rejects remote catalogue portraits explicitly so "CSP img-src does
  not need widening"; the `f-20260830-24` closure note (`tasks/findings.md:2500`) records "The CSP
  is untouched" as a property of that run and hands *this* defect forward by id; and
  `CLAUDE.md:290` states that widening a declared scope "is a security decision, not a build fix".
  `data:` is already in the policy (`src-tauri/tauri.conf.json:75`), so option (a) needs no
  security decision at all.
* **Against it:** a `data:` URL materialises the base64 as a JS string (~4/3 of the byte length)
  and React holds it in state, where an object URL is a handle. And it is **not** the smaller
  change: option (b) is one CSP token, while (a) adds the chunked encoder of D3. The claim that
  (a) is "strictly less code" was in r1 and was wrong (round 1, I11); the case for (a) is the
  narrower policy surface alone. See D2 for why memory does not decide it either.
* **Reversal path:** if a future consumer genuinely needs large or streamed images, the honest
  move is a scoped custom protocol, not `blob:`; `d-20260906-04` already rejected
  bytes-over-IPC-plus-`blob:` for audio on separate measured grounds.

### D2 — the memory argument does not decide this

`EngineImageData.bytes` is `number[]`, not a typed array: Specta maps `Vec<u8>` that way, so a
10 MiB image already crosses IPC as a JSON array of ten million integers and lands as a
ten-million-element JS array **before either option runs**. The base64 string (~13.3 MB) is a
fraction of what the transport already spent. Neither option changes the dominant cost, so the
decision is made on policy surface (D1), not on bytes. Reducing `MAX_ENGINE_IMAGE_BYTES` or moving
off `number[]` is a separate question and is **not** in this mandate.

### D3 — chunked `btoa`, not `FileReader.readAsDataURL`

* **Chosen:** a module-local `toDataUrl(bytes, mimeType)` accumulating a binary string over
  8192-byte chunks and calling `btoa` once (Approach 2 carries all three measurements).
* **Rejected:** `new Blob(...)` + `FileReader.readAsDataURL`, which lets the browser do the base64.
* **Reason:** `FileReader` is a second asynchronous hop with its own `onload`/`onerror` pair, so the
  effect would carry two cancellation points instead of one — the `async-resource-invariants` rule
  asks for one owner and named exit paths, and this keeps them at one. It would also reintroduce a
  `Blob`, which is the thing this change is removing. Chunked `btoa` is synchronous and has no
  lifecycle.
* **Also rejected, for the third time:** inlining the loop in the `.then` (`review-minimalism`
  I13, J10, K5 — the only lens ever to raise it, in all three rounds). Three non-obvious facts
  have to live next to this code: the unstable stack limit, that `btoa` must be called once
  because per-chunk base64 corrupts at a non-3-aligned boundary, and that 8192 is chosen
  *because* it is not 3-aligned so the test can see that regression. A named function is where
  those can be stated; inlined, they sit inside a promise callback that is about something else.
  Single use is accepted deliberately.
* **Against it:** hand-rolled base64 chunking is code we now own.

### D4 — the dependency list stays `[image, key]` (r1's D4 is withdrawn)

Revision r1 proposed changing the effect's deps from `[image, key]` to `[key]`, on the stated
ground that `EngineSelection.tsx:31`'s `toggleLoaded()` mints a new `imageHandle` object and so
re-runs the read on every engine toggle. **That mechanism is false**, and eight of the nine round-1
lenses said so independently (confidence 97–100). Verified directly at source:
`EngineSelection.tsx:78-80` is
`(await prev).map((e) => (e.id === engine.id ? { ...e, loaded: !e.loaded } : e))` — a shallow spread
that preserves the nested `imageHandle` **by reference**, and returns every other engine object
unchanged; `enginesAtom` forwards that value as-is (`src/state/atoms.ts:213-216`) and
`engineOwnerStorage` only serialises it on the way to disk (`:430-432`). No toggle produces a new
handle object.

This was asserted rather than measured, which is what rule 12b forbids, and the correction to
`[image, key]` stands: **the deps do not change in this task.**

**Round 2 then found that a different trigger does exist** (`review-plan`, J3, confidence 98) and
the arbiter verified it: `EnginesPage.tsx:694` replaces the engine with
`parsePersistedEngineJson(value).data` from `JSONModal` (`:735-742`) — a **freshly parsed** object,
so `imageHandle` is a new reference with the same id and the effect does re-read the same image.
So r1's conclusion was right for the wrong reason, and r2's "no mechanism reaches it" was itself
false. The real mechanism is rare (a user editing an engine's raw JSON and saving) and costs one
redundant read; it is a separable defect not required by MANDATE, so it is **filed as `f-20260920-12`**
rather than carried here — see "Not part of this task".

### D5 — a single `warn`, no latch, no per-key failure set

`f-20260906-10` records three lens rounds failing to converge on a bounded failure latch for
`sound.ts`. That question does not arise here and must not be imported: `playSound` is called on
every move, whereas this effect runs once per mount per `[image, key]` change. No latch, no `Set`,
no cache.

`review-error-handling` additionally asked for a console fallback when the `warn` IPC itself
rejects (round 1, I9). **Skipped:** the established repository form is exactly
`void warn(...).catch(() => undefined)` (`src/hooks/downloadJobs.ts:47`), a logger-of-last-resort is
not required by MANDATE, and adding a second reporting channel here would make this component the
only one in the tree with one. The message-content half of that finding is adopted (Approach 4).

## Risks / open questions

* **R1 — `mimeType` interpolation.** Verified by four round-1 lenses: `engine_image_mime_type`
  (`main.rs:1618-1631`) returns one of four `&'static str` literals and nothing else reaches
  `EngineImageData.mimeType` (`:1813-1815`). If it ever returns a caller-derived string this
  becomes an injection into the URL header and the encoder must whitelist instead.
* **R2 — `btoa` and non-Latin1.** `String.fromCharCode` over values already constrained to
  0–255 by `Vec<u8>` is safe, but `bytes` is typed `number[]` on the renderer side, so a
  hypothetical value outside 0–255 would throw `InvalidCharacterError` inside the `.then` and land
  in the `.catch` — it degrades to the logged-failure path rather than crashing the render.
* **R3 — jsdom `btoa`.** Present in jsdom, so the unit test needs no polyfill. Proved by the test
  running, not asserted.
* **R4 — the second session.** `src-tauri/src/fs.rs`, `src-tauri/src/main.rs` and
  `src-tauri/src/infra/platform_support.rs` are dirty for `f-20260906-08`. This change touches
  none of them, but `verify:app` and `frontend-build` rebuild shared output, so neither runs until
  that session has pushed.
* **R5 — the engines route in the probe.** The positive check depends on the engines page
  rendering the seeded fixture engine's card under WebDriver. The Files-page precedent (item 10)
  shows the harness can do this, but if the card does not render, that is a probe defect to repair,
  **not** grounds to fall back to an independently-constructed `data:` URL — that fallback is
  exactly what round 1 rejected.
