# Plan: Account import survives a renderer reload

## Goal

A Lichess or Chess.com game download that this process has already accepted still imports exactly once when the document that started it is destroyed. The replacement document hears the result once. Engine install and upgrade completion stays as it is on this base.

## MANDATE

Finding `f-20261005-05`, the account half that still holds. The engine half no longer holds; evidence is under Traced premises. This text stays fixed.

* **ID:** f-20261005-05 · **Status:** open · **Area:** frontend-state · **Root:** - · **Entry:** build · **Blocked:** none
* **Defect:** each of these flows splits its effect in two: the native command downloads and publishes the artefact, and the renderer's JavaScript continuation then registers the engine, applies the upgrade, or converts the downloaded PGN into a database. A renderer reload (WebKitGTK Ctrl+R, a crash-recovery reload) destroys that continuation while the native download keeps running under its accepted lease to completion. The engine archive is then installed on disk but never registered, an upgrade's new version is installed but never applied and the old engine stays current, and an account import leaves a published PGN artefact that is never converted. Nothing reports the half-finished state.
* **Why it matters:** `.claude/rules/async-resource-invariants.md` requires cleanup on every exit path; the reload is an exit path of the renderer owner. `f-20260919-10`'s plan keeps downloads running across a reload and gives them a Cancel, which leaves this half of the class as the remaining gap.
* **Open question:** should the post-download step move behind the native command, should a reload cancel downloads whose completion needs the renderer, or should startup reconcile installed-but-unregistered artefacts? Answered for this finding by `d-20261023-01` and `d-20261023-04`. This plan does not reopen those options.
* **Correction (2026-10-05):** a second install does not re-download. The lost engine registration is recovered by a retry without a second transfer. The account-import continuation is `AccountCard`'s `convert` after publication, reaching `convertPgn`, not the provider download helpers. The linked path appends through `appendCollectionGames` instead of `convert`.
* **Remaining obligation on this base:** account Phase 2. The 2026-10-23 delivery annotations record that engine Phase 1 landed and that this finding stays open for the account import. Those engine annotations are history, not new work.

## Threat model and non-goals

The adversary is loss of the renderer document while this native process stays alive: WebKitGTK reload, or a crash-recovery reload. The user is the same local user. The renderer may call only the commands it can already call. A bearer token, a filesystem path, and a raw provider body stay out of renderer messages, as they do for the existing download commands.

Not in this threat model: killing the native process, a second OS user, a malicious plugin, or a renderer that forges another webview's owner label. Those are out of scope. Process exit drops the in-memory completion mailbox. Durable download artefacts and existing account-batch receipts keep the persistence they already have. There is no new restart recovery and no durable job queue (`d-20261023-11`).

## Approach

### O1 — One native account workflow

After the renderer has chosen the workspace, refused or finished migration, and seen a ready collection or an unlinked database handle, one new command owns the rest. It downloads, or it adopts the prepared pending batch, and then it imports. Linked import calls the existing append core. Unlinked import calls the existing convert core and then the existing empty-game deletion on that same database. The command calls the existing Lichess and Chess.com download runtimes, including their filenames, admission keys, credential lookup, and receipt recording. It does not grow a second downloader or a second importer.

The Lichess call continues to take the existing opaque account handle. Chess.com does not. No bearer token is added to the request.

### O2 — Admission, join, and exactly once

The workflow identity is the webview owner plus the provider plus the lowercase account. An identical request joins the existing record and does not take another lease. A second request for that same account, while a record is still unacknowledged, also joins that record and does not start a second transfer. This replaces the in-memory pending guard, which a reload clears.

Download cancellation keeps today's commit gate: a cancel before publication does not publish, and a cancel after the publication gate does not undo it. Append keeps today's rule that a committed batch stays committed. Empty-game deletion runs only after unlinked conversion has committed. If deletion fails, the completion keeps the committed database handle and the published artefact. A later join retries that deletion only. It does not convert again and it does not download again. Calling acknowledge while that deletion is unfinished returns success and leaves the checkpoint in the map. The record is removed only after deletion succeeds. A failure that committed nothing (no publication, a rolled-back convert, an uncommitted append) may be removed after the document has reported it.

A prepared pending batch skips the provider transfer and imports that handle. A new download uses the destination the renderer already chose.

Account records live in their own map. The map uses the existing `MAX_ACCEPTED_OPERATIONS` limit on its own, and it never evicts an unacknowledged record. Engine admission, engine snapshots, engine receipts, and the engine map stay byte-for-byte in behavior. Sharing one entry type with engine retirement was rejected because it would change that admission.

### O3 — The replacement document applies the outcome once

The workflow publishes `CompletionOutcome` and emits the existing `CompletionChanged` event. Every retained outcome also carries the publication durability the download runtime already returned, including when a later import fails. The home account surface subscribes before it reads a new pending-account snapshot, the same ordering the engine observer already uses. A running record keeps the account card pending and disables the download action, including when the in-memory ticket map is empty. A succeeded record refreshes the database list once, shows the existing durability and collection notices from the outcome, and acknowledges. A deletion-unfinished record shows the deletion failure and the durability notice, and the acknowledge call leaves the checkpoint in place. Any other failed record is reported once and then acknowledged.

The click handler keeps `notifyUnlessCancelled`. The observer and that handler share one reported-error mark on the rejection object the handler catches. Marking the event payload is not enough: the command path builds a separate error object. Both event-first and command-first delivery mark the caught rejection, produce one notification, and still reject the caller.

Acknowledgement of a missing record succeeds and does not change databases. Acknowledgement is not what performs the import. The native workflow finishes a committed import even if no document acknowledges it. The mailbox still lives only for this process (`d-20261023-11`). Uncertain publication durability keeps today's notice, including the instruction not to retry, on the original document and on a replacement document that observes the retained outcome.

No account receipt is written into the engine owner keys (`d-20261023-02`).

# Plan: Account import survives a renderer reload

## Goal

A Lichess or Chess.com game download that this process has already accepted still imports exactly once when the document that started it is destroyed. The replacement document hears the result once. Engine install and upgrade completion stays as it is on this base.

## MANDATE

* **Defect:** each of these flows splits its effect in two: the native command downloads and publishes the artefact, and the renderer's JavaScript continuation then registers the engine, applies the upgrade, or converts the downloaded PGN into a database. ## Approach

### O1 — One native account workflow

After the renderer has chosen the workspace, refused or finished migration, and seen a ready collection or an unlinked database handle, one new command owns the rest. It downloads, or it adopts the prepared pending batch, and then it imports. Linked import calls the existing append core. Unlinked import calls the existing convert core and then the existing empty-game deletion on that same database. The command calls the existing Lichess and Chess.com download runtimes, including their filenames, admission keys, credential lookup, and receipt recording. It does not grow a second downloader or a second importer.

The Lichess call continues to take the existing opaque account handle. Chess.com does not. No bearer token is added to the request.

### O2 — Admission, join, and exactly once

The workflow identity is the webview owner plus the provider plus the lowercase account. An identical request joins the existing record and does not take another lease. A second request for that same account, while a record is still unacknowledged, also joins that record and does not start a second transfer. This replaces the in-memory pending guard, which a reload clears.

Download cancellation keeps today's commit gate: a cancel before publication does not publish, and a cancel after the publication gate does not undo it. Append keeps today's rule that a committed batch stays committed. Empty-game deletion runs only after unlinked conversion has committed. If deletion fails, the completion keeps the committed database handle and the published artefact. A later join retries that deletion only. It does not convert again and it does not download again. Calling acknowledge while that deletion is unfinished returns success and leaves the checkpoint in the map. The record is removed only after deletion succeeds. A failure that committed nothing (no publication, a rolled-back convert, an uncommitted append) may be removed after the document has reported it.

A prepared pending batch skips the provider transfer and imports that handle. A new download uses the destination the renderer already chose.

Account records live in their own map. The map uses the existing `MAX_ACCEPTED_OPERATIONS` limit on its own, and it never evicts an unacknowledged record. Engine admission, engine snapshots, engine receipts, and the engine map stay byte-for-byte in behavior. Sharing one entry type with engine retirement was rejected because it would change that admission.

### O3 — The replacement document applies the outcome once

The workflow publishes `CompletionOutcome` and emits the existing `CompletionChanged` event. Every retained outcome also carries the publication durability the download runtime already returned, including when a later import fails. The home account surface subscribes before it reads a new pending-account snapshot, the same ordering the engine observer already uses. A running record keeps the account card pending and disables the download action, including when the in-memory ticket map is empty. A succeeded record refreshes the database list once, shows the existing durability and collection notices from the outcome, and acknowledges. A deletion-unfinished record shows the deletion failure and the durability notice, and the acknowledge call leaves the checkpoint in place. Any other failed record is reported once and then acknowledged.

The click handler keeps `notifyUnlessCancelled`. The observer and that handler share one reported-error mark on the rejection object the handler catches. Marking the event payload is not enough: the command path builds a separate error object. Both event-first and command-first delivery mark the caught rejection, produce one notification, and still reject the caller.

Acknowledgement of a missing record succeeds and does not change databases. Acknowledgement is not what performs the import. The native workflow finishes a committed import even if no document acknowledges it. The mailbox still lives only for this process (`d-20261023-11`). Uncertain publication durability keeps today's notice, including the instruction not to retry, on the original document and on a replacement document that observes the retained outcome.

No account receipt is written into the engine owner keys (`d-20261023-02`).

### O4 — Proof

Native tests, added beside the existing reload-completion tests and named so the `reload_completion` filter runs them, cover the retained import by admitting the workflow and holding that import so it cannot commit yet. They drop the command receiver while the import is still unfinished, then release it. They see the committed rows while that receiver is still dropped, before any reconnect, snapshot, or acknowledgement. A second start joins and does not duplicate rows. The unlinked case checks real database rows. The pending-batch case checks that no provider transfer runs and that one append commits. Separately, for a committed convert whose empty-game deletion fails, the test acknowledges that failure, then joins again, and sees one deletion and no second download or conversion. One assertion fails if the completion is not retained, with the tests unchanged. The unlinked row assertion is not wrapped in a Unix-only cfg. Windows CI remains the hosted Windows run. ## Approach

### O1 — One native account workflow

After the renderer has chosen the workspace, refused or finished migration, and seen a ready collection or an unlinked database handle, one new command owns the rest. It downloads, or it adopts the prepared pending batch, and then it imports. Linked import calls the existing append core. Unlinked import calls the existing convert core and then the existing empty-game deletion on that same database. The command calls the existing Lichess and Chess.com download runtimes, including their filenames, admission keys, credential lookup, and receipt recording. It does not grow a second downloader or a second importer.

The Lichess call continues to take the existing opaque account handle. Chess.com does not. No bearer token is added to the request.

### O2 — Admission, join, and exactly once

The workflow identity is the webview owner plus the provider plus the lowercase account. An identical request joins the existing record and does not take another lease. A second request for that same account, while a record is still unacknowledged, also joins that record and does not start a second transfer. This replaces the in-memory pending guard, which a reload clears.

Download cancellation keeps today's commit gate: a cancel before publication does not publish, and a cancel after the publication gate does not undo it. Append keeps today's rule that a committed batch stays committed. Empty-game deletion runs only after unlinked conversion has committed. If deletion fails, the completion keeps the committed database handle and the published artefact. A later join retries that deletion only. It does not convert again and it does not download again. Calling acknowledge while that deletion is unfinished returns success and leaves the checkpoint in the map. The record is removed only after deletion succeeds. A failure that committed nothing (no publication, a rolled-back convert, an uncommitted append) may be removed after the document has reported it.

A prepared pending batch skips the provider transfer and imports that handle. A new download uses the destination the renderer already chose.

Account records live in their own map. The map uses the existing `MAX_ACCEPTED_OPERATIONS` limit on its own, and it never evicts an unacknowledged record. Engine admission, engine snapshots, engine receipts, and the engine map stay byte-for-byte in behavior. Sharing one entry type with engine retirement was rejected because it would change that admission.

### O3 — The replacement document applies the outcome once

The workflow publishes `CompletionOutcome` and emits the existing `CompletionChanged` event. Every retained outcome also carries the publication durability the download runtime already returned, including when a later import fails. The home account surface subscribes before it reads a new pending-account snapshot, the same ordering the engine observer already uses. A running record keeps the account card pending and disables the download action, including when the in-memory ticket map is empty. A succeeded record refreshes the database list once, shows the existing durability and collection notices from the outcome, and acknowledges. A deletion-unfinished record shows the deletion failure and the durability notice, and the acknowledge call leaves the checkpoint in place. Any other failed record is reported once and then acknowledged.

The click handler keeps `notifyUnlessCancelled`. The observer and that handler share one reported-error mark on the rejection object the handler catches. Marking the event payload is not enough: the command path builds a separate error object. Both event-first and command-first delivery mark the caught rejection, produce one notification, and still reject the caller.

Acknowledgement of a missing record succeeds and does not change databases. Acknowledgement is not what performs the import. The native workflow finishes a committed import even if no document acknowledges it. The mailbox still lives only for this process (`d-20261023-11`). Uncertain publication durability keeps today's notice, including the instruction not to retry, on the original document and on a replacement document that observes the retained outcome.

No account receipt is written into the engine owner keys (`d-20261023-02`).

### O4 — Proof

Native tests, added beside the existing reload-completion tests and named so the `reload_completion` filter runs them, cover the retained import by admitting the workflow and holding that import so it cannot commit yet. They drop the command receiver while the import is still unfinished, then release it. They see the committed rows while that receiver is still dropped, before any reconnect, snapshot, or acknowledgement. A second start joins and does not duplicate rows. The unlinked case checks real database rows. The pending-batch case checks that no provider transfer runs and that one append commits. Separately, for a committed convert whose empty-game deletion fails, the test acknowledges that failure, then joins again, and sees one deletion and no second download or conversion. One assertion fails if the completion is not retained, with the tests unchanged. The unlinked row assertion is not wrapped in a Unix-only cfg. Windows CI remains the hosted Windows run. This machine proves the shared test.

Renderer tests in the existing account card tests reconstruct a document with an empty ticket map. A running snapshot disables the download action. One snapshot refreshes once. A failed snapshot whose durability is uncertain shows the existing do-not-retry notice and the import error together. Event-first and command-first delivery of the same failure notify once and still reject the caller. Engine completion tests still pass under the same `reload_completion` filter.

The adopting build's browser stage checks the real account card: a retained running completion leaves the download action unavailable, and a retained uncertain-durability failure shows the existing notice. That stage is not part of the leaf proof command.

`pnpm checks:pre-review` is part of the phase proof. Cargo tests need the ignored `dist/` directory the Tauri context macro reads. When that directory is absent, the existing `pnpm build` creates it and it is not committed.
