## Mandate (fixed)

Close `f-20260921-03`: `scripts/gate-receipt.mjs` `runGate` runs every receipt gate with
`stdio: "inherit"` and on failure prints only `gate failed: <gate> (exit <n>)`; nothing is written
to disk, so a caller that pipes the run through `tail` loses the failing test's name for good
(observed 2026-09-21, tree `fb0b212b`). Open question: pty, second fd or caller contract for the
tee; whether a failed run records a negative receipt; retention and git-ignore of transcripts; TTY

## Planned answer

- One shared gate-log primitive `scripts/gate-logs.mjs` used by the receipt runner and the push
  scheduler (rule 11): run directories `artifacts/gates/<ts>-<pid>/` (git-ignored), transcript
  `receipt-<gate>.log`, scheduler run directory inherited through one exported env-var constant
  (`GATE_LOG_DIRECTORY`), 8 KiB tail reader, failure trailer.
- `runGate` streams the child through a pipe tee (measured: no change for any piped caller;
  `cargo test`/`vitest` failure content identical between pipe and pty), header/footer with tree
  and exit; refuses before start if the transcript cannot be opened; fails closed on a mid-run
  write failure; drains output on interruption (child stays in the caller's process group;
  lone-signal descendants of compound commands are a named known limit, no worse than today);
  failure trailer is the last line gate-receipt writes, followed through `pnpm` only by its one
  measured `ELIFECYCLE` line.
- No negative receipt; the transcript (with tree/command header) is the failure record.
- Retention: newest 100 run directories of `artifacts/gates/`, only real directories matching the
  run-directory name pattern; pruning under the machine-wide gate lock.
- The scheduler ends a failed run with one `… — log: <path>` line per failed task.
- Per-gate pty-vs-tee measurement of all seven gates after implementation, recorded in this
  handoff; a substantive difference stops the run and returns to plan review.
- Decisions to record on adoption (plan `## Decided autonomously`): pipe tee; no negative receipt;
  shared location and retention 100; transcript-unavailable refusal / fail-closed.

# Plan: a failing gate leaves a durable, named transcript (f-20260921-03)

## Goal

Every receipt-backed gate run (`pnpm gate:ensure|gate:run <gate>`) writes the gate child's
complete output to a retained transcript file and, on failure, ends its own output with a line
naming that file — so a red gate stays attributable whatever the caller does with stdout. The
transcript directory is shared with the push-gate scheduler's existing lane logs and is bounded.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260921-03:

> * **Where:** `scripts/gate-receipt.mjs` — `runGate` at `:263-290`, which spawns the gate command with `stdio: "inherit"` and, on a non-zero status, prints only `gate failed: <gate> (exit <status>)` before returning. All seven registered gates run through it (`backend-test`, `backend-coverage`, `frontend-coverage`, `frontend-mutation`, `frontend-build`, `e2e-container`, `tauri-build`).
> * **Defect:** the gate's own output exists only in whatever the caller happened to keep. A `$push` orchestrator that pipes the run through `tail` — the normal shape, because a green `cargo test --all-targets` is about 1400 lines — sees the summary line and loses every line above it, including the `failures:` block that names the test. Nothing is written to disk: `.gate-receipts/<gate>.json` is written only on success and records the tree and toolchain, not a transcript, so a red run leaves the repository in exactly the state it was in before.
> * **Observed, 2026-09-21 (this run, tree `fb0b212b`):** `pnpm gate:ensure backend-test` failed with `test result: FAILED. 1364 passed; 1 failed; 1 ignored` and `error: test failed, to rerun pass --bin chessfable`. The name of the failing test is **not recoverable** — the orchestrator had piped the run through `tail -6`. Ten subsequent full runs of the identical command on the identical tree were green (1365 passed), including the gate itself, which then recorded receipt `0517ca9ec0a4`. So a real intermittent failure in the backend suite was observed once and cannot be identified, and the receipt now asserts the gate green for this tree.
> * **Why it matters:** a receipt-backed gate that flakes teaches re-running instead of looking, which is the failure `f-20260917-11` records for the frontend-mutation fence test on the CI runner. Here it is worse than on CI, because CI keeps the job log and this keeps nothing: the first observation of a flake is usually also the last chance to name it, and a green receipt written minutes later makes the tree look proven. It also means every red gate in every future push is one careless pipe away from being unattributable.
> * **Fix shape:** `runGate` tees the child's output to a per-gate transcript under `.gate-receipts/` (or a sibling log directory) and, on failure, prints the transcript path and the last N lines regardless of what the caller does with stdout — so the artefact survives a `tail`. Design questions the run has to settle rather than assume: whether `stdio: "inherit"` can be kept alongside a tee without changing what an interactive caller sees (a pipe changes the child's TTY detection and therefore `cargo`'s colour and progress output, which is measurable and must be measured, not asserted); whether a failed transcript is retained across runs or overwritten; whether the path is git-ignored like the rest of `.gate-receipts/`; and whether a failing run should refuse to record anything at all or record a negative receipt naming the transcript. Separately, the flake itself needs finding once it can be named — do not fold that into this entry.
> * **Open question:** can a tee coexist with `stdio: "inherit"` without changing what the child writes — `cargo` and `vitest` both switch colour, progress and failure formatting on TTY detection, so a transcript captured through a pipe may not be the transcript an interactive caller saw, and the difference has to be measured on each of the seven gates rather than assumed. That choice decides the shape: a tee through a pty, a second inherited fd, or a caller-side contract that forbids piping a gate at all. It also decides whether a failing run records a negative receipt naming its transcript, or keeps recording nothing and leaves the transcript as the only artefact.

## Approach

### O1 — One shared gate-log primitive (`scripts/gate-logs.mjs`)

Rests on MANDATE: "tees the child's output to a per-gate transcript under `.gate-receipts/` (or
a sibling log directory)", "whether a failed transcript is retained across runs or overwritten",
"whether the path is git-ignored". The scheduler already owns the second copy of "capture a
child into a per-run log directory and print a tail on failure" (P2); rule 11 routes both
sites through one module rather than adding a parallel layout.

Contract:

* **Run directory.** `artifacts/gates/<ISO-timestamp-without-separators>-<pid>/` under the
  repository root — the scheduler's existing layout, git-ignored (P4). Creating one prunes the
  base directory (O3) after creation.
* **Inherited run directory.** The scheduler exports the environment variable
  `GATE_LOG_DIRECTORY=<its run directory>` to every child it spawns. A gate-receipt run honours
  it only if it resolves to an existing real directory (not a symlink) whose parent is exactly
  this repository's `artifacts/gates/`; otherwise it ignores it with one stderr warning line and
  creates its own run directory. One scheduler run therefore stays one directory.
* **Transcript file name** `receipt-<gate>.log`, distinct from every lane log name (P2: three
  lane names equal gate names).
* **Tail reader** — the last `LOG_TAIL_BYTES` (8 KiB, moved from `run-push-gates.mjs:55`) of a
  log file as UTF-8; an unreadable file yields a one-line reason, never a throw.
* **Failure trailer** — formats the final output line(s) a failed run prints (O2, O4).

Verification level: unit tests in a new `scripts/gate-logs-tests.mjs`, wired into
`gates:contract:check` as `gates:logs:test` (P9 requires routing).

### O2 — `runGate` streams the child through a transcript

Rests on MANDATE: "`runGate` tees the child's output to a per-gate transcript … and, on failure,
prints the transcript path and the last N lines regardless of what the caller does with stdout —
so the artefact survives a `tail`."

Required behaviour:

* **Before the run:** after removing the stale receipt and before `treeState`, obtain the run
  directory (O1) and open `receipt-<gate>.log` exclusively. If the directory cannot be created or
  the file cannot be opened, print `gate transcript unavailable: <gate> — <reason>` and return
  `EXIT_USAGE` (2) **without starting the gate** (same class as the existing "stale receipt could
  not be removed" refusal).
* **Header** written first: gate, command, tree fingerprint (`before.tree`, or `unavailable`),
  start time (ISO). **Footer** after exit: exit status, signal if any, duration.
* **Streaming tee:** the child is spawned asynchronously (`spawn`, `shell: true`,
  `stdio: ["ignore", "pipe", "pipe"]`); each stdout chunk is written to the transcript and
  forwarded to the gate-receipt process's stdout, each stderr chunk to the transcript and to its
  stderr, in arrival order. Nothing is buffered beyond a chunk (no `spawnSync` with pipes:
  its `maxBuffer` would kill a long gate).
* **Process group:** the child stays in gate-receipt's own process group (no `detached`), so the
  scheduler's lane-group termination (P2, `killProcessGroup: true`) and a terminal Ctrl-C keep
  reaching it exactly as today. Supervision and SIGINT/SIGTERM forwarding reuse
  `superviseChild` (`killProcessGroup: false`) and `installMultiChildSignalForwarding` (P8); a
  signal delivered only to gate-receipt terminates the child before gate-receipt exits (today it
  orphans it). A signalled child keeps today's status mapping (`signalExitCode`, `143` for
  SIGTERM).
* **Forwarding failure** (caller closed the pipe, `EPIPE`): forwarding to that stream stops
  silently; the transcript keeps receiving everything and the gate runs to completion.
* **Transcript write failure during the run:** recorded; after the child exits, the run is
  failed closed — no receipt, exit status 1 if the child succeeded (the child's own status if it
  failed), and the error named in the final line. This is the scheduler's existing `logError`
  contract (`run-push-gates.mjs` `runCommand`), so one rule covers both sites.
* **On failure:** print the transcript tail (O1 tail reader) to stderr, then as the **last line
  of all output** `gate failed: <gate> (exit <status>[, signal <sig>]) — transcript: <absolute
  path>`. The existing prefix `gate failed: <gate> (exit …` is preserved.
* **On success:** one line `gate transcript: <path>` before the existing receipt lines; receipt
  behaviour (tree/metadata checks, `writeReceipt`) is unchanged.
* `executeAction` becomes async; the CLI entry awaits it. `gate:check` behaviour is unchanged
  (it never runs a gate and writes no transcript).
* **No negative receipt.** A failed run writes nothing under `.gate-receipts/`; the retained
  transcript plus its header (tree, command) is the failure record. See Decisions D2.

Verification level: `scripts/gate-receipt-tests.mjs` integration tests against a fixture repo
whose `.gitignore` also ignores `artifacts/` (P4), plus one test that the real repository's
`.gitignore` ignores `artifacts/gates/<x>/receipt-<gate>.log`.

### O3 — Bounded retention of `artifacts/gates/`

Rests on MANDATE "whether a failed transcript is retained across runs or overwritten" and the
always-loaded `async-resource-invariants.md` ("Bound anything that accumulates … and say what the
bound is"); P3 shows the existing directory already unbounded.

* Every creation of a run directory (scheduler start and standalone gate-receipt) keeps the
  newest **100** entries of `artifacts/gates/` whose name matches the run-directory pattern
  `^\d{8}T\d{9}Z-\d+$` and which `lstat` reports as real directories; older matching directories
  are removed with `rmSync(recursive, force)` (P6: does not follow inner symlinks). Non-matching
  names and symlinks are never touched. Names sort chronologically (fixed-width timestamp
  prefix).
* The bound and its reason are a named constant beside the code: 100 run directories ≈ two
  days at the measured ~48 runs/day (P3), ≤ ~140 MB at the measured 1.37 MB maximum.
* Liveness: pruning runs inside the machine-wide gate lock (P10), so no other top-level run can
  be live; the run directory just created is the newest and is never a candidate.
* A pruning failure prints one warning line naming the path and never fails the gate.

Verification level: unit tests in `gate-logs-tests.mjs` (105 fixture dirs → newest 100 kept;
non-matching name, symlink and a file entry untouched).

### O4 — The scheduler routes through O1 and ends with the failed log paths

Rests on MANDATE "every red gate in every future push is one careless pipe away from being
unattributable" and rule 11 (second copy, P2).

* `run-push-gates.mjs` obtains its run directory from O1 (gaining O3's pruning), exports
  `GATE_LOG_DIRECTORY` to its children, and reads tails through O1's tail reader.
* After the existing summary and tails, a failed or interrupted scheduler run prints, as its
  last output lines, one `push gate failed: <task> — log: <absolute path>` line per failed or
  interrupted task (`pre-review check failed: …` in pre-review mode). A green run's output is
  unchanged apart from the run directory now being pruned.

Verification level: `scripts/run-push-gates-tests.mjs` (env export observed by a fake spawn;
final lines on a failing schedule; pruning on start).

### O5 — The push skill names the transcript

The push skill's "Exact-tree gate receipts" prose gains two sentences: where a gate's transcript
lands (`artifacts/gates/<run>/receipt-<gate>.log`, retained newest 100 runs) and that a failed
gate's last output line names it. No fenced command changes (the receipt-fence test and the
routing checker parse the fences).

## Decisions and trade-offs

* **D1 — pipe tee, not a pty and not a caller contract.** Measured (P5): every agent and
  scheduler caller already gives the child a pipe, so the tee changes nothing they see; the
  measured failure content of `cargo test` and `vitest` is identical between pipe and pty.
  Rejected: a pty via `script(1)` (an extra process, util-linux-specific argv, CR/LF and ANSI
  noise in the transcript, merged streams, and no benefit to any agent caller); a second inherited
  fd (the child would still need one stream to write to both places — that is the tee); a
  caller-side "never pipe a gate" contract (unenforceable — the incident *was* a caller pipe —
  and it moves work onto every caller). Known limit: an interactive TTY caller loses TTY-only
  decoration (colour where keyed on TTY, cargo's progress bar).
* **D2 — no negative receipt.** `.gate-receipts/` is a success cache with one consumer
  (`receiptStatus`, "is there reusable proof for this tree?"); a failure entry would gate nothing
  and add a second record type to it. The transcript header carries tree and command, so a later
  session can see that a tree failed once even after a green receipt was recorded for it.
  Rejected: negative receipt naming the transcript.
* **D3 — shared location `artifacts/gates/`, inherited run directory, retention 100.** Rejected:
  `.gate-receipts/<gate>.log` overwritten per run (loses the one failure the MANDATE is about as
  soon as the agent re-runs); a gate-receipt-only directory with its own retention (a second
  copy of the scheduler's layout, rule 11); writing no transcript when run under the scheduler
  (two behaviours depending on the caller; the lane log contains wrapper noise and is named after
  the lane, not the gate). Cost accepted: a scheduler lane's gate output is stored twice inside one
  run directory (lane log + transcript), bounded by O3.
* **D4 — transcript write failure fails closed**, matching the scheduler's existing `logError`
  rule; rejected: warn and record the receipt anyway (two contracts for one failure).
* **D5 — child stays in gate-receipt's process group.** Rejected: `detached: true` like the
  scheduler — the scheduler's group kill of a lane would then miss the gate's child (P2),
  orphaning `cargo`/`docker` on interruption.
* **D6 — stdin becomes `ignore`** (was inherited), matching the scheduler, which already runs six
  of the seven gates with stdin ignored (P2); no gate command reads stdin
  (`scripts/run-e2e-container.mjs`, `scripts/run-frontend-mutation.mjs` contain no `isTTY`/stdin
  use).

## Decided autonomously

* **Q:** How does the gate capture its transcript (pty, second fd, pipe tee, or caller
  contract)? **Chosen:** pipe tee (D1). **Rejected:** pty via `script(1)`, caller contract.
  **Reason:** P5 measurement — no agent or scheduler caller sees any change; failure content is
  identical for the measured tools.
* **Q:** Does a failing gate record a negative receipt? **Chosen:** no; the retained transcript
  with its tree/command header is the failure record (D2). **Rejected:** negative receipt.
  **Reason:** the receipt cache has one success-only consumer.
* **Q:** Where are transcripts kept and for how long? **Chosen:** `artifacts/gates/<run>/
  receipt-<gate>.log`, shared with the scheduler through `GATE_LOG_DIRECTORY`, newest 100 run
  directories (D3, O3). **Rejected:** overwrite per gate; separate directory; no transcript under
  the scheduler. **Reason:** retention across re-runs is the point; one layout and one bound.
* **Q:** What happens when the transcript cannot be written? **Chosen:** refuse before start if
  it cannot be opened; fail closed if writing fails mid-run (D4). **Rejected:** proceed silently.

## Approach

### O1 — One shared gate-log primitive (`scripts/gate-logs.mjs`)

Rests on MANDATE: "tees the child's output to a per-gate transcript under `.gate-receipts/` (or
a sibling log directory)", "whether a failed transcript is retained across runs or overwritten",
"whether the path is git-ignored". The scheduler already owns the second copy of "capture a
child into a per-run log directory and print a tail on failure" (P2); rule 11 routes both
sites through one module rather than adding a parallel layout.

Contract:

* **Run directory.** `artifacts/gates/<ISO-timestamp-without-separators>-<pid>/` under the
  repository root — the scheduler's existing layout, git-ignored (P4). Creating one prunes the
  base directory (O3) after creation.
* **Inherited run directory.** The scheduler exports the environment variable
  `GATE_LOG_DIRECTORY=<its run directory>` to every child it spawns. A gate-receipt run honours
  it only if it resolves to an existing real directory (not a symlink) whose parent is exactly
  this repository's `artifacts/gates/`; otherwise it ignores it with one stderr warning line and
  creates its own run directory. One scheduler run therefore stays one directory.
* **Transcript file name** `receipt-<gate>.log`, distinct from every lane log name (P2: three
  lane names equal gate names).
* **Tail reader** — the last `LOG_TAIL_BYTES` (8 KiB, moved from `run-push-gates.mjs:55`) of a
  log file as UTF-8; an unreadable file yields a one-line reason, never a throw.
* **Failure trailer** — formats the final output line(s) a failed run prints (O2, O4).

Verification level: unit tests in a new `scripts/gate-logs-tests.mjs`, wired into
`gates:contract:check` as `gates:logs:test` (P9 requires routing).

### O2 — `runGate` streams the child through a transcript

Rests on MANDATE: "`runGate` tees the child's output to a per-gate transcript … and, on failure,
prints the transcript path and the last N lines regardless of what the caller does with stdout —
so the artefact survives a `tail`."

Required behaviour:

* **Before the run:** after removing the stale receipt and before `treeState`, obtain the run
  directory (O1) and open `receipt-<gate>.log` exclusively. If the directory cannot be created or
  the file cannot be opened, print `gate transcript unavailable: <gate> — <reason>` and return
  `EXIT_USAGE` (2) **without starting the gate** (same class as the existing "stale receipt could
  not be removed" refusal).
* **Header** written first: gate, command, tree fingerprint (`before.tree`, or `unavailable`),
  start time (ISO). **Footer** after exit: exit status, signal if any, duration.
* **Streaming tee:** the child is spawned asynchronously (`spawn`, `shell: true`,
  `stdio: ["ignore", "pipe", "pipe"]`); each stdout chunk is written to the transcript and
  forwarded to the gate-receipt process's stdout, each stderr chunk to the transcript and to its
  stderr, in arrival order. Nothing is buffered beyond a chunk (no `spawnSync` with pipes:
  its `maxBuffer` would kill a long gate).
* **Process group:** the child stays in gate-receipt's own process group (no `detached`), so the
  scheduler's lane-group termination (P2, `killProcessGroup: true`), its SIGKILL escalation and a
  terminal Ctrl-C keep reaching the child and every descendant exactly as today.
* **Interruption drains, it does not abandon.** Today a SIGINT/SIGTERM delivered to the group
  kills gate-receipt's Node process at once while the inherited-stdio child keeps writing its
  shutdown output straight to the caller (the scheduler keeps that output in the lane log,
  commit `eb69843d`). With a tee, gate-receipt dying at once would lose that output from both the
  transcript and the lane log. So gate-receipt installs SIGINT/SIGTERM handling through
  `installMultiChildSignalForwarding` and supervises the direct child with `superviseChild`
  (`killProcessGroup: false`) (P8): on a signal it forwards termination to its direct child, keeps
  copying every chunk until the child's pipes close (all pipe holders gone), writes the footer
  naming the signal, prints the failure trailer, and returns `signalExitCode(<received signal>)`
  (130 / 143). The supervisor's SIGKILL escalation uses the scheduler's termination timeouts
  (`E2E_LANE_TERMINATION_TIMEOUT_MS` for `e2e-container`, `CHILD_TERMINATION_TIMEOUT_MS`
  otherwise); both constants move from `run-push-gates.mjs` to `scripts/child-supervisor.mjs` and
  are imported by both runners rather than copied. A child that exits by its own signal keeps today's
  mapping (`signalExitCode`, 143 for SIGTERM).
* **Known limit — a signal sent to gate-receipt alone.** For a compound shell command
  (`backend-coverage`, `frontend-coverage`) the direct child is `/bin/sh`; terminating it does not
  reach the running descendant, which keeps the transcript pipes open, so gate-receipt waits until
  that descendant ends and then completes the transcript. Today the same lone signal kills
  gate-receipt and orphans the whole tree; the new behaviour is no worse (the gate work runs to
  its end in both cases) and is not extended by a new mechanism here (rule 12a adoption gate:
  a hazard present equally before the change is a named limit). Every group-delivered signal
  (terminal, scheduler, `agent-gate` scope) reaches the descendants directly, as today.
* **Forwarding failure** (caller closed the pipe, `EPIPE`): forwarding to that stream stops
  silently; the transcript keeps receiving everything and the gate runs to completion.
* **Transcript write failure during the run:** recorded; after the child exits, the run is
  failed closed — no receipt, exit status 1 if the child succeeded (the child's own status if it
  failed), and the error named in the final line. This is the scheduler's existing `logError`
  contract (`run-push-gates.mjs` `runCommand`), so one rule covers both sites.
* **On failure:** print the transcript tail (O1 tail reader) to stderr, then as the **last line
  of all output** `gate failed: <gate> (exit <status>[, signal <sig>]) — transcript: <absolute
  path>`. The existing prefix `gate failed: <gate> (exit …` is preserved.
* **On success:** one line `gate transcript: <path>` before the existing receipt lines; receipt
  behaviour (tree/metadata checks, `writeReceipt`) is unchanged.
* `executeAction` becomes async; the CLI entry awaits it. `gate:check` behaviour is unchanged
  (it never runs a gate and writes no transcript).
* **No negative receipt.** A failed run writes nothing under `.gate-receipts/`; the retained
  transcript plus its header (tree, command) is the failure record. See Decisions D2.

Verification level: `scripts/gate-receipt-tests.mjs` integration tests against a fixture repo
whose `.gitignore` also ignores `artifacts/` (P4), each of which goes red if the named behaviour
is removed:

* **Complete capture:** a failing child writes more than 1 MiB to stdout and to stderr with
  distinct numbered marker lines (above any pipe buffer); the transcript contains every marker of
  both streams in full, the forwarded stdout/stderr carry their own stream's markers, and the
  last emitted output line matches `— transcript: <path>` with an existing path.
* **Retention across reruns:** a failing run followed by a green run on the same fixture leaves
  the failing run's transcript byte-identical in its own run directory beside the green one.
* **Refusal before start:** with the run-directory base made uncreatable (a regular file at
  `artifacts/gates`), the run returns 2, prints `gate transcript unavailable`, and the gate
  command's marker file is never created.
* **Mid-run write failure:** with an injected transcript writer that throws after the first
  chunk, a child that exits 0 yields exit 1, no receipt, and a final line naming the write error.
* **Interruption drain:** a child started with `exec` (so the direct child is the gate process,
  as the existing SIGTERM test does) that, on SIGTERM, writes a marker line and exits;
  gate-receipt receives SIGTERM (alone — the drain path does not depend on who else got it); the
  transcript contains the post-signal marker and a footer naming SIGTERM, and the return is 143.
* **Inherited directory:** with `GATE_LOG_DIRECTORY` set to a directory created by the shared
  primitive, the transcript lands in it as `receipt-<gate>.log` and no new run directory appears;
  with it set to a path outside `artifacts/gates/`, a new run directory is created and the
  warning printed. The environment variable name is one exported constant of
  `scripts/gate-logs.mjs`, used by the scheduler (producer, O4) and gate-receipt (consumer).
* One test that the real repository's `.gitignore` ignores
  `artifacts/gates/<x>/receipt-<gate>.log` (`git check-ignore`).
* The existing tests keep passing unchanged in meaning (SIGTERM child → 143, receipt
  hit/miss cases), adapted only to the async `executeAction`.

## Decisions and trade-offs

* **D1 — pipe tee, not a pty and not a caller contract.** Measured (P5): every agent and
  scheduler caller already gives the child a pipe, so the tee changes nothing they see; the
  measured failure content of `cargo test` and `vitest` is identical between pipe and pty.
  Rejected: a pty via `script(1)` (an extra process, util-linux-specific argv, CR/LF and ANSI
  noise in the transcript, merged streams, and no benefit to any agent caller); a second inherited
  fd (the child would still need one stream to write to both places — that is the tee); a
  caller-side "never pipe a gate" contract (unenforceable — the incident *was* a caller pipe —
  and it moves work onto every caller). Known limit: an interactive TTY caller loses TTY-only
  decoration (colour where keyed on TTY, cargo's progress bar).
* **D2 — no negative receipt.** `.gate-receipts/` is a success cache with one consumer
  (`receiptStatus`, "is there reusable proof for this tree?"); a failure entry would gate nothing
  and add a second record type to it. The transcript header carries tree and command, so a later
  session can see that a tree failed once even after a green receipt was recorded for it.
  Rejected: negative receipt naming the transcript.
* **D3 — shared location `artifacts/gates/`, inherited run directory, retention 100.** Rejected:
  `.gate-receipts/<gate>.log` overwritten per run (loses the one failure the MANDATE is about as
  soon as the agent re-runs); a gate-receipt-only directory with its own retention (a second
  copy of the scheduler's layout, rule 11); writing no transcript when run under the scheduler
  (two behaviours depending on the caller; the lane log contains wrapper noise and is named after
  the lane, not the gate). Cost accepted: a scheduler lane's gate output is stored twice inside one
  run directory (lane log + transcript), bounded by O3.
* **D4 — transcript write failure fails closed**, matching the scheduler's existing `logError`
  rule; rejected: warn and record the receipt anyway (two contracts for one failure).
* **D5 — child stays in gate-receipt's process group.** Rejected: `detached: true` like the
  scheduler — the scheduler's group kill of a lane would then miss the gate's child (P2),
  orphaning `cargo`/`docker` on interruption.
* **D6 — stdin becomes `ignore`** (was inherited), matching the scheduler, which already runs six
  of the seven gates with stdin ignored (P2); no gate command reads stdin
  (`scripts/run-e2e-container.mjs`, `scripts/run-frontend-mutation.mjs` contain no `isTTY`/stdin
  use).

## Decided autonomously

* **Q:** How does the gate capture its transcript (pty, second fd, pipe tee, or caller
  contract)? **Chosen:** pipe tee (D1). **Rejected:** pty via `script(1)`, caller contract.
  **Reason:** P5 measurement — no agent or scheduler caller sees any change; failure content is
  identical for the measured tools.
* **Q:** Does a failing gate record a negative receipt? **Chosen:** no; the retained transcript
  with its tree/command header is the failure record (D2). **Rejected:** negative receipt.
  **Reason:** the receipt cache has one success-only consumer.
* **Q:** Where are transcripts kept and for how long? **Chosen:** `artifacts/gates/<run>/
  receipt-<gate>.log`, shared with the scheduler through `GATE_LOG_DIRECTORY`, newest 100 run

  the scheduler. **Reason:** retention across re-runs is the point; one layout and one bound.
* **Q:** What happens when the transcript cannot be written? **Chosen:** refuse before start if
  it cannot be opened; fail closed if writing fails mid-run (D4). **Rejected:** proceed silently.

### plan-r3.md

# Plan: a failing gate leaves a durable, named transcript (f-20260921-03)

## Goal

Every receipt-backed gate run (`pnpm gate:ensure|gate:run <gate>`) writes the gate child's
complete output to a retained transcript file and, on failure, ends its own output with a line
naming that file — so a red gate stays attributable whatever the caller does with stdout. The
transcript directory is shared with the push-gate scheduler's existing lane logs and is bounded.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260921-03:

> * **Where:** `scripts/gate-receipt.mjs` — `runGate` at `:263-290`, which spawns the gate command with `stdio: "inherit"` and, on a non-zero status, prints only `gate failed: <gate> (exit <status>)` before returning. All seven registered gates run through it (`backend-test`, `backend-coverage`, `frontend-coverage`, `frontend-mutation`, `frontend-build`, `e2e-container`, `tauri-build`).
> * **Defect:** the gate's own output exists only in whatever the caller happened to keep. A `$push` orchestrator that pipes the run through `tail` — the normal shape, because a green `cargo test --all-targets` is about 1400 lines — sees the summary line and loses every line above it, including the `failures:` block that names the test. Nothing is written to disk: `.gate-receipts/<gate>.json` is written only on success and records the tree and toolchain, not a transcript, so a red run leaves the repository in exactly the state it was in before.
> * **Observed, 2026-09-21 (this run, tree `fb0b212b`):** `pnpm gate:ensure backend-test` failed with `test result: FAILED. 1364 passed; 1 failed; 1 ignored` and `error: test failed, to rerun pass --bin chessfable`. The name of the failing test is **not recoverable** — the orchestrator had piped the run through `tail -6`. Ten subsequent full runs of the identical command on the identical tree were green (1365 passed), including the gate itself, which then recorded receipt `0517ca9ec0a4`. So a real intermittent failure in the backend suite was observed once and cannot be identified, and the receipt now asserts the gate green for this tree.
> * **Why it matters:** a receipt-backed gate that flakes teaches re-running instead of looking, which is the failure `f-20260917-11` records for the frontend-mutation fence test on the CI runner. Here it is worse than on CI, because CI keeps the job log and this keeps nothing: the first observation of a flake is usually also the last chance to name it, and a green receipt written minutes later makes the tree look proven. It also means every red gate in every future push is one careless pipe away from being unattributable.
> * **Fix shape:** `runGate` tees the child's output to a per-gate transcript under `.gate-receipts/` (or a sibling log directory) and, on failure, prints the transcript path and the last N lines regardless of what the caller does with stdout — so the artefact survives a `tail`. Design questions the run has to settle rather than assume: whether `stdio: "inherit"` can be kept alongside a tee without changing what an interactive caller sees (a pipe changes the child's TTY detection and therefore `cargo`'s colour and progress output, which is measurable and must be measured, not asserted); whether a failed transcript is retained across runs or overwritten; whether the path is git-ignored like the rest of `.gate-receipts/`; and whether a failing run should refuse to record anything at all or record a negative receipt naming the transcript. Separately, the flake itself needs finding once it can be named — do not fold that into this entry.
> * **Open question:** can a tee coexist with `stdio: "inherit"` without changing what the child writes — `cargo` and `vitest` both switch colour, progress and failure formatting on TTY detection, so a transcript captured through a pipe may not be the transcript an interactive caller saw, and the difference has to be measured on each of the seven gates rather than assumed. That choice decides the shape: a tee through a pty, a second inherited fd, or a caller-side contract that forbids piping a gate at all. It also decides whether a failing run records a negative receipt naming its transcript, or keeps recording nothing and leaves the transcript as the only artefact.

## Threat model and non-goals

* **Accidental input only.** Single-user workstation (`tuxedo-atlas`); callers are Felix's own
  agents (`$push`, `build`, drains) and occasionally an interactive shell. No adversary controls
  the environment, the repository, or `artifacts/`. Edge cases reachable only by deliberately
  evasive input (a crafted environment variable pointing elsewhere, a planted symlink in
  `artifacts/gates/`) must fail safe (no deletion outside `artifacts/gates/`, no crash), not be
  defended against further.
* **Environments that count:** local Linux runs through `agent-gate` (the only route
  `package.json` offers for `gate:ensure`/`gate:run`, `d-20261002-01`), both standalone and as a
  lane of `pnpm gates:push` / `pnpm checks:pre-review`. CI never calls `gate-receipt.mjs`
  (traced premise P7).
* **Non-goals:** finding or fixing the intermittent backend test itself (MANDATE: "do not fold
  that into this entry"); changing what a receipt certifies or its cache key; colour/progress
  fidelity for an interactive TTY caller beyond what is measured below.

## Approach

### O1 — One shared gate-log primitive (`scripts/gate-logs.mjs`)

Rests on MANDATE: "tees the child's output to a per-gate transcript under `.gate-receipts/` (or
a sibling log directory)", "whether a failed transcript is retained across runs or overwritten",
"whether the path is git-ignored". The scheduler already owns the second copy of "capture a
child into a per-run log directory and print a tail on failure" (P2); rule 11 routes both
sites through one module rather than adding a parallel layout.

Contract:

* **Run directory.** `artifacts/gates/<ISO-timestamp-without-separators>-<pid>/` under the
  repository root — the scheduler's existing layout, git-ignored (P4). Creating one prunes the
  base directory (O3) after creation.
* **Inherited run directory.** The scheduler exports the environment variable
  `GATE_LOG_DIRECTORY=<its run directory>` to every child it spawns. A gate-receipt run honours
  it only if it resolves to an existing real directory (not a symlink) whose parent is exactly
  this repository's `artifacts/gates/`; otherwise it ignores it with one stderr warning line and
  creates its own run directory. One scheduler run therefore stays one directory.
* **Transcript file name** `receipt-<gate>.log`, distinct from every lane log name (P2: three
  lane names equal gate names).
* **Tail reader** — the last `LOG_TAIL_BYTES` (8 KiB, moved from `run-push-gates.mjs:55`) of a
  log file as UTF-8; an unreadable file yields a one-line reason, never a throw.
* **Failure trailer** — formats the final output line(s) a failed run prints (O2, O4).

Verification level: unit tests in a new `scripts/gate-logs-tests.mjs`, wired into
`gates:contract:check` as `gates:logs:test` (P9 requires routing).

### O2 — `runGate` streams the child through a transcript

Rests on MANDATE: "`runGate` tees the child's output to a per-gate transcript … and, on failure,
prints the transcript path and the last N lines regardless of what the caller does with stdout —
so the artefact survives a `tail`."

Required behaviour:

* **Before the run:** after removing the stale receipt and before `treeState`, obtain the run
  directory (O1) and open `receipt-<gate>.log` exclusively. If the directory cannot be created or
  the file cannot be opened, print `gate transcript unavailable: <gate> — <reason>` and return
  `EXIT_USAGE` (2) **without starting the gate** (same class as the existing "stale receipt could
  not be removed" refusal).
* **Header** written first: gate, command, tree fingerprint (`before.tree`, or `unavailable`),
  start time (ISO). **Footer** after exit: exit status, signal if any, duration.
* **Streaming tee:** the child is spawned asynchronously (`spawn`, `shell: true`,
  `stdio: ["ignore", "pipe", "pipe"]`); each stdout chunk is written to the transcript and
  forwarded to the gate-receipt process's stdout, each stderr chunk to the transcript and to its
  stderr, in arrival order. Nothing is buffered beyond a chunk (no `spawnSync` with pipes:
  its `maxBuffer` would kill a long gate).
* **Process group:** the child stays in gate-receipt's own process group (no `detached`), so the
  scheduler's lane-group termination (P2, `killProcessGroup: true`), its SIGKILL escalation and a
  terminal Ctrl-C keep reaching the child and every descendant exactly as today.
* **Interruption drains, it does not abandon.** Today a SIGINT/SIGTERM delivered to the group
  kills gate-receipt's Node process at once while the inherited-stdio child keeps writing its
  shutdown output straight to the caller (the scheduler keeps that output in the lane log,
  commit `eb69843d`). With a tee, gate-receipt dying at once would lose that output from both the
  transcript and the lane log. So gate-receipt installs SIGINT/SIGTERM handling through
  `installMultiChildSignalForwarding` and supervises the direct child with `superviseChild`
  (`killProcessGroup: false`) (P8): on a signal it forwards termination to its direct child, keeps
  copying every chunk until the child's pipes close (all pipe holders gone), writes the footer
  naming the signal, prints the failure trailer, and returns `signalExitCode(<received signal>)`
  (130 / 143). The supervisor's SIGKILL escalation uses the scheduler's termination timeouts
  (`E2E_LANE_TERMINATION_TIMEOUT_MS` for `e2e-container`, `CHILD_TERMINATION_TIMEOUT_MS`
  otherwise); both constants move from `run-push-gates.mjs` to `scripts/child-supervisor.mjs` and
  are imported by both runners rather than copied, and their one other consumer,
  `scripts/run-e2e-launchers-tests.mjs` (P12), imports from `child-supervisor.mjs` too — no
  re-export from the scheduler, one source. A child that exits by its own signal keeps today's
  mapping (`signalExitCode`, 143 for SIGTERM).
* **Known limit — a signal sent to gate-receipt alone.** For a compound shell command
  (`backend-coverage`, `frontend-coverage`) the direct child is `/bin/sh`; terminating it does not
  reach the running descendant, which keeps the transcript pipes open, so gate-receipt waits until
  that descendant ends and then completes the transcript. Today the same lone signal kills
  gate-receipt and orphans the whole tree; the new behaviour is no worse (the gate work runs to
  its end in both cases) and is not extended by a new mechanism here (rule 12a adoption gate:
  a hazard present equally before the change is a named limit). Every group-delivered signal
  (terminal, scheduler, `agent-gate` scope) reaches the descendants directly, as today.
* **Forwarding failure** (caller closed the pipe, `EPIPE`): forwarding to that stream stops
  silently; the transcript keeps receiving everything and the gate runs to completion.
* **Transcript write failure during the run:** recorded; after the child exits, the run is
  failed closed — no receipt, exit status 1 if the child succeeded (the child's own status if it
  failed), and the error named in the final line. This is the scheduler's existing `logError`
  contract (`run-push-gates.mjs` `runCommand`), so one rule covers both sites.
* **On failure:** print the transcript tail (O1 tail reader) to stderr, then as the **last line
  gate-receipt writes** `gate failed: <gate> (exit <status>[, signal <sig>]) — transcript:
  <absolute path>`. The existing prefix `gate failed: <gate> (exit …` is preserved. Through the
  package entry points the wrappers add a bounded, measured suffix (P11): `agent-gate` adds
  nothing and `pnpm` appends exactly one ` ELIFECYCLE  Command failed with exit code <n>.` line,
  so through `pnpm gate:ensure|gate:run` the trailer is the second-to-last line of the combined
  output — inside any `tail -n` with n ≥ 2, including the incident's `tail -6`.
* **On success:** one line `gate transcript: <path>` before the existing receipt lines; receipt
  behaviour (tree/metadata checks, `writeReceipt`) is unchanged.
* `executeAction` becomes async; the CLI entry awaits it. `gate:check` behaviour is unchanged
  (it never runs a gate and writes no transcript).
* **No negative receipt.** A failed run writes nothing under `.gate-receipts/`; the retained
  transcript plus its header (tree, command) is the failure record. See Decisions D2.

Verification level: `scripts/gate-receipt-tests.mjs` integration tests against a fixture repo
whose `.gitignore` also ignores `artifacts/` (P4), each of which goes red if the named behaviour
is removed:

* **Complete capture:** a failing child writes more than 1 MiB to stdout and to stderr with
  distinct numbered marker lines (above any pipe buffer); the transcript contains every marker of
  both streams in full, the forwarded stdout/stderr carry their own stream's markers, and the
  last line gate-receipt emits matches `— transcript: <path>` with an existing path.
* **Retention across reruns:** a failing run followed by a green run on the same fixture leaves
  the failing run's transcript byte-identical in its own run directory beside the green one.
* **Refusal before start:** with the run-directory base made uncreatable (a regular file at
  `artifacts/gates`), the run returns 2, prints `gate transcript unavailable`, and the gate
  command's marker file is never created.
* **Mid-run write failure:** with an injected transcript writer that throws after the first
  chunk, a child that exits 0 yields exit 1, no receipt, and a final line naming the write error.
* **Interruption drain:** a child started with `exec` (so the direct child is the gate process,
  as the existing SIGTERM test does) that, on SIGTERM, writes a marker line and exits;
  gate-receipt receives SIGTERM (alone — the drain path does not depend on who else got it); the
  transcript contains the post-signal marker and a footer naming SIGTERM, and the return is 143.
* **Inherited directory:** with `GATE_LOG_DIRECTORY` set to a directory created by the shared
  primitive, the transcript lands in it as `receipt-<gate>.log` and no new run directory appears;
  with it set to a path outside `artifacts/gates/`, a new run directory is created and the
  warning printed. The environment variable name is one exported constant of
  `scripts/gate-logs.mjs`, used by the scheduler (producer, O4) and gate-receipt (consumer).
* One test that the real repository's `.gitignore` ignores
  `artifacts/gates/<x>/receipt-<gate>.log` (`git check-ignore`).
* The existing tests keep passing unchanged in meaning (SIGTERM child → 143, receipt
  hit/miss cases), adapted only to the async `executeAction`.

End-to-end evidence: the implementation's final `pnpm gates:push` (all blocks, because
`package.json` changes) leaves its scheduler run directory holding the lane logs **and**
`receipt-<gate>.log` for every receipt lane that ran; the adopting session lists that directory
in its report.

### O3 — Bounded retention of `artifacts/gates/`

Rests on MANDATE "whether a failed transcript is retained across runs or overwritten" and the
always-loaded `async-resource-invariants.md` ("Bound anything that accumulates … and say what the
bound is"); P3 shows the existing directory already unbounded.

* Every creation of a run directory (scheduler start and standalone gate-receipt) keeps the
  newest **100** entries of `artifacts/gates/` whose name matches the run-directory pattern
  `^\d{8}T\d{9}Z-\d+$` and which `lstat` reports as real directories; older matching directories
  are removed with `rmSync(recursive, force)` (P6: does not follow inner symlinks). Non-matching
  names and symlinks are never touched. Names sort chronologically (fixed-width timestamp
  prefix).
* The bound and its reason are a named constant beside the code: 100 run directories ≈ two
  days at the measured ~48 runs/day (P3), ≤ ~140 MB at the measured 1.37 MB maximum.
* Liveness: pruning runs inside the machine-wide gate lock (P10), so no other top-level run can
  be live; the run directory just created is the newest and is never a candidate.
* A pruning failure prints one warning line naming the path and never fails the gate.

Verification level: unit tests in `gate-logs-tests.mjs` (105 fixture dirs → newest 100 kept;
non-matching name, symlink and a file entry untouched).

### O4 — The scheduler routes through O1 and ends with the failed log paths

Rests on MANDATE "every red gate in every future push is one careless pipe away from being
unattributable" and rule 11 (second copy, P2).

* `run-push-gates.mjs` obtains its run directory from O1 (gaining O3's pruning), exports
  `GATE_LOG_DIRECTORY` to its children, and reads tails through O1's tail reader.
* After the existing summary and tails, a failed or interrupted scheduler run prints, as its
  last output lines, one `push gate failed: <task> — log: <absolute path>` line per failed or
  interrupted task (`pre-review check failed: …` in pre-review mode). A green run's output is
  unchanged apart from the run directory now being pruned.

Verification level: `scripts/run-push-gates-tests.mjs` (env export observed by a fake spawn;
final lines on a failing schedule; pruning on start).

### O6 — Per-gate measurement of pipe vs. TTY output

Rests on MANDATE: "the difference has to be measured on each of the seven gates rather than
assumed" and "a pipe changes the child's TTY detection … which is measurable and must be
measured, not asserted". P5 measured the two test runners (`cargo test`, `vitest`) on failing
fixtures; the five other gate commands are not measured yet.

* After Phase 2, run each of the seven gates twice on the same clean tree through the real entry
  point, under `agent-gate` placement: (a) the gate's registered command under a pty
  (`script -qec '<GATES[gate]>' /dev/null`, what an interactive caller saw before this change),
  and (b) `pnpm gate:run <gate>` under the same pty (gate-receipt's stdout is a TTY, the child
  writes to the tee pipe), keeping (b)'s transcript.
* Normalise both sides (strip ANSI/CSI and `\r`-redrawn progress lines, mask durations,
  timestamps, PIDs/thread ids, temporary paths) and diff (a) against (b)'s transcript body.
* Record a per-gate table (gate, exit status both runs, remaining differing lines by kind) in the
  review handoff `tasks/handoffs/<date>-gate-failure-transcript-review.md` under
  "Per-gate TTY measurement".
* **Acceptance:** for every gate, no line that (a) shows is missing from (b)'s transcript except
  TTY-only decoration (colour, progress/status redraws). A gate that fails this is a plan defect:
  the implementation stops before final gates and returns the design question (forced-colour or
  full-output environment for that tool) to plan review instead of shipping.

### O5 — The push skill names the transcript

The push skill's "Exact-tree gate receipts" prose gains two sentences: where a gate's transcript
lands (`artifacts/gates/<run>/receipt-<gate>.log`, retained newest 100 runs) and that a failed
gate's last output line names it. No fenced command changes (the receipt-fence test and the
routing checker parse the fences).

## Decisions and trade-offs

* **D1 — pipe tee, not a pty and not a caller contract.** Measured (P5): every agent and
  scheduler caller already gives the child a pipe, so the tee changes nothing they see; the
  measured failure content of `cargo test` and `vitest` is identical between pipe and pty.
  Rejected: a pty via `script(1)` (an extra process, util-linux-specific argv, CR/LF and ANSI
  noise in the transcript, merged streams, and no benefit to any agent caller); a second inherited
  fd (the child would still need one stream to write to both places — that is the tee); a
  caller-side "never pipe a gate" contract (unenforceable — the incident *was* a caller pipe —
  and it moves work onto every caller). Known limit: an interactive TTY caller loses TTY-only
  decoration (colour where keyed on TTY, cargo's progress bar).
* **D2 — no negative receipt.** `.gate-receipts/` is a success cache with one consumer
  (`receiptStatus`, "is there reusable proof for this tree?"); a failure entry would gate nothing
  and add a second record type to it. The transcript header carries tree and command, so a later
  session can see that a tree failed once even after a green receipt was recorded for it.
  Rejected: negative receipt naming the transcript.
* **D3 — shared location `artifacts/gates/`, inherited run directory, retention 100.** Rejected:
  `.gate-receipts/<gate>.log` overwritten per run (loses the one failure the MANDATE is about as
  soon as the agent re-runs); a gate-receipt-only directory with its own retention (a second
  copy of the scheduler's layout, rule 11); writing no transcript when run under the scheduler
  (two behaviours depending on the caller; the lane log contains wrapper noise and is named after
  the lane, not the gate). Cost accepted: a scheduler lane's gate output is stored twice inside one
  run directory (lane log + transcript), bounded by O3.
* **D4 — transcript write failure fails closed**, matching the scheduler's existing `logError`
  rule; rejected: warn and record the receipt anyway (two contracts for one failure).
* **D5 — child stays in gate-receipt's process group.** Rejected: `detached: true` like the
  scheduler — the scheduler's group kill of a lane would then miss the gate's child (P2),
  orphaning `cargo`/`docker` on interruption.
* **D6 — stdin becomes `ignore`** (was inherited), matching the scheduler, which already runs six
  of the seven gates with stdin ignored (P2); no gate command reads stdin
  (`scripts/run-e2e-container.mjs`, `scripts/run-frontend-mutation.mjs` contain no `isTTY`/stdin
  use).

## Decided autonomously

* **Q:** How does the gate capture its transcript (pty, second fd, pipe tee, or caller
  contract)? **Chosen:** pipe tee (D1). **Rejected:** pty via `script(1)`, caller contract.
  **Reason:** P5 measurement — no agent or scheduler caller sees any change; failure content is
  identical for the measured tools.
* **Q:** Does a failing gate record a negative receipt? **Chosen:** no; the retained transcript
  with its tree/command header is the failure record (D2). **Rejected:** negative receipt.
  **Reason:** the receipt cache has one success-only consumer.
* **Q:** Where are transcripts kept and for how long? **Chosen:** `artifacts/gates/<run>/
  receipt-<gate>.log`, shared with the scheduler through `GATE_LOG_DIRECTORY`, newest 100 run
  directories (D3, O3). **Rejected:** overwrite per gate; separate directory; no transcript under
  the scheduler. **Reason:** retention across re-runs is the point; one layout and one bound.
* **Q:** What happens when the transcript cannot be written? **Chosen:** refuse before start if
  it cannot be opened; fail closed if writing fails mid-run (D4). **Rejected:** proceed silently.

## Risks / open questions

* `executeAction` turning async changes every test call site; tests that call it without
  `await` would compare a Promise to a number and fail loudly (not silently).
* The first scheduler or gate run after landing prunes ~211 existing directories in the main
  checkout (P3) — intended; they are ignored local logs.
* Forwarded output ordering between stdout and stderr in the caller's view may differ from the
  inherited case by chunk interleaving; content per stream is unchanged.

## Not part of this task

* Identifying or fixing the intermittent backend test (MANDATE).
* `f-20261003-04` (local mutation timeouts) and `f-20260917-11` (CI fence test race) — same
  files or area, different defects.
* Any change to receipt validity, TTL, cache key, or the scheduler's lane schedule.

### plan-r4.md

# Plan: a failing gate leaves a durable, named transcript (f-20260921-03)

## Goal

Every receipt-backed gate run (`pnpm gate:ensure|gate:run <gate>`) writes the gate child's
complete output to a retained transcript file and, on failure, ends its own output with a line
naming that file — so a red gate stays attributable whatever the caller does with stdout. The
transcript directory is shared with the push-gate scheduler's existing lane logs and is bounded.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260921-03:

> * **Where:** `scripts/gate-receipt.mjs` — `runGate` at `:263-290`, which spawns the gate command with `stdio: "inherit"` and, on a non-zero status, prints only `gate failed: <gate> (exit <status>)` before returning. All seven registered gates run through it (`backend-test`, `backend-coverage`, `frontend-coverage`, `frontend-mutation`, `frontend-build`, `e2e-container`, `tauri-build`).
> * **Defect:** the gate's own output exists only in whatever the caller happened to keep. A `$push` orchestrator that pipes the run through `tail` — the normal shape, because a green `cargo test --all-targets` is about 1400 lines — sees the summary line and loses every line above it, including the `failures:` block that names the test. Nothing is written to disk: `.gate-receipts/<gate>.json` is written only on success and records the tree and toolchain, not a transcript, so a red run leaves the repository in exactly the state it was in before.
> * **Observed, 2026-09-21 (this run, tree `fb0b212b`):** `pnpm gate:ensure backend-test` failed with `test result: FAILED. 1364 passed; 1 failed; 1 ignored` and `error: test failed, to rerun pass --bin chessfable`. The name of the failing test is **not recoverable** — the orchestrator had piped the run through `tail -6`. Ten subsequent full runs of the identical command on the identical tree were green (1365 passed), including the gate itself, which then recorded receipt `0517ca9ec0a4`. So a real intermittent failure in the backend suite was observed once and cannot be identified, and the receipt now asserts the gate green for this tree.
> * **Why it matters:** a receipt-backed gate that flakes teaches re-running instead of looking, which is the failure `f-20260917-11` records for the frontend-mutation fence test on the CI runner. Here it is worse than on CI, because CI keeps the job log and this keeps nothing: the first observation of a flake is usually also the last chance to name it, and a green receipt written minutes later makes the tree look proven. It also means every red gate in every future push is one careless pipe away from being unattributable.
> * **Fix shape:** `runGate` tees the child's output to a per-gate transcript under `.gate-receipts/` (or a sibling log directory) and, on failure, prints the transcript path and the last N lines regardless of what the caller does with stdout — so the artefact survives a `tail`. Design questions the run has to settle rather than assume: whether `stdio: "inherit"` can be kept alongside a tee without changing what an interactive caller sees (a pipe changes the child's TTY detection and therefore `cargo`'s colour and progress output, which is measurable and must be measured, not asserted); whether a failed transcript is retained across runs or overwritten; whether the path is git-ignored like the rest of `.gate-receipts/`; and whether a failing run should refuse to record anything at all or record a negative receipt naming the transcript. Separately, the flake itself needs finding once it can be named — do not fold that into this entry.
> * **Open question:** can a tee coexist with `stdio: "inherit"` without changing what the child writes — `cargo` and `vitest` both switch colour, progress and failure formatting on TTY detection, so a transcript captured through a pipe may not be the transcript an interactive caller saw, and the difference has to be measured on each of the seven gates rather than assumed. That choice decides the shape: a tee through a pty, a second inherited fd, or a caller-side contract that forbids piping a gate at all. It also decides whether a failing run records a negative receipt naming its transcript, or keeps recording nothing and leaves the transcript as the only artefact.

## Approach

### O1 — One shared gate-log primitive (`scripts/gate-logs.mjs`)

Rests on MANDATE: "tees the child's output to a per-gate transcript under `.gate-receipts/` (or
a sibling log directory)", "whether a failed transcript is retained across runs or overwritten",
"whether the path is git-ignored". The scheduler already owns the second copy of "capture a
child into a per-run log directory and print a tail on failure" (P2); rule 11 routes both
sites through one module rather than adding a parallel layout.

Contract:

* **Run directory.** `artifacts/gates/<ISO-timestamp-without-separators>-<pid>/` under the
  repository root — the scheduler's existing layout, git-ignored (P4). Creating one prunes the
  base directory (O3) after creation.
* **Inherited run directory.** The scheduler exports the environment variable
  `GATE_LOG_DIRECTORY=<its run directory>` to every child it spawns. A gate-receipt run honours
  it only if it resolves to an existing real directory (not a symlink) whose parent is exactly
  this repository's `artifacts/gates/`; otherwise it ignores it with one stderr warning line and
  creates its own run directory. One scheduler run therefore stays one directory.
* **Transcript file name** `receipt-<gate>.log`, distinct from every lane log name (P2: three
  lane names equal gate names).
* **Tail reader** — the last `LOG_TAIL_BYTES` (8 KiB, moved from `run-push-gates.mjs:55`) of a
  log file as UTF-8; an unreadable file yields a one-line reason, never a throw.
* **Failure trailer** — formats the final output line(s) a failed run prints (O2, O4).

Verification level: unit tests in a new `scripts/gate-logs-tests.mjs`, wired into
`gates:contract:check` as `gates:logs:test` (P9 requires routing).

### O2 — `runGate` streams the child through a transcript

Rests on MANDATE: "`runGate` tees the child's output to a per-gate transcript … and, on failure,
prints the transcript path and the last N lines regardless of what the caller does with stdout —
so the artefact survives a `tail`."

Required behaviour:

* **Before the run:** after removing the stale receipt and before `treeState`, obtain the run
  directory (O1) and open `receipt-<gate>.log` exclusively. If the directory cannot be created or
  the file cannot be opened, print `gate transcript unavailable: <gate> — <reason>` and return
  `EXIT_USAGE` (2) **without starting the gate** (same class as the existing "stale receipt could
  not be removed" refusal).
* **Header** written first: gate, command, tree fingerprint (`before.tree`, or `unavailable`),
  start time (ISO). **Footer** after exit: exit status, signal if any, duration.
* **Streaming tee:** the child is spawned asynchronously (`spawn`, `shell: true`,
  `stdio: ["ignore", "pipe", "pipe"]`); each stdout chunk is written to the transcript and
  forwarded to the gate-receipt process's stdout, each stderr chunk to the transcript and to its
  stderr, in arrival order. Nothing is buffered beyond a chunk (no `spawnSync` with pipes:
  its `maxBuffer` would kill a long gate).
* **Process group:** the child stays in gate-receipt's own process group (no `detached`), so the
  scheduler's lane-group termination (P2, `killProcessGroup: true`), its SIGKILL escalation and a
  terminal Ctrl-C keep reaching the child and every descendant exactly as today.
* **Interruption drains, it does not abandon.** Today a SIGINT/SIGTERM delivered to the group
  kills gate-receipt's Node process at once while the inherited-stdio child keeps writing its
  shutdown output straight to the caller (the scheduler keeps that output in the lane log,
  commit `eb69843d`). With a tee, gate-receipt dying at once would lose that output from both the
  transcript and the lane log. So gate-receipt installs SIGINT/SIGTERM handling through
  `installMultiChildSignalForwarding` and supervises the direct child with `superviseChild`
  (`killProcessGroup: false`) (P8): on a signal it forwards termination to its direct child, keeps
  copying every chunk until the child's pipes close (all pipe holders gone), writes the footer
  naming the signal, prints the failure trailer, and returns `signalExitCode(<received signal>)`
  (130 / 143). The supervisor's SIGKILL escalation uses the scheduler's termination timeouts
  (`E2E_LANE_TERMINATION_TIMEOUT_MS` for `e2e-container`, `CHILD_TERMINATION_TIMEOUT_MS`
  otherwise); both constants move from `run-push-gates.mjs` to `scripts/child-supervisor.mjs` and
  are imported by both runners rather than copied, and their one other consumer,
  `scripts/run-e2e-launchers-tests.mjs` (P12), imports from `child-supervisor.mjs` too — no
  re-export from the scheduler, one source. A child that exits by its own signal keeps today's
  mapping (`signalExitCode`, 143 for SIGTERM).
* **Known limit — a signal sent to gate-receipt alone.** For a compound shell command
  (`backend-coverage`, `frontend-coverage`) the direct child is `/bin/sh`; terminating it does not
  reach the running descendant, which keeps the transcript pipes open, so gate-receipt waits until
  that descendant ends and then completes the transcript. Today the same lone signal kills
  gate-receipt and orphans the whole tree; the new behaviour is no worse (the gate work runs to
  its end in both cases) and is not extended by a new mechanism here (rule 12a adoption gate:
  a hazard present equally before the change is a named limit). Every group-delivered signal
  (terminal, scheduler, `agent-gate` scope) reaches the descendants directly, as today.
* **Forwarding failure** (caller closed the pipe, `EPIPE`): forwarding to that stream stops
  silently; the transcript keeps receiving everything and the gate runs to completion.
* **Transcript write failure during the run:** recorded; after the child exits, the run is
  failed closed — no receipt, exit status 1 if the child succeeded (the child's own status if it
  failed), and the error named in the final line. This is the scheduler's existing `logError`
  contract (`run-push-gates.mjs` `runCommand`), so one rule covers both sites.
* **On failure:** print the transcript tail (O1 tail reader) to stderr, then as the **last line
  gate-receipt writes** `gate failed: <gate> (exit <status>[, signal <sig>]) — transcript:
  <absolute path>`. The existing prefix `gate failed: <gate> (exit …` is preserved. Through the
  package entry points the wrappers add a bounded, measured suffix (P11): `agent-gate` adds
  nothing and `pnpm` appends exactly one ` ELIFECYCLE  Command failed with exit code <n>.` line,
  so through `pnpm gate:ensure|gate:run` the trailer is the second-to-last line of the combined
  output — inside any `tail -n` with n ≥ 2, including the incident's `tail -6`.
* **On success:** one line `gate transcript: <path>` before the existing receipt lines; receipt
  behaviour (tree/metadata checks, `writeReceipt`) is unchanged.
* `executeAction` becomes async; the CLI entry awaits it. `gate:check` behaviour is unchanged
  (it never runs a gate and writes no transcript).
* **No negative receipt.** A failed run writes nothing under `.gate-receipts/`; the retained
  transcript plus its header (tree, command) is the failure record. See Decisions D2.

Verification level: `scripts/gate-receipt-tests.mjs` integration tests against a fixture repo
whose `.gitignore` also ignores `artifacts/` (P4), each of which goes red if the named behaviour
is removed:

* **Complete capture:** a failing child writes more than 1 MiB to stdout and to stderr with
  distinct numbered marker lines (above any pipe buffer); the transcript contains every marker of
  both streams in full, the forwarded stdout/stderr carry their own stream's markers, and the
  last line gate-receipt emits matches `— transcript: <path>` with an existing path.
* **Retention across reruns:** a failing run followed by a green run on the same fixture leaves
  the failing run's transcript byte-identical in its own run directory beside the green one.
* **Refusal before start:** with the run-directory base made uncreatable (a regular file at
  `artifacts/gates`), the run returns 2, prints `gate transcript unavailable`, and the gate
  command's marker file is never created.
* **Mid-run write failure:** with an injected transcript writer that throws after the first
  chunk, a child that exits 0 yields exit 1, no receipt, and a final line naming the write error.

## Decisions and trade-offs

* **D1 — pipe tee, not a pty and not a caller contract.** Measured (P5): every agent and
  scheduler caller already gives the child a pipe, so the tee changes nothing they see; the
  measured failure content of `cargo test` and `vitest` is identical between pipe and pty.
  Rejected: a pty via `script(1)` (an extra process, util-linux-specific argv, CR/LF and ANSI
  noise in the transcript, merged streams, and no benefit to any agent caller); a second inherited
  fd (the child would still need one stream to write to both places — that is the tee); a
  caller-side "never pipe a gate" contract (unenforceable — the incident *was* a caller pipe —
  and it moves work onto every caller). Known limit: an interactive TTY caller loses TTY-only
  decoration (colour where keyed on TTY, cargo's progress bar).
* **D2 — no negative receipt.** `.gate-receipts/` is a success cache with one consumer
  (`receiptStatus`, "is there reusable proof for this tree?"); a failure entry would gate nothing
  and add a second record type to it. The transcript header carries tree and command, so a later
  session can see that a tree failed once even after a green receipt was recorded for it.
  Rejected: negative receipt naming the transcript.
* **D3 — shared location `artifacts/gates/`, inherited run directory, retention 100.** Rejected:
  `.gate-receipts/<gate>.log` overwritten per run (loses the one failure the MANDATE is about as
  soon as the agent re-runs); a gate-receipt-only directory with its own retention (a second
  copy of the scheduler's layout, rule 11); writing no transcript when run under the scheduler
  (two behaviours depending on the caller; the lane log contains wrapper noise and is named after
  the lane, not the gate). Cost accepted: a scheduler lane's gate output is stored twice inside one
  run directory (lane log + transcript), bounded by O3.
* **D4 — transcript write failure fails closed**, matching the scheduler's existing `logError`
  rule; rejected: warn and record the receipt anyway (two contracts for one failure).
* **D5 — child stays in gate-receipt's process group.** Rejected: `detached: true` like the
  scheduler — the scheduler's group kill of a lane would then miss the gate's child (P2),
  orphaning `cargo`/`docker` on interruption.
* **D6 — stdin becomes `ignore`** (was inherited), matching the scheduler, which already runs six
  of the seven gates with stdin ignored (P2); no gate command reads stdin
  (`scripts/run-e2e-container.mjs`, `scripts/run-frontend-mutation.mjs` contain no `isTTY`/stdin
  use).

## Decided autonomously

* **Q:** How does the gate capture its transcript (pty, second fd, pipe tee, or caller
  contract)? **Chosen:** pipe tee (D1). **Rejected:** pty via `script(1)`, caller contract.
  **Reason:** P5 measurement — no agent or scheduler caller sees any change; failure content is
  identical for the measured tools.
* **Q:** Does a failing gate record a negative receipt? **Chosen:** no; the retained transcript
  with its tree/command header is the failure record (D2). **Rejected:** negative receipt.
  **Reason:** the receipt cache has one success-only consumer.
* **Q:** Where are transcripts kept and for how long? **Chosen:** `artifacts/gates/<run>/
  receipt-<gate>.log`, shared with the scheduler through `GATE_LOG_DIRECTORY`, newest 100 run
  directories (D3, O3). **Rejected:** overwrite per gate; separate directory; no transcript under
  the scheduler. **Reason:** retention across re-runs is the point; one layout and one bound.
* **Q:** What happens when the transcript cannot be written? **Chosen:** refuse before start if
  it cannot be opened; fail closed if writing fails mid-run (D4). **Rejected:** proceed silently.
