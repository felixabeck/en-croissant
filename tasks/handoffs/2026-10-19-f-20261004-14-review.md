## Approach

### O1 — sanitized document ownership

Make one session-specific boundary own the current sanitized public list for the document. Bootstrap and sessionsAtom use it, rather than independently reading/writing a key with different lifetimes. After safe erasure, publish the sanitized/reconciled list before feature consumers mount. Initial atom reads, mount hydration and later remounts must retain that list even if the key was removed or contains an older public snapshot. Preserve aliases, provider data, updatedAt, and current native handle reconciliation. A successful native listing remains authoritative over migration and old handles. A failed listing keeps the current offline behavior, as settled by d-20261014-10.

All ordinary account atom updates must replace this same current list. A later save retry uses its latest value, including edits and removals, never a captured startup list. Keep at most the current list and a small persistence status, with listeners cleaned up when consumers unmount. No retry queue, polling loop, unload task or captured legacy-token snapshot.

Verification: an integration test using the real bootstrap and actual sessionsAtom must observe the complete safe list before and after account consumer mount/remount under permanent write refusal. It must observe a later alias edit/removal and prevent retry from resurrecting the startup list. This must fail with the retention fix reverted while the new test remains.

### O2 — explicit public save outcome

Session persistence success is a successful write of the current safe list. A failed final write is a typed recoverable unsaved outcome carrying the public list/status, distinct from SessionSanitizationError and from unavailable native reconciliation. Preserve the automatic post-removal write attempt, which can succeed when erasure frees quota. Do not discard the safe in-memory list or treat failed persistence as a successful empty list.

Use the same session-specific validated serialization boundary for startup writes, normal atom writes, retries and hydration. Write with serializeStorageValue, read its encoding with legacy JSON compatibility through decodeCompressedOrJson, and retain sessionsSchema stripping. Do not change unrelated createZodStorage consumers. Storage exceptions stay handled and never expose raw exception text or stored contents. Existing account writer APIs continue to work, including functional atom updates. Persistent success clears unsaved status only for the latest list. Retry is a bounded explicit save attempt without native migration, listing, token revocation or reload.

Verification: real storage fault injection must distinguish a first overwrite refusal followed by successful post-removal persistence from permanent refusal. After recovery, a reload without fixture reseeding must restore the latest saved public list through the production decoder. Existing raw JSON records must still migrate, and canonical encoded values must round-trip through both startup and atom paths. Failed retry keeps the list and unsaved status.

### O3 — truthful mounted failure surface

Show a persistent, translated warning in the normal App provider tree while the current list is unsaved. It must be visible beyond the Accounts route, say accounts are available for this session but changes can be lost on close/reload, and offer an in-document save retry. A transient toast or a native migration-durability warning is insufficient. Hide the warning only once the current list is saved. Ordinary account updates that still fail keep the warning current, and a successful ordinary write may clear it. Use existing Mantine components and existing i18next catalog/extraction conventions. Do not offer reload/reset as recovery for this volatile list.

Verification: component tests assert warning persistence, the save action and status clearing. Container Playwright tests assert actual cards/aliases plus the warning under storage refusal, a newer edit surviving retry, and recovery after storage becomes writable. Inspect a desktop and a narrow 320px/200% font-scale screenshot for the new warning, with no clipped explanation or action. Localization failures retain readable shipped fallback copy as in the existing startup failure view.

### O4 — preserve the credential failure boundary

If both legacy erasure routes fail, keep existing token revocation and standalone fail-closed behavior from d-20261004-11 and d-20261004-12. Do not mount App or publish a usable session snapshot on that path. The new public-save status cannot convert it into recoverable App startup. Sanitization remains synchronous before the first native await, and only schema-sanitized public data can pass to the new owner. Errors, UI and logs remain credential-free. No native command, generated binding, capability, or keyring change is required.
