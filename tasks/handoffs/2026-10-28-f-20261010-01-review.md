# Plan: Database-view durable admission

## Goal

Give every `database-view` mutation one synchronous admission: the next value is stored under `database-view` before memory changes, a refusal leaves both the previous memory and the previous stored bytes in place and reports the existing storage error, and opening a database navigates only after that admission succeeds.

## MANDATE

f-20261010-01. Status open. Area frontend-state. Entry build. Blocked none. This plan does not close it.

* **Defect:** `activeDatabaseViewStore` uses raw `createJSONStorage(() => sessionStorage)`. Its setters publish in-memory state through Zustand and persist without a handled storage-write contract. A refused `database-view` write, such as shared session-storage quota exhaustion, escapes `setDatabase` after memory changes. The existing database double-click path navigates and calls that setter without catching the refusal. Later reload restores the previous stored database-view value.
* **Open question:** what is the durable admission and refusal contract for all database-view setters, including clear, selection and filter writes, and which existing storage adapter should own it? Resolve memory/durable-state agreement together with failure reporting, rather than adding a catch only to one new opening control.
* **Why build:** the design must settle whether a database-view mutation is refused atomically or admitted transiently with an explicit durability state, and route every setter/reader through the same contract. This is a separate persisted-state ownership problem. It exists independently of which visible button or row gesture invokes database opening.
* **Related:** f-20261001-13 concerns hydration validation in the same store. It does not cover write refusal. f-20261001-08 concerns discoverable opening controls. Its plan review identified this independent persistence hazard and retains the existing persistence limitation without adding a new storage mechanism to that mandate.
* **Proof required:** real-store tests with `setItem` refusing after a seeded previous value, assertions for both memory and stored state, reload, a successful retry, and affected database-route consumer behavior. Preserve previous stored bytes and user tab trees.
* **D2 review evidence from f-20261001-14 (2026-10-14):** review-persisted-state traced the unchanged raw createJSONStorage sessionStorage writer in database.ts. ## Threat model and non-goals

The adversary is `sessionStorage.setItem` throwing for the key `database-view`, including `QuotaExceededError` when the origin quota is already full. The previous value of that key must remain. Other session keys, including tab-tree keys, must keep their bytes. The user can retry the same mutation after the refusal. Reload reads whatever bytes survived.

In scope: every mutation of this store, including the public `setState`, and every reader of the `database-view` key that must understand the bytes those mutations write. The readers today are the persist hydration path and `collectOriginalSnapshots` in `pathOwners.ts`.

Out of scope for this adversary: a crash inside the browser's `setItem` after it has already replaced the key, cross-webview coordination, a second writer of the same key, and a subscriber that throws after a write that already succeeded. Web Storage is treated as all-or-nothing for the proof: the refusing spy throws before the native write. No new durability flag, journal, IndexedDB, debounce, or cap.

## Approach

### Admission before publish

One admission serves every mutation of this store, including the public `setState`. It computes the state the raw setter would publish, including a partial object, a function partial, and the replace flag. It JSON-encodes that state the same way `JSON.stringify` drops functions, wraps `{ state, version: 0 }`, and writes `serializeStorageValue` of that envelope to `sessionStorage` under `database-view`. Only after that write returns does it publish through the raw setter captured outside persist, the same capture `transitionPuzzleSession` uses so publish does not queue a second write.

At the moment `setItem` throws, memory and any subscriber still see the previous state, and the seeded bytes of `database-view` are unchanged. There is no publish-then-rollback. Hydration keeps using persist's raw `set` and does not rewrite storage while the version stays 0, so rehydrate does not double-write.

Named `DatabaseViewStore` methods return `true` after publish and `false` when the write throws. The public `setState` wrapper uses the same admission and returns that boolean at runtime. Preserve Zustand's partial and replace behavior. Do not leave any named setter on the persist-wrapped `set`.

If the raw setter's subscriber throws after a successful write, memory is already updated. Do not report that throw as a storage refusal and do not try to undo the write.

### Encoding and readers

The adapter that owns the key is `serializeStorageValue` for the write and `decodeCompressedOrJson` for every read. It is not `tabStorage`, not debounce, and not `createZodStorage`.

The persist storage `getItem` returns the JSON text of `decodeCompressedOrJson` so both a legacy plain `{state, version: 0}` value and a compressed envelope hydrate through the existing `merge`. A failed decode hydrates as absent. `setItem` on that adapter, if persist still calls it, writes the compressed envelope too, so a stray persist write cannot put plain JSON back.

`pathOwners.ts` reads this key with `readCompressed` and leaves every other `readJson` key on `readJson`. A failed decode still withholds trust for `databaseView` and does not delete the key.

Do not bump the persist version and do not add `migrate`. The next successful mutation is what replaces plain JSON with the compressed envelope. Startup repair, workspace load, and tab-tree clone must not rewrite `database-view`.

`src/utils/db.test.ts` must decode with `decodeCompressedOrJson` and still assert version 0 and the decimal `storage_size`. The plain-JSON hydration seeds in `database.test.ts`, `GameTable.test.tsx`, and `workspace.test.ts` stay valid inputs.

### Failure reporting

On refusal, call `reportPersistError(new Error(storageErrorCause(cause), { cause }))` and return `false`. Do not throw into a React effect. Do not use `persistStorageWriteError` or `createTabStorageQuotaError`. Do not add an i18n key. Do not cap repeated notifications: each refused call reports once, which matches the engine-list posture.

### Callers

`openDatabase` navigates only when `setDatabase` returns `true`. Any other result, including `undefined`, is a refusal and does not navigate. Test doubles that stand in for a successful open must return `true`. `DatabasesPage.test.tsx` is one of those doubles. It is not the admission proof.

Effects and filter, selection, and tab setters may ignore `false`. They must not retry inside the same effect while its inputs are unchanged. A refused route-sync `setDatabase` leaves `resolveDatabaseRoute` at `synchronizing`, so database children do not render, and the effect does not loop. A later change to the effect's inputs, or another user call after quota is free, is the retry.

`clearDatabase` after a native database delete stays after the delete. A refused clear leaves memory and storage naming that database until a later clear succeeds. `DatabaseView` may try `clearDatabase` again when it resolves `not_found`. Do not clear before the native delete: a refused clear would block deleting a file that is still there, and a failed delete after a successful clear would drop the view of a file that is still there. d-20260910-11 is the reversal path if a later finding wants the delete gated on admission. This plan does not add that transaction.

A refused filter or selection write does not change the query, so a result list keyed by that query does not refetch.

### Limits that stay

Hydration schemas and per-field fallback stay as they are. f-20261001-13 is not reopened. No shared helper is extracted with `transitionPuzzleSession` or the workspace receipt. The order is the same and the format, parser, debounce, and error copy are not. A transient `persistence: "memory" | "refused"` flag is rejected: the proof requires the previous memory and the previous bytes, and a subscriber must not observe an unadmitted view.

Direct navigation to a database URL while `setItem` is refusing can sit on `synchronizing` with the existing storage notification. That is the honest state. It is not a new product screen.

`Sidebar.test.tsx` may `setState` an invalid database. A successful write stores that value and publishes it. Reload still drops a malformed `database` in `merge`. This plan does not add a new validation on the write path.

## Decisions and trade-offs

### Decided autonomously

Question: what is the durable admission and refusal contract for all database-view setters, including clear, selection and filter writes, and which existing storage adapter should own it?

Chosen: refuse the mutation unless the compressed `{state, version: 0}` envelope is stored under `database-view` first, then publish with the raw setter. `serializeStorageValue` and `decodeCompressedOrJson` own the bytes. `storageErrorCause` plus `reportPersistError` own the report. Named setters return boolean. `openDatabase` navigates only on `true`. `pathOwners` reads this key through `readCompressed`. Legacy plain JSON remains readable. No version bump.

## Approach

### Admission before publish

One admission serves every mutation of this store, including the public `setState`. It computes the state the raw setter would publish, including a partial object, a function partial, and the replace flag. It JSON-encodes that state the same way `JSON.stringify` drops functions, wraps `{ state, version: 0 }`, and writes `serializeStorageValue` of that envelope to `sessionStorage` under `database-view`. Only after that write returns does it publish through the raw setter captured outside persist, the same capture `transitionPuzzleSession` uses so publish does not queue a second write.

At the moment `setItem` throws, memory and any subscriber still see the previous state, and the seeded bytes of `database-view` are unchanged. There is no publish-then-rollback. Hydration keeps using persist's raw `set` and does not rewrite storage while the version stays 0, so rehydrate does not double-write.

Named `DatabaseViewStore` methods return `true` after publish and `false` when the write throws. The public `setState` wrapper uses the same admission and returns that boolean at runtime. Preserve Zustand's partial and replace behavior. Do not leave any named setter on the persist-wrapped `set`.

If the raw setter's subscriber throws after a successful write, memory is already updated. Do not report that throw as a storage refusal and do not try to undo the write.

### Encoding and readers

The adapter that owns the key is `serializeStorageValue` for the write and `decodeCompressedOrJson` for every read. It is not `tabStorage`, not debounce, and not `createZodStorage`.

The persist storage `getItem` returns the JSON text of `decodeCompressedOrJson` so both a legacy plain `{state, version: 0}` value and a compressed envelope hydrate through the existing `merge`. A failed decode hydrates as absent. `setItem` on that adapter, if persist still calls it, writes the compressed envelope too, so a stray persist write cannot put plain JSON back.

`pathOwners.ts` reads this key with `readCompressed` and leaves every other `readJson` key on `readJson`. A failed decode still withholds trust for `databaseView` and does not delete the key.

Do not bump the persist version and do not add `migrate`. The next successful mutation is what replaces plain JSON with the compressed envelope. Startup repair, workspace load, and tab-tree clone must not rewrite `database-view`.

`src/utils/db.test.ts` must decode with `decodeCompressedOrJson` and still assert version 0 and the decimal `storage_size`. The plain-JSON hydration seeds in `database.test.ts`, `GameTable.test.tsx`, and `workspace.test.ts` stay valid inputs. A successful write is proved only when `deserializeStorageValue` of the stored string returns the envelope. `decodeCompressedOrJson` also accepts plain JSON, so it cannot be the sole proof that the writer compressed. The stored string must not be `JSON.stringify` of that envelope.

### Failure reporting

On refusal, call `reportPersistError(new Error(storageErrorCause(cause), { cause }))` and return `false`. Do not throw into a React effect. Do not use `persistStorageWriteError` or `createTabStorageQuotaError`. Do not add an i18n key. Do not cap repeated notifications: each refused call reports once, which matches the engine-list posture.

### Callers

Every control that opens a database navigates only after `setDatabase` returns `true`. Any other result, including `undefined`, is a refusal and does not navigate.

* `openDatabase` (double-click and the Open button) returns before `navigate` unless the result is `true`.
* Explore calls `preventDefault` on the click when admission is not `true`, then returns. It does not rely on the click handler's return value. Link preload may still warm the route; preload does not publish `database-view` and is not gated.
* The info-panel database card admits first and calls `navigate` only after `true`. It does not navigate while the write is still in flight or after a refusal.

Test doubles that stand in for a successful open must return `true`. `DatabasesPage.test.tsx` is one of those doubles. It is not the admission proof. `InfoPanel.test.tsx` currently expects navigation to start before `setDatabase`. That assertion is rewritten to the admission-then-navigate order, and a refusal case on the real store asserts that `navigate` is not called and the previous view remains.

Effects and filter, selection, and tab setters may ignore `false`. They must not retry inside the same effect while its inputs are unchanged.

A refused `setDatabase` from the synchronizing branch leaves the resolution at `synchronizing`. `DatabaseView` does not render database children. The effect runs one admission attempt and does not loop. A refused `setDatabase` from the ready generation-mismatch branch leaves the resolution at `ready`, because the handles still match. Memory, stored bytes, and the rendered children stay on the previously admitted generation, including the SWR key `GameTable` builds from that generation. That effect also attempts admission once and does not loop. A later change to the effect's inputs, or another user call after quota is free, is the retry. The route proof renders the real `DatabaseView` with the real store. The existing mocked `DatabaseView.test.tsx` does not count.

`clearDatabase` after a native database delete stays after the delete. A refused clear leaves memory and storage naming that database until a later clear succeeds. `DatabaseView` may try `clearDatabase` again when it resolves `not_found`. Do not clear before the native delete: a refused clear would block deleting a file that is still there, and a failed delete after a successful clear would drop the view of a file that is still there. d-20260910-11 is the reversal path if a later finding wants the delete gated on admission. This plan does not add that transaction.

A refused filter or selection write does not change the query, so a result list keyed by that query does not refetch.

## Approach

### Admission before publish

One admission serves every mutation of this store, including the public `setState`. It computes the state the raw setter would publish, including a partial object, a function partial, and the replace flag. It JSON-encodes that state the same way `JSON.stringify` drops functions, wraps `{ state, version: 0 }`, and writes `serializeStorageValue` of that envelope to `sessionStorage` under `database-view`. Only after that write returns does it publish through the raw setter captured outside persist, the same capture `transitionPuzzleSession` uses so publish does not queue a second write.

At the moment `setItem` throws, memory and any subscriber still see the previous state, and the seeded bytes of `database-view` are unchanged. There is no publish-then-rollback. Hydration keeps using persist's raw `set` and does not rewrite storage while the version stays 0, so rehydrate does not double-write.

Named `DatabaseViewStore` methods return `true` after publish and `false` when the write throws. The public `setState` wrapper uses the same admission and returns that boolean at runtime. Preserve Zustand's partial and replace behavior. Do not leave any named setter on the persist-wrapped `set`.

If the raw setter's subscriber throws after a successful write, memory is already updated. Do not report that throw as a storage refusal and do not try to undo the write.

### Encoding and readers

The adapter that owns the key is `serializeStorageValue` for the write and `decodeCompressedOrJson` for every read. It is not `tabStorage`, not debounce, and not `createZodStorage`.

The persist storage `getItem` returns the JSON text of `decodeCompressedOrJson` so both a legacy plain `{state, version: 0}` value and a compressed envelope hydrate through the existing `merge`. A failed decode hydrates as absent. `setItem` on that adapter, if persist still calls it, writes the compressed envelope too, so a stray persist write cannot put plain JSON back.

`pathOwners.ts` reads this key with `readCompressed` and leaves every other `readJson` key on `readJson`. A failed decode still withholds trust for `databaseView` and does not delete the key.

Do not bump the persist version and do not add `migrate`. The next successful mutation is what replaces plain JSON with the compressed envelope. Startup repair, workspace load, and tab-tree clone must not rewrite `database-view`.

`src/utils/db.test.ts` must decode with `decodeCompressedOrJson` and still assert version 0 and the decimal `storage_size`. The plain-JSON hydration seeds in `database.test.ts`, `GameTable.test.tsx`, and `workspace.test.ts` stay valid inputs. A successful write is proved only when `deserializeStorageValue` of the stored string returns the envelope. `decodeCompressedOrJson` also accepts plain JSON, so it cannot be the sole proof that the writer compressed. The stored string must not be `JSON.stringify` of that envelope.

### Failure reporting

On refusal, call `reportPersistError(new Error(storageErrorCause(cause), { cause }))` and return `false`. Do not throw into a React effect. Do not use `persistStorageWriteError` or `createTabStorageQuotaError`. Do not add an i18n key. Do not cap repeated notifications: each refused call reports once, which matches the engine-list posture.

### Callers

A control that calls `setDatabase` and navigates in the same action navigates only after that call returns `true`. Any other result, including `undefined`, is a refusal and does not navigate. The production controls are `openDatabase`, library Explore, and the info-panel database card.

* `openDatabase` (double-click and the Open button) returns before `navigate` unless the result is `true`.
* Explore calls `preventDefault` on the click when admission is not `true`, then returns. It does not rely on the click handler's return value. Link preload may still warm the route; preload does not publish `database-view` and is not gated.
* The info-panel database card admits first and calls `navigate` only after `true`. It does not navigate while the write is still in flight or after a refusal.

Test doubles that stand in for a successful open must return `true`. `DatabasesPage.test.tsx` is one of those doubles. It is not the admission proof. `InfoPanel.test.tsx` currently expects navigation to start before `setDatabase`. That assertion is rewritten to the admission-then-navigate order, and a refusal case on the real store asserts that `navigate` is not called and the previous view remains.

Effects and filter, selection, and tab setters may ignore `false`. They must not retry inside the same effect while its inputs are unchanged.

A refused `setDatabase` from the synchronizing branch leaves the resolution at `synchronizing`. `DatabaseView` does not render database children. The effect runs one admission attempt and does not loop. A refused `setDatabase` from the ready generation-mismatch branch leaves the resolution at `ready`, because the handles still match. Memory, stored bytes, and the rendered children stay on the previously admitted generation, including the SWR key `GameTable` builds from that generation. That effect also attempts admission once and does not loop. A later change to the effect's inputs, or another user call after quota is free, is the retry. The route proof renders the real `DatabaseView` with the real store. The existing mocked `DatabaseView.test.tsx` does not count.

`clearDatabase` after a native database delete stays after the delete. A refused clear leaves memory and storage naming that database until a later clear succeeds. `DatabaseView` may try `clearDatabase` again when it resolves `not_found`. Do not clear before the native delete: a refused clear would block deleting a file that is still there, and a failed delete after a successful clear would drop the view of a file that is still there. d-20260910-11 is the reversal path if a later finding wants the delete gated on admission. This plan does not add that transaction.

A refused filter or selection write does not change the query, so a result list keyed by that query does not refetch.

URL-only navigation does not call `setDatabase` and must not grow one. `LinkedCollection` Explore, the retired-collection redirect, the sidebar library target, and a pasted database URL leave admission to the `DatabaseView` effect. A refusal there uses the synchronizing or generation-mismatch behavior above. Adding a setter to those links would publish a view before the URL effect runs and would race that effect. No new test file is required for them: the real `DatabaseView` refusal proof is the behavior after the URL has changed.

### Limits that stay

Hydration schemas and per-field fallback stay as they are. f-20261001-13 is not reopened. No shared helper is extracted with `transitionPuzzleSession` or the workspace receipt. The order is the same and the format, parser, debounce, and error copy are not. A transient `persistence: "memory" | "refused"` flag is rejected: the proof requires the previous memory and the previous bytes, and a subscriber must not observe an unadmitted view.

Direct navigation to a database URL while `setItem` is refusing can sit on `synchronizing` with the existing storage notification when the URL handle is not the admitted handle. When the handle matches and only the generation differs, the page stays on the admitted generation. Neither case is a new product screen.

`Sidebar.test.tsx` may `setState` an invalid database. A successful write stores that value and publishes it. Reload still drops a malformed `database` in `merge`. This plan does not add a new validation on the write path.

## Decisions and trade-offs

### Decided autonomously

Question: what is the durable admission and refusal contract for all database-view setters, including clear, selection and filter writes, and which existing storage adapter should own it?

Chosen: refuse the mutation unless the compressed `{state, version: 0}` envelope is stored under `database-view` first, then publish with the raw setter. `serializeStorageValue` and `decodeCompressedOrJson` own the bytes. `storageErrorCause` plus `reportPersistError` own the report. Named setters return boolean. `openDatabase`, Explore, and the info-panel database card navigate only on `true`. Explore stops the router with `preventDefault` because the router ignores the handler's return value. A refused generation refresh keeps the admitted generation and leaves the route `ready`. A refused handle sync stays `synchronizing` and does not render database children. `pathOwners` reads this key through `readCompressed`. Legacy plain JSON remains readable. No version bump.

Rejected: a catch after the persist-wrapped publish, including a rollback after publish; a `memory`/`refused` flag that lets subscribers see an unadmitted view; treating only `openDatabase` as the navigation gate; stopping Explore by returning `false` from `onClick`; navigating from the info panel before admission returns; calling `setDatabase` from a URL-only link before navigation; `tabStorage.seed` or its debounced `setItem`; `createZodStorage.write`; a new IndexedDB, journal, cap, or i18n key; sharing code with the tree transition or the workspace receipt; gating native database deletion on `clearDatabase`; bumping the persist version so hydration rewrites the key.

Reason: Zustand 5.0.11 publishes before `setItem`, which is the defect. d-20260910-10 already requires publish-after-success and navigation only after a committed id, without crash atomicity. The persisted-state rule requires this serializer for the write and the matching decode for every reader, and `pathOwners` is the other reader. The tree and workspace helpers throw different errors, debounce, or use a different envelope.

Reversal: a later finding that needs the native delete to wait for a successful clear follows d-20260910-11's order and records its own decision. A different encoding needs both readers and the decimal-metadata test updated together. The adopter records this decision with `record-decision` before implementation. This plan does not edit `tasks/decisions.md`.

## Approach

### Admission before publish

One admission serves every mutation of this store, including the public `setState`. It computes the state the raw setter would publish, including a partial object, a function partial, and the replace flag. It JSON-encodes that state the same way `JSON.stringify` drops functions, wraps `{ state, version: 0 }`, and writes `serializeStorageValue` of that envelope to `sessionStorage` under `database-view`. Only after that write returns does it publish through the raw setter captured outside persist, the same capture `transitionPuzzleSession` uses so publish does not queue a second write.

At the moment `setItem` throws, memory and any subscriber still see the previous state, and the seeded bytes of `database-view` are unchanged. There is no publish-then-rollback. Hydration keeps using persist's raw `set` and does not rewrite storage while the version stays 0, so rehydrate does not double-write.

Named `DatabaseViewStore` methods return `true` after publish and `false` when the write throws. The public `setState` wrapper uses the same admission and returns that boolean at runtime. Preserve Zustand's partial and replace behavior. Do not leave any named setter on the persist-wrapped `set`.

If the raw setter's subscriber throws after a successful write, memory is already updated. Do not report that throw as a storage refusal and do not try to undo the write.

### Encoding and readers

The adapter that owns the key is `serializeStorageValue` for the write and `decodeCompressedOrJson` for every read. It is not `tabStorage`, not debounce, and not `createZodStorage`.

The persist storage `getItem` returns the JSON text of `decodeCompressedOrJson` so both a legacy plain `{state, version: 0}` value and a compressed envelope hydrate through the existing `merge`. A failed decode hydrates as absent. `setItem` on that adapter, if persist still calls it, writes the compressed envelope too, so a stray persist write cannot put plain JSON back.

`pathOwners.ts` reads this key with `readCompressed` and leaves every other `readJson` key on `readJson`. A failed decode still withholds trust for `databaseView` and does not delete the key.

Do not bump the persist version and do not add `migrate`. The next successful mutation is what replaces plain JSON with the compressed envelope. Startup repair, workspace load, and tab-tree clone must not rewrite `database-view`.

`src/utils/db.test.ts` must decode with `decodeCompressedOrJson` and still assert version 0 and the decimal `storage_size`. The plain-JSON hydration seeds in `database.test.ts`, `GameTable.test.tsx`, and `workspace.test.ts` stay valid inputs. A successful write is proved only when `deserializeStorageValue` of the stored string returns the envelope. `decodeCompressedOrJson` also accepts plain JSON, so it cannot be the sole proof that the writer compressed. The stored string must not be `JSON.stringify` of that envelope.

### Failure reporting

On refusal, call `reportPersistError(new Error(storageErrorCause(cause), { cause }))` and return `false`. Do not throw into a React effect. Do not use `persistStorageWriteError` or `createTabStorageQuotaError`. Do not add an i18n key. Do not cap repeated notifications: each refused call reports once, which matches the engine-list posture.

### Callers

A control that calls `setDatabase` and navigates in the same action navigates only after that call returns `true`. Any other result, including `undefined`, is a refusal and does not navigate. The production controls are `openDatabase`, library Explore, and the info-panel database card.

* `openDatabase` (double-click and the Open button) returns before `navigate` unless the result is `true`.
* Explore calls `preventDefault` on the click when admission is not `true`, then returns. It does not rely on the click handler's return value. Link preload may still warm the route; preload does not publish `database-view` and is not gated.
* The info-panel database card admits first and calls `navigate` only after `true`. It does not navigate while the write is still in flight or after a refusal.

Test doubles that stand in for a successful open must return `true`. `DatabasesPage.test.tsx` is one of those doubles. It is not the admission proof. `InfoPanel.test.tsx` currently expects navigation to start before `setDatabase`. That assertion is rewritten to the admission-then-navigate order, and a refusal case on the real store asserts that `navigate` is not called and the previous view remains.

Effects and filter, selection, and tab setters may ignore `false`. They must not retry inside the same effect while its inputs are unchanged.

A refused `setDatabase` from the synchronizing branch leaves the resolution at `synchronizing`. `DatabaseView` does not render database children. The effect runs one admission attempt and does not loop. A refused `setDatabase` from the ready generation-mismatch branch leaves the resolution at `ready`, because the handles still match. Memory, stored bytes, and the rendered children stay on the previously admitted generation, including the SWR key `GameTable` builds from that generation. That effect also attempts admission once and does not loop. A later change to the effect's inputs, or another user call after quota is free, is the retry. The route proof renders the real `DatabaseView` with the real store. The existing mocked `DatabaseView.test.tsx` does not count.

`clearDatabase` after a native database delete stays after the delete. A refused clear leaves memory and storage naming that database until a later clear succeeds. `DatabaseView` may try `clearDatabase` again when it resolves `not_found`. Do not clear before the native delete: a refused clear would block deleting a file that is still there, and a failed delete after a successful clear would drop the view of a file that is still there. d-20260910-11 is the reversal path if a later finding wants the delete gated on admission. This plan does not add that transaction.

A refused filter or selection write does not change the query, so a result list keyed by that query does not refetch.

URL-only navigation does not call `setDatabase` and must not grow one. `LinkedCollection` Explore, the retired-collection redirect, the sidebar library target, and a pasted database URL leave admission to the `DatabaseView` effect. A refusal there uses the synchronizing or generation-mismatch behavior above. Adding a setter to those links would publish a view before the URL effect runs and would race that effect. No new test file is required for them: the real `DatabaseView` refusal proof is the behavior after the URL has changed.

### Limits that stay

Hydration schemas and per-field fallback stay as they are. f-20261001-13 is not reopened. No shared helper is extracted with `transitionPuzzleSession` or the workspace receipt. The order is the same and the format, parser, debounce, and error copy are not. A transient `persistence: "memory" | "refused"` flag is rejected: the proof requires the previous memory and the previous bytes, and a subscriber must not observe an unadmitted view.

Direct navigation to a database URL while `setItem` is refusing can sit on `synchronizing` with the existing storage notification when the URL handle is not the admitted handle. When the handle matches and only the generation differs, the page stays on the admitted generation. Neither case is a new product screen.

`Sidebar.test.tsx` may `setState` an invalid database. A successful write stores that value and publishes it. Reload still drops a malformed `database` in `merge`. This plan does not add a new validation on the write path.

## Decisions and trade-offs

### Decided autonomously

Question: what is the durable admission and refusal contract for all database-view setters, including clear, selection and filter writes, and which existing storage adapter should own it?

Chosen: refuse the mutation unless the compressed `{state, version: 0}` envelope is stored under `database-view` first, then publish with the raw setter. `serializeStorageValue` and `decodeCompressedOrJson` own the bytes. `storageErrorCause` plus `reportPersistError` own the report. Named setters return boolean. `openDatabase`, Explore, and the info-panel database card navigate only on `true`. Explore stops the router with `preventDefault` because the router ignores the handler's return value. A refused generation refresh keeps the admitted generation and leaves the route `ready`. A refused handle sync stays `synchronizing` and does not render database children. `pathOwners` reads this key through `readCompressed`. Legacy plain JSON remains readable. No version bump.

Rejected: a catch after the persist-wrapped publish, including a rollback after publish; a `memory`/`refused` flag that lets subscribers see an unadmitted view; treating only `openDatabase` as the navigation gate; stopping Explore by returning `false` from `onClick`; navigating from the info panel before admission returns; calling `setDatabase` from a URL-only link before navigation; `tabStorage.seed` or its debounced `setItem`; `createZodStorage.write`; a new IndexedDB, journal, cap, or i18n key; sharing code with the tree transition or the workspace receipt; gating native database deletion on `clearDatabase`; bumping the persist version so hydration rewrites the key.

Reason: Zustand 5.0.11 publishes before `setItem`, which is the defect. d-20260910-10 already requires publish-after-success and navigation only after a committed id, without crash atomicity. The persisted-state rule requires this serializer for the write and the matching decode for every reader, and `pathOwners` is the other reader. The tree and workspace helpers throw different errors, debounce, or use a different envelope.

Reversal: a later finding that needs the native delete to wait for a successful clear follows d-20260910-11's order and records its own decision. A different encoding needs both readers and the decimal-metadata test updated together. The adopter records this decision with `record-decision` before implementation. This plan does not edit `tasks/decisions.md`.

d-20261027-30, d-20261027-31, and d-20261027-32 use the word admission for the native exclusive-open flag. They govern f-20261009-03. They do not answer this question and do not change the chosen contract above.
