## Goal

## MANDATE

## Approach

### A. Native page byte budget

Rests on MANDATE: "caps the number of games … but not their total size … materialised into one
`Vec<String>` in a single call".

* **Contract.** `read_games(file, start, end)` returns a *non-empty prefix* of the requested
  inclusive range: games in order, starting at `start`, while the running sum of their scanned
  byte lengths (`range.end - range.start`) stays ≤ the page byte budget. The first requested game
  is always selected, so every non-empty request makes progress and a game over `MAX_PGN_BYTES`
  still fails with today's `ResourceLimit` from `read_range_bytes` (`pgn.rs:696-697`) instead of
  silently yielding an empty page. A game is included when the sum *equals* the budget.
* **Budget.** New `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). With the first-game rule, no page
  exceeds 10 MiB — the same ceiling one `read_game` call already has.
* **Where.** The selection runs inside `read_games_core`'s `select` closure, on the cached index,
  before any read. Games after the prefix are never read.
* **Unchanged.** The whole requested range is still bounds-checked first (`InvalidInput`), the
  1 000-game count cap stays (`d-20260905-20` keeps page protections), the empty-file `(0, 0) → []`
  case stays, an inverted cached range is still `Conflict` (never a zero-length game), cancellation
  and the per-game `stamp`/`revision` (`d-20260924-02`) are unchanged. The command signature and
  `src/bindings/generated.ts` do not change; `pnpm bindings:check` stays green.
* **Doc.** `read_games_core` carries a doc comment stating the short-page contract.
* **Verification** (Rust unit tests in `pgn.rs`, through `read_games_core` with the production
  budget of `PgnRepository::default()`, never a test-only limit). Tests 1–3 go red if the budget is
  removed or raised; tests 4–5 guard preserved behaviour:
  1. a request whose games exceed the budget returns exactly the fitting prefix, with the same
     `pgn`/`stamp`/`revision` a full read gives for those games;
  2. games after the prefix are never read — the test goes red for an implementation that reads the
     whole requested range and truncates afterwards;
  3. a game that lands the sum exactly on the budget is included;
  4. a first game over `MAX_PGN_BYTES` still yields `ResourceLimit`, not an empty page;
  5. an out-of-bounds `end` is still `InvalidInput` even when the prefix alone would be in bounds.

### B. Renderer continuation over short pages

Rests on MANDATE: "a byte budget per call with continuation".

* **Contract.** `GameSelector`'s `loadPage(start, end)` requests `readGames(path, next, end)` with
  `next = start + rows received so far`, converting each page to rows (headers parsed, PGN text
  dropped) before requesting the next, until `next > end`. Rows keep the index `next + i`.
* **Termination.** A page with zero games ends the continuation and returns the rows collected so
  far. The merge callback returns `previous` unchanged when it receives no entries, so an empty
  result cannot change `games` identity and re-trigger the visible-range effect.
* **Cancellation.** The abort signal is passed to every call; no further page is requested after
  the signal aborts.
* **Failure.** A rejected page rejects the whole load: the continuation stops and no rows of that
  load are merged. Merging the earlier pages' rows would change `games`, and the effect
  (`GameSelector.tsx:84-98`) would at once re-request the same visible range, so a persistent
  failure would loop. No rejection may reach a `loadMoreRows` call site unhandled (today an
  ordinary failure becomes an unhandled rejection: `useVirtualPageLoader.ts:55-58` rethrows it,
  `GameSelector.tsx:88,98` drop the promise with `void`). A cancellation, or any failure after the
  load's signal aborted, stays silent; any other error is surfaced **exactly once per failed load**
  with the existing `notifyUnlessCancelled(t("Common.Error"), error)`
  (`src/components/files/notifyError`), as `FileCard.tsx:59-62` does for the same command — once
  even when both call sites share one deduplicated request (`useVirtualPageLoader.ts:42-44` hands
  the same promise to `GameSelector.tsx:88` and `:98` when both ask for `(0, 0)` in a one-row list).
  Rows stay unloaded and are requested again on the next visible-range change, which is today's
  retry path.
* **Unchanged.** `useVirtualPageLoader` (range-keyed dedupe, one merge per load, generation guard
  against stale merges) and `FileCard` (a single-game request always receives its one game, or `[]`
  for an empty file).
* **Verification** (`GameSelector.test.tsx`, each would go red if the behaviour were removed):
  1. a short first page leads to a second call `(start + n, end)` and all rows merge at the right
     indices;
  2. each page is reduced to rows before the next read: with page one's header parse held pending,
     the second `readGames` call has not been issued;
  3. every `readGames` call of one load, continuation calls included, receives the load's signal;
  4. an abort between pages stops further calls;
  5. an empty page stops further calls, and an empty load leaves `games` identity unchanged (the
     `readGames` call count stays stable after settling);
  6. a rejected later page merges nothing, issues no further call, is surfaced once through the
     notification, and leaves no unhandled rejection; a cancellation rejection is not surfaced;
  7. in a one-row list where both call sites share the deduplicated `(0, 0)` request, one failure
     produces exactly one notification.

Dependency: B before A — the consumer must tolerate short pages before the producer emits them.

## Decisions and trade-offs

### Decided autonomously

1. **Page contract.** Question: byte budget with continuation, or a streaming reader? Chosen:
   byte-budgeted non-empty prefix page, continued by the renderer. Rejected: a Tauri channel or
   event stream (a new IPC event surface with listener lifetimes, for a ≤1 000-row virtual list);
   refusing an over-budget page with an error (files of large games become unbrowsable); an
   explicit `next`/`truncated` response field (a bindings change carrying what the result length
   already says). Reason: the cached index knows every game's size before reading, so the bound is
   enforced before allocation, with no new surface.
2. **Budget value.** Chosen: `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). Rejected: a smaller budget
   such as 1 MiB (more round trips for ordinary pages while one `read_game` may already carry
   10 MiB). Reason: keeps the existing largest single IPC response as the only ceiling.
3. **Continuation owner.** Chosen: `GameSelector.loadPage`, the sole multi-row consumer. Rejected:
   `useVirtualPageLoader` (generic range-keyed dedupe; the short-page rule is a `readGames`
   property) and the platform facade (would hide a multi-call loop behind one command name).
4. **ImportModal clause.** Already resolved by `fefd7a5f` / `d-20260927-01`; no change here.

### Considered and not taken

* A header-only listing command: `GameSelector` reads whole games only for their headers. It would
  move header parsing native and change the identity/stamp path, and still needs a byte budget —
  outside this MANDATE.

## Risks / open questions

* **Known limit, not worse than today:** rows from different continuation pages (or from separate

* The e2e mock returns one game for every range; with `numGames = 1` the continuation issues one

## Decisions and trade-offs

### Decided autonomously

1. **Page contract.** Question: byte budget with continuation, or a streaming reader? Chosen:
   byte-budgeted non-empty prefix page, continued by the renderer. Rejected: a Tauri channel or
   event stream (a new IPC event surface with listener lifetimes, for a ≤1 000-row virtual list);
   refusing an over-budget page with an error (files of large games become unbrowsable); an
   explicit `next`/`truncated` response field (a bindings change carrying what the result length
   already says). Reason: the cached index knows every game's size before reading, so the bound is
   enforced before allocation, with no new surface.
2. **Budget value.** Chosen: `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). Rejected: a smaller budget
   such as 1 MiB (more round trips for ordinary pages while one `read_game` may already carry
   10 MiB). Reason: keeps the existing largest single IPC response as the only ceiling.
3. **Continuation owner.** Chosen: `GameSelector.loadPage`, the sole multi-row consumer. Rejected:
   `useVirtualPageLoader` (generic range-keyed dedupe; the short-page rule is a `readGames`
   property) and the platform facade (would hide a multi-call loop behind one command name).
4. **ImportModal clause.** Already resolved by `fefd7a5f` / `d-20260927-01`; no change here.

### A. Native page byte budget

Rests on MANDATE: "caps the number of games … but not their total size … materialised into one
`Vec<String>` in a single call".

* **Contract.** `read_games(file, start, end)` returns a *non-empty prefix* of the requested
  inclusive range: games in order, starting at `start`, while the running sum of their scanned
  byte lengths (`range.end - range.start`) stays ≤ the page byte budget. The first requested game
  is always selected, so every non-empty request makes progress and a game over `MAX_PGN_BYTES`
  still fails with today's `ResourceLimit` from `read_range_bytes` (`pgn.rs:696-697`) instead of
  silently yielding an empty page. A game is included when the sum *equals* the budget.
* **Budget.** New `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). With the first-game rule, no page
  exceeds 10 MiB — the same ceiling one `read_game` call already has.
* **Where.** The selection runs inside `read_games_core`'s `select` closure, on the cached index,
  before any read. Games after the prefix are never read.
* **Unchanged.** The whole requested range is still bounds-checked first (`InvalidInput`), the
  1 000-game count cap stays (`d-20260905-20` keeps page protections), the empty-file `(0, 0) → []`

* **Verification** (Rust unit tests in `pgn.rs`, through `read_games_core` with the production

## Goal

## Approach

### A. Native page byte budget

Rests on MANDATE: "caps the number of games … but not their total size … materialised into one
`Vec<String>` in a single call".

* **Contract.** `read_games(file, start, end)` returns a *non-empty prefix* of the requested
  inclusive range: games in order, starting at `start`, while the running sum of their scanned
  byte lengths (`range.end - range.start`) stays ≤ the page byte budget. The first requested game
  is always selected, so every non-empty request makes progress and a game over `MAX_PGN_BYTES`
  still fails with today's `ResourceLimit` from `read_range_bytes` (`pgn.rs:696-697`) instead of
  silently yielding an empty page. A game is included when the sum *equals* the budget.
* **Budget.** New `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). With the first-game rule, no page
  exceeds 10 MiB — the same ceiling one `read_game` call already has.
* **Where.** The selection runs inside `read_games_core`'s `select` closure, on the cached index,
  before any read. Games after the prefix are never read.
* **Unchanged.** The whole requested range is still bounds-checked first (`InvalidInput`), the
  1 000-game count cap stays (`d-20260905-20` keeps page protections), the empty-file `(0, 0) → []`
  case stays, an inverted cached range is still `Conflict` (never a zero-length game), cancellation
  and the per-game `stamp`/`revision` (`d-20260924-02`) are unchanged. The command signature and
  `src/bindings/generated.ts` do not change; `pnpm bindings:check` stays green.
* **Doc.** `read_games_core` carries a doc comment stating the short-page contract.
* **Verification** (Rust unit tests in `pgn.rs`, through `read_games_core` with the production
  budget of `PgnRepository::default()`, never a test-only limit). Tests 1–3 go red if the budget is
  removed or raised; tests 4–5 guard preserved behaviour:
  1. a request whose games exceed the budget returns exactly the fitting prefix, with the same
     `pgn`/`stamp`/`revision` a full read gives for those games;
  2. games after the prefix are never read — the test goes red for an implementation that reads the
     whole requested range and truncates afterwards;
  3. a game that lands the sum exactly on the budget is included and the next game is excluded;
  4. a first game over `MAX_PGN_BYTES` still yields `ResourceLimit`, not an empty page;
  5. an out-of-bounds `end` is still `InvalidInput` even when the prefix alone would be in bounds.

### B. Renderer continuation over short pages

Rests on MANDATE: "a byte budget per call with continuation".

* **Contract.** `GameSelector`'s `loadPage(start, end)` requests `readGames(path, next, end)` with
  `next = start + rows received so far`, converting each page to rows (headers parsed, PGN text
  dropped) before requesting the next, until `next > end`. Rows keep the index `next + i`.
* **Termination.** A page with zero games ends the continuation and returns the rows collected so
  far. The merge callback returns `previous` unchanged when it receives no entries, so an empty
  result cannot change `games` identity and re-trigger the visible-range effect.
* **Cancellation.** The abort signal is passed to every call; no further page is requested after
  the signal aborts.
* **Failure.** A rejected page rejects the whole load: the continuation stops and no rows of that
  load are merged. Merging the earlier pages' rows would change `games`, and the effect
  (`GameSelector.tsx:84-98`) would at once re-request the same visible range, so a persistent
  failure would loop. No rejection may reach a `loadMoreRows` call site unhandled (today an
  ordinary failure becomes an unhandled rejection: `useVirtualPageLoader.ts:55-58` rethrows it,
  `GameSelector.tsx:88,98` drop the promise with `void`). A cancellation, or any failure after the
  load's signal aborted, stays silent; any other error is surfaced **exactly once per failed load**
  with the existing `notifyUnlessCancelled(t("Common.Error"), error)`
  (`src/components/files/notifyError`), as `FileCard.tsx:59-62` does for the same command — once
  even when both call sites share one deduplicated request (`useVirtualPageLoader.ts:42-44` hands
  the same promise to `GameSelector.tsx:88` and `:98` when both ask for `(0, 0)` in a one-row list).
  Rows stay unloaded and are requested again on the next visible-range change, which is today's
  retry path.
* **Unchanged.** `useVirtualPageLoader` (range-keyed dedupe, one merge per load, generation guard
  against stale merges) and `FileCard` (a single-game request always receives its one game, or `[]`
  for an empty file).
* **Verification** (`GameSelector.test.tsx`, each would go red if the behaviour were removed):
  1. a short first page leads to a second call `(start + n, end)` and all rows merge at the right
     indices;
  2. each page is reduced to rows before the next read: with page one's header parse held pending,
     the second `readGames` call has not been issued;
  3. every `readGames` call of one load, continuation calls included, receives the load's signal;
  4. an abort between pages stops further calls;
  5. an empty page stops further calls, and an empty load leaves `games` identity unchanged (the
     `readGames` call count stays stable after settling);
  6. a rejected later page merges nothing, issues no further call, is surfaced once through the
     notification, and leaves no unhandled rejection; a cancellation rejection is not surfaced;
  7. in a one-row list where both call sites share the deduplicated `(0, 0)` request, one failure
     produces exactly one notification;
  8. a pending load whose signal is aborted and whose `readGames` then rejects with an ordinary
     (non-cancellation) error produces no notification, no merge and no unhandled rejection
     (reachable: `src/platform/tauri.ts:285-287` rethrows a command failure without checking the
     signal, and `useVirtualPageLoader.ts:57` suppresses only the cancellation category).

## Decisions and trade-offs

### Decided autonomously

1. **Page contract.** Question: byte budget with continuation, or a streaming reader? Chosen:
   byte-budgeted non-empty prefix page, continued by the renderer. Rejected: a Tauri channel or
   event stream (a new IPC event surface with listener lifetimes, for a ≤1 000-row virtual list);
   refusing an over-budget page with an error (files of large games become unbrowsable); an
   explicit `next`/`truncated` response field (a bindings change carrying what the result length
   already says). Reason: the cached index knows every game's size before reading, so the bound is
   enforced before allocation, with no new surface.

## Goal

## Approach

### A. Native page byte budget

Rests on MANDATE: "caps the number of games … but not their total size … materialised into one
`Vec<String>` in a single call".

* **Contract.** `read_games(file, start, end)` returns a *non-empty prefix* of the requested
  inclusive range: games in order, starting at `start`, while the running sum of their scanned
  byte lengths (`range.end - range.start`) stays ≤ the page byte budget. The first requested game
  is always selected, so every non-empty request makes progress and a game over `MAX_PGN_BYTES`
  still fails with today's `ResourceLimit` from `read_range_bytes` (`pgn.rs:696-697`) instead of
  silently yielding an empty page. A game is included when the sum *equals* the budget.
* **Budget.** New `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). With the first-game rule, no page
  exceeds 10 MiB — the same ceiling one `read_game` call already has.
* **Where.** The selection runs inside `read_games_core`'s `select` closure, on the cached index,
  before any read. Games after the prefix are never read.
* **Unchanged.** The whole requested range is still bounds-checked first (`InvalidInput`), the
  1 000-game count cap stays (`d-20260905-20` keeps page protections), the empty-file `(0, 0) → []`
  case stays, an inverted cached range is still `Conflict` (never a zero-length game), cancellation
  and the per-game `stamp`/`revision` (`d-20260924-02`) are unchanged. The command signature and
  `src/bindings/generated.ts` do not change; `pnpm bindings:check` stays green.
* **Doc.** `read_games_core` carries a doc comment stating the short-page contract.
* **Verification** (Rust unit tests in `pgn.rs`, through `read_games_core` with the production
  budget of `PgnRepository::default()`, never a test-only limit). Tests 1–3 go red if the budget is
  removed or raised; tests 4–5 guard preserved behaviour:
  1. a request whose games exceed the budget returns exactly the fitting prefix, with the same
     `pgn`/`stamp`/`revision` a full read gives for those games;
  2. games after the prefix are never read — the test goes red for an implementation that reads the
     whole requested range and truncates afterwards;
  3. a game that lands the sum exactly on the budget is included and the next game is excluded;
  4. a first game over `MAX_PGN_BYTES` still yields `ResourceLimit`, not an empty page;
  5. an out-of-bounds `end` is still `InvalidInput` even when the prefix alone would be in bounds.

### B. Renderer continuation over short pages

Rests on MANDATE: "a byte budget per call with continuation".

* **Contract.** `GameSelector`'s `loadPage(start, end)` requests `readGames(path, next, end)` with
  `next = start + rows received so far`, converting each page to rows (headers parsed, PGN text
  dropped) before requesting the next, until `next > end`. Rows keep the index `next + i`.
* **Termination.** A page with zero games ends the continuation and returns the rows collected so
  far. The merge callback returns `previous` unchanged when it receives no entries, so an empty
  result cannot change `games` identity and re-trigger the visible-range effect.
* **Cancellation.** The abort signal is passed to every call; no further page is requested after
  the signal aborts.
* **Failure.** A rejected page rejects the whole load: the continuation stops and no rows of that
  load are merged. Merging the earlier pages' rows would change `games`, and the effect
  (`GameSelector.tsx:84-98`) would at once re-request the same visible range, so a persistent
  failure would loop. No rejection may reach a `loadMoreRows` call site unhandled (today an
  ordinary failure becomes an unhandled rejection: `useVirtualPageLoader.ts:55-58` rethrows it,
  `GameSelector.tsx:88,98` drop the promise with `void`). A cancellation, or any failure after the
  load's signal aborted, stays silent; any other error is surfaced **exactly once per failed load**
  with the existing `notifyUnlessCancelled(t("Common.Error"), error)`
  (`src/components/files/notifyError`), as `FileCard.tsx:59-62` does for the same command — once
  even when both call sites share one deduplicated request (`useVirtualPageLoader.ts:42-44` hands
  the same promise to `GameSelector.tsx:88` and `:98` when both ask for `(0, 0)` in a one-row list).
  Rows stay unloaded and are requested again on the next visible-range change, which is today's
  retry path.
* **Unchanged.** `useVirtualPageLoader` (range-keyed dedupe, one merge per load, generation guard
  against stale merges) and `FileCard` (a single-game request always receives its one game, or `[]`
  for an empty file).
* **Verification** (`GameSelector.test.tsx`, each would go red if the behaviour were removed):
  1. a short first page leads to a second call `(start + n, end)` and all rows merge at the right
     indices;
  2. each page is reduced to rows before the next read: with page one's header parse held pending,
     the second `readGames` call has not been issued;
  3. every `readGames` call of one load, continuation calls included, receives the load's signal;
  4. an abort between pages stops further calls;
  5. an empty page stops further calls, and an empty load leaves `games` identity unchanged (the
     `readGames` call count stays stable after settling);
  6. a rejected later page merges nothing, issues no further call, is surfaced once through the
     notification, and leaves no unhandled rejection; a cancellation rejection is not surfaced;
  7. in a one-row list where both call sites share the deduplicated `(0, 0)` request, one failure
     produces exactly one notification;
  8. a pending load whose signal is aborted and whose `readGames` then rejects with an ordinary
     (non-cancellation) error produces no notification, no merge and no unhandled rejection
     (reachable: `src/platform/tauri.ts:285-287` rethrows a command failure without checking the
     signal, and `useVirtualPageLoader.ts:57` suppresses only the cancellation category).

## Decisions and trade-offs

### Decided autonomously

1. **Page contract.** Question: byte budget with continuation, or a streaming reader? Chosen:
   byte-budgeted non-empty prefix page, continued by the renderer. Rejected: a Tauri channel or
   event stream (a new IPC event surface with listener lifetimes, for a ≤1 000-row virtual list);
   refusing an over-budget page with an error (files of large games become unbrowsable); an
   explicit `next`/`truncated` response field (a bindings change carrying what the result length
   already says). Reason: the cached index knows every game's size before reading, so the bound is
   enforced before allocation, with no new surface.
2. **Budget value.** Chosen: `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). Rejected: a smaller budget
   such as 1 MiB (more round trips for ordinary pages while one `read_game` may already carry
   10 MiB). Reason: keeps the existing largest single IPC response as the only ceiling.
3. **Continuation owner.** Chosen: `GameSelector.loadPage`, the sole multi-row consumer. Rejected:
   `useVirtualPageLoader` (generic range-keyed dedupe; the short-page rule is a `readGames`
   property) and the platform facade (would hide a multi-call loop behind one command name).
4. **ImportModal clause.** Already resolved by `fefd7a5f` / `d-20260927-01`; no change here.

### Considered and not taken

* A header-only listing command: `GameSelector` reads whole games only for their headers. It would
  move header parsing native and change the identity/stamp path, and still needs a byte budget —
  outside this MANDATE.

## Approach

### A. Native page byte budget

Rests on MANDATE: "caps the number of games … but not their total size … materialised into one
`Vec<String>` in a single call".

* **Contract.** `read_games(file, start, end)` returns a *non-empty prefix* of the requested
  inclusive range: games in order, starting at `start`, while the running sum of their scanned
  byte lengths (`range.end - range.start`) stays ≤ the page byte budget. The first requested game
  is always selected, so every non-empty request makes progress and a game over `MAX_PGN_BYTES`
  still fails with today's `ResourceLimit` from `read_range_bytes` (`pgn.rs:696-697`) instead of
  silently yielding an empty page. A game is included when the sum *equals* the budget.
* **Budget.** New `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). With the first-game rule, no page
  exceeds 10 MiB — the same ceiling one `read_game` call already has.
* **Where.** The selection runs inside `read_games_core`'s `select` closure, on the cached index,
  before any read. Games after the prefix are never read.
* **Unchanged.** The whole requested range is still bounds-checked first (`InvalidInput`), the
  1 000-game count cap stays (`d-20260905-20` keeps page protections), the empty-file `(0, 0) → []`
  case stays, an inverted cached range is still `Conflict` (never a zero-length game), cancellation
  and the per-game `stamp`/`revision` (`d-20260924-02`) are unchanged. The command signature and
  `src/bindings/generated.ts` do not change; `pnpm bindings:check` stays green.
* **Doc.** `read_games_core` carries a doc comment stating the short-page contract.
* **Verification** (Rust unit tests in `pgn.rs`, through `read_games_core` with the production
  budget of `PgnRepository::default()`, never a test-only limit). Tests 1–3 go red if the budget is
  removed or raised; tests 4–5 guard preserved behaviour:
  1. a request whose games exceed the budget returns exactly the fitting prefix, with the same
     `pgn`/`stamp`/`revision` a full read gives for those games;
  2. games after the prefix are never read — the test goes red for an implementation that reads the
     whole requested range and truncates afterwards;
  3. a game that lands the sum exactly on the budget is included and the next game is excluded;
  4. a first game over `MAX_PGN_BYTES` still yields `ResourceLimit`, not an empty page;
  5. an out-of-bounds `end` is still `InvalidInput` even when the prefix alone would be in bounds.

### B. Renderer continuation over short pages

Rests on MANDATE: "a byte budget per call with continuation".

* **Contract.** `GameSelector`'s `loadPage(start, end)` requests `readGames(path, next, end)` with
  `next = start + rows received so far`, converting each page to rows (headers parsed, PGN text
  dropped) before requesting the next, until `next > end`. Rows keep the index `next + i`.
* **Termination.** A page with zero games ends the continuation and returns the rows collected so
  far. The merge callback returns `previous` unchanged when it receives no entries, so an empty
  result cannot change `games` identity and re-trigger the visible-range effect.
* **Cancellation.** The abort signal is passed to every call; no further page is requested after
  the signal aborts.
* **Failure.** A rejected page rejects the whole load: the continuation stops and no rows of that
  load are merged. Merging the earlier pages' rows would change `games`, and the effect
  (`GameSelector.tsx:84-98`) would at once re-request the same visible range, so a persistent
  failure would loop. No rejection may reach a `loadMoreRows` call site unhandled (today an
  ordinary failure becomes an unhandled rejection: `useVirtualPageLoader.ts:55-58` rethrows it,
  `GameSelector.tsx:88,98` drop the promise with `void`). A cancellation, or any failure after the
  load's signal aborted, stays silent; any other error is surfaced **exactly once per failed load**
  with the existing `notifyUnlessCancelled(t("Common.Error"), error)`
  (`src/components/files/notifyError`), as `FileCard.tsx:59-62` does for the same command — once
  even when both call sites share one deduplicated request (`useVirtualPageLoader.ts:42-44` hands
  the same promise to `GameSelector.tsx:88` and `:98` when both ask for `(0, 0)` in a one-row list).
  Rows stay unloaded and are requested again on the next visible-range change, which is today's
  retry path.
* **Unchanged.** `useVirtualPageLoader` (range-keyed dedupe, one merge per load, generation guard
  against stale merges) and `FileCard` (a single-game request always receives its one game, or `[]`
  for an empty file).
* **Verification** (`GameSelector.test.tsx`, each would go red if the behaviour were removed):
  1. a short first page leads to a second call `(start + n, end)` and all rows merge at the right
     indices;
  2. each page is reduced to rows before the next read: with page one's header parse held pending,
     the second `readGames` call has not been issued;
  3. every `readGames` call of one load, continuation calls included, receives the load's signal;
  4. an abort between pages stops further calls;
  5. an empty page stops further calls, and an empty load leaves `games` identity unchanged (the
     `readGames` call count stays stable after settling);
  6. a rejected later page merges nothing, issues no further call, is surfaced once through the
     notification, and leaves no unhandled rejection; a cancellation rejection is not surfaced;
  7. in a one-row list where both call sites share the deduplicated `(0, 0)` request, one failure
     produces exactly one notification;
  8. a pending load whose signal is aborted and whose `readGames` then rejects with an ordinary
     (non-cancellation) error produces no notification, no merge and no unhandled rejection
     (reachable: `src/platform/tauri.ts:285-287` rethrows a command failure without checking the
     signal, and `useVirtualPageLoader.ts:57` suppresses only the cancellation category).

## Decisions and trade-offs

### Decided autonomously

1. **Page contract.** Question: byte budget with continuation, or a streaming reader? Chosen:
   byte-budgeted non-empty prefix page, continued by the renderer. Rejected: a Tauri channel or
   event stream (a new IPC event surface with listener lifetimes, for a ≤1 000-row virtual list);
   refusing an over-budget page with an error (files of large games become unbrowsable); an
   explicit `next`/`truncated` response field (a bindings change carrying what the result length
   already says). Reason: the cached index knows every game's size before reading, so the bound is
   enforced before allocation, with no new surface.
2. **Budget value.** Chosen: `MAX_PAGE_BYTES = MAX_PGN_BYTES` (10 MiB). Rejected: a smaller budget
   such as 1 MiB (more round trips for ordinary pages while one `read_game` may already carry
   10 MiB). Reason: keeps the existing largest single IPC response as the only ceiling.
3. **Continuation owner.** Chosen: `GameSelector.loadPage`, the sole multi-row consumer. Rejected:
   `useVirtualPageLoader` (generic range-keyed dedupe; the short-page rule is a `readGames`
   property) and the platform facade (would hide a multi-call loop behind one command name).
4. **ImportModal clause.** Already resolved by `fefd7a5f` / `d-20260927-01`; no change here.

### Considered and not taken

* A header-only listing command: `GameSelector` reads whole games only for their headers. It would
  move header parsing native and change the identity/stamp path, and still needs a byte budget —
  outside this MANDATE.

## Risks / open questions

* The e2e mock returns one game for every range; with `numGames = 1` the continuation issues one
