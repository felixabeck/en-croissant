# Plan: supervisor-owned termination of an engine whose publication is aborted (f-20260914-34)

## Goal

An engine child that has been spawned but not yet published into `EngineSupervisor.actors` is
owned by the supervisor from the moment it exists until it is either published or reaped. Tab
shutdown, engine retirement and application exit terminate and await such children exactly as they
already do registered ones, and their termination failures reach the same aggregate result. The
`Drop` backstop of a dropped publisher stops being the sole owner of the child.

## MANDATE

Verbatim, `tasks/findings.md` entry `f-20260914-34` (the only member of the cluster):

> ### A spawned engine whose publication is aborted is terminated by an untracked task that shutdown does not await
>
> * **ID:** f-20260914-34 · **Status:** open · **Area:** engine-uci · **Root:** - · **Entry:** build · **Blocked:** none
> * **Where:** `src-tauri/src/engine/process.rs` `impl Drop for PendingActorGuard` (around line 1351): when the guard still holds an actor, it moves it into `tokio::spawn(async move { actor.terminate().await … })` and returns. Reached when `spawn_registered` has spawned the child but publication is aborted before registration (admission cancelled by tab close, retirement or shutdown, or an initialization error).

## Threat model and non-goals

Frozen in round 1.

* **Accidental, not adversarial.** The inputs are ordinary concurrency between engine launches
  and the three supervisor drains (tab close → `terminate_tab`, engine removal or executable
  retirement → `retire_matching`, application exit → `terminate_all`), and the cancellation of
  a caller future while it is inside publication. Nothing here is attacker-controlled.
* **Dropped publisher futures are a real exit path even though no production caller drops one
  today.** The locate probe found every production chain (`analyze_game` native worker,

* **Live inline rejection racing a drain is the production-reachable half.** A publisher that
  is still running when a drain crosses the barrier rejects inline (`reject_actor`), but no drain
  waits for it today, so application exit can reach `process::exit` while that rejection is
  still terminating the child.
* **Environments:** Linux, macOS and Windows alike. The change contains no `cfg(target_os)`
  code; its tests use the in-process fake UCI I/O, so they run unchanged on every runner.
* **Non-goal — launches that have not spawned yet.** A launch that passed its admission check
  before the seal and spawns only after `terminate_all` has finished draining is not caught by
  this plan's set: nothing exists to own until the spawn returns. That window (the

## Approach

### O1 — Every spawned, unpublished actor is in a supervisor-owned pending set

MANDATE: "no owner, no join handle and no registration the shutdown path walks".

* The supervisor holds a pending-actor set keyed by the admission generation (P10). Each entry
  carries the actor, its `EngineKey`, generation, application engine id and executable `PathRef`:
  the identity the three drain predicates match on.
* An actor enters the set as soon as it is spawned for an admitted publication, before the first
  await of publication: in `initialize_admitted_actor` (all `spawn_registered` callers) and in the
  fresh-actor branch of `start_interactive_search`. The guard that today wraps that span becomes
  the handle of the entry.
* The entry leaves the set in exactly one of these ways:
  1. **Publication commit** removes it inside the same `admission_coordination` critical section
     that inserts into `actors` (P4), so at no coordination-observed instant is a live actor in
     neither set or in both.
  2. **Inline rejection** removes it after `reject_actor`'s termination has completed; the error
     still returns to the caller exactly as today.
  3. **A drain** (O2) removes it after its own termination of that actor has completed.
  4. **The dropped-publisher cleanup** (O3) removes it after its termination has completed.
  Removal is by generation and idempotent: whichever owner completes first removes it, the others
  find it gone.
* **Retention bound:** the set holds at most one entry per spawned actor whose publication is
  unresolved; every exit path above removes it, so it cannot grow across a session.
* The test-only `replace_handle` tracks its actor only once `admit` has returned a generation.
  A drop while it waits inside `admit` releases the last actor handle, and the actor loop
  terminates its runtime itself (P8), which is what
  `dropped_replacement_waiting_for_registration_reaps_actor_and_admission` already observes. With
  that, an entry always has a generation and the "not-yet-assigned" log variant disappears.

### O2 — The three drains terminate and await matching pending actors

MANDATE: "Tab shutdown and application exit terminate only registered actors"; Open question
"(a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing
bounded deadlines)".

* `terminate_all`, `terminate_tab` and `retire_matching` keep their existing barrier (seal where
  applicable, cancel matching admissions under registration + coordination). After it, each drains
  **both** matching registered actors (unchanged `terminate_exact` route) and matching pending
  entries, concurrently, and loops until neither set holds a match.
* A pending entry is drained by terminating its actor directly (no lifecycle lease: a live
  publisher may hold that lease while it waits, and the drain must not wait behind it), awaiting
  that termination, then removing the entry. A live publisher's own inline rejection may terminate
  the same actor concurrently; P7 makes the two converge on one cleanup.
* Admission cancellation before the scan guarantees that a pending entry a drain matches can no
  longer be published: publication commits only with the current, uncancelled admission (P4), and
  each drain's pending predicate is the same predicate it uses to cancel admissions (tab for
  `terminate_tab`, engine id / executable for `retire_matching`, everything for `terminate_all`).
* **Failure semantics:** a pending actor's termination failure enters the drain's existing
  `aggregate_shutdown_failures` with its key and generation (logged, first error returned). It no
  longer surfaces only as a detached-task log line when a drain is the one that terminated it.
* **Deadlines:** no new timeout. Each termination is bounded by the existing `EngineDeadlines`
  (`quit`, `kill_reap`, stderr reap); application exit stays inside the existing
  `SHUTDOWN_BUDGET` because `terminate_all` is already awaited there (P6).
* The three drain loops are today three copies of "cancel matching admissions, then loop
  terminate-matching until none remain". They are routed through one shared drain that takes the
  predicate, so the pending half is written once (universal rule 11).
* Exact single-generation paths (`terminate_exact`, `release_generation`, `kill_engine`) are not
  changed; a reserved-but-unpublished generation there is open `f-20260914-23`.

### O3 — A dropped publisher starts its cleanup, but no longer owns it alone

MANDATE: "if the runtime is torn down before the detached task runs, the child is neither
terminated nor reaped, and its termination error surfaces only as a log line"; Open question "how
is the `Drop` backstop then reduced".

* Dropping an armed guard leaves its entry in the pending set and starts the termination in a
  spawned task, so a long-running session reaps the child promptly without waiting for a drain.
  The task removes the entry when its termination completes and logs a failure with key and
  generation (the existing `log_pending_actor_cleanup_error` shape).
* Ownership is the set, not the task: if any drain runs before that task has finished — or if the
  task never runs — the drain terminates and awaits the actor itself (O2). The spawned task is an
  accelerator whose loss cannot leak the child into an exit.
* Answer to the finding's second question: the `Drop` backstop is **not** reduced to a logged
  invariant violation. `Drop` is synchronous and fires only when no caller remains to await
  anything (P2), so "inline by the caller" cannot cover this path; reducing it to a log would leave
  the child running for the rest of the session, against `d-20260927-07`.
* `RegistrationGuard`'s `Drop` (also a spawned cleanup) is unchanged: its actor is already
  registered in `actors`, every drain reaches it there, and its `terminate_exact` runs under the
  per-key lifecycle lease that the drain's own `terminate_exact` also takes, so drains already await
  it. The only code the two `Drop`s share is "spawn and log", which is coincidental, not the same
  domain concept (rule 11's exception).

## Decisions and trade-offs

* Option (a) over (b): settled in D1. The trade-off is one more supervisor map against making
  exit and tab close wait for every child the process has spawned.
* Pending drain bypasses the lifecycle lease: a live publisher can hold that lease while it waits
  on a previous actor's stop or on the registration lock; taking it would make the drain wait for
  the very publisher it is cancelling.
* The dropped-publisher task is kept rather than removed: without it a dropped publication would
  keep its engine alive until the next drain, which may be application exit.

## Threat model and non-goals

Frozen in round 1.

* **Accidental, not adversarial.** The inputs are ordinary concurrency between engine launches
  and the three supervisor drains (tab close → `terminate_tab`, engine removal or executable
  retirement → `retire_matching`, application exit → `terminate_all`), and the cancellation of
  a caller future while it is inside publication. Nothing here is attacker-controlled.
* **Dropped publisher futures are a real exit path even though no production caller drops one
  today.** The locate probe found every production chain (`analyze_game` native worker,
  `get_engine_config`, `start_game` white and black, `get_best_moves` →

  is still running when a drain crosses the barrier rejects inline (`reject_actor`), but no drain
  waits for it today, so application exit can reach `process::exit` while that rejection is

* **Environments:** Linux, macOS and Windows alike. The change contains no `cfg(target_os)`
  code; its tests use the in-process fake UCI I/O, so they run unchanged on every runner.
* **Non-goal — launches that have not spawned yet.** A launch that passed its admission check
  before the seal and spawns only after `terminate_all` has finished draining is not caught by
  this plan's set: nothing exists to own until the spawn returns. That window (the

  `tasks/findings-inbox/20261006-191213-2962197-1791306733058862538-6.md`, "An engine spawned after
  `terminate_all` finished draining is reaped by nobody before the process exits"), because closing
  it needs a reserve-before-spawn or live-lease wait that is its own design question.

## Approach

### O1 — Every spawned, unpublished actor is in a supervisor-owned pending set

MANDATE: "no owner, no join handle and no registration the shutdown path walks".

* The supervisor holds a pending-actor set keyed by the admission generation (P10). Each entry
  carries the actor, its `EngineKey`, generation, application engine id and executable `PathRef`:
  the identity the three drain predicates match on.
* An actor enters the set as soon as it is spawned for an admitted publication, before the first
  await of publication: in `initialize_admitted_actor` (all `spawn_registered` callers) and in the
  fresh-actor branch of `start_interactive_search`. The guard that today wraps that span becomes
  the handle of the entry.
* The entry leaves the set in exactly one of these ways:
  1. **Publication commit** removes it inside the same `admission_coordination` critical section
     that inserts into `actors` (P4), so at no coordination-observed instant is a live actor in
     neither set or in both.
  2. **Inline rejection** removes it after the entry's shared termination (below) has completed;
     the rejection error, combined with that termination's result, still returns to the caller as
     today.
  3. **A drain** (O2) removes it after the entry's shared termination has completed.
  4. **The dropped-publisher cleanup** (O3) removes it after the entry's shared termination has
     completed.
  Removal is by generation and idempotent: whichever owner completes first removes it, the others
  find it gone.
* **One termination per entry, one result for every owner.** Whichever owner first needs the
  actor terminated (inline rejection, a drain, or the dropped-publisher cleanup) starts the
  entry's termination; every other owner awaits that same termination instead of calling
  `EngineActor::terminate` again, and receives its terminal result. A failed termination is
  therefore an `Err` for **every** awaiting owner — never the `Ok` a second concurrent
  `EngineActor::terminate` caller gets today. The owner that ran the termination receives the
  original error; the others receive an error with the same `category()` whose renderer-facing
  text is the existing safe label (no raw diagnostic crosses IPC, `d-20260927-09`; the actor's own
  keyed log carries the OS cause, `d-20260927-08`). No new `ErrorCategory`, no change to the
  serialized error shape. If the owner that started the termination is itself dropped before it
  completes, a later owner takes the termination over rather than waiting forever. This sharing is
  local to pending entries; registered actors keep today's termination path (`f-20260927-01`,
  `f-20261001-14`).
* **Retention bound:** the set holds at most one entry per spawned actor whose publication is
  unresolved; every exit path above removes it, so it cannot grow across a session.
* The test-only `replace_handle` tracks its actor only once `admit` has returned a generation.
  A drop while it waits inside `admit` releases the last actor handle, and the actor loop
  terminates its runtime itself (P8), which is what
  `dropped_replacement_waiting_for_registration_reaps_actor_and_admission` already observes. With
  that, an entry always has a generation and the "not-yet-assigned" log variant disappears.

### O2 — The three drains terminate and await matching pending actors

MANDATE: "Tab shutdown and application exit terminate only registered actors"; Open question
"(a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing
bounded deadlines)".

* `terminate_all`, `terminate_tab` and `retire_matching` keep their existing barrier (seal where
  applicable, cancel matching admissions under registration + coordination). After it, each drains
  **both** matching registered actors (unchanged `terminate_exact` route) and matching pending
  entries, concurrently, and loops until neither set holds a match.
* A pending entry is drained through its shared termination (O1) — started by the drain if no
  other owner has started it, otherwise awaited — and removed once that termination has completed.
  No lifecycle lease is taken: a live publisher may hold that lease while it waits, and the drain
  must not wait behind it. A live publisher's inline rejection and a dropped publisher's cleanup
  await the same termination, so the drain never returns before a rejection or cleanup already in
  progress has reaped the child.
* Admission cancellation before the scan guarantees that a pending entry a drain matches can no
  longer be published: publication commits only with the current, uncancelled admission (P4), and
  each drain's pending predicate is the same predicate it uses to cancel admissions (tab for
  `terminate_tab`, engine id / executable for `retire_matching`, everything for `terminate_all`).
* **Failure semantics:** a pending actor's termination failure enters the drain's existing
  `aggregate_shutdown_failures` with its key and generation (logged, first error returned),
  whichever owner started that termination. It no longer surfaces only as a detached-task log
  line.
* **Deadlines:** no new timeout. Each termination is bounded by the existing `EngineDeadlines`
  (`quit`, `kill_reap`, stderr reap); application exit stays inside the existing
  `SHUTDOWN_BUDGET` because `terminate_all` is already awaited there (P6).
* The three drain loops are today three copies of "cancel matching admissions, then loop
  terminate-matching until none remain". They are routed through one shared drain that takes the
  predicate, so the pending half is written once (universal rule 11).
* Exact single-generation paths (`terminate_exact`, `release_generation`, `kill_engine`) are not
  changed; a reserved-but-unpublished generation there is open `f-20260914-23`.

### O3 — A dropped publisher starts its cleanup, but no longer owns it alone

MANDATE: "if the runtime is torn down before the detached task runs, the child is neither
terminated nor reaped, and its termination error surfaces only as a log line"; Open question "how
is the `Drop` backstop then reduced".

* Dropping an armed guard leaves its entry in the pending set and starts the entry's shared
  termination (O1) in a spawned task, so a long-running session reaps the child promptly without
  waiting for a drain. The task removes the entry when that termination completes and logs a
  failure with key and generation (the existing `log_pending_actor_cleanup_error` shape).
* Ownership is the set, not the task: if any drain runs before that task has finished — or if the
  task never runs — the drain terminates and awaits the actor itself (O2). The spawned task is an
  accelerator whose loss cannot leak the child into an exit.
* Answer to the finding's second question: the `Drop` backstop is **not** reduced to a logged
  invariant violation. `Drop` is synchronous and fires only when no caller remains to await
  anything (P2), so "inline by the caller" cannot cover this path; reducing it to a log would leave
  the child running for the rest of the session, against `d-20260927-07`.
* `RegistrationGuard`'s `Drop` (also a spawned cleanup) is unchanged: its actor is already
  registered in `actors`, every drain reaches it there, and its `terminate_exact` runs under the
  per-key lifecycle lease that the drain's own `terminate_exact` also takes, so drains already await
  it. The only code the two `Drop`s share is "spawn and log", which is coincidental, not the same
  domain concept (rule 11's exception).

### O4 — Verification

MANDATE: "Not reproduced by a test."

Each case uses the in-process fake UCI I/O (`actor_with`, `actor_with_terminate_delay`,
`TerminateErrorIo` in `process.rs` tests), runs on all three platforms, and must go red when O1–O3
are reverted:

* **V1 dropped publisher, then exit.** A publisher is blocked inside publication (for example
  behind a held `registration` lock or lifecycle lease) with an actor whose termination is
  delayed; the publisher task is aborted; `terminate_all` then returns only after that actor's
  termination has completed (termination counter is 1 at the moment `terminate_all` returns), the
  pending set is empty, and the actor is terminated exactly once overall. Today `terminate_all`
  returns immediately with the counter still 0.
* **V2 live publisher, then exit.** A publisher blocked before its commit (it is not aborted);
  `terminate_all` returns `Ok` after terminating its actor while the publisher is still blocked;
  once unblocked, the publisher returns an error, the actor is not published, and it was
  terminated exactly once.
* **V2b inline rejection already in progress, then exit.** A publisher whose inline rejection is
  terminating an actor with a delayed termination when `terminate_all` starts; `terminate_all`
  returns only after that termination has completed (termination counter is 1 at the moment it
  returns), and the actor is terminated exactly once. Removing the pending entry before the
  rejection's termination completes must make this case fail.
* **V3 tab scope.** Two blocked publishers on tabs A and B; `terminate_tab(A)` returns after A's
  pending actor is terminated; B's actor is untouched and B still publishes once unblocked.
* **V4 retirement scope.** A blocked publisher for engine id E and another for engine id F;
  `retire_engine(E)` drains E's pending actor and leaves F's.
* **V5 failure reaches the aggregate, whoever started the termination.** A pending actor whose
  termination fails makes `terminate_all` return `Err`, and the shutdown failure log names its key
  and generation — both when the drain starts that termination and when a dropped publisher's
  cleanup (or an inline rejection) started it first and the drain only awaits it. In the second
  case the starting owner also sees the failure (cleanup log, or the rejection's combined error).
* **V6 set retention.** After a successful publication, an inline rejection and a completed
  dropped-publisher cleanup, the pending set is empty.
* **V7 existing tests** keep their assertions: the guard-drop, registration-guard, shutdown,
  retirement and game-construction tests listed by probe 2 (`process.rs`, `game.rs`, `main.rs`).
  `pending_actor_cleanup_log_carries_key_and_generation` loses its unassigned-generation half
  (O1) and keeps the assigned half.

## Decided autonomously

`full auto`; recorded here for review, and by the adopting session through
`./scripts/findings.py record-decision`.

* **D1 — Who owns the termination of an actor whose publication is aborted?** Chosen: a
  supervisor-owned pending-actor set that `terminate_all`, `terminate_tab` and `retire_matching`
  drain and await (the finding's option (a)). Rejected: termination inline by the caller with the
  `Drop` reduced to a logged invariant violation (option (b)) — every rejection is already inline
  (P2), and the guard fires only on a dropped future, where no caller remains to await; logging
  instead would leak the child, against `d-20260927-07`. Rejected: a `tokio_util::task::TaskTracker`
  of termination tasks — it cannot be filtered by tab or engine for `terminate_tab` and retirement,
  and it would not cover a live publisher's inline rejection racing exit. Reversal path: remove
  the set and the drains' pending half; V1–V5 go red first.
* **D2 — Is `RegistrationGuard`'s spawned cleanup merged with the pending guard?** Chosen: no.
  Its actor is registered, drains reach it in `actors`, and drains already await it through the
  per-key lifecycle lease. Rejected: one generic "spawn cleanup from Drop" helper — the two share
  only the spawn-and-log call, not an ownership model. Reversal path: route both through one
  helper if a third guard of either shape appears.
* **D3 — Do exact single-generation terminations drain the pending set?** Chosen: no;
  `f-20260914-23` owns a reserved-but-unpublished generation on `kill_engine`. Rejected: widening
  `terminate_exact` here, which would change that finding's mandate without its review.
* **D4 — How do a drain, an inline rejection and a dropped publisher's cleanup share one pending
  actor's termination?** Chosen: one termination per pending entry, started by the first owner and
  awaited by the others, whose terminal result every owner receives (O1). Rejected: each owner
  calling `EngineActor::terminate` independently — a second concurrent caller receives
  `EngineDisconnected`, which `terminate` maps to `Ok` once the task is reaped, so a drain racing a
  failed cleanup would report success and the failure would stay log-only (round-1 issue I1,
  verified at `process.rs:3459-3466` and `:3815-3825`). Rejected: extending result sharing to
  registered actors — that is `f-20260927-01` / `f-20261001-14`. Reversal path: remove the shared
  termination; V5's await-case goes red first.

## Decisions and trade-offs

* Option (a) over (b): settled in D1. The trade-off is one more supervisor map against making
  exit and tab close wait for every child the process has spawned.
* Pending drain bypasses the lifecycle lease: a live publisher can hold that lease while it waits
  on a previous actor's stop or on the registration lock; taking it would make the drain wait for
  the very publisher it is cancelling.
* The dropped-publisher task is kept rather than removed: without it a dropped publication would
  keep its engine alive until the next drain, which may be application exit.

## Risks / open questions

* Registered actors keep today's termination path, where the losing caller of a concurrent
  termination reports `Ok` while the winner may have failed (P7); that is `f-20260927-01` /
  `f-20261001-14`. Pending entries no longer have this gap (O1).
* The spawn-after-final-drain window (P9) remains, filed separately (see Threat model).

### plan-r3.md

# Plan: supervisor-owned termination of an engine whose publication is aborted (f-20260914-34)

## Goal

An engine child that has been spawned but not yet published into `EngineSupervisor.actors` is
owned by the supervisor from the moment it exists until it is either published or reaped. Tab
shutdown, engine retirement and application exit terminate and await such children exactly as they
already do registered ones, and their termination failures reach the same aggregate result. The
`Drop` backstop of a dropped publisher stops being the sole owner of the child.

## MANDATE

Verbatim, `tasks/findings.md` entry `f-20260914-34` (the only member of the cluster):

> ### A spawned engine whose publication is aborted is terminated by an untracked task that shutdown does not await
>
> * **ID:** f-20260914-34 · **Status:** open · **Area:** engine-uci · **Root:** - · **Entry:** build · **Blocked:** none
> * **Where:** `src-tauri/src/engine/process.rs` `impl Drop for PendingActorGuard` (around line 1351): when the guard still holds an actor, it moves it into `tokio::spawn(async move { actor.terminate().await … })` and returns. Reached when `spawn_registered` has spawned the child but publication is aborted before registration (admission cancelled by tab close, retirement or shutdown, or an initialization error).
> * **Defect:** the termination and reap of that child run in a detached task with no owner, no join handle and no registration the shutdown path walks. Tab shutdown and application exit terminate only registered actors; if the runtime is torn down before the detached task runs, the child is neither terminated nor reaped, and its termination error surfaces only as a log line. This contradicts `.claude/rules/async-resource-invariants.md` ("Leave a spawned process … whose removal depends on the happy path" is a DO NOT) and the engine-lifecycle rule that a canceled late actor is reaped.
> * **Why it matters:** engine children outliving the application is the incident class of issue #723 (`e5422566`) and `f-20260830-51`; this is the remaining unowned path. The macOS engine-launch plan (`tasks/plans/2026-09-14-macos-engine-launch-and-removed-dir.md`, round 4, R4-04) relies on this reap for its cancellation guarantee.
> * **Open question:** should aborted-publication termination be owned by the supervisor (a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing bounded deadlines), or be performed inline by the caller of `spawn_registered` on its error path before returning, and how is the `Drop` backstop then reduced to a logged invariant violation?
> * **Related:** `f-20260830-51` (app exit terminates nothing deterministically — handled), `f-20260830-53` (detached stderr reader — handled), `f-20260914-31`.
> * **Found by:** Codex `review-engine-protocol` plan lens (round 4, confidence 91) during the macOS engine-launch build run, 2026-09-14; source verified by the orchestrator. Not reproduced by a test.

## Threat model and non-goals

Frozen in round 1.

* **Accidental, not adversarial.** The inputs are ordinary concurrency between engine launches
  and the three supervisor drains (tab close → `terminate_tab`, engine removal or executable
  retirement → `retire_matching`, application exit → `terminate_all`), and the cancellation of
  a caller future while it is inside publication. Nothing here is attacker-controlled.
* **Dropped publisher futures are a real exit path even though no production caller drops one
  today.** The locate probe found every production chain (`analyze_game` native worker,
  `get_engine_config`, `start_game` white and black, `get_best_moves` →
  `start_interactive_search`) awaiting publication directly, with no select, timeout or abort
  around it. `d-20260927-07` settled the same question for game construction: the cancellation
  path is implemented anyway, proven by deterministic drop tests, because the next cancellation
  wrapper would otherwise turn the latent gap into a leak.
* **Live inline rejection racing a drain is the production-reachable half.** A publisher that
  is still running when a drain crosses the barrier rejects inline (`reject_actor`), but no drain
  waits for it today, so application exit can reach `process::exit` while that rejection is
  still terminating the child.
* **Environments:** Linux, macOS and Windows alike. The change contains no `cfg(target_os)`
  code; its tests use the in-process fake UCI I/O, so they run unchanged on every runner.
* **Non-goal — launches that have not spawned yet.** A launch that passed its admission check
  before the seal and spawns only after `terminate_all` has finished draining is not caught by
  this plan's set: nothing exists to own until the spawn returns. That window (the
  `resolve_launch` hand-off in `start_interactive_search`) is filed as its own finding through the
  planner inbox (published entry
  `tasks/findings-inbox/20261006-191213-2962197-1791306733058862538-6.md`, "An engine spawned after
  `terminate_all` finished draining is reaped by nobody before the process exits"), because closing
  it needs a reserve-before-spawn or live-lease wait that is its own design question.

## Approach

### O1 — Every spawned, unpublished actor is in a supervisor-owned pending set

MANDATE: "no owner, no join handle and no registration the shutdown path walks".

* The supervisor holds a pending-actor set keyed by the admission generation (P10). Each entry
  carries the actor, its `EngineKey`, generation, application engine id and executable `PathRef`:
  the identity the three drain predicates match on.
* An actor enters the set as soon as it is spawned for an admitted publication, before the first
  await of publication: in `initialize_admitted_actor` (all `spawn_registered` callers) and in the
  fresh-actor branch of `start_interactive_search`. The guard that today wraps that span becomes
  the handle of the entry.
* The entry leaves the set in exactly one of these ways:
  1. **Publication commit** removes it inside the same `admission_coordination` critical section
     that inserts into `actors` (P4), so at no coordination-observed instant is a live actor in
     neither set or in both.
  2. **The entry's termination task** (below) removes it once the child's termination has
     completed, whichever owner started that task: an inline rejection, a drain (O2) or a dropped
     publisher (O3). The rejection error, combined with that termination's result, still returns
     to a live publisher as today.
  Removal is by generation and idempotent.
* **One entry-owned termination, one result for every owner.** The first owner that needs the
  actor terminated (inline rejection, a drain, or a dropped publisher) starts the entry's
  termination as a task that belongs to the entry, not to that owner; later owners attach to the
  same task instead of calling `EngineActor::terminate` again. Dropping or cancelling any owner —
  including the one that started it — never cancels the task, so the termination always runs to
  completion and no owner has to take it over. The task calls `EngineActor::terminate` exactly
  once, logs a failure itself with key and generation (the reporter no owner cancellation can
  bypass, as `d-20260927-08` does for the actor), records the terminal result, then removes the
  entry. Every owner awaiting it receives that result: a failed termination is an `Err` for
  **every** owner — never the `Ok` a second concurrent `EngineActor::terminate` caller gets today.
  Each owner's error carries the original's `category()` and its local `diagnostic()` text; its
  renderer-facing form is the category's existing safe label (no raw diagnostic crosses IPC,
  `d-20260927-09`). `ErrorCategory` and every `specta::Type` stay unchanged. This sharing is local
  to pending entries; registered actors keep today's termination path (`f-20260927-01`,
  `f-20261001-14`).
* **Retention bound:** the set holds at most one entry per spawned actor whose publication is
  unresolved; every exit path above removes it, so it cannot grow across a session.
* The test-only `replace_handle` tracks its actor only once `admit` has returned a generation.
  A drop while it waits inside `admit` releases the last actor handle, and the actor loop
  terminates its runtime itself (P8), which is what
  `dropped_replacement_waiting_for_registration_reaps_actor_and_admission` already observes. With
  that, an entry always has a generation and the "not-yet-assigned" log variant disappears.

### O2 — The three drains terminate and await matching pending actors

MANDATE: "Tab shutdown and application exit terminate only registered actors"; Open question
"(a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing
bounded deadlines)".

* `terminate_all`, `terminate_tab` and `retire_matching` keep their existing barrier (seal where
  applicable, cancel matching admissions under registration + coordination). After it, each drains
  **both** matching registered actors (unchanged `terminate_exact` route) and matching pending
  entries, concurrently, and loops until neither set holds a match.
* A pending entry is drained through its entry-owned termination (O1) — started by the drain if
  no other owner has started it, otherwise attached to — and the drain awaits that task's result.
  No lifecycle lease is taken: a live publisher may hold that lease while it waits, and the drain
  must not wait behind it. A live publisher's inline rejection and a dropped publisher's cleanup
  await the same termination, so the drain never returns before a rejection or cleanup already in
  progress has reaped the child.
* Admission cancellation before the scan guarantees that a pending entry a drain matches can no
  longer be published: publication commits only with the current, uncancelled admission (P4), and
  each drain's pending predicate is the same predicate it uses to cancel admissions (tab for
  `terminate_tab`, engine id / executable for `retire_matching`, everything for `terminate_all`).
* **Failure semantics:** a pending actor's termination failure enters the drain's existing
  `aggregate_shutdown_failures` with its key and generation (logged, first error returned),
  whichever owner started that termination. It no longer surfaces only as a detached-task log
  line.
* **Deadlines:** no new timeout. Each termination is bounded by the existing `EngineDeadlines`
  (`quit`, `kill_reap`, stderr reap); application exit stays inside the existing
  `SHUTDOWN_BUDGET` because `terminate_all` is already awaited there (P6).
* The three drain loops are today three copies of "cancel matching admissions, then loop
  terminate-matching until none remain". They are routed through one shared drain that takes the
  predicate, so the pending half is written once (universal rule 11).
* Exact single-generation paths (`terminate_exact`, `release_generation`, `kill_engine`) are not
  changed; a reserved-but-unpublished generation there is open `f-20260914-23`.

### O3 — A dropped publisher starts its cleanup, but no longer owns it alone

MANDATE: "if the runtime is torn down before the detached task runs, the child is neither
terminated nor reaped, and its termination error surfaces only as a log line"; Open question "how
is the `Drop` backstop then reduced".

* Dropping an armed guard leaves its entry in the pending set and starts the entry-owned
  termination (O1), so a long-running session reaps the child promptly without waiting for a
  drain. That task logs a failure with key and generation (the existing
  `log_pending_actor_cleanup_error` shape) and removes the entry when it completes.
* Ownership is the set, not the dropped owner: a drain that runs before that termination has
  finished attaches to the same entry-owned task and awaits it (O2), and application exit awaits
  `terminate_all` inside `SHUTDOWN_BUDGET` (P6), so the runtime is alive while the task runs. The
  dropped publisher's role is only to start the termination early.
* Answer to the finding's second question: the `Drop` backstop is **not** reduced to a logged
  invariant violation. `Drop` is synchronous and fires only when no caller remains to await
  anything (P2), so "inline by the caller" cannot cover this path; reducing it to a log would leave
  the child running for the rest of the session, against `d-20260927-07`.
* `RegistrationGuard`'s `Drop` (also a spawned cleanup) is unchanged: its actor is already
  registered in `actors`, every drain reaches it there, and its `terminate_exact` runs under the
  per-key lifecycle lease that the drain's own `terminate_exact` also takes, so drains already await
  it. The only code the two `Drop`s share is "spawn and log", which is coincidental, not the same
  domain concept (rule 11's exception).

### O4 — Verification

MANDATE: "Not reproduced by a test."

Each case uses the in-process fake UCI I/O (`actor_with`, `actor_with_terminate_delay`,
`TerminateErrorIo` in `process.rs` tests), runs on all three platforms, and must go red when O1–O3
are reverted:

* **V1 dropped publisher, then exit.** A publisher is blocked inside publication (for example
  behind a held `registration` lock or lifecycle lease) with an actor whose termination is
  delayed; the publisher task is aborted; `terminate_all` then returns only after that actor's
  termination has completed (termination counter is 1 at the moment `terminate_all` returns), the
  pending set is empty, and the actor is terminated exactly once overall. Today `terminate_all`
  returns immediately with the counter still 0.
* **V2 live publisher, then exit.** A publisher blocked before its commit (it is not aborted);
  `terminate_all` returns `Ok` after terminating its actor while the publisher is still blocked;
  once unblocked, the publisher returns an error, the actor is not published, and it was
  terminated exactly once.
* **V2b inline rejection already in progress, then exit.** A publisher whose inline rejection is
  terminating an actor with a delayed termination when `terminate_all` starts; `terminate_all`
  returns only after that termination has completed (termination counter is 1 at the moment it
  returns), and the actor is terminated exactly once. Removing the pending entry before the
  rejection's termination completes must make this case fail.
* **V3 tab scope.** Two blocked publishers on tabs A and B; `terminate_tab(A)` returns after A's
  pending actor is terminated; B's actor is untouched and B still publishes once unblocked.
* **V4 retirement scope.** A blocked publisher for engine id E and another for engine id F;
  `retire_engine(E)` drains E's pending actor and leaves F's.
* **V5 failure reaches the aggregate, whoever started the termination.** A pending actor whose
  termination fails makes `terminate_all` return `Err`, and the shutdown failure log names its key
  and generation — both when the drain starts that termination and when a dropped publisher's
  cleanup (or an inline rejection) started it first and the drain only awaits it. In the second
  case the starting owner also sees the failure (cleanup log, or the rejection's combined error).
* **V8 the starting owner is cancelled mid-termination.** A live publisher's inline rejection
  starts the termination of an actor whose termination is delayed and fails; that publisher task
  is aborted while the termination is in progress; a subsequent `terminate_all` completes within a
  bounded time, returns the failure with key and generation, the actor's termination ran exactly
  once, and the pending set is empty. An implementation that ties the termination to the starting
  owner's future (hang, a second `terminate()` that returns `Ok`, or a lost failure) fails it.
* **V6 set retention.** After a successful publication, an inline rejection and a completed
  dropped-publisher cleanup, the pending set is empty.
* **V7 existing tests** keep their assertions: the guard-drop, registration-guard, shutdown,
  retirement and game-construction tests listed by probe 2 (`process.rs`, `game.rs`, `main.rs`).
  `pending_actor_cleanup_log_carries_key_and_generation` loses its unassigned-generation half
  (O1) and keeps the assigned half.

## Decided autonomously

`full auto`; recorded here for review, and by the adopting session through
`./scripts/findings.py record-decision`.

* **D1 — Who owns the termination of an actor whose publication is aborted?** Chosen: a
  supervisor-owned pending-actor set that `terminate_all`, `terminate_tab` and `retire_matching`
  drain and await (the finding's option (a)). Rejected: termination inline by the caller with the
  `Drop` reduced to a logged invariant violation (option (b)) — every rejection is already inline
  (P2), and the guard fires only on a dropped future, where no caller remains to await; logging
  instead would leak the child, against `d-20260927-07`. Rejected: a `tokio_util::task::TaskTracker`
  of termination tasks — it cannot be filtered by tab or engine for `terminate_tab` and retirement,
  and it would not cover a live publisher's inline rejection racing exit. Reversal path: remove
  the set and the drains' pending half; V1–V5 go red first.
* **D2 — Is `RegistrationGuard`'s spawned cleanup merged with the pending guard?** Chosen: no.
  Its actor is registered, drains reach it in `actors`, and drains already await it through the
  per-key lifecycle lease. Rejected: one generic "spawn cleanup from Drop" helper — the two share
  only the spawn-and-log call, not an ownership model. Reversal path: route both through one
  helper if a third guard of either shape appears.
* **D3 — Do exact single-generation terminations drain the pending set?** Chosen: no;
  `f-20260914-23` owns a reserved-but-unpublished generation on `kill_engine`. Rejected: widening
  `terminate_exact` here, which would change that finding's mandate without its review.
* **D4 — How do a drain, an inline rejection and a dropped publisher's cleanup share one pending
  actor's termination?** Chosen: one termination per pending entry, started by the first owner and
  awaited by the others, whose terminal result every owner receives (O1); the termination is an
  entry-owned task, so no owner's cancellation can interrupt it (round-2 issue I3). Rejected: each owner
  calling `EngineActor::terminate` independently — a second concurrent caller receives
  `EngineDisconnected`, which `terminate` maps to `Ok` once the task is reaped, so a drain racing a
  failed cleanup would report success and the failure would stay log-only (round-1 issue I1,
  verified at `process.rs:3459-3466` and `:3815-3825`). Rejected: a termination run inside the
  starting owner's future with takeover by a later owner — once `Terminate` was sent, the failure
  reaches only the original reply and a takeover's second `terminate()` returns `Ok` (round-2 I3,
  `:3824`, `:3461`). Rejected: extending result sharing to
  registered actors — that is `f-20260927-01` / `f-20261001-14`. Reversal path: remove the shared
  termination; V5's await-case goes red first.

## Decisions and trade-offs

* Option (a) over (b): settled in D1. The trade-off is one more supervisor map against making
  exit and tab close wait for every child the process has spawned.
* Pending drain bypasses the lifecycle lease: a live publisher can hold that lease while it waits
  on a previous actor's stop or on the registration lock; taking it would make the drain wait for
  the very publisher it is cancelling.
* The dropped-publisher task is kept rather than removed: without it a dropped publication would
  keep its engine alive until the next drain, which may be application exit.

## Risks / open questions

* Registered actors keep today's termination path, where the losing caller of a concurrent
  termination reports `Ok` while the winner may have failed (P7); that is `f-20260927-01` /
  `f-20261001-14`. Pending entries no longer have this gap (O1).
* The spawn-after-final-drain window (P9) remains, filed separately (see Threat model).

# Plan: supervisor-owned termination of an engine whose publication is aborted (f-20260914-34)

## Goal

An engine child that has been spawned but not yet published into `EngineSupervisor.actors` is
owned by the supervisor from the moment it exists until it is either published or reaped. Tab
shutdown, engine retirement and application exit terminate and await such children exactly as they
already do registered ones, and their termination failures reach the same aggregate result. The
`Drop` backstop of a dropped publisher stops being the sole owner of the child.

## MANDATE

Verbatim, `tasks/findings.md` entry `f-20260914-34` (the only member of the cluster):

> ### A spawned engine whose publication is aborted is terminated by an untracked task that shutdown does not await
>
> * **ID:** f-20260914-34 · **Status:** open · **Area:** engine-uci · **Root:** - · **Entry:** build · **Blocked:** none
> * **Where:** `src-tauri/src/engine/process.rs` `impl Drop for PendingActorGuard` (around line 1351): when the guard still holds an actor, it moves it into `tokio::spawn(async move { actor.terminate().await … })` and returns. Reached when `spawn_registered` has spawned the child but publication is aborted before registration (admission cancelled by tab close, retirement or shutdown, or an initialization error).
> * **Defect:** the termination and reap of that child run in a detached task with no owner, no join handle and no registration the shutdown path walks. Tab shutdown and application exit terminate only registered actors; if the runtime is torn down before the detached task runs, the child is neither terminated nor reaped, and its termination error surfaces only as a log line. This contradicts `.claude/rules/async-resource-invariants.md` ("Leave a spawned process … whose removal depends on the happy path" is a DO NOT) and the engine-lifecycle rule that a canceled late actor is reaped.
> * **Why it matters:** engine children outliving the application is the incident class of issue #723 (`e5422566`) and `f-20260830-51`; this is the remaining unowned path. The macOS engine-launch plan (`tasks/plans/2026-09-14-macos-engine-launch-and-removed-dir.md`, round 4, R4-04) relies on this reap for its cancellation guarantee.
> * **Open question:** should aborted-publication termination be owned by the supervisor (a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing bounded deadlines), or be performed inline by the caller of `spawn_registered` on its error path before returning, and how is the `Drop` backstop then reduced to a logged invariant violation?
> * **Related:** `f-20260830-51` (app exit terminates nothing deterministically — handled), `f-20260830-53` (detached stderr reader — handled), `f-20260914-31`.
> * **Found by:** Codex `review-engine-protocol` plan lens (round 4, confidence 91) during the macOS engine-launch build run, 2026-09-14; source verified by the orchestrator. Not reproduced by a test.

## Threat model and non-goals

Frozen in round 1.

* **Accidental, not adversarial.** The inputs are ordinary concurrency between engine launches
  and the three supervisor drains (tab close → `terminate_tab`, engine removal or executable
  retirement → `retire_matching`, application exit → `terminate_all`), and the cancellation of
  a caller future while it is inside publication. Nothing here is attacker-controlled.
* **Dropped publisher futures are a real exit path even though no production caller drops one
  today.** The locate probe found every production chain (`analyze_game` native worker,
  `get_engine_config`, `start_game` white and black, `get_best_moves` →

  path is implemented anyway, proven by deterministic drop tests, because the next cancellation
  wrapper would otherwise turn the latent gap into a leak.
* **Live inline rejection racing a drain is the production-reachable half.** A publisher that
  is still running when a drain crosses the barrier rejects inline (`reject_actor`), but no drain
  waits for it today, so application exit can reach `process::exit` while that rejection is
  still terminating the child.
* **Environments:** Linux, macOS and Windows alike. The change contains no `cfg(target_os)`

* **Non-goal — launches that have not spawned yet.** A launch that passed its admission check
  before the seal and spawns only after `terminate_all` has finished draining is not caught by
  this plan's set: nothing exists to own until the spawn returns. That window (the

  `tasks/findings-inbox/20261006-191213-2962197-1791306733058862538-6.md`, "An engine spawned after

  it needs a reserve-before-spawn or live-lease wait that is its own design question.

## Approach

### O1 — Every spawned, unpublished actor is in a supervisor-owned pending set

MANDATE: "no owner, no join handle and no registration the shutdown path walks".

* The supervisor holds a pending-actor set keyed by the admission generation (P10). Each entry
  carries the actor, its `EngineKey`, generation, application engine id and executable `PathRef`:
  the identity the three drain predicates match on.
* An actor enters the set as soon as it is spawned for an admitted publication, before the first
  await of publication: in `initialize_admitted_actor` (all `spawn_registered` callers) and in the
  fresh-actor branch of `start_interactive_search`. The guard that today wraps that span becomes
  the handle of the entry.
* The entry leaves the set in exactly one of these ways:
  1. **Publication commit** removes it inside the same `admission_coordination` critical section
     that inserts into `actors` (P4), so at no coordination-observed instant is a live actor in
     neither set or in both.
  2. **The entry's termination task** (below) removes it once the child's termination has
     completed, whichever owner started that task: an inline rejection, a drain (O2) or a dropped
     publisher (O3). The rejection error, combined with that termination's result, still returns
     to a live publisher as today.
  Removal is by generation and idempotent.
* **One entry-owned termination, one result for every owner.** The first owner that needs the
  actor terminated (inline rejection, a drain, or a dropped publisher) starts the entry's
  termination as a task that belongs to the entry, not to that owner; later owners attach to the
  same task instead of calling `EngineActor::terminate` again. Dropping or cancelling any owner —
  including the one that started it — never cancels the task, so the termination always runs to
  completion and no owner has to take it over. The task calls `EngineActor::terminate` exactly
  once, logs a failure itself with key and generation (the reporter no owner cancellation can
  bypass, as `d-20260927-08` does for the actor), records the terminal result, then removes the
  entry. Every owner awaiting it receives that result: a failed termination is an `Err` for
  **every** owner — never the `Ok` a second concurrent `EngineActor::terminate` caller gets today.
  Every owner's error is indistinguishable from the original on every observable surface — the
  same `category()`, `Display` (and therefore the same serialized `message`), `diagnostic()` and
  `root_failure()` — i.e. exactly what the owner that started the termination would have received
  from `EngineActor::terminate` today, so the renderer sees nothing it would not see today
  (`d-20260927-09` is unaffected). Because `Error` is not `Clone`, `src-tauri/src/error.rs` may
  gain one internal representation that shares the original behind an `Arc` and delegates those
  methods and `source()`; the serialized payload shape, `ErrorCategory` and every `specta::Type`
  stay unchanged. This sharing is local to pending entries; registered actors keep today's termination path (`f-20260927-01`,
  `f-20261001-14`).
* **Retention bound:** the set holds at most one entry per spawned actor whose publication is
  unresolved; every exit path above removes it, so it cannot grow across a session.
* The test-only `replace_handle` tracks its actor only once `admit` has returned a generation.
  A drop while it waits inside `admit` releases the last actor handle, and the actor loop
  terminates its runtime itself (P8), which is what
  `dropped_replacement_waiting_for_registration_reaps_actor_and_admission` already observes. With
  that, an entry always has a generation and the "not-yet-assigned" log variant disappears.

### O2 — The three drains terminate and await matching pending actors

MANDATE: "Tab shutdown and application exit terminate only registered actors"; Open question
"(a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing
bounded deadlines)".

* `terminate_all`, `terminate_tab` and `retire_matching` keep their existing barrier (seal where
  applicable, cancel matching admissions under registration + coordination). After it, each drains
  **both** matching registered actors (unchanged `terminate_exact` route) and matching pending
  entries, concurrently, and loops until neither set holds a match.
* A pending entry is drained through its entry-owned termination (O1) — started by the drain if
  no other owner has started it, otherwise attached to — and the drain awaits that task's result.
  No lifecycle lease is taken: a live publisher may hold that lease while it waits, and the drain
  must not wait behind it. A live publisher's inline rejection and a dropped publisher's cleanup
  await the same termination, so the drain never returns before a rejection or cleanup already in
  progress has reaped the child.
* Admission cancellation before the scan guarantees that a pending entry a drain matches can no
  longer be published: publication commits only with the current, uncancelled admission (P4), and
  each drain's pending predicate is the same predicate it uses to cancel admissions (tab for
  `terminate_tab`, engine id / executable for `retire_matching`, everything for `terminate_all`).
* **Failure semantics:** a pending actor's termination failure enters the drain's existing
  `aggregate_shutdown_failures` with its key and generation (logged, first error returned),
  whichever owner started that termination, whenever that termination is still in progress or not
  yet started when the drain scans after its barrier. It no longer surfaces only as a
  detached-task log line. A pending termination that already completed — and removed its entry —
  before the drain's scan is not the drain's to report: its child is no longer pending, and its
  failure was logged with key and generation by the entry's task. That is the same boundary a
  registered actor has today when its guard cleanup completes before a drain; keeping failed
  terminations findable for later drains is open `f-20261001-14`.
* **Deadlines:** no new timeout. Each termination is bounded by the existing `EngineDeadlines`
  (`quit`, `kill_reap`, stderr reap); application exit stays inside the existing
  `SHUTDOWN_BUDGET` because `terminate_all` is already awaited there (P6).
* The three drain loops are today three copies of "cancel matching admissions, then loop
  terminate-matching until none remain". They are routed through one shared drain that takes the
  predicate, so the pending half is written once (universal rule 11).
* Exact single-generation paths (`terminate_exact`, `release_generation`, `kill_engine`) are not
  changed; a reserved-but-unpublished generation there is open `f-20260914-23`.

### O3 — A dropped publisher starts its cleanup, but no longer owns it alone

MANDATE: "if the runtime is torn down before the detached task runs, the child is neither
terminated nor reaped, and its termination error surfaces only as a log line"; Open question "how
is the `Drop` backstop then reduced".

* Dropping an armed guard leaves its entry in the pending set and starts the entry-owned
  termination (O1), so a long-running session reaps the child promptly without waiting for a
  drain. That task logs a failure with key and generation (the existing
  `log_pending_actor_cleanup_error` shape) and removes the entry when it completes.
* Ownership is the set, not the dropped owner: a drain that runs before that termination has
  finished attaches to the same entry-owned task and awaits it (O2), and application exit awaits
  `terminate_all` inside `SHUTDOWN_BUDGET` (P6), so the runtime is alive while the task runs. The
  dropped publisher's role is only to start the termination early.
* Answer to the finding's second question: the `Drop` backstop is **not** reduced to a logged
  invariant violation. `Drop` is synchronous and fires only when no caller remains to await
  anything (P2), so "inline by the caller" cannot cover this path; reducing it to a log would leave
  the child running for the rest of the session, against `d-20260927-07`.
* `RegistrationGuard`'s `Drop` (also a spawned cleanup) is unchanged: its actor is already
  registered in `actors`, every drain reaches it there, and its `terminate_exact` runs under the
  per-key lifecycle lease that the drain's own `terminate_exact` also takes, so drains already await
  it. The only code the two `Drop`s share is "spawn and log", which is coincidental, not the same
  domain concept (rule 11's exception).

### O4 — Verification

MANDATE: "Not reproduced by a test."

Each case uses the in-process fake UCI I/O (`actor_with`, `actor_with_terminate_delay`,
`TerminateErrorIo` in `process.rs` tests), runs on all three platforms, and must go red when O1–O3
are reverted:

* **V1 dropped publisher, then exit.** A publisher is blocked inside publication (for example
  behind a held `registration` lock or lifecycle lease) with an actor whose termination is
  delayed; the publisher task is aborted; `terminate_all` then returns only after that actor's
  termination has completed (termination counter is 1 at the moment `terminate_all` returns), the
  pending set is empty, and the actor is terminated exactly once overall. Today `terminate_all`
  returns immediately with the counter still 0.
* **V2 live publisher, then exit.** A publisher blocked before its commit (it is not aborted);
  `terminate_all` returns `Ok` after terminating its actor while the publisher is still blocked;
  once unblocked, the publisher returns an error, the actor is not published, and it was
  terminated exactly once.
* **V2b inline rejection already in progress, then exit.** A publisher whose inline rejection is
  terminating an actor with a delayed termination when `terminate_all` starts; `terminate_all`
  returns only after that termination has completed (termination counter is 1 at the moment it
  returns), and the actor is terminated exactly once. Removing the pending entry before the
  rejection's termination completes must make this case fail.
* **V3 tab scope.** Two blocked publishers on tabs A and B; `terminate_tab(A)` returns after A's
  pending actor is terminated; B's actor is untouched and B still publishes once unblocked.
* **V4 retirement scope.** A blocked publisher for engine id E and another for engine id F;
  `retire_engine(E)` drains E's pending actor and leaves F's.
* **V5 failure reaches the aggregate, whoever started the termination.** A pending actor whose
  termination fails makes `terminate_all` return `Err`, and the shutdown failure log names its key
  and generation — both when the drain starts that termination and when a dropped publisher's
  cleanup (or an inline rejection) started it first and the drain only awaits it. In the second
  case the starting owner also sees the failure (cleanup log, or the rejection's combined error).
  The failing fake termination carries a unique diagnostic sentinel; every owner's error has the
  original's `category()`, the same `Display`, and a `diagnostic()` containing the sentinel.
* **V8 the starting owner is cancelled mid-termination.** A live publisher's inline rejection
  starts the termination of an actor whose termination is delayed (gated) and fails; that
  publisher task is aborted while the termination is in progress; `terminate_all` is then started
  and crosses its barrier while the termination is still held by the gate; after the gate opens,
  `terminate_all` completes within a bounded time and returns the failure with key and
  generation, its error has the original's `category()` and a `diagnostic()` containing the
  sentinel, the actor's termination ran exactly once, and the pending set is empty. An implementation that ties the termination to the starting
  owner's future (hang, a second `terminate()` that returns `Ok`, or a lost failure) fails it.
* **V6 set retention.** After a successful publication, an inline rejection and a completed
  dropped-publisher cleanup, the pending set is empty.
* **V7 existing tests** keep their assertions: the guard-drop, registration-guard, shutdown,
  retirement and game-construction tests listed by probe 2 (`process.rs`, `game.rs`, `main.rs`).
  `pending_actor_cleanup_log_carries_key_and_generation` loses its unassigned-generation half
  (O1) and keeps the assigned half.

  drain and await (the finding's option (a)). Rejected: termination inline by the caller with the
  `Drop` reduced to a logged invariant violation (option (b)) — every rejection is already inline
  (P2), and the guard fires only on a dropped future, where no caller remains to await; logging
  instead would leak the child, against `d-20260927-07`. Rejected: a `tokio_util::task::TaskTracker`
  of termination tasks — it cannot be filtered by tab or engine for `terminate_tab` and retirement,
  and it would not cover a live publisher's inline rejection racing exit. Reversal path: remove
  the set and the drains' pending half; V1–V5 go red first.
* **D2 — Is `RegistrationGuard`'s spawned cleanup merged with the pending guard?** Chosen: no.
  Its actor is registered, drains reach it in `actors`, and drains already await it through the
  per-key lifecycle lease. Rejected: one generic "spawn cleanup from Drop" helper — the two share
  only the spawn-and-log call, not an ownership model. Reversal path: route both through one
  helper if a third guard of either shape appears.
* **D3 — Do exact single-generation terminations drain the pending set?** Chosen: no;
  `f-20260914-23` owns a reserved-but-unpublished generation on `kill_engine`. Rejected: widening
  `terminate_exact` here, which would change that finding's mandate without its review.
* **D4 — How do a drain, an inline rejection and a dropped publisher's cleanup share one pending
  actor's termination?** Chosen: one termination per pending entry, started by the first owner and
  awaited by the others, whose terminal result every owner receives (O1); the termination is an
  entry-owned task, so no owner's cancellation can interrupt it (round-2 issue I3). Rejected: each owner
  calling `EngineActor::terminate` independently — a second concurrent caller receives
  `EngineDisconnected`, which `terminate` maps to `Ok` once the task is reaped, so a drain racing a
  failed cleanup would report success and the failure would stay log-only (round-1 issue I1,
  verified at `process.rs:3459-3466` and `:3815-3825`). Rejected: a termination run inside the
  starting owner's future with takeover by a later owner — once `Terminate` was sent, the failure
  reaches only the original reply and a takeover's second `terminate()` returns `Ok` (round-2 I3,
  `:3824`, `:3461`). Rejected: extending result sharing to
  registered actors — that is `f-20260927-01` / `f-20261001-14`. Reversal path: remove the shared
  termination; V5's await-case goes red first.

## Decisions and trade-offs

* Option (a) over (b): settled in D1. The trade-off is one more supervisor map against making
  exit and tab close wait for every child the process has spawned.
* Pending drain bypasses the lifecycle lease: a live publisher can hold that lease while it waits
  on a previous actor's stop or on the registration lock; taking it would make the drain wait for
  the very publisher it is cancelling.
* The dropped-publisher task is kept rather than removed: without it a dropped publication would
  keep its engine alive until the next drain, which may be application exit.

## Risks / open questions

* Registered actors keep today's termination path, where the losing caller of a concurrent
  termination reports `Ok` while the winner may have failed (P7); that is `f-20260927-01` /
  `f-20261001-14`. Pending entries no longer have this gap (O1).
* The spawn-after-final-drain window (P9) remains, filed separately (see Threat model).

# Plan: supervisor-owned termination of an engine whose publication is aborted (f-20260914-34)

## Goal

An engine child that has been spawned but not yet published into `EngineSupervisor.actors` is
owned by the supervisor from the moment it exists until it is either published or reaped. Tab
shutdown, engine retirement and application exit terminate and await such children exactly as they
already do registered ones, and their termination failures reach the same aggregate result. The
`Drop` backstop of a dropped publisher stops being the sole owner of the child.

## MANDATE

Verbatim, `tasks/findings.md` entry `f-20260914-34` (the only member of the cluster):

> ### A spawned engine whose publication is aborted is terminated by an untracked task that shutdown does not await
>
> * **ID:** f-20260914-34 · **Status:** open · **Area:** engine-uci · **Root:** - · **Entry:** build · **Blocked:** none
> * **Where:** `src-tauri/src/engine/process.rs` `impl Drop for PendingActorGuard` (around line 1351): when the guard still holds an actor, it moves it into `tokio::spawn(async move { actor.terminate().await … })` and returns. Reached when `spawn_registered` has spawned the child but publication is aborted before registration (admission cancelled by tab close, retirement or shutdown, or an initialization error).
> * **Defect:** the termination and reap of that child run in a detached task with no owner, no join handle and no registration the shutdown path walks. Tab shutdown and application exit terminate only registered actors; if the runtime is torn down before the detached task runs, the child is neither terminated nor reaped, and its termination error surfaces only as a log line. This contradicts `.claude/rules/async-resource-invariants.md` ("Leave a spawned process … whose removal depends on the happy path" is a DO NOT) and the engine-lifecycle rule that a canceled late actor is reaped.
> * **Why it matters:** engine children outliving the application is the incident class of issue #723 (`e5422566`) and `f-20260830-51`; this is the remaining unowned path. The macOS engine-launch plan (`tasks/plans/2026-09-14-macos-engine-launch-and-removed-dir.md`, round 4, R4-04) relies on this reap for its cancellation guarantee.
> * **Open question:** should aborted-publication termination be owned by the supervisor (a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing bounded deadlines), or be performed inline by the caller of `spawn_registered` on its error path before returning, and how is the `Drop` backstop then reduced to a logged invariant violation?
> * **Related:** `f-20260830-51` (app exit terminates nothing deterministically — handled), `f-20260830-53` (detached stderr reader — handled), `f-20260914-31`.
> * **Found by:** Codex `review-engine-protocol` plan lens (round 4, confidence 91) during the macOS engine-launch build run, 2026-09-14; source verified by the orchestrator. Not reproduced by a test.

## Threat model and non-goals

Frozen in round 1.

* **Accidental, not adversarial.** The inputs are ordinary concurrency between engine launches
  and the three supervisor drains (tab close → `terminate_tab`, engine removal or executable
  retirement → `retire_matching`, application exit → `terminate_all`), and the cancellation of
  a caller future while it is inside publication. Nothing here is attacker-controlled.
* **Dropped publisher futures are a real exit path even though no production caller drops one
  today.** The locate probe found every production chain (`analyze_game` native worker,
  `get_engine_config`, `start_game` white and black, `get_best_moves` →
  `start_interactive_search`) awaiting publication directly, with no select, timeout or abort
  around it. `d-20260927-07` settled the same question for game construction: the cancellation
  path is implemented anyway, proven by deterministic drop tests, because the next cancellation
  wrapper would otherwise turn the latent gap into a leak.
* **Live inline rejection racing a drain is the production-reachable half.** A publisher that
  is still running when a drain crosses the barrier rejects inline (`reject_actor`), but no drain
  waits for it today, so application exit can reach `process::exit` while that rejection is
  still terminating the child.
* **Environments:** Linux, macOS and Windows alike. The change contains no `cfg(target_os)`
  code; its tests use the in-process fake UCI I/O, so they run unchanged on every runner.
* **Non-goal — launches that have not spawned yet.** A launch that passed its admission check
  before the seal and spawns only after `terminate_all` has finished draining is not caught by
  this plan's set: nothing exists to own until the spawn returns. That window (the
  `resolve_launch` hand-off in `start_interactive_search`) is filed as its own finding through the
  planner inbox (published entry

## Approach

### O1 — Every spawned, unpublished actor is in a supervisor-owned pending set

MANDATE: "no owner, no join handle and no registration the shutdown path walks".

* The supervisor holds a pending-actor set keyed by the admission generation (P10). Each entry
  carries the actor, its `EngineKey`, generation, application engine id and executable `PathRef`:
  the identity the three drain predicates match on.
* An actor enters the set as soon as it is spawned for an admitted publication, before the first
  await of publication: in `initialize_admitted_actor` (all `spawn_registered` callers) and in the
  fresh-actor branch of `start_interactive_search`. The guard that today wraps that span becomes
  the handle of the entry.
* The entry leaves the set in exactly one of these ways:
  1. **Publication commit** removes it inside the same `admission_coordination` critical section
     that inserts into `actors` (P4), so at no coordination-observed instant is a live actor in
     neither set or in both.
  2. **The entry's termination task** (below) removes it once the child's termination has
     completed, whichever owner started that task: an inline rejection, a drain (O2) or a dropped
     publisher (O3). The rejection error, combined with that termination's result, still returns
     to a live publisher as today.
  Removal is by generation and idempotent.
* **One entry-owned termination, one result for every owner.** The first owner that needs the
  actor terminated (inline rejection, a drain, or a dropped publisher) starts the entry's
  termination as a task that belongs to the entry, not to that owner; later owners attach to the
  same task instead of calling `EngineActor::terminate` again. Dropping or cancelling any owner —
  including the one that started it — never cancels the task, so the termination always runs to
  completion and no owner has to take it over. The task calls `EngineActor::terminate` exactly
  once, logs a failure itself with key and generation (the reporter no owner cancellation can
  bypass, as `d-20260927-08` does for the actor), records the terminal result, then removes the
  entry. Every owner awaiting it receives that result: a failed termination is an `Err` for
  **every** owner — never the `Ok` a second concurrent `EngineActor::terminate` caller gets today.
  Every owner's error is indistinguishable from the original on every observable surface — the
  same `category()`, `Display` (and therefore the same serialized `message`), `diagnostic()` and
  `root_failure()` — i.e. exactly what the owner that started the termination would have received
  from `EngineActor::terminate` today, so the renderer sees nothing it would not see today
  (`d-20260927-09` is unaffected). Because `Error` is not `Clone`, `src-tauri/src/error.rs` may
  gain one internal representation that shares the original behind an `Arc` and delegates those
  methods and `source()`; the serialized payload shape, `ErrorCategory` and every `specta::Type`
  stay unchanged. This sharing is local to pending entries; registered actors keep today's termination path (`f-20260927-01`,
  `f-20261001-14`).
* **Retention bound:** the set holds at most one entry per spawned actor whose publication is
  unresolved; every exit path above removes it, so it cannot grow across a session.
* The test-only `replace_handle` tracks its actor only once `admit` has returned a generation.
  A drop while it waits inside `admit` releases the last actor handle, and the actor loop
  terminates its runtime itself (P8), which is what
  `dropped_replacement_waiting_for_registration_reaps_actor_and_admission` already observes. With
  that, an entry always has a generation and the "not-yet-assigned" log variant disappears.

### O2 — The three drains terminate and await matching pending actors

MANDATE: "Tab shutdown and application exit terminate only registered actors"; Open question
"(a pending-termination set that tab shutdown and `RunEvent::ExitRequested` await with the existing
bounded deadlines)".

* `terminate_all`, `terminate_tab` and `retire_matching` keep their existing barrier (seal where
  applicable, cancel matching admissions under registration + coordination). After it, each drains
  **both** matching registered actors (unchanged `terminate_exact` route) and matching pending
  entries, concurrently, and loops until neither set holds a match.
* A pending entry is drained through its entry-owned termination (O1) — started by the drain if
  no other owner has started it, otherwise attached to — and the drain awaits that task's result.
  No lifecycle lease is taken: a live publisher may hold that lease while it waits, and the drain
  must not wait behind it. A live publisher's inline rejection and a dropped publisher's cleanup
  await the same termination, so the drain never returns before a rejection or cleanup already in
  progress has reaped the child.
* Admission cancellation before the scan guarantees that a pending entry a drain matches can no
  longer be published: publication commits only with the current, uncancelled admission (P4), and
  each drain's pending predicate is the same predicate it uses to cancel admissions (tab for
  `terminate_tab`, engine id / executable for `retire_matching`, everything for `terminate_all`).
* **Failure semantics:** a pending actor's termination failure enters the drain's existing
  `aggregate_shutdown_failures` with its key and generation (logged, first error returned),
  whichever owner started that termination, whenever that termination is still in progress or not
  yet started when the drain scans after its barrier. It no longer surfaces only as a
  detached-task log line. A pending termination that already completed — and removed its entry —
  before the drain's scan is not the drain's to report: its child is no longer pending, and its
  failure was logged with key and generation by the entry's task. That is the same boundary a
  registered actor has today when its guard cleanup completes before a drain; keeping failed
  terminations findable for later drains is open `f-20261001-14`.
* **Deadlines:** no new timeout. Each termination is bounded by the existing `EngineDeadlines`
  (`quit`, `kill_reap`, stderr reap); application exit stays inside the existing
  `SHUTDOWN_BUDGET` because `terminate_all` is already awaited there (P6).
* The three drain loops are today three copies of "cancel matching admissions, then loop
  terminate-matching until none remain". They are routed through one shared drain that takes the
  predicate, so the pending half is written once (universal rule 11).
* Exact single-generation paths (`terminate_exact`, `release_generation`, `kill_engine`) are not
  changed; a reserved-but-unpublished generation there is open `f-20260914-23`.

### O3 — A dropped publisher starts its cleanup, but no longer owns it alone

MANDATE: "if the runtime is torn down before the detached task runs, the child is neither
terminated nor reaped, and its termination error surfaces only as a log line"; Open question "how
is the `Drop` backstop then reduced".

* Dropping an armed guard leaves its entry in the pending set and starts the entry-owned
  termination (O1), so a long-running session reaps the child promptly without waiting for a
  drain. That task logs a failure with key and generation (the existing
  `log_pending_actor_cleanup_error` shape) and removes the entry when it completes.
* Ownership is the set, not the dropped owner: a drain that runs before that termination has
  finished attaches to the same entry-owned task and awaits it (O2), and application exit awaits
  `terminate_all` inside `SHUTDOWN_BUDGET` (P6), so the runtime is alive while the task runs. The
  dropped publisher's role is only to start the termination early.
* Answer to the finding's second question: the `Drop` backstop is **not** reduced to a logged
  invariant violation. `Drop` is synchronous and fires only when no caller remains to await
  anything (P2), so "inline by the caller" cannot cover this path; reducing it to a log would leave
  the child running for the rest of the session, against `d-20260927-07`.
* `RegistrationGuard`'s `Drop` (also a spawned cleanup) is unchanged: its actor is already
  registered in `actors`, every drain reaches it there, and its `terminate_exact` runs under the
  per-key lifecycle lease that the drain's own `terminate_exact` also takes, so drains already await
  it. The only code the two `Drop`s share is "spawn and log", which is coincidental, not the same
  domain concept (rule 11's exception).

### O4 — Verification

MANDATE: "Not reproduced by a test."

Each case uses the in-process fake UCI I/O (`actor_with`, `actor_with_terminate_delay`,
`TerminateErrorIo` in `process.rs` tests), runs on all three platforms, and must go red when O1–O3
are reverted:

* **V1 dropped publisher, then exit.** A publisher is blocked inside publication (for example
  behind a held `registration` lock or lifecycle lease) with an actor whose termination is
  delayed; the publisher task is aborted; `terminate_all` then returns only after that actor's
  termination has completed (termination counter is 1 at the moment `terminate_all` returns), the
  pending set is empty, and the actor is terminated exactly once overall. Today `terminate_all`
  returns immediately with the counter still 0.
* **V2 live publisher, then exit.** A publisher blocked before its commit (it is not aborted);
  `terminate_all` returns `Ok` after terminating its actor while the publisher is still blocked;
  once unblocked, the publisher returns an error, the actor is not published, and it was
  terminated exactly once.
* **V2b inline rejection already in progress, then exit.** A publisher whose inline rejection is
  terminating an actor with a delayed termination when `terminate_all` starts; `terminate_all`
  returns only after that termination has completed (termination counter is 1 at the moment it
  returns), and the actor is terminated exactly once. Removing the pending entry before the
  rejection's termination completes must make this case fail.
* **V3 tab scope.** Two blocked publishers on tabs A and B; `terminate_tab(A)` returns after A's
  pending actor is terminated; B's actor is untouched and B still publishes once unblocked.
* **V4 retirement scope.** A blocked publisher for engine id E and another for engine id F;
  `retire_engine(E)` drains E's pending actor and leaves F's.
* **V5 failure reaches the aggregate, whoever started the termination.** A pending actor whose
  termination fails makes `terminate_all` return `Err`, and the shutdown failure log names its key
  and generation — both when the drain starts that termination and when a dropped publisher's
  cleanup (or an inline rejection) started it first and the drain only awaits it. In the second
  case the starting owner also sees the failure (cleanup log, or the rejection's combined error).
  The failing fake termination carries a unique diagnostic sentinel; every owner's error has the
  original's `category()`, the same `Display`, and a `diagnostic()` containing the sentinel.
* **V8 the starting owner is cancelled mid-termination.** A live publisher's inline rejection
  starts the termination of an actor whose termination is delayed (gated) and fails; that
  publisher task is aborted while the termination is in progress; `terminate_all` is then started
  and crosses its barrier while the termination is still held by the gate; after the gate opens,
  `terminate_all` completes within a bounded time and returns the failure with key and
  generation, its error has the original's `category()` and a `diagnostic()` containing the
  sentinel, the actor's termination ran exactly once, and the pending set is empty. An implementation that ties the termination to the starting
  owner's future (hang, a second `terminate()` that returns `Ok`, or a lost failure) fails it.
* **V6 set retention.** After a successful publication, an inline rejection and a completed
  dropped-publisher cleanup, the pending set is empty.
* **V7 existing tests** keep their assertions: the guard-drop, registration-guard, shutdown,
  retirement and game-construction tests listed by probe 2 (`process.rs`, `game.rs`, `main.rs`).
  `pending_actor_cleanup_log_carries_key_and_generation` loses its unassigned-generation half
  (O1) and keeps the assigned half.

## Decided autonomously

`full auto`; recorded here for review, and by the adopting session through
`./scripts/findings.py record-decision`.

* **D1 — Who owns the termination of an actor whose publication is aborted?** Chosen: a
  supervisor-owned pending-actor set that `terminate_all`, `terminate_tab` and `retire_matching`
  drain and await (the finding's option (a)). Rejected: termination inline by the caller with the
  `Drop` reduced to a logged invariant violation (option (b)) — every rejection is already inline
  (P2), and the guard fires only on a dropped future, where no caller remains to await; logging
  instead would leak the child, against `d-20260927-07`. Rejected: a `tokio_util::task::TaskTracker`
  of termination tasks — it cannot be filtered by tab or engine for `terminate_tab` and retirement,
  and it would not cover a live publisher's inline rejection racing exit. Reversal path: remove
  the set and the drains' pending half; V1–V5 go red first.
* **D2 — Is `RegistrationGuard`'s spawned cleanup merged with the pending guard?** Chosen: no.
  Its actor is registered, drains reach it in `actors`, and drains already await it through the
  per-key lifecycle lease. Rejected: one generic "spawn cleanup from Drop" helper — the two share
  only the spawn-and-log call, not an ownership model. Reversal path: route both through one
  helper if a third guard of either shape appears.
* **D3 — Do exact single-generation terminations drain the pending set?** Chosen: no;
  `f-20260914-23` owns a reserved-but-unpublished generation on `kill_engine`. Rejected: widening
  `terminate_exact` here, which would change that finding's mandate without its review.
* **D4 — How do a drain, an inline rejection and a dropped publisher's cleanup share one pending
  actor's termination?** Chosen: one termination per pending entry, started by the first owner and
  awaited by the others, whose terminal result every owner receives (O1); the termination is an
  entry-owned task, so no owner's cancellation can interrupt it (round-2 issue I3). Rejected: each owner
  calling `EngineActor::terminate` independently — a second concurrent caller receives
  `EngineDisconnected`, which `terminate` maps to `Ok` once the task is reaped, so a drain racing a
  failed cleanup would report success and the failure would stay log-only (round-1 issue I1,
  verified at `process.rs:3459-3466` and `:3815-3825`). Rejected: a termination run inside the
  starting owner's future with takeover by a later owner — once `Terminate` was sent, the failure
  reaches only the original reply and a takeover's second `terminate()` returns `Ok` (round-2 I3,
  `:3824`, `:3461`). Rejected: extending result sharing to
  registered actors — that is `f-20260927-01` / `f-20261001-14`. Reversal path: remove the shared
  termination; V5's await-case goes red first.

## Decisions and trade-offs

* Option (a) over (b): settled in D1. The trade-off is one more supervisor map against making
  exit and tab close wait for every child the process has spawned.
* Pending drain bypasses the lifecycle lease: a live publisher can hold that lease while it waits
  on a previous actor's stop or on the registration lock; taking it would make the drain wait for
  the very publisher it is cancelling.
* The dropped-publisher task is kept rather than removed: without it a dropped publication would
  keep its engine alive until the next drain, which may be application exit.

## Risks / open questions

* Registered actors keep today's termination path, where the losing caller of a concurrent
  termination reports `Ok` while the winner may have failed (P7); that is `f-20260927-01` /
  `f-20261001-14`. Pending entries no longer have this gap (O1).
* The spawn-after-final-drain window (P9) remains, filed separately (see Threat model).
