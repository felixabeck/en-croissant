## Approach

### What the interval is

The failing number is in-page wall clock from the `readGame` hook's return until the freshness attribute mutates. It is not WebDriver delivery. The observer runs as a microtask on that mutation.

That wall clock currently mixes three costs: the awaited `lexPgn` backend call, synchronous `innerParsePGN`, and the React render that walks the replacement tree in notation, PGN text, the eval chart, and practice stats. The practice deck sync effect is not in the interval.

### Main-thread budget

`FILE_FRESHNESS_APPLY_BUDGET_MS` stays 1,000. The pass/fail applies to main-thread publication only:

`mainThreadMs = observedAt - readFinishedAt - lexAwaitMs`

`lexAwaitMs` is the duration recorded by a platform hook around `lexPgn`, using the same finally-hook pattern as `readGame`. The hook records only while the freshness measurement is armed and has not reached a terminal state. Production behavior is unchanged when the hook is absent.

`mainThreadMs <= 1,000` is the apply assertion. A synchronous stall after lex returns still fails it. Time spent inside the `lexPgn` await does not. `lexAwaitMs` is printed beside the existing read and apply figures.

The one-poll assertion keeps its meaning: elapsed time from the rewrite to the observation is at most one poll interval plus the measured `readGame`, the measured `lexPgn` await, and `mainThreadMs`. Those three replace the single old apply term. The poll interval constant stays 2,000.

An idle `verify:app` that reports `lexAwaitMs` above 1,000 fails the phase. The constant is not raised. That case returns to the orchestrator with the segment log. A loaded-host `lexAwaitMs` spike with `mainThreadMs` inside 1,000 is the backend wait this split removes from the main-thread ceiling, which is the same class of wait `readGame` is already excluded for.

### Publication ordering

The render that commits the new `verified` reload count does not, for the replacement root:

- build notation rows
- serialize the full PGN
- walk the eval mainline
- compute practice stats across every card
- run `syncDeck` or `buildFromTree` (already true today; keep it true)

The replacement tree is in the store before that commit. The board shows the new current position. Notation, PGN text, the eval chart, and practice stats may keep their previous result for that commit. They must not present a move, row, or chart point from the previous tree as the selected move of the new tree. They rebuild on a following turn, before the verifier looks for a move that exists only in the rewritten PGN.

The deferral flag is not a field of the persisted tree. Zustand persist stores the tree snapshot, and a new persisted field would change the stored shape. Use a non-persisted side table keyed by the store.

`installDiskTree` does not return until that freshness commit has flushed. `flushSync` is allowed for this install only. `startTransition` is the wrong tool: it would delay the attribute this budget measures. No other call site gains a synchronous flush.

Conflict, unavailable, and unchanged-stamp paths do not parse the replacement and do not take the heavy-view deferral.

### Slow-application proof

A test-only synchronous wedge runs inside the install path after lex would have returned and before the attribute commit. The apply comparison fails when the measured main-thread interval exceeds 1,000 ms with the wedge, and passes when the wedge is removed. The wedge is absent from production. The test drives the real install and the real attribute, not a mocked clock and not a copied threshold.

### Segment log

`verify:app` prints `readGame`, `lexAwaitMs`, and `mainThreadMs` on the existing freshness info line. The numbers come from the in-page measurement, not from the driver's poll. A later miss can be read from that line.

## Decisions and trade-offs

### Decided autonomously

## Approach

### What the interval is

The failing number is in-page wall clock from the `readGame` hook's return until the freshness attribute mutates. It is not WebDriver delivery. The observer runs as a microtask on that mutation.

That wall clock currently mixes three costs: the awaited `lexPgn` backend call, synchronous `innerParsePGN`, and the React render that walks the replacement tree in whichever full-tree consumers are mounted. Those consumers include notation, PGN text, the eval chart, practice stats, repertoire stats and its board-state map, and info-panel stats. The practice deck sync effect is not in the interval. WebDriver polling is not in it either.

### Main-thread budget

`FILE_FRESHNESS_APPLY_BUDGET_MS` stays 1,000. The pass/fail applies to main-thread publication only.

The page records four timestamps. `readFinishedAt` is the existing `readGame` hook. `lexAwaitMs` is a platform hook around `lexPgn`, using the same finally-hook pattern. It records only while the freshness measurement is armed and has not reached a terminal state, and it is a no-op when the hook is absent. `appliedAt` is `performance.now()` in the page at the moment `installDiskTree` has put the replacement root in the store, before `flushSync` and before the freshness attribute is committed. `observedAt` stays the MutationObserver stamp on that attribute.

`applicationMs = appliedAt - readFinishedAt - lexAwaitMs`

`observationGapMs = observedAt - appliedAt`

`mainThreadMs = observedAt - readFinishedAt - lexAwaitMs`

`mainThreadMs` is `applicationMs + observationGapMs`. `mainThreadMs <= 1,000` is the only apply assertion. `applicationMs` and `observationGapMs` are printed so a miss shows whether the stall is the store write or the commit and observer. Neither gets its own ceiling, and they are not added to 1,000 to make a 2,000 ms budget. A synchronous stall after lex returns still fails `mainThreadMs`. Time inside the `lexPgn` await does not.

The one-poll assertion keeps its meaning: elapsed time from the rewrite to the observation is at most one poll interval plus the measured `readGame`, the measured `lexPgn` await, and `mainThreadMs`. The poll interval constant stays 2,000.

An idle run after the publication change that reports `lexAwaitMs` above 1,000, or `mainThreadMs` above 1,000, fails the phase. The constant is not raised. A loaded-host `lexAwaitMs` spike with `mainThreadMs` inside 1,000 is the backend wait this split removes from the main-thread ceiling, the same class of wait `readGame` is already excluded for.

Before any publication change, two ordinary idle `verify:app` runs print these segments on the current commit path. Those two runs are diagnostic. They may miss the old combined 1,000 ms check, and that miss does not edit a constant and does not by itself fail the phase. If either diagnostic reports `applicationMs` above 1,000, stop red before deferring walks and do not move the parser. That stop is the reversal of the third decision below.

### Publication ordering

The render that commits the new `verified` reload count does not walk the replacement root in any mounted full-tree consumer. The consumers are:

- notation rows
- both PGN serializations in the editor
- the eval mainline
- practice stats across every card
- repertoire stats and the repertoire board-state map, including the move index built from that map
- info-panel tree stats
- `syncDeck` or `buildFromTree` (already outside this commit; keep them there)

Unmounted panels do not run. The practice test that mocks the repertoire panel away does not count as proof for that panel. A closed positions dialog that is not mounted is not one of these consumers.

The replacement tree is in the store before that commit. The board shows the new current position. The deferred panels may keep their previous result for that commit. A retained notation row or chart point cannot be activated as a move of the new tree. The editor text stays bound to the root that produced it. While that root is not the installed root, Update does not call `setState`, including the case where comments are off and the button would otherwise show because the two serializations differ. The panels rebuild on a following turn, before the verifier looks for a move that exists only in the rewritten PGN.

The deferral flag is not a field of the persisted tree. Use one non-persisted side table keyed by the store, read by every consumer above. The flag is cleared when that following turn is scheduled, before the rebuild runs. A rebuild that throws uses the existing render error path. It does not gain a new error panel, and it does not leave the flag set. The next successful render of that store walks the replacement root.

`installDiskTree` stamps `appliedAt` at the store write, then does not return until the freshness commit has flushed. `flushSync` is allowed for this install only. `startTransition` is the wrong tool: it would delay the attribute this budget measures. No other call site gains a synchronous flush.

Conflict, unavailable, and unchanged-stamp paths do not parse the replacement and do not take the heavy-view deferral.

### Slow-application proof

A test-only synchronous wedge runs inside the real install path after lex would have returned and before the attribute commit. It is armed only through the verifier page hook and is a no-op when that hook is absent. It is not a production sleep and it does not add lex time.

The unit test drives that install and the real attribute. The comparison fails while the wedge makes `mainThreadMs` exceed 1,000 and passes after the wedge is removed. The same wedge then fails the native `verify:app` main-thread assertion, and an exact removal passes. A passing unit arithmetic test is not a substitute for the native failure. The test does not mock the clock and does not copy the threshold into an expectation that skips the comparison.

### Segment log

`verify:app` prints `readGame`, `lexAwaitMs`, `applicationMs`, `observationGapMs`, and `mainThreadMs` on the existing freshness info line. The numbers come from the in-page timestamps, not from the driver's poll. The two diagnostic runs and every later run print all five. A later miss can be read from that line.

## Approach

### What the interval is

The failing number is in-page wall clock from the `readGame` hook's return until the freshness attribute mutates. It is not WebDriver delivery. The observer runs as a microtask on that mutation.

That wall clock currently mixes three costs: the awaited `lexPgn` backend call, synchronous `innerParsePGN`, and the React render that walks the replacement tree in whichever full-tree consumers are mounted. Those consumers include notation, PGN text, the eval chart, practice stats, repertoire stats and its board-state map, and info-panel stats. The practice deck sync effect is not in the interval. WebDriver polling is not in it either.

### Main-thread budget

`FILE_FRESHNESS_APPLY_BUDGET_MS` stays 1,000. The pass/fail applies to main-thread publication only.

The page records four timestamps. `readFinishedAt` is the existing `readGame` hook. `lexAwaitMs` is a platform hook around `lexPgn`, using the same finally-hook pattern. It records only while the freshness measurement is armed and has not reached a terminal state, and it is a no-op when the hook is absent. `appliedAt` is `performance.now()` in the page at the moment `installDiskTree` has put the replacement root in the store, before `flushSync` and before the freshness attribute is committed. `observedAt` stays the MutationObserver stamp on that attribute.

`applicationMs = appliedAt - readFinishedAt - lexAwaitMs`

`observationGapMs = observedAt - appliedAt`

`mainThreadMs = observedAt - readFinishedAt - lexAwaitMs`

`mainThreadMs` is `applicationMs + observationGapMs`. `mainThreadMs <= 1,000` is the only apply assertion. `applicationMs` and `observationGapMs` are printed so a miss shows whether the stall is the store write or the commit and observer. Neither gets its own ceiling, and they are not added to 1,000 to make a 2,000 ms budget. A synchronous stall after lex returns still fails `mainThreadMs`. Time inside the `lexPgn` await does not.

The one-poll assertion keeps its meaning: elapsed time from the rewrite to the observation is at most one poll interval plus the measured `readGame`, the measured `lexPgn` await, and `mainThreadMs`. The poll interval constant stays 2,000.

An idle run after the publication change that reports `lexAwaitMs` above 1,000, or `mainThreadMs` above 1,000, fails the phase. The constant is not raised. A loaded-host `lexAwaitMs` spike with `mainThreadMs` inside 1,000 is the backend wait this split removes from the main-thread ceiling, the same class of wait `readGame` is already excluded for.

Before any publication change, two ordinary idle `verify:app` runs print these segments on the current commit path. Those two runs are diagnostic. They may miss the old combined 1,000 ms check, and that miss does not edit a constant and does not by itself fail the phase. If either diagnostic reports `applicationMs` above 1,000, stop red before deferring walks and do not move the parser. That stop is the reversal of the third decision below.

### Publication ordering

The render that commits the new `verified` reload count does not walk the replacement root in any mounted full-tree consumer. The consumers are:

- notation rows
- both PGN serializations in the editor
- the eval mainline
- practice stats across every card
- repertoire stats and the repertoire board-state map, including the move index built from that map
- info-panel tree stats
- `syncDeck` or `buildFromTree` (already outside this commit; keep them there)

Unmounted panels do not run. The practice test that mocks the repertoire panel away does not count as proof for that panel. A closed positions dialog that is not mounted is not one of these consumers.

The replacement tree is in the store before that commit. The board shows the new current position. The deferred panels may keep their previous result for that commit. A retained notation row or chart point cannot be activated as a move of the new tree. The editor text stays bound to the root that produced it. While that root is not the installed root, Update does not call `setState`, including the case where comments are off and the button would otherwise show because the two serializations differ. The panels rebuild on a following turn, before the verifier looks for a move that exists only in the rewritten PGN.

The deferral flag is not a field of the persisted tree. Use one non-persisted side table keyed by the store, read by every consumer above. The flag is cleared when that following turn is scheduled, before the rebuild runs. A rebuild that throws uses the existing render error path. It does not gain a new error panel, and it does not leave the flag set. The next successful render of that store walks the replacement root.

`installDiskTree` stamps `appliedAt` at the store write, then does not return until the freshness commit has flushed. `flushSync` is allowed for this install only. `startTransition` is the wrong tool: it would delay the attribute this budget measures. No other call site gains a synchronous flush.

Conflict, unavailable, and unchanged-stamp paths do not parse the replacement and do not take the heavy-view deferral.

### Slow-application proof

A test-only synchronous wedge runs inside the real install path after lex would have returned and before the attribute commit. It is armed only through the verifier page hook and is a no-op when that hook is absent. It is not a production sleep and it does not add lex time.

The unit test drives that install and the real attribute. The comparison fails while the wedge makes `mainThreadMs` exceed 1,000 and passes after the wedge is removed. The same wedge then fails the native `verify:app` main-thread assertion, and an exact removal passes. A passing unit arithmetic test is not a substitute for the native failure. The test does not mock the clock and does not copy the threshold into an expectation that skips the comparison.

### Segment log

`verify:app` prints `readGame`, `lexAwaitMs`, `applicationMs`, `observationGapMs`, and `mainThreadMs` on the existing freshness info line. The numbers come from the in-page timestamps, not from the driver's poll. The two diagnostic runs and every later run print all five. A later miss can be read from that line.

## Decisions and trade-offs

### Decided autonomously

Question: is the failing interval WebDriver observer delay, or production work after `readGame`? Chosen: production work after `readGame`, specifically the `lexPgn` await plus synchronous parse and the full-tree React render. The observer stamps the attribute mutation in the page. Rejected: treating the 50 ms driver poll as the interval. It is not in the subtraction. Rejected: raising 1,000 ms or retrying the scenario until it passes. The finding and d-20260925-11 forbid both. Reversal: a trace that shows `observedAt` moving without an attribute mutation.

Question: does the 1,000 ms ceiling cover the `lexPgn` await? Chosen: no. d-20260925-11 names main-thread apply after the read, and the harness already subtracts `readGame` because that native wait is not main-thread apply. `lexPgn` is the same kind of wait and is currently inside the ceiling only because `parsePGN` awaits it after the hook. Rejected: keeping one wall-clock sum, which fails the gate when the backend lexer waits on a loaded host even if the renderer publish is cheap. Rejected: a second 1,000 ms ceiling whose sum with main-thread time may reach 2,000 ms. The poll check still includes the measured lex wait, and an idle run whose lex wait itself exceeds 1,000 ms stops the phase. Reversal: new evidence that a user-visible freshness stall is dominated by lexer CPU on an idle machine and still passes the idle stop.

Question: where does the heavy tree walk leave the freshness commit? Chosen: out of the committing render, for every mounted consumer named under Publication ordering, rebuilt on the next turn, without a persisted flag and without moving `innerParsePGN` to Rust. Rejected: parsing the repertoire in Rust or a worker in this slice. That reopens the chess-tree and IPC boundary for a cost this plan has not shown is required once the render walks are off the commit. Rejected: deferring the debounced session write. It is already outside the interval. Reversal: an idle diagnostic whose `applicationMs` is already above 1,000, or an idle `verify:app` whose `mainThreadMs` is still above 1,000 after the walks are deferred.

Question: when is the split measured relative to the publication change? Chosen: two idle diagnostic runs print the five segments on the unchanged publication path before any walk is deferred. Rejected: measuring only after the deferral, which cannot show whether the original interval was lexer wait, store application, or the commit. The 1,000 ms pass/fail still applies to `mainThreadMs` after the publication change, and to the native wedge. It is not applied to excuse or fail those two diagnostic runs, except the `applicationMs` stop above.

## Risks / open questions

An idle diagnostic can show `applicationMs` above 1,000 before any deferral. The phase stops red and does not raise the constant or move the parser. An idle run after the deferral can still show `mainThreadMs` above 1,000 for the same reason. Both returns are the reversal of the third decision above.

Preemption during the synchronous burst still counts toward `mainThreadMs`. The plan does not claim a load-average-30 guarantee beyond making that burst the parse plus a cheap commit.

`getPGN` and the eval walk stay correct on the following turn. A one-turn stale panel must not be selectable as the new game's move.
