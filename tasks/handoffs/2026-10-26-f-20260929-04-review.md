## Approach

### O1 — actual open failure ends the waiting acquisition

Preserve failure origin through the existing manager, customizer and error-handler boundary. A failure from native SQLite establishment or its binding-lifetime setup reaches the waiting caller promptly after observation, without consuming a further pool timeout. Connection customization and validation failures retain the existing ordinary retry budget, because they include healthy contention that can recover within the same acquisition. A worker admission/predecessor outcome cannot become another caller's terminal result. Every caller still observes its own cancellation, predecessor and identity checks before returning, and a healthy connection available at its availability observation takes precedence over cached failure. Preserve concrete error provenance and existing bound-refusal classification without inferring OS codes or retryability from diagnostic text. No production deadline changes and no claim that every open failure is permanently unrecoverable. Permanent customization failures can still consume the existing ordinary budget, this plan does not claim promptness for that separate phase.

### O2 — one contextual diagnostic per failure episode

Use the existing pool-owned state to report repeated failed setup attempts once until successful establishment ends the episode. The diagnostic identifies the bound database unambiguously even when two databases share a leaf name. A later failure after successful recovery is reportable again. Failed acquisition still returns an error, never an empty success. Native diagnostic details stay native and existing renderer-safe error categories and payload protection remain intact.

### O3 — healthy recovery and ownership remain independent

Keep the ordinary30second establishment and SQLite busy budgets, lazy pool construction, healthy contention and per-caller cancellation semantics. Both reader-lock waiting and writer-lock customization failure must recover for the same waiting caller after release. Preserve r2d2's existing bounded pool/scheduler ownership and recovery backoff rather than adding a second retry controller, registry or global logger. This change does not claim to stop r2d2 background retries. Those existing owned retries can recover the pool after a transient failure. Successful recovery clears stale failure so a later healthy caller succeeds. Availability and failure observations must have a coherent rule, with an actually available connection preferred at the caller's observation, without promising an atomic ordering across r2d2's separate AcquireEvent and connection-publication steps. A failure from one worker cannot leak its admission outcome into another caller. Existing retirement still owns cancellation, connection drainage, worker ownership and binding lifetime.

### O4 — proof at the real pool boundary

Real repository/VFS identity refusal and a separate real non-identity native establishment failure must each return the correct concrete error under the unchanged production pool budget before that budget expires, with classification and cleanup assertions intact. The non-identity witness must prove an unchanged identity or a zero refusal counter as appropriate to its real input and correct native-open error provenance, so a counter-only fast path cannot satisfy it. Prove diagnostic count/context/reset through the production handler and existing capture facility. Prove delayed healthy establishment, reader-lock setup wait, and an actual writer-lock customization failure followed by successful recovery of that same waiting caller after release. Cover transient recovery, available-connection precedence and caller-specific predecessor/cancellation behavior. Keep platform-portable witnesses where supported and name Unix-only limits. New regression assertions stay while only the production behavior is reversed with unique-context Git hunks, producing semantic failures for both prompt-open cases, deduplication and customization-retry preservation, followed by exact restoration and green. Do not count a compile error as a semantic negative control. No host-pressure diagnosis, faster-host promise or cross-worker log capture is claimed without measurement.
