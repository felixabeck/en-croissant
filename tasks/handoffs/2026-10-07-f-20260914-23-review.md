**`kill_engine` sequence**

1. Construct and validate `(tab, engine)`; invalid input returns `Err`.
2. Call `get_exact`, consulting only `actors`.
3. If no published actor exists, return `Ok(())` immediately—even if an admission or pending actor exists.
4. Otherwise capture the published actor’s `generation` and call `terminate_exact`.
5. Under `registration` and `admission_coordination`, `terminate_exact` marks that exact published generation cancelled and cancels any admission with **that same generation**.
6. Acquire the per-key lifecycle lock and re-read `actors`.
7. If the entry disappeared or now has a different generation, return `Ok(())` without terminating the replacement.
8. Otherwise mark cancellation again, await actor termination, remove the actor entry even on failure, and return the termination result.
9. `kill_engine` propagates that error or returns `Ok(())`.

The command’s success condition is literally:

```rust
if let Some(process) = state.engine_supervisor.get_exact(&key) {
    state
        .engine_supervisor
        .terminate_exact(&key, process.generation)
        .await?;
}
Ok(())
```

`kill_engine` itself does **not** consult `admissions`, `pending_actors`, `retired`, `retired_executables`, `retired_binaries`, or the native operation registry’s `reads`. Its published-actor branch indirectly consults `admissions` and lifecycle `locks`; neither that branch nor `terminate_exact` consults `pending_actors` or the three retirement sets.

**Meaning of successful returns**

| State | `kill_engine` | `kill_engines` |
|---|---|---|
| Published actor | Captured actor generation was terminated successfully, or was absent/replaced at the locked recheck; its cancelled publication is blocked. | Matching tab actors are drained; returned report-analysis ids also receive exact termination when published. |
| Spawned, unpublished pending actor | No cleanup or cancellation guarantee for that pending generation; it can still publish if its admission remains valid. | Matching tab pending entries are awaited through the shared termination task; this is broader than the report loop, which checks published actors under `"analysis"` keys. |
| Reserved, not yet spawned | Reservation is untouched when no actor exists; a different reservation alongside an existing actor is also untouched. | Matching tab admissions are cancelled under the barrier, so those reservations cannot subsequently publish, although a child still spawning may require later rejection cleanup. |

For `kill_engines`, the quoted success condition is `if failures.is_empty() { Ok(()) }`; operation-registry/key errors can also return early. It does not seal the tab or create a tombstone: fresh admissions after its cancellation pass can still publish. Unrelated tabs remain eligible. Report-operation cancellation is not an await of every unpublished report actor.

## Approach

### O1 — Cancel the reservation that is already stored

Quotes the mandate: "When `prepare_engine_search` has reserved generation G2 but not yet published it, Kill Engine returns success" and "a cancel must reach work admitted before it".

`kill_engine` keeps the signature `(engine, tab) -> Result<(), Error>`. No Specta field, no binding, no renderer change.

Under the same `registration` plus `admission_coordination` barrier that publication uses, and without waiting for the per-key lifecycle lock, Kill flags the admission currently stored for that exact `EngineKey`, whether or not `prepared` is still true and whether or not `actors` holds a different generation. The flag is the existing `AtomicBool` on that admission. Kill does not call `cancel_admission_exact`'s remove. The entry stays so a later consume of that same generation can see the flag (P4, P5, P9).

Kill then clears `prepared` on that entry so the cancelled reservation does not keep counting toward `MAX_PENDING_ENGINE_SEARCHES` (P11).

`consume_engine_search` checks that flag before the `prepared` / identity mismatch and before treating a generation mismatch as expiry. When the stored entry's generation is the requested one and the flag is set, consume returns `Error::Cancellation`. A missing entry, or a stored entry of a different generation, stays the existing `Conflict` (tab close, supersession, and a generation that was never reserved).

Failure semantics: flagging a reservation is not itself an error. Kill returns `Ok(())` when there is nothing to terminate and the flag is set, including when no admission and no actor exist.

Ownership: the supervisor owns the flag. `chess.rs` does not reimplement the barrier.

Integration boundary: the IPC command and its success type stay. `get_best_moves_core` is unchanged; it already surfaces consume's error.

Verification: V1, V2.

### O2 — Terminate what is already tracked, and do not wait for a spawn that has not started

Quotes the mandate: G2 must not "publish and run", and the open question's alternative "wait for publication and then terminate".

After the barrier in O1 is released, Kill awaits cleanup for that same key:

* The published actor captured under the barrier is terminated with the existing `terminate_exact` for its actor generation. A generation that appears only after the snapshot is not Kill's target, matching today's replace recheck (P7).
* Every pending actor whose `key` matches and whose generation was already in `pending_actors` under that barrier is awaited through `PendingActor::terminate` (the shared task, `d-20261006-19`). Kill does not call `EngineActor::terminate` a second time.

A reservation that has been flagged and has not yet reached `track_pending_actor` has no child to await (P8). Publication's existing `reject_actor` reaps a child that is spawned afterwards, because O1's flag fails the publication check (P6). Kill does not block on spawn, executable resolution, or a future publication.

`terminate_exact`, `release_generation`, and `stop_search` are not modified. `d-20261006-18` stands for those functions. Their pending-actor behavior stays as it is today.

Failure semantics: a published termination error and a pending termination error are both failures of Kill. One failure is returned as that error (`Error::Shared` for a pending failure, unchanged). When both fail, `Error::with_cleanup` keeps the published failure as the primary and the pending failure as the cleanup; neither becomes `Ok(())`. Locks are not held across those awaits. Lock order stays registration, then admission coordination, then the lifecycle lock inside the existing `terminate_exact`.

Ownership: the in-flight publisher remains the owner of a child that is not yet in `pending_actors`. Kill owns actors that are already in `actors` or `pending_actors` at the barrier.

Verification: V3, V4, V5.

### O3 — A later search on the same key still starts

Quotes the mandate's open question only for the generation already reserved. A tombstone is not in the mandate and is ruled out in the threat model.

The next `prepare_engine_search` for that key still admits. `admit` replaces the cancelled entry. Kill does not seal the key, the engine id, or the tab.

A different key's admission, published actor, and pending actor are untouched.

Verification: V6, V7.

## Decisions and trade-offs

### D1 — Cancel the reserved generation; do not wait for it to publish

Chosen: O1. Rejected: block Kill until the in-flight search publishes, then `terminate_exact` the new actor. That wait includes executable resolution and spawn while the per-key lifecycle lock is already held by the search (P8), so Kill would queue behind the work it is trying to stop, and it would need a rendezvous that does not exist. `d-20260901-18` already rejected an unbounded wait on engine teardown. Flagging the admission uses the publication check that already refuses a cancelled generation (P6).

### D2 — Await pending actors from Kill only

Chosen: O2's pending await on the kill path. Rejected: adding that await inside `terminate_exact`. The reversal line of `d-20261006-18` names that widening as future work under this finding; doing it would also change `release_generation` and every exact stop, which this mandate does not. A pending generation also differs from the published generation whenever a warm actor is up and a new reservation exists, so `terminate_exact` of the published generation would not see it (P7).

### D3 — The in-flight search of the killed generation is `Error::Cancellation`

Chosen: O1's consume order and the kept map entry. Rejected: calling `cancel_admission_exact` as it stands. Removal makes the following consume return `Conflict` ("invalid or expired"), and the renderer shows every error whose message is not exactly `Cancellation` (P9). The user pressed Kill and would be told the search failed. This is the failure semantics of the stop the mandate requires, not a second product behavior: analysis already treats `Cancellation` as silence (`d-20260830-05`, cited by `errors.ts`).

A second `EngineActor::terminate` on one actor is not a waiter for the first: the caller that loses the task handle can observe `EngineDisconnected` and return `Ok(())`, which drops the owner's failure (`d-20261006-19`'s rejected shape). Pending actors stay on their existing shared task. This plan does not extend that sharing to registered actors (`f-20261001-14`).

`publish_admitted_locked` today clones the previous actor before it takes `registration`. That read moves under the `registration` lock it already takes, so a Kill that already removed the entry is visible, and the lock is dropped before the terminate await.

Failure semantics: a published termination error and a pending termination error are both failures of Kill when Kill owns those calls. One failure is returned as that error (`Error::Shared` for a pending failure, unchanged). When both owned calls fail, `Error::with_cleanup` keeps the published failure as the primary and the pending failure as the cleanup; neither becomes `Ok(())`. `with_cleanup(primary, Ok(()))` returns the primary unchanged. Locks are not held across those awaits. Lock order for the barrier stays registration, then admission coordination. Kill does not take the lifecycle lock.

Known limit, bounded by the existing kill reap rather than by spawn: if another owner has already removed the published entry before Kill's barrier, Kill does not await that owner's reap and does not return that owner's error. During a fresh launch the published entry is still in the map, so this limit is not the reservation window.

Ownership: Kill owns the published entry it removed and the pending entries it snapshotted. The publisher owns an untracked child. `chess.rs` stays a thin wrapper.

Verification: V3, V4, V5, V8.

### O3 — A later search on the same key still starts

Quotes the mandate's open question only for the generation already reserved. A tombstone is not in the mandate and is ruled out in the threat model.

The next `prepare_engine_search` for that key still admits. `admit` replaces the cancelled entry. Kill does not seal the key, the engine id, or the tab.

A different key's admission, published actor, and pending actor are untouched.

Verification: V6, V7.

## Decisions and trade-offs

### D1 — Cancel the reserved generation; do not wait for it to publish

Chosen: O1 plus O2's off-lock reap of an actor already in the map. Rejected: block Kill until the in-flight search publishes, then terminate the new actor. Rejected as well: calling `terminate_exact` as it stands after the barrier. That call waits on the lifecycle lock the fresh launch already holds across resolution and spawn (P8), so the published actor keeps running until that spawn unwinds. `d-20260901-18` bounds kill reap and rejected an unbounded wait. Flagging the admission uses the publication check that already refuses a cancelled generation (P6).

### D2 — Await pending actors from Kill only

Chosen: O2's pending await on the kill path. Rejected: adding that await inside `terminate_exact`. The reversal line of `d-20261006-18` names that widening as future work under this finding; doing it would also change `release_generation` and every exact stop, which this mandate does not. A pending generation also differs from the published generation whenever a warm actor is up and a new reservation exists, so `terminate_exact` of the published generation would not see it (P7). The guard in O2 is not that drain: `terminate_exact` still does not read `pending_actors`.

### D3 — The in-flight search of the killed generation is `Error::Cancellation`

Chosen: O1's consume order and the kept map entry. Rejected: calling `cancel_admission_exact` as it stands. Removal makes the following consume return `Conflict` ("invalid or expired"), and the renderer shows every error whose message is not exactly `Cancellation` (P9). The user pressed Kill and would be told the search failed. Analysis already drops that message in `errorUnlessCancelled`. `d-20260830-05` is the destructive-operation category decision and is not the authority for this silence.

### D4 — One `EngineActor::terminate` per published actor

Chosen: O2's remove-to-own guard at every published-actor terminate site in the supervisor. Rejected: a second direct `EngineActor::terminate` racing Kill. Rejected: giving registered actors the pending shared-termination task. `d-20261006-19` rejected independent terminate calls because the loser can return `Ok(())`, and it explicitly did not extend result sharing to registered actors.

## Decided autonomously

The adopting session records these four through `findings.py record-decision` before implementation. Question, chosen, rejected, reason:

* **D1 question:** Does Kill cancel an already-reserved generation, or wait until that generation is published and then terminate it?
  * **Chosen:** cancel under the publication barrier (O1) and reap a published actor without taking the lifecycle lock (O2). The reserved generation never publishes and never reaches `go`.
  * **Rejected:** wait for publication, then terminate. Also rejected: calling unchanged `terminate_exact`, which waits on the lifecycle lock held across spawn.
  * **Reason:** the publication check already refuses a flagged admission, and the lifecycle wait leaves the published engine running for the whole fresh launch. Reversal path: make Kill await the in-flight `start_interactive_search` before returning.

* **D2 question:** Does this finding add a pending-actor await to `terminate_exact`?
  * **Chosen:** no. Kill awaits pending actors for its key itself. `terminate_exact` stays published-generation only (`d-20261006-18`).
  * **Rejected:** widening `terminate_exact` so every exact caller drains a matching pending actor.
  * **Reason:** the reserved generation is often not the published generation, and the other callers are outside this mandate. Reversal path: move the pending await into `terminate_exact` and delete Kill's extra await.

* **D3 question:** After Kill flags a reservation, what does a later `consume_engine_search` of that generation return?
  * **Chosen:** `Error::Cancellation`. The entry stays, `prepared` is cleared, and the check order is generation, then the flag, then identity and `prepared`.
  * **Rejected:** the current remove-and-`Conflict` result of `cancel_admission_exact`.
  * **Reason:** `Conflict` is shown as an analysis error after Kill; `errorUnlessCancelled` drops only the message `Cancellation`. Reversal path: remove the entry and accept the `Conflict` toast.

* **D4 question:** Who calls `EngineActor::terminate` on a published actor once Kill no longer takes the lifecycle lock?
  * **Chosen:** only the caller that removed that `actors` entry, at every published-actor terminate site in the supervisor.
  * **Rejected:** a second direct `terminate` on the same actor, and extending pending-actor result sharing to registered actors.
  * **Reason:** a second `terminate` can return `Ok(())` and hide the owner's failure. Reversal path: shared termination for registered actors under `f-20261001-14`.

## Risks / open questions

* A child spawned after the barrier snapshot and before `track_pending_actor` is reaped by `reject_actor`, not by Kill's await. Kill has no tracked child for that generation. The search still cannot publish. V2 pins that late child; V4 pins a child that was already tracked.
* When both an owned published terminate and an owned pending terminate fail, `Error::with_cleanup` becomes `Error::OperationAndCleanup`. Its `Display` and serialized message are `Operation failed; temporary cleanup also failed`, category `operation-and-cleanup`. The renderer shows that fixed message, not the primary error's `Display`. Both causes stay in the variant fields and in `diagnostic()`. `with_cleanup(primary, Ok(()))` returns the primary unchanged, so a lone `Cancellation` stays `Cancellation`. No new IPC shape.
* If another owner has already removed the published entry, Kill returns without awaiting that reap. The reap is still bounded by the existing kill deadline (`d-20260901-18`). Fresh launch does not remove the published entry, so V8 is outside this limit.
* Cancelled entries that are not yet replaced still occupy the key's single admission slot. They do not count toward the 256 cap once `prepared` is cleared. Tab close, retirement, and shutdown keep their existing admission cancellation.

## Threat model and non-goals

Written in round 1 and frozen with the MANDATE.

Accidental interleaving is in scope. The Kill button and an in-flight `prepare_engine_search` / `get_best_moves_core` are separate async commands. The user can press Kill after a generation has been reserved and before that generation is published. A second command can also hold the per-key lifecycle lock across spawn while Kill runs. No hostile engine, forged generation, or cross-key attacker is in scope. Input validation on `EngineKey` stays as it is.

Environments that count: the production supervisor on the existing Linux runtime, with the same bounded kill/reap deadlines already used for a published actor (`d-20260901-18`). The proof is Rust tests in this crate. There is no browser surface and no IPC signature change.

Known limit, not a new mechanism: an admission inserted only after Kill has released the publication barrier is a later search. Kill does not tombstone the key. That later-admission window is the same class as `f-20260915-07` (tab close does not record a closed-tab marker) and stays that finding's. The mandate's G2 is a generation already reserved when Kill crosses the barrier.

Out of scope: `stop_engine` (the handled unscoped-stop entry), `kill_engines` / `terminate_tab`, report-analysis tickets, game-engine keys, a dropped `get_best_moves` after publication (`f-20260915-06`), spawn after `terminate_all` (`f-20261006-04`), and sharing termination results for registered actors (`f-20261001-14`, excluded by `d-20261006-19`).

## Approach

### O1 — Cancel the reservation that is already stored

Quotes the mandate: "When `prepare_engine_search` has reserved generation G2 but not yet published it, Kill Engine returns success" and "a cancel must reach work admitted before it".

`kill_engine` keeps the signature `(engine, tab) -> Result<(), Error>`. No Specta field, no binding, no renderer change.

Under the same `registration` plus `admission_coordination` barrier that publication uses, and without waiting for the per-key lifecycle lock, Kill flags the admission currently stored for that exact `EngineKey`, whether or not `prepared` is still true and whether or not `actors` holds a different generation. The flag is the existing `AtomicBool` on that admission. Kill does not call `cancel_admission_exact`'s remove. The entry stays so a later consume of that same generation can see the flag (P4, P5, P9).

Kill then clears `prepared` on that entry so the cancelled reservation does not keep counting toward `MAX_PENDING_ENGINE_SEARCHES` (P11).

`consume_engine_search` keeps today's generation test first. A missing entry, or a stored entry of a different generation, stays `Error::Conflict` ("invalid or expired"): tab close, supersession, and a generation that was never reserved. When the stored generation is the requested one, consume checks the flag next and returns `Error::Cancellation` if it is set. Only a matching generation whose flag is clear then checks engine id, executable, and `prepared`, and a mismatch there stays `Error::Conflict` ("does not match the request"). Clearing `prepared` on a killed reservation must not turn that generation into the mismatch `Conflict`.

Failure semantics: flagging a reservation is not itself an error. Kill returns `Ok(())` when there is nothing to terminate and the flag is set, including when no admission and no actor exist.

Ownership: the supervisor owns the flag. `chess.rs` does not reimplement the barrier.

Integration boundary: the IPC command and its success type stay. `get_best_moves_core` is unchanged; it already surfaces consume's error.

Verification: V1, V2.

### O2 — Terminate what is already tracked, without queueing behind spawn

Quotes the mandate: G2 must not "publish and run", and the open question's alternative "wait for publication and then terminate". The threat model already includes a second command holding the per-key lifecycle lock across spawn while Kill runs.

Kill does not call `terminate_exact`. That function acquires the per-key lifecycle lock before it looks at `actors`, and `start_interactive_search` holds the same lock from before executable resolution through `EngineActor::spawn` and publication (P8). Calling it would leave a published actor alive until that spawn unwinds. Flagging the reservation does not release the lock.

Under the O1 barrier, before any await and without the lifecycle lock, Kill does three things when `actors` holds this key:

* `mark_cancelled` on that `SupervisedEngine`, which sets the publication flag and the bound search flag. `EngineActor::terminate` cancels only the actor's interrupt. Without `mark_cancelled`, a line already dequeued can still `try_publish`, and `EngineDisconnected` stays a failure instead of `Cancellation`.
* Hand that actor to the existing pending-actor set for its generation, and remove it from `actors`. `drain_matching` scans both sets. An entry removed from both before the reap returns is invisible to `terminate_all` and `terminate_tab`, so shutdown can exit while the child is still quitting. The pending map is keyed by generation. Publication already removed that generation's entry before the actor sat in `actors` (the remove inside P6's publish range). The handoff inserts only when that slot is empty, and it builds the entry from the published `SupervisedEngine`: the admission is already gone, so this is not `track_pending_actor`. If this generation is already pending, the caller joins that entry and does not replace it. The pending entry stays until the shared termination task finishes and removes it.
* Remember pending actors whose `key` already matched.

After the barrier is released, Kill awaits each of those pending entries through `PendingActor::terminate`. That is the one shared task (`d-20261006-19`): one `EngineActor::terminate`, and every joiner sees the same result. Kill does not call `EngineActor::terminate` itself. Dropping Kill's future does not cancel that task. A later drain still finds the pending entry and awaits it.

When the barrier finds no published entry, Kill does not acquire the lifecycle lock. It still joins a pending reap already started for this key. A fresh launch that holds the lifecycle lock cannot delay Kill's return.

Kill has no tracked child to await for a reservation that has not reached `track_pending_actor`. The in-flight publisher owns an already-spawned untracked child and reaps it with the existing `reject_actor` once publication sees the flag (P6, P8). Kill does not wait for executable resolution, spawn, or a future publication.

`terminate_exact` gains no scan of other generations' pending actors. `d-20261006-18` stands for that. `release_generation` and `stop_search` keep their generation choice. What changes at every direct `EngineActor::terminate` of a published actor — `terminate_exact`, `stop_or_release`, the previous-actor cleanup inside `publish_admitted_locked`, and the failure arms inside `start_interactive_search` — is the same handoff: `mark_cancelled`, move that generation from `actors` into the pending set if it is not already there, drop `registration` before any await, then join `PendingActor::terminate`. A caller that finds the generation already pending only joins. Nobody calls `EngineActor::terminate` except that shared task. `publish_admitted_locked` today clones the previous actor before it takes `registration`. That read moves under the `registration` lock it already takes, so a handoff that already ran is visible.

This is not the registered-actor result sharing `f-20261001-14` asks for and `d-20261006-19` left out. A generation that is not being reaped stays in `actors`. The pending set is only the reap of an actor that has left `actors`. There is no remaining direct `EngineActor::terminate` of a published actor. `d-20261006-17` still holds for a generation that remains registered: drains reach it in `actors`. During this reap they reach it in `pending_actors`, which those drains already await.

Failure semantics: each joined pending failure is `Error::Shared` carrying the original failure, unchanged. A published-generation failure and another pending failure of the same Kill are both returned. When both fail, `Error::with_cleanup` keeps the published generation's failure as the primary and the other as the cleanup; neither becomes `Ok(())`. `with_cleanup(primary, Ok(()))` returns the primary unchanged. Locks are not held across those awaits. Lock order for the barrier stays registration, then admission coordination. Kill does not take the lifecycle lock.

Ownership: the pending shared task owns the process. Kill and any drain that finds the entry await that task. The publisher owns an untracked child. `chess.rs` stays a thin wrapper.

Verification: V3, V4, V5, V8, V9.

### O3 — A later search on the same key still starts

Quotes the mandate's open question only for the generation already reserved. A tombstone is not in the mandate and is ruled out in the threat model.

The next `prepare_engine_search` for that key still admits. `admit` replaces the cancelled entry. Kill does not seal the key, the engine id, or the tab.

A different key's admission, published actor, and pending actor are untouched.

Verification: V6, V7.

## Decisions and trade-offs

### D1 — Cancel the reserved generation; do not wait for it to publish

Chosen: O1 plus O2's off-lock reap of an actor already in the map. Rejected: block Kill until the in-flight search publishes, then terminate the new actor. Rejected as well: calling `terminate_exact` as it stands after the barrier. That call waits on the lifecycle lock the fresh launch already holds across resolution and spawn (P8), so the published actor keeps running until that spawn unwinds. `d-20260901-18` bounds kill reap and rejected an unbounded wait. Flagging the admission uses the publication check that already refuses a cancelled generation (P6).

### D2 — Do not scan other generations' pending actors from `terminate_exact`

Chosen: O2. Kill joins every pending actor whose key matches, including the published generation after the handoff. `terminate_exact` uses that same handoff for the generation it is already terminating and still does not scan a different generation's pending entry. Rejected: adding that other-generation scan inside `terminate_exact`. The reversal line of `d-20261006-18` names that widening as future work under this finding; doing it would also change `release_generation` and every exact stop beyond the handoff this mandate needs. A pending generation also differs from the published generation whenever a warm actor is up and a new reservation exists (P7). `d-20261006-18` stands for that other-generation scan.

### D3 — The in-flight search of the killed generation is `Error::Cancellation`

Chosen: O1's consume order and the kept map entry. Rejected: calling `cancel_admission_exact` as it stands. Removal makes the following consume return `Conflict` ("invalid or expired"), and the renderer shows every error whose message is not exactly `Cancellation` (P9). The user pressed Kill and would be told the search failed. Analysis already drops that message in `errorUnlessCancelled`. `d-20260830-05` is the destructive-operation category decision and is not the authority for this silence.

### D4 — The published actor's reap is a pending entry the drains already await

Chosen: O2's handoff. `mark_cancelled` first, then the existing pending set until the shared task finishes. Rejected: remove the `actors` entry and call `EngineActor::terminate` with no supervisor entry left. `drain_matching` would not see the child, and a dropped owner would not leave a drain anything to await. Rejected: a second direct `EngineActor::terminate`. Rejected: sharing termination results for an actor that stays in `actors` (`f-20261001-14`, `d-20261006-19`).

## Decided autonomously

The adopting session records these four through `findings.py record-decision` before implementation. Question, chosen, rejected, reason:

* **D1 question:** Does Kill cancel an already-reserved generation, or wait until that generation is published and then terminate it?
  * **Chosen:** cancel under the publication barrier (O1) and reap a published actor without taking the lifecycle lock (O2). The reserved generation never publishes and never reaches `go`.
  * **Rejected:** wait for publication, then terminate. Also rejected: calling unchanged `terminate_exact`, which waits on the lifecycle lock held across spawn.
  * **Reason:** the publication check already refuses a flagged admission, and the lifecycle wait leaves the published engine running for the whole fresh launch. Reversal path: make Kill await the in-flight `start_interactive_search` before returning.

* **D2 question:** Does this finding add a pending-actor await to `terminate_exact`?
  * **Chosen:** no scan of other generations. Kill joins pending actors for its key. `terminate_exact` joins only the pending reap of the generation it is already terminating (`d-20261006-18`).
  * **Rejected:** widening `terminate_exact` so every exact caller drains a pending actor of a different generation.
  * **Reason:** the reserved generation is often not the published generation, and draining it from every exact caller is outside this mandate. Reversal path: move that other-generation await into `terminate_exact` and delete Kill's extra await.

* **D3 question:** After Kill flags a reservation, what does a later `consume_engine_search` of that generation return?
  * **Chosen:** `Error::Cancellation`. The entry stays, `prepared` is cleared, and the check order is generation, then the flag, then identity and `prepared`.
  * **Rejected:** the current remove-and-`Conflict` result of `cancel_admission_exact`.
  * **Reason:** `Conflict` is shown as an analysis error after Kill; `errorUnlessCancelled` drops only the message `Cancellation`. Reversal path: remove the entry and accept the `Conflict` toast.

* **D4 question:** Once Kill no longer takes the lifecycle lock, where does a published actor live until its reap finishes, and who calls `EngineActor::terminate`?
  * **Chosen:** `mark_cancelled`, then the existing pending-actor entry. The shared task is the only `EngineActor::terminate`. Drains that already scan `pending_actors` await it.
  * **Rejected:** delete the `actors` entry and terminate with nothing left for `drain_matching`. Also rejected: a second direct `terminate`, and result sharing for an actor that stays registered.
  * **Reason:** `drain_matching` only sees `actors` and `pending_actors`, and `d-20261006-16` makes those drains the owner shutdown reaches. A second `terminate` can return `Ok(())`. Reversal path: shared termination for actors that remain in `actors`, under `f-20261001-14`.

## Risks / open questions

* A child spawned after the barrier snapshot and before `track_pending_actor` is reaped by `reject_actor`, not by Kill's await. Kill has no tracked child for that generation. The search still cannot publish. V2 pins that late child; V4 pins a child that was already tracked.
* When both an owned published terminate and an owned pending terminate fail, `Error::with_cleanup` becomes `Error::OperationAndCleanup`. Its `Display` and serialized message are `Operation failed; temporary cleanup also failed`, category `operation-and-cleanup`. The renderer shows that fixed message, not the primary error's `Display`. Both causes stay in the variant fields and in `diagnostic()`. `with_cleanup(primary, Ok(()))` returns the primary unchanged, so a lone `Cancellation` stays `Cancellation`. No new IPC shape.
* The published generation is absent from `actors` during the reap and present in `pending_actors` until the shared task finishes. `get_exact` is therefore `None` before Kill returns. Shutdown still awaits the reap, because it scans `pending_actors`. V9 pins that.
* Cancelled entries that are not yet replaced still occupy the key's single admission slot. They do not count toward the 256 cap once `prepared` is cleared. Tab close, retirement, and shutdown keep their existing admission cancellation.

## Not part of this task

* `stop_engine`'s choice of which generation to stop, `release_engine_search`, `kill_engines`, `terminate_tab`, and `retire_engine`. Their published-actor `terminate` calls use the same handoff so they cannot pair a second `EngineActor::terminate` with Kill, and so a reap already in `pending_actors` stays visible to the drains. Which generation they select, and the pending scan those drains already have, stay as they are.
* A closed-tab marker (`f-20260915-07`) or any tombstone that refuses an admission created after Kill returns.
* Frontend copy, the Kill button's enablement order, bindings, capabilities.
* `f-20260915-06`, `f-20261006-04`, `f-20261001-14`, and the other open `engine-uci` entries. They stay at their filed tiers.

## Approach

### O1 — Cancel the reservation that is already stored

Quotes the mandate: "When `prepare_engine_search` has reserved generation G2 but not yet published it, Kill Engine returns success" and "a cancel must reach work admitted before it".

`kill_engine` keeps the signature `(engine, tab) -> Result<(), Error>`. No Specta field, no binding, no renderer change.

Under the same `registration` plus `admission_coordination` barrier that publication uses, and without waiting for the per-key lifecycle lock, Kill flags the admission currently stored for that exact `EngineKey`, whether or not `prepared` is still true and whether or not `actors` holds a different generation. The flag is the existing `AtomicBool` on that admission. Kill does not call `cancel_admission_exact`'s remove. The entry stays so a later consume of that same generation can see the flag (P4, P5, P9).

Kill then clears `prepared` on that entry so the cancelled reservation does not keep counting toward `MAX_PENDING_ENGINE_SEARCHES` (P11).

`consume_engine_search` keeps today's generation test first. A missing entry, or a stored entry of a different generation, stays `Error::Conflict` ("invalid or expired"): tab close, supersession, and a generation that was never reserved. When the stored generation is the requested one, consume checks the flag next and returns `Error::Cancellation` if it is set. Only a matching generation whose flag is clear then checks engine id, executable, and `prepared`, and a mismatch there stays `Error::Conflict` ("does not match the request"). Clearing `prepared` on a killed reservation must not turn that generation into the mismatch `Conflict`.

Failure semantics: flagging a reservation is not itself an error. Kill returns `Ok(())` when there is nothing to terminate and the flag is set, including when no admission and no actor exist.

Ownership: the supervisor owns the flag. `chess.rs` does not reimplement the barrier.

Integration boundary: the IPC command and its success type stay. `get_best_moves_core` is unchanged; it already surfaces consume's error.

Verification: V1, V2.

### O2 — Terminate what is already tracked, without queueing behind spawn

Quotes the mandate: G2 must not "publish and run", and the open question's alternative "wait for publication and then terminate". The threat model already includes a second command holding the per-key lifecycle lock across spawn while Kill runs.

Kill does not call `terminate_exact`. That function acquires the per-key lifecycle lock before it looks at `actors`, and `start_interactive_search` holds the same lock from before executable resolution through `EngineActor::spawn` and publication (P8). Calling it would leave a published actor alive until that spawn unwinds. Flagging the reservation does not release the lock.

Under the O1 barrier, before any await and without the lifecycle lock, Kill does three things when `actors` holds this key:

* `mark_cancelled` on that `SupervisedEngine`, which sets the publication flag and the bound search flag. `EngineActor::terminate` cancels only the actor's interrupt. Without `mark_cancelled`, a line already dequeued can still `try_publish`, and `EngineDisconnected` stays a failure instead of `Cancellation`.
* Hand that actor to the existing pending-actor set for its generation, and remove it from `actors`. `drain_matching` scans both sets. An entry removed from both before the reap returns is invisible to `terminate_all` and `terminate_tab`, so shutdown can exit while the child is still quitting. The pending map is keyed by generation. Publication already removed that generation's entry before the actor sat in `actors` (the remove inside P6's publish range). The handoff inserts only when that slot is empty, and it builds the entry from the published `SupervisedEngine`: the admission is already gone, so this is not `track_pending_actor`. If this generation is already pending, the caller joins that entry and does not replace it. The pending entry stays until the shared termination task finishes and removes it.
* Remember pending actors whose `key` already matched.

After the barrier is released, Kill awaits each of those pending entries through `PendingActor::terminate`. That is the one shared task (`d-20261006-19`): one `EngineActor::terminate`, and every joiner sees the same result. Kill does not call `EngineActor::terminate` itself. Dropping Kill's future does not cancel that task. A later drain still finds the pending entry and awaits it.

When the barrier finds no published entry, Kill does not acquire the lifecycle lock. It still joins a pending reap already started for this key. A fresh launch that holds the lifecycle lock cannot delay Kill's return.

Kill has no tracked child to await for a reservation that has not reached `track_pending_actor`. The in-flight publisher owns an already-spawned untracked child and reaps it with the existing `reject_actor` once publication sees the flag (P6, P8). Kill does not wait for executable resolution, spawn, or a future publication.

`terminate_exact` gains no scan of other generations' pending actors. `d-20261006-18` stands for that. `release_generation` and `stop_search` keep their generation choice. What changes at every direct `EngineActor::terminate` of a published actor — `terminate_exact`, `stop_or_release`, the previous-actor cleanup inside `publish_admitted_locked`, and the failure arms inside `start_interactive_search` — is the same handoff: `mark_cancelled`, move that generation from `actors` into the pending set if it is not already there, drop `registration` before any await, then join `PendingActor::terminate`. A caller that finds the generation already pending only joins. Nobody calls `EngineActor::terminate` except that shared task. `publish_admitted_locked` today clones the previous actor before it takes `registration`. That read moves under the `registration` lock it already takes, so a handoff that already ran is visible.

This is not the registered-actor result sharing `f-20261001-14` asks for and `d-20261006-19` left out. A generation that is not being reaped stays in `actors`. The pending set is only the reap of an actor that has left `actors`. There is no remaining direct `EngineActor::terminate` of a published actor. `d-20261006-17` still holds for a generation that remains registered: drains reach it in `actors`. During this reap they reach it in `pending_actors`, which those drains already await.

Failure semantics: each joined pending failure is `Error::Shared` carrying the original failure, unchanged. A published-generation failure and another pending failure of the same Kill are both returned. When both fail, `Error::with_cleanup` keeps the published generation's failure as the primary and the other as the cleanup; neither becomes `Ok(())`. `with_cleanup(primary, Ok(()))` returns the primary unchanged. Locks are not held across those awaits. Lock order for the barrier stays registration, then admission coordination. Kill does not take the lifecycle lock.

Ownership: the pending shared task owns the process. Kill and any drain that finds the entry await that task. The publisher owns an untracked child. `chess.rs` stays a thin wrapper.

Verification: V3, V4, V5, V8, V9.

### O3 — A later search on the same key still starts

Quotes the mandate's open question only for the generation already reserved. A tombstone is not in the mandate and is ruled out in the threat model.

The next `prepare_engine_search` for that key still admits. `admit` replaces the cancelled entry. Kill does not seal the key, the engine id, or the tab.

A different key's admission, published actor, and pending actor are untouched.

Verification: V6, V7.

## Decisions and trade-offs

### D1 — Cancel the reserved generation; do not wait for it to publish

Chosen: O1 plus O2's off-lock reap of an actor already in the map. Rejected: block Kill until the in-flight search publishes, then terminate the new actor. Rejected as well: calling `terminate_exact` as it stands after the barrier. That call waits on the lifecycle lock the fresh launch already holds across resolution and spawn (P8), so the published actor keeps running until that spawn unwinds. `d-20260901-18` bounds kill reap and rejected an unbounded wait. Flagging the admission uses the publication check that already refuses a cancelled generation (P6).

### D2 — Do not scan other generations' pending actors from `terminate_exact`

Chosen: O2. Kill joins every pending actor whose key matches, including the published generation after the handoff. `terminate_exact` uses that same handoff for the generation it is already terminating and still does not scan a different generation's pending entry. Rejected: adding that other-generation scan inside `terminate_exact`. The reversal line of `d-20261006-18` names that widening as future work under this finding; doing it would also change `release_generation` and every exact stop beyond the handoff this mandate needs. A pending generation also differs from the published generation whenever a warm actor is up and a new reservation exists (P7). `d-20261006-18` stands for that other-generation scan.

### D3 — The in-flight search of the killed generation is `Error::Cancellation`

Chosen: O1's consume order and the kept map entry. Rejected: calling `cancel_admission_exact` as it stands. Removal makes the following consume return `Conflict` ("invalid or expired"), and the renderer shows every error whose message is not exactly `Cancellation` (P9). The user pressed Kill and would be told the search failed. Analysis already drops that message in `errorUnlessCancelled`. `d-20260830-05` is the destructive-operation category decision and is not the authority for this silence.

### D4 — The published actor's reap is a pending entry the drains already await

Chosen: O2's handoff. `mark_cancelled` first, then the existing pending set until the shared task finishes. Rejected: remove the `actors` entry and call `EngineActor::terminate` with no supervisor entry left. `drain_matching` would not see the child, and a dropped owner would not leave a drain anything to await. Rejected: a second direct `EngineActor::terminate`. Rejected: sharing termination results for an actor that stays in `actors` (`f-20261001-14`, `d-20261006-19`).

## Decided autonomously

The adopting session records these four through `findings.py record-decision` before implementation. Question, chosen, rejected, reason:

* **D1 question:** Does Kill cancel an already-reserved generation, or wait until that generation is published and then terminate it?
  * **Chosen:** cancel under the publication barrier (O1) and reap a published actor without taking the lifecycle lock (O2). The reserved generation never publishes and never reaches `go`.
  * **Rejected:** wait for publication, then terminate. Also rejected: calling unchanged `terminate_exact`, which waits on the lifecycle lock held across spawn.
  * **Reason:** the publication check already refuses a flagged admission, and the lifecycle wait leaves the published engine running for the whole fresh launch. Reversal path: make Kill await the in-flight `start_interactive_search` before returning.

* **D2 question:** Does this finding add a pending-actor await to `terminate_exact`?
  * **Chosen:** no scan of other generations. Kill joins pending actors for its key. `terminate_exact` joins only the pending reap of the generation it is already terminating (`d-20261006-18`).
  * **Rejected:** widening `terminate_exact` so every exact caller drains a pending actor of a different generation.
  * **Reason:** the reserved generation is often not the published generation, and draining it from every exact caller is outside this mandate. Reversal path: move that other-generation await into `terminate_exact` and delete Kill's extra await.

* **D3 question:** After Kill flags a reservation, what does a later `consume_engine_search` of that generation return?
  * **Chosen:** `Error::Cancellation`. The entry stays, `prepared` is cleared, and the check order is generation, then the flag, then identity and `prepared`.
  * **Rejected:** the current remove-and-`Conflict` result of `cancel_admission_exact`.
  * **Reason:** `Conflict` is shown as an analysis error after Kill; `errorUnlessCancelled` drops only the message `Cancellation`. Reversal path: remove the entry and accept the `Conflict` toast.

* **D4 question:** Once Kill no longer takes the lifecycle lock, where does a published actor live until its reap finishes, and who calls `EngineActor::terminate`?
  * **Chosen:** `mark_cancelled`, then the existing pending-actor entry. The shared task is the only `EngineActor::terminate`. Drains that already scan `pending_actors` await it.
  * **Rejected:** delete the `actors` entry and terminate with nothing left for `drain_matching`. Also rejected: a second direct `terminate`, and result sharing for an actor that stays registered.
  * **Reason:** `drain_matching` only sees `actors` and `pending_actors`, and `d-20261006-16` makes those drains the owner shutdown reaches. A second `terminate` can return `Ok(())`. Reversal path: shared termination for actors that remain in `actors`, under `f-20261001-14`.

## Risks / open questions

* A child spawned after the barrier snapshot and before `track_pending_actor` is reaped by `reject_actor`, not by Kill's await. Kill has no tracked child for that generation. The search still cannot publish. V2 pins that late child; V4 pins a child that was already tracked.
* When both an owned published terminate and an owned pending terminate fail, `Error::with_cleanup` becomes `Error::OperationAndCleanup`. Its `Display` and serialized message are `Operation failed; temporary cleanup also failed`, category `operation-and-cleanup`. The renderer shows that fixed message, not the primary error's `Display`. Both causes stay in the variant fields and in `diagnostic()`. `with_cleanup(primary, Ok(()))` returns the primary unchanged, so a lone `Cancellation` stays `Cancellation`. No new IPC shape.
* The published generation is absent from `actors` during the reap and present in `pending_actors` until the shared task finishes. `get_exact` is therefore `None` before Kill returns. Shutdown still awaits the reap, because it scans `pending_actors`. V9 pins that.
* Cancelled entries that are not yet replaced still occupy the key's single admission slot. They do not count toward the 256 cap once `prepared` is cleared. Tab close, retirement, and shutdown keep their existing admission cancellation.

## Not part of this task

* `stop_engine`'s choice of which generation to stop, `release_engine_search`, `kill_engines`, `terminate_tab`, and `retire_engine`. Their published-actor `terminate` calls use the same handoff so they cannot pair a second `EngineActor::terminate` with Kill, and so a reap already in `pending_actors` stays visible to the drains. Which generation they select, and the pending scan those drains already have, stay as they are.
* A closed-tab marker (`f-20260915-07`) or any tombstone that refuses an admission created after Kill returns.
* Frontend copy, the Kill button's enablement order, bindings, capabilities.
* `f-20260915-06`, `f-20261006-04`, `f-20261001-14`, and the other open `engine-uci` entries. They stay at their filed tiers.
