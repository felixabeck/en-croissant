# Plan: workspace file type editing (f-20260919-07)

## Goal

A workspace PGN's type (game, repertoire, tournament, puzzle, other) can be changed from the Files
page without renaming the file, and a rename that keeps the file's leaf no longer fails with an I/O
error. The Files page's file card regains the "Edit metadata" control that `d-20260919-12` removed
until this capability existed.

## MANDATE

Verbatim, `tasks/findings.md` f-20260919-07:

> * **Where:** `src-tauri/src/file_workspace.rs` (`rename_workspace_file_blocking`, the only writer of the
>   `.info` sidecar after creation), `src/bindings/generated.ts` (`renameWorkspaceFile`), and the
>   empty `EditModal` stub formerly in `src/components/files/Modals.tsx`.
> * **Defect:** upstream's Files page had an `EditModal` that changed a file's name **and its type**
>   (game, repertoire, tournament, puzzle, other). The audit commit `3afed031` replaced the plugin-fs
>   sidecar write with `rename_workspace_file(workspace, entry, name, metadata)`, which writes type and
>   tags only as part of a rename. Measured 2026-09-19 through real IPC in the release binary
>   (disposable `verify:app`-style probe, seeded workspace): calling it with the **unchanged** name and
>   `metadata.type = "repertoire"` rejects with `{"category":"io","message":"I/O failure"}` and leaves
>   the listing unchanged. So a type can only be changed by also renaming the file, and no UI offers
>   even that: `FilesPage.tsx` always passes the file's current type and tags. A file without a sidecar
>   lists as `other` and can never become a repertoire from inside the app, which also hollows out the

## Threat model and non-goals

Frozen in round 1.

* **Untrusted:** every renderer argument — the opaque workspace and entry handles, the typed name and
  the metadata object (size-capped by `serialize_metadata`, `MAX_WORKSPACE_METADATA_BYTES`).

  `.info` sidecar between resolution and the write. The write must never land a sidecar beside a PGN
  that is not the registered file, and must never follow a symlink or write into a non-regular sidecar.
* **Out of scope:** a local adversary racing the identity recheck and the sidecar install to win the
  window between them. The existing rename, move, create and delete paths have the same residual
  window; this plan narrows it the same way (recheck immediately before commit) and does not claim to
  close it. Parent-directory replacement (`f-20260915-03`, `f-20260917-03`) stays with those findings.
* **Platforms:** Linux, macOS and Windows behave alike through the existing descriptor-relative
  `infra::fs` primitives; no new platform-specific code is added.

## Approach

### O1 — A metadata-only command, and a same-leaf rename that does not fail

MANDATE: "calling it with the **unchanged** name and `metadata.type = "repertoire"` rejects … So a type
can only be changed by also renaming the file"; "a native command that atomically replaces the sidecar
for a registered workspace file (same descriptor-relative discipline and durability reporting as the
rename path), registered in Specta, bound, routed through `src/platform/tauri.ts`".

* New command `write_workspace_file_metadata(workspace, entry, metadata) -> Result<(), Error>`, shaped
  like `rename_workspace_file` (`file_workspace.rs:1248-1336`): accepted-operation ownership under its
  own label, cancellable blocking dispatch, the cancellable `workspace_mutation` lock, metadata
  serialised (size-capped) before the lock, `mutation_target` for root and entry,
  `ensure_registered_descendant`, refusal of a directory entry (`InvalidInput`), a cancellation check,
  then O2. It never renames anything and never rebinds the registry. It returns `Ok(())`, or
  `CommittedDurabilityUncertain(WorkspaceSidecarReplacement)` when O2 reports uncertainty.
* Registered in `collect_commands!`, the binding regenerated with `pnpm bindings:generate` (never
  hand-edited), reached through the existing `tauri` facade proxy; its production consumer is O4. Every
  explicit inventory in P15 includes it (the seven-command lists become eight).
* `rename_workspace_file` keeps its signature and contract. A normalised target leaf (`pgn_name(name)`)
  equal to the registered source leaf byte for byte — reachable when the user types `foo.pgn` for a
  file listed as `foo`, which the renderer correctly treats as a changed name — performs no PGN rename
  and no rebind and runs only O2, instead of failing with `I/O failure` (P1; precedent
  `move_workspace_entry`'s same-path no-op, P2).
* Failure semantics: every refusal before the sidecar commit (validation, resource limit, cancellation,
  identity conflict, non-regular sidecar, directory entry, unregistered or foreign handle) leaves the PGN
  and its sidecar byte-identical and the registry unchanged.
* Verification level: Rust unit tests in `file_workspace.rs`, the generated-binding proof, and the
  real-IPC check of O6.

### O2 — One sidecar-replacement core with a PGN identity recheck

MANDATE: "same descriptor-relative discipline and durability reporting as the rename path".

* One private helper in `file_workspace.rs` replaces a registered PGN's sidecar under a retained parent
  descriptor: it installs the serialised metadata at the PGN's sidecar leaf (P6) through an
  `atomic_replace_at*_with_precommit` primitive (P3) whose precommit closure rechecks the PGN leaf with
  `assert_entry_identity(parent, pgn_leaf, pgn_identity, false)` (P4) and the cancellation token, and
  maps the outcome through `durability_uncertainty(…, WorkspaceSidecarReplacement)`.
* The metadata-only command, the same-leaf rename and the rename path's post-rename sidecar write (O3)
  all go through this one helper (rule 11: the second copy is extracted, not duplicated). For the rename
  path the recheck uses the target leaf and the moved PGN's unchanged identity.
* Ownership: the caller holds `workspace_mutation` (cancellable lock) for the whole operation, as today.
* A PGN replaced, removed or turned into a non-regular entry after resolution yields `Error::Conflict`
  and no sidecar change; the staging temporary is cleaned up by the existing atomic driver.

### O3 — A rename applies name and metadata together or not at all

MANDATE: "an edit dialog … that edits name and type together"; "its rollback contract" (Open question).
Traced premises P7, P19.

* When the paired rename landed and the O2 sidecar replacement returns an ordinary `Err` (not a
  committed-uncertain outcome), the rename is reversed through the same retained descriptors: the PGN
  goes back to the source leaf (identity-checked, no-replace) and a sidecar that was moved goes back to
  the source sidecar leaf. The original error is returned; the registry still records the source path,
  which is again correct. This is `d-20261006-05`'s compensate-don't-report contract applied to rename.
* A failed reversal folds through `Error::with_cleanup` (P19) and is logged. `paired_rename`'s own
  existing rollback (P7, `:799`) is routed through the same `Error::with_cleanup` instead of its
  hand-built `OperationAndCleanup` (rule 11). The renderer's mapping of that category is unchanged
  (non-goal; `f-20261003-09`).
* A committed-but-uncertain sidecar outcome keeps today's behaviour: rebind, then report
  `WorkspaceSidecarReplacement` uncertainty (`file_workspace.rs:1318-1335` ordering preserved).
* Verification level: Rust unit tests with the existing `AtomicFileFaultPoint` injectors
  (`rename_under_injector`, `FailAtFaultPoints`).

### Decided autonomously

* **Q1 — New metadata-only command, or an unchanged name in `rename_workspace_file` as sidecar-only?**
  Chosen: a new `write_workspace_file_metadata` command (O1), sharing one sidecar core with the rename
  path (O2); the renderer chooses it when the Name field equals the listed display name. Rejected:
  inferring "unchanged" inside `rename_workspace_file` from the normalised leaf. Reason: the listed
  display name does not round-trip to the leaf (P16) — `study.pgn.pgn` lists as `study`, which
  normalises to `study.pgn` — so the native side cannot tell a type-only edit from a rename, and the
  overload would silently rename such a file or fail if `study.pgn` exists. Only the caller knows the
  name was left untouched, so that fact must cross IPC as the choice of command. The rename command
  still treats a same-leaf target as sidecar-only so a typed `foo.pgn` for `foo.pgn` stops failing with
  `I/O failure`. Reversal path: an `Option<String>` name on `rename_workspace_file` carries the same
  information through one command; the O2 core is unchanged either way.
* **Q2 — Where does the edit dialog live?** Chosen: the restored card `IconAction` opens the existing
  shared `AppModal` in an edit mode with Name + type `Select`; the Rename button keeps its name-only
  dialog; both submit through one path (O4). Rejected: upstream's five type cards/chips (rejected at
  320px in `d-20260919-12`); relabelling the Rename button as the editor (`d-20260919-12` rejected
  "keeping "Edit metadata" as a relabelled rename"); a separate modal component (a second copy of the
  name field and submit path). Reversal path: one JSX block in `FilesPage.tsx` and one prop on
  `FileCard`.
* **Q3 — Are tags editable?** Chosen: no; tags are carried through unchanged. Rejected: a tags field.
  Reason: upstream's dialog had none and no renderer code displays tags (P11); upstream even discarded
  them, which this plan does not repeat.
* **Q4 — What happens when a rename's sidecar write fails after the PGN moved?** Chosen: reverse the
  rename (O3). Rejected: keep the PGN renamed, rebind, and report applied-despite-error. Reason: the
  dialog edits name and type together; a half-applied edit (new name, old type) is the worse outcome,
  the reversal uses descriptors the operation already holds, and `d-20261006-05` chose compensation
  over applied-despite-error for the create paths on the same grounds.

## Threat model and non-goals

Frozen in round 1.

* **Untrusted:** every renderer argument — the opaque workspace and entry handles, the typed name and
  the metadata object (size-capped by `serialize_metadata`, `MAX_WORKSPACE_METADATA_BYTES`).
* **Accidental concurrency:** another program or window replacing, removing or renaming the PGN or its
  `.info` sidecar between resolution and the write. The write must never land a sidecar beside a PGN
  that is not the registered file, and must never follow a symlink or write into a non-regular sidecar.
* **Out of scope:** a local adversary racing the identity recheck and the sidecar install to win the
  window between them. The existing rename, move, create and delete paths have the same residual
  window; this plan narrows it the same way (recheck immediately before commit) and does not claim to
  close it. Parent-directory replacement (`f-20260915-03`, `f-20260917-03`) stays with those findings.
* **Platforms:** Linux, macOS and Windows behave alike through the existing descriptor-relative
  `infra::fs` primitives; no new platform-specific code is added.

## Approach

### O1 — A metadata-only command, and a same-leaf rename that does not fail

MANDATE: "calling it with the **unchanged** name and `metadata.type = "repertoire"` rejects … So a type
can only be changed by also renaming the file"; "a native command that atomically replaces the sidecar
for a registered workspace file (same descriptor-relative discipline and durability reporting as the
rename path), registered in Specta, bound, routed through `src/platform/tauri.ts`".

* New command `write_workspace_file_metadata(workspace, entry, metadata) -> Result<(), Error>`, shaped
  like `rename_workspace_file` (`file_workspace.rs:1248-1336`): accepted-operation ownership under its
  own label, cancellable blocking dispatch, the cancellable `workspace_mutation` lock, metadata
  serialised (size-capped) before the lock, `mutation_target` for root and entry,
  `ensure_registered_descendant`, refusal of a directory entry (`InvalidInput`), a cancellation check,
  then O2. It never renames anything and never rebinds the registry. It returns `Ok(())`, or
  `CommittedDurabilityUncertain(WorkspaceSidecarReplacement)` when O2 reports uncertainty.
* Registered in `collect_commands!`, the binding regenerated with `pnpm bindings:generate` (never
  hand-edited), reached through the existing `tauri` facade proxy; its production consumer is O4. Every
  explicit inventory in P15 includes it (the seven-command lists become eight).
* `rename_workspace_file` keeps its signature and contract. A normalised target leaf (`pgn_name(name)`)
  equal to the registered source leaf byte for byte — reachable when the user types `foo.pgn` for a
  file listed as `foo`, which the renderer correctly treats as a changed name — performs no PGN rename
  and no rebind and runs only O2, instead of failing with `I/O failure` (P1; precedent
  `move_workspace_entry`'s same-path no-op, P2).
* Failure semantics: every refusal before the sidecar commit (validation, resource limit, cancellation,
  identity conflict, non-regular sidecar, directory entry, unregistered or foreign handle) leaves the PGN
  and its sidecar byte-identical and the registry unchanged.
* Verification level: Rust unit tests in `file_workspace.rs`, the generated-binding proof, and the
  real-IPC check of O6.

### O2 — One sidecar-replacement core with a PGN identity recheck

MANDATE: "same descriptor-relative discipline and durability reporting as the rename path".

* One private helper in `file_workspace.rs` replaces a registered PGN's sidecar under a retained parent
  descriptor: it installs the serialised metadata at the PGN's sidecar leaf (P6) through an
  `atomic_replace_at*_with_precommit` primitive (P3) whose precommit closure rechecks the PGN leaf with
  `assert_entry_identity(parent, pgn_leaf, pgn_identity, false)` (P4) and the cancellation token, and
  maps the outcome through `durability_uncertainty(…, WorkspaceSidecarReplacement)`.
* The metadata-only command, the same-leaf rename and the rename path's post-rename sidecar write (O3)
  all go through this one helper (rule 11: the second copy is extracted, not duplicated). For the rename
  path the recheck uses the target leaf and the moved PGN's unchanged identity.
* Ownership: the caller holds `workspace_mutation` (cancellable lock) for the whole operation, as today.
* Failure semantics of the recheck: a PGN replaced by another object or turned into a non-regular entry
  after resolution yields `Error::Conflict`; a PGN removed after resolution yields the recheck's
  missing-entry I/O error (renderer category `missing-resource`, P20). In every case the sidecar is not
  changed and the staging temporary is cleaned up by the existing atomic driver.

### O3 — The rename path's post-move failure contract is unchanged (owned by f-20261006-03)

MANDATE: "an edit dialog … that edits name and type together"; "its rollback contract" (Open question).
Traced premises P7, P19, P21.

* Revised r2 (issues I3, I4, I6): this plan does **not** compensate a rename after the paired move. The
  open finding `f-20261006-03` owns exactly that question — whether an ordinary failure after a
  committed `paired_rename` (sidecar rewrite or registry rebind) rolls the move back or is reported as
  applied-despite-error — for rename, move, trash and restore together (P21).
* What this plan guarantees on the rename path: an ordinary O2 failure after the paired move — now
  including O2's PGN-identity `Conflict` — returns that error before the rebind, exactly as any sidecar
  failure does today (P7): the PGN and the moved old sidecar stay under the new leaf, nothing is moved
  back, a replaced PGN is never touched, and the registry still records the source path. A
  committed-but-uncertain sidecar outcome keeps today's behaviour: rebind, then report
  `WorkspaceSidecarReplacement` (`file_workspace.rs:1318-1335` ordering preserved). An ordinary rebind
  failure after both commits keeps today's plain error (`file_workspace.rs:3947` pins it).
* The type-only edit (O1's command) and the same-leaf rename perform no PGN move, so neither has a
  post-move state; the dialog's metadata-only path is therefore all-or-nothing by construction.
* Two constraints found in this review bind `f-20261006-03`'s future rollback and are handed to it by the
  implementing session (Phase 1 record step): a reversal must move a sidecar back only while it is the
  object the rename moved (a substituted `new.info` is left in place and reported as a failed cleanup;
  `rename_optional_regular_at` checks only kind, `src-tauri/src/infra/fs.rs:4913-4950`), and an
  identity-checked PGN reversal after a PGN substitution fails, so its outcome is a cleanup failure,
  not a plain `Conflict`.
* Verification level: Rust unit tests (Phase 1) pinning the guarantees above.

### O4 — The card's Edit-metadata control and the edit dialog

MANDATE: "an edit dialog on the Files page's file card that edits name and type together and picks
rename-with-metadata or metadata-only by whether the name changed"; `d-20260919-12`: "the icon returns

## Decisions and trade-offs

This plan starts from the draft of an earlier PLAN-ONLY lane for the same finding (drain session
85ca2084-2a68-4bde-8c07-92715007a9f5, 2026-10-05, base `18baa3b0`, three review rounds, plan and lens
evidence lost before publication; recovered from that session's transcript). Its premises were
re-traced at `ecbe66fa` (P11 corrected, P3/P19 updated for the f-20260914-02 create-path changes); its
review is not counted here and the full round-1 review runs again.

### Decided autonomously

* **Q1 — New metadata-only command, or an unchanged name in `rename_workspace_file` as sidecar-only?**
  Chosen: a new `write_workspace_file_metadata` command (O1), sharing one sidecar core with the rename
  path (O2); the renderer chooses it when the Name field equals the listed display name. Rejected:
  inferring "unchanged" inside `rename_workspace_file` from the normalised leaf. Reason: the listed
  display name does not round-trip to the leaf (P16) — `study.pgn.pgn` lists as `study`, which
  normalises to `study.pgn` — so the native side cannot tell a type-only edit from a rename, and the
  overload would silently rename such a file or fail if `study.pgn` exists. Only the caller knows the
  name was left untouched, so that fact must cross IPC as the choice of command. The rename command
  still treats a same-leaf target as sidecar-only so a typed `foo.pgn` for `foo.pgn` stops failing with
  `I/O failure`. Reversal path: an `Option<String>` name on `rename_workspace_file` carries the same
  information through one command; the O2 core is unchanged either way.
* **Q2 — Where does the edit dialog live?** Chosen: the restored card `IconAction` opens the existing
  shared `AppModal` in an edit mode with Name + type `Select`; the Rename button keeps its name-only
  dialog; both submit through one path (O4). Rejected: upstream's five type cards/chips (rejected at
  320px in `d-20260919-12`); relabelling the Rename button as the editor (`d-20260919-12` rejected
  "keeping "Edit metadata" as a relabelled rename"); a separate modal component (a second copy of the
  name field and submit path). Reversal path: one JSX block in `FilesPage.tsx` and one prop on
  `FileCard`.
* **Q3 — Are tags editable?** Chosen: no; tags are carried through unchanged. Rejected: a tags field.
  Reason: upstream's dialog had none and no renderer code displays tags (P11); upstream even discarded
  them, which this plan does not repeat.
* **Q4 — Does this plan settle what happens when a rename's sidecar write fails after the PGN moved?**
  Chosen (r2): no; the rename keeps today's failure contract and `f-20261006-03` settles it for rename,
  move, trash and restore together (O3). Rejected: reversing only the rename's sidecar-failure half here
  (this plan's r1 choice) — it would answer one quarter of an open build-tier design question and leave
  its three siblings on a different contract, and round 1 showed the reversal needs identity guarantees
  (issues I4, I6) that belong to that design. Reason: the type-only edit, which is what the MANDATE is
  missing, never moves a PGN, so it is all-or-nothing without any rollback. Reversal path: `f-20261006-03`
  replaces the early return after O2 with whichever contract it chooses.

* Snapshot churn: the restored icon changes card pixels in existing snapshots; re-recording happens in
  the pinned container only.

### O1 — A metadata-only command, and a same-leaf rename that does not fail

MANDATE: "calling it with the **unchanged** name and `metadata.type = "repertoire"` rejects … So a type

* New command `write_workspace_file_metadata(workspace, entry, metadata) -> Result<(), Error>`, shaped
  like `rename_workspace_file` (`file_workspace.rs:1248-1336`): accepted-operation ownership under its
  own label, cancellable blocking dispatch, the cancellable `workspace_mutation` lock, metadata

  file listed as `foo`, which the renderer correctly treats as a changed name — performs no PGN rename
  and no rebind and runs only O2, instead of failing with `I/O failure` (P1; precedent
  `move_workspace_entry`'s same-path no-op, P2).

  identity conflict, non-regular sidecar, directory entry, unregistered or foreign handle) leaves the PGN

### O2 — One sidecar-replacement core with a PGN identity recheck

MANDATE: "same descriptor-relative discipline and durability reporting as the rename path".

* One private helper in `file_workspace.rs` replaces a registered PGN's sidecar under a retained parent
  descriptor: it installs the serialised metadata at the PGN's sidecar leaf (P6) through an
  `atomic_replace_at*_with_precommit` primitive (P3) whose precommit closure rechecks the PGN leaf with
  `assert_entry_identity(parent, pgn_leaf, pgn_identity, false)` (P4) and the cancellation token, and
  maps the outcome through `durability_uncertainty(…, WorkspaceSidecarReplacement)`.
* The metadata-only command, the same-leaf rename and the rename path's post-rename sidecar write (O3)
  all go through this one helper (rule 11: the second copy is extracted, not duplicated). For the rename

### Decided autonomously

* **Q1 — New metadata-only command, or an unchanged name in `rename_workspace_file` as sidecar-only?**
  Chosen: a new `write_workspace_file_metadata` command (O1), sharing one sidecar core with the rename
  path (O2); the renderer chooses it when the Name field equals the listed display name. Rejected:

## Approach

### O1 — A metadata-only command, and a same-leaf rename that does not fail

MANDATE: "calling it with the **unchanged** name and `metadata.type = "repertoire"` rejects … So a type
can only be changed by also renaming the file"; "a native command that atomically replaces the sidecar
for a registered workspace file (same descriptor-relative discipline and durability reporting as the
rename path), registered in Specta, bound, routed through `src/platform/tauri.ts`".

* New command `write_workspace_file_metadata(workspace, entry, metadata) -> Result<(), Error>`, shaped
  like `rename_workspace_file` (`file_workspace.rs:1248-1336`): accepted-operation ownership under its
  own label, cancellable blocking dispatch, the cancellable `workspace_mutation` lock, metadata
  serialised (size-capped) before the lock, `mutation_target` for root and entry,
  `ensure_registered_descendant`, refusal of a directory entry (`InvalidInput`), a cancellation check,
  then O2. It never renames anything and never rebinds the registry. It returns `Ok(())`, or
  `CommittedDurabilityUncertain(WorkspaceSidecarReplacement)` when O2 reports uncertainty.
* Registered in `collect_commands!`, the binding regenerated with `pnpm bindings:generate` (never
  hand-edited), reached through the existing `tauri` facade proxy; its production consumer is O4. Every
  explicit inventory in P15 includes it (the seven-command lists become eight).
* `rename_workspace_file` keeps its signature and contract. A normalised target leaf (`pgn_name(name)`)
  equal to the registered source leaf byte for byte — reachable when the user types `foo.pgn` for a
  file listed as `foo`, which the renderer correctly treats as a changed name — performs no PGN rename
  and no rebind and runs only O2, instead of failing with `I/O failure` (P1; precedent
  `move_workspace_entry`'s same-path no-op, P2).
* Failure semantics: every refusal before the sidecar commit (validation, resource limit, cancellation,
  identity conflict, non-regular sidecar, directory entry, unregistered or foreign handle) leaves the PGN
  and its sidecar byte-identical and the registry unchanged.
* Verification level: Rust unit tests in `file_workspace.rs`, the generated-binding proof, and the
  real-IPC check of O6.

### O2 — One sidecar-replacement core with a PGN identity recheck

MANDATE: "same descriptor-relative discipline and durability reporting as the rename path".

* One private helper in `file_workspace.rs` replaces a registered PGN's sidecar under a retained parent
  descriptor: it installs the serialised metadata at the PGN's sidecar leaf (P6) through an
  `atomic_replace_at*_with_precommit` primitive (P3) whose precommit closure rechecks the PGN leaf with
  `assert_entry_identity(parent, pgn_leaf, pgn_identity, false)` (P4) and the cancellation token, and
  maps the outcome through `durability_uncertainty(…, WorkspaceSidecarReplacement)`.
* The metadata-only command, the same-leaf rename and the rename path's post-rename sidecar write (O3)
  all go through this one helper (rule 11: the second copy is extracted, not duplicated). For the rename
  path the recheck uses the target leaf and the moved PGN's unchanged identity.
* Ownership: the caller holds `workspace_mutation` (cancellable lock) for the whole operation, as today.
* Failure semantics of the recheck: a PGN replaced by another object or turned into a non-regular entry
  after resolution yields `Error::Conflict`; a PGN removed after resolution yields the recheck's
  missing-entry I/O error (backend category `missing-resource`, renderer category `not-found`, P20). In every case the sidecar is not
  changed and the staging temporary is cleaned up by the existing atomic driver.

### O3 — The rename path's post-move failure contract is unchanged (owned by f-20261006-03)

MANDATE: "an edit dialog … that edits name and type together"; "its rollback contract" (Open question).
Traced premises P7, P19, P21.

* Revised r2 (issues I3, I4, I6): this plan does **not** compensate a rename after the paired move. The
  open finding `f-20261006-03` owns exactly that question — whether an ordinary failure after a
  committed `paired_rename` (sidecar rewrite or registry rebind) rolls the move back or is reported as
  applied-despite-error — for rename, move, trash and restore together (P21).
* What this plan guarantees on the rename path: an ordinary O2 failure after the paired move — now
  including O2's PGN-identity `Conflict` — returns that error before the rebind, exactly as any sidecar
  failure does today (P7): the PGN and the moved old sidecar stay under the new leaf, nothing is moved
  back, a replaced PGN is never touched, and the registry still records the source path. A
  committed-but-uncertain sidecar outcome keeps today's behaviour: rebind, then report
  `WorkspaceSidecarReplacement` (`file_workspace.rs:1318-1335` ordering preserved). An ordinary rebind
  failure after both commits keeps today's plain error (`file_workspace.rs:3947` pins it).
* The type-only edit (O1's command) and the same-leaf rename perform no PGN move, so neither has a
  post-move state; the dialog's metadata-only path is therefore all-or-nothing by construction.
* Two constraints found in this review bind `f-20261006-03`'s future rollback and are handed to it by the
  implementing session (Phase 1 record step): a reversal must move a sidecar back only while it is the
  object the rename moved (a substituted `new.info` is left in place and reported as a failed cleanup;
  `rename_optional_regular_at` checks only kind, `src-tauri/src/infra/fs.rs:4913-4950`), and an
  identity-checked PGN reversal after a PGN substitution fails, so its outcome is a cleanup failure,
  not a plain `Conflict`.
* Verification level: Rust unit tests (Phase 1) pinning the guarantees above.

MANDATE: "an edit dialog on the Files page's file card that edits name and type together and picks
rename-with-metadata or metadata-only by whether the name changed"; `d-20260919-12`: "the icon returns
with that command".

* Both modes share one submission path. "Unchanged" means the Name field's raw value is exactly equal
  to the selected file's listed display name, compared **before** any trimming or normalisation:
  unchanged → `writeWorkspaceFileMetadata` with the chosen type (or no IPC call at all when the type is
  also unchanged); otherwise → `renameWorkspaceFile` with the field value and the chosen type (the
  existing blank-name guard stays). An untouched displayed name therefore never reaches

  `runAppliedMutationWithRefresh` so an applied-despite-error outcome relists.
* Tags are carried through unchanged and not edited (P11).
* Error handling unchanged: failures show `Files.OperationFailed`; applied-despite-error relists and
  closes the dialog, exactly as the create dialog does today (`FilesPage.test.tsx:480`). Whether these

## Decisions and trade-offs

This plan starts from the draft of an earlier PLAN-ONLY lane for the same finding (drain session
85ca2084-2a68-4bde-8c07-92715007a9f5, 2026-10-05, base `18baa3b0`, three review rounds, plan and lens
evidence lost before publication; recovered from that session's transcript). Its premises were
re-traced at `ecbe66fa` (P11 corrected, P3/P19 updated for the f-20260914-02 create-path changes); its
review is not counted here and the full round-1 review runs again.

### Decided autonomously

* **Q1 — New metadata-only command, or an unchanged name in `rename_workspace_file` as sidecar-only?**
  Chosen: a new `write_workspace_file_metadata` command (O1), sharing one sidecar core with the rename
  path (O2); the renderer chooses it when the Name field equals the listed display name. Rejected:
  inferring "unchanged" inside `rename_workspace_file` from the normalised leaf. Reason: the listed
  display name does not round-trip to the leaf (P16) — `study.pgn.pgn` lists as `study`, which
  normalises to `study.pgn` — so the native side cannot tell a type-only edit from a rename, and the
  overload would silently rename such a file or fail if `study.pgn` exists. Only the caller knows the
  name was left untouched, so that fact must cross IPC as the choice of command. The rename command
  still treats a same-leaf target as sidecar-only so a typed `foo.pgn` for `foo.pgn` stops failing with
  `I/O failure`. Reversal path: an `Option<String>` name on `rename_workspace_file` carries the same
  information through one command; the O2 core is unchanged either way.
* **Q2 — Where does the edit dialog live?** Chosen: the restored card `IconAction` opens the existing
  shared `AppModal` in an edit mode with Name + type `Select`; the Rename button keeps its name-only
  dialog; both submit through one path (O4). Rejected: upstream's five type cards/chips (rejected at
  320px in `d-20260919-12`); relabelling the Rename button as the editor (`d-20260919-12` rejected
  "keeping "Edit metadata" as a relabelled rename"); a separate modal component (a second copy of the
  name field and submit path). Reversal path: one JSX block in `FilesPage.tsx` and one prop on
  `FileCard`.
* **Q3 — Are tags editable?** Chosen: no; tags are carried through unchanged. Rejected: a tags field.
  Reason: upstream's dialog had none and no renderer code displays tags (P11); upstream even discarded
  them, which this plan does not repeat.
* **Q4 — Does this plan settle what happens when a rename's sidecar write fails after the PGN moved?**
  Chosen (r2): no; the rename keeps today's failure contract and `f-20261006-03` settles it for rename,
  move, trash and restore together (O3). Rejected: reversing only the rename's sidecar-failure half here
  (this plan's r1 choice) — it would answer one quarter of an open build-tier design question and leave
  its three siblings on a different contract, and round 1 showed the reversal needs identity guarantees
  (issues I4, I6) that belong to that design. Reason: the type-only edit, which is what the MANDATE is
  missing, never moves a PGN, so it is all-or-nothing without any rollback. Reversal path: `f-20261006-03`
  replaces the early return after O2 with whichever contract it chooses.

## Risks / open questions

* Case-only renames on case-insensitive filesystems (macOS/Windows) are byte-different leaves and keep
  the rename path; whether `NOREPLACE` refuses them there is not measured on this machine and is
  outside this mandate.
* Snapshot churn: the restored icon changes card pixels in existing snapshots; re-recording happens in
  the pinned container only.

## Not part of this task

* Changing how the listing derives display names (P16); the dialog's comparison against the listed
  name makes the type-only edit independent of it.
* Reporting a post-rename parent-sync failure in `rename_entry_at` as committed-but-uncertain
  (`f-20261005-03`, open).
* Compensating or reporting an ordinary failure after a committed `paired_rename`, and routing
  `paired_rename`'s hand-built `OperationAndCleanup` through `Error::with_cleanup` (`f-20261006-03`, open).
* Telling the user that a Files mutation's durability is uncertain (filed from issue I2).
* Relisting after an `operation-and-cleanup` outcome (`f-20261003-09`, open) and category-specific copy
  for the Files mutation dialogs (`f-20261005-04`, open).
* Tag editing; type chips; persisting the filter or search.
* Changing the renderer category of `OperationAndCleanup`.
* Any capability or CSP change.
* Directory metadata (directories have no sidecar).
