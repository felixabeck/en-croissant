## Mandate (fixed)

Close `f-20260921-04`: `EnginesPage`'s removal handler awaits `retire_engine` (which tombstones
the application id first and then drains, bounded by `kill_reap`) and only then drops the engine
from `enginesAtom`, so for the whole round trip the renderer list holds a permanently dead id; a
game started then passes the f-20260906-15 liveness check and is refused with the generic error.
Open question: drop first (proving the prepare/storage/reconcile crash boundaries) or a
pending-retirement set.

## Planned answer

- Drop first: `onConfirm` clears the selection, awaits `setEngines(filter)` (publication to the
  default store precedes the save; the awaited promise resolves after prepare → setItem →
  reconcile), then calls `retireEngine`. Retirement runs on every save exit (`saved:false`,
  `synchronized:false`, rejected setter); only a rejected setter is notified by the handler
  (receipts were already reported by `reportPersistError`); `onConfirm` never rejects.
- `ConfirmModal` owns closing (`onClose` after `onConfirm` resolves); the handler's own
  `toggleDeleteModal()` (a double toggle) is removed; `EngineSettings` is keyed by engine id so a
  list shift remounts instead of re-binding the pending confirmation to the next engine.
- Crash proof: each save's prepare → setItem → reconcile order (d-20260906-10) is unchanged; the
  native tombstone is in-memory, so on a successful setItem the new order removes the old
  resurrect-after-crash row; on a failed save the outcome equals the old order's and is reported.
- Pending-retirement set rejected: a second liveness authority beside `enginesAtom`
  (d-20260921-04/-05) that `EvalListener` and `EnginesSelect` would not consult.
- Decision to record (adopting session, `findings.py record-decision`): supersede only the
  "after the command returns" clause of d-20260901-17; new evidence is f-20260906-15/d-20260921-04
  (2026-09-21) making `enginesAtom` the liveness authority. The finding's citation of d-20260913-01
  for the coordinator ordering is a miscitation; it is d-20260906-10.
- Out of scope, filed via the inbox spool before round 1: a start admitted across the tombstone is
  shown the generic error because `Conflict` is untyped (needs a typed native refusal).

## Proof obligations for the diff

O3.1 retire observes the dropped list and a resolved save; O3.2 every save-failure exit still
retires, only the rejection notifies, handler never rejects; O3.3 real `enginesAtom` + real
confirm path: `toPlayerConfig` throws `MissingLocalEngineError` while retirement is pending;
O3.4 removing the first of two engines with retirement pending yields a fresh, closed settings
instance for the shifted engine. `EnginesPage.tsx` is in no frontend mutation package.

### plan-r1.md

# Plan: engine removal publishes the dropped list before the native tombstone (f-20260921-04)

## Goal

Removing a local engine must never leave its application id in the renderer's engine list after
the supervisor has tombstoned that id. Then every consumer that treats `enginesAtom` as the
liveness authority — the game-start check from f-20260906-15, `EnginesSelect`, `EvalListener`,
the report modal — stops offering or using the engine before the native side starts refusing it.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260921-04:

> **Defect:** the removal handler `await retireEngine(engine)` and only then filters `enginesAtom`. `retire_engine` tombstones the application id and drains its actors before it returns, and draining is bounded by `EngineDeadlines.kill_reap` (2s default, d-20260901-18), so for the whole round trip the renderer's engine list still contains an id that is already permanently dead. A game started in that window passes the liveness check added for f-20260906-15 and is refused by the supervisor with the generic operation error. The check is only as fresh as the atom it reads.
>
> **Fix direction:** the obvious repair — drop the engine from `enginesAtom` before issuing `retire_engine` — is not free: `d-20260913-01` serializes engine-list and player-owner updates as durable native prepare-retain → renderer persistence → native reconcile, and records that changing that ordering requires proving every prepare/storage/reconcile crash boundary first. `d-20260901-17` separately fixes "the renderer always drops `enginesAtom` after the command returns". So either that ordering is re-derived with the crash boundaries proven, or the renderer carries an explicit pending-retirement set that the liveness check consults. Filed at `build` because which of the two is right is an open design question against two recorded decisions.
>
> **Open question:** does the renderer drop the engine from `enginesAtom` before `retire_engine` is issued — which reverses the ordering clause of d-20260901-17 and touches the coordinator ordering d-20260913-01 guards — or does it keep that ordering and carry an explicit pending-retirement set that the liveness check consults? The first is smaller but has to prove the prepare/storage/reconcile crash boundaries d-20260913-01 names; the second adds renderer state that must itself be cleaned up on every exit path.

## Threat model and non-goals

Accidental input only: a user removes a local engine on the Engines page and, within the
retirement round trip, starts a game (or has an analysis tab using that engine) in another tab.
No adversarial renderer. The environment is the desktop app on Linux, macOS and Windows; nothing
here is platform-specific. Crash means abrupt process termination at any await point (power loss,
SIGKILL); a crash is not a clean `RunEvent::ExitRequested`.

Non-goal (filed separately, see Risks): a start whose IPC was issued **before** the removal
published and whose native admission is still running when `retire_engine` tombstones the id.
No renderer-side check can close that race; it exists unchanged before and after this change.

## Traced premises

Frozen Locate evidence at BASE `b41144cd`.

1. `src/components/engines/EnginesPage.tsx:659-672` — `onConfirm` awaits `retireEngine(engine)`
   (errors → `notifyUnlessCancelled`), then calls `setEngines(filter)` without awaiting it, then
   `setSelected(null)` and `toggleDeleteModal()`. The engine is therefore in `enginesAtom` for the
   whole `retire_engine` round trip.
2. `src-tauri/src/engine/process.rs:1939-1944` — `retire_engine` validates the id, inserts it into
   the tombstone set **first**, then `retire_matching` cancels admissions under the registration
   barrier and drains matching actors (bounded by `kill_reap`, d-20260901-18).
3. `src-tauri/src/engine/process.rs:1422-1431` — the tombstone set is an in-memory `Mutex`; it is
   not persisted, so a crash erases it. `process.rs:1218-1236` — admission of a tombstoned id fails
   with `Error::Conflict("engine id is retired")`.
4. `src/components/boards/BoardGame.tsx:561-579` — game start reads

* **Drop-first over a pending-retirement set.** A pending set would be a second liveness source

# Plan: engine removal publishes the dropped list before the native tombstone (f-20260921-04)

## Goal

Removing a local engine must never leave its application id in the renderer's engine list after
the supervisor has tombstoned that id. Then every consumer that treats `enginesAtom` as the
liveness authority — the game-start check from f-20260906-15, `EnginesSelect`, `EvalListener`,
the report modal — stops offering or using the engine before the native side starts refusing it.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260921-04:

> **Defect:** the removal handler `await retireEngine(engine)` and only then filters `enginesAtom`. `retire_engine` tombstones the application id and drains its actors before it returns, and draining is bounded by `EngineDeadlines.kill_reap` (2s default, d-20260901-18), so for the whole round trip the renderer's engine list still contains an id that is already permanently dead. A game started in that window passes the liveness check added for f-20260906-15 and is refused by the supervisor with the generic operation error. The check is only as fresh as the atom it reads.
>
> **Fix direction:** the obvious repair — drop the engine from `enginesAtom` before issuing `retire_engine` — is not free: `d-20260913-01` serializes engine-list and player-owner updates as durable native prepare-retain → renderer persistence → native reconcile, and records that changing that ordering requires proving every prepare/storage/reconcile crash boundary first. `d-20260901-17` separately fixes "the renderer always drops `enginesAtom` after the command returns". So either that ordering is re-derived with the crash boundaries proven, or the renderer carries an explicit pending-retirement set that the liveness check consults. Filed at `build` because which of the two is right is an open design question against two recorded decisions.
>
> **Open question:** does the renderer drop the engine from `enginesAtom` before `retire_engine` is issued — which reverses the ordering clause of d-20260901-17 and touches the coordinator ordering d-20260913-01 guards — or does it keep that ordering and carry an explicit pending-retirement set that the liveness check consults? The first is smaller but has to prove the prepare/storage/reconcile crash boundaries d-20260913-01 names; the second adds renderer state that must itself be cleaned up on every exit path.

## Threat model and non-goals

Accidental input only: a user removes a local engine on the Engines page and, within the
retirement round trip, starts a game (or has an analysis tab using that engine) in another tab.
No adversarial renderer. The environment is the desktop app on Linux, macOS and Windows; nothing
here is platform-specific. Crash means abrupt process termination at any await point (power loss,
SIGKILL); a crash is not a clean `RunEvent::ExitRequested`.

Non-goal (filed separately, see Risks): a start whose IPC was issued **before** the removal
published and whose native admission is still running when `retire_engine` tombstones the id.
No renderer-side check can close that race; it exists unchanged before and after this change.

### plan-r3.md

# Plan: engine removal publishes the dropped list before the native tombstone (f-20260921-04)

## Goal

Removing a local engine must never leave its application id in the renderer's engine list after
the supervisor has tombstoned that id. Then every consumer that treats `enginesAtom` as the
liveness authority — the game-start check from f-20260906-15, `EnginesSelect`, `EvalListener`,
the report modal — stops offering or using the engine before the native side starts refusing it.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260921-04:

> **Defect:** the removal handler `await retireEngine(engine)` and only then filters `enginesAtom`. `retire_engine` tombstones the application id and drains its actors before it returns, and draining is bounded by `EngineDeadlines.kill_reap` (2s default, d-20260901-18), so for the whole round trip the renderer's engine list still contains an id that is already permanently dead. A game started in that window passes the liveness check added for f-20260906-15 and is refused by the supervisor with the generic operation error. The check is only as fresh as the atom it reads.
>
> **Fix direction:** the obvious repair — drop the engine from `enginesAtom` before issuing `retire_engine` — is not free: `d-20260913-01` serializes engine-list and player-owner updates as durable native prepare-retain → renderer persistence → native reconcile, and records that changing that ordering requires proving every prepare/storage/reconcile crash boundary first. `d-20260901-17` separately fixes "the renderer always drops `enginesAtom` after the command returns". So either that ordering is re-derived with the crash boundaries proven, or the renderer carries an explicit pending-retirement set that the liveness check consults. Filed at `build` because which of the two is right is an open design question against two recorded decisions.
>
> **Open question:** does the renderer drop the engine from `enginesAtom` before `retire_engine` is issued — which reverses the ordering clause of d-20260901-17 and touches the coordinator ordering d-20260913-01 guards — or does it keep that ordering and carry an explicit pending-retirement set that the liveness check consults? The first is smaller but has to prove the prepare/storage/reconcile crash boundaries d-20260913-01 names; the second adds renderer state that must itself be cleaned up on every exit path.

## Threat model and non-goals

Accidental input only: a user removes a local engine on the Engines page and, within the
retirement round trip, starts a game (or has an analysis tab using that engine) in another tab.
No adversarial renderer. The environment is the desktop app on Linux, macOS and Windows; nothing
here is platform-specific. Crash means abrupt process termination at any await point (power loss,
SIGKILL); a crash is not a clean `RunEvent::ExitRequested`.

Non-goal (filed separately, see Risks): a start whose IPC was issued **before** the removal
published and whose native admission is still running when `retire_engine` tombstones the id.
No renderer-side check can close that race; it exists unchanged before and after this change.

## Approach

### O1 — Removal publishes the dropped engine list before `retire_engine` is issued

Rests on: "drop the engine from `enginesAtom` before issuing `retire_engine`" and "for the whole
round trip the renderer's engine list still contains an id that is already permanently dead".

`onConfirm` in the local-engine settings of `EnginesPage.tsx`:

1. clears the selection (`setSelected(null)`) first, so the settings view is not left showing
   whichever engine the shrinking list moves into the removed index;
2. awaits `setEngines(filter out engine.id)` — when it resolves, the dropped list has been
   published to the default store and the coordinated save has finished (premise 5);
3. then issues `retireEngine(engine)`, with the existing `notifyUnlessCancelled` on failure.

Modal and view binding: `ConfirmModal` already calls `onClose` (= `toggleDeleteModal`) after
`onConfirm` resolves and shows an inline error only when `onConfirm` rejects
(`src/components/common/ConfirmModal.tsx`, `confirm()`), so the handler no longer toggles the
modal itself — today's extra `toggleDeleteModal()` double-toggles. Because the drop now publishes
while the confirmation is still pending (for the whole retirement round trip), the parent renders
`EngineSettings` with `key` = the selected engine's id: a list shift then mounts a fresh settings
instance for the engine that moved into the index, instead of re-binding the open, pending
confirmation (and its `onConfirm` closure) to that other engine. The removed engine's instance
unmounts; its in-flight `onConfirm` continues, and the late `onClose` on the unmounted instance
is a no-op.

Failure semantics: retirement is issued on **every** exit of step 2 — a receipt with
`saved: false`, a receipt with `saved: true, synchronized: false`, and a rejected or throwing
`setEngines` promise (try/finally). A failure that resolves as a receipt was already reported by
`reportPersistError` inside the save sequence (premise 6); the handler adds no second report. A
**rejected** `setEngines` (a throw outside the save sequence's own catches, e.g. in the atom
setter or the storage adapter) is reported by the handler through `notifyUnlessCancelled`, since
the confirmation that could have shown it inline is closing or unmounted. `onConfirm` therefore
never rejects. A retirement failure is reported exactly as today and does not restore the engine
to the list (d-20260901-17's rejected "keeping the atom on failure", and "un-retiring on command
failure", stay rejected). Ownership: the handler owns the whole removal; it holds no state of its
own, so nothing new needs cleanup.

Verification level: unit (component) tests plus one real-store test; see O3.

### O2 — The crash-boundary proof the finding demands, carried into the decision record

Rests on: "has to prove the prepare/storage/reconcile crash boundaries".

The prepare → `localStorage.setItem` → reconcile order of each save (d-20260906-10) is not
changed: O1 changes only *when* the in-memory `retire_engine` command runs relative to one
complete save. Every crash point of the new sequence, given premises 3 and 6:

| Crash after | Durable engine list | Tombstone | State after restart |
|---|---|---|---|
| publication, before `prepare` | still contains X | none | X present and usable — the removal did not happen; consistent |
| `prepare`, before `setItem` | still contains X | none | as above; `prepare` only retains attachment ids, startup reconcile resolves them (d-20260906-10) |
| `setItem`, before `reconcile` | X gone | none | X gone; its attachments are reconciled at the next startup (d-20260906-10's existing boundary, unchanged) |
| `reconcile`, before or during `retire_engine` | X gone | lost with the process | X gone; consistent |

Failed-save exits (O1 still retires on each of them):

| Exit | Durable engine list | Tombstone | State after a later crash and restart |
|---|---|---|---|
| `prepare` rejects (`saved: false`) | still contains X | X, in memory, until the process ends | X present and usable again; the save failure was reported (`reportPersistError`) |
| `localStorage.setItem` throws (`saved: false`) | still contains X | as above | as above |
| setter rejects before the save sequence ran | still contains X | as above | as above; the rejection was reported by the handler (O1) |
| `reconcile` fails or a sibling owner is untrusted (`saved: true, synchronized: false`) | X gone | as above | X gone; attachments reconciled at startup (d-20260906-10, unchanged) |

So the durability guarantee is conditional: **on a successful `setItem`**, the old order's one
inconsistent row is removed — a crash after `retire_engine` and before `setItem` left X durable
with no tombstone, so X came back after restart. On a failed `setItem` the new order has exactly
that outcome (X durable, tombstone lost at the crash), the same as the old order with a failed
save; it is reported, and it is not made worse. Within the running session a failed save still
leaves X dropped from the renderer and tombstoned natively, which is d-20260901-17's chosen
"always drop" behaviour. Engine children at a crash are unchanged by either order (they are not reaped by a
SIGKILL'd parent in either ordering; f-20260830-51 covers clean exit).

Integration boundary: this table and the reversal of d-20260901-17's *after* clause become one
superseding decision record (see Decided autonomously), written by the adopting session through
`./scripts/findings.py record-decision`, naming d-20260901-17 as superseded in that clause only
and citing d-20260906-10 as unchanged.

## Decisions and trade-offs

* **Drop-first over a pending-retirement set.** A pending set would be a second liveness source
  beside `enginesAtom`, contradicting d-20260921-04/-05 (the engine list is *the* authority for
  existence). It would also have to be consulted by every list consumer — premise 7 shows
  `EvalListener` and `EnginesSelect` use the list for liveness too, so a set read only by
  `toPlayerConfig` would leave analysis searches running into the tombstone in the same window.
  Drop-first fixes all consumers at their existing authority and adds no state to clean up.
* **Await the full save receipt, not only the publication.** Retiring after the save completes
  makes the durable removal precede the in-memory tombstone, which is what removes the
  resurrect-after-crash row (O2). Cost: the engine's processes run for one extra save round trip
  (two IPC calls and one `localStorage` write) before they are drained. Rejected: a new
  "published" hook on the atom setter — new mechanism, for a few milliseconds.
* **The coordinator ordering of d-20260906-10 is not touched**, so its reversal clause is not
  triggered; the finding's citation of d-20260913-01 for it is a miscitation (premise 8).

## Decided autonomously

1. **Question:** drop the engine from `enginesAtom` before `retire_engine`, or keep the order and
   add a pending-retirement set? **Chosen:** drop first, awaiting the coordinated save, then
   retire on every exit path. **Rejected:** pending-retirement set (second liveness authority,
   misses `EvalListener`/`EnginesSelect`); keeping the current order. **Reason:** O2's crash table
   — the prepare/storage/reconcile order of a save is unchanged, and the new order removes the
   old resurrect-after-crash row. **New evidence vs d-20260901-17:** f-20260906-15 / d-20260921-04
   (2026-09-21) made `enginesAtom` the renderer's liveness authority after d-20260901-17
   (2026-09-01) fixed the order, so the *after* clause became observable; d-20260901-17 recorded
   no reason for it. **Supersedes:** the "after the command returns" clause of d-20260901-17 only;
   "always drops", the tombstone and the rejected alternatives stand. **Reversal path:** move
   `retireEngine` back before `setEngines` in `onConfirm`; the O3 tests go red first.
