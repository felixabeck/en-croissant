# Plan: download staging carries its payload as a descriptor, never a pathname (f-20260919-02)

## Goal

`download_to_destination_inner` (and the shared PGN installer it shares its install half with)
holds the downloaded payload only as an open descriptor from creation to install: nothing
creates, replaces, or reopens a named `staged/payload` leaf, and the two `path_authority`
helpers that read the staged payload stop opening a pathname.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260919-02:

> ### Download staging still creates and reopens the payload by pathname
>
> * **Where:** `src-tauri/src/fs.rs:563` and `:685` (`create_dir_all` of `path.parent()` in `download_file_core_control_with_integrity` when `path` is `staged/payload`), `:686` (`atomic_replace` of that payload), `:999` (`std::fs::File::open(staged_file)` on the non-reservation arm), `src-tauri/src/infra/path_authority/mod.rs` (`hash_staged_payload_cancellable` `File::open`), `src-tauri/src/infra/path_authority/resolved.rs` (`atomic_install_reserved_download_cancellable` `File::open`).
> * **Defect:** `download_to_destination_inner` creates `tempfile::tempdir()`, joins `payload`, and lets the shared download core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install. `f-20260905-08` closed zip/tar *inner* member writes through `OwnedStagingDir` and deliberately left this caller: converting only the last `File::open` would leave the bytes created by pathname, and converting the shared core would also hit engine-archive dest parents. Reservation-arm opens are pinned in `path_authority` (`File::open` count in `resolved.rs`).
> * **Why it matters:** the process-owned download staging directory is still a pathname TOCTOU between create and install. Closing it empties more of `fs.rs`'s counted surface (`File::open` plus the core sites when they name this tempfile).
> * **Related:** `f-20260905-08` (the slice that split this out; Root `-`, so named here). `d-20260919-03` (OwnedStagingDir, no checker exemption).
> * **Open question:** Should payload creation in `download_file_core_control_with_integrity` take an already-adopted `OwnedStagingDir` when the destination is process-owned staging, or should the shared core stay pathname and only `download_to_destination_inner` write through a descriptor-relative create of `payload`?

`fs.rs:528`, `:651`, `:652` and `:978` on `BASE` — see Traced premises.)

## Threat model and non-goals

* **In scope (accidental):** anything that changes, removes, or replaces a name in the shared
  system temp directory between payload creation and install — temp-directory cleaners
  (`systemd-tmpfiles` ages `/tmp` entries during a multi-GB download), other processes, a
  crash that leaves a named staging directory behind. And the repository invariant the finding
  cites: process-owned staging is never reopened by pathname, and the pathname-primitive
  surface (`scripts/check-rust-release-surface.mjs`) shrinks rather than relocates.
* **Structural, not adversarial:** a deliberate same-user attacker is not modelled beyond what
  removing the name gives structurally (there is nothing left to swap). No new defence against
  an attacker holding the process's own descriptors.
* **Environments:** Linux (primary; `O_TMPFILE`), macOS and Windows (CI-only targets; the
  `tempfile` crate's create-then-unlink and delete-on-close paths).
* **Non-goals:** the engine-archive route (`download_engine_archive_core`, its
  `private_tempdir_in(".archive", …)` staging, the core's `tempfile_in(target_dir)`,
  `create_dir_all` and plain-file `atomic_replace` tail it still uses — `d-20260919-03`,
  `d-20260919-05`); `chesscom.rs`'s own creation of its `NamedTempFile`; folding the duplicated
  hash → reserve → install → activate sequence of `download_to_destination_inner` and
  `install_staged_pgn_artifact` into one helper; blocking per-chunk writes in the async fetch
  loop (pre-existing, unchanged by this plan).

## Approach

### O1 — The download payload is an anonymous temporary file

Rests on MANDATE: "creates `tempfile::tempdir()`, joins `payload`, and lets the shared download
core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install".

* `download_to_destination_inner` creates its payload with `tempfile::tempfile()` — an unnamed,
  `0o600`, read-write file — instead of `tempfile::tempdir()` + `join("payload")`. It no longer
  creates any staging directory, and `DOWNLOAD_STAGING_PAYLOAD_LEAF` is deleted.
* The descriptor is created after the existing pre-progress validation and before
  `begin_progress`, exactly where the tempdir is created today, so a creation failure still
  leaves no running progress entry (the function's own comment at `fs.rs:859-860`).
* Ownership: the descriptor is owned by `download_to_destination_inner`'s future for its whole
  life and is dropped on every exit path (success, error, cancellation, deadline, caller drop
  inside `run_native_operation`); dropping it frees the payload — there is no named leftover
  to clean up, and no cleanup step to forget.

### O2 — The shared core's network stage writes into a caller-supplied descriptor

Rests on MANDATE: "converting only the last `File::open` would leave the bytes created by
pathname, and converting the shared core would also hit engine-archive dest parents".

* The network stage of `download_file_core_control_with_integrity` (URL validation, bearer
  origin check, redirects, 60 s request timeout, declared/actual size limits, optional SHA-256
  over the stream, progress, cancellation — `fs.rs:441-583`) becomes one function that writes
  the validated body into a caller-supplied open file and flushes it. Its behaviour, error
  values and error texts are unchanged.
* The engine route keeps its current shape around it: it still creates its own
  `tempfile_in(target_dir)` and runs the existing sniff → extract / plain `atomic_replace` tail
  (non-goal). The payload route (O1) calls the same network stage with its anonymous file. One
  network-stage implementation, two callers (rule 11; `async-resource-invariants.md` "the
  second approximately similar implementation gets extracted").
* The archive sniff (`fs.rs:597-616`: zip / ustar / gzip magic, rewinding the file) is likewise
  one shared function used by both routes.

### O3 — The payload route installs exactly the downloaded bytes

Rests on MANDATE: "lets the shared download core mkdir/write/replace that leaf by pathname".

* After the network stage, the payload route sniffs its file. Any archive magic (zip, ustar,
  gzip) is refused with the existing `Error::InvalidInput("Archive payload is not allowed for
  this operation")` for **every** op class: the route installs one regular file and has no
  extraction step. For the three production classes this is today's behaviour unchanged. The
  only behavioural difference is the non-production combination recorded in
  `## Decided autonomously` (D2).
* No intermediate copy: the plain-file `atomic_replace` onto `staged/payload` disappears from
  this route; the payload file is what gets hashed and installed.

### O4 — `path_authority` reads the staged payload from a descriptor

Rests on MANDATE: "`hash_staged_payload_cancellable` `File::open`", "`atomic_install_reserved_download_cancellable` `File::open`", "Reservation-arm opens are pinned in `path_authority`".

* `hash_staged_payload_cancellable` and `atomic_install_reserved_download_cancellable` take an
  already-open payload file instead of a `PathBuf` / `&Path`, read it from offset 0 (each
  rewinds before reading — the caller's file offset after writing or hashing is otherwise at
  EOF), and open no pathname. The caller keeps a usable descriptor for install after hashing
  (hashing runs on the blocking gateway, so the hash either returns the file or works on a
  cloned descriptor; executor's choice).
* The installer's existing reservation check (size + SHA-256 re-computed while copying, before
  `renameat`) is unchanged and still the substitution guard.
* The `cfg(all(test, unix))` wrapper `atomic_install_reserved_download` follows the same
  descriptor signature; tests that need a file open it in the test module, so `resolved.rs`
  contains no `File::open` at all.
* Both production consumers pass descriptors: `download_to_destination_inner` (its payload
  file, O1) and `install_staged_pgn_artifact`, which converts its `NamedTempFile` with
  `into_file()` at entry (its parameter type and `chesscom.rs` stay unchanged). The
  non-reservation arm of `download_to_destination_inner` copies from its payload file after a
  rewind instead of `File::open(staged_file)`.

### O5 — The payload-leaf staging form leaves the core

Rests on MANDATE: "Closing it empties more of `fs.rs`'s counted surface (`File::open` plus the
core sites when they name this tempfile)".

* With O1 the core's `staging = Some((root, Some(leaf)))` form has no producer. The `staging`

# Plan: download staging carries its payload as a descriptor, never a pathname (f-20260919-02)

## Goal

`download_to_destination_inner` (and the shared PGN installer it shares its install half with)
holds the downloaded payload only as an open descriptor from creation to install: nothing
creates, replaces, or reopens a named `staged/payload` leaf, and the two `path_authority`
helpers that read the staged payload stop opening a pathname.

## Threat model and non-goals

* **In scope (accidental):** anything that changes, removes, or replaces a name in the shared
  system temp directory between payload creation and install — temp-directory cleaners
  (`systemd-tmpfiles` ages `/tmp` entries during a multi-GB download), other processes, a
  crash that leaves a named staging directory behind. And the repository invariant the finding
  cites: process-owned staging is never reopened by pathname, and the pathname-primitive

* **Environments:** Linux (primary; `O_TMPFILE`), macOS and Windows (CI-only targets; the

## Approach

### O1 — The download payload is an anonymous temporary file

Rests on MANDATE: "creates `tempfile::tempdir()`, joins `payload`, and lets the shared download
core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install".

* `download_to_destination_inner` creates its payload with `tempfile::tempfile()` — a read-write
  file reachable only through the returned descriptor — instead of `tempfile::tempdir()` +
  `join("payload")`. It no longer creates any staging directory, and
  `DOWNLOAD_STAGING_PAYLOAD_LEAF` is deleted.
* The descriptor is created after the existing pre-progress validation and before
  `begin_progress`, exactly where the tempdir is created today, so a creation failure still
  leaves no running progress entry (the function's own comment at `fs.rs:859-860`).
* Ownership: the descriptor is owned by `download_to_destination_inner`'s future for its whole
  life and is dropped on every exit path (success, error, cancellation, deadline, caller drop
  inside `run_native_operation`); dropping it frees the payload, and no code path of this
  function names, reopens or removes the payload by pathname.
* Failure semantics of the name: on Linux with `O_TMPFILE` the payload never has a name. On the
  crate's fallback (other Unix, Linux filesystems refusing `O_TMPFILE`) and in
  `NamedTempFile::into_file` (O4) the crate creates a name and unlinks it immediately,
  **ignoring an unlink error** (Traced premises). Then a named temp file outlives the download
  in the temp directory — the same leak today's `TempDir` drop has when its removal fails. It
  is a named known limit, not handled here: the download still succeeds or fails on its own
  merits, because no read or install goes through that name, and adding detection would need a
  pathname re-check (the operation this plan removes) for a hazard that is not worse than
  today.

### O2 — The shared core's network stage writes into a caller-supplied descriptor

Rests on MANDATE: "converting only the last `File::open` would leave the bytes created by
pathname, and converting the shared core would also hit engine-archive dest parents".

* The network stage of `download_file_core_control_with_integrity` (URL validation, bearer
  origin check, redirects, 60 s request timeout, declared/actual size limits, optional SHA-256
  over the stream, progress, cancellation — `fs.rs:441-583`) becomes one function that writes
  the validated body into a caller-supplied open file and flushes it. Its behaviour, error
  values and error texts are unchanged.
* The engine route keeps its current shape around it: it still creates its own
  `tempfile_in(target_dir)` and runs the existing sniff → extract / plain `atomic_replace` tail
  (non-goal). The payload route (O1) calls the same network stage with its anonymous file. One
  network-stage implementation, two callers (rule 11; `async-resource-invariants.md` "the
  second approximately similar implementation gets extracted").
* The archive sniff (`fs.rs:597-616`: zip / ustar / gzip magic, rewinding the file) is likewise
  one shared function used by both routes.

### O3 — The payload route installs exactly the downloaded bytes

Rests on MANDATE: "lets the shared download core mkdir/write/replace that leaf by pathname".

* After the network stage, the payload route sniffs its file. Any archive magic (zip, ustar,
  gzip) is refused with the existing `Error::InvalidInput("Archive payload is not allowed for
  this operation")` for **every** op class: the route installs one regular file and has no
  extraction step. For the three production classes this is today's behaviour unchanged. The
  only behavioural difference is the non-production combination recorded in
  `## Decided autonomously` (D2).
* No intermediate copy: the plain-file `atomic_replace` onto `staged/payload` disappears from
  this route; the payload file is what gets hashed and installed.

### O4 — `path_authority` reads the staged payload from a descriptor

Rests on MANDATE: "`hash_staged_payload_cancellable` `File::open`", "`atomic_install_reserved_download_cancellable` `File::open`", "Reservation-arm opens are pinned in `path_authority`".

* `hash_staged_payload_cancellable` and `atomic_install_reserved_download_cancellable` take an
  already-open payload file instead of a `PathBuf` / `&Path`, read it from offset 0 (each
  rewinds before reading — the caller's file offset after writing or hashing is otherwise at
  EOF), and open no pathname. The caller keeps a usable descriptor for install after hashing
  (hashing runs on the blocking gateway, so the hash either returns the file or works on a
  cloned descriptor; executor's choice).
* The installer's existing reservation check (size + SHA-256 re-computed while copying, before
  `renameat`) is unchanged and still the substitution guard.
* The `cfg(all(test, unix))` wrapper `atomic_install_reserved_download` follows the same
  descriptor signature; tests that need a file open it in the test module, so `resolved.rs`
  contains no `File::open` at all.
* Both production consumers pass descriptors: `download_to_destination_inner` (its payload
  file, O1) and `install_staged_pgn_artifact`, which converts its `NamedTempFile` with
  `into_file()` at entry (its parameter type and `chesscom.rs` stay unchanged). The
  non-reservation arm of `download_to_destination_inner` copies from its payload file after a
  rewind instead of `File::open(staged_file)`.

### O5 — The payload-leaf staging form leaves the core

# Plan: download staging carries its payload as a descriptor, never a pathname (f-20260919-02)

## Goal

`download_to_destination_inner` (and the shared PGN installer it shares its install half with)
holds the downloaded payload only as an open descriptor from creation to install: nothing
creates, replaces, or reopens a named `staged/payload` leaf, and the two `path_authority`
helpers that read the staged payload stop opening a pathname.

## Threat model and non-goals

* **In scope (accidental):** anything that changes, removes, or replaces a name in the shared
  system temp directory between payload creation and install — temp-directory cleaners
  (`systemd-tmpfiles` ages `/tmp` entries during a multi-GB download), other processes, a

* **Environments:** Linux (primary; `O_TMPFILE`), macOS and Windows (CI-only targets; the

## Approach

### O1 — The download payload is an anonymous temporary file

Rests on MANDATE: "creates `tempfile::tempdir()`, joins `payload`, and lets the shared download
core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install".

* `download_to_destination_inner` creates its payload with `tempfile::tempfile()` — a read-write
  file reachable only through the returned descriptor — instead of `tempfile::tempdir()` +
  `join("payload")`. It no longer creates any staging directory, and
  `DOWNLOAD_STAGING_PAYLOAD_LEAF` is deleted.
* The descriptor is created after the existing pre-progress validation and before
  `begin_progress`, exactly where the tempdir is created today, so a creation failure still
  leaves no running progress entry (the function's own comment at `fs.rs:859-860`).
* Ownership: the descriptor is owned by `download_to_destination_inner`'s future for its whole
  life and is dropped on every exit path (success, error, cancellation, deadline, caller drop
  inside `run_native_operation`); dropping it frees the payload, and no code path of this
  function names, reopens or removes the payload by pathname.
* Failure semantics of the name: on Linux with `O_TMPFILE` the payload never has a name. On the
  crate's fallback (other Unix, Linux filesystems refusing `O_TMPFILE`) and in
  `NamedTempFile::into_file` (O4) the crate creates a name and unlinks it immediately,
  **ignoring an unlink error** (Traced premises). Then a named temp file outlives the download
  in the temp directory — the same leak today's `TempDir` drop has when its removal fails. It
  is a named known limit, not handled here: the download still succeeds or fails on its own
  merits, because no read or install goes through that name, and adding detection would need a
  pathname re-check (the operation this plan removes) for a hazard that is not worse than
  today.

### O2 — The shared core's network stage writes into a caller-supplied descriptor

Rests on MANDATE: "converting only the last `File::open` would leave the bytes created by
pathname, and converting the shared core would also hit engine-archive dest parents".

* The network stage of `download_file_core_control_with_integrity` (URL validation, bearer
  origin check, redirects, 60 s request timeout, declared/actual size limits, optional SHA-256
  over the stream, progress, cancellation — `fs.rs:441-583`) becomes one function that writes
  the validated body into a caller-supplied open file and flushes it. Its behaviour, error
  values and error texts are unchanged.
* The engine route keeps its current shape around it: it still creates its own
  `tempfile_in(target_dir)` and runs the existing sniff → extract / plain `atomic_replace` tail
  (non-goal). The payload route (O1) calls the same network stage with its anonymous file. One
  network-stage implementation, two callers (rule 11; `async-resource-invariants.md` "the
  second approximately similar implementation gets extracted").
* The archive sniff (`fs.rs:597-616`: zip / ustar / gzip magic, rewinding the file) is likewise
  one shared function used by both routes.

### O3 — The payload route installs exactly the downloaded bytes

Rests on MANDATE: "lets the shared download core mkdir/write/replace that leaf by pathname".

* After the network stage, the payload route sniffs its file. Any archive magic (zip, ustar,
  gzip) is refused with the existing `Error::InvalidInput("Archive payload is not allowed for
  this operation")` for **every** op class: the route installs one regular file and has no
  extraction step. This acceptance check depends only on the downloaded file (not on the op
  class), lives in one function, and runs before any hash, reservation or install. For the three production classes this is today's behaviour unchanged. The
  only behavioural difference is the non-production combination recorded in
  `## Decided autonomously` (D2).
* No intermediate copy: the plain-file `atomic_replace` onto `staged/payload` disappears from
  this route; the payload file is what gets hashed and installed.

### O4 — `path_authority` reads the staged payload from a descriptor

Rests on MANDATE: "`hash_staged_payload_cancellable` `File::open`", "`atomic_install_reserved_download_cancellable` `File::open`", "Reservation-arm opens are pinned in `path_authority`".

* `hash_staged_payload_cancellable` and `atomic_install_reserved_download_cancellable` take an
  already-open payload file instead of a `PathBuf` / `&Path`, read it from offset 0 (each
  rewinds before reading — the caller's file offset after writing or hashing is otherwise at
  EOF), and open no pathname. The caller keeps a usable descriptor for install after hashing
  (hashing runs on the blocking gateway, so the hash either returns the file or works on a
  cloned descriptor; executor's choice).
* The installer's existing reservation check (size + SHA-256 re-computed while copying, before
  `renameat`) is unchanged and still the substitution guard.
* The `cfg(all(test, unix))` wrapper `atomic_install_reserved_download` follows the same
  descriptor signature; tests that need a file open it in the test module, so `resolved.rs`
  contains no `File::open` at all.
* Both production consumers pass descriptors: `download_to_destination_inner` (its payload
  file, O1) and `install_staged_pgn_artifact`, which converts its `NamedTempFile` with
  `into_file()` at entry (its parameter type and `chesscom.rs` stay unchanged). The
  non-reservation arm of `download_to_destination_inner` copies from its payload file after a
  rewind instead of `File::open(staged_file)`.

### O5 — The payload-leaf staging form leaves the core

Rests on MANDATE: "Closing it empties more of `fs.rs`'s counted surface (`File::open` plus the
core sites when they name this tempfile)".

* With O1 the core's `staging = Some((root, Some(leaf)))` form has no producer. The `staging`
  parameter keeps only the engine form (the staging root the extractor installs onto itself),
  `archive_install_names` loses its leaf arm, and the test of that arm
  (`download_archive_staging_payload_path_mismatch_is_invalid_input`) is removed. The engine
  root-form mismatch and missing-staging tests stay.
* `scripts/check-rust-release-surface.mjs` `INITIAL_FS_SURFACE_COUNTS["src-tauri/src/fs.rs"]`
  is set to the newly measured count (7 → 6: the `File::open` at `fs.rs:978` goes; `:528`,
  `:651`, `:652` remain because the engine route still uses them and no longer name this
  tempfile). The measured value, not the predicted one, is recorded.

* **Gates:** `pnpm checks:pre-review` per commit; final `pnpm gates:push -- --rust` (backend

## Decided autonomously

* **D1 — Which staging mechanism closes the payload TOCTOU?**
  Chosen: an anonymous `tempfile::tempfile()` payload descriptor, with the core's network stage
  writing into a caller-supplied file (O1, O2). Rejected: (a) passing an adopted
  `OwnedStagingDir` into the shared core — the engine route's staging is the outer
  `private_tempdir_in(".archive")` beside the destination, which `d-20260919-03` refused to
  convert and `d-20260919-05` refused to drag into this cluster; (b) keeping the core pathname
  and only creating `payload` descriptor-relative under an `OwnedStagingDir` in
  `download_to_destination_inner` — works, but keeps a named leaf, a directory, identity-checked
  `Drop` cleanup and a Windows open-file-in-directory removal ordering for a single file that
  never needs a name; (c) converting only `File::open` (rejected by `d-20260919-05`). Reason: a
  single-file payload that is copied (not renamed) into the destination needs no name at all;
  an unnamed file has no pathname to race, cannot be aged out by a temp cleaner, and is freed
  by the kernel when its descriptor closes on any exit, a crash included (Linux `O_TMPFILE`;
  on the crate's fallback the name exists only until its immediate best-effort unlink — O1
  failure semantics). `d-20260919-03` governs directory staging for
  `atomic_install_dir`; this choice extends its principle (a type that cannot express an
  arbitrary path; no checker exemption, `PATHNAME_FNS` unchanged) rather than reversing it.
* **D2 — What does the payload route do with an archive payload for an `Engine`-class
  destination that also grants `DownloadFile`?**
  Chosen: refuse it like every other archive on this route (O3). Rejected: keep gzip
  decompression on this route (would need a second pathname-free gzip writer for a combination
  no production capability produces — canonical engine roots do not grant `DownloadFile`,
  `mod.rs:2257`; an `Engine`-class download through this route additionally needs metadata
  signed with the production key, `fs.rs:872`, `fs.rs:266-271`; engines download through
  `download_engine_archive`). Today zip/tar there
  already fail (a directory at `staged/payload` cannot be copied as a file); only plain gzip
  "worked". No user-visible behaviour changes in production.
* **D3 — Does the payload-leaf staging form stay in the core?** Chosen: remove it (O5); it has
  no producer after O1. Rejected: keep it for its one test (dead production code; coverage
  ratchet is shrink-neutral for deleted covered code, `d-20260829-03`).

## Decisions and trade-offs

* Location of the payload is unchanged: `tempfile::tempfile()` and `tempfile::tempdir()` both
  use `env::temp_dir()`. A `/tmp` on tmpfs holds a multi-GB database in RAM today and still
  will (known limit, not changed here).
* The `tempfile` crate's fallback briefly names the file before unlinking it; the data written
  goes only through the returned descriptor, so a name substituted in that window can redirect
  nothing. Windows: delete-on-close handle; same property.
* Known limit (O1 failure semantics): a failed best-effort unlink on the fallback paths leaves a
  named temp file behind, as a failed `TempDir` removal does today.
* The Linux `O_TMPFILE` inode carries the umask-masked default mode, not `0o600`; with
  `st_nlink 0` no other process can open it by name, so the mode grants nothing.

# Plan: download staging carries its payload as a descriptor, never a pathname (f-20260919-02)

## Goal

`download_to_destination_inner` (and the shared PGN installer it shares its install half with)
holds the downloaded payload only as an open descriptor from creation to install: nothing
creates, replaces, or reopens a named `staged/payload` leaf, and the two `path_authority`
helpers that read the staged payload stop opening a pathname.

## MANDATE

> ### Download staging still creates and reopens the payload by pathname
>
> * **Where:** `src-tauri/src/fs.rs:563` and `:685` (`create_dir_all` of `path.parent()` in `download_file_core_control_with_integrity` when `path` is `staged/payload`), `:686` (`atomic_replace` of that payload), `:999` (`std::fs::File::open(staged_file)` on the non-reservation arm), `src-tauri/src/infra/path_authority/mod.rs` (`hash_staged_payload_cancellable` `File::open`), `src-tauri/src/infra/path_authority/resolved.rs` (`atomic_install_reserved_download_cancellable` `File::open`).

## Threat model and non-goals

* **In scope (accidental):** anything that changes, removes, or replaces a name in the shared
  system temp directory between payload creation and install — temp-directory cleaners
  (`systemd-tmpfiles` ages `/tmp` entries during a multi-GB download), other processes, a
  crash that leaves a named staging directory behind. And the repository invariant the finding
  cites: process-owned staging is never reopened by pathname, and the pathname-primitive
  surface (`scripts/check-rust-release-surface.mjs`) shrinks rather than relocates.
* **Structural, not adversarial:** a deliberate same-user attacker is not modelled beyond what
  removing the name gives structurally (there is nothing left to swap). No new defence against
  an attacker holding the process's own descriptors.
* **Environments:** Linux (primary; `O_TMPFILE`), macOS and Windows (CI-only targets; the
  `tempfile` crate's create-then-unlink and delete-on-close paths).
* **Non-goals:** the engine-archive route (`download_engine_archive_core`, its

## Approach

### O1 — The download payload is an anonymous temporary file

Rests on MANDATE: "creates `tempfile::tempdir()`, joins `payload`, and lets the shared download
core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install".

* `download_to_destination_inner` creates its payload with `tempfile::tempfile()` — a read-write
  file reachable only through the returned descriptor — instead of `tempfile::tempdir()` +
  `join("payload")`. It no longer creates any staging directory, and
  `DOWNLOAD_STAGING_PAYLOAD_LEAF` is deleted.
* The descriptor is created after the existing pre-progress validation and before
  `begin_progress`, exactly where the tempdir is created today, so a creation failure still
  leaves no running progress entry (the function's own comment at `fs.rs:859-860`).
* Ownership: the descriptor is owned by `download_to_destination_inner`'s future for its whole
  life and is dropped on every exit path (success, error, cancellation, deadline, caller drop
  inside `run_native_operation`); dropping it frees the payload, and no code path of this
  function names, reopens or removes the payload by pathname.
* Failure semantics of the name: on Linux with `O_TMPFILE` the payload never has a name. On the
  crate's fallback (other Unix, Linux filesystems refusing `O_TMPFILE`) and in
  `NamedTempFile::into_file` (O4) the crate creates a name and unlinks it immediately,
  **ignoring an unlink error** (Traced premises). Then a named temp file outlives the download
  in the temp directory — the same leak today's `TempDir` drop has when its removal fails. It
  is a named known limit, not handled here: the download still succeeds or fails on its own
  merits, because no read or install goes through that name, and adding detection would need a
  pathname re-check (the operation this plan removes) for a hazard that is not worse than
  today.

### O2 — The shared core's network stage writes into a caller-supplied descriptor

Rests on MANDATE: "converting only the last `File::open` would leave the bytes created by
pathname, and converting the shared core would also hit engine-archive dest parents".

* The network stage of `download_file_core_control_with_integrity` (URL validation, bearer
  origin check, redirects, 60 s request timeout, declared/actual size limits, optional SHA-256
  over the stream, progress, cancellation — `fs.rs:441-583`) becomes one function that writes
  the validated body into a caller-supplied open file and flushes it. Its behaviour, error
  values and error texts are unchanged.
* The engine route keeps its current shape around it: it still creates its own
  `tempfile_in(target_dir)` and runs the existing sniff → extract / plain `atomic_replace` tail
  (non-goal). The payload route (O1) calls the same network stage with its anonymous file. One
  network-stage implementation, two callers (rule 11; `async-resource-invariants.md` "the
  second approximately similar implementation gets extracted").
* The archive sniff (`fs.rs:597-616`: zip / ustar / gzip magic, rewinding the file) is likewise
  one shared function used by both routes.

### O3 — The payload route installs exactly the downloaded bytes

Rests on MANDATE: "lets the shared download core mkdir/write/replace that leaf by pathname".

* After the network stage, the payload route sniffs its file. Any archive magic (zip, ustar,
  gzip) is refused with the existing `Error::InvalidInput("Archive payload is not allowed for
  this operation")` for **every** op class: the route installs one regular file and has no
  extraction step. This acceptance check depends only on the downloaded file (not on the op
  class), lives in one function, and runs before any hash, reservation or install. For the three production classes this is today's behaviour unchanged. The
  only behavioural difference is the non-production combination recorded in
  `## Decided autonomously` (D2).
* No intermediate copy: the plain-file `atomic_replace` onto `staged/payload` disappears from
  this route; the payload file is what gets hashed and installed.

### O4 — `path_authority` reads the staged payload from a descriptor

Rests on MANDATE: "`hash_staged_payload_cancellable` `File::open`", "`atomic_install_reserved_download_cancellable` `File::open`", "Reservation-arm opens are pinned in `path_authority`".

* `hash_staged_payload_cancellable` and `atomic_install_reserved_download_cancellable` take an
  already-open payload file instead of a `PathBuf` / `&Path`, read it from offset 0 (each
  rewinds before reading — the caller's file offset after writing or hashing is otherwise at
  EOF), and open no pathname. The caller keeps a usable descriptor for install after hashing
  (hashing runs on the blocking gateway, so the hash either returns the file or works on a
  cloned descriptor; executor's choice).
* The installer's existing reservation check (size + SHA-256 re-computed while copying, before
  `renameat`) is unchanged and still the substitution guard.
* The `cfg(all(test, unix))` wrapper `atomic_install_reserved_download` follows the same
  descriptor signature; tests that need a file open it in the test module, so `resolved.rs`
  contains no `File::open` at all.
* Both production consumers pass descriptors: `download_to_destination_inner` (its payload
  file, O1) and `install_staged_pgn_artifact`, which converts its `NamedTempFile` with
  `into_file()` at entry (its parameter type and `chesscom.rs` stay unchanged). The
  non-reservation arm of `download_to_destination_inner` copies from its payload file after a
  rewind instead of `File::open(staged_file)`.

### O5 — The payload-leaf staging form leaves the core

Rests on MANDATE: "Closing it empties more of `fs.rs`'s counted surface (`File::open` plus the
core sites when they name this tempfile)".

* With O1 the core's `staging = Some((root, Some(leaf)))` form has no producer. The `staging`
  parameter keeps only the engine form (the staging root the extractor installs onto itself),
  `archive_install_names` loses its leaf arm, and the test of that arm
  (`download_archive_staging_payload_path_mismatch_is_invalid_input`) is removed. The engine
  root-form mismatch and missing-staging tests stay.
* `scripts/check-rust-release-surface.mjs` `INITIAL_FS_SURFACE_COUNTS["src-tauri/src/fs.rs"]`
  is set to the newly measured count (7 → 6: the `File::open` at `fs.rs:978` goes; `:528`,
  `:651`, `:652` remain because the engine route still uses them and no longer name this
  tempfile). The measured value, not the predicted one, is recorded.

## Decided autonomously

* **D1 — Which staging mechanism closes the payload TOCTOU?**
  Chosen: an anonymous `tempfile::tempfile()` payload descriptor, with the core's network stage
  writing into a caller-supplied file (O1, O2). Rejected: (a) passing an adopted
  `OwnedStagingDir` into the shared core — the engine route's staging is the outer
  `private_tempdir_in(".archive")` beside the destination, which `d-20260919-03` refused to
  convert and `d-20260919-05` refused to drag into this cluster; (b) keeping the core pathname
  and only creating `payload` descriptor-relative under an `OwnedStagingDir` in
  `download_to_destination_inner` — works, but keeps a named leaf, a directory, identity-checked
  `Drop` cleanup and a Windows open-file-in-directory removal ordering for a single file that
  never needs a name; (c) converting only `File::open` (rejected by `d-20260919-05`). Reason: a
  single-file payload that is copied (not renamed) into the destination needs no name at all;
  an unnamed file has no pathname to race, cannot be aged out by a temp cleaner, and is freed
  by the kernel when its descriptor closes on any exit, a crash included (Linux `O_TMPFILE`;
  on the crate's fallback the name exists only until its immediate best-effort unlink — O1
  failure semantics). `d-20260919-03` governs directory staging for
  `atomic_install_dir`; this choice extends its principle (a type that cannot express an
  arbitrary path; no checker exemption, `PATHNAME_FNS` unchanged) rather than reversing it.
* **D2 — What does the payload route do with an archive payload for an `Engine`-class
  destination that also grants `DownloadFile`?**
  Chosen: refuse it like every other archive on this route (O3). Rejected: keep gzip
  decompression on this route (would need a second pathname-free gzip writer for a combination
  no production capability produces — canonical engine roots do not grant `DownloadFile`,
  `mod.rs:2257`; an `Engine`-class download through this route additionally needs metadata
  signed with the production key, `fs.rs:872`, `fs.rs:266-271`; engines download through
  `download_engine_archive`). Today zip/tar there
  already fail (a directory at `staged/payload` cannot be copied as a file); only plain gzip
  "worked". No user-visible behaviour changes in production.
* **D3 — Does the payload-leaf staging form stay in the core?** Chosen: remove it (O5); it has
  no producer after O1. Rejected: keep it for its one test (dead production code; coverage
  ratchet is shrink-neutral for deleted covered code, `d-20260829-03`).

## Decisions and trade-offs

* Location of the payload is unchanged: `tempfile::tempfile()` and `tempfile::tempdir()` both
  use `env::temp_dir()`. A `/tmp` on tmpfs holds a multi-GB database in RAM today and still
  will (known limit, not changed here).
* The `tempfile` crate's fallback briefly names the file before unlinking it; the data written
  goes only through the returned descriptor, so a name substituted in that window can redirect
  nothing. Windows: delete-on-close handle; same property.
* Known limit (O1 failure semantics): a failed best-effort unlink on the fallback paths leaves a
  named temp file behind, as a failed `TempDir` removal does today.
* The Linux `O_TMPFILE` inode carries the umask-masked default mode, not `0o600`; with
  `st_nlink 0` no other process can open it by name, so the mode grants nothing.

## Risks / open questions

* **Contested invariant R1-3 (second closure failure; focused judgment requested in r4).**
  Invariant: the payload route never installs an archive, for every op class that can reach
  it, and a test fails if an implementation gates the acceptance check by op class.
  Previous answers: r2 — an end-to-end `Engine`-class test (not constructible: production-key
  integrity validation at `fs.rs:872` runs before staging); r3 — a file-only acceptance
  function with a unit test (does not prove the caller invokes it unconditionally: the caller
  still holds `op`, `fs.rs:871`, and could keep the old `op.payload_format()` guard of
  `fs.rs:618-623` around the call). Source trace: `download_to_destination_inner` derives `op`
  (`fs.rs:870-871`), validates integrity (`:872`, production key `:251-256`, required for
  `Engine | Db | PuzzleDb` `:266-271`), resolves `DownloadFile` (`:873-877`), then stages.
  Candidate mechanisms:
  (A) keep r3 and carry "the acceptance call is unconditional" to the cumulative diff review
  as a branch-structure check;
  (B) add a source-scan assertion that the call is not inside an op-dependent branch;
  (C) make the route's op-class contract explicit and testable: right after `op` is derived
  and **before** integrity validation, the payload route refuses every op class whose
  `payload_format()` is not `PlainFile` with a fixed `Error::InvalidInput`; then every op that
  reaches the acceptance check is a `PlainFile` class, so an op-gated call cannot differ from
  an unconditional one for any reachable input, and an end-to-end `[DownloadFile,
  EngineExecute]` test is constructible (it fails before integrity, with zero transport
  requests). D2 widens to: `Engine`-class destinations are refused by this route outright
  (plain bytes included), which no production flow uses;
  (D) restructure so the post-network stage receives no `op` at all.
  Orchestrator's recommendation: (C).

* Windows `NamedTempFile::into_file` and `tempfile()` semantics are exercised only by the

* Fault-injection skip counts (O6) are inferred from the removed parent sync; the leaf must

# Plan: download staging carries its payload as a descriptor, never a pathname (f-20260919-02)

## Goal

`download_to_destination_inner` (and the shared PGN installer it shares its install half with)
holds the downloaded payload only as an open descriptor from creation to install: nothing
creates, replaces, or reopens a named `staged/payload` leaf, and the two `path_authority`
helpers that read the staged payload stop opening a pathname.

## Threat model and non-goals

* **In scope (accidental):** anything that changes, removes, or replaces a name in the shared
  system temp directory between payload creation and install — temp-directory cleaners
  (`systemd-tmpfiles` ages `/tmp` entries during a multi-GB download), other processes, a
  crash that leaves a named staging directory behind. And the repository invariant the finding
  cites: process-owned staging is never reopened by pathname, and the pathname-primitive
  surface (`scripts/check-rust-release-surface.mjs`) shrinks rather than relocates.
* **Structural, not adversarial:** a deliberate same-user attacker is not modelled beyond what
  removing the name gives structurally (there is nothing left to swap). No new defence against
  an attacker holding the process's own descriptors.
* **Environments:** Linux (primary; `O_TMPFILE`), macOS and Windows (CI-only targets; the
  `tempfile` crate's create-then-unlink and delete-on-close paths).
* **Non-goals:** the engine-archive route (`download_engine_archive_core`, its

## Approach

### O1 — The download payload is an anonymous temporary file

Rests on MANDATE: "creates `tempfile::tempdir()`, joins `payload`, and lets the shared download
core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install".

* `download_to_destination_inner` creates its payload with `tempfile::tempfile()` — a read-write
  file reachable only through the returned descriptor — instead of `tempfile::tempdir()` +
  `join("payload")`. It no longer creates any staging directory, and
  `DOWNLOAD_STAGING_PAYLOAD_LEAF` is deleted.
* The descriptor is created after the existing pre-progress validation and before
  `begin_progress`, exactly where the tempdir is created today, so a creation failure still
  leaves no running progress entry (the function's own comment at `fs.rs:859-860`).
* Ownership: the descriptor is owned by `download_to_destination_inner`'s future for its whole
  life and is dropped on every exit path (success, error, cancellation, deadline, caller drop
  inside `run_native_operation`); dropping it frees the payload, and no code path of this
  function names, reopens or removes the payload by pathname.
* Failure semantics of the name: on Linux with `O_TMPFILE` the payload never has a name. On the
  crate's fallback (other Unix, Linux filesystems refusing `O_TMPFILE`) and in
  `NamedTempFile::into_file` (O4) the crate creates a name and unlinks it immediately,
  **ignoring an unlink error** (Traced premises). Then a named temp file outlives the download
  in the temp directory — the same leak today's `TempDir` drop has when its removal fails. It
  is a named known limit, not handled here: the download still succeeds or fails on its own
  merits, because no read or install goes through that name, and adding detection would need a
  pathname re-check (the operation this plan removes) for a hazard that is not worse than
  today.

### O2 — The shared core's network stage writes into a caller-supplied descriptor

Rests on MANDATE: "converting only the last `File::open` would leave the bytes created by
pathname, and converting the shared core would also hit engine-archive dest parents".

* The network stage of `download_file_core_control_with_integrity` (URL validation, bearer
  origin check, redirects, 60 s request timeout, declared/actual size limits, optional SHA-256
  over the stream, progress, cancellation — `fs.rs:441-583`) becomes one function that writes
  the validated body into a caller-supplied open file and flushes it. Its behaviour, error
  values and error texts are unchanged.
* The engine route keeps its current shape around it: it still creates its own
  `tempfile_in(target_dir)` and runs the existing sniff → extract / plain `atomic_replace` tail
  (non-goal). The payload route (O1) calls the same network stage with its anonymous file. One
  network-stage implementation, two callers (rule 11; `async-resource-invariants.md` "the
  second approximately similar implementation gets extracted").
* The archive sniff (`fs.rs:597-616`: zip / ustar / gzip magic, rewinding the file) is likewise
  one shared function used by both routes.

### O3 — The payload route installs exactly the downloaded bytes

Rests on MANDATE: "lets the shared download core mkdir/write/replace that leaf by pathname".

* **Route admission.** Immediately after `download_to_destination_inner` derives the op class
  (`OpClass::from_operations`) and **before** integrity validation, resolution, staging or
  progress, it refuses every class whose `payload_format()` is not `PlainFile` with
  `Error::InvalidInput("Payload download requires a plain-file operation")`. Today only
  `Engine` is such a class (`fs.rs:182-188`); engines keep their own archive route
  (`download_engine_archive`). Admitted classes keep integrity validation unchanged.
* **Archive refusal.** After the network stage, the payload route sniffs its file. Any archive
  magic (zip, ustar, gzip) is refused with the existing `Error::InvalidInput("Archive payload
  is not allowed for this operation")`: the route installs one regular file and has no
  extraction step. This acceptance check depends only on the downloaded file, lives in one
  function, and runs before any hash, reservation or install.
* Behavioural invariant: a class that is not `PlainFile` never enters payload processing, and an
  admitted class never installs archive bytes. For the three production classes (`Lichess`,
  `Db`, `PuzzleDb`) this is today's behaviour unchanged; the only difference is the
  non-production combination recorded in `## Decided autonomously` (D2).
* No intermediate copy: the plain-file `atomic_replace` onto `staged/payload` disappears from
  this route; the payload file is what gets hashed and installed.

### O4 — `path_authority` reads the staged payload from a descriptor

Rests on MANDATE: "`hash_staged_payload_cancellable` `File::open`", "`atomic_install_reserved_download_cancellable` `File::open`", "Reservation-arm opens are pinned in `path_authority`".

* `hash_staged_payload_cancellable` and `atomic_install_reserved_download_cancellable` take an
  already-open payload file instead of a `PathBuf` / `&Path`, read it from offset 0 (each
  rewinds before reading — the caller's file offset after writing or hashing is otherwise at
  EOF), and open no pathname. The caller keeps a usable descriptor for install after hashing
  (hashing runs on the blocking gateway, so the hash either returns the file or works on a
  cloned descriptor; executor's choice).
* The installer's existing reservation check (size + SHA-256 re-computed while copying, before
  `renameat`) is unchanged and still the substitution guard.
* The `cfg(all(test, unix))` wrapper `atomic_install_reserved_download` follows the same
  descriptor signature; tests that need a file open it in the test module, so `resolved.rs`
  contains no `File::open` at all.
* Both production consumers pass descriptors: `download_to_destination_inner` (its payload
  file, O1) and `install_staged_pgn_artifact`, which converts its `NamedTempFile` with
  `into_file()` at entry (its parameter type and `chesscom.rs` stay unchanged). The
  non-reservation arm of `download_to_destination_inner` copies from its payload file after a
  rewind instead of `File::open(staged_file)`.

### O5 — The payload-leaf staging form leaves the core

Rests on MANDATE: "Closing it empties more of `fs.rs`'s counted surface (`File::open` plus the
core sites when they name this tempfile)".

* With O1 the core's `staging = Some((root, Some(leaf)))` form has no producer. The `staging`
  parameter keeps only the engine form (the staging root the extractor installs onto itself),
  `archive_install_names` loses its leaf arm, and the test of that arm

## Decided autonomously

* **D1 — Which staging mechanism closes the payload TOCTOU?**
  Chosen: an anonymous `tempfile::tempfile()` payload descriptor, with the core's network stage
  writing into a caller-supplied file (O1, O2). Rejected: (a) passing an adopted
  `OwnedStagingDir` into the shared core — the engine route's staging is the outer
  `private_tempdir_in(".archive")` beside the destination, which `d-20260919-03` refused to
  convert and `d-20260919-05` refused to drag into this cluster; (b) keeping the core pathname
  and only creating `payload` descriptor-relative under an `OwnedStagingDir` in
  `download_to_destination_inner` — works, but keeps a named leaf, a directory, identity-checked
  `Drop` cleanup and a Windows open-file-in-directory removal ordering for a single file that
  never needs a name; (c) converting only `File::open` (rejected by `d-20260919-05`). Reason: a
  single-file payload that is copied (not renamed) into the destination needs no name at all;
  an unnamed file has no pathname to race, cannot be aged out by a temp cleaner, and is freed
  by the kernel when its descriptor closes on any exit, a crash included (Linux `O_TMPFILE`;
  on the crate's fallback the name exists only until its immediate best-effort unlink — O1
  failure semantics). `d-20260919-03` governs directory staging for
  `atomic_install_dir`; this choice extends its principle (a type that cannot express an
  arbitrary path; no checker exemption, `PATHNAME_FNS` unchanged) rather than reversing it.
* **D2 — What does the payload route do for an `Engine`-class destination that also grants
  `DownloadFile`?**
  Chosen: refuse every such invocation at route admission, before integrity validation, plain
  bytes included (O3 route admission). Rejected: (a) keep archive handling for it on this route
  (gzip "worked" today; would need a second pathname-free gzip writer); (b) refuse only archive
  bytes (r3: an op-gated acceptance call is then indistinguishable from an unconditional one by
  any constructible test, because an `Engine`-class end-to-end call cannot pass production-key
  integrity validation, `fs.rs:872`, `fs.rs:251-271`). Reason: the payload route installs one
  plain file, and archive classes have their own route, so admission makes the existing
  boundary explicit and testable. No production capability produces this combination —
  canonical engine roots do not grant `DownloadFile` (`mod.rs:2257`) and engines download
  through `download_engine_archive` — so no user-visible behaviour changes. Settled by the
  focused fresh-context `review-plan` judgment of r4 (candidate C).
* **D3 — Does the payload-leaf staging form stay in the core?** Chosen: remove it (O5); it has
  no producer after O1. Rejected: keep it for its one test (dead production code; coverage
  ratchet is shrink-neutral for deleted covered code, `d-20260829-03`).

## Decisions and trade-offs

* Location of the payload is unchanged: `tempfile::tempfile()` and `tempfile::tempdir()` both
  use `env::temp_dir()`. A `/tmp` on tmpfs holds a multi-GB database in RAM today and still
  will (known limit, not changed here).
* The `tempfile` crate's fallback briefly names the file before unlinking it; the data written
  goes only through the returned descriptor, so a name substituted in that window can redirect
  nothing. Windows: delete-on-close handle; same property.
* Known limit (O1 failure semantics): a failed best-effort unlink on the fallback paths leaves a
  named temp file behind, as a failed `TempDir` removal does today.
* The Linux `O_TMPFILE` inode carries the umask-masked default mode, not `0o600`; with
  `st_nlink 0` no other process can open it by name, so the mode grants nothing.

# Plan: download staging carries its payload as a descriptor, never a pathname (f-20260919-02)

## Goal

`download_to_destination_inner` (and the shared PGN installer it shares its install half with)
holds the downloaded payload only as an open descriptor from creation to install: nothing
creates, replaces, or reopens a named `staged/payload` leaf, and the two `path_authority`
helpers that read the staged payload stop opening a pathname.

## MANDATE

Verbatim from `tasks/findings.md`, f-20260919-02:

> ### Download staging still creates and reopens the payload by pathname
>
> * **Where:** `src-tauri/src/fs.rs:563` and `:685` (`create_dir_all` of `path.parent()` in `download_file_core_control_with_integrity` when `path` is `staged/payload`), `:686` (`atomic_replace` of that payload), `:999` (`std::fs::File::open(staged_file)` on the non-reservation arm), `src-tauri/src/infra/path_authority/mod.rs` (`hash_staged_payload_cancellable` `File::open`), `src-tauri/src/infra/path_authority/resolved.rs` (`atomic_install_reserved_download_cancellable` `File::open`).
> * **Defect:** `download_to_destination_inner` creates `tempfile::tempdir()`, joins `payload`, and lets the shared download core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install. `f-20260905-08` closed zip/tar *inner* member writes through `OwnedStagingDir` and deliberately left this caller: converting only the last `File::open` would leave the bytes created by pathname, and converting the shared core would also hit engine-archive dest parents. Reservation-arm opens are pinned in `path_authority` (`File::open` count in `resolved.rs`).
> * **Why it matters:** the process-owned download staging directory is still a pathname TOCTOU between create and install. Closing it empties more of `fs.rs`'s counted surface (`File::open` plus the core sites when they name this tempfile).
> * **Related:** `f-20260905-08` (the slice that split this out; Root `-`, so named here). `d-20260919-03` (OwnedStagingDir, no checker exemption).
> * **Open question:** Should payload creation in `download_file_core_control_with_integrity` take an already-adopted `OwnedStagingDir` when the destination is process-owned staging, or should the shared core stay pathname and only `download_to_destination_inner` write through a descriptor-relative create of `payload`?

(The line numbers in the MANDATE are from filing time; the same sites sit at
`fs.rs:528`, `:651`, `:652` and `:978` on `BASE` — see Traced premises.)

## Threat model and non-goals

* **In scope (accidental):** anything that changes, removes, or replaces a name in the shared
  system temp directory between payload creation and install — temp-directory cleaners
  (`systemd-tmpfiles` ages `/tmp` entries during a multi-GB download), other processes, a
  crash that leaves a named staging directory behind. And the repository invariant the finding
  cites: process-owned staging is never reopened by pathname, and the pathname-primitive
  surface (`scripts/check-rust-release-surface.mjs`) shrinks rather than relocates.
* **Structural, not adversarial:** a deliberate same-user attacker is not modelled beyond what
  removing the name gives structurally (there is nothing left to swap). No new defence against
  an attacker holding the process's own descriptors.
* **Environments:** Linux (primary; `O_TMPFILE`), macOS and Windows (CI-only targets; the
  `tempfile` crate's create-then-unlink and delete-on-close paths).
* **Non-goals:** the engine-archive route (`download_engine_archive_core`, its
  `private_tempdir_in(".archive", …)` staging, the core's `tempfile_in(target_dir)`,
  `create_dir_all` and plain-file `atomic_replace` tail it still uses — `d-20260919-03`,
  `d-20260919-05`); `chesscom.rs`'s own creation of its `NamedTempFile`; folding the duplicated
  hash → reserve → install → activate sequence of `download_to_destination_inner` and
  `install_staged_pgn_artifact` into one helper; blocking per-chunk writes in the async fetch
  loop (pre-existing, unchanged by this plan).

## Approach

### O1 — The download payload is an anonymous temporary file

Rests on MANDATE: "creates `tempfile::tempdir()`, joins `payload`, and lets the shared download
core mkdir/write/replace that leaf by pathname, then reopens it by pathname to install".

* `download_to_destination_inner` creates its payload with `tempfile::tempfile()` — a read-write
  file reachable only through the returned descriptor — instead of `tempfile::tempdir()` +
  `join("payload")`. It no longer creates any staging directory, and
  `DOWNLOAD_STAGING_PAYLOAD_LEAF` is deleted.
* The descriptor is created after the existing pre-progress validation and before
  `begin_progress`, exactly where the tempdir is created today, so a creation failure still
  leaves no running progress entry (the function's own comment at `fs.rs:859-860`).
* Ownership: the descriptor is owned by `download_to_destination_inner`'s future for its whole
  life and is dropped on every exit path (success, error, cancellation, deadline, caller drop
  inside `run_native_operation`); dropping it frees the payload, and no code path of this
  function names, reopens or removes the payload by pathname.
* Failure semantics of the name: on Linux with `O_TMPFILE` the payload never has a name. On the
  crate's fallback (other Unix, Linux filesystems refusing `O_TMPFILE`) and in
  `NamedTempFile::into_file` (O4) the crate creates a name and unlinks it immediately,
  **ignoring an unlink error** (Traced premises). Then a named temp file outlives the download
  in the temp directory — the same leak today's `TempDir` drop has when its removal fails. It
  is a named known limit, not handled here: the download still succeeds or fails on its own
  merits, because no read or install goes through that name, and adding detection would need a
  pathname re-check (the operation this plan removes) for a hazard that is not worse than
  today.

### O2 — The shared core's network stage writes into a caller-supplied descriptor

Rests on MANDATE: "converting only the last `File::open` would leave the bytes created by
pathname, and converting the shared core would also hit engine-archive dest parents".

* The network stage of `download_file_core_control_with_integrity` (URL validation, bearer
  origin check, redirects, 60 s request timeout, declared/actual size limits, optional SHA-256
  over the stream, progress, cancellation — `fs.rs:441-583`) becomes one function that writes
  the validated body into a caller-supplied open file and flushes it. Its behaviour, error
  values and error texts are unchanged.
* The engine route keeps its current shape around it: it still creates its own
  `tempfile_in(target_dir)` and runs the existing sniff → extract / plain `atomic_replace` tail
  (non-goal). The payload route (O1) calls the same network stage with its anonymous file. One
  network-stage implementation, two callers (rule 11; `async-resource-invariants.md` "the
  second approximately similar implementation gets extracted").
* The archive sniff (`fs.rs:597-616`: zip / ustar / gzip magic, rewinding the file) is likewise
  one shared function used by both routes.

### O3 — The payload route installs exactly the downloaded bytes

Rests on MANDATE: "lets the shared download core mkdir/write/replace that leaf by pathname".

* **Route admission.** Immediately after `download_to_destination_inner` derives the op class
  (`OpClass::from_operations`) and **before** integrity validation, resolution, staging or
  progress, it refuses every class whose `payload_format()` is not `PlainFile` with
  `Error::InvalidInput("Payload download requires a plain-file operation")`. Today only
  `Engine` is such a class (`fs.rs:182-188`); engines keep their own archive route
  (`download_engine_archive`). Admitted classes keep integrity validation unchanged.
* **Archive refusal.** After the network stage, the payload route sniffs its file. Any archive
  magic (zip, ustar, gzip) is refused with the existing `Error::InvalidInput("Archive payload
  is not allowed for this operation")`: the route installs one regular file and has no
  extraction step. This acceptance check depends only on the downloaded file, lives in one
  function, and runs before any hash, reservation or install.
* Behavioural invariant: a class that is not `PlainFile` never enters payload processing, and an
  admitted class never installs archive bytes. For the three production classes (`Lichess`,
  `Db`, `PuzzleDb`) this is today's behaviour unchanged; the only difference is the
  non-production combination recorded in `## Decided autonomously` (D2).
* No intermediate copy: the plain-file `atomic_replace` onto `staged/payload` disappears from
  this route; the payload file is what gets hashed and installed.

### O4 — `path_authority` reads the staged payload from a descriptor

Rests on MANDATE: "`hash_staged_payload_cancellable` `File::open`", "`atomic_install_reserved_download_cancellable` `File::open`", "Reservation-arm opens are pinned in `path_authority`".

* `hash_staged_payload_cancellable` and `atomic_install_reserved_download_cancellable` take an
  already-open payload file instead of a `PathBuf` / `&Path`, read it from offset 0 (each
  rewinds before reading — the caller's file offset after writing or hashing is otherwise at
  EOF), and open no pathname. The caller keeps a usable descriptor for install after hashing
  (hashing runs on the blocking gateway, so the hash either returns the file or works on a
  cloned descriptor; executor's choice).
* The installer's existing reservation check (size + SHA-256 re-computed while copying, before
  `renameat`) is unchanged and still the substitution guard.
* The `cfg(all(test, unix))` wrapper `atomic_install_reserved_download` follows the same
  descriptor signature; tests that need a file open it in the test module, so `resolved.rs`
  contains no `File::open` at all.
* Both production consumers pass descriptors: `download_to_destination_inner` (its payload
  file, O1) and `install_staged_pgn_artifact`, which converts its `NamedTempFile` with
  `into_file()` at entry (its parameter type and `chesscom.rs` stay unchanged). The
  non-reservation arm of `download_to_destination_inner` copies from its payload file after a
  rewind instead of `File::open(staged_file)`.

### O5 — The payload-leaf staging form leaves the core

Rests on MANDATE: "Closing it empties more of `fs.rs`'s counted surface (`File::open` plus the
core sites when they name this tempfile)".

* With O1 the core's `staging = Some((root, Some(leaf)))` form has no producer. The `staging`
  parameter keeps only the engine form (the staging root the extractor installs onto itself),
  `archive_install_names` loses its leaf arm, and the test of that arm
  (`download_archive_staging_payload_path_mismatch_is_invalid_input`) is removed. The engine
  root-form mismatch and missing-staging tests stay.
* `scripts/check-rust-release-surface.mjs` `INITIAL_FS_SURFACE_COUNTS["src-tauri/src/fs.rs"]`
  is set to the newly measured count (7 → 6: the `File::open` at `fs.rs:978` goes; `:528`,
  `:651`, `:652` remain because the engine route still uses them and no longer name this
  tempfile). The measured value, not the predicted one, is recorded.

## Decided autonomously

* **D1 — Which staging mechanism closes the payload TOCTOU?**
  Chosen: an anonymous `tempfile::tempfile()` payload descriptor, with the core's network stage
  writing into a caller-supplied file (O1, O2). Rejected: (a) passing an adopted
  `OwnedStagingDir` into the shared core — the engine route's staging is the outer
  `private_tempdir_in(".archive")` beside the destination, which `d-20260919-03` refused to
  convert and `d-20260919-05` refused to drag into this cluster; (b) keeping the core pathname
  and only creating `payload` descriptor-relative under an `OwnedStagingDir` in
  `download_to_destination_inner` — works, but keeps a named leaf, a directory, identity-checked
  `Drop` cleanup and a Windows open-file-in-directory removal ordering for a single file that
  never needs a name; (c) converting only `File::open` (rejected by `d-20260919-05`). Reason: a
  single-file payload that is copied (not renamed) into the destination needs no name at all;
  an unnamed file has no pathname to race, cannot be aged out by a temp cleaner, and is freed
  by the kernel when its descriptor closes on any exit, a crash included (Linux `O_TMPFILE`;
  on the crate's fallback the name exists only until its immediate best-effort unlink — O1
  failure semantics). `d-20260919-03` governs directory staging for
  `atomic_install_dir`; this choice extends its principle (a type that cannot express an
  arbitrary path; no checker exemption, `PATHNAME_FNS` unchanged) rather than reversing it.
* **D2 — What does the payload route do for an `Engine`-class destination that also grants
  `DownloadFile`?**
  Chosen: refuse every such invocation at route admission, before integrity validation, plain
  bytes included (O3 route admission). Rejected: (a) keep archive handling for it on this route
  (gzip "worked" today; would need a second pathname-free gzip writer); (b) refuse only archive
  bytes (r3: an op-gated acceptance call is then indistinguishable from an unconditional one by
  any constructible test, because an `Engine`-class end-to-end call cannot pass production-key
  integrity validation, `fs.rs:872`, `fs.rs:251-271`). Reason: the payload route installs one
  plain file, and archive classes have their own route, so admission makes the existing
  boundary explicit and testable. No production capability produces this combination —
  canonical engine roots do not grant `DownloadFile` (`mod.rs:2257`) and engines download
  through `download_engine_archive` — so no user-visible behaviour changes. Settled by the
  focused fresh-context `review-plan` judgment of r4 (candidate C).
* **D3 — Does the payload-leaf staging form stay in the core?** Chosen: remove it (O5); it has
  no producer after O1. Rejected: keep it for its one test (dead production code; coverage
  ratchet is shrink-neutral for deleted covered code, `d-20260829-03`).

## Decisions and trade-offs

* Location of the payload is unchanged: `tempfile::tempfile()` and `tempfile::tempdir()` both
  use `env::temp_dir()`. A `/tmp` on tmpfs holds a multi-GB database in RAM today and still
  will (known limit, not changed here).
* The `tempfile` crate's fallback briefly names the file before unlinking it; the data written
  goes only through the returned descriptor, so a name substituted in that window can redirect
  nothing. Windows: delete-on-close handle; same property.
* Known limit (O1 failure semantics): a failed best-effort unlink on the fallback paths leaves a
  named temp file behind, as a failed `TempDir` removal does today.
* The Linux `O_TMPFILE` inode carries the umask-masked default mode, not `0o600`; with
  `st_nlink 0` no other process can open it by name, so the mode grants nothing.

## Risks / open questions

* **Contested invariant R1-3 (second closure failure; focused judgment requested in r4).**
  Invariant: the payload route never installs an archive, for every op class that can reach
  it, and a test fails if an implementation gates the acceptance check by op class.
  Previous answers: r2 — an end-to-end `Engine`-class test (not constructible: production-key
  integrity validation at `fs.rs:872` runs before staging); r3 — a file-only acceptance
  function with a unit test (does not prove the caller invokes it unconditionally: the caller
  still holds `op`, `fs.rs:871`, and could keep the old `op.payload_format()` guard of
  `fs.rs:618-623` around the call). Source trace: `download_to_destination_inner` derives `op`
  (`fs.rs:870-871`), validates integrity (`:872`, production key `:251-256`, required for
  `Engine | Db | PuzzleDb` `:266-271`), resolves `DownloadFile` (`:873-877`), then stages.
  Candidate mechanisms:
  (A) keep r3 and carry "the acceptance call is unconditional" to the cumulative diff review
  as a branch-structure check;
  (B) add a source-scan assertion that the call is not inside an op-dependent branch;
  (C) make the route's op-class contract explicit and testable: right after `op` is derived
  and **before** integrity validation, the payload route refuses every op class whose
  `payload_format()` is not `PlainFile` with a fixed `Error::InvalidInput`; then every op that
  reaches the acceptance check is a `PlainFile` class, so an op-gated call cannot differ from
  an unconditional one for any reachable input, and an end-to-end `[DownloadFile,
  EngineExecute]` test is constructible (it fails before integrity, with zero transport
  requests). D2 widens to: `Engine`-class destinations are refused by this route outright
  (plain bytes included), which no production flow uses;
  (D) restructure so the post-network stage receives no `op` at all.
  Orchestrator's recommendation: (C).
  **Judgment (r4, fresh-context `review-plan`): C.** Resulting obligation changes adopted in
  r5: O3 route admission + archive refusal + behavioural invariant; O6 test (c); D2 rewritten.
  The syntactic "caller invokes the check unconditionally" requirement is replaced by the
  behavioural invariant.

* Windows `NamedTempFile::into_file` and `tempfile()` semantics are exercised only by the
  CI-only `rust-windows-test`; `pnpm rust:windows:check` type-checks locally.
* Fault-injection skip counts (O6) are inferred from the removed parent sync; the leaf must
  confirm by the tests' own `DownloadTargetReplacement` assertions, not by the count.
