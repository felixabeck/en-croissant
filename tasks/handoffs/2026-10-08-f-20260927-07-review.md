## Approach

### O1 — Identity from the target and the mapped descriptor

MANDATE words: "derived from the descriptor-retained database target the repository already holds
(so no pathname canonicalisation or stat is needed)"; "resolve to a different file than the one
the search index is later opened from".

* `SearchIndexIdentity` holds: `database: PathBuf` = the `DatabaseFileTarget::path()` the loader
  resolved (no canonicalisation); the sidecar's object identity, byte length and modification
  time, all taken from the **same opened descriptor that is mapped**; and `source: IndexSource`.
  The `index: PathBuf` field and the preferred/legacy selection are removed: the legacy sidecar is
  never an identity input (it is only ever promoted, never served — P1).
* One production constructor takes the target, the `IndexSource` and the opened sidecar `&File`,
  and has no `Path` parameter. It uses `opened_file_identity` and `File::metadata()` only.
* `open_valid_preferred` builds the identity from the opened descriptor **before** handing that
  descriptor to `MmapSearchIndex::open_file_cancellable`, and returns the identity together with
  the index (still `None` when the archived source differs). `cache_loaded_index` receives that
  identity; it performs no filesystem call and no fallible identity step after the map.
* **Failure semantics:** an error from `opened_file_identity` or `File::metadata()` on the opened
  sidecar is returned as an error from `open_valid_preferred`; it is never treated as absence and
  never falls through to another sidecar (closes `f-20261002-12`'s fallback). The existing
  `ProbeErrorClass` handling of the open itself is unchanged.
* **Linearization:** the database identity probe stays the linearization point
  (`d-20260929-03`). A database renamed or deleted after the probe no longer turns into an `Io` or
  `Conflict` after the map: the load returns the mapping under the probed identity; the
  invalidation counter still decides whether it is cached (`d-20261005-06`), and every later load
  re-probes before reuse. The `Conflict("search index changed while loading")` mapping inside
  `cache_loaded_index`, which existed only for a failed identity construction, is removed; the
  same message stays where generation's final reload finds no valid sidecar (`search.rs:315-318`).

### O2 — Invalidation by target

MANDATE words: "`invalidate_entries` (`database.canonicalize()`)", moved to
`SearchCache::invalidate_database`.

* `SearchCache::invalidate_database` takes `&DatabaseFileTarget`. It keeps its order (counter
  increment, then results, then indexes — P8 scan `:3618`) and evicts every entry whose identity
  satisfies `identity.database == target.path()` **or** `identity.source.object ==
  target.identity()`.
* Why both: the full-path `canonicalize` it replaces unified leaf-spelling aliases of one file
  (P4); the object match preserves that without a pathname call. The path match keeps evicting
  entries cached for an earlier inode at the same path (a replaced database), as today.
  Over-eviction is harmless (one uncached reload).
* `finish_search_cache_after_transaction` takes `&DatabaseFileTarget`; every production caller
  passes its target (P6). No caller passes a raw path any more.

### O3 — Gate: delete the pins and empty the R5 baseline

MANDATE words: "the migration must delete the attribute and shrink R5's pinned-site baseline in
the same change".

* All six `#[expect(clippy::disallowed_methods, …)]` attributes in `main.rs` disappear with their
  reaches. The crate-root test allowance (P10) and `src-tauri/clippy.toml` stay byte-identical.
* `INITIAL_PATH_EXPECT_BASELINE` and `PATH_EXPECT_BASELINE` both become empty frozen arrays (the
  ceiling is zero). The R5 machinery (hash pin, method multiset, residency, suppression
  containment) stays: it is what would count any future pin, and its synthetic tests keep it
  exercised.
* The three checker tests that relied on the checkout's pinned sites (P9) are rewritten onto
  synthetic fixtures with `customExpectBaseline`, keeping each property: a pinned function's text
  change is rejected, an expect outside a pinned function is rejected, and the CLI (real checkout)
  rejects a counted expect added to `main.rs` with "has no pinned baseline entry".

### O4 — Verification

* **Single construction path in tests:** the test-only identity helper builds a
  `DatabaseFileTarget::for_test_path`, opens the preferred sidecar relative to its parent with
  `open_regular_at`, and calls the production constructor, so seeded identities equal production
  ones (P7, `db/mod.rs:8414`). Every test caller of `for_database` moves to it.
* **Descriptor anchor (unix):** open sidecar A through the production open path, rename a
  different file B over the preferred name, then build the identity from A's descriptor: its
  object identity equals A's and differs from B's; the mapped index is A's. Reintroducing any
  pathname stat in the constructor turns this red.
* **No legacy identity (f-20261002-12):** with both preferred and legacy sidecars present, the
  identity's object is the preferred descriptor's; there is no code path that names the legacy
  sidecar in an identity.
* **Linearization tests replace P8's two pathname-failure tests:** database removed after the
  probe — with invalidation the load returns the mapping uncached; without invalidation it returns
  the mapping cached under the probed identity, and the next load fails resolution/probe and never
  serves the cached mapping.
* **Invalidation keys:** an entry is evicted by a target with the same path; by a target with a
  different path to the same object (a hard link in the same directory); and is kept for a target
  naming another object at another path.
* Updated source scans: `db/search.rs:1567-1592` and any `infra/platform_support/tests.rs` scan
  whose required text changes move to the new call shape without weakening what they forbid
  (`canonicalize(` stays forbidden in production `search.rs`; `open_regular_at(` still precedes
  `MmapSearchIndex::open_file_cancellable(file,cancellation)`; one `insert_index`).

## Decisions and trade-offs

* **Descriptor-derived identity, not a counted `infra` canonicalisation primitive.** The primitive
  would move the reach without removing it and keep the window between pathname resolution and the
  mapped object — `d-20260928-05` already rejected "wrapping the calls in `infra` helpers" for that
  reason.
* **Path plus object in invalidation**, not object alone (would keep entries for a replaced inode
  at the same path until LRU eviction — worse than today) and not path alone (would stop unifying
  leaf-spelling aliases on case-insensitive filesystems — worse than today).
* **No post-map failure.** `d-20261005-06`'s clause "a cache-identity construction failure after
  the map, with a moved counter, is returned as … `Conflict`" covered a failure this change makes
  impossible; the counter mechanism it chose is unchanged. This is not a reversal of that decision.

## Approach

### O1 — Identity from the target and the mapped descriptor

MANDATE words: "derived from the descriptor-retained database target the repository already holds
(so no pathname canonicalisation or stat is needed)"; "resolve to a different file than the one
the search index is later opened from".

* `SearchIndexIdentity` holds: `database: PathBuf` = the `DatabaseFileTarget::path()` the loader
  resolved (no canonicalisation); the sidecar's object identity, byte length and modification
  time, all taken from the **same opened descriptor that is mapped**; and `source: IndexSource`.
  The `index: PathBuf` field and the preferred/legacy selection are removed: the legacy sidecar is
  never an identity input (it is only ever promoted, never served — P1).
* One production constructor takes the target, the `IndexSource` and the opened sidecar `&File`,
  and has no `Path` parameter. It uses `opened_file_identity` and `File::metadata()` only.
* `open_valid_preferred` builds the identity from the opened descriptor **before** handing that
  descriptor to `MmapSearchIndex::open_file_cancellable`, and returns the identity together with
  the index (still `None` when the archived source differs). `cache_loaded_index` receives that
  identity; it performs no filesystem call and no fallible identity step after the map.
* **Failure semantics:** an error from `opened_file_identity` or `File::metadata()` on the opened
  sidecar is returned as an error from `open_valid_preferred`; it is never treated as absence and
  never falls through to another sidecar (closes `f-20261002-12`'s fallback). The existing
  `ProbeErrorClass` handling of the open itself is unchanged.
* **Linearization:** the database identity probe stays the linearization point
  (`d-20260929-03`). A database renamed or deleted after the probe no longer turns into an `Io` or
  `Conflict` after the map: the load returns the mapping under the probed identity; the
  invalidation counter still decides whether it is cached (`d-20261005-06`), and every later load
  re-probes before reuse. The `Conflict("search index changed while loading")` mapping inside
  `cache_loaded_index`, which existed only for a failed identity construction, is removed; the
  same message stays where generation's final reload finds no valid sidecar (`search.rs:315-318`).

### O2 — Invalidation by target

MANDATE words: "`invalidate_entries` (`database.canonicalize()`)", moved to
`SearchCache::invalidate_database`.

* `SearchCache::invalidate_database` takes `&DatabaseFileTarget`. It keeps its order (counter
  increment, then results, then indexes — P8 scan `:3618`) and evicts every entry whose identity
  satisfies `identity.database == target.path()` **or** `identity.source.object ==
  target.identity()`.
* Why both: the full-path `canonicalize` it replaces unified leaf-spelling aliases of one file
  (P4); the object match preserves that without a pathname call. The path match keeps evicting
  entries cached for an earlier inode at the same path (a replaced database), as today.
  Over-eviction is harmless (one uncached reload).
* `finish_search_cache_after_transaction` takes `&DatabaseFileTarget`; every production caller
  passes its target (P6). No caller passes a raw path any more.
* **Known limit (R1-01):** one database authorized under two leaf spellings on a case-insensitive
  filesystem **and** replaced externally between a load and an invalidation through the other
  spelling keeps the earlier entry until LRU eviction. It is never served: the key carries the
  probed database object and revision, and every load re-probes. The cause is the authority keeping
  the caller's leaf spelling (`path_authority/mod.rs:2073`, lexical reuse at `:5851`), which already
  splits the generation and collision lock keys today; it is filed as its own `native-fs` finding
  (inbox `20261008-075745-2632118-1791439065931264586-6.md`) rather than patched with a second
  normalisation inside the search cache.

### O3 — Gate: delete the pins and empty the R5 baseline

MANDATE words: "the migration must delete the attribute and shrink R5's pinned-site baseline in
the same change".

* All six `#[expect(clippy::disallowed_methods, …)]` attributes in `main.rs` disappear with their
  reaches. The crate-root test allowance (P10) and `src-tauri/clippy.toml` stay byte-identical.
* `INITIAL_PATH_EXPECT_BASELINE` and `PATH_EXPECT_BASELINE` both become empty frozen arrays (the
  ceiling is zero). The R5 machinery (hash pin, method multiset, residency, suppression
  containment) stays: it is what would count any future pin, and its synthetic tests keep it
  exercised.
* The three checker tests that relied on the checkout's pinned sites (P9) are rewritten onto
  synthetic fixtures with `customExpectBaseline`, keeping each property: a pinned function's text
  change is rejected, an expect outside a pinned function is rejected, and the CLI (real checkout)
  rejects a counted expect added to `main.rs` with "has no pinned baseline entry".

### O4 — Verification

* **Single construction path in tests:** the test-only identity helper builds a
  `DatabaseFileTarget::for_test_path`, opens the preferred sidecar relative to its parent with
  `open_regular_at`, and calls the production constructor, so seeded identities equal production
  ones (P7, `db/mod.rs:8414`). Every test caller of `for_database` moves to it.
* **Platform placement (R1-02):** the descriptor anchor, the failure witness and the
  invalidation-key tests below live in a test module that compiles and runs on Linux, macOS and
  Windows (not behind `cfg(unix)`). Their runtime proof on the other platforms is the
  `rust-macos-test` and `rust-windows-test` jobs of `.github/workflows/test.yml` on the pushed
  head; locally `pnpm rust:windows:check` proves only that they compile. The two linearization
  tests stay in the existing `cfg(all(test, unix))` loader module (`db/search.rs:996`), because
  they delete a database file while the repository holds it open.
* **Descriptor anchor:** open sidecar A through the production open path, rename a different
  file B over the preferred name, then build the identity from A's descriptor: its object identity
  equals A's and differs from B's; the mapped index is A's. Reintroducing any pathname stat in the
  constructor turns this red.
* **Failure witness (R1-03):** a `#[cfg(test)]` fault injector (the existing
  `FAIL_NEXT_REVISION_BUMP` pattern; R2 requires fault-injection items inside `#[cfg(test)]`) makes
  the descriptor stamp step fail once. `open_valid_preferred`, and the loader through it, return
  that error — not `Ok(None)`, not a legacy sidecar — and nothing is inserted into the index or
  result cache. Changing the propagation to absence turns this red.
* **No legacy identity (f-20261002-12):** with both preferred and legacy sidecars present, the
  identity's object is the preferred descriptor's; there is no code path that names the legacy
  sidecar in an identity.
* **Linearization tests replace P8's two pathname-failure tests:** database removed after the
  probe — with invalidation the load returns the mapping uncached; without invalidation it returns
  the mapping cached under the probed identity, and the next load fails resolution/probe and never
  serves the cached mapping.
* **Invalidation keys (R1-04):** with an index and a result cached for object A: a target with
  the same path naming a **different object** (A replaced by B at that path) evicts both; a target
  with a different path naming object A (a hard link in the same directory) evicts both; a target
  naming another object at another path keeps both. Object-only or path-only matching each fail
  one case.
* Updated source scans: `db/search.rs:1567-1592` and any `infra/platform_support/tests.rs` scan
  whose required text changes move to the new call shape without weakening what they forbid
  (`canonicalize(` stays forbidden in production `search.rs`; `open_regular_at(` still precedes
  `MmapSearchIndex::open_file_cancellable(file,cancellation)`; one `insert_index`).

## Decisions and trade-offs

* **Descriptor-derived identity, not a counted `infra` canonicalisation primitive.** The primitive
  would move the reach without removing it and keep the window between pathname resolution and the
  mapped object — `d-20260928-05` already rejected "wrapping the calls in `infra` helpers" for that
  reason.
* **Path plus object in invalidation**, not object alone (would keep entries for a replaced inode
  at the same path until LRU eviction — worse than today) and not path alone (would stop unifying
  leaf-spelling aliases on case-insensitive filesystems — worse than today).
* **No post-map failure.** `d-20261005-06`'s clause "a cache-identity construction failure after
  the map, with a moved counter, is returned as … `Conflict`" covered a failure this change makes
  impossible; the counter mechanism it chose is unchanged. This is not a reversal of that decision.

## Approach

### O1 — Identity from the target and the mapped descriptor

MANDATE words: "derived from the descriptor-retained database target the repository already holds
(so no pathname canonicalisation or stat is needed)"; "resolve to a different file than the one
the search index is later opened from".

* `SearchIndexIdentity` holds: `database: PathBuf` = the `DatabaseFileTarget::path()` the loader
  resolved (no canonicalisation); the sidecar's object identity, byte length and modification
  time, all taken from the **same opened descriptor that is mapped**; and `source: IndexSource`.
  The `index: PathBuf` field and the preferred/legacy selection are removed: the legacy sidecar is
  never an identity input (it is only ever promoted, never served — P1).
* One production constructor takes the target, the `IndexSource` and the opened sidecar `&File`,
  and has no `Path` parameter. It uses `opened_file_identity` and `File::metadata()` only.
* `open_valid_preferred` builds the identity from the opened descriptor **before** handing that
  descriptor to `MmapSearchIndex::open_file_cancellable`, and returns the identity together with
  the index (still `None` when the archived source differs). `cache_loaded_index` receives that
  identity; it performs no filesystem call and no fallible identity step after the map.
* **Failure semantics:** an error from `opened_file_identity` or `File::metadata()` on the opened
  sidecar is returned as an error from `open_valid_preferred`; it is never treated as absence and
  never falls through to another sidecar (closes `f-20261002-12`'s fallback). The existing
  `ProbeErrorClass` handling of the open itself is unchanged.
* **Linearization:** the database identity probe stays the linearization point
  (`d-20260929-03`). A database renamed or deleted after the probe no longer turns into an `Io` or
  `Conflict` after the map: the load returns the mapping under the probed identity; the
  invalidation counter still decides whether it is cached (`d-20261005-06`), and every later load
  re-probes before reuse. The `Conflict("search index changed while loading")` mapping inside
  `cache_loaded_index`, which existed only for a failed identity construction, is removed; the
  same message stays where generation's final reload finds no valid sidecar (`search.rs:315-318`).

### O2 — Invalidation by target

MANDATE words: "`invalidate_entries` (`database.canonicalize()`)", moved to
`SearchCache::invalidate_database`.

* `SearchCache::invalidate_database` takes `&DatabaseFileTarget`. It keeps its order (counter
  increment, then results, then indexes — P8 scan `:3618`) and evicts every entry whose identity
  satisfies `identity.database == target.path()` **or** `identity.source.object ==
  target.identity()`.
* Why both: the full-path `canonicalize` it replaces unified leaf-spelling aliases of one file
  (P4); the object match preserves that without a pathname call. The path match keeps evicting
  entries cached for an earlier inode at the same path (a replaced database), as today.
  Over-eviction is harmless (one uncached reload).
* `finish_search_cache_after_transaction` takes `&DatabaseFileTarget`; every production caller
  passes its target (P6). No caller passes a raw path any more.
* **Known limit (R1-01):** one database authorized under two leaf spellings on a case-insensitive
  filesystem **and** replaced externally between a load and an invalidation through the other
  spelling keeps the earlier entry until LRU eviction. It is never served: the key carries the
  probed database object and revision, and every load re-probes. The cause is the authority keeping
  the caller's leaf spelling (`path_authority/mod.rs:2073`, lexical reuse at `:5851`), which already
  splits the generation and collision lock keys today; it is filed as its own `native-fs` finding
  (inbox `20261008-075745-2632118-1791439065931264586-6.md`) rather than patched with a second
  normalisation inside the search cache.

### O3 — Gate: delete the pins and empty the R5 baseline

MANDATE words: "the migration must delete the attribute and shrink R5's pinned-site baseline in
the same change".

* All six `#[expect(clippy::disallowed_methods, …)]` attributes in `main.rs` disappear with their
  reaches. The crate-root test allowance (P10) and `src-tauri/clippy.toml` stay byte-identical.
* `INITIAL_PATH_EXPECT_BASELINE` and `PATH_EXPECT_BASELINE` both become empty frozen arrays (the
  ceiling is zero). The R5 machinery (hash pin, method multiset, residency, suppression
  containment) stays: it is what would count any future pin, and its synthetic tests keep it
  exercised.
* The three checker tests that relied on the checkout's pinned sites (P9) are rewritten onto
  synthetic fixtures with `customExpectBaseline`, keeping each property: a pinned function's text
  change is rejected, an expect outside a pinned function is rejected, and the CLI (real checkout)
  rejects a counted expect added to `main.rs` with "has no pinned baseline entry".

### O4 — Verification

* **Single construction path in tests:** the test-only identity helper builds a
  `DatabaseFileTarget::for_test_path`, opens the preferred sidecar relative to its parent with
  `open_regular_at`, and calls the production constructor, so seeded identities equal production
  ones (P7, `db/mod.rs:8414`). Every test caller of `for_database` moves to it.
* **Platform placement (R1-02):** the descriptor anchor, the failure witness and the
  invalidation-key tests below live in a test module that compiles and runs on Linux, macOS and
  Windows (not behind `cfg(unix)`). Their runtime proof on the other platforms is the
  `rust-macos-test` and `rust-windows-test` jobs of `.github/workflows/test.yml` on the pushed
  head; locally `pnpm rust:windows:check` proves only that they compile. The two linearization
  tests stay in the existing `cfg(all(test, unix))` loader module (`db/search.rs:996`), because
  they delete a database file while the repository holds it open.
* **Descriptor anchor:** open sidecar A through the production open path, rename a different
  file B over the preferred name, then build the identity from A's descriptor: its object identity
  equals A's and differs from B's; the mapped index is A's. Reintroducing any pathname stat in the
  constructor turns this red.
* **Failure witness (R1-03):** a `#[cfg(test)]` fault injector (the existing
  `FAIL_NEXT_REVISION_BUMP` pattern; R2 requires fault-injection items inside `#[cfg(test)]`) makes
  the descriptor stamp step fail once. `open_valid_preferred`, and the loader through it, return
  that error — not `Ok(None)`, not a legacy sidecar — and nothing is inserted into the index or
  result cache. Changing the propagation to absence turns this red.
* **No legacy identity (f-20261002-12):** with both preferred and legacy sidecars present, the
  identity's object is the preferred descriptor's; there is no code path that names the legacy
  sidecar in an identity.
* **Linearization tests replace P8's two pathname-failure tests:** database removed after the
  probe — with invalidation the load returns the mapping uncached; without invalidation it returns
  the mapping cached under the probed identity, and the next load fails resolution/probe and never
  serves the cached mapping.
* **Invalidation keys (R1-04):** with an index and a result cached for object A: a target with
  the same path naming a **different object** (A replaced by B at that path) evicts both; a target
  with a different path naming object A (a hard link in the same directory) evicts both; a target
  naming another object at another path keeps both. Object-only or path-only matching each fail
  one case.
* Updated source scans: `db/search.rs:1567-1592` and any `infra/platform_support/tests.rs` scan
  whose required text changes move to the new call shape without weakening what they forbid
  (`canonicalize(` stays forbidden in production `search.rs`; `open_regular_at(` still precedes
  `MmapSearchIndex::open_file_cancellable(file,cancellation)`; one `insert_index`).

## Decisions and trade-offs

* **Descriptor-derived identity, not a counted `infra` canonicalisation primitive.** The primitive
  would move the reach without removing it and keep the window between pathname resolution and the
  mapped object — `d-20260928-05` already rejected "wrapping the calls in `infra` helpers" for that
  reason.
* **Path plus object in invalidation**, not object alone (would keep entries for a replaced inode
  at the same path until LRU eviction — worse than today) and not path alone (would stop unifying
  leaf-spelling aliases on case-insensitive filesystems — worse than today).
* **No post-map failure.** `d-20261005-06`'s clause "a cache-identity construction failure after
  the map, with a moved counter, is returned as … `Conflict`" covered a failure this change makes
  impossible; the counter mechanism it chose is unchanged. This is not a reversal of that decision.
