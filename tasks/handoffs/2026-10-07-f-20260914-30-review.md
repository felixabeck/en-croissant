# Plan: Workspace delete reports engine-retirement failure

## Goal

After a workspace entry is gone, `permanently_delete_workspace_entry` reports an engine-retirement failure instead of returning success. The report uses the existing applied-despite-error path. The count in that report is the registry ids this removal itself dropped.

## MANDATE

* **ID:** f-20260914-30 · **Status:** open · **Area:** native-fs · **Root:** - · **Entry:** build · **Blocked:** none
* **Where:** src-tauri/src/file_workspace.rs:1255-1262
* **Defect:** A workspace deletion that succeeds on disk returns success even when retiring the engine processes or executable registrations it owned fails; the failure is only logged, so engines or registrations may remain active with no error surfaced.
* **Why it matters:** `.claude/rules/async-resource-invariants.md`: every exit path is cleaned up or reported truthfully. Distinct from the inbox entry about workspace creation post-commit errors (filed the same day).
* **Open question:** After a committed delete, is a retirement failure returned as an applied-despite-error outcome the renderer acts on, retried, or recorded for startup reconciliation?
* **Found by:** `review-error-handling` cumulative diff review lens (Codex), 2026-09-14, confidence 98, during the `f-20260830-06` slice-1 build run (range `950f2e1d..16476781`). Pre-existing (originating commit `dc6b7841`), outside that run's area, so deferred; not reproduced in that run.

The `Where` line is historical. The live swallow is named in Traced premises. This block stays verbatim across rounds.

## Threat model and non-goals

The actor is the local user deleting a workspace entry whose engine executable the supervisor cannot reap. The renderer is not treated as an adversary. A malicious engine that refuses to die stays inside the existing `kill_reap` bound (`d-20260901-18`). This plan adds no kill path, no retry, and no new process control.

Known limit, unchanged from a failed terminate elsewhere: the OS process may still be alive after the error returns; the session tombstone is set before the drain; the registry row is already gone or the blocking result is already `CommittedDurabilityUncertain`. Tombstones are in-memory, capped, and evict the oldest entry. They are not a startup record.

Non-goals: the trash and restore paths; a startup reconciliation store; a new error category; a new `DurabilityStage`; changing `retire_engine` or `retire_executables`; editing `error.rs`; database and puzzle removal (`f-20260917-08`, including `remove_database` and `remove_puzzle_database` gaining a retirement tail); restoring a registration after a failed reap.

## Approach

### Report a retirement failure after a committed workspace delete

Quotes the defect: a deletion that succeeds on disk must not return success when retiring the engine processes or executable registrations fails, and the failure must be surfaced rather than only logged.

Owner: `permanently_delete_entry` in `file_workspace.rs`. `retire_executables` is unchanged. After it returns:

* Blocking `Ok(())` and retirement `Err`: `log::warn!` with `diagnostic()` (the engine identity stays in the log), then `Err(PartialRemoval { removed_entries, cause })` where `cause` is that retirement error. Category `partial-removal`. The renderer already refreshes and shows the generic applied-despite-error confirmation. No new category, no new dialog, no production frontend change.
* Blocking `Ok(())` and retirement `Ok(())`: `Ok(())`. An empty executable list stays on this arm because `retire_executables` returns `Ok` immediately.
* Blocking `Err(kept)` and retirement `Err`: `log::warn!` with `diagnostic()`, return `kept` unchanged. This covers an existing walk `PartialRemoval` and `CommittedDurabilityUncertain`. Do not call `CommittedRemoval::finish` on `kept`.
* Blocking `Err(kept)` and retirement `Ok`: return `kept`.
